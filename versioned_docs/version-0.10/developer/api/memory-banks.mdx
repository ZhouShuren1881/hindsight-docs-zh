## 什么是记忆库？ {#what-is-a-memory-bank}

记忆库是一个完整且隔离的存储单元，其中包含：

- **记忆** — 从对话中保留的事实和信息
- **文档** — 为检索建立索引的文件和内容
- **实体** — 从记忆中提取的人物、地点、概念
- **关系** — 知识图中实体之间的连接
- **强制指令** — 智能体在反思操作中必须遵守的硬性规则

记忆库彼此完全隔离——存储在一个记忆库中的记忆对另一个记忆库不可见。

无需预先创建记忆库。首次使用时，Hindsight 会自动按默认设置创建。

只有写操作才会创建记忆库，例如存入记忆、更新其资料或更改其配置。**读取不存在的记忆库会返回 `404`**，因此拼错、已重命名或已删除的 `bank_id` 会被明确报告，而不会以空结果作答。这对监控记忆库很重要：对不存在的记忆库执行 `GET .../stats` 会明确失败，而不是返回一组看似健康、实际只是计数归零的空库指标。

:::tip 先决条件
请先完成[快速开始](./quickstart)，安装客户端并启动服务器。
:::

## 别名 {#aliases}

**别名**是记忆库额外接受的一个 ID。每个接受记忆库 ID 的端点也接受其别名，因此别名提供了访问同一记忆库的另一种方式，不会复制、移动或重复任何内容。

之所以提供别名，是因为记忆库 ID 是其所有数据的键。更改 ID 就意味着重写每一行数据，并让所有客户端同时切换（这需要停机，可使用 [`rename-bank`](/developer/admin-cli#rename-bank) 完成）。别名允许分阶段迁移：先添加新 ID，在两个 ID 都可用期间逐批迁移客户端，等不再有请求使用旧 ID 后再结束迁移。

```
POST   /v1/default/banks/{bank_id}/aliases             {"alias": "new-id"}
GET    /v1/default/banks/{bank_id}/aliases
PATCH  /v1/default/banks/{bank_id}/aliases/{alias}     {"primary": true}
DELETE /v1/default/banks/{bank_id}/aliases/{alias}
```

### 在别名下显示记忆库 {#showing-a-bank-under-an-alias}

客户端完成迁移后，控制平面可以用新 ID（而不是创建记忆库时使用的 ID）显示该库。将 `PATCH` 请求中的 `primary` 设为 `true` 可提升别名；设为 `false` 则让控制平面恢复显示记忆库自身的 ID，但不会删除别名。

这项设置**只影响显示**。`bank_id` 仍是记忆库的身份标识：授权、计量、导出和审计日志仍使用它，所有响应也都会报告它。控制平面会同时显示真实 ID 和别名，以免混淆。

- **可选，没有默认值。** 记忆库自己的 ID 不是别名，因此通常不会以别名显示。
- **最多一个。** 提升一个别名时，会在同一事务中取消此前显示的别名。
- **别名删除后，主显示设置也随之失效。** 删除已提升的别名后，控制平面会恢复显示记忆库自身的 ID。

**需要了解：**

- **一个记忆库可以有多个别名**，因此可以同时逐步淘汰多个旧 ID。
- **记忆库 ID 和别名在所有记忆库之间必须唯一。** 如果添加的名称已被某个记忆库或其他别名占用，请求会返回 `409`，因此一个别名不可能指向两个记忆库。
- **别名不会取代记忆库自身的 ID。** 真实 ID 始终有效，所有响应（包括通过别名发送的请求所获响应）都会报告该 ID。无法删除记忆库的真实 ID；如需更改它，请使用 `rename-bank`。
- **删除别名只会关闭这条访问路径。** 记忆库及其记忆不会受影响；仍使用已删除别名的客户端会收到与该别名从未存在时相同的结果。
- **删除记忆库会移除其别名**，释放这些名称以供重复使用。
- **导出、导入或克隆不会携带别名。** 别名描述的是在*当前部署*中哪些 ID 可以访问某个记忆库，因此副本不会继承别名；需要时请在目标库上自行添加。
- **更改需要几秒钟才能传播到所有 API 副本。** 参见 [`HINDSIGHT_API_BANK_ALIAS_CACHE_TTL_SECONDS`](/developer/configuration)。

## 记忆库配置 {#bank-configuration}

每个记忆库都可以针对不同操作单独配置。可以通过[记忆库配置 API](#updating-configuration)、[控制平面界面](/)或[服务器级环境变量](/developer/configuration)设置配置。

### retain_mission {#retain-configuration}

用通俗语言说明记忆库在提取过程中应关注什么。任务说明会与内置规则一同注入提取提示，用来引导关注重点，但不会取代提取逻辑。

```
e.g. Always include technical decisions, API design choices, and architectural trade-offs.
     Ignore meeting logistics, greetings, and social exchanges.
```

可与任何提取模式配合使用。留空则采用通用提取方式。

### retain_extraction_mode {#retain_extraction_mode}

控制事实提取的详细程度：

|模式|说明|
|------|-------------|
|`concise` *（默认）*|选择性提取，只保留值得长期记忆的事实|
|`verbose`|每条事实提取更多细节；速度较慢且消耗更多 token|
|`custom`|通过 `retain_custom_instructions` 编写自己的提取规则|
|`verbatim`|将每个文本分块的原文作为一条记忆存储；LLM 仍会提取实体、日期等元数据|
|`chunks`|不调用 LLM，将每个文本分块直接存为一条记忆；只有调用方提供的实体可用|

### retain_custom_instructions {#retain_custom_instructions}

仅当 `retain_extraction_mode` 为 `custom` 时生效。此设置会用你提供的指令完全替换内置提取规则。

### retain_chunk_size {#retain_chunk_size}

为提取事实而拆分内容时，每个文本分块允许的最大字符数。分块越大，LLM 调用次数越少，但长输入的提取质量可能下降；分块越小，内容粒度越细，但调用次数会增加。

默认：`3000`

### retain_structured_chunk_size {#retain_structured_chunk_size}

当单行 JSONL 记录或单轮对话超过 `retain_chunk_size` 时，仍保持完整的最大字符数。未设置时，上限与 `retain_chunk_size` 完全相同。对于拆开单条记录会丢失有用上下文的结构化日志或聊天记录，可以将此值设得更大。

默认：未设置，此时使用 `retain_chunk_size` 的值

参见[Retain 配置](/developer/configuration#retain)，了解环境变量名称和默认值。

### entity_labels {#entity-labels}

定义一套受控的 `key:value` 分类标签，在存入时提取并存储为实体。标签会成为实体，因此会自动在知识图中关联记忆（例如，两条带有 `pedagogy:scaffolding` 的记忆会彼此关联），并改善语义检索和 BM25 检索。若某个组设置了 `tag: true`，还可以通过标准 `tags` / `tags_match` API 筛选记忆。

`entity_labels` 中的每个条目都是一个**标签组**，代表一个分类维度：

```json
{
  "entity_labels": [
    {
      "key": "engagement",
      "description": "Student engagement level during the session",
      "type": "value",
      "optional": true,
      "values": [
        { "value": "active",  "description": "Student is actively participating" },
        { "value": "passive", "description": "Student is listening but not participating" }
      ]
    },
    {
      "key": "pedagogy",
      "description": "Teaching strategies used",
      "type": "multi-values",
      "values": [
        { "value": "scaffolding",          "description": "Breaking complex tasks into smaller steps" },
        { "value": "direct_instruction",   "description": "Explicit explanation by the teacher" },
        { "value": "socratic_questioning", "description": "Guiding through questions rather than answers" }
      ]
    }
  ]
}
```

|字段|默认值|说明|
|-------|---------|-------------|
|`key`|—|标签组标识符。它会成为 `key:value` 实体的前缀；对于 `"map"` 类型，则成为 `key:field:value` 的前缀。|
|`description`|`""`|提供给 LLM，用于指导标签分配。|
|`type`|`"value"`|`"value"`：选择一个枚举值；`"multi-values"`：选择多个值；`"text"`：自由文本字符串；`"multi-text"`：任意数量的自由文本字符串；`"map"`：包含命名字段的结构化组。|
|`values`|`[]`|`"value"` 和 `"multi-values"` 类型的允许值。对于 `"text"`、`"multi-text"` 和 `"map"` 类型会被忽略。|
|`fields`|`{}`|`"map"` 类型的字段定义。每个字段都带有自己的类型（`"text"`、`"multi-text"`、`"value"`、`"multi-values"` 或嵌套的 `"map"`）。对非 map 类型会被忽略。|
|`optional`|`true`|为 `true` 时，若标签不适用，LLM 可以跳过它；为 `false` 时，LLM 必须始终为标签赋值。对 `"multi-values"` 和 `"multi-text"` 组无效，因为这两类组始终可选。|
|`tag`|`false`|为 `true` 时，提取出的 `key:value` 标签也会写入记忆单元的 tags 字段，因此可在 Recall / Reflect 中通过 `tags` / `tags_match` 筛选。|

**枚举组**（`type: "value"` 或 `type: "multi-values"`）：LLM 从预定义的 `values` 列表中选择；列表之外的值会被直接丢弃。这样可以保持词汇稳定，并使图中的关联更准确。当一条事实可能同时属于多个值时，使用 `"multi-values"`。

**自由文本组**（`type: "text"`）：LLM 可以写入任意字符串。可通过 `description` 字段提供示例和指导。由于模型可能在不同会话中用不同说法表达同一概念，这类组在图中的聚类不如枚举组可靠。

```json
{
  "key": "topic",
  "description": "Specific subject being discussed. Examples: algebra, quadratic equations, geometry.",
  "type": "text",
  "optional": true,
  "values": []
}
```

**开放词汇组**（`type: "multi-text"`）：与 `"text"` 类似，但 LLM 会写入字符串*列表*，因此一条事实可以携带多个未在记忆库配置中预先枚举的值。适用于只有内容本身才提供相关值的情况，例如某个对象的所有名称（规范名称、缩写、首字母缩略词和其他拼写）、事实引用的工单编号、产品代码或 SKU。每个值都会成为独立的 `key:value` 实体；若设置 `tag: true`，每个值也会写成标签。这样，记忆库便可从内容中推导分类，并在后续召回时据此筛选，无需调用方提供词汇表。

```json
{
  "key": "name",
  "description": "Every name the subject of this fact is known by — canonical name plus abbreviations, acronyms, short forms and alternative spellings.",
  "type": "multi-text",
  "tag": true
}
```

存入 *“We deploy services to a Kubernetes cluster on EKS — the team usually just says k8s, or kube”* 后，会生成实体和标签 `name:kubernetes`、`name:k8s`、`name:kube`，因此 `{"tags": ["name:k8s"], "tags_match": "any_strict"}` 可以找到这条事实。`"text"` 组则只能保留这三个名称中的一个。

**映射组**（`type: "map"`）：定义包含命名字段的结构化实体类型。每个字段本身也带有类型（`"text"`、`"multi-text"`、`"value"`、`"multi-values"` 或嵌套的 `"map"`），因此可以描述由姓名、角色和组织等信息构成的丰富实体。提取出的每个字段都会存储为扁平的 `key:field:value` 实体字符串（例如 `person:name:Alice`），复用现有实体存储，无需更改架构。因此，映射字段与单值标签一样参与知识图和检索。

```json
{
  "key": "person",
  "description": "A person mentioned in the text",
  "type": "map",
  "fields": {
    "name":         { "type": "text", "description": "Full name of the person" },
    "role":         { "type": "text", "description": "Job title or role" },
    "organization": { "type": "text", "description": "Company or organization" }
  }
}
```

**标签实体的解析方式。** 普通实体采用模糊解析，因此相近的人名变体（例如 “Alice” 和 “Alice Chen”）会合并。标签实体则不同：其规范名称由用户定义，所以两个外观相似的值（`use:use-001` 和 `use:use-002`）必须保持区分。标签实体只通过**精确匹配**解析，并以 `entity_kind = "label"` 存储，因此完全不会参与模糊名称匹配。即使自由文本标签组累积了数千个相似值，也不会拖慢记忆库中普通实体的解析。实体首次存储时即确定分类；之后删除标签组也不会重新分类已有实体。

### entities_allow_free_form {#entities_allow_free_form}

默认情况下，除常规命名实体（人物、地点、概念）外，也会提取实体标签。将此项设为 `false` 可禁用自由形式实体提取，只存储标签实体：

```json
{
  "entity_labels": [...],
  "entities_allow_free_form": false
}
```

### enable_observations {#observations-configuration}

启用或停用观测整合。设为 `false` 时，此记忆库不会运行自动或手动整合。服务器启用观测功能时，默认值为 `true`。

### enable_auto_consolidation {#enable_auto_consolidation}

控制存入、删除和更新操作后是否自动运行整合。设为 `false` 时，只有通过[整合端点](/developer/observations#trigger-consolidation)明确触发，才会运行整合。默认值为 `true`。

当你需要完全控制整合时机时，这项设置会很有用。例如，可以先批量存入多条记忆，再统一整合；也可以针对特定范围运行[定向整合](/developer/observations#targeted-consolidation)。

### observations_mission {#observations_mission}

定义此记忆库应综合生成哪些持久观测。此设置会完全替换内置整合规则；留空则使用服务器默认值。

```
e.g. Observations are stable facts about people and projects.
     Always include preferences, skills, and recurring patterns.
     Ignore one-off events and ephemeral state.
```

### consolidation_llm_batch_size {#consolidation_llm_batch_size}

单次整合调用中发送给 LLM 的事实数量。数值越大，LLM 调用越少、吞吐量越高，但提示也会更长。设为 `1` 可禁用批处理。留空则使用服务器默认值（`8`）。

### consolidation_source_facts_max_tokens {#consolidation_source_facts_max_tokens}

整合提示中随观测一同提供的来源事实总 token 预算。来源事实为 LLM 提供证据，使其能够将新事实与现有观测进行比较。`-1` 表示不设上限。留空则使用服务器默认值（`-1`）。

### consolidation_source_facts_max_tokens_per_observation {#consolidation_source_facts_max_tokens_per_observation}

整合提示中每条观测的来源事实 token 上限。每条观测都会单独受此上限约束，避免某条含有大量来源事实的观测耗尽全部预算。`-1` 表示不设上限。留空则使用服务器默认值（`256`）。

参见[观测配置](/developer/configuration#observations)，了解环境变量名称和默认值。

### reflect_mission {#reflect_mission}

```

     Always ground answers in documented decisions and rationale.
     Ignore speculation. Be direct and precise.
```

|`1`|疏离——侧重事实和逻辑|

### mcp_enabled_tools {#mcp_enabled_tools}

此记忆库允许使用的 MCP 工具名称清单。设置后，只能调用清单中的工具；调用未列出的工具会返回错误（为兼容协议，这些工具仍会出现在 MCP 工具列表中）。设为 `null` 或省略此项可允许使用所有工具。

```json
["recall", "reflect"]
```

可用工具名称：`retain`，`recall`，`reflect`，`list_banks`，`create_bank`，`list_mental_models`，`get_mental_model`，`create_mental_model`，`update_mental_model`，`delete_mental_model`，`refresh_mental_model`，`list_directives`，`create_directive`，`delete_directive`，`list_memories`，`get_memory`，`list_documents`，`get_document`，`delete_document`，`list_operations`，`get_operation`，`cancel_operation`，`list_tags`，`get_bank`，`get_bank_stats`，`update_bank`，`delete_bank`，`clear_memories`，`get_knowledge_base_tree`，`search_knowledge_base`，`get_knowledge_page`，`create_knowledge_folder`，`create_knowledge_page`，`update_knowledge_node`，`delete_knowledge_node`。

### llm_gemini_safety_settings {#llm_gemini_safety_settings}

控制 Gemini 和 VertexAI 提供商的内容过滤阈值。接受符合 [Google AI 安全设置格式](https://ai.google.dev/api/generate-content#v1beta.SafetySetting)的安全设置对象列表。为 `null`（默认值）时，使用 Gemini 内置的安全默认值。

```json
[
  {"category": "HARM_CATEGORY_HARASSMENT", "threshold": "BLOCK_NONE"},
  {"category": "HARM_CATEGORY_HATE_SPEECH", "threshold": "BLOCK_NONE"}
]
```

仅当 `HINDSIGHT_API_LLM_PROVIDER` 为 `gemini` 或 `vertexai` 时适用。

### recall_budget_function {#recall-budget-configuration}

选择 [`recall` 请求中的 `budget` 参数](./recall)（`low` / `mid` / `high`）如何映射为各检索方法（语义、BM25、图和时间检索）使用的内部整数 `thinking_budget`。支持两种映射函数：

|函数|行为|
|----------|-----------|
|`fixed` *（默认）*|`thinking_budget = recall_budget_fixed_<level>`，不受 `max_tokens` 影响。保留旧版行为。|
|`adaptive`|`thinking_budget = round(max_tokens * recall_budget_adaptive_<level>)`，并限制在 `[recall_budget_min, recall_budget_max]` 范围内。检索范围会随请求的输出大小调整。|

```json
{
  "recall_budget_function": "adaptive",
  "recall_budget_adaptive_low": 0.05,
  "recall_budget_adaptive_mid": 0.1,
  "recall_budget_adaptive_high": 0.3,
  "recall_budget_min": 30,
  "recall_budget_max": 1500
}
```

### recall_budget_fixed_low / recall_budget_fixed_mid / recall_budget_fixed_high {#recall_budget_fixed_low--recall_budget_fixed_mid--recall_budget_fixed_high}

当 `recall_budget_function` 为 `fixed`（默认值）时，这些正整数会直接作为每种方法在相应 `budget` 级别下的检索上限。默认值为 `100` / `300` / `1000`，与旧版硬编码映射完全一致。

### recall_budget_adaptive_low / recall_budget_adaptive_mid / recall_budget_adaptive_high {#recall_budget_adaptive_low--recall_budget_adaptive_mid--recall_budget_adaptive_high}

当 `recall_budget_function` 为 `adaptive` 时，这些正比例值会乘以请求的 `max_tokens`，得出每种方法的检索上限。默认值为 `0.025` / `0.075` / `0.25`，选择这些值是为了让 `max_tokens = 4096` 时的结果大致匹配固定模式的默认值。

### recall_budget_min / recall_budget_max {#recall_budget_min--recall_budget_max}

对自适应函数计算结果（比例乘法之后）应用的下限和上限。两者都必须是正整数，且 `min ≤ max`。默认值为 `20` / `2000`。

参见[Recall 预算映射](/developer/configuration#recall-budget-mapping)，了解环境变量名称和全部默认值。

### memory_defense {#memory_defense}

每个记忆库的 Memory Defense 策略。默认未设置（此记忆库禁用 Memory Defense）。

|字段|类型|默认值|说明|
|---|---|---|---|
|`enabled`|bool|`false`|主开关。|
|`default_action`|`allow`\|`redact`\|`quarantine`\|`block`|`allow`|没有规则匹配时的后备操作。|
|`protected_tag_namespaces`|`list[str]`|`[]`|写入时若标签属于这些命名空间（`ns:*`），则交由 `protected_key` 检测器处理。|
|`immutable_tag_namespaces`|`list[str]`|`[]`|对这些命名空间的写入被阻止。|
|`rules`|`list[Rule]`|`[]`|检测器到动作的映射（见下文）。|
|`detector_overrides`|`dict`|`{}`|针对各检测器的参数调整（例如 `size_anomaly.max_size`）。|

`Rule` 的结构：

|字段|必填|说明|
|---|---|---|
|`on`|是|检测器名称（`prompt_injection`、`sensitive_data`、`protected_key`、`immutable_key`、`size_anomaly`），或表示任意检测器的 `*`。|
|`action`|是|可选值：`allow`、`redact`、`quarantine`、`block`。|
|`min_severity`|否|触发规则所需的最低严重级别（`low`、`medium`、`high`、`critical`）。默认值为 `low`。|

通过 PATCH 提交的无效策略会被拒绝，并返回 HTTP 422。

使用示例请参见 [Memory Defense 指南](../memory-defense/index.md)。

对于 `retain`，添加 `"strategy": "<name>"` 可按记忆库中指定的某个存入策略呈现提示。省略此项时会采用记忆库的 `retain_default_strategy`，与未指定策略的实际存入请求行为完全相同，因此预览结果就是存入操作将发送的内容。响应会在 `strategy` 字段中返回实际采用的策略，并在 `strategies` 字段中列出该记忆库的策略名称，因此选择器无需再次调用 API。

预览接口不接受可覆盖值。它回答的是“这个记忆库会发送什么”；如果调用方可以传入自己的任务说明或示例文本，问题就变成了记忆库本身无法回答的内容。若要测试候选值，请先保存该值再查看预览；响应会指出哪些设置可以编辑。

响应会按发送顺序返回消息，并将每条消息拆分为构成它的各个文本块：

```json
{
  "messages": [
    {
      "role": "system",
      "blocks": [
        {
          "text": "Extract SIGNIFICANT facts from text...",
          "source": "builtin",
          "field": "retain_extraction_mode",
          "section": "",
          "heading": "Selectivity",
          "active": true,
          "value": "concise",
          "kind": "choice",
          "choices": ["concise", "verbose", "verbatim", "chunks", "custom"],
          "editable": true
        },
        {
          "text": "",
          "source": "config",
          "field": "retain_custom_instructions",
          "section": "",
          "heading": "",
          "active": false,
          "kind": "text",
          "editable": true
        }
      ]
    },
    { "role": "user", "blocks": [] }
  ],
  "response_schema": { "type": "object", "properties": { "facts": {} } }
}
```

- **`messages`** — 请求消息，先列出系统消息，内容与模型实际收到的完全相同。
- **`blocks`** — 消息中所有**启用的**文本块按原样拼接后，必须与消息文本完全一致：不丢失、不重复，也不改变顺序。`source` 表示每个块的来源：`config` 表示可更改的设置，`builtin` 表示 Hindsight 内置文本。操作收到的运行时数据不是文本块，而是消息中的一个空位，以 `«…»` 内联标出。
- **未启用的文本块**（`active: false`）不含文本。它们标明某项已关闭设置原本会出现的位置，因此即使尚未编写任务说明，也能看出它会插入在哪里。
- **识别文本块** — 按优先顺序使用适用的字段：`field` 是对应的配置字段；`section` 是没有单个字段归属的部分的 slug（`bank_identity`、`disposition`、`directives`）；`heading` 是提示文本自身带有的部分标题。这三项都是机器值。响应**不包含用于显示的标签文本**；文本块的名称，以及启用某个关闭设置后会产生什么效果，应由客户端使用其运行语言呈现。
- **`editable`** — 对于 `llm_output_language` 等服务器级字段为 `false`；这些字段会影响提示，但无法按记忆库覆盖。

**有意同时返回这两条消息。** 对 `retain` 和 `consolidation` 来说，任务说明放在*用户消息*中，而不是系统提示中：让所有记忆库共用相同的系统提示，可使提供商侧的单个提示缓存服务于所有记忆库，从而为高吞吐量摄取节省大量成本。只有 `reflect` 会将其任务说明放入系统提示。

### 没有提示时 {#when-there-is-no-prompt}

`chunks` 提取模式会逐字存储每个文本分块，且从不调用 LLM。由于没有提示可显示，`messages` 会为空，而 `skipped_reason` 会说明原因：

```json
{
  "operation": "retain",
  "messages": [],
  "skipped_reason": "Chunks mode stores each chunk verbatim as its own memory and never calls an LLM, ..."
}
```

在控制平面中，记忆库**配置**选项卡里的每个任务说明字段都有一个**预览提示**按钮；你可以在该处编辑各文本块对应的设置，并将更改保存到记忆库。

:::tip
[试运行提取](/developer/api/memories)是需要付费的对应功能：它会实际调用 LLM，展示相同配置最终*提取*出的内容。它以相同方式解析配置（包括策略），因此两者结果一致。控制平面会在同一个提示测试器中并列提供这两项功能。
:::

## 指令 {#directives}

强制指令是智能体在[反思](./reflect)操作中必须遵守的硬性规则。性格倾向会影响智能体*如何*推理，而强制指令是明确的要求，只要适用范围涵盖当前请求，就必须执行（参见[指令范围与标签](#directive-scope-and-tags)）。

:::info
强制指令只影响 `reflect` 操作。它们会被注入提示，智能体必须在所有响应中遵守。
:::

### 何时使用指令 {#when-to-use-directives}

使用指令来制定绝对不能违反的规则：

- **语言与风格约束**：“始终用正式英语回复”
- **隐私规则**：“切勿与第三方共享个人数据”
- **领域约束**：“偏好保守的投资建议”
- **行为约束**：“在提出主张时始终引用来源”

### 指令范围和标签 {#directive-scope-and-tags}

强制指令可以带有 `tags`。这些标签限定指令在 `reflect` 期间**何时**适用，其作用方式与记忆标签限定记忆的适用范围相似：

- **未带标签的强制指令始终适用**，每次 `reflect` 都会执行。
- **带标签的强制指令仅在 `reflect` 请求包含匹配标签时适用**（按请求的 `tags_match` 模式匹配）。不带标签的 `reflect` 请求只会应用未带标签的强制指令。

若要应用**所有**有效强制指令，不论其标签为何，请在 `reflect` 请求中设置 `apply_all_directives: true`。此项会忽略强制指令的标签范围，确保执行所有带标签和未带标签的强制指令。当运维人员用标签整理指令，但仍希望无标签反思请求执行全部指令时，这项设置很有用。

## 记忆库传输（导出和导入） {#bank-transfer-export--import}

在记忆库或实例之间迁移整个记忆库，也可以只迁移其中的文档，**无需再次运行 LLM**。流程使用一种归档格式和一对端点，并由三个标志决定传输哪些内容：

|标志|默认值|包含的内容|
|------|---------|-----------------|
|`include_data`|`true`|文档、原始文本分块、提取出的事实、整合后的观测、实体及其链接、附件**及附件字节**、已失效事实的人工维护归档、操作日志、维护队列，以及基于这些数据综合生成的心智模型、刷新历史和知识页树。|
|`include_bank_config`|`true`|记忆库的配置方式，包括配置覆盖项、强制指令和 Webhook。|
|`include_history`|`false`|`audit_log` 和 `llm_requests`。|

心智模型和知识页属于**数据**，而非配置。心智模型是对记忆库事实的解读，并通过 `based_on` 证据按 ID 引用这些事实；如果没有这些事实，恢复出来的综合内容就会失去依据。基于同样的原因，心智模型的刷新历史也会一并传输。

归档不会携带嵌入向量或数据库 ID：事实会使用*目标*记忆库的模型重新生成嵌入，实体也会在目标库中重新解析。因此，归档可以迁移到采用不同嵌入模型、向量扩展或文本搜索后端的实例。

Webhook 随 `include_bank_config` 一同传输。如果要复制的记忆库中的 Webhook 指向某个专属消费者，请在导出时设置 `include_bank_config=false`，或在副本上删除这些 Webhook。

在 `restore` 模式下，操作记录在 URL 中的记忆库 `{bank_id}` 上，因为目标库此时尚不存在。请轮询该记忆库的操作端点，以查看状态和各组件的计数。

恢复时，操作日志会作为历史记录带入，而不会作为待执行工作带入：导出时仍在进行的任务会留在原库中，因此副本不会重新运行原库中排队的存入操作，也不会再次触发其 Webhook。执行中的任务属于被导出的记忆库；克隆本身就在其中一项此类操作内运行，若一并复制这些任务，就会把克隆自身尚未完成的操作记录放进副本。

### 导入在 Hindsight 外部提取的事实 {#import-facts-extracted-outside-hindsight}

归档不一定必须由导出端点生成。如果你运行自己的提取管道，可以自行构建归档并以 `mode=merge` 导入：文本分块和事实会按提供的内容存储，不调用 LLM，也不会重新分块。同时，Hindsight 仍会重新生成事实的嵌入、根据记忆库解析实体、建立语义、时间、实体和因果链接；如果记忆库启用了相应功能，也会像存入操作一样触发 `retain.completed` Webhook 和自动整合。

归档是一个 ZIP 文件，其中包含 `manifest.json`，以及 `documents/` 目录下每份文档对应的一个 JSON 文件：

```text
import.zip
├── manifest.json            {"schema_version": 1, "source_bank_id": "external"}
└── documents/
    └── session-2026-09-22.json
```

文档文件：

```json
{
  "id": "session-2026-09-22",
  "original_text": "Full original session text...",
  "tags": ["source:pi"],
  "chunks": [{ "chunk_index": 0, "chunk_text": "Caller-defined source region..." }],
  "facts": [
    {
      "text": "The user prefers lightweight local speech recognition models.",
      "fact_type": "experience",
      "chunk_index": 0,
      "context": "Discussion of local speech recognition",
      "mentioned_at": "2026-09-22T18:34:00Z",
      "occurred_start": "2026-09-22T18:34:00Z",
      "occurred_end": "2026-09-22T18:34:00Z",
      "entities": ["Parakeet"],
      "metadata": { "source_turn": "143" },
      "tags": ["source:pi"],
      "observation_scopes": "shared",
      "causal_relations": []
    }
  ]
}
```

|事实字段|说明|
|------------|-------------|
|`text`|必填。将被召回的记忆内容。|
|`fact_type`|必填。`world` 或 `experience`。|
|`chunk_index`|可选。 中的块 `chunks`这个事实来自。|
|`context`、`metadata`、`tags`、`observation_scopes`|可选。含义与 Retain 项目中的相同，并按事实分别设置。|
|`mentioned_at`、`occurred_start`、`occurred_end`|可选的 ISO 8601 日期。若这些字段均未设置，则以导入时间作为事实日期。|
|`entities`|可选的实体名称，会根据记忆库中已有的实体进行解析。|
|`causal_relations`|可选。格式为 `[{"relation_type": "caused_by", "target_fact_index": N}]`，其中 `N` 是同一文档 `facts` 列表中另一条事实的位置。|

元数据和日期属于单条事实；文档本身不带元数据或时间戳。再次发送相同的文档 ID 时，按 `document_conflict` 处理（使用 `replace` 可覆盖现有文档）。

### 文档导出和导入（已取代） {#document-export--import-superseded}

下列端点仍按文档所述工作，且行为没有变化；新集成应使用上文的 `/transfer/export` 和 `/transfer/import`，它们传输相同的文档归档，并额外包含记忆库自身的配置。

在记忆库之间迁移文档及其已提取的事实，**无需再次运行 LLM**。这适用于测试不同的嵌入模型，或在不同记忆库/实例之间复制数据，避免为重新提取付费。归档包含文档、原始文本分块和提取出的事实（实体使用规范名称，包含因果链接），但**不包含嵌入向量或数据库 ID**。导入时，事实会使用*目标*记忆库的模型重新生成嵌入，实体和链接也会在目标库中重新计算，因此导入文档会与目标库已有内容整合。

### 观测 {#observations}

默认不包含整合后的观测；目标记忆库会在整合期间根据导入的事实重新生成观测。若要一并传输观测，请设置 `include_observations=true`：观测会直接恢复，无需调用 LLM；其来源引用会重新映射到导入的事实（这些事实会标记为已整合，因此目标库不会再次整合它们）。

由于一条观测可能由多个文档中的事实共同生成，`include_observations` 仅支持**整个记忆库导出**（省略 `document_id`）；与部分文档导出组合使用会返回 `400`。

:::warning 导入的观测会原样插入，不会合并
它们不会与目标记忆库中已有的观测合并或去重（整合过程会合并相关观测，但导入过程不会）。建议将观测导入空记忆库，或者省略 `include_observations`，让目标库自行整合导入的事实。
:::

### 启用/禁用 {#enabling--disabling}

这两个端点都受服务器级标志控制（默认值为 `true`）。禁用的端点会返回 `404`；`/version` 会在 `features.document_export_api` / `features.document_import_api` 中报告其状态（控制平面会相应隐藏按钮）。

|变量|控制的端点|
|----------|-------|
|`HINDSIGHT_API_ENABLE_DOCUMENT_EXPORT_API`|`POST …/document-transfer/export` 和 `GET …/files/download/{key}`|
|`HINDSIGHT_API_ENABLE_DOCUMENT_IMPORT_API`|`POST …/document-transfer`|

## 将记忆库迁移到新实例 {#migrating-a-bank-to-a-new-instance}

若要将记忆库迁移到使用不同**嵌入模型**、**向量扩展**或**文本搜索后端**的实例（已填充数据的记忆库无法原地更改这些设置），请导出整个记忆库并导入新实例。新实例会从存储文本重新生成所有嵌入和索引，**无需再次调用 LLM 提取事实**。归档会包含文档、事实、观测、记忆库配置、心智模型、强制指令和 Webhook，但不包含嵌入向量。

使用 `hindsight-admin export-bank` / `import-bank` 命令，并按照[管理 CLI → 将记忆库迁移到新实例](../admin-cli.md#migrating-a-bank-to-a-new-instance)中的蓝绿部署手册操作。
