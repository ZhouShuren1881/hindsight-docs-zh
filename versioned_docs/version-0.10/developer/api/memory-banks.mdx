## 什么是记忆库？ {#what-is-a-memory-bank}

A 记忆库是一个完整的、独立的存储单元，包含：

- **记忆** — 从对话中保留的事实和信息
- **文档** — 为检索建立索引的文件和内容
- **实体** — 从记忆中提取的人物、地点、概念
- **关系** — 知识图中实体之间的连接
- **指令** — 智能体在铰操作过程中必须遵循的硬性规则

记忆库彼此完全隔离——存储在一个记忆库中的记忆对另一个记忆库不可见。

您不需要预先创建记忆库。当您第一次使用时，Hindsight会自动以默认设置创建它。

仅*写道*创建一个记忆库——保留、更新其配置文件、更改其配置。 **阅读了
不存在的记忆库返回`404`**，所以拼写错误，重命名或删除`bank_id` 已报告
而不是用空结果来回答。如果您正在监控记忆库，这很重要：`GET .../stats`
在丢失的记忆库上失败很大，而不是返回看起来健康的归零计数器，
空记忆库。

:::tip 先决条件
确保您已完成[快速开始](./quickstart) 安装客户端并启动服务器。
:::

## 别名 {#aliases}

安**别名** 是记忆库回答的额外 ID。每个接受记忆库 ID 的端点也接受其别名，因此别名是进入同一记忆库的第二种方式 - 不会复制、移动或重复任何内容。

之所以存在，是因为记忆库的id是其所有数据的关键，因此更改它意味着重写每一行并立即切断所有客户端（即[`rename-bank`](/developer/admin-cli#rename-bank)，并且需要停机）。别名允许您分阶段进行相同的迁移：添加新 ID，在两个 ID 都工作时一次移动几个客户端，并在没有任何内容调用旧 ID 时停止。

```
POST   /v1/default/banks/{bank_id}/aliases             {"alias": "new-id"}
GET    /v1/default/banks/{bank_id}/aliases
PATCH  /v1/default/banks/{bank_id}/aliases/{alias}     {"primary": true}
DELETE /v1/default/banks/{bank_id}/aliases/{alias}
```

### 在别名下显示记忆库 {#showing-a-bank-under-an-alias}

一旦调用者移动，控制平面就可以在新的 ID（而不是创建它时使用的 ID）下显示记忆库。 `PATCH` 与 `primary: true` 提升别名； `primary: false` 返回记忆库以显示其自己的 id，而不删除别名。

这是**仅供显示**。 `bank_id` 保留记忆库的身份：授权、计量、导出和审核日志都继续使用它，这也是每个响应报告的内容。控制平面显示真实 ID 和别名，因此两者永远不会混淆。

- **可选，无默认值。** 记忆库自己的id不是别名，所以“未在别名下显示”是正常状态。
- **最多一个。** 在单个事务中提升别名会降低之前显示的别名。
- **它的有效期不会超过别名。** 删除升级后的别名将使记忆库恢复显示其自己的 ID。

**需要了解：**

- **一个记忆库可以有多个别名**，因此一次可以退役多个旧ID。
- **记忆库名称与别名共用唯一的命名空间。** 添加已命名记忆库或另一个别名的返回 `409`，所以一个别名永远不可能达到两个记忆库。
- **别名始终不会替换记忆库自身的 ID。** 真实 ID 持续有效，并且是每个响应报告的内容，包括对通过别名发出的请求的响应。删除记忆库的真实 ID 是不可能的 — 这就是 `rename-bank` 是为了。
- **删除别名只会关闭这一访问入口。** 记忆库及其记忆未受影响，仍然使用删除的 ID 的调用者将获得其存在之前所获得的完全相同的内容。
- **删除记忆库会移除其别名**，释放这些名称以供重复使用。
- **导出、导入或克隆不会携带别名。** 他们描述了哪些 id 到达了记忆库*这个*部署，因此副本不会继承它们 - 故意将它们添加到目标。
- **更改需要几秒钟才能传递到所有 API 副本。** 参见[`HINDSIGHT_API_BANK_ALIAS_CACHE_TTL_SECONDS`](/developer/configuration)。

## 记忆库配置 {#bank-configuration}

每个记忆库都可以根据操作独立配置。可以通过 设置配置 [记忆库配置 API](#updating-configuration)，[控制平面界面](/)，或[服务器级环境变量](/developer/configuration)。

### retain_mission {#retain-configuration}

用通俗易懂的语言描述这个记忆库在提取过程中应该注意什么。任务与内置规则一起注入提取提示中 - 它可以在不替换提取逻辑的情况下引导焦点。

```
例如：始终包含技术决策、API 设计选择和架构权衡。
     忽略会议安排、问候和社交交流。
```

可与任何提取模式一起使用。留空用于通用提取。

### retain_extraction_mode {#retainextractionmode}

控制如何积极地提取事实：

|模式|说明|
|------|-------------|
|`concise`*（默认）*|选择性 — 只选择值得长期记住的事实|
|`verbose`|提取每条事实的更多细节；速度较慢，消耗的 token 更多|
|`custom`|通过编写自己的提取规则 `retain_custom_instructions`|
|`verbatim`|将每个块的原始文本存储为一个记忆； LLM 提取元数据，例如实体和日期|
|`chunks`|将每个块存储为一个记忆，无需LLM调用；仅调用者提供的实体可用|

### retain_custom_instructions {#retaincustominstructions}

仅在 时有效 `retain_extraction_mode` 是 `custom`。用您自己的指令完全替换内置提取规则。

### retain_chunk_size {#retainchunksize}

分割内容进行事实提取时每个块的最大字符数。更大的块意味着更少的LLM调用，但可能会降低长输入的提取质量；较小的块可以提高粒度，但代价是需要更多的调用。

默认：`3000`

### retain_structured_chunk_size {#retainstructuredchunksize}

单个 JSONL 行或会话的最大字符数，当超过 时保持完整 `retain_chunk_size`。未设置时，限制恰好为 `retain_chunk_size`；为结构化日志或聊天记录设置较大的值，其中拆分单个记录会丢失有用的上下文。

默认：未设置，使用`retain_chunk_size`

参见[记忆存储配置](/developer/configuration#retain) 用于环境变量名称和默认值。

### entity_labels {#entity-labels}

定义的受控词汇 `key:value` 在记忆存储时提取并存储为实体的分类标签。因为标签成为实体，所以它们会自动链接知识图中的记忆（两个带有的记忆） `pedagogy:scaffolding` 链接），改善语义和BM25检索，并可选择通过标准过滤记忆 `tags`/`tags_match`API当 `tag: true` 设置在一个组上。

中的每个条目 `entity_labels` 是一个 **标签组** — 一个分类维度：

```json
{
  "entity_labels": [
    {
      "key": "engagement",
      "description": "课程期间学生的参与程度",
      "type": "value",
      "optional": true,
      "values": [
        { "value": "active",  "description": "学生积极参与" },
        { "value": "passive", "description": "学生在听但没有参与" }
      ]
    },
    {
      "key": "pedagogy",
      "description": "使用的教学策略",
      "type": "multi-values",
      "values": [
        { "value": "scaffolding",          "description": "将复杂的任务分解为更小的步骤" },
        { "value": "direct_instruction",   "description": "老师的明确讲解" },
        { "value": "socratic_questioning", "description": "通过问题而不是答案进行指导" }
      ]
    }
  ]
}
```

|领域|默认|说明|
|-------|---------|-------------|
|`key`|—|标签组标识符。成为中的前缀 `key:value`实体（或`key:field:value` `"map"`）。|
|`description`|`""`|显示给LLM 以指导标签分配。|
|`type`|`"value"`|`"value"` → 选择一个枚举值； `"multi-values"` → 选择多个； `"text"` → 自由格式字符串； `"multi-text"` → 任意数量的自由格式字符串； `"map"` → 具有命名字段的结构化组。|
|`values`|`[]`|的允许值 `"value"` 和 `"multi-values"`类型。忽略 `"text"`，`"multi-text"` 和 `"map"`。|
|`fields`|`{}`|的字段定义 `"map"`类型。每个字段都是自己键入的（`"text"`，`"multi-text"`，`"value"`，`"multi-values"`，或嵌套`"map"`）。对于非地图类型将被忽略。|
|`optional`|`true`|当`true`  如果不适用，LLM可以跳过标签。当`false` 如果不适用，LLM必须始终分配一个值。对没有影响 `"multi-values"`或`"multi-text"` 组（始终可选）。|
|`tag`|`false`|当`true`，提取`key:value` 标签也被写为记忆单元上的标签，可以通过进行过滤 `tags`/`tags_match` 在recall/reflect。|

**枚举标签组** (`type: "value"`或`type: "multi-values"`)：LLM从预定义的中选择 `values`列表；列表之外的任何内容都会被悄悄删除。词汇保持稳定，图表链接保持紧密。使用`"multi-values"` 当一个事实可以同时属于多个值时。

**自由文本标签组** (`type: "text"`)：LLM写入任何字符串。使用`description`字段提供示例和指导。图聚类的可靠性不如枚举组，因为模型可能会在会话中以不同的方式表达相同的概念。

```json
{
  "key": "topic",
  "description": "正在讨论的具体主题。例如：代数、二次方程、几何。",
  "type": "text",
  "optional": true,
  "values": []
}
```

**开放词汇标签组** (`type: "multi-text"`): 喜欢`"text"`，但是LLM写了一个*列表*字符串而不是一个——因此一个事实可以携带多个值，而没有人在记忆库配置中枚举这些值。当有趣的值仅存在于内容中时使用它：事物的名称（规范名称加上缩写、首字母缩略词和替代拼写）、事实引用的票证引用、产品代码或 SKU。每个值都有自己的`key:value`实体，并且带有`tag: true` 每个都被写成标签，因此记忆库可以从内容中导出分类，然后在记忆召回中对其进行过滤，而无需调用者提供词汇。

```json
{
  "key": "name",
  "description": "该事实的主题的每个名称都是已知的 - 规范名称加上缩写词、首字母缩略词、缩写形式和替代拼写。",
  "type": "multi-text",
  "tag": true
}
```

保留*“我们将服务部署到 EKS 上的Kubernetes 集群 - 团队通常只是说k8s，或 kube”*产生实体和标签 `name:kubernetes`，`name:k8s` 和 `name:kube`，所以`{"tags": ["name:k8s"], "tags_match": "any_strict"}`发现事实。 `"text"`组只保留三人中的一个。

**映射标签组** (`type: "map"`)：定义具有命名字段的结构化实体类型。每个字段都是自己键入的（`"text"`，`"multi-text"`，`"value"`，`"multi-values"`，或嵌套`"map"`），因此您可以描述丰富的实体，例如具有姓名、角色和组织的人。每个提取的字段都存储为一个平面 `key:field:value` 实体字符串（例如 `person:name:Alice`），重用现有的实体存储，无需更改架构 - 因此映射字段以与单值标签相同的方式参与知识图谱和检索。

```json
{
  "key": "person",
  "description": "文中提到的一个人",
  "type": "map",
  "fields": {
    "name":         { "type": "text", "description": "此人的全名" },
    "role":         { "type": "text", "description": "职位或角色" },
    "organization": { "type": "text", "description": "公司或组织" }
  }
}
```

**标签实体的解析方式。** 常规实体模糊解析，因此相近的名称变体合并（“Alice”/“Alice Chen”）。标签实体是不同的：它们的规范名称是用户定义的，因此两个看起来相似的值（`use:use-001` / `use:use-002`）必须保持独特。因此他们通过解决 **仅精确匹配** 并与 一起存储 `entity_kind = "label"`，这使它们完全脱离模糊名称匹配——积累数千个相似值的自由文本标签组不会减慢记忆库常规实体的分辨率。实体首次存储时分类是固定的；稍后删除标签组不会对其现有实体进行重新分类。

### entities_allow_free_form {#entitiesallowfreeform}

默认提取实体标签**同时** 常规命名实体（人、地点、概念）。设置为 `false` 禁用自由格式提取，以便仅存储标签实体：

```json
{
  "entity_labels": [...],
  "entities_allow_free_form": false
}
```

### enable_observations {#observations-configuration}

打开或关闭观察整合。当`false`，这个记忆库没有运行任何整合——既不是自动也不是手动。默认为 `true` 当服务器上启用观察功能时。

### enable_auto_consolidation {#enableautoconsolidation}

控制在记忆存储、删除和更新操作后是否自动运行整合。当`false`，整合仅在通过 显式触发时运行 [整合端点](/developer/observations#trigger-consolidation)。默认为 `true`。

当您想要完全控制整合时间时，这非常有用 - 例如，在合并或运行之前对许多保留进行批处理 [定向整合](/developer/observations#targeted-consolidation) 仅适用于特定范围。

### observations_mission {#observationsmission}

定义这个记忆库应该将什么合成为持久的观察。完全替换内置的集成规则 - 留空以使用服务器默认值。

```
例如：观察是关于人员与项目的稳定事实。
     始终包含偏好、技能与反复出现的模式。
     忽略一次性事件与临时状态。
```

### consolidation_llm_batch_size {#consolidationllmbatchsize}

发送到的事实数量  一次整合调用中的LLM。较高的值会减少LLM调用并提高吞吐量，但代价是更大的提示。设置为 `1` 禁用批处理。保留未设置以使用服务器默认值 (`8`）。

### consolidation_source_facts_max_tokens {#consolidationsourcefactsmaxtokens}

整合提示中的观察包含的源事实的总token 预算。来源事实给出了LLM将新事实与现有观察进行比较的证据。 `-1` = 无限。保留未设置以使用服务器默认值 (`-1`）。

### consolidation_source_facts_max_tokens_per_observation {#consolidationsourcefactsmaxtokensperobservation}

集成提示中源事实的每观察令牌上限。每个观察最多独立获取这么多源事实的标记，从而防止具有许多源事实的单个观察消耗整个预算。 `-1` = 无限。保留未设置以使用服务器默认值 (`256`）。

参见[观察配置](/developer/configuration#observations) 用于环境变量名称和默认值。

仅适用于 `HINDSIGHT_API_LLM_PROVIDER` 是 `gemini`或`vertexai`。

### recall_budget_function {#recall-budget-configuration}

选择[`recall` 请求的 `budget` 参数](./recall) (`low` / `mid` / `high`) 映射到内部 `thinking_budget` 每种检索方法使用的整数（语义、BM25，图表，时间）。支持两个功能：

|功能|行为|
|----------|-----------|
|`fixed`*（默认）*|`thinking_budget = recall_budget_fixed_<level>` — 独立于 `max_tokens`。保留遗留行为。|
|`adaptive`|`thinking_budget = round(max_tokens * recall_budget_adaptive_<level>)`，夹至 `[recall_budget_min, recall_budget_max]`。检索宽度与请求的输出大小成比例。|

```json
{
  "recall_budget_function": "adaptive",
  "recall_budget_adaptive_low": 0.05,
  "recall_budget_adaptive_mid": 0.1,
  "recall_budget_adaptive_high": 0.3,
  "recall_budget_min": 30,
  "recall_budget_max": 1500
}
```

### recall_budget_fixed_low / recall_budget_fixed_mid / recall_budget_fixed_high {#recallbudgetfixedlow--recallbudgetfixedmid--recallbudgetfixedhigh}

当`recall_budget_function` 是 `fixed`（默认），这些正整数直接用作每个的每个方法的检索限制 `budget`级别。默认值：`100` / `300` / `1000` — 完全匹配传统的硬编码映射。

### recall_budget_adaptive_low / recall_budget_adaptive_mid / recall_budget_adaptive_high {#recallbudgetadaptivelow--recallbudgetadaptivemid--recallbudgetadaptivehigh}

当`recall_budget_function` 是 `adaptive`，这些正比率乘以请求的 `max_tokens` 导出每个方法的检索限制。默认值：`0.025` / `0.075` / `0.25` — 选择大致匹配 处的固定默认值 `max_tokens = 4096`。

### recall_budget_min / recall_budget_max {#recallbudgetmin--recallbudgetmax}

应用于自适应函数结果的下限和上限（比率相乘之后）。两者都必须是正整数并且 `min ≤ max`。默认值：`20` / `2000`。

参见[记忆召回预算映射](/developer/configuration#recall-budget-mapping) 用于环境变量名称和完整默认值。

### memory_defense {#memory_defense}

每记忆库 记忆防御政策。默认为不存在（在此记忆库上禁用记忆防御）。

|领域|类型|默认|说明|
|---|---|---|---|
|`enabled`|bool|`false`|主开关。|
|`default_action`|`allow`\|`redact`\|`quarantine`\|`block`|`allow`|没有规则匹配时的后备操作。|
|`protected_tag_namespaces`|`list[str]`|`[]`|在这些命名空间中使用标签进行写入 (`ns:*`) 受 `protected_key`探测器。|
|`immutable_tag_namespaces`|`list[str]`|`[]`|对这些命名空间的写入被阻止。|
|`rules`|`list[Rule]`|`[]`|检测器到动作的映射（见下文）。|
|`detector_overrides`|`dict`|`{}`|每个探测器调整（例如 `size_anomaly.max_size`）。|

`Rule`形状：

|领域|必填|说明|
|---|---|---|
|`on`|是的|探测器名称 (`prompt_injection`，`sensitive_data`，`protected_key`，`immutable_key`，`size_anomaly`) 或 `*` 任何。|
|`action`|是的|之一 `allow`，`redact`，`quarantine`，`block`。|
|`min_severity`|没有|最低严重程度 (`low`，`medium`，`high`，`critical`) 用于触发规则。默认为 `low`。|

无效策略在 PATCH 上被拒绝，HTTP 422。

参见[记忆防护指南](../memory-defense/index.md) 使用示例。

没有刻意要覆盖的内容。预览回答“这个记忆库发送什么”；让调用者传递自己的任务或示例文本只会将该问题移至记忆库无法回答的地方。要尝试候选值，请将其保存并再次查看 - 响应会说明哪些设置是可编辑的。

响应按发送顺序携带消息，每个消息都分为构建它的块：

```json
{
  "messages": [
    {
      "role": "system",
      "blocks": [
        {
          "text": "从文本中提取重要事实...",
          "source": "builtin",
          "field": "retain_extraction_mode",
          "section": "",
          "heading": "Selectivity",
          "active": true,
          "value": "concise",
          "kind": "choice",
          "choices": ["concise", "verbose", "verbatim", "chunks", "custom"],
          "editable": true
        },
        {
          "text": "",
          "source": "config",
          "field": "retain_custom_instructions",
          "section": "",
          "heading": "",
          "active": false,
          "kind": "text",
          "editable": true
        }
      ]
    },
    { "role": "user", "blocks": [] }
  ],
  "response_schema": { "type": "object", "properties": { "facts": {} } }
}
```

- **`messages`** — 请求，系统优先，与模型收到的请求完全相同。
- **`blocks`** — **活跃** 消息块准确地连接回其文本：没有任何丢失、重复或重新排序。 `source` 说明了每个的产生原因：`config` 可以更改的设置，`builtin` 为Hindsight自己的措辞。给定操作的运行时数据不是一个块——它是文本中的一个洞，用 内联标记 `«…»`。
- **未激活的记忆块** (`active: false`) 没有文字。它们标记了一个已关闭的设置，此时它*会*土地 — 因此您尚未编写的任务仍然可以看到它要去的地方。
- **标识记忆块** — 以其中适用者为准，按顺序：`field`是后面的config字段； `section` 是一个没有单个字段拥有的部分的 slug (`bank_identity`，`disposition`，`directives`); `heading` 是提示文本本身携带的部分标题。这三个都是机器值。响应带有**不生成展示副本** — 一个块的名称以及打开一个关闭的块会做什么，是由客户端用它运行时使用的语言说出的。
- **`editable`** — 对于服务器级字段（例如 ）为 false `llm_output_language`，它塑造提示但不能被每个记忆库覆盖。

**同时返回两条消息是有意为之。** 对于`retain` 和 `consolidation` 任务在*用户*消息，而不是系统提示：保持每个记忆库的系统提示相同，可以让一个提供者端提示缓存为所有记忆库提供服务，这对于大批量摄取来说可以节省大量成本。只有`reflect`将其任务放入系统提示中。

### 没有提示时 {#when-there-is-no-prompt}

`chunks` 提取模式逐字存储每个块并且从不调用LLM。没有提示显示，所以`messages` 为空且 `skipped_reason`解释原因：

```json
{
  "operation": "retain",
  "messages": [],
  "skipped_reason": "块模式将每个块逐字存储为自己的记忆，并且从不调用LLM，..."
}
```

控制平面中，记忆库上的每个任务字段**配置** 选项卡有一个 **预览提示词**按钮，可以在那里编辑每个块的设置并保存到记忆库。

:::tip [试运行提取](/developer/api/memories) 是付费对应物：它花费真实的LLM调用以显示相同的配置实际上是什么*摘录*。它以相同的方式解析其配置，包括策略，因此两者一致。控制平面将它们在一个提示测试器中配对。
:::

## 指令 {#directives}

指令是智能体在期间必须遵循的硬性规则 [反思](./reflect) 操作。与影响的性格特征不同*如何*智能体原因，指令是明确的指令，只要它们在范围内就会强制执行（参见[指令作用域与标签](#directive-scope-and-tags)）。

:::info 指令仅影响`reflect`操作。它们被注入到提示中，并且智能体需要在所有响应中遵守它们。
:::

### 何时使用指令 {#when-to-use-directives}

使用指令来制定绝对不能违反的规则：

- **语言与风格约束**：“始终用正式英语回复”
- **隐私规则**：“切勿与第三方共享个人数据”
- **领域约束**：“偏好保守的投资建议”
- **行为约束**：“在提出主张时始终引用来源”

### 指令范围和标签 {#directive-scope-and-tags}

指令可携带`tags`，以及那些标签范围**何时** 在期间应用指令 `reflect` — 镜像标签如何影响记忆：

- **无标签的指令始终适用**，每个`reflect`。
- **带标签的指令仅在 `reflect` 请求包含匹配标签时适用**（使用请求的`tags_match`模式）。 `reflect` 不带标签的调用仅适用于未标记的指令。

申请**每一个** 主动指令，无论标签如何，设置 `apply_all_directives: true` `reflect`请求。这会忽略指令的标签范围（强制执行未标记和已标记的指令），并且当操作员保留组织的标记指令但希望所有指令都在无标签的反思请求上强制执行时非常有用。

## 记忆库传输（导出和导入） {#bank-transfer-export--import}

在记忆库和实例之间移动记忆库（或只是其文档）**无需重新运行 LLM**。一种存档格式、一对端点和三个决定传输内容的标志：

|旗帜|默认|它携带什么|
|------|---------|-----------------|
|`include_data`|`true`|文档、原始块、提取的事实、综合观察、实体和链接、附件 **及其字节内容**，无效事实的管理档案、操作日志、维护队列——以及记忆库从所有这些中合成的内容：心智模型、它们的刷新历史以及它们之上的知识页面树。|
|`include_bank_config`|`true`|记忆库是如何设置的：它的配置覆盖、指令和 webhooks。|
|`include_history`|`false`|`audit_log` 和 `llm_requests`。|

心智模型及知识页计为**数据**，不是配置。心智模型是对记忆库事实的阅读，并在其中通过 id 引用它们 `based_on`证据，因此如果没有证据就携带它，就会恢复一个基础为零的综合。出于同样的原因，他们的刷新历史也随之而来。

嵌入和数据库 ID 永远不会被携带：事实使用 *目标* 记忆库的模型重新嵌入，并且实体根据它重新解析，因此存档干净地移动到配置有不同嵌入模型、向量扩展或文本搜索后端的实例。

Webhooks 与 一起旅行 `include_bank_config`。当复制 webhook 指向每个记忆库使用者的记忆库时，使用 导出 `include_bank_config=false`，或在副本上删除它们。

恢复将操作日志作为历史记录，而不是作为工作：导出记忆库时仍在运行的任何内容都会被留下，因此复制的记忆库永远不会重新运行原始的排队保留或重新触发其 Webhook。飞行中的工作属于导出的记忆库——克隆体运行*里面*这样的操作，因此携带它们会将克隆体自己未完成的记录放入副本中。

### 导入在 Hindsight 外部提取的事实 {#import-facts-extracted-outside-hindsight}

存档不一定来自导出。如果您运行自己的提取管道，请自行构建存档并使用 导入 `mode=merge`：你的块和事实按照给定的方式存储 - 不LLM调用，无需重新分块 — whileHindsight仍然重新嵌入事实，根据记忆库解析其实体，构建语义、时间、实体和因果链接，并且 - 就像记忆存储一样 - 激发 `retain.completed` webhook 和自动集成（当记忆库启用时）。

存档是带有 的 ZIP `manifest.json` 和一个JSON下每个文档的文件 `documents/`：

```text
import.zip
├── manifest.json            {"schema_version": 1, "source_bank_id": "external"}
└── documents/
    └── session-2026-09-22.json
```

文档文件：

```json
{
  "id": "session-2026-09-22",
  "original_text": "完整的原始会话文本...",
  "tags": ["source:pi"],
  "chunks": [{ "chunk_index": 0, "chunk_text": "调用者定义的源区域..." }],
  "facts": [
    {
      "text": "用户更喜欢轻量级的本地语音识别模型。",
      "fact_type": "experience",
      "chunk_index": 0,
      "context": "本地语音识别讨论",
      "mentioned_at": "2026-09-22T18:34:00Z",
      "occurred_start": "2026-09-22T18:34:00Z",
      "occurred_end": "2026-09-22T18:34:00Z",
      "entities": ["Parakeet"],
      "metadata": { "source_turn": "143" },
      "tags": ["source:pi"],
      "observation_scopes": "shared",
      "causal_relations": []
    }
  ]
}
```

|事实字段|说明|
|------------|-------------|
|`text`|必填。记忆，就像会被回忆起来一样。|
|`fact_type`|必填。 `world`或`experience`。|
|`chunk_index`|可选。 中的块 `chunks`这个事实来自。|
|`context`，`metadata`，`tags`，`observation_scopes`|可选。与记忆存储项目的含义相同，按事实设置。|
|`mentioned_at`，`occurred_start`，`occurred_end`|可选 ISO 8601 日期。如果没有设置任何一个，则事实的日期是导入时的。|
|`entities`|可选实体名称，根据记忆库的现有实体进行解析。|
|`causal_relations`|​​ 可选。 `[{"relation_type": "caused_by", "target_fact_index": N}]`，其中 `N` 是同一文档中另一个事实的位置 `facts` 列表。|

元数据和日期基于每个事实；文档不携带自己的元数据或时间戳。重新发送文档id如下`document_conflict` (`replace`覆盖它）。

### 文档导出和导入（已取代） {#document-export--import-superseded}

下面的端点仍然完全按照记录工作并且没有改变；新的集成应该使用 上面的 `/transfer/export` 和 `/transfer/import`，带有相同的文档档案加上记忆库自己的配置。

在记忆库之间移动文档以及已从中提取的事实**无需重新运行 LLM**。对于测试不同的嵌入模型或在不同的嵌入模型之间复制数据很有用banks/instances无需支付重新提取费用。档案包含文档、原始块和提取的事实（按规范名称、因果关系列出的实体）——但是 **不包含嵌入向量或数据库 ID**。导入时，事实会重新嵌入*目标*记忆库的模型和entities/links会根据它重新计算，因此导入的文档会与已有的文档集成。

### 观察 {#observations}

综合观察被排除——目标记忆库在整合过程中从导入的事实中重新生成它们。通过`include_observations=true` 来携带它们：它们无需任何操作即可恢复LLM，它们的源引用重新映射到导入的事实（这些事实被标记为合并的，因此目标不会重新合并它们）。

因为观察可以从跨越多个文档的事实中得出，`include_observations` 仅在 上受支持 **全库导出**（省略`document_id`);将其与文档子集组合返回 `400`。

:::warning 导入的观察按原样插入 - 不合并
它们不会针对目标记忆库中已有的观察进行合并或重复数据删除（整合合并相关观察；导入不会）。更喜欢将观察导入到fresh/empty记忆库，或省略`include_observations`并让目标自己巩固导入的事实。
:::

### 启用/禁用 {#enabling--disabling}

两个端点都由服务器级标志进行门控（默认`true`）。禁用的端点返回 `404`，和`/version` 报告下的状态 `features.document_export_api` / `features.document_import_api`（控制平面相应地隐藏按钮）。

|变量|大门|
|----------|-------|
|`HINDSIGHT_API_ENABLE_DOCUMENT_EXPORT_API`|`POST …/document-transfer/export` 和 `GET …/files/download/{key}`|
|`HINDSIGHT_API_ENABLE_DOCUMENT_IMPORT_API`|`POST …/document-transfer`|

## 将记忆库迁移到新实例 {#migrating-a-bank-to-a-new-instance}

将记忆库移动到配置有不同的实例 **嵌入模型**，**向量扩展**，或**文本搜索后端** - 无法在填充的记忆库上进行更改 - 导出整个记忆库并将其导入到新实例中，其中每个嵌入和索引都是使用 从存储的文本中重新派生的 **无需 LLM 重新提取**。它携带文档、事实、观察、记忆库配置、心智模型、指令和网络钩子（从不嵌入）。

使用`hindsight-admin export-bank` / `import-bank` 命令并遵循 中的蓝绿色操作手册 **[管理 CLI → 将记忆库迁移到新实例](../admin-cli.md#migrating-a-bank-to-a-new-instance)**。
