# 召回记忆 {#recall-memories}

使用多策略召回，从记忆库中检索记忆。

调用 **记忆召回** 时，Hindsight 并行执行语义相似度、关键词（BM25）、图遍历和时间四种检索策略，再融合并重排序为统一的结果列表。响应包含结构化事实，而非原始文档。

## 参数 {#parameters}

### query

要搜索的自然语言问题或陈述，是唯一的必填字段。查询同时驱动四种检索策略：生成嵌入用于语义搜索、分词用于 BM25 关键词搜索、作为图遍历起点，并解析其中的时间表达。检索后，原始查询还会交给交叉编码器重排序模型，对每个候选项重新评分。超过 500 token 的查询会被拒绝。

### types

控制搜索的记忆事实类别。支持 `world`（客观事实）、`experience`（事件与对话）和 `observation`（由多条记忆整合得到、去重且有证据支持的认知）。省略时搜索全部三类。

每种类型独立执行完整的四策略检索流程，因此缩小 `types` 范围可同时减少结果数量和查询成本。

:::tip 关于观察
观察是由多个事实整合得到、去重且有证据支持的认知，包括偏好、反复出现的模式，以及记忆库积累的持久经验。每条观察都引用支持它的记忆并保留准确引文；新证据到来时逐步完善，而非直接覆盖。观察在 retain 操作后由后台自动创建和维护。
:::

### prefer_observations

观察由原始事实整合而成，同时召回 `observation`、`world` 和 `experience` 时，同一信息可能出现两次：一次作为原始事实，一次包含在观察中。`prefer_observations` 保留所有类型，但若结果中的观察由某条原始事实生成，就删除该原始事实，由观察替代。空出的名额会用排名靠后的结果补齐，不减少覆盖。

这样无需在“仅原始事实”（没有整合）和“仅观察”（整合可能尚未跟上最新存储）之间选择。该选项**默认关闭**，设为 `true` 启用。只有 `types` 同时包含 `observation` 和 `world`／`experience` 中至少一种时才生效。

### budget

控制检索深度和广度。支持 `low`、`mid`（默认）和 `high`。简单快速查询使用 `low`，日常查询使用平衡的 `mid`，需要间接关联或全面覆盖时使用 `high`。

### max_tokens

返回事实可共同占用的最大 token 数，默认 `4096`。仅计算事实的 `text`，不计元数据、标签、实体等字段。重排序后按相关性顺序选取事实，直到预算耗尽。某条事实超出剩余预算时会跳过，不会终止选择，后面更短的事实仍可返回。Hindsight 面向以 token 而非结果数量规划上下文的智能体，`max_tokens` 应设为希望分配给记忆的上下文预算。

:::note
查询匹配到内容时不会返回空列表：即使最高排名的事实也放不进预算，仍会完整返回并超出预算，而非在句中截断。空列表会被理解为“记忆库没有这种记忆”，截断的事实则可能表达原记忆从未作出的断言。唯一例外是 `max_tokens=0`，它明确表示“不返回事实”，可用于只请求分块。
:::

### query_timestamp

从用户视角表示提问时间的 ISO 8601 日期时间。提供后，它作为查询中相对时间表达和新鲜度评分的基准。例如查询为“上个月”，`query_timestamp` 为 `2023-05-30` 时，时间搜索窗口约为 2023 年 4 月，新鲜度加权以 2023 年 5 月 30 日为基准。省略时使用服务器当前时间。重放历史对话或构建需要固定时间基准的智能体时，此字段尤其重要。

### temporal_window

为时间搜索显式提供 `{ "start": ..., "end": ... }`，两者均为 ISO 8601 日期时间。若已明确时间区间，例如界面日期选择器的结果，或智能体已解析“上季度”，Hindsight 会直接使用边界，不再从查询文本提取日期。

```json
{ "query": "我们对价格作了什么决定", "temporal_window": { "start": "2023-04-01T00:00:00Z", "end": "2023-06-30T23:59:59Z" } }
```

**它影响排名，不执行筛选。** Hindsight 同时采用多种搜索方式，时间窗口只影响其中与时间相关的部分：窗口内的记忆更容易被找到且排名更高，其他内容仍正常搜索。因此窗口外的结果也会返回，不能用它将答案限制在某个时期。比较的是*记忆描述的事件日期*，而非存入记忆的日期。

边界包含在窗口内；没有时区的日期时间按 UTC 解释。关闭时间感知搜索的记忆库会忽略此窗口。`temporal_window` 仅替代日期提取，[`query_timestamp`](#query_timestamp) 仍是新鲜度评分的基准，两者可以一起使用。

### include

可选对象，控制主事实之外返回的补充数据。

#### chunks

启用后，响应包含提取各事实的原始来源文本分块。分块在 `max_tokens` 筛选前获取，因此 `max_tokens=0` 虽不返回事实，仍可返回分块。子选项 `max_tokens`（默认 `8192`）独立控制分块的总 token 预算，适合智能体需要事实周边原文的场景。

:::note
启用 `include_chunks` 后，先根据重排序结果中得分最高的条目获取分块，再进行 token 筛选。最后一个分块会截断而非丢弃，恰好适应预算；每个分块的 `truncated` 标志指示是否被截断。

使用标签筛选（`tags`、`tags_match`、`tag_groups`）时，分块所属**文档**的标签也必须满足条件。事实可能凭自身标签匹配，例如由[实体标签](./memory-banks#entity-labels)生成的 `kind:rule` 事实，但来源文档不匹配时，不应返回文档的其他文本。此时仍返回事实，不返回其分块。
:::

#### source_facts

启用且 `types` 包含 `observation` 时，每条观察都附带生成它的原始事实。来源事实位于顶层 `source_facts` 字典，以事实 ID 为键；观察的 `source_fact_ids` 列表用于关联。不同观察共享的事实会去重。子选项 `max_tokens`（默认 `4096`）限制来源事实总 token 预算。

:::note
预算按结果顺序使用，因此耗尽时，排名最低的结果先失去来源事实，最高排名的结果始终保留。`source_fact_ids` 仍列出全部来源，所以部分 ID 可能没有 `source_facts` 条目。如果原因是预算耗尽而非事实缺失，响应设置 `source_facts_truncated: true`。需要解析全部来源时，提高 `max_tokens` 或设为 `-1`。
:::

#### entities

默认启用，使每条事实包含相关实体的规范名称。设为 `null` 可跳过实体 JOIN 查询并减小响应。子选项 `max_tokens`（默认 `500`）是为未来实体数据预算预留的限制。

### tags

将召回限制在请求的标签范围内。`tags` 默认为 `null`，
`tags_match` 默认为 `any`。

`tags_match` 参数控制筛选逻辑：

| 模式 | 无标签记忆 | 匹配条件 |
|------|-------------------|-----------------|
| `any`（默认） | 包含 | 记忆具有指定标签中的**至少一个** |
| `any_strict` | 排除 | 记忆具有指定标签中的**至少一个** |
| `all` | 包含 | 记忆具有指定的**所有**标签 |
| `all_strict` | 排除 | 记忆具有指定的**所有**标签 |
| `exact` | 排除 | 记忆的标签集合与指定集合**完全一致** |

默认值与空筛选条件的行为如下：

| `tags` | `tags_match` | 可返回的记忆 |
|--------|--------------|-------------------|
| 省略、`null` 或 `[]` | 省略（`any`） | 所有有标签和无标签记忆 |
| 省略、`null` 或 `[]` | `any`、`all`、`any_strict` 或 `all_strict` | 所有有标签和无标签记忆；空标签列表表示不筛选 |
| 省略、`null` 或 `[]` | `exact` | 仅无标签／全局记忆 |
| 非空 | `any` 或 `all` | 匹配的有标签记忆，以及无标签／全局记忆 |
| 非空 | `any_strict` 或 `all_strict` | 仅匹配的有标签记忆 |
| 非空 | `exact` | 完整标签集合与 `tags` 完全相等的记忆 |

:::note MCP 的空范围行为
MCP `recall` 工具仅在存在 `tags` 时转发 `tags_match`。
通过 MCP 选择无标签／全局范围时，请同时传入 `tags: []` 和
`tags_match: "exact"`，不要省略 `tags`。
:::

适用于精确筛选 `GET /v1/default/banks/{bank_id}/observations/scopes` 返回的观察范围，例如 `["user:alice"]` 不应匹配范围为 `["user:alice", "project:x"]` 的观察。

:::tip 只筛选全局（无标签）观察

```json

```

:::

### tag_groups

`tag_groups` 是复合布尔标签筛选列表，顶层按 AND 组合。每组是递归布尔表达式：**叶节点** `{tags, match}`，或**复合节点** `{and: [...]}`、`{or: [...]}`、`{not: ...}`。

`tag_groups` 默认为 `null`。公开 REST 和 MCP 请求模型将
`tag_groups` 与 `tags` 视为互斥参数，
同时提供会被拒绝。复合筛选应单独使用 `tag_groups`，通常将
顶层 `tags_match` 保持为默认 `any`。每个叶节点具有自己的
`match`。例外是顶层 `tags_match: "exact"`：
完全匹配会赋予缺少平铺标签特殊含义，新增仅全局范围的约束，
再与复合表达式按 AND 组合。

#### 叶节点 {#leaf-node}

```json
{ "tags": ["step:5", "step:8"], "match": "any_strict" }
```

`match` 支持与 `tags_match` 相同的值：`any`、`all`、`any_strict`、`all_strict`、`exact`，默认 `any_strict`。

#### 模糊叶节点 {#fuzzy-leaves}

叶节点可设置 `resolve: "fuzzy"`（默认 `"exact"`），按三元组相似度而非字面值匹配记忆库标签，因此 `typsecript` 仍能找到带 `typescript` 标签的记忆：

```json
{ "tags": ["typsecript"], "match": "any_strict", "resolve": "fuzzy" }
```

每个标签会解析为相似度至少 0.45 的记忆库标签，叶节点再与这些标签精确匹配，因此 `resolve` 可与任何 `match` 模式组合。相似度对长度敏感：`kubernets` 可匹配 `kubernetes`，但短标签的三元组太少，无法承受一次编辑，`kakfa` 不匹配 `kafka`。没有解析结果的标签不会匹配任何记忆，筛选条件不会被丢弃。记忆库超过 5000 个不同标签，或 `resolve: "fuzzy"` 且 `match: "exact"` 的叶节点展开为超过 32 个候选范围时，返回 422。

#### 复合节点 {#compound-nodes}

```json
{ "and": [ <TagGroup>, <TagGroup>, ... ] }
{ "or":  [ <TagGroup>, <TagGroup>, ... ] }
{ "not": <TagGroup> }
```

#### 示例 {#examples}

**步骤筛选 AND 用户范围**：两个顶层分组按 AND 组合：

```json
{
  "tag_groups": [
    { "tags": ["step:5", "step:8", "step:12"], "match": "any_strict" },
    { "tags": ["user:ep_42"], "match": "all_strict" }
  ]
}
```

**AND 内嵌 OR**：必须匹配用户，并匹配步骤或优先级之一：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "or": [
        { "tags": ["step:5"], "match": "any_strict" },
        { "tags": ["priority:high"], "match": "all_strict" }
    ]}
  ]
}
```

**排除**：必须匹配用户，但排除已归档记忆：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "not": { "tags": ["archived"], "match": "any_strict" } }
  ]
}
```

### trace

设为 `true` 后，响应包含详细调试跟踪，涵盖查询嵌入、入口点、各策略检索结果、RRF 融合候选项、重排序结果、解析出的时间约束和各阶段耗时。不改变检索逻辑，适合解释某条记忆为何返回或未返回。

### min_scores

可选的各阶段最低分数对象，使用**包含边界**的比较（`>=`）。未设置的字段没有下限；完全省略 `min_scores`（默认）时不按分数筛选。四个字段作用于流程的**两个不同层级**，决定每个返回结果保证满足什么条件：

| 字段 | 层级 | 作用 | 每条结果都保证满足？ |
|---|---|---|---|
| `semantic` | 检索 | 最低向量相似度，进入**语义分支** SQL，在融合前排除弱向量匹配；覆盖本次请求的全局相似度下限 | 否 |
| `keyword` | 检索 | 最低关键词／全文（BM25）分数，进入**关键词分支** SQL，在融合前排除弱关键词匹配 | 否 |
| `reranker` | 查询后 | 对排序结果应用最低归一化交叉编码器分数 | 是 |
| `final` | 查询后 | 对排序结果应用最低最终排名分数 | 是 |

```json
{ "query": "...", "min_scores": { "reranker": 0.5 } }
```

#### 检索下限约束单个分支，不约束最终结果 {#retrieval-floors-constrain-one-arm-not-the-result}

Recall 使用[四个检索分支](#results)：语义、关键词、图和时间。任一分支找到的记忆都可进入响应。`semantic` 和 `keyword` 只在各自分支内裁剪，改变*候选项集合*及最终顺序，**并不是对每条返回结果的判断条件**：

- 仅由语义搜索找到的结果返回 `"keyword": null`，无论如何设置 `min_scores.keyword`。
- 仅由关键词搜索找到的结果返回 `"semantic": null`，无论如何设置 `min_scores.semantic`。
- 由图或时间分支找到的结果**两者都为空**，不受这两个下限影响。

因此，同时设置 `semantic` 和 `keyword` 不会将结果限制为同时满足两者的记忆。这是有意的：取交集会排除混合检索本就希望找到的强单分支匹配，例如与查询没有共同词语的改写，或嵌入得分较低的精确标识符 `amber-17`。

#### 需要在低置信度时不返回结果，使用 `reranker` 或 `final` {#for-abstention-use-reranker-or-final}

查询后下限在融合和重排序后应用于每条有分数的结果，因此返回结果都满足下限，没有结果满足时返回空列表。低置信度或无意义查询需要停止返回记忆时，应使用这些下限。但它们约束的是*综合*信号：`final` 结合 RRF 排名、交叉编码器相关性、新鲜度／时间和策略加权，`reranker` 取决于交叉编码器校准，均不等同于检索阶段阈值。

因为空出的名额**不会**补齐，设置下限可能使结果数量低于预算可容纳的数量。

**谨慎使用分数下限。** 重排序分数适合判断*顺序*，不适合作为*绝对*值。同一条明显相关的记忆，在一次查询中可能得分 `~0.001`，另一次却为 `~1.0`，固定阈值可能静默丢弃好结果。请先不设置 `min_scores` 进行召回，观察 [`scores`](#scores)，再根据实际分数校准阈值。使用固定阈值前，请阅读 [`scores`](#scores) 关于相对尺度的说明。

**TypeSafe 重排序模型不支持此下限。** TypeSafe 一次对整个候选池排序，返回排名位置而非相关性分数；每次查询的首条记忆都是 `1.0`，因此 `reranker` 下限只会保留固定比例的结果。配置 TypeSafe 时，`min_scores.reranker` 返回 HTTP 400；故障转移链回退到 TypeSafe 时跳过该下限。请改用 `final`。

## 响应 {#response}

### results

按相关性排序的召回事实主列表。语义相似度、BM25 关键词、图遍历和时间四种检索策略并行运行，通过倒数排名融合（RRF）合并排名，再用交叉编码器依据原始查询为候选项重新评分。

每条结果都有 [`scores`](#scores) 对象。它们是**相对**信号，反映单次查询中的排序，不是跨查询可比的绝对置信度；一次查询的 `0.8` 不能与另一次的 `0.8` 比较。多数智能体应按顺序使用记忆，让 `max_tokens` 决定容纳多少条，而非按分数筛选。`scores` 和 [`min_scores`](#min_scores) 用于观察排名或裁剪低置信度尾部；阈值应依据未筛选查询的实际分数校准。

`results` 的每项包含以下字段：

#### id

事实的唯一标识符，用于与 `source_facts` 交叉关联或在应用层去重。

#### text

记忆库中保存的已提取事实文本。

#### type

事实类别：`world` 为客观信息，`experience` 为事件和对话，`observation` 为随时间整合的知识。

#### context

存储事实时提供的上下文标签，例如 `"团队会议"`、`"slack"`；未设置时为 `null`。

#### metadata

存储事实时附加的字符串键值对；未设置时为 `null`。

#### tags

附加在事实上的可见范围标签。

#### entities

与事实关联的规范实体名称字符串列表。仅在启用 `include.entities`（默认）时填充，否则为 `null`。

#### occurred_start / occurred_end

描述事件开始和结束时间的 ISO 8601 日期时间，由 LLM 在存储时从内容中提取。没有时间信息时为 `null`。

#### mentioned_at

事实存入记忆库时的 ISO 8601 日期时间。

#### document_id

存储时设置的所属文档 ID。

#### chunk_id

提取该事实的来源文本分块 ID，启用 `include.chunks` 时用于与响应中的 `chunks` 关联。

#### source_fact_ids

仅 `observation` 结果返回：生成该观察的原始事实 ID，与响应中的 `source_facts` 关联。其他类型或未启用 `include.source_facts` 时为 `null`。

#### scores

该结果各阶段的分数对象。`source_facts` 条目按来源关系附加而非排名，因此为 `null`。字段包括：

- **`final`**：事实的排名分数（交叉编码器相关性 × 新鲜度／时间／证据加权），`results` 按其降序排列。它是相对信号，不是校准后的概率。
- **`reranker`**：交叉编码器归一化相关性（`0`～`1`）。使用透传重排序（RRF/interleave）或返回排名位置而非分数的模型（TypeSafe）时为 `null`。
- **`semantic`**：原始向量余弦相似度（`0`～`1`）；未被语义搜索找到时为 `null`。
- **`keyword`**：原始关键词／全文（BM25）分数（`≥ 0`，无上限）；未被关键词搜索找到时为 `null`。

每个字段也可作为 [`min_scores`](#min_scores) 下限，但 `semantic` 和 `keyword` 约束各自检索分支，因此即使设置下限，该值也可能为 `null`。非空值始终满足下限，详情见 [`min_scores`](#min_scores)。

---

### source_facts

以事实 ID 为键的字典，包含参与生成观察结果的来源事实完整 `RecallResult` 对象。仅启用 `include.source_facts` 时返回。事实会去重，两个观察共享的来源事实只出现一次。

### source_facts_truncated

token 预算是否截断了 `source_facts` 字典。为 `true` 时，部分 `results[].source_fact_ids` 因预算耗尽而没有对应条目，并不表示引用失效。仅启用 `include.source_facts` 时返回。

### chunks

以分块 ID 为键的字典，包含与返回事实关联的原始来源文本分块。仅启用 `include.chunks` 时返回。每个分块包含 `id`、`text`、`chunk_index` 和 `truncated`（文本是否为适应预算而截断）。

### entities

以规范实体名称为键的实体状态字典。仅启用 `include.entities` 时返回。每项包含 `entity_id`、`canonical_name` 和 `observations`。

### trace

仅请求设置 `trace: true` 时返回的调试对象，包含各阶段耗时、检索明细和 RRF 融合详情。
