# Webhooks {#webhooks}

Hindsight可以通过向您配置的URL发送HTTP POST请求来实时通知您的应用程序。

## 投递与重试 {#delivery-and-retries}

Webhooks 按记忆库注册，并在发生匹配事件时自动触发。跟踪每次交付尝试，并以指数退避重试失败的交付：

|尝试|失败后延迟|
|---------|---------------------|
|1|5秒|
|2|5 分钟|
|3|30分钟|
|4|2小时|
|5|5小时|
|6|永久失败|

如果您的终端返回non-2xx状态代码或在配置的超时（默认30秒）内未响应，则视为传送失败。尝试失败 6 次后，交付将被标记为永久失败，并且不会再进行重试。

:::info 至少一次交付
Webhook 交付任务在与主要操作相同的数据库事务中排队（例如，记忆存储或集成写入）。这意味着如果服务器在提交之后但在发送之前崩溃，交付任务将继续存在并将重试。结果**你的端点可能多次收到同一事件** — 使用 如果需要， `operation_id` 字段可进行重复数据删除。
:::

## 验证投递 {#verifying-deliveries}

当使用秘密注册 Webhook 时，每次交付都会携带确切请求正文的 HMAC-SHA256 签名。在信任有效负载之前验证它——仅 URL 并不能证明请求来自 Hindsight。

|标题|价值|注释|
|--------|-------|-------|
|`X-Hindsight-Event`|事件类型，例如`retain.completed`|始终发送|
|`X-Hindsight-Signature`|`sha256=<hex>`在原始身体上|配置机密时发送|
|`X-Hub-Signature-256`|与相同 `X-Hindsight-Signature`|此结构的常规名称，因此 GitHub 型接收器开箱即用验证|
|`X-Hindsight-Signature-V2`|`t=<unix_seconds>,v1=<hex>`超过`<t>.<raw body>`|时间戳变体 - 如果您想要重放保护，请使用此选项|

`X-Hindsight-Signature` 和 `X-Hub-Signature-256` 始终携带相同的值：相同的秘密、相同的算法、相同的字节。验证您的框架已经理解哪一个；没有理由同时检查两者。

:::warning 更喜欢带时间戳的签名
`X-Hindsight-Signature` / `X-Hub-Signature-256` 在正文上签名，不要做任何其他事情，所以他们说*此有效负载来自Hindsight*但不是*这个有效负载是新鲜的*。在线捕获的交付永远可以验证。 `X-Hindsight-Signature-V2` 将有效负载与其签名时间绑定 — 检查`t` 在您选择的容差范围内（五分钟是常见的默认值）并拒绝任何较旧的内容。时间戳位于签名字符串内，因此在不破坏 MAC 的情况下无法对其进行编辑。每次重试都会重新签名，因此数小时后重试的交付仍会以新的 到达 `t`。
:::

```python
import hashlib
import hmac
import time

TOLERANCE_SECONDS = 300


def verify(secret: str, body: bytes, header: str) -> bool:
    """根据原始请求正文验证 X-Hindsight-Signature-V2 标头。"""
    parts = dict(p.split("=", 1) for p in header.split(","))
    timestamp, received = parts["t"], parts["v1"]

    if abs(time.time() - int(timestamp)) > TOLERANCE_SECONDS:
        return False  #太旧（或太远的未来）——视为重播

    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, received)
```

任何语言中需要正确处理的两件事：

- **对原始字节签名。** 重新序列化解析的JSON更改空格和按键顺序，签名将不匹配。在框架对其进行解码之前阅读正文。
- **使用常量时间比较** (`hmac.compare_digest`，`crypto.timingSafeEqual`，……），从不与`==`。

在 Webhook 上设置的自定义标头 `http_config` 无法覆盖 `X-Hindsight-Event` 或任何签名标头，因此接收者可以信任这些值，无论其他配置如何。

## 事件类型 {#event-types}

### `consolidation.completed` {#consolidationcompleted}

在Hindsight完成将新记忆整合到记忆库的观察中后触发。

**请求载荷：**

```json
{
  "event": "consolidation.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-04T12:00:00Z",
  "data": {
    "observations_created": 3,
    "observations_updated": 1,
    "observations_deleted": null,
    "error_message": null
  }
}
```

**`data` 字段：**

|字段|类型|说明|
|-------|------|-------------|
|`observations_created`|`整数\|空`|创建的新观察数|
|`observations_updated`|`整数\|空`|现有观察数量已更新|
|`observations_deleted`|`整数\|空`|删除的观察数|
|`error_message`|`字符串\|空`|设置当 `status` 是 `"failed"`|

**`status` 值：**`"completed"`或`"failed"`

---

### `retain.completed` {#retaincompleted}

记忆存储操作完成后（同步和异步）每个文档触发一次。当保留一批 N 个文档时，会触发 N 个单独的事件。

**请求载荷：**

```json
{
  "event": "retain.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-04T12:00:01Z",
  "data": {
    "document_id": "doc-abc123",
    "tags": ["meeting", "q1-2026"],
    "memory_unit_count": 12
  }
}
```

**`data` 字段：**

|字段|类型|说明|
|-------|------|-------------|
|`document_id`|`字符串\|空`|文档 ID（如果在记忆存储请求中提供）|
|`tags`|`字符串[] \|空`|记忆存储期间应用的文档级标签|
|`memory_unit_count`|`数字\|空`|在此记忆存储之后文档拥有的记忆单位。 `null` 当请求不包含时 `document_id`。|

**注意事项：**
- 对于异步记忆存储（`async: true`), `operation_id` 匹配 记忆存储返回的 `operation_id`API。
- 对于同步记忆存储，`operation_id` 是出于跟踪目的而生成的标识符。
- 记忆存储请求中的每个内容项都会触发一个事件。
- `memory_unit_count: 0` 表示事实提取没有为文档返回任何内容。记忆存储仍然成功并且文本被存储，但是`recall` 和 `reflect` 搜索记忆 — 因此文档在之前无法检索 [重新处理](/developer/retain#when-a-mission-excludes-everything-in-a-document)。观看此字段，了解排除了超出预期内容的记忆存储任务。

### `memory_defense.triggered` {#memory_defensetriggered}

当记忆库时触发 [记忆防护](../memory-defense/index.md) 策略作用于保留的项目 — 每个项目一次，即 **已脱敏**或**已阻止**。顺利通过的项目不会触发事件。需要在记忆库上启用记忆防御策略以及订阅此事件类型的 Webhook。

**请求载荷：**

```json
{
  "event": "memory_defense.triggered",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "redact",
  "timestamp": "2026-03-04T12:00:02Z",
  "data": {
    "action": "redact",
    "detector": "sensitive_data",
    "document_id": "doc-abc123",
    "matched_types": ["github_token", "aws_access_key"],
    "message": "匹配的敏感数据模式：github_token、aws_access_key"
  }
}
```

**`data` 字段：**

|字段|类型|说明|
|-------|------|-------------|
|`action`|`string`|针对该项目采取的行动：`"redact"`或`"block"`|
|`detector`|`字符串\|空`|匹配的探测器 (`"sensitive_data"`)|
|`document_id`|`字符串\|空`|文档 ID（如果在记忆存储请求中提供）|
|`matched_types`|`字符串[] \|空`|触发的密文模式的标签（例如 `github_token`，`ssn_us`)|
|`message`|`字符串\|空`|匹配内容的人类可读摘要|

**`status` 值：**镜子`data.action` — `"redact"`或`"block"`。

**注意事项：**
- A`redact`事件意味着秘密被清除，并且编辑过的记忆仍然被存储。 `block`事件表示物品被掉落；如果记忆存储请求中的每个项目都被阻止，则记忆存储调用将返回 `422`。
