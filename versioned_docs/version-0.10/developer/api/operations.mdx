# 操作 {#operations}

Hindsight 会异步执行多种维护和摄取任务，避免触发任务的 API 调用被阻塞。这些任务共用一个队列（`async_operations`）和一个工作进程池；同一组 REST 端点——列表、状态、取消、重试——适用于所有类型的任务。

本页介绍各类操作、它们的触发时机，以及如何检查或管理它们。

## 操作的工作方式 {#how-operations-work}

API 调用需要后台处理时，请求处理程序会向 `async_operations` 表写入一行，状态设为 `pending`，然后立即返回。工作进程（默认在 API 进程内运行，也可以作为独立服务运行，参见[服务 - 工作进程服务](../services#worker-service)）会轮询该表，领取待处理行，执行相应的处理程序，并将状态标记为 `completed` 或 `failed`。

默认情况下，所有操作都在进程内运行：无需外部队列，也无需部署额外进程。同一套代码路径也支持在吞吐量需求增加时扩展到独立工作进程。

### 生命周期 {#lifecycle}

| 状态 | 含义 |
|--------|---------|
| `pending` | 该行已进入队列。可能还没有工作进程领取，也可能是扩展通过未来的 `next_retry_at` 暂缓了它（例如用于背压控制）。 |
| `processing` | 工作进程已领取该行，正在执行处理程序。 |
| `completed` | 处理程序已成功返回。 |
| `failed` | 处理程序抛出了异常。`error_message` 中记录原因；可以通过 `POST /…/retry` 重新入队。 |
| `cancelled` | 操作已通过 `DELETE /…/operations/{id}` 取消。`pending` 和 `processing` 状态的操作都可以取消。 |

工作进程最多会重试失败的操作 `HINDSIGHT_API_WORKER_MAX_RETRIES` 次，之后将其置为 `failed`。确定性故障（例如嵌入维度无效或完整性约束冲突）会跳过重试，因为重新运行也不会成功。

默认情况下，`completed`、`failed` 和 `cancelled` 操作会无限期保留。将 `HINDSIGHT_API_OPERATION_RETENTION_DAYS` 设为正数天数，可限制这些历史记录的保留时间：随后后台维护循环会按自己的计划，以有界批次清理过期的终态记录，而不是在处理任务时顺带清理。此功能仅适用于 PostgreSQL；Oracle 上不会运行维护循环，因此操作历史不会因保留期限而清理。整行数据共用此 TTL，所以只要操作记录仍被保留，其负载就仍可用——失败和已取消的操作可以重试，已完成的操作可以通过 `include_payload=true` 检查。保留清理绝不会删除 `pending` 和 `processing` 操作。

## 操作类型 {#operation-types}

每个操作在数据库中都有一个 `operation_type`，在负载中都有一个 `task_type`。两者通常相同。

### `retain` {#retain}

通过带有 `async=true` 的 `POST /v1/default/banks/{bank_id}/memories` 提交，或通过多项输入的 `retain_batch` 调用提交。处理程序运行与同步存入相同的流程：事实提取（LLM）、嵌入生成、实体消解和链接创建（时间链接、语义链接）。

摄取数千项内容且不希望 HTTP 调用等待数分钟时，可以使用异步存入。响应中的 `operation_id` 可用于轮询操作是否完成。

#### 父操作：`retain_batch` {#parent-op-retain_batch}

对于大型提交，Hindsight 会自动将输入拆分为多个子批次，并创建一个跟踪这些子项的 `retain_batch` 父操作。父操作的状态反映聚合结果：在至少一个子项开始运行前为 `pending`；子项执行期间为 `processing`；所有子项完成后为 `completed`；任一子项失败时为 `failed`。每个子项本身都是关联到父操作的 `retain` 操作，因此可以进一步查看每个批次的错误消息。

列出操作时，默认会同时显示父操作及其所有子项。传入 `exclude_parents=true` 可隐藏聚合行，只显示各个 `retain` 任务。

### `file_convert_retain` {#file_convert_retain}

由文件上传端点提交。处理程序会根据 MIME 类型执行转换（PDF → 文本、DOCX → 文本等），然后将提取出的文本传入存入流程。默认情况下，此类故障**不可重试**：损坏的 PDF 或缺少 OCR 不会因重新运行而改善，因此操作会直接进入 `failed` 状态。

每个部署通过 `HINDSIGHT_API_FILE_PARSER` 选择使用哪个解析器（`markitdown`、`iris` 或 `llama_parse`）；客户端也可以在每个请求中覆盖该设置，参见[配置 → 文件处理](../configuration#file-processing)。

### `consolidation` {#consolidation}

根据新的世界事实/经历事实生成**观测**。观测的含义及其综合生成方式请参见[观测](../observations)。

以下情况会触发：

- 每次存入新增世界事实/经历事实后都会触发（受每个记忆库的 `enable_auto_consolidation` 和 `enable_observations` 设置控制）。
- 删除使现有观测失效后触发（来源记忆消失 → 派生观测待更新 → 根据仍然存在的共同来源记忆重新运行整合）。
- 也可以通过 `POST /v1/default/banks/{bank_id}/consolidate` 手动触发。传入 `observation_scopes`，只整合与指定标签组合匹配的记忆。

**按记忆库去重**：当某个记忆库已有一个 `consolidation` 任务处于 `pending` 状态时，重复提交会返回现有的 `operation_id`，不会继续堆积任务。该任务开始处理后，下一次提交会占用下一个待处理位置。

### `refresh_mental_model` {#refresh_mental_model}

心智模型有一个 `source_query`，用于定义它要概括哪些记忆。处理程序会重新运行该查询，再次概括查询结果，并原位更新心智模型的内容。

可以通过 `POST /v1/default/banks/{bank_id}/mental-models/{id}/refresh` 手动触发；如果某个心智模型配置了自动刷新计划，也可以由该计划自动触发。

### `graph_maintenance` {#graph_maintenance}

协调删除后变得待更新的派生状态。每次运行都会排空两个由删除操作填充的队列，因此只会处理该次删除所触及的内容：

1. **补充链接。** 排空那些因邻居丢失而失去外向时间/语义链接的记忆单元。对于每个记忆单元，如果链接数低于上限（时间链接 20 条，语义链接 50 条），Hindsight 会重新运行存入流程使用的相同探测，并插入缺失的链接。如果没有此处理，存入流程按 top-K 限制链接数的做法会导致幸存的记忆单元每次删除后都永久低于上限，从而降低图扩展召回效果。
2. **清理实体。** 排空可能因删除而成为孤立状态的实体。没有剩余 `unit_entities` 引用的实体会被删除（外键 `ON DELETE CASCADE` 会连带删除其 `entity_cooccurrences` 行）；对于仍保留的实体，如果两个端点都存在、但当前没有任何 `memory_unit` 同时引用二者，则清理对应的共现行——记录时这次共现确实存在，但见证它的所有记忆单元后来都已删除。

提交时按记忆库去重，因此同一记忆库上的并发触发会合并为一次队列排空。

每次运行都会在墙钟时间预算内，以已提交的批次处理。如果积压任务太多，无法在一次运行中完成（例如批量删除），这不算错误：本次运行会报告已完成的部分，下次运行会从停止处继续。

**触发条件**：任何会删除 `memory_units` 的删除操作，包括 `DELETE /documents/{id}`、`DELETE /memories/{id}`，以及重新存入已有 `document_id` 的内容（upsert 路径）。清空整个记忆库（`delete_bank`）不会触发处理：库中已无内容需要维护。

### `webhook_delivery` {#webhook_delivery}

某些操作完成后（例如已注册 webhook 的记忆库完成观测整合），Hindsight 会将 `webhook_delivery` 任务加入队列。处理程序会向配置的 URL 发送包含负载的 POST 请求，并在遇到暂时性故障时重试。

| 字段 | 说明 |
|-------|-------------|
| `updated_at` | 操作记录最近一次变更的时间，例如被领取、进度心跳或完成时。 |
| `progress` | 正在运行的操作最近一次记录的进度快照；如果没有记录（例如即时完成的操作或该功能推出前的记录），则为 `null`。 |
| `task_payload` | 原始提交参数；仅当 `include_payload=true` 时填充。 |

`progress` 会在较粗略的阶段/批次边界写入（例如观测整合、批量存入），可用于区分健康运行的长任务和停滞任务：如果轮询时 `processed` 持续增加，说明任务仍在运行；如果数字完全相同且 `at` 没有变化，说明任务已卡住。其结构如下：

| 字段 | 说明 |
|-------|-------------|
| `stage` | 操作最近报告的粗略阶段（例如 `processing_batch`）。 |
| `at` | 写入此快照时的 ISO-8601 时间戳。 |
| `processed` | 已完成的工作单元数（子批次、记忆），如果已知。 |
| `total` | 操作的工作单元总数，如果已知。 |
| `detail` | 操作特有的计数器（例如 `observations_created`、`round`、`items_in_sub_batch`）。 |

### 取消操作 {#cancel-an-operation}

可以取消处于 `pending` 或 `processing` 状态的操作。如果操作已进入终态（`completed`、`failed`、`cancelled`），则返回 `409`。

记录会立即标记为 `cancelled`，但取消正在运行的工作采用**协作式方式，并非立即生效**。执行操作的工作进程会在下一个检查点发现取消请求——对于存入操作，检查点位于子批次或文档之间；对于观测整合，检查点位于 LLM 批次之间——然后在该处停止。因此，已经提交的内容会保留，正在处理的批次也可能仍会完成。没有检查点的操作类型会继续运行到结束；无论哪种情况，记录都会保持 `cancelled`，因为工作进程不得写入覆盖该状态。

如果某个工作进程在完成操作前被终止，导致操作卡在 `processing`，也可以用此方式清理：此时已没有任务在运行，因此取消会立即生效。之后可以通过 `POST /…/operations/{id}/retry` 将工作重新入队。

## 工作进程调优 {#worker-tuning}

每个工作进程都有一个由所有操作类型共用的并发预算（`HINDSIGHT_API_WORKER_MAX_SLOTS`，默认值为 10）。按类型预留的槽位（`HINDSIGHT_API_WORKER_<TYPE>_MAX_SLOTS`）会在此预算内划出保证容量；其余槽位构成所有类型均可使用的共享池。完整配置表请参见[配置 → 工作进程配置](../configuration#distributed-workers)。

大多数部署使用默认值即可。如果某类操作曾因另一类操作大量涌入而得不到处理，可以为其预留槽位（例如，在删除频繁的工作负载中，长时间运行的 `file_convert_retain` 阻塞了 `graph_maintenance`）。

槽位也会在不同记忆库之间轮转。每次领取都会依次服务下一个记忆库中的一个操作，然后从所有记忆库中按创建时间从早到晚填满池中剩余槽位。因此，一个正在批量摄取的记忆库不会独占整个池，让另一个记忆库的单次写入排在积压任务之后等待；同时它也不会被限流：没有其他记忆库在等待时，它仍可占用所有槽位。
