# 模型 {#models}

Hindsight 使用多种机器学习模型来执行不同任务。

## 概览 {#overview}

- **LLM** — 用于事实提取、推理和生成。具体能力因提供方而异，且可完全配置。
- **嵌入模型** — 将文本转换为向量表示，用于语义检索。默认值：`BAAI/bge-small-en-v1.5`。
- **交叉编码器** — 对检索结果重新排序。默认值：`cross-encoder/ms-marco-MiniLM-L-6-v2`。

首次运行时，系统会自动从 HuggingFace 下载嵌入模型和交叉编码器模型。

## LLM {#llm}

用于事实提取、实体消解、心智模型整合和答案合成。

**支持的提供方：**

<LLMProvidersGrid />

此外还支持**任意 OpenAI 兼容 API**（例如 Azure OpenAI、Together AI、Fireworks），以及 **LiteLLM 提供的 100 多个提供方**（例如 AWS Bedrock、Azure OpenAI、Together AI）。

:::tip OpenAI 兼容提供方
Hindsight 可与任何提供 OpenAI 兼容 API 的服务配合使用。将 `HINDSIGHT_API_LLM_PROVIDER=openai`，并把 `HINDSIGHT_API_LLM_BASE_URL` 指向提供 `/chat/completions` 的端点。对大多数提供方来说，这个 URL 以 `/v1` 结尾，**而不是**账户或资源根路径。

**Azure OpenAI 不会在资源根路径提供 API**，因此单独使用 `https://<resource>.openai.azure.com` 会返回 `404 Resource not found`。请参阅 [Azure OpenAI 设置](#azure-openai-setup)，了解两种可用的 URL 格式。

`openai` 提供方使用 **Chat Completions API**（`/v1/chat/completions`）。如需使用较新的 **Responses API**（`/v1/responses`），请设置 `HINDSIGHT_API_LLM_PROVIDER=openai-responses`，详见下方提示。两者都接受自定义 `HINDSIGHT_API_LLM_BASE_URL`，因此提供 `/v1/responses` 的 OpenAI 兼容端点也能像 Chat Completions 端点一样使用。

请参阅[配置](./configuration#llm-provider)中的设置示例。
:::

:::tip OpenAI Responses API（推理与工具调用并用）
设置 `HINDSIGHT_API_LLM_PROVIDER=openai-responses`，即可调用 OpenAI 的 **Responses API**（`/v1/responses`），而非 Chat Completions。

它的用途：某些推理模型（例如 `gpt-5.6-terra`）在 Chat Completions 中遇到函数工具时，**会拒绝 `reasoning_effort`**（除非 `reasoning_effort="none"`，否则返回 HTTP 400）。Reflect 会循环调用工具，因此使用 `openai`（Completions）提供方时，整个操作（包括最终答案合成）都被迫关闭推理。（Hindsight 遇到该 400 错误时会用 `reasoning_effort="none"` 重试一次，因此调用仍会成功，但不会启用推理。）Responses API 会将模型的思维链作为一等推理项保留，因此**推理和工具可以并用**：Reflect 的检索循环可使用实际的 `HINDSIGHT_API_LLM_REASONING_EFFORT` 值（例如 `high`）。

建议将其用于需要调用工具的推理模型（gpt-5.x、o 系列）。它也支持自定义 `HINDSIGHT_API_LLM_BASE_URL`，因此任何提供 `/v1/responses` 的 OpenAI 兼容端点（网关、Azure 风格部署）都可以像 Chat Completions 端点一样使用。

请参阅[配置](./configuration#llm-provider)中的设置示例。
:::

:::info 推理/思考模型与 `max_tokens`
对于思考模型（Gemini 2.5+/3.x、GPT-5/o 系列、Grok 推理模型、Claude extended thinking），提供方的输出预算同时涵盖**推理 token 和可见输出**；推理会占用同一个 `max_output_tokens`/`max_completion_tokens` 上限。因此，上限较小时，预算可能全部被推理耗尽，可见答案便会在句中被截断。

Hindsight 将 Reflect/心智模型的 `max_tokens` 定义为**可见页面长度**：它作为提示词层面的目标，并在生成后进行改写，**不会**作为提供方调用的硬性上限。默认情况下，Reflect 的合成调用没有上限，因此推理不会挤占答案的预算。如果需要为该调用设置硬性成本上限，请配置 `HINDSIGHT_API_REFLECT_MAX_COMPLETION_TOKENS`；但上限必须高于页面长度并留出足够的推理空间，否则思考模型仍会截断输出。

Gemini 调用达到上限时，Hindsight 会记录 `truncated at max_output_tokens` 警告，而不会把只写了一半的文本当作成功结果静默返回。
:::

:::tip AWS Bedrock
设置 `HINDSIGHT_API_LLM_PROVIDER=bedrock`，即可直接使用 AWS Bedrock 模型。模型名称使用 Bedrock 模型 ID（例如 `us.amazon.nova-2-lite-v1:0`）。无需 API 密钥；使用 AWS 凭据（`AWS_ACCESS_KEY_ID`、`AWS_SECRET_ACCESS_KEY`、`AWS_REGION_NAME`）或 IAM 角色进行身份验证。若要将吞吐量费用降低 50%，请设置 `HINDSIGHT_API_LLM_BEDROCK_SERVICE_TIER=flex`（参阅[配置](./configuration#llm-provider)）。

请参阅[配置](./configuration#llm-provider)中的设置示例。
:::

:::tip 内置 llama.cpp（完全本地运行，无需 API 密钥）
设置 `HINDSIGHT_API_LLM_PROVIDER=llamacpp`，即可运行内置的 llama.cpp 服务，无需外部依赖。首次运行时会自动下载 Gemma 4 E2B GGUF 模型（约 3.5 GB）。需要安装 `local-llm` 扩展：`pip install 'hindsight-api-slim[local-llm]'`。

发布的 Docker 镜像不包含 `llama-cpp-python`（以控制镜像大小）。如需可运行且基于该镜像添加此依赖的 Docker 配置，请参阅 [`docker/docker-compose/local-llm/`](https://github.com/vectorize-io/hindsight/tree/main/docker/docker-compose/local-llm)。

所有选项请参阅[配置](./configuration#built-in-llamacpp)。
:::

:::tip LiteLLM 提供方（Azure、Together AI 等）
设置 `HINDSIGHT_API_LLM_PROVIDER=litellm`，即可使用 [LiteLLM](https://docs.litellm.ai/docs/providers) 支持的任意模型，包括 **Azure OpenAI**、**Together AI**、**Fireworks AI** 等。模型名称使用 LiteLLM 的提供方前缀格式（例如 `azure/gpt-4o`）。

请参阅[配置](./configuration#llm-provider)中的设置示例。
:::

:::tip LiteLLM Router（回退链、负载均衡、按部署设置限制）
设置 `HINDSIGHT_API_LLM_PROVIDER=litellmrouter`，通过 [LiteLLM Router](https://docs.litellm.ai/docs/routing) 运行默认 LLM。其 [`Router` 配置](https://docs.litellm.ai/docs/routing#fallbacks)支持按部署顺序回退、同级部署间负载均衡、加权选择、按部署设置 `rpm`/`tpm` 限制和冷却时间。Hindsight 会原样传递 JSON 配置。

设置方法请参阅[配置](./configuration#llm-router-litellm-router)。
:::

### 提供方能力 {#provider-capabilities}

除基本生成能力外，某些提供方还支持可降低成本或延迟的可选功能。配置的提供方支持某项功能时，Hindsight 会自动使用该功能。

<LLMProviderCapabilities />

- **Batch API** — 通过提供方的异步批处理端点批量提交存入时的事实提取任务，费用通常低约 50%。若可用，系统会自动使用；否则改为同步调用。
- **显式提示缓存** — 重复使用每次调用都会发送的大段固定系统前缀，其中包括存入（事实提取）、整合和 Reflect 工具循环的提示词，并按提供方的缓存输入费率计费。在 Gemini/Vertex 上，此功能使用 `CachedContent` API。**默认启用**；设置 `HINDSIGHT_API_LLM_PROMPT_CACHE_ENABLED=false` 可关闭。Hindsight 会将提示词组织为**不依赖记忆库**的缓存前缀：所有记忆库共享一个缓存，而不是每个记忆库/任务说明各用一个缓存。如果创建缓存失败，会软失败并改为不使用缓存调用，不会导致请求失败。

:::note
“显式提示缓存”列为空，不代表提供方不支持缓存。例如，OpenAI 会在服务器端**自动**缓存稳定的提示词前缀，因此无需配置也能受益；Anthropic 支持通过 `cache_control` 分界点缓存提示词，可通过同一个提供方钩子接入。此列仅记录 Hindsight 的显式 `get_or_create_cached_prefix` 钩子，目前只有 Gemini/Vertex 实现了该钩子。
:::

### 提供方默认模型 {#provider-default-models}

每个提供方都有一个建议的默认模型；未显式设置 `HINDSIGHT_API_LLM_MODEL` 时会使用该模型。这样可以简化配置：只需指定提供方即可使用合适的默认模型：

<LLMProvidersTable />

**示例**：只设置服务提供方时，将使用其默认模型：
```bash
# Uses claude-haiku-4-5 automatically
export HINDSIGHT_API_LLM_PROVIDER=anthropic
export HINDSIGHT_API_LLM_API_KEY=sk-ant-xxxxxxxxxxxx
```

可显式设置 `HINDSIGHT_API_LLM_MODEL` 来覆盖默认模型：
```bash
# Override to use Sonnet instead
export HINDSIGHT_API_LLM_PROVIDER=anthropic
export HINDSIGHT_API_LLM_API_KEY=sk-ant-xxxxxxxxxxxx
export HINDSIGHT_API_LLM_MODEL=claude-sonnet-4-5-20250929
```

按操作配置的覆盖项也遵循这一规则：
```bash
# Global: OpenAI gpt-4o-mini (default)
export HINDSIGHT_API_LLM_PROVIDER=openai

# Retain: Anthropic claude-haiku-4-5 (default)
export HINDSIGHT_API_RETAIN_LLM_PROVIDER=anthropic
```

### 使用其他模型 {#using-other-models}

Hindsight 也可能支持上表未列出的其他 LLM 模型，但模型必须支持**至少 65,000 个输出 token**，才能可靠地提取事实。如果你需要支持不满足此要求的特定模型，请[提交 issue](https://github.com/hindsight-ai/hindsight/issues)申请例外。

:::tip 输出 token 数量有限的模型
如果模型最多只支持 32k 个输出 token（例如某些较旧的模型），可以调低存入操作的补全 token 上限：

```bash
# For models that support 32k output tokens
export HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS=32000

# For models that support 16k output tokens
export HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS=16000
```

**重要：**`HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS` 必须大于 `HINDSIGHT_API_RETAIN_CHUNK_SIZE`（默认值：3000）。系统会在启动时验证此设置；如果配置无效，会显示错误信息。
:::

:::warning Groq 免费套餐不适合运行 Hindsight
Groq 免费套餐每分钟仅允许使用 8,000 个 token，远低于 Hindsight 单次存入调用所需的约 64k token。因此，Hindsight 不能使用 Groq 免费套餐中的模型；请改用付费 Groq 套餐或其他提供方。
:::

### 设置 GitHub Copilot {#github-copilot-setup}

通过官方 GitHub Copilot SDK 使用 GitHub Copilot 订阅执行 Hindsight 的提取、整合和反思调用。

**前提条件：**
- 已开通 GitHub Copilot
- 运行 Hindsight 的操作系统用户已登录 Copilot CLI

**配置 Hindsight：**

```bash
export HINDSIGHT_API_LLM_PROVIDER=github-copilot
export HINDSIGHT_API_LLM_MODEL=gpt-5.6-terra
# No HINDSIGHT_API_LLM_API_KEY is needed.
```

该提供方会为 Hindsight 的所有 LLM 通道启动一个共享的 Copilot 运行时。运行时使用不带钩子的临时 `COPILOT_HOME`，其中只保存已登录的账户选择；凭据由运行时从系统密钥链或现有的 `gh` CLI 登录中解析。每次调用都会使用相互隔离的临时会话，并禁用仓库说明、技能、Copilot 记忆、内置工具和跨会话存储。这样可防止记忆集成递归地存入自身的提取调用。

用于自动化时，Copilot SDK 还接受 `COPILOT_GITHUB_TOKEN`、`GH_TOKEN` 或 `GITHUB_TOKEN`。设置其中任一项后，主机无需运行过 Copilot CLI，因此容器和 CI 镜像无需包含 `~/.copilot` 也能运行。GitHub Actions 和服务器到服务器的部署必须具备相应的 Copilot 组织策略和令牌权限。

**重要说明：**
- 用量计入已验证身份的账户或组织的 Copilot 配额及 AI Credits。
- `HINDSIGHT_API_LLM_BASE_URL` 可选，用于指向现有的无头 Copilot 运行时，例如 `http://127.0.0.1:4321`；对于此提供方，它不是 LLM 提供方端点。
- GitHub 托管的 Copilot 会话不会通过 SDK 提供 temperature 或最大输出 token 控制，因此不会应用 Hindsight 的这些设置。
- 嵌入和重排继续使用 Hindsight 单独配置的提供方；其本地默认配置无需 API 密钥。

### 设置 OpenAI Codex（ChatGPT Plus/Pro） {#openai-codex-setup-chatgpt-pluspro}

使用 ChatGPT Plus 或 Pro 订阅运行 Hindsight，无需额外支付 OpenAI Platform API 费用。

**前提条件：**
- 有效的 ChatGPT Plus 或 Pro 订阅
- 已安装 Node.js/npm（用于 Codex CLI）

**设置步骤：**

1. **安装 Codex CLI：**
   ```bash
   npm install -g @openai/codex
   ```

2. **使用 ChatGPT 凭据登录：**
   ```bash
   codex auth login
   ```
   这会打开浏览器，让你使用 ChatGPT 账户验证身份，并将 OAuth 令牌保存到 `~/.codex/auth.json`。

3. **验证身份：**
   ```bash
   ls ~/.codex/auth.json  # 应显示认证文件存在
   ```

4. **配置 Hindsight：**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=openai-codex
   # export HINDSIGHT_API_LLM_MODEL=gpt-5.6-luna  # 默认值为 gpt-5.4-mini
   # 无需 API 密钥——会自动读取 ~/.codex/auth.json
   ```

5. **启动 Hindsight：**
   ```bash
   hindsight-api
   ```

你可以使用 OpenAI Codex CLI 支持的任意模型。

**重要说明：**
- OAuth 令牌保存在 `~/.codex/auth.json`。
- 令牌会在需要时自动刷新。
- 用量计入你的 ChatGPT 订阅（无需另付 API 费用）。
- 仅供个人开发使用（请参阅 ChatGPT 服务条款）。

#### 为长期运行的服务隔离 Codex 身份验证 {#isolating-codex-auth-for-long-running-services}

默认情况下，Hindsight 从 `~/.codex/auth.json` 读取 Codex 凭据；`@openai/codex` CLI、编辑器插件和其他智能体运行时也使用此文件。这对本地开发很方便，但当 Hindsight 与另一个 Codex 进程一起作为**长期运行的服务**（systemd 单元、容器、后台守护进程）运行时，可能会出现一个不易察觉的问题：

- Codex 刷新令牌只能使用一次，刷新后就会轮换。
- 如果另一个进程刷新了共享令牌，Hindsight 的长期运行进程仍持有过期的刷新令牌。
- Recall 和 `/health` 仍可用（数据库和 API 正常），但 `/reflect` 会失败，并显示类似以下错误：
  ```text
  Codex refresh_token is permanently invalid (error.code=refresh_token_reused).
  Run 'codex auth login' to re-authenticate.
  ```

为避免此问题，请通过 `CODEX_HOME` 环境变量为 Hindsight 服务指定**专用的 Codex 身份验证目录**。Hindsight 与 `@openai/codex` CLI 一样遵循 `CODEX_HOME`：设置该变量后会读取 `$CODEX_HOME/auth.json`，而不是 `~/.codex/auth.json`。

```bash
# Dedicated credentials directory for the Hindsight service
export CODEX_HOME=/var/lib/hindsight/codex

# One-time login into that isolated home (opens a browser / device-code flow)
codex auth login   # writes $CODEX_HOME/auth.json

export HINDSIGHT_API_LLM_PROVIDER=openai-codex
hindsight-api
```

对于 systemd 单元，请在服务定义中设置此变量，避免它与交互式 Codex 会话共享凭据：

```ini
[Service]
Environment=CODEX_HOME=/var/lib/hindsight/codex
```

在专用目录中重新登录并仅重启 Hindsight 服务后，`/reflect` 就会使用自己的令牌，不会被其他 Codex 进程轮换失效。

`openai-codex` 嵌入提供方也遵循 `CODEX_HOME`。

#### 在同一进程中使用两个 Codex 配置 {#two-codex-profiles-in-one-process}

`CODEX_HOME` 是进程级设置，因此 Hindsight 进程创建的每个 Codex 提供方都会解析到同一个 `auth.json`。若要运行多个分别授权的 ChatGPT 账户（例如首选账户达到用量上限时进行故障转移），请通过 `HINDSIGHT_API_LLM_CODEX_HOME`（主配置）和 `HINDSIGHT_API_LLM_<n>_CODEX_HOME`（索引式[多 LLM 链](./configuration#multi-llm-strategies-failover--round-robin)成员）为每个账户指定独立凭据目录。未设置时，每个配置会依次回退到 `CODEX_HOME`，再回退到 `~/.codex`。

```bash
# Two profiles, logged in separately
CODEX_HOME=/var/lib/hindsight/codex-a codex auth login
CODEX_HOME=/var/lib/hindsight/codex-b codex auth login

export HINDSIGHT_API_LLM_PROVIDER=openai-codex
export HINDSIGHT_API_LLM_CODEX_HOME=/var/lib/hindsight/codex-a
export HINDSIGHT_API_LLM_1_PROVIDER=openai-codex
export HINDSIGHT_API_LLM_1_CODEX_HOME=/var/lib/hindsight/codex-b
export HINDSIGHT_API_LLM_STRATEGY='{"mode": "failover"}'
```

令牌刷新按身份验证文件路径协调，因此两个配置会分别刷新，互不覆盖。故障转移遵循通用的多 LLM 行为：前一个成员用尽自身重试并报错后，才会尝试下一个成员。系统没有单独的配额分类器或冷却机制，因此达到速率限制的主配置会在每个请求开始时再次重试（并失败），然后才由回退配置处理请求。

### 设置 Meta Model API {#meta-model-api-setup}

[Meta Model API](https://ai.developer.meta.com) 通过 OpenAI 兼容端点提供 Muse Spark 模型。请先在 Model API 控制面板获取密钥，然后：

```bash
export HINDSIGHT_API_LLM_PROVIDER=meta
export HINDSIGHT_API_LLM_API_KEY=your-meta-model-api-key
export HINDSIGHT_API_LLM_MODEL=muse-spark-1.3
```

默认基础 URL 为 `https://api.meta.ai/v1`。可用模型包括 `muse-spark-1.3`（推荐）、`muse-spark-1.2`、`muse-spark-1.1`，以及 1.3 和 1.2 的折扣版 `-contributor` 变体；这些变体允许使用你的提示词和补全内容进行训练。所有模型的上下文窗口均为 1,048,576 个 token。

#### 必须设置的参数 {#required-knobs}

Muse Spark **总是在回复前进行推理**。以下所有设置都由这一特性决定，因此应将它们视为必需项，而非可选的调优参数：

| 变量 | 设置值 | 原因 |
|----------|-----------|-----|
| `HINDSIGHT_API_REFLECT_LLM_TIMEOUT` | `300` | Reflect 的默认值为 30s。Muse Spark 的最终答案合成耗时更久；重试后调用仍会失败，而非降低要求继续运行，Reflect 将不会返回任何内容。 |
| `HINDSIGHT_API_LLM_TIMEOUT` | `300` | 全局超时（默认 120s）也涵盖存入和整合，这两项操作在此模型上的耗时比非推理模型更长。 |
| `HINDSIGHT_API_LLM_REASONING_EFFORT` | 不设置，或设为 `minimal`/`low`/`medium`/`high`/`xhigh` | `none` 会被拒绝并返回 `HTTP 400`。保持未设置可让模型自行决定推理深度。 |
| `HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS` | 保留 `64000` 默认值 | 推理 token 会计入**输出**预算。若将此值调得过低，回复可能完全没有内容。 |

#### 其他说明 {#good-to-know}

- **自动缓存提示词。** 无需设置密钥、开关或分界点；Meta 会自行复用匹配的提示词前缀。因此，下方能力表不会列出显式提示缓存支持，但仍可享受缓存带来的好处。
- **不提供 Batch API 或嵌入端点。** 嵌入仍由你配置的 `HINDSIGHT_API_EMBEDDINGS_PROVIDER` 提供。
- **不接受递归 JSON Schema**（返回 `HTTP 400`）。Hindsight 的代码路径不会发送此类 Schema，只有在你添加自引用响应模型时才需要注意。
- **调用耗时可能更长。** 即使提示词很简单，模型用于推理的 token 也可能多于最终返回的 token。

### 设置 Cursor（Cursor 订阅） {#cursor-setup-cursor-subscription}

通过无头打印模式下运行的 `cursor-agent` CLI，使用 **Cursor 订阅**提供 Hindsight 的提取、整合和反思调用。无需 API 密钥，也无需建立第二种按 token 计费的关系。

其方向与 [Cursor 集成](/sdks/integrations/cursor)正好相反：后者让 Cursor 作为 Hindsight 的*客户端*。此处则是由 Hindsight 调用 Cursor 作为模型后端。

**前提条件：**
- 有效的 Cursor 订阅（免费计划也可使用，但只能选择 `auto`，详见下文）
- 已在运行 Hindsight 的同一操作系统用户下安装并登录 `cursor-agent`

**设置步骤：**

1. **安装 CLI：**
   ```bash
   curl https://cursor.com/install -fsS | bash
   ```

2. **登录：**
   ```bash
   cursor-agent login
   ```

3. **验证：**
   ```bash
   cursor-agent --version
   cursor-agent --list-models
   ```

4. **配置 Hindsight：**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=cursor
   export HINDSIGHT_API_LLM_MODEL=auto
   # 智能体 CLI 每轮需要 15–30s，远超 Reflect 默认的 30s 超时。
   export HINDSIGHT_API_LLM_TIMEOUT=300
   export HINDSIGHT_API_REFLECT_LLM_TIMEOUT=180
   # 无需 API 密钥。也可改用密钥进行身份验证：
   # export HINDSIGHT_API_LLM_API_KEY=...   # 或 CURSOR_API_KEY
   ```

**重要说明：**

- **调高超时。** 每次调用都会启动一个 `cursor-agent` 轮次，使用 `auto` 时需要 15–30s，比 Chat Completions 请求慢，也超过 `HINDSIGHT_API_REFLECT_LLM_TIMEOUT` 默认的 30s。若保留默认值，Reflect 的第一次迭代会先因超时而重试，之后才恢复。
- **结构化输出和工具调用通过提示词模拟。** CLI 没有 `response_format`、JSON Schema、temperature 或工具定义标志，只有用于描述封装格式的 `--output-format text|json|stream-json`。Hindsight 会把 Schema（或工具列表）放入提示词，再解析模型返回的 JSON；解析失败时会重试。这种方式不如原生 Schema 可靠，因此建议 Reflect（最依赖工具的操作）使用明确命名的强模型，而不是 `auto`。
- **免费计划只能使用 `auto`。** 指定 `--model` 会返回 `Named models unavailable Free plans can only use Auto`。付费计划可使用 `cursor-agent --list-models` 列出的任意 ID。
- **会关闭智能体自身的工具。** `cursor-agent` 是智能体而非补全端点：它带有 Shell、Read、Write、Delete、网页抓取等工具；`--mode ask` **不能**关闭工具，无头运行时仍会读取工作目录中的文件。因此，Hindsight 会在空临时工作区中运行 CLI，为其指定独立的 `CURSOR_CONFIG_DIR`（使其无法读取你的 `~/.cursor` 配置、钩子或会话历史），并在其中写入 `cli-config.json`，按名称禁用所有工具。这相当于 `claude-code` 提供方传给 SDK 的 `tools=[]`；由于存入提示词基于你保存在 Hindsight 中的文本构建，因此这一点很重要。
- 用量计入你的 Cursor 订阅。
- 不支持推理强度设置：CLI 没有对应标志；若设置了 `HINDSIGHT_API_LLM_REASONING_EFFORT`，Hindsight 会在启动时警告一次。
- 嵌入和重排仍使用 Hindsight 单独配置的提供方。

### 设置 SuperGrok 订阅（设备码 OAuth） {#supergrok-subscription-setup-device-code-oauth}

通过 **SuperGrok 订阅**（设备码 OAuth）提供 LLM 调用，无需 API 密钥。如需通过 API 密钥访问 `api.x.ai`，请使用 `provider: openai`，并设置 `HINDSIGHT_API_LLM_BASE_URL=https://api.x.ai/v1`。**此处的提供方用于订阅登录**，与 `openai-codex`（ChatGPT 订阅）及 `claude-code`（Claude 订阅）同类。两种路径访问同一个公开端点，区别仅在凭据：一种是在浏览器中授权一次的固定费率个人订阅，另一种是按 token 计量的密钥。

身份验证使用 xAI 自己的 OIDC 发行方 `https://auth.x.ai` 和 RFC 8628 设备码流程；公开 OAuth 客户端 ID 发布在 xAI 的 Apache-2.0 许可 Grok CLI 源代码中。Hindsight 使用自己的凭据文件，绝不会读写 Grok CLI 的 `~/.grok/auth.json`。

:::note 订阅权限

xAI 可能会根据 SuperGrok 订阅层级限制 `api.x.ai` 的访问：OAuth 授权本身可能有效，但请求仍会被拒绝并返回 HTTP 403。Hindsight 会将其报告为单独的权限错误并说明原因，而不是凭据错误；同时不会重试，也不会丢弃令牌。遇到此问题时，请确认账户层级，或改用 API 密钥提供方。

用量计入你的 SuperGrok 订阅限额。账户支出上限阻止调用时，Hindsight 会报告单独的配额错误，并保留凭据。

:::

**前提条件：**
- 有效的 SuperGrok 订阅
- 登录所用的计算机上有浏览器（设备码流程需要交互式批准；运行中的服务不会执行该流程）

**设置步骤：**

1. **在要保存凭据的主机上登录一次：**
   ```bash
   python -m hindsight_api.engine.providers.xai_oauth_auth login
   ```
   命令会显示验证 URL 和用户代码，等待你批准，然后以仅所有者可访问的权限写入 `~/.hindsight/xai_oauth.json`。

2. **配置 Hindsight：**
   ```bash
   export HINDSIGHT_API_LLM_PROVIDER=xai-oauth
   # export HINDSIGHT_API_LLM_MODEL=grok-4.5   # 默认值为 grok-4.5
   # 无需 API 密钥
   ```

3. **启动 Hindsight：**
   ```bash
   hindsight-api
   ```

**重要说明：**
- 访问令牌会自动刷新：通常在过期前 60 秒刷新（或按配置的请求超时时间提前刷新，以较长者为准）；收到 HTTP 401 后也会刷新一次。多个已配置的通道可以安全地共用一个凭据文件：刷新时会取得咨询锁，并在锁内重新读取文件，因此同级通道不会各自重复刷新。
- 运行中的服务**绝不会**启动设备码流程。若只有重新登录才能恢复服务，调用会失败并显示需要运行的确切命令。
- 通过 `provider: openai` 访问 `api.x.ai` 时不会这样处理；此提供方会发送该成员配置的 `reasoning_effort`，因此此设置在这里生效。唯一不会转发的值是 `none`：xAI 会直接拒绝它（HTTP 400），所以此通道按 API 要求省略该字段。
- 目前只实现了非流式调用。流式响应不会提供 `prompt_tokens_details`，因此缓存 token 的统计值会偏低。

**可选的环境变量覆盖项：**

| 变量 | 用途 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_XAI_OAUTH_BASE_URL` | 指向其他上游；优先级高于 `HINDSIGHT_API_LLM_BASE_URL`。 | `https://api.x.ai/v1` |
| `HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH` | 更改凭据存储位置，读取和写入都会使用此路径。 | `~/.hindsight/xai_oauth.json` |
| `HINDSIGHT_API_XAI_OAUTH_CLIENT_ID` | 覆盖登录和刷新时使用的 OAuth 客户端 ID。 | xAI 发布的公开客户端 ID |
| `HINDSIGHT_API_XAI_OAUTH_SCOPE` | 覆盖登录时请求的 scope 字符串。 | `openid profile email offline_access grok-cli:access api:access` |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_SKEW_SECONDS` | 提前这么多秒刷新。很少访问提供方的部署可适当调大。 | `60` |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_TIMEOUT_SECONDS` | 发现、登录和刷新请求的超时时间。 | `20` |

#### 部署说明 {#deployment-note}

凭据保存在主机本地文件中，只有交互式登录才能创建该文件。因此，容器化引擎需要挂载在已完成登录的主机上创建的凭据存储（也可在容器内交互式登录一次），并将 `HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH` 指向该文件。挂载必须**可写**：与 Grok CLI 自己的文件不同，Hindsight 需要在此存储中写入每次轮换后的令牌，因此只读挂载会在当前令牌过期后导致调用失败。

xAI 每次刷新都会颁发一个**新的刷新令牌**，并使被替换的令牌失效。因此，各个副本必须共用同一个凭据文件，而不能各自从一次登录结果的副本启动：只要另一个副本刷新令牌，副本文件就会失效，必须重新登录。支持的部署方式是使用一个共享的可写卷；如果无法提供该卷，请只在一个副本上使用此提供方，并让其他副本使用 API 密钥通道。

### 设置 Azure OpenAI {#azure-openai-setup}

Azure OpenAI 通过 **`openai`** 提供方访问；没有 `azure` 提供方，若设置该值，启动时会报错：`Invalid LLM provider: azure`。

容易出错的地方是基础 URL。Azure 不会在资源根路径提供 OpenAI API，因此 Azure 门户中显示的端点不能单独使用：

| `HINDSIGHT_API_LLM_BASE_URL` | 结果 |
|---|---|
| `https://<resource>.openai.azure.com` | `404 Resource not found` |
| `https://<resource>.openai.azure.com/openai/deployments/<deployment>` | `404 Resource not found`（缺少 `api-version`） |
| `https://<resource>.openai.azure.com/openai/v1` | 可用 |
| `https://<resource>.openai.azure.com/openai/deployments/<deployment>?api-version=<version>` | 可用 |

**建议使用 v1 端点：**

```bash
export HINDSIGHT_API_LLM_PROVIDER=openai
export HINDSIGHT_API_LLM_API_KEY=<azure-openai-resource-key>
export HINDSIGHT_API_LLM_MODEL=<deployment-name>
export HINDSIGHT_API_LLM_BASE_URL=https://<resource>.openai.azure.com/openai/v1
```

**或者使用指定部署的格式**。保留 `api-version` 查询字符串；Hindsight 会从基础 URL 中解析该值并传给 SDK：

```bash
export HINDSIGHT_API_LLM_BASE_URL=https://<resource>.openai.azure.com/openai/deployments/<deployment>?api-version=2025-01-01-preview
```

**重要说明：**
- `HINDSIGHT_API_LLM_MODEL` 应填写你的**部署名称**，而非模型名称。例如，将 `gpt-4o` 部署为 `my-gpt4o` 后，配置值应为 `my-gpt4o`。
- 密钥应使用 Azure OpenAI **资源**密钥（`az cognitiveservices account keys list -n <resource> -g <group>`）。API Management 订阅密钥属于另一种凭据：如果前面有 APIM，基础 URL 必须指向 APIM 路由，并且 APIM 必须转发 `api-key` 标头。请先直接请求 Azure 端点，以确认是哪一层出错。
- 网关和代理必须保留相同的路径格式（`/openai/v1` 或 `/openai/deployments/...?api-version=`）。
- Azure OpenAI 的 GPT 部署接受 `prompt_cache_key`（可改进 GPT-5.6 及更高版本的缓存路由），但同一个 `*.openai.azure.com` 端点也可能提供不接受此参数的非 OpenAI Foundry 模型（DeepSeek、Llama、Mistral）；这类模型会返回 `unrecognized_request_argument`。单看主机名无法区分，因此对于 Azure 主机，[`HINDSIGHT_API_LLM_CACHE_AFFINITY`](./configuration#llm-provider) 会将 `auto` 解析为 `none`。如果部署提供的是 OpenAI 模型，请显式设置为 `openai_prompt_cache_key`。

### 设置 Vertex AI（Google Cloud） {#vertex-ai-setup-google-cloud}

Google Cloud 的 Vertex AI 通过原生 Google GenAI SDK 提供 Gemini 模型。

**前提条件：**
- 已启用 Vertex AI API 的 GCP 项目
- 凭据具备 IAM 角色 `roles/aiplatform.user`

**环境变量：**

| 变量 | 说明 | 必需 |
|----------|-------------|----------|
| `HINDSIGHT_API_LLM_VERTEXAI_PROJECT_ID` | GCP 项目 ID | 是 |
| `HINDSIGHT_API_LLM_VERTEXAI_REGION` | GCP 区域（例如 `us-central1`） | 否（默认值：`us-central1`） |

**身份验证方式：**

1. **应用默认凭据（ADC）** — 建议用于开发环境
   ```bash
   # 设置 ADC
   gcloud auth application-default login

   # 配置 Hindsight
   export HINDSIGHT_API_LLM_PROVIDER=vertexai
   export HINDSIGHT_API_LLM_MODEL=gemini-3.1-flash-lite
   export HINDSIGHT_API_LLM_VERTEXAI_PROJECT_ID=your-project-id
   ```

2. **服务账户密钥** — 建议用于生产环境
   ```bash
   # 创建服务账户并下载密钥
   gcloud iam service-accounts create hindsight-api
   gcloud projects add-iam-policy-binding your-project-id \
     --member="serviceAccount:hindsight-api@your-project-id.iam.gserviceaccount.com" \

     --iam-account=hindsight-api@your-project-id.iam.gserviceaccount.com

   export HINDSIGHT_API_LLM_PROVIDER=vertexai
   export HINDSIGHT_API_LLM_MODEL=gemini-3.1-flash-lite
   export HINDSIGHT_API_LLM_VERTEXAI_PROJECT_ID=your-project-id
   export HINDSIGHT_API_LLM_VERTEXAI_SERVICE_ACCOUNT_KEY=/path/to/key.json
   ```

**说明：**
- 模型名称可以带有可选的 `google/` 前缀（例如 `google/gemini-3.1-flash-lite`）；系统会自动移除此前缀。
- 原生 SDK 会自动刷新令牌。
- 如果提供了服务账户凭据，则使用这些凭据；否则回退到 ADC。

## 嵌入模型 {#embedding-model}

将文本转换为稠密向量表示，以执行语义相似度检索。

**默认值：**`BAAI/bge-small-en-v1.5`（384 维，约 130MB）

### 支持的提供方 {#supported-providers}

| 提供方 | 说明 | 适用场景 |
|----------|-------------|----------|
| `local` | SentenceTransformers（默认） | 开发、低延迟 |
| `onnx` | 进程内 ONNX Runtime 嵌入器（无需 Ollama/TEI/API sidecar） | 轻量级本地 CPU、多语言 |
| `openai` | OpenAI embeddings API | 生产环境、高质量 |
| `openai-codex` | 通过 Codex OAuth 使用 OpenAI 嵌入（ChatGPT Plus/Pro，无需 API 密钥） | 现有 ChatGPT/Codex 订阅用户 |
| `openrouter` | OpenRouter 嵌入（OpenAI 兼容网关） | 多提供方配置 |
| `cohere` | Cohere embeddings API | 生产环境、多语言 |
| `google` | Google 嵌入（Gemini API 或 Vertex AI） | 生产环境、多语言、高质量 |
| `tei` | HuggingFace Text Embeddings Inference | 生产环境、自托管 |
| `zeroentropy` | ZeroEntropy zembed-1 | 生产环境、高质量检索 |
| `litellm` | LiteLLM 代理（统一网关） | 多提供方配置 |
| `litellm-sdk` | LiteLLM SDK（直接调用 API，无需代理） | 多提供方、配置更简单 |

### 本地模型 {#local-models}

| 模型 | 维度 | 用途 |
|-------|------------|----------|
| `BAAI/bge-small-en-v1.5` | 384 | 默认模型，速度快、质量好 |
| `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | 384 | 多语言（50 多种语言） |

### OpenAI 模型 {#openai-models}

| 模型 | 维度 | 用途 |
|-------|------------|----------|
| `text-embedding-3-small` | 1536 | OpenAI 默认模型，成本效益高 |
| `text-embedding-3-large` | 3072 | 质量更高，费用也更高 |
| `text-embedding-ada-002` | 1536 | 旧版模型 |

### Google 模型 {#google-models}

| 模型 | 维度 | 用途 |
|-------|------------|----------|
| `gemini-embedding-001` | 768（可配置） | Google 默认模型，通用 |
| `gemini-embedding-2-preview` | 768（可配置） | Gemini Embedding 2 系列；多模态，每个输入对应一个向量 |

Google 的 `gemini-embedding-001` 支持通过截断配置输出维度；Google 建议使用 768、1536 或 3072，并通过 `HINDSIGHT_API_EMBEDDINGS_GEMINI_OUTPUT_DIMENSIONALITY` 配置。默认值为 768。

Gemini API 和 Vertex AI 均支持 `gemini-embedding-2` 系列，包括 `gemini-embedding-2-preview`。这些模型会聚合多个输入的请求，因此 Hindsight 会自动调整为每次调用仅嵌入一个输入，以确保每条事实的向量保持对应。

### Cohere 模型 {#cohere-models}

| 模型 | 维度 | 用途 |
|-------|------------|----------|
| `embed-english-v3.0` | 1024 | 英文文本 |
| `embed-multilingual-v3.0` | 1024 | 100 多种语言 |

### ZeroEntropy 模型 {#zeroentropy-models}

| 模型 | 维度 | 用途 |
|-------|------------|----------|
| `zembed-1` | 默认 1280（可配置为 2560/1280/640/320/160/80/40） | 高质量非对称检索 |

Hindsight 将存入的记忆文本作为 `document` 输入发送给 ZeroEntropy，将召回/检索文本作为 `query` 输入发送。ZeroEntropy API 的默认维度为 2560；Hindsight 默认为 1280，使 pgvector HNSW 无需更改向量扩展即可运行。

:::warning 嵌入维度
Hindsight 会在启动时自动检测嵌入维度并调整数据库架构。保存记忆后，若要更改维度就必须丢失数据。
:::

**配置示例：**

```bash
# Local provider (default)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=local
export HINDSIGHT_API_EMBEDDINGS_LOCAL_MODEL=BAAI/bge-small-en-v1.5

# ONNX provider (in-process local CPU, no Ollama/TEI/API sidecar; pip install hindsight-api-slim[local-onnx])
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=onnx
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID=intfloat/multilingual-e5-small
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=384

# OpenAI
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=openai
export HINDSIGHT_API_EMBEDDINGS_OPENAI_API_KEY=sk-xxxxxxxxxxxx
export HINDSIGHT_API_EMBEDDINGS_OPENAI_MODEL=text-embedding-3-small

# Cohere
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=cohere
export HINDSIGHT_API_COHERE_API_KEY=your-api-key
export HINDSIGHT_API_EMBEDDINGS_COHERE_MODEL=embed-english-v3.0

# Google (API key auth)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=google
export HINDSIGHT_API_EMBEDDINGS_GEMINI_API_KEY=xxxxxxxxxxxx
export HINDSIGHT_API_EMBEDDINGS_GEMINI_MODEL=gemini-embedding-001

# Google (Vertex AI auth - auto-detected when project ID is set)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=google
export HINDSIGHT_API_EMBEDDINGS_GEMINI_MODEL=gemini-embedding-001
export HINDSIGHT_API_EMBEDDINGS_VERTEXAI_PROJECT_ID=your-gcp-project-id

# TEI (self-hosted)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=tei
export HINDSIGHT_API_EMBEDDINGS_TEI_URL=http://localhost:8080

# ZeroEntropy
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=zeroentropy
export HINDSIGHT_API_EMBEDDINGS_ZEROENTROPY_API_KEY=your-api-key
export HINDSIGHT_API_EMBEDDINGS_ZEROENTROPY_MODEL=zembed-1
export HINDSIGHT_API_EMBEDDINGS_ZEROENTROPY_DIMENSIONS=1280

# LiteLLM proxy
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=litellm
export HINDSIGHT_API_LITELLM_API_BASE=http://localhost:4000
export HINDSIGHT_API_EMBEDDINGS_LITELLM_MODEL=text-embedding-3-small

# LiteLLM SDK (direct, no proxy)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=litellm-sdk
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_API_KEY=sk-xxxxxxxxxxxx
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_MODEL=openai/text-embedding-3-small

# AWS Bedrock (via LiteLLM SDK; credentials come from the environment or an IAM role)
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=litellm-sdk
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_MODEL=bedrock/amazon.titan-embed-text-v2:0
```

:::tip AWS Bedrock 应用推理配置文件

如果组织的 Service Control Policy 在存在[应用推理配置文件](https://docs.aws.amazon.com/bedrock/latest/userguide/inference-profiles-support.html)后仍禁止对裸模型 ID 调用 `bedrock:InvokeModel`，请保持 `..._MODEL` 不变，并单独添加配置文件 ARN：

```bash
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=litellm-sdk
# Stays a recognizable model id — this is what picks the request format
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_MODEL=bedrock/amazon.titan-embed-text-v2:0
# The profile actually invoked
export HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_MODEL_ID=arn:aws:bedrock:eu-west-1:123456789012:application-inference-profile/abc123
```

两者必须分开设置，因为 Bedrock 的嵌入请求和响应格式因模型系列（Titan、Cohere、TwelveLabs、Nova）而异；系统通过模型 ID 判断系列。配置文件 ARN 不透明且绑定账户，不能用于识别模型系列；应将 ARN 放入 `..._MODEL_ID`，并让 `..._MODEL` 保留真实模型名称。

聊天模型无需此设置：将 `HINDSIGHT_API_LLM_MODEL=bedrock/converse/<arn>`，因为 Converse API 对所有模型使用相同格式。

:::

所有选项（包括 Azure OpenAI 和自定义端点）请参阅[配置](./configuration#embeddings)。

如需可运行的 Docker Compose 配置，通过自托管 TEI sidecar 同时提供嵌入和重排服务，请参阅 [`docker/docker-compose/tei/`](https://github.com/vectorize-io/hindsight/tree/main/docker/docker-compose/tei)。

### SiliconFlow 模型 {#siliconflow-models}

SiliconFlow 通过兼容 Cohere 的 `/rerank` 端点托管多种开放权重重排模型：

| 模型 | 用途 |
|-------|----------|
| `BAAI/bge-reranker-v2-m3` | 多语言，优秀的默认选择 |
| `Qwen/Qwen3-Reranker-8B` | 规模更大，准确率更高 |

### TypeSafe 模型 {#typesafe-models}

TypeSafe 并非 `/rerank` 端点；它会针对某个*状态*回答类型化的*问题*。Hindsight 将候选项设为 Choice 问题的选项，因此返回的概率分布即为排序结果。候选池不超过 250 个选项且符合上下文 token 预算时，一次调用即可为整个候选池排序。候选池较大或文档较长时，系统会将其分组，并在最终排序阶段让每组的头部候选项晋级，同时截断 token 以适配上下文窗口。

| 模型 | 用途 |
|-------|----------|
| `jev-latest` | 默认值；跟踪当前 Jev 版本 |

设置 `HINDSIGHT_API_RERANKER_TYPESAFE_PRUNE_CANDIDATES=true` 会增加第二个问题，在相关性结束处截断排序列表，使 Recall 只返回相关候选项。此功能默认关闭，因为会明显缩小 Recall 返回的内容。完整行为及权衡请参阅[配置](/developer/configuration#typesafe)。

TypeSafe 的分数表示单次 Recall 中的名次，而非相关性分数，因此使用 TypeSafe 时 Recall 不会发布 `scores.reranker`，并且会拒绝 `min_scores.reranker`，返回 HTTP 400。

| 模型 | 用途 |

# SiliconFlow (Cohere-compatible /rerank endpoint)
export HINDSIGHT_API_RERANKER_PROVIDER=siliconflow
