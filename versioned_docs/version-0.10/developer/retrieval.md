# 记忆召回：Hindsight 如何检索记忆 {#recall-how-hindsight-retrieves-memories}

调用 `recall()` 时，Hindsight 会并行使用多种搜索策略查找最相关的记忆，无论你的查询采用何种措辞。

<Figure doc={tempr} />

---

## 记忆召回的挑战 {#the-challenge-of-memory-recall}

不同查询需要不同的搜索方式：

- **「Alice 在 Google 工作」** → 需要精确匹配名称
- **「Alice 在哪里工作？」** → 需要理解语义
- **「Alice 去年春天做了什么？」** → 需要时间推理
- **「Alice 为什么离开？」** → 需要追踪因果关系

没有一种搜索方法能同时很好地处理所有情况。Hindsight 会**并行运行四种互补策略**，并融合它们的结果。

---

## 四种搜索策略 {#four-search-strategies}

### 语义搜索 {#semantic-search}

**作用：**理解词语背后的*含义*，而不仅是词语本身。

**最适合：**
- 概念匹配：「Alice 的职业」→「Alice 是软件工程师」
- 不同表述：「Bob 的专长」→「Bob 擅长机器学习」
- 同义词：「会议」匹配「研讨会」、「讨论」、「聚会」

**为什么这很重要：**你可以自然地提问，无需精确匹配关键词。

---

### 关键词搜索 {#keyword-search}

**作用：**查找精确的术语和名称，即使它们的拼写很独特。

**最适合：**
- 专有名词：「Google」、「Alice Chen」、「MIT」
- 技术术语：「PostgreSQL」、「HNSW」、「TensorFlow」
- 唯一标识：URL、产品名称、特定短语

**为什么这很重要：**即使与你的查询在语义上相距较远，也能确保不会遗漏提及特定名称或术语的结果。

**后端：**Hindsight 提供五种可插拔的 BM25 后端，通过 `HINDSIGHT_API_TEXT_SEARCH_EXTENSION` 选择：

| 后端 | 使用的技术 | 是否兼容 Citus？ |
|---|---|---|
| `native` | PostgreSQL `tsvector` + `ts_rank_cd`（TF-IDF，并非真正的 BM25） | 是 |
| `vchord` | `vchord_bm25` 扩展 | 否 |
| `pg_textsearch` | Timescale `pg_textsearch` 扩展 | 否 |
| `pgroonga` | PGroonga（Groonga）全文扩展，`TokenBigram` 多语言分词器 | 否 |
| `pg_search` | ParadeDB `pg_search` 扩展，可通过 `HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_TOKENIZER` 配置分词器（如 `jieba`、`chinese_compatible`、`ngram`） | 是 |

如果需要在水平扩展的 Postgres（Citus）集群上使用真正的 BM25 排序，`pg_search` 是唯一选项。参阅 [`pg_search` docker-compose 示例](https://github.com/vectorize-io/hindsight/tree/v0.10.3/docker/docker-compose/pg_search)。

---

### 图遍历 {#graph-traversal}

**作用：**沿着实体之间的关联查找间接相关的信息。

**最适合：**
- 间接关系：「Alice 做什么工作？」→ Alice → Google → Google 的产品
- 实体探索：「Bob 的同事」→ Bob → 同事 → 共同项目
- 多跳推理：「Alice 所在团队的成果」

**为什么这很重要：**通过知识图谱检索在语义或词汇上不相似，但在**结构上相连**的事实。

**示例：**即使 Alice 和她的经理从未一起被提及，图遍历也可以通过共同项目或团队关系找到这位经理。

---

### 时间搜索 {#temporal-search}

**作用：**理解时间表达，并按事件发生时间过滤。

**最适合：**
- 历史查询：「Alice 在 2023 年做了什么？」
- 时间范围：「去年春天发生了什么？」
- 相对时间：「Bob 去年从事了什么工作？」
- 前后关系：「Alice 加入 Google 之前发生了什么？」

**工作方式：**查询包含时间信息时，Hindsight 会将其解析为日期窗口，然后检索时间与该窗口重叠的记忆。在窗口内，它根据**与查询的语义相关性**选择候选，而不是根据新旧程度，因此最相关的窗口内记忆不会仅因其他记忆更新而被丢弃。接着，它会**让选择覆盖整个窗口范围**：将窗口分为时间分桶，优先从每个非空分桶中选出最强匹配。因此，「2023 年发生了什么？」这样的查询会呈现全年各时期的记忆，而不是集中在数据最密集的一段时间。时间也会作为*评分*信号：越接近窗口中心的记忆获得的加权越多，但幅度较小（参阅[时间接近程度信号](#temporal-proximity-signal)）。

**为什么这很重要：**支持精确的历史查询，结果既相关，也能代表整个时期。对于时间戳高度集中的记忆库（例如大量内容以同一日期批量导入），它仍然快速且有效：由于优先按相关性选择，即使时间窗口匹配了记忆库的大部分内容，也会返回最佳匹配，而不是任意截取一部分。

---

## 结果融合 {#result-fusion}

四种策略运行后，结果会被**融合**：

- 在**多种策略**中出现的记忆排名更高（形成共识）
- **排名比原始分数更重要**（能适应不同评分体系）
- 使用考虑查询与记忆交互的神经模型对最终结果**重排序**

**为什么融合很重要：**一条既语义相似、又提及正确实体的事实，会比仅语义相似的事实排名更高。

---

## 为什么需要多种策略？ {#why-multiple-strategies}

考虑查询：**「Alice 去年春天谈到 Python 时说了什么？」**

- **语义搜索**查找 Alice 对编程的看法
- **关键词搜索**确保内容确实提及「Python」
- **图搜索**连接 Alice → 编程语言 → 相关实体
- **时间搜索**将结果限定在「去年春天」

四种策略的**融合**能准确找到你需要的内容，即使任何单一策略都不足以完成任务。

---

## Token 预算管理 {#token-budget-management}

Hindsight 面向 AI 智能体构建。传统搜索系统返回「top-k」结果，但智能体以 token 而非结果数量衡量信息。智能体的上下文窗口以 token 计量，Hindsight 也以同样方式衡量返回的结果。

**工作方式：**
- 优先选择排名最高的记忆
- token 预算耗尽时停止
- 由你指定上下文预算，Hindsight 用最相关的记忆填充它

**可控制的参数：**
- `max_tokens`：返回多少记忆内容（默认 4096 token）
- `budget`：搜索深度级别（low、mid、high）
- `types`：按 world、experience、observation 过滤，或返回全部类型
- `tags`：按可见性标签过滤记忆
- `tags_match`：标签匹配方式（全部选项参阅[记忆召回 API](./api/recall)）

### 扩展上下文：文本块 {#expanding-context-chunks}

记忆是提炼后的事实，简洁，但有时会缺少细微含义。当智能体需要更深入的上下文时，可以选择检索原始材料。

**文本块**会返回生成每条记忆的原始文本，适用于提炼后的事实丢失重要细节的情况：

```
记忆：「Alice 比起 JavaScript 更喜欢 Python」
文本块：「Alice 提到，比起 JavaScript，她更喜欢 Python，主要是因为
         Python 的数据科学生态。不过她承认 JS 更适合前端开发，
         而且最近一直在学习 TypeScript。」
```

使用 `include_chunks=True`，并通过 `max_chunk_tokens` 控制文本块的 token 预算。这适合生成需要逐字引用的回答，或上下文很重要的场景（例如「Alice 对这个项目究竟说了什么？」）。

## 调整记忆召回：质量与延迟 {#tuning-recall-quality-vs-latency}

不同场景需要在**召回质量**与**响应速度**之间做出不同权衡。以下两个参数控制这一点。

### Budget：搜索深度 {#budget-search-depth}

控制 Hindsight 探索记忆库的深度，影响图遍历深度、候选池大小和交叉编码器重排序：

| Budget | 适用场景 | 权衡 |
|--------|----------|------|
| **low** | 快速查找、简单查询 | 速度快，可能遗漏间接关联 |
| **mid** | 大多数查询，平衡选择 | 覆盖良好，速度合理 |
| **high** | 需要深入探索的复杂查询 | 全面，但较慢 |

**示例：**「Alice 的经理所在团队从事了什么工作？」适合使用 high 预算，以遍历多个跳点（Alice → 经理 → 团队 → 项目）并评估更多候选。

### Max Tokens：上下文窗口大小 {#max-tokens-context-window-size}

控制返回多少记忆内容：

| Max Tokens | 约合文本页数 | 适用场景 | 权衡 |
|------------|--------------|----------|------|
| **2048** | 约 2 页 | 聚焦的回答、快速 LLM | 记忆较少，速度更快 |
| **4096**（默认） | 约 4 页 | 平衡的上下文 | 覆盖良好，标准选择 |
| **8192** | 约 8 页 | 全面的上下文 | 记忆更多，LLM 更慢 |

**示例：**「总结关于 Alice 的全部信息」适合使用较高的 max_tokens，以包含更多事实。

### 两个独立维度 {#two-independent-dimensions}

Budget 和 max_tokens 控制记忆召回的不同方面：

| 参数 | 控制的内容 | 对延迟的影响 | 示例 |
|------|------------|--------------|------|
| **Budget** | 探索记忆的深入程度 | 搜索时间 | 高预算找到 Alice → 经理 → 团队 → 项目 |
| **Max Tokens** | 返回的上下文数量 | LLM 处理时间 | 高 token 数向智能体返回更多记忆 |

**两者相互独立。**常见组合：

| Budget | Max Tokens | 场景 |
|--------|------------|------|
| high | low | 深入搜索，只返回最佳结果 |
| low | high | 快速搜索，返回找到的全部内容 |
| high | high | 全面的研究查询 |
| low | low | 快速聊天机器人响应 |

### 推荐配置 {#recommended-configurations}

| 场景 | Budget | Max Tokens | 原因 |
|------|--------|------------|------|
| **聊天机器人回复** | low | 2048 | 响应快，上下文聚焦 |
| **文档问答** | mid | 4096 | 平衡覆盖范围与速度 |
| **研究查询** | high | 8192 | 全面，支持多跳推理 |
| **实时搜索** | low | 2048 | 尽量降低延迟 |

## 深入理解评分与排序 {#scoring--ranking-deep-dive}

本节详细说明 Hindsight 如何将原始检索结果转换为最终排名列表。流水线包含三个阶段：**RRF 融合**、**交叉编码器重排序**和**组合评分**。

### 阶段 1：倒数排名融合（RRF） {#stage-1-reciprocal-rank-fusion-rrf}

所有策略并行运行后，其结果通过[倒数排名融合](https://plg.uwaterloo.ca/~gvcormac/cormacksigir09-rrf.pdf)合并。RRF 奖励在多种策略中排名靠前的条目，以此组合排名列表，不依赖原始分数（不同检索方法的原始分数无法直接比较）。

**公式：**

```
score(d) = Σ  1 / (k + rank_i(d))
           i
```

其中：
- **k = 60**（平滑常数，防止排名最高的条目占据过大的优势）
- **rank_i(d)** = 文档 *d* 在策略 *i* 中的位置（从 1 开始）
- 求和覆盖所有包含 *d* 的策略

**在 RRF 内，四种策略的权重相等。**融合使用排名位置，而不是结果来源，因此任何策略都不会获得隐含的倍数加权。不过，你可以用 [`HINDSIGHT_API_RECALL_STRATEGY_BOOSTS`](./configuration) 有意偏向某个来源。该加权在独立阶段应用：先在重排序预过滤的候选上限截断之前应用，再在交叉编码器重排序之后应用，而不参与上述 RRF 融合。上限截断前的步骤只在合并后的候选池超过上限时运行，且不会改写 RRF 分数。直接传递结果的重排序器（`rrf` 模式、`rrf` 提供商，或降级到 `rrf` 的故障转移链）会跳过重排序后的调整：此时，候选池在上限内，该设置不产生作用；超过上限时，它只改变保留哪些候选。

**为什么选择 RRF，而不是合并原始分数？**各检索策略的分数尺度不同（余弦相似度、BM25 tf-idf、图激活值）。BM25 的 12.5 分与余弦相似度 0.85 并不意味着同一件事。RRF 只使用排名位置，避免了这一问题，因此无需校准就能适应任何评分体系。

**示例：**一条记忆在语义搜索中排名第 1，在 BM25 中排名第 5：
```
RRF 分数 = 1/(60+1) + 1/(60+5) = 0.0164 + 0.0154 = 0.0318
```

一条仅在语义搜索中排名第 1 的记忆：
```
RRF 分数 = 1/(60+1) = 0.0164
```

第一条记忆排名更高，因为它在多种策略之间形成了**共识**。

---

### 阶段 2：交叉编码器重排序 {#stage-2-cross-encoder-reranking}

RRF 能给出良好的初始排名，但依据的是位置，而非对查询和文档的深入理解。交叉编码器将查询与每个候选配对评估，生成相关性分数。

**预过滤：**重排序之前，候选会按 RRF 分数截取前 **300** 条，以限制计算成本。可通过 `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 配置这个数量。如果设置了 [`HINDSIGHT_API_RECALL_STRATEGY_BOOSTS`](./configuration)，加权会在截取之前应用，使优先来源的候选更容易保留下来。加权作用于*排名*空间：先将该检索分支的排名除以对应级别的除数，再计算其 RRF 贡献，而不是缩放分数。因此，即使合并候选池远大于上限，也能从该分支中保留更靠后的结果，同时不会挤掉其他分支排名最高的命中。请求 `trace: true` 时，`rerank_prefilter` 阶段会报告保留和丢弃的候选数量、实际上限、生效的加权设置，以及保留下来的候选中各分支的构成。

**为什么在 RRF 后重排序？**RRF 依据位置，知道一条记忆在多个策略中排名不错，却不会真正将查询和记忆一起阅读。交叉编码器则会这样做：它接收查询与每个候选组成的配对，根据完整交互生成相关性分数。这能捕捉基于位置的融合所遗漏的细节。例如，一条记忆因匹配了常见词而在关键词搜索中排名第 1，但实际上与查询意图无关。

**分数归一化：**交叉编码器会输出原始 logit（可能为负值）。已处于 [0, 1] 范围内的分数，例如 Cohere、SiliconFlow、ZeroEntropy、Alibaba、Jina 等经过校准的外部 API 重排序器返回的分数，会原样传递，以保留绝对置信度。超出 [0, 1] 的原始 logit 会通过 sigmoid 函数归一化到 [0, 1]：

```
CE_normalized = 1 / (1 + e^(-raw_logit))
```

**批处理：**候选按批评分。本地重排序器每批 **32 对**，TEI 每批 **128 对**。

:::tip 没有交叉编码器？
在没有交叉编码器的环境中运行时（例如精简镜像且未配置外部重排序器），系统会回退到基于 RRF 的分数：根据候选的 RRF 排名，赋予分布于 [0.1, 1.0] 的合成分数，使下文的组合评分加权仍然有效。`HINDSIGHT_API_RECALL_STRATEGY_BOOSTS` 在这条路径上不会添加重排序后的调整。如果合并候选池在重排序器上限内，该设置不会改变任何结果；超过上限时，它只改变保留哪些候选，候选顺序仍由这些基于 RRF 的分数以及时效性、时间接近程度和证据共同决定。
:::

### 阶段 3：组合评分（加权） {#stage-3-combined-scoring-boosts}

归一化后的交叉编码器分数通过三个**乘法加权**调整，以加入交叉编码器看不到的信号：时效性、时间接近程度和证据强度。

**为什么使用乘法而不是加法？**加法加权（例如 `CE + 0.1 × recency`）会给所有候选相同的绝对增量，不论相关性如何。仅有一点相关的记忆可能只因较新就超过高度相关的记忆。乘法加权使调整幅度与基础相关性分数成正比：对于高度相关的记忆，+10% 带来的绝对变化比对低相关记忆更大。这样可以确保次要信号不会压过主要的相关性判断。

**公式：**

```
final_score = CE_normalized × recency_boost × temporal_boost × proof_count_boost
```

每个加权以 1.0 为中心（中性），由 alpha 控制最大变化幅度：

```
boost = 1 + α × (signal - 0.5)
```

| 加权 | α | 最大调整幅度 | 奖励的内容 |
|------|---|--------------|------------|
| **时效性** | 0.2 | ±10% | 较新的记忆 |
| **时间接近程度** | 0.2 | ±10% | 接近查询时间窗口的记忆 |
| **证据数量** | 0.1 | ±5% | 有更多证据支持的观察 |

#### 时效性信号 {#recency-signal}

从记忆的发生日期起，在 365 天内线性衰减：

```
recency = clamp(1.0 - days_ago / 365, 0.1, 1.0)
```

发生于查询时间戳的记忆，时效性为 1.0（+10% 加权）。发生于查询时间戳前 6 个月的记忆，时效性约为 0.5（中性）。发生于查询时间戳前一年以上的记忆，时效性为 0.1（-8% 惩罚）。未提供 `query_timestamp` 时，使用服务器当前时间。没有日期的记忆取 0.5（中性，没有加权或惩罚）。

#### 时间接近程度信号 {#temporal-proximity-signal}

仅当查询包含时间信息时生效（如「去年春天」、「在 2023 年」）。它衡量记忆日期距查询时间窗口中心的接近程度：

```
temporal_proximity = 1.0 - min(days_from_center / (window_days / 2), 1.0)
```

位于窗口中心的记忆取 1.0（+10% 加权），位于窗口边缘的记忆取 0.0（-10% 惩罚）。对于不涉及时间的查询，所有记忆均取 0.5（中性）。

#### 证据数量信号 {#proof-count-signal}

对于 observation 类型的记忆，使用对数曲线奖励有更多证据支持的观察：

```
proof_norm = clamp(0.5 + ln(proof_count) / 10, 0.0, 1.0)
```

| 证据数量 | proof_norm | 加权 |
|----------|------------|------|
| 1 | 0.5 | 中性 |
| 3 | 0.61 | +1.1% |
| 10 | 0.73 | +2.3% |
| 150+ | 1.0 | +5%（最大值） |

#### 最大组合范围 {#maximum-combined-range}

所有加权都取极值时：
- **最佳情况：**×1.10 × 1.10 × 1.05 ≈ **+27%**
- **最差情况：**×0.90 × 0.90 × 0.95 ≈ **-23%**

这些加权刻意保持保守，只微调排名，不会覆盖交叉编码器的相关性判断。

---

### 阶段 4：Token 截断 {#stage-4-token-truncation}

评分后，结果按 `final_score` 排序，从高到低选择，直到 `max_tokens` 预算耗尽。只有记忆文本计入预算，元数据不占预算。如果某条结果长度超过剩余预算，就跳过它并继续尝试下一条，这样一条很长的事实不会让排在后面的短事实都无法返回。如果没有任何结果能放入预算，仍会完整返回排名最高的结果，确保匹配到内容的查询不会得到空列表。

### Budget 如何映射到流水线参数 {#how-budget-maps-to-pipeline-parameters}

`budget` 参数（low/mid/high）控制**搜索深度**，即各策略考虑多少候选。每个级别都会映射为一个贯穿流水线各阶段的**召回预算**数值：

| Budget | 召回预算（固定模式） | 覆盖值的环境变量 |
|--------|----------------------|------------------|
| **low** | 100 | `HINDSIGHT_API_RECALL_BUDGET_FIXED_LOW` |
| **mid** | 300（默认） | `HINDSIGHT_API_RECALL_BUDGET_FIXED_MID` |
| **high** | 1000 | `HINDSIGHT_API_RECALL_BUDGET_FIXED_HIGH` |

召回预算在流水线中的使用方式如下：

| 流水线阶段 | 召回预算的使用方式 |
|------------|--------------------|
| **语义搜索** | SQL 中使用 `LIMIT recall_budget`，并为查询设置相应大小的 ANN 候选列表（在 pgvector 中为 `hnsw.ef_search`，不超过该设置的最大值 1000） |
| **BM25 搜索** | SQL 中使用 `LIMIT recall_budget` |
| **图遍历** | 最多探索 recall_budget 个节点 |
| **时间传播** | 通过关联最多激活 recall_budget 个节点 |
| **结果选择** | 考虑排名最高的 recall_budget × 2 条结果进行 token 过滤 |

重排序预过滤（300 个候选）与预算**相互独立**，由单独参数 `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 控制。

:::info 自适应预算
另一种预算模式根据 `max_tokens` 缩放召回预算，而不使用固定值：

```
recall_budget = clamp(max_tokens × ratio, min, max)
```

| Budget | 比例 | 覆盖值的环境变量 |
|--------|------|------------------|
| low | max_tokens 的 2.5% | `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_LOW` |
| mid | max_tokens 的 7.5% | `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_MID` |
| high | max_tokens 的 25% | `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_HIGH` |

结果会限制在下限 **20**（`HINDSIGHT_API_RECALL_BUDGET_MIN`）和上限 **2000**（`HINDSIGHT_API_RECALL_BUDGET_MAX`）之间。

通过 `HINDSIGHT_API_RECALL_BUDGET_FUNCTION=adaptive` 启用。
:::

### 图评分细节 {#graph-scoring-detail}

图遍历（关联扩展）对每个候选以加法组合三个独立信号：

| 信号 | 评分公式 | 范围 |
|------|----------|------|
| **实体重叠** | tanh(shared_entity_count × 0.5) | [0, ~1.0] |
| **语义关联** | 预先计算的 kNN 关联权重 | [0.7, 1.0] |
| **因果关联** | 因果关联权重 | [0, 1.0] |

```
graph_score = entity_score + semantic_score + causal_score   ∈ [0, 3]
```

加法组合会奖励**相互印证的证据**。通过多种信号与查询关联的记忆，比仅通过单一强信号关联的记忆排名更高。

**实体分数为什么使用 tanh？**原始共享实体数量没有上限。「user」这样的高连接度实体可能产生 50 以上的计数，淹没另两个信号。`tanh(count × 0.5)` 会自然趋于饱和：前几个共享实体影响很大（1→0.46、2→0.76、3→0.91），但后续实体贡献逐渐递减，使实体信号保持在 [0, 1] 内，与语义和因果分数的尺度一致。

**这里为什么使用加法而不是乘法？**与组合评分中的加权不同，图信号是独立的证据渠道，而不是对基础分数的调整。一条记忆可能仅通过因果关联连接（没有共享实体，也没有语义相似性），乘法组合会将它归零。加法评分让各信号独立贡献，策略之间的排序则由外层 RRF 融合处理。

**实体信号示例：**与查询共享 1 个实体的记忆，得分为 tanh(0.5) ≈ 0.46；共享 2 个实体，得分为 tanh(1.0) ≈ 0.76；共享 3 个或更多实体时，逐渐饱和于约 0.91 以上。
