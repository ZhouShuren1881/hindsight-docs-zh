人人都在谈检索：嵌入、BM25、图遍历、时间窗口——挑选检索策略、融合排名，然后交付结果。

但融合不会告诉你哪些内容*相关*。它只会把若干独立系统各自认为合理的内容投票合并成一个列表。决定智能体实际读到什么的，是最后运行的那个阶段；恰恰也是最少受到关注的阶段。

本文深入介绍 [Hindsight](https://hindsight.vectorize.io) 中的这个阶段——交叉编码器重排序器。它如何评分，为什么辅助信号采用乘法而非加法，哪种微妙的故障会让重排序器退化成按日期排序，以及如何配置重排序器，让模型不可达时系统可以降级运行，而不至于连带中断记忆召回。

## 概览 {#tldr}

- **交叉编码器会把查询和记忆放在一起读取。** 嵌入是分别计算、之后再比较的；交叉编码器则对两者进行联合评分。这让它准确得多，也意味着它无法用于建索引。
- 每个候选项都要调用一次模型，因此重排序**最后运行，只处理数量受限的候选项**。`HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 的默认值为 `300`。
- 分数会**按情况进行归一化**：托管重排序器返回的校准后相关性分数 `[0, 1]` 原样使用；本地 logits 则经过 sigmoid 函数处理。系统刻意避免按排名归一化，因此排名靠前但较弱的命中仍会保持较低分数。
- 近期性、时间接近度和证据强度采用**乘法加权提升**，合计调整幅度限制在约 **+21% / −19%**，只微调排名，不会压过相关性。
- 直通重排序器会造成一个陷阱：所有候选项分数相同，辅助信号就会成为**唯一**的排序依据，让记忆召回退化成纯粹按近期性排序。Hindsight 会根据融合排名生成基础分数，以避免这种情况。
- 如果重排序器链以 `rrf` 成员收尾，重排序器不可用时记忆召回就能**故障开放**，而不是返回 500 错误。
- 本文介绍的功能均已在 **v0.9.2** 发布。

## 为什么光靠融合还不够 {#why-fusion-isnt-enough}

Hindsight 中的每条检索支路都会生成排名，再由系统融合这些排名。问题在于，融合本质上是一种*投票*操作：它会让多个检索支路都认可的记忆排得更靠前。这可以作为相关性的近似指标，却不能取代真正的相关性判断。

更深层的问题来自系统结构。语义检索会比较查询嵌入与记忆嵌入，而这两种嵌入是**分别**计算的——记忆早在写入时就已完成嵌入，那时查询还不存在。

这正是向量检索速度快的原因：它可以建索引。这也是它只能近似匹配的原因：模型没有机会同时查看查询和记忆。

交叉编码器则可以同时处理两者。它接收 `(query, document)` 这一对输入，将它们一起送入模型，让注意力机制跨越两者之间的边界。比如，它可以识别出查询里的“服务中断”指的就是记忆中记作“结账时出现 502 错误”的同一事件；分别计算的两组嵌入无法表达这种对应关系。

代价是交叉编码器无法用于建索引。由于只有查询到来后才能计算分数，因此没有预先计算好的向量可供查找。每个候选项都要经过一次模型前向计算。仅这一点就决定了整个阶段的设计：必须放在最后运行，只处理少量候选项，并设定严格的预算上限。

## 模型实际看到的内容 {#what-the-model-actually-sees}

评分前，系统会把每个候选项整理成模型可读的文本。`rerank()` 中会进行三项处理。

记忆文本会作为文档内容。如果记忆带有上下文，系统会在前面加上：

```
{context}: {text}
```

如果记忆有起始日期，系统会同时添加**两种格式**的日期：

```
[Date: June 05, 2022 (2022-06-05)] {doc_text}
```

这种冗余是有意为之。交叉编码器属于语言模型，对书写形式的日期与 ISO 日期的处理方式并不相同。两种格式都提供给模型，就能让它更好地依据文档回答时间相关查询，而不必另设日期处理流程。

这项处理的影响比乍看之下更大：时间相关性有两个彼此独立的机会影响结果——一个在模型内部，由文本中的日期发挥作用；另一个在模型外部，由下文介绍的时间加权提升发挥作用。

## 归一化：校准问题 {#normalization-the-calibration-problem}

不同的重排序器会返回不同类型的数值。Cohere 和 Jina 等托管 API 已经会返回位于 `[0, 1]` 的校准后相关性分数。本地交叉编码器模型则返回原始 logits，数值可以是任意实数。

Hindsight 会按情况处理：

- **分数已处于 `[0, 1]`**：原样使用。
- **Logits**：通过 sigmoid 函数转换。

系统明确**不会**按排名归一化，原因值得说明：如果按排名归一化，排名第一的候选项分数总会变成 1.0。

但“糟糕的一组里最好的”不等于“好的”。如果智能体把两者视为相同，就会信心十足地引用一条几乎不相关的记忆。正如原文所说，排名第一的候选项如果只得 `0.007`，就应该维持低分，而不是被抬高到 `1.0`。保留绝对置信度，才能让下游调用方区分强匹配与“最不差”的选项。

## 三种加权提升，以及采用乘法的原因 {#the-three-boosts-and-why-they-multiply}

交叉编码器分数是相关性的主要信号，但并非唯一重要的信号。三年前出现的一条高度相关记忆，可能仍排在昨天出现的一条稍弱记忆之后。Hindsight 会综合以下三个辅助信号：

```
recency_boost     = 1 + recency_alpha     * (recency    - 0.5)
temporal_boost    = 1 + temporal_alpha    * (temporal   - 0.5)
proof_count_boost = 1 + proof_count_alpha * (proof_norm - 0.5)

combined_score = CE_normalized * recency_boost * temporal_boost * proof_count_boost
```

每个信号都会映射到 `[0, 1]`，并以 `0.5` 为中性值，再转换为以 `1.0` 为中心的乘数。

| 信号 | Alpha | 单项调整范围 | 以下情况为中性值 |
|---|---|---|---|
| 近期性 | `0.2` | ±10% | 记忆没有可用日期 |
| 时间接近度 | `0.2` | ±10% | 查询与时间无关 |
| 支持事实数 | `0.1` | ±5% | 事实不是观测 |

合并两个系数为 0.2 的信号后，调整幅度大致限定在 `(1 + α/2)² ≈ +21%` 和 `(1 − α/2)² ≈ −19%` 之内。

**为什么采用乘法，而不是加法？** 因为不同模型返回的交叉编码器分数，校准方式各不相同。加上 `+0.1`，对于某个模型的分数分布可能只是舍入误差，对另一个模型却可能造成压倒性的影响。乘法会按比例调整：无论基础分数处在哪个数值范围，辅助信号相对于基础分数的影响都会保持一致。更换重排序器后，原来的参数仍然适用。

限制调整幅度是设计的另一部分。把合并影响限制在约 ±20%，意味着这些信号可以调整分数接近的候选项，却无法让不相关的记忆排到相关记忆之前。近期性可以打破平局，但不能左右相关性判断。

### 近期性 {#recency}

近期性使用记忆的**有效时间**，并按以下顺序回退：`occurred_start`、`mentioned_at`、`occurred_end`。这与检索采用的合并取值顺序相同。

设置回退顺序，是因为许多真实记忆本来就没有起始日期。对话中提到的事实或持续存在的状态可能只有 `mentioned_at`。如果不进行回退，这些记忆都会停留在中性值 0.5，完全无法按近期性排序。

系统提供三种衰减曲线：

| 函数 | 曲线形状 | 默认参数 |
|---|---|---|
| `linear`（默认） | 从今天的 1.0 线性降至最低 0.1 | 365 天窗口 |
| `exponential` | `0.5 ** (days_ago / halflife)`，平滑渐近，不设硬性截止 | 90 天半衰期 |
| `none` | 始终为中性值 | — |

指数曲线的半衰期，指记忆分数恰好达到中性值时的记忆年龄。较新的记忆会获得加权提升，较旧的记忆会受到惩罚，中间不会出现骤变。这适合记忆相关性确实会随时间减弱的记忆库。线性曲线作为默认值，则适合去年存入的记忆至今仍有价值的记忆库。

还有一个刻意保留的边缘情况：**未来日期的记忆会被设为最高的新鲜度**，而不会受到惩罚。下周安排的会议，不该因为简单计算得出负数年龄，就排在上个月的会议之后。

### 支持事实数 {#proof-count}

对于观测——由重复证据整合得到的事实——支持它的事实数确实能反映相关性。一条被观测到 40 次的内容，比只观测到一次的内容更有支撑力。

系统使用对数曲线进行归一化：

```
proof_norm = clamp(0.5 + log(proof_count) / 10.0, 0, 1)
```

支持事实数为 1 时，结果恰好为中性值。采用对数增长，是因为 1 条与 10 条支持事实之间的差距有意义，而 100 条与 110 条之间的差异则不大。支持事实数达到约 150 时，曲线会封顶于 1.0，对应文档规定的最高 +5% 加权提升。

`world`、`experience` 和 `opinion` 类型的事实没有支持事实数，因此该信号为中性，加权乘数精确为 1.0。

## 直通模式的陷阱 {#the-passthrough-trap}

这是一个微妙的问题，只会在特定部署方式下出现。

有些部署完全不运行交叉编码器，而是采用 RRF 直通模式。在这种模式下，每个候选项得到的交叉编码器分数都**相同**。

再看一次公式：如果 `CE_normalized` 对所有候选项都是同一个常数，它就无法再区分候选项，乘法加权提升便会成为**唯一**剩下的排序信号。记忆召回会悄无声息地退化成纯粹按近期性排序——最新的记忆排在最前面，无论它是否与查询相关。

系统表面上看起来仍在正常运行，也会返回结果，只是结果错得很隐蔽，不会触发任何错误。

修复方法是根据融合排名生成基础分数，将排名映射到 `[0.1, 1.0]`：

```
cross_encoder_score_normalized = 1.0 - (0.9 * rank / (n - 1))
```

这样，加权提升调整的是有意义的基础顺序，而不会取代它。直通模式也就能按其预期工作：保留融合顺序，并进行轻微调整。

触发这一处理的方式也体现了一个重要的工程细节：调用方会显式传入 `is_passthrough` 标志，而不是由代码检查“所有分数是否相同”。后者过于脆弱——真正的交叉编码器也可能合法地给出相同分数，尤其是在较小或合成的结果集中。若把相同分数误判为直通模式，就会破坏真实的重排序结果。

## 候选项预算 {#the-candidate-budget}

交叉编码器是大规模记忆召回的主要成本，因此候选项数量会受到限制。`HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 的默认值为 `300`；融合阶段会预先筛除超出上限的候选项。

固定上限并非总是合适，因此预算可以随记忆召回自身的预算等级调整：

| 变量 | 用途 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` | 每次记忆召回的固定上限 | `300` |
| `HINDSIGHT_API_RERANKER_MAX_CANDIDATES_LOW` | 覆盖 `budget=low` 的上限 | `0`（使用固定上限） |
| `HINDSIGHT_API_RERANKER_MAX_CANDIDATES_MID` | 覆盖 `budget=mid` 的上限 | `0`（使用固定上限） |
| `HINDSIGHT_API_RERANKER_MAX_CANDIDATES_HIGH` | 覆盖 `budget=high` 的上限 | `0`（使用固定上限） |
| `HINDSIGHT_API_RECALL_MAX_CANDIDATES_PER_SOURCE` | 全局上限生效前，每条检索支路的候选项上限 | `0`（禁用） |

按检索支路设置上限，可以解决一个具体问题：某条过度扩展的检索支路独自占满整个重排序器预算，在交叉编码器处理其他支路之前，就挤掉了它们的最佳命中。

另一个设置 `HINDSIGHT_API_RECALL_STRATEGY_BOOSTS`，可以通过 `strategy:level` 列表提升指定检索支路，例如 `graph:high` 或 `graph:high,bm25:low`。它会在**两个**阶段生效：一是在重排序器上限生效前，让优先候选项保留在预算范围内；二是在重排序后，再把它们稍微推向最终排序的前列。必须应用两次，是因为两个阶段使用的分数尺度不同；这也是设置采用命名等级，而不是直接指定数字的原因。

## 让记忆召回故障开放 {#making-recall-fail-open}

默认情况下，重排序器不可达会导致记忆召回失败。该阶段是硬性依赖，因此自托管模型发生超时，就会让请求返回 500。

解决方法是配置一条**故障转移链**。未编入索引的配置是主成员（成员 0），额外成员从 1 开始连续编号：

```bash
# 主成员：一台并非始终在线的自托管重排序器。
export HINDSIGHT_API_RERANKER_PROVIDER=tei
export HINDSIGHT_API_RERANKER_TEI_URL=http://workstation:8081

# 成员 1：用作回退的托管重排序器。
export HINDSIGHT_API_RERANKER_1_PROVIDER=cohere
export HINDSIGHT_API_RERANKER_1_COHERE_API_KEY=...

# 成员 2：最后的回退手段——保留融合顺序，不让请求失败。
export HINDSIGHT_API_RERANKER_2_PROVIDER=rrf
```

发生超时、连接错误、HTTP 错误或响应不可用时，系统会按顺序尝试各成员。**以 `rrf` 作为链末成员，就能让记忆召回故障开放**：系统按融合顺序返回结果，效果与未配置重排序器相同，而不会让请求失败。如果没有配置 `rrf` 成员，或者所有成员都不可用，错误仍会向上报告——这就是现有默认行为。

依赖这项机制前，有四点需要了解：

- **各成员单独读取配置。** 每个成员都不会继承主成员或共享服务提供方密钥的设置，因此必须为其索引明确写出所有配置。未设置的项会采用内置默认值，而不是主成员的值。
- **没有熔断器。** 每个请求都会重新尝试各成员，因此不可用的成员会在系统尝试下一成员前耗尽完整超时时间。对不可靠的主成员，应将超时设得较短。
- **不同服务提供方的分数不可直接比较。** 有些返回经过校准的相关性分数，有些返回 logits，因此由回退成员处理的请求，分数可能与主成员处理的请求不同。故障转移事件会以 `WARNING` 级别记录。由于这条链平时不会发出提示，建议针对这类日志设置告警。
- **带索引的成员仅适用于服务器级配置。** 这些成员包含凭据字段，不会由记忆库配置 API 返回，也不能按记忆库配置。

成员如果在启动时初始化失败，系统会记录该问题而不会因此退出，并会在下一个请求访问该成员时重试。

## 选择服务提供方 {#choosing-a-provider}

Hindsight 支持 13 种重排序器服务提供方：`local`、`tei`、`cohere`、`openrouter`、`zeroentropy`、`siliconflow`、`alibaba`、`google`、`flashrank`、`litellm`、`litellm-sdk`、`jina-mlx` 和 `rrf`。默认使用 `local`，在进程内运行 `cross-encoder/ms-marco-MiniLM-L-6-v2`。

有两项本地配置在默认情况下关闭，但在适合的硬件上可以带来显著收益：

- **`HINDSIGHT_API_RERANKER_LOCAL_FP16`**：在 MPS 上速度提高 27–36%，质量不变。默认关闭，仅仅是因为部分 CPU 不支持原生 FP16。
- **`HINDSIGHT_API_RERANKER_LOCAL_BUCKET_BATCHING`**：批处理前按 token 长度对输入对排序，以减少填充浪费。不同模型的速度提高 36–54%，而且按设计不会影响质量，因为它只改变任务分组方式。

还有一项配置关闭的原因则充分得多。Apple Silicon 的 MPS 后端需要通过 `HINDSIGHT_API_RERANKER_LOCAL_ALLOW_MPS` 显式启用，因为 **MPS 会为每种输入形状缓存独立的内核和分配器内存池，而且从不释放它们**。重排序的输入长度本来就会变化，因此内存会无限增长；已有空闲实例占用约 20 GB 内存的记录。CUDA 和 XPU 没有这个问题，仍会自动选用。

如果使用 TEI，应仔细设定其内存池大小。TEI 会在一次重排序请求中为每段文本预留一个槽位，内存池满时会拒绝整个请求。因此，槽位数至少应为 `TEI_MAX_CONCURRENT × TEI_BATCH_SIZE`。按 Hindsight 的默认值计算，这需要 1024 个槽位，而 TEI 自身的默认值只有 512 个。

## 关闭重排序 {#turning-it-off}

重排序是一个处理阶段，不是必需项。设置 `HINDSIGHT_API_ENABLE_RERANKING=false` 后，系统会直接返回融合排序：速度更快，精度也会降低。与其他记忆召回阶段开关一样，这项设置支持分层配置，因此可以通过配置 API 让某个记忆库跳过重排序，而不影响部署中的其他记忆库。

如果记忆库用于检索内容一致的文本分块，而且各检索支路的判断大多一致，那么关闭重排序是合理的权衡，因为交叉编码器很少有内容需要纠正。若记忆库包含关于反复出现实体的整合观测，这就不是好选择；恰恰在这种情况下，融合顺序最不可靠。

## 常见问题 {#faq}

**双编码器和交叉编码器有什么区别？**
双编码器分别为查询和文档生成嵌入，再比较两组向量，因此文档可以提前生成嵌入并建索引。交叉编码器会把查询和文档一起输入模型，直接输出相关性分数。它的准确度高得多，但无法预先计算，因此用于对候选列表重排序，而不是用于检索。

**重排序会取代混合检索吗？**
不会。重排序只会重新排列候选项，无法检索各条检索支路都没有返回的内容。如果一条记忆没有通过检索和融合，重排序器也无法找回它。两者解决的是不同问题，参见[智能体记忆中的知识图谱与向量检索](/blog/2026/08/24/knowledge-graphs-vs-vector-search-agent-memory)。

**应该对多少个候选项进行重排序？**
默认值 300 是合理的折中。提高上限可以扩大记忆召回的深度，代价是交叉编码器调用次数大致线性增加；这些调用是大规模记忆召回延迟的主要来源。如果需要低预算召回时成本较低、高预算召回时检索全面，可以使用按预算设置的上限，而不要调整固定上限。

**为什么我的最高排名结果分数这么低？**
因为 Hindsight 会保留绝对置信度，而不会按排名归一化。最高排名结果分数低，传达的是真实信息：记忆库中没有内容与查询很好地匹配。应将它视为记忆内容尚不存在的信号，而不是缩放导致的假象。

**可以使用自己的重排序器吗？**
可以。任何兼容 Cohere 的 `/rerank` 端点都可以通过 `cohere` 服务提供方配合自定义基础 URL 使用，其中包括 Azure AI Foundry、Jina、Voyage 和自托管 BGE 部署。自托管模型也可以通过 `tei` 或 `litellm` 运行。

**重排序器能看到我的记忆库 ID 吗？**
只有在启用该功能时才会看到。`HINDSIGHT_API_RERANKER_SEND_BANK_AS_HEADER` 会在发往远程重排序器的请求中添加 `X-Hindsight-Bank-Id` 标头。该功能默认关闭，因为它会将记忆库 ID 发送给第三方。只有在信任相应端点时才应启用。
