检索是每个人都在谈论的部分。嵌入、BM25、图遍历、时间窗口：拿起武器，融合排名，发货。

但是融合并不能告诉你什么是*相关*。它告诉您每个人认为合理的几个独立系统，并混合到一个列表中。决定你的智能体实际读取内容的阶段是最后运行的阶段，也是最不受关注的阶段。

这是[Hindsight](https://hindsight.vectorize.io)中该阶段的内部视图——交叉编码器重排序器。它如何评分，为什么辅助信号是乘法而不是加法，将重排序器变成日期排序的微妙故障模式，以及如何对其进行配置，以便使无法访问的模型降级而不是使记忆召回随之下降。

## 概览 {#tldr}

- **交叉编码器一起读取查询和记忆。** 嵌入是独立计算的，并在事后进行比较；交叉编码器对这对进行联合评分，这就是为什么它更准确并且不能作为索引的原因。
- 因为每个候选者需要调用一次模型，所以它运行**最后，在上限集上** — `HINDSIGHT_API_RERANKER_MAX_CANDIDATES`，默认`300`。
- 分数标准化**有条件**：按原样使用托管重新排名器的校准`[0, 1]`相关性，本地logits经过S形。故意避免排名标准化，因此弱热门命中仍然很弱。
- 新近度、时间接近度和证据强度为**倍增提升**，上限约为**+21% / −19%**，因此它们会在不影响相关性的情况下推动排名。
- 直通重排序器创建了一个陷阱：相同的分数会增强**信号，将记忆召回变成纯粹的新近度排序。 Hindsight 从融合等级中播种基本分数以防止这种情况发生。
- 使用`rrf`成员结束重排序器链会产生记忆召回**打开失败
当您的重排序器关闭时，**，而不是返回 500。
- 这里的所有内容都在**v0.9.2**中发布。

## 为什么融合还不够 {#why-fusion-isnt-enough}

Hindsight中的每个检索臂都会产生一个排名，并且这些排名会被融合。问题是融合是一个*投票*操作。它奖励多个手臂独立喜欢的记忆，这是相关性的一个不错的代理，但却是一个糟糕的替代品。

更深层次的问题是结构性的。语义检索将查询嵌入与记忆嵌入进行比较，这些嵌入是在**独立**计算的——记忆是在写入时嵌入的，早在查询存在之前。

这就是矢量搜索快速的原因：您可以对其进行索引。这也是它近似的原因。该模型永远不会同时查看查询和记忆。

交叉编码器正是这样做的。它需要一对 `(query, document)` 并一起运行模型，因此注意力会跨越它们之间的边界。它可以注意到，查询中的“中断”指的是记忆中称为“结帐时的 502”的同一事件，没有独立的嵌入对可以表示该事件。

代价是它不可索引。没有预先计算的向量可供查找，因为在查询到达之前分数并不存在。您为每位候选人支付一张模型正向通行证。这个单一属性决定了舞台的整个设计：它必须在小布景上最后运行，并且预算严格。

## 模型实际看到的内容 {#what-the-model-actually-sees}

在评分之前，每个候选者都会被组装成模型可以阅读的文本。 `rerank()` 中发生了三件事。

记忆的文本用作文档。如果记忆带有上下文，则它的前缀是：

```
{context}: {text}
```

如果记忆有开始日期，则该日期会添加到**同时支持两种格式**中：

```
[Date: June 05, 2022 (2022-06-05)] {doc_text}
```

冗余是有意的。交叉编码器是语言模型，它们以不同的方式处理写出日期和 ISO 日期。提供两者可以让模型更好地根据文档进行时间查询，而无需单独的日期处理路径。

这比看起来更重要。这意味着时间相关性有两个独立的机会影响结果：一次在模型内部，通过文本中的日期，一次在模型外部，通过下面描述的时间提升。

## 归一化：校准问题 {#normalization-the-calibration-problem}

不同的重新排序器返回不同类型的数字。 Cohere 和 Jina 等托管 API 返回 `[0, 1]` 中已校准的相关性分数。本地交叉编码器模型返回原始 logits，它可以是任何实数。

Hindsight 分支：

- **已经在`[0, 1]`** — 按原样使用。
- **Logits** — 通过 sigmoid。

*不是*所做的就是排名归一化，其原因值得说清楚。如果按排名进行标准化，则排名靠前的候选人得分始终为 1.0。

但是“糟糕的集合中的最好的”与“好的”并不相同，并且以相同方式对待它们的智能体将自信地引用几乎不匹配的记忆。正如消息来源所说，得分最高的候选人`0.007`应该保持较低水平，而不是被夸大到`1.0`。保持绝对的信心可以让下游的呼叫者区分出强烈的打击和最不糟糕的选择。

## 三种提升，以及它们为何倍增 {#the-three-boosts-and-why-they-multiply}

交叉编码器分数是主要的相关性信号，但它并不是唯一重要的事情。三年前高度相关的记忆可能仍然会输给昨天不太相关的记忆。 Hindsight 折叠成三个辅助信号：

```
recency_boost     = 1 + recency_alpha     * (recency    - 0.5)
temporal_boost    = 1 + temporal_alpha    * (temporal   - 0.5)
proof_count_boost = 1 + proof_count_alpha * (proof_norm - 0.5)

combined_score = CE_normalized * recency_boost * temporal_boost * proof_count_boost
```

每个信号都映射到`[0, 1]`，其中`0.5`作为中性，然后转化为以`1.0`为中心的乘法器。

|信号|阿尔法|每个信号范围|中性时|
|---|---|---|---|
|最近经历|`0.2`|±10%|记忆没有可用日期|
|时间邻近度|`0.2`|±10%|查询不是临时的|
|证明计数|`0.1`|±5%|事实不是观察|

结合起来，两个 0.2 信号将调整范围大致限制在 `(1 + α/2)² ≈ +21%` 和 `(1 − α/2)² ≈ −19%`。

**为什么是乘法而不是加法？** 因为跨编码器分数校准因模型而异。 `+0.1` 的附加奖励是针对一个模型分数分布的舍入误差以及针对另一个模型分数分布的压倒性优势。乘数通过构造成比例：辅助信号的影响对基本分数保持相同的*相对*，无论基本分数碰巧处于什么等级。更换重排序器，调整仍然有效。

边界是设计的另一半。将综合效应限制在±20%附近意味着这些信号会对已经接近的候选信号进行重新排序，并且不能促进不相关的记忆超过相关的记忆。近因打破了联系；它不会赢得争论。

### 近期经历 {#recency}

新近度使用记忆的**有效时间**，回退到`occurred_start`，然后`mentioned_at`，然后`occurred_end`——与合并顺序检索使用相同。

这种后退的存在是因为大量真实的记忆理所当然地缺乏开始日期。一个对话事实或一个正在进行的状态可能只带有 `mentioned_at`，如果没有回退，它们中的每一个都将保持在中性 0.5 并完全失去新近度排序。

提供三种衰减曲线：

|功能|形状|默认参数|
|---|---|---|
|`linear`（默认）|从今天的 1.0 到 0.1 的下限的直线|365 天窗口|
|`exponential`|`0.5 ** (days_ago / halflife)`，平滑渐近线，无硬截止|90 天半衰期|
|`none`|始终保持中立|—|

指数曲线的半衰期是记忆完全中性的年龄：年轻的记忆得到增强，年长的记忆受到惩罚，没有悬崖。它适合记忆库，因为记忆库的相关性确实会随着年龄的增长而减弱。线性默认适合记忆库，其中去年的记忆仍然有价值。

一个故意的边缘情况：**未来的记忆保持最大的新鲜度**而不是受到惩罚。下周安排的会议不应低于上个月的会议，因为天真的年龄计算结果为负。

### 证明计数 {#proof-count}

对于观察——从重复的证据中整合事实——支持证据的数量是一个真正的相关性信号。观察 40 次的东西比观察一次的东西更能承载。

它在对数曲线上标准化：

```
proof_norm = clamp(0.5 + log(proof_count) / 10.0, 0, 1)
```

证明计数为 1 正好处于中性。增长是对数的，因为 1 和 10 个证明之间的差异是有意义的，而 100 和 110 个证明之间的差异则没有意义。通过大约 150 的证明计数，曲线钳制在 1.0，这是记录的最大值 +5%。

对于 `world`、`experience` 和`opinion` 事实，这些事实不带有证明计数，信号是中性的，并且乘数精确到 1.0。

## 穿越陷阱 {#the-passthrough-trap}

这是一个微妙的错误，它是一种仅在特定部署形状中出现的错误。

有些部署根本不运行交叉编码器，而是使用 RRF 直通。在该模式下，每个候选人都会收到一个 **相同** 交叉编码器分数。

现在再看一下公式。如果 `CE_normalized` 对于每个候选者来说都是相同的常数，它将停止区分任何东西，并且乘法提升成为 ** 剩余排名信号。 记忆召回会默默地降级为纯粹的新近度排序——最新的优先，无论记忆是否与查询有关。

系统看起来正在运行。它会返回结果。他们只是在某种程度上犯了错误，没有错误的表面。

修复方法是从融合排名中播种基本分数，将排名映射到`[0.1, 1.0]`：

```
cross_encoder_score_normalized = 1.0 - (0.9 * rank / (n - 1))
```

现在，提升调整了有意义的基本顺序而不是替换它，并且直通的行为就像它声称的那样：融合顺序，轻轻调整。

关于如何触发它有一个很好的工程细节。调用者传递显式的 `is_passthrough` 标志，而不是检测“所有分数都相同”的代码，因为这种启发式太脆弱了——真正的交叉编码器可以合法地捆绑分数，特别是在小型或合成结果集上，并且从捆绑中推断传递会破坏真正的重新排名。

## 候选人预算 {#the-candidate-budget}

因为交叉编码器是大记忆召回的主要成本，所以候选集是有上限的。 `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 默认为`300`； fusion 预过滤了除此之外的所有内容。

固定上限并不总是正确的，因此预算可以根据记忆召回自己的预算水平进行调整：

|变量|目的|默认|
|---|---|---|
|`HINDSIGHT_API_RERANKER_MAX_CANDIDATES`|记忆召回平顶帽|`300`|
|`HINDSIGHT_API_RERANKER_MAX_CANDIDATES_LOW`|覆盖`budget=low`|`0`（使用平放）|
|`HINDSIGHT_API_RERANKER_MAX_CANDIDATES_MID`|覆盖`budget=mid`|`0`（使用平放）|
|`HINDSIGHT_API_RERANKER_MAX_CANDIDATES_HIGH`|覆盖`budget=high`|`0`（使用平放）|
|`HINDSIGHT_API_RECALL_MAX_CANDIDATES_PER_SOURCE`|每个检索臂的盖，在全局盖之前应用|`0`（禁用）|

每源上限解决了一个特定的故障：一个过度扩张的臂自行填充了整个重排序器预算，在交叉编码器发现之前挤出了所有其他臂的最佳命中。

还有`HINDSIGHT_API_RECALL_STRATEGY_BOOSTS`，它支持将命名武器作为`strategy:level`列表，例如`graph:high`或`graph:high,bm25:low`。它应用于**二**地方：在重排序器上限之前，因此受青睐的候选人在预算中幸存下来，并在重排序之后再次将其推向最终顺序。两个应用程序是必要的，因为这些阶段在不同的分数范围上运行，这也是设置采用命名级别而不是原始数字的原因。

## 使记忆召回无法打开 {#making-recall-fail-open}

默认情况下，无法访问的重排序器会导致记忆召回随之下降。该阶段是硬依赖项，因此自托管模型的超时变成了请求的 500。

修复是**故障转移链**。未索引的配置是主要的（成员 0），额外的成员从 1 开始连续编号：

```bash
#Primary：一个自托管的重排序器，并不总是处于运行状态。
export HINDSIGHT_API_RERANKER_PROVIDER=tei
export HINDSIGHT_API_RERANKER_TEI_URL=http://workstation:8081

#成员 1：可以依靠的托管重排序器。
export HINDSIGHT_API_RERANKER_1_PROVIDER=cohere
export HINDSIGHT_API_RERANKER_1_COHERE_API_KEY=...

#成员2：最后的手段——保持融合顺序而不是失败。
export HINDSIGHT_API_RERANKER_2_PROVIDER=rrf
```

按超时、连接错误、HTTP 错误或不可用响应的顺序尝试成员。 **以`rrf`结束链条是导致记忆召回失败的原因**：结果按照融合顺序返回，就像没有配置重排序器一样，而不是请求失败。如果没有 `rrf` 成员，或者每个成员都关闭，错误仍然会出现 - 这是现有的默认行为。

在依赖它之前，有四件事值得了解：

- **每个成员都是单独阅读的。** 它不会从主键继承任何内容，也不会从共享提供程序键继承任何内容，因此请用自己的索引拼写每个设置。未设置的设置将回退到内置默认值，而不是主要值。
- **没有断路器。** 每个请求都会重试成员，因此每次失败的成员都会在尝试下一个请求之前花费全部超时时间。保持不可靠主节点的超时时间较短。
- **不同提供商之间的分数不具有可比性。** 一些返回校准的相关性，另一些返回登录，因此后备服务的请求可能与主服务的请求得分不同。故障转移记录在`WARNING`——值得警惕，因为否则该链是静默的。
- **索引成员仅是服务器级别的。** 它们是凭据字段，永远不会由记忆库配置API 返回，并且不可按记忆库配置。

​​启动时未能初始化的成员会被记录而不是致命的，并在下一个到达它的请求时重试。

## 选择提供商 {#choosing-a-provider}

Hindsight 提供 13 个重排序器提供商：`local`、`tei`、`cohere`、`openrouter`、`zeroentropy`、`siliconflow`、`alibaba`、`google`、 `flashrank`、`litellm`、`litellm-sdk`、`jina-mlx` 和 `rrf`。默认为 `local`，在进程内运行 `cross-encoder/ms-marco-MiniLM-L-6-v2`。

尽管在正确的硬件上免费获胜，但默认情况下两个本地旋钮处于关闭状态：

- **`HINDSIGHT_API_RERANKER_LOCAL_FP16`** — MPS 速度提高 27–36%，质量相同。默认情况下它处于关闭状态，只是因为某些 CPU 缺乏本机 FP16 支持。
- **`HINDSIGHT_API_RERANKER_LOCAL_BUCKET_BATCHING`** — 在批处理之前按标记长度对对进行排序，以减少填充浪费。跨模型速度提高 36-54%，且质量相同 *按构造*，因为它仅改变工作的分组方式。

还有一个因为更好的原因而关闭的人。 Apple Silicon 的 MPS 后端通过 `HINDSIGHT_API_RERANKER_LOCAL_ALLOW_MPS` 选择加入，因为 **MPS 为每个输入形状缓存一个不同的内核和分配器池，并且从不释放它**。 重排序本质上是一种可变长度的工作负载，因此记忆会无限制地增长——观察到空闲实例的大小约为 20 GB。 CUDA和XPU没有这个问题，仍然是自动选择的。

如果您运行 TEI，请谨慎调整其池的大小。 TEI 在重新排序请求中为每个文本保留一个槽，并在其池已满时拒绝整个请求，因此它至少需要 `TEI_MAX_CONCURRENT × TEI_BATCH_SIZE` 槽 — Hindsight 的默认值是 1024 个，而 TEI 自己的默认值是 512 个。

## 关闭它 {#turning-it-off}

重排序是一个阶段，而不是要求。 `HINDSIGHT_API_ENABLE_RERANKING=false` 直接返回融合排序：更快，但精度较低。与其他记忆召回阶段切换一样，它是分层的，因此一个记忆库可以通过配置API跳过它，而无需更改其余部署的回忆方式。

对于用作统一块的简单检索的记忆库来说，这是一个合理的交易，其中手臂大多一致，并且交叉编码器几乎不需要纠正。对于关于重复实体的综合观察的记忆库来说，这是一个糟糕的交易，而这正是融合顺序最不值得信赖的地方。

## 常见问题解答 {#faq}

**双编码器和交叉编码器有什么区别？**
双编码器分别嵌入查询和文档并比较两个向量，这意味着文档可以提前嵌入并索引。交叉编码器通过模型一起输入查询和文档，并直接输出相关性分数。它的准确度要高得多，并且无法预先计算，因此它用于对候选列表进行重新排名而不是用于搜索。

**重排序会取代混合搜索吗？**
没有。 重排序对候选者重新排序；它无法取回手臂从未返回的东西。如果记忆无法在检索和融合中幸存下来，则任何重排序器都无法挽救它。两者解决不同的问题——参见[知识图与矢量搜索智能体记忆](/blog/2026/08/24/knowledge-graphs-vs-vector-search-agent-memory)。

**我应该对多少候选人重新排名？**
默认300是一个合理的余额。提高它可以在跨编码器调用中以大致线性的成本提高记忆召回深度，这主导了大记忆召回的延迟。如果您需要廉价的低预算召回和彻底的高预算召回，请使用按预算覆盖，而不是移动固定上限。

**为什么我的最高成绩得分这么低？**
​​因为Hindsight保留绝对置信度而不是排名归一化。较低的最高分是真实的信息：这意味着记忆库中没有任何内容与您的查询很好地匹配。将其视为记忆尚不存在的信号，而不是缩放伪影。

**我可以使用自己的重排序器吗？**
是的。任何与 Cohere 兼容的 `/rerank` 端点都通过具有自定义基本 URL 的 `cohere` 提供程序工作，其中涵盖 Azure AI Foundry、Jina、Voyage 和自托管 BGE 部署。自托管模型也通过`tei`或`litellm`运行。

**重排序器能看到我的记忆库ID吗？**
仅当您打开它时。 `HINDSIGHT_API_RERANKER_SEND_BANK_AS_HEADER`向远程重排序器请求添加`X-Hindsight-Bank-Id`标头，默认情况下关闭，因为它将记忆库ID传输给第三方。仅对您信任的端点启用它。
