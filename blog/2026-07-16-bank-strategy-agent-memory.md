每个Hindsight集成都会告诉您设置`bank_id`。几乎没有人告诉你如何决定记忆库应该是什么*be*。这个决定看起来微不足道，但它决定了你的智能体实际上可以记忆的内容。范围太宽，一个用户的记忆会渗透到另一个用户的记忆中；范围太窄，智能体无法达到它需要的东西，因为该东西存在于它看不到的不同记忆库中。

这是智能体记忆的模式设计决策。这是制作方法。

<!-- truncate -->

## 概览 {#tldr}

- A**记忆库是记忆召回边界**。 `recall`、`retain`、`reflect`都是在一个记忆库内操作，不存在跨记忆库查询。那么“这两个东西应该共享一个记忆库吗？”真正的意思是“A存储的记忆应该可以被B调用吗？”
- 将 **独立记忆库** 用于任何硬隔离边界（租户、客户、不受信任的上下文）。对于有时想要过滤、有时想要交叉引用的软分区使用**一个记忆库中的标签**。
- ​​记忆库是在第一次使用时延迟创建的，因此新的`bank_id`字符串是一个新的空记忆。这就是大多数碎片化背后的失败模式：每个对话都有一个记忆库，意味着每个对话都以空白开始。
- 一些集成将其公开为配置：静态`bankId`或由`user`、`project`和`agent`等上下文字段组成的`dynamicBankId`。
- 您可以稍后更改策略，但记忆召回历史范围仅限于记忆库，因此提前选择好可以节省回填。

## 核心概念：记忆库是召回边界 {#the-one-idea-a-bank-is-a-recall-boundary}

A记忆库Hindsight是一个完整的、孤立的存储：从对话中保留的记忆、索引用于检索的文档、从中提取的实体、连接这些实体的知识图以及记忆库自己的配置和指令。 记忆库相互隔离，不存在跨记忆库的内置查询。每个`recall`，`retain`，以及`reflect`准确地称呼一个名字`bank_id`并留在其中。

这个事实就是整个设计工具。不要问“我应该如何组织记忆”，而是针对每个边界问一个问题：

> 如果A保留了记忆，B应该能够记忆它吗？

如果**是的**，A和B属于同一个记忆库。如果**无**，则它们属于不同的记忆库。下面的每个模式都是应用于不同 A 和 B 的问题：两个用户、两个项目、两个智能体、两个渠道。

还有一个机械细节很重要。您无需预先创建记忆库。第一次使用 `bank_id` 时，Hindsight 使用默认设置创建它。这里有一个真正的好处（没有配置步骤）和一个真正的陷阱：你从未写入过的`bank_id`只是一个空的记忆库，一个拼写错误或一个不稳定的ID默默地给你一个新鲜的、空白的记忆，而不是一个错误。 记忆库的身份是承载的。

## 主轴：一个记忆库代表什么？ {#the-main-axis-what-does-one-bank-represent}

这里是常见的策略，每个策略都以记忆召回边界问题为框架，并以它咬人的情况为例。

|策略|每人一个记忆库|适合|咬到的地方|
|---|---|---|---|
|**全球**|一切|单用户工具，独立开发助手|第二个用户出现的那一刻，他们的记忆混合在一起|
|**每用户**|最终用户|SaaS 产品、个人助理|一个用户拥有多个项目，所有项目都模糊在一起|
|**每个项目/每个存储库**|代码库或工作区|编码智能体，项目工作|用户的跨项目上下文不跟随他们|
|**每智能体**|智能体角色|具有不同角色的多智能体系统|*应该* 池上下文无法实现的智能体|
|**共享/团队**|一群人，故意的|跨多个表面或队友的同一个记忆|需要明确的选择加入；这不是默认值|

从抽象意义上讲，这些都不正确。正确的选择取决于你的 A 和 B 是谁：

- **消费者助理** 每个人的记忆绝不能触及其他人的：**每用户**。用户是隔离边界，因此也是记忆库边界。
- **A编码智能体**，其中有用的记忆是关于*这个代码库*（它的约定、它的决定、它的布局）：**每个存储库**。这正是 Aider 集成默认执行的操作，从 git 存储库名称派生记忆库，以便每个处理该存储库的编辑共享一个项目记忆。
- **专业智能团队**（计划者、研究员、审阅者），每个人都应该保留自己的经验：**每智能体**。但当您希望他们在共享上下文上进行协作时，请将他们指向一个**共享**记忆库。

## 大多数人错过的第二个轴：记忆库中的标签 {#the-second-axis-most-people-miss-tags-inside-a-bank}

这是我最常看到的错误：每次你想在同一个信任域内分离两个*种*记忆库时，都会去寻找一个新的记忆库。为此，您不需要新的记忆库。你需要标签。

Hindsight让您在记忆存储记忆时附加`tags`，并在您记忆召回或梦想时过滤它们。标签是记忆库内分区，在查询时应用，因此同一个记忆库可以容纳许多带标签的切片，您可以决定每个查询要查看哪些切片。

```python
#带有范围标签的记忆存储
client.retain(bank_id="acme", content="我们仅在紧急情况下在周五部署",
              tags=["project:web"])

#仅在该切片内记忆
client.recall(bank_id="acme", query="部署政策？",
              tags=["project:web"], tags_match="all")
```

`tags_match`模式是值得了解的部分，因为默认的比人们想象的更友好：

- **`any`**（默认）：OR匹配，且*包括未标记的记忆*。当标签是提示而不是墙壁时，这很好。
- **`all`**：AND匹配，仍然包括未标记的记忆。
- **`any_strict` / `all_strict`**：相同的匹配，但排除未标记的记忆。
- **`exact`**：记忆的标签集必须等于查询的标签集。

该默认值表明标签何时是错误的工具。因为`any`包含未标记的记忆，所以标记是*软件*分区：方便组织，而不是安全控制。如果记忆绝对不能在错误的上下文中出现，请不要依赖可能会忘记通过的标签过滤器。把它放在自己的记忆库里。

所以真正的决策是两层的：

- **硬隔离**（租户，客户，不受信任的来源，任何泄漏都是错误的东西）：**独立记忆库**。隔离是通过存储边界来强制执行的，而不是通过记住过滤来强制执行。
- **软隔断**（将一个信任域组织为有时想要过滤、有时想要一起查看的项目、主题或用户）：**一个记忆库，标签**。

一个有效的例子。为一家公司服务的单租户内部助理可以生活在一个记忆库中，其中的`tags`如`project:web`、`project:billing`和`team:sre`，因此有关计费的问题可以限制范围很窄，也可以保留开放的范围以利用所有内容。但在多租户 SaaS 中，每个客户都是不同的公司，必须为每个客户提供自己的记忆库。标签组织； 记忆库隔离。

除了标签之外，记忆召回还可以按事实`types`和时间进行过滤（`created_after` / `created_before`，以及用于询问“截至该日期我们知道什么”的`query_timestamp`），因此单个记忆库在多个维度上保持可查询性。但标签是构建共同生活的主要旋钮。

## 你不必用手卷这个 {#you-do-not-have-to-hand-roll-this}

上面的策略不仅仅是你手工实现的概念。一些集成将记忆库范围直接公开为配置，阅读它们是如何实现的是内化模型的最快方法。

一些集成采用单个静态记忆库 ID，这是一行中的整个“共享记忆库”模式。在“一个记忆，三个表面”设置中，OpenClaw 固定到静态 `bankId`，并且 Vapi Webhook 是使用相同的 `bank_id` 构建的，因此语音呼叫和编码会话写入一个存储并从一个存储读取。

其他人从上下文中导出记忆库。 Claude Code集成有一个`dynamicBankId`开关和一个`dynamicBankGranularity`列表，用于命名要组合到id中的上下文字段，可以从`agent`、`project`、`session`、`channel`和`user`中进行选择。将其设置为`["user"]`，您将获得每个用户的记忆库；将其设置为`["agent", "project"]`，您将获得每个项目的每个智能体的记忆库。 Paperclip 与默认为 `["company", "agent"]` 的 `bankGranularity` 暴露了相同的想法，因此记忆的范围仅限于智能体在公司中的角色，而不是单次运行。 oh-my-pi 示例将选择拼写为三种命名模式：`global`、`per-project` 和 `per-project-tagged`，最后一个正是“一个记忆库加项目标签”。

`per-project-tagged`值得停下来，因为它是将两个轴组合成一个推荐：一个用于信任域的记忆库，一个用于其中项目的标签。当您不确定时，这通常就是您想要的形状。

## 一个或多个记忆库会影响性能吗？ {#does-one-bank-or-many-affect-performance}

比人们想象的要少，所以它很少是值得优化的正确选择。所有记忆都存在于一个表中，`bank_id` 作为每行的一列，而不是每个记忆库都有一个单独的表或数据库。分成许多记忆库不会增加配置，并且将所有内容放入一个库中也不会创建自己的整体结构。 记忆召回由 `bank_id` 过滤器限定范围，并且在默认的 Postgres 后端，每个记忆库都有自己的向量索引，因此一个记忆库的搜索在很大程度上与另一个记忆库保存的内容无关。

所以记忆库的数量通常并不是决定记忆召回快慢的杠杆。 “一个大的记忆库因此可以扩展”和“许多小的记忆库因此每个都保持快速”都是选择结构的薄弱理由。根据正确性来决定谁应该记忆什么，并将表现视为一个单独的问题。

## 反模式 {#anti-patterns}

**每个对话都有一个记忆库，作为你的实际策略。** 当没有配置任何其他内容时，某些集成会回退到对话范围的记忆库。这是一个好的*默认*和一个坏的*策略*：因为记忆库是在第一次使用时全新创建的，所以每个新的对话都会解析为一个新的、空的记忆库，因此智能体永远不会记住跨会话的任何内容。过去的记忆并没有被删除，只是无法访问，因为没有任何东西可以指向该对话的 ID。如果您的智能体“忘记了会话之间的所有内容”，这几乎总是原因：检查记忆库 id 实际解析的内容。

**多租户应用程序中的一个全局记忆库。** 经典泄漏。它在一个用户的演示中完美运行，但对于第二个用户来说却成为一个事件。租赁边界是记忆库边界，句号。

**过度碎片化。** 相反的失败。每个（用户 × 项目 × 智能体 × 会话）的记忆库感觉很整洁并且缺乏记忆召回：每个记忆库所容纳的内容非常少，以至于智能体几乎没有足够的上下文来发挥作用。 记忆召回的好坏取决于共享记忆库的内容。如有疑问，请选择较少的记忆库并依靠标签。

​​**记忆库 ID 不稳定。** 因为一个新的 id 是一个新的空记忆库，所以从不应该改变的东西（每台机器不同的绝对路径、会话令牌、被编辑的显示名称）中派生 id 会默默地将一个记忆分成许多个。从稳定身份中派生记忆库 ID：用户 ID、存储库名称、租户 ID。

## 决策清单 {#a-decision-checklist}

按顺序运行每个边界：

1. **它是租赁还是安全边界？**（不同的客户，不同的不可信来源）→ **独立记忆库**，始终。不要与标签协商这一点。
2. **A 的记忆是否需要到达 B？** 无 → 单独的记忆库。是的 → 继续阅读。
3. **相同的信任域，只是组织上的？**（一个租户内的项目、主题、团队）→ **一个记忆库，标签**。
4. **这些智能体应该在共享环境中进行协作吗？** → **一个共享记忆库** 他们都指向。
5. **无论你选择什么，记忆库id稳定吗？** 从持久的身份中衍生出来，而不是从偶然的事物中衍生出来。

## 你可以改变主意，但要付出代价 {#you-can-change-your-mind-at-a-cost}

记忆库策略不是一扇单向门，但也不是可以随意逆转的。由于记忆召回的范围仅限于记忆库，因此将一个记忆库拆分为多个（或将多个记忆库合并为一个）意味着在记忆库之间移动记忆并在您想要的位置重新建立历史记录，而不是翻转配置标志。这是非常可行的，而且在你积累了一年的记忆之前比之后更容易做到。现在花十分钟在清单上。
