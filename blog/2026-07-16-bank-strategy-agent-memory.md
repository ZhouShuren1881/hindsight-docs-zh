每个 Hindsight 集成都告诉你要设置 `bank_id`，却几乎没有集成会告诉你该如何决定记忆库应该*代表什么*。这个决定看似微不足道，却会影响智能体实际能召回什么。范围太宽，一个用户的记忆就可能泄露给另一个用户；范围太窄，智能体又无法获取所需内容，因为那部分内容位于它看不到的另一个记忆库中。

这是智能体记忆的模式设计问题。下面介绍如何作出选择。

<!-- truncate -->

## 概览 {#tldr}

- **记忆库是召回边界。** `recall`、`retain` 和 `reflect` 都在单个记忆库内运行，也没有跨记忆库查询。因此，“这两类内容应该放在同一个记忆库吗？”实际是在问：“A 存入的记忆，B 是否应该能够召回？”
- 对任何硬性隔离边界（例如租户、客户或不受信任的上下文），都应使用**独立记忆库**。对于有时需要筛选、有时需要交叉引用的软分区，则在**同一个记忆库中使用标签**。
- 记忆库会在首次使用时延迟创建，因此一个新的 `bank_id` 字符串对应一个新的空记忆库。这是造成大多数记忆碎片化的原因：每次对话使用一个记忆库，意味着每次对话都从空白开始。
- 有些集成会将这一选择作为配置项提供：可以设置静态 `bankId`，也可以根据 `user`、`project` 和 `agent` 等上下文字段组合出 `dynamicBankId`。
- 之后可以更改策略，但召回历史以记忆库为范围，因此一开始选好策略就能省去回填工作。

## 核心概念：记忆库是召回边界 {#the-one-idea-a-bank-is-a-recall-boundary}

在 Hindsight 中，记忆库是一个完整且彼此隔离的存储空间：其中包含从对话中存入的记忆、为检索而索引的文档、从文档中提取的实体、连接这些实体的知识图谱，以及该记忆库自己的性格倾向和强制指令。记忆库彼此隔离，也没有内置的跨库查询。每次 `recall`、`retain` 或 `reflect` 调用都必须指定一个 `bank_id`，且只能在这个记忆库内操作。

这个事实就是整个设计方法。与其问“我应该如何组织记忆”，不如针对每条边界问一个问题：

> 如果 A 存入一条记忆，B 是否应该能够召回它？

如果**是**，A 和 B 就属于同一个记忆库。如果**否**，它们就应属于不同的记忆库。下面的每种模式，都是把这个问题分别应用于两个用户、两个项目、两个智能体或两个渠道。

还有一个值得注意的机制细节：你不需要预先创建记忆库。首次使用某个 `bank_id` 时，Hindsight 会使用默认设置创建记忆库。这有一个实际好处（无需预配），也有一个容易踩的坑：从未写入过的 `bank_id` 就是一个空记忆库；拼写错误或不稳定的 ID 会悄悄创建一个新的空记忆库，而不会报错。记忆库的身份至关重要。

## 主要维度：一个记忆库代表什么？ {#the-main-axis-what-does-one-bank-represent}

下面是几种常见策略。每种策略都围绕召回边界问题来定义，并指出它在哪种情况下会出问题。

| 策略 | 每个记忆库对应 | 适用场景 | 可能的问题 |
|---|---|---|---|
| **全局** | 所有内容 | 单用户工具、个人开发助手 | 一旦出现第二个用户，两人的记忆就会混在一起 |
| **按用户划分** | 一个终端用户 | SaaS 产品、个人助理 | 一个用户有多个项目时，所有项目的内容都会混在一起 |
| **按项目 / 代码库划分** | 一个代码库或工作区 | 编程智能体、项目协作 | 用户在不同项目间的上下文无法随用户共享 |
| **按智能体划分** | 一种智能体角色 | 角色各异的多智能体系统 | 本应共享上下文的智能体无法共享 |
| **共享 / 团队** | 有意组成的一组人 | 在多个界面或团队成员之间共享同一份记忆 | 需要明确选择启用，并非默认设置 |

这些策略没有哪一种在抽象意义上绝对正确。合适的选择取决于 A 和 B 分别是谁：

- **面向消费者的助理**：每个人的记忆都绝不能触及其他人，选择**按用户划分**。用户是隔离边界，也就是记忆库边界。
- **编程智能体**：如果有用的记忆与*当前代码库*（它的约定、决策和布局）有关，选择**按代码库划分**。Aider 集成默认就是如此：它从 Git 代码库名称派生记忆库 ID，使得每个处理该代码库的编辑器都共享同一份项目记忆。
- **由专业智能体组成的团队**（例如规划者、研究员、审查者）：如果每个智能体都应保留自己的经历，选择**按智能体划分**。但如果希望它们协作并共享上下文，就让它们使用同一个**共享**记忆库。

## 多数人忽略的第二个维度：记忆库内的标签 {#the-second-axis-most-people-miss-tags-inside-a-bank}

我最常看到的一种错误，是每当想在同一个信任域内区分两*类*记忆时，就新建一个记忆库。其实不需要新建记忆库，只需要使用标签。

存入记忆时，Hindsight 允许附加 `tags`；召回或反思时，也可以按标签筛选。标签是在查询时应用于记忆库内部的分区，因此同一个记忆库可以容纳许多带标签的切片，并由你决定每次查询要查看哪些切片。

```python
# 存入时添加范围标签
client.retain(bank_id="acme", content="We deploy on Fridays only in emergencies",
              tags=["project:web"])

# 只在该切片内召回
client.recall(bank_id="acme", query="deploy policy?",
              tags=["project:web"], tags_match="all")
```

值得了解的是 `tags_match` 模式，因为它的默认行为比很多人预想的宽松：

- **`any`**（默认）：按 OR 匹配，并且*包含无标签记忆*。适合把标签当作提示而非隔离墙的情况。
- **`all`**：按 AND 匹配，也仍然包含无标签记忆。
- **`any_strict` / `all_strict`**：匹配方式相同，但会排除无标签记忆。
- **`exact`**：记忆的标签集合必须与查询的标签集合完全相同。

这个默认行为说明了何时不该使用标签：由于 `any` 会包含无标签记忆，标签只是**软分区**，便于组织内容，却不是安全控制。如果某条记忆绝不能出现在错误的上下文中，就不要依赖一个可能被忘记传入的标签筛选条件。应将它放进独立的记忆库。

因此，真正的决策分为两个层次：

- **硬性隔离**（租户、客户、不受信任的来源，或任何发生泄漏就属于错误的情况）：使用**独立记忆库**。隔离由存储边界强制保障，而不是靠记住要加筛选条件。
- **软分区**（在一个信任域内组织项目、主题或用户，并且有时希望筛选、有时希望一起查看）：使用**一个记忆库加标签**。

举个例子：服务于一家公司的单租户内部助理可以只使用一个记忆库，并用 `project:web`、`project:billing` 和 `team:sre` 这样的 `tags` 来组织内容。这样，关于计费的问题既可以严格限定范围，也可以开放范围以利用所有内容。但在多租户 SaaS 中，如果每个客户都是不同的公司，就必须给每个客户分配自己的记忆库。标签负责组织，记忆库负责隔离。

除了标签，召回还可以按事实 `types` 和时间筛选（使用 `created_after` / `created_before`，或通过 `query_timestamp` 询问“截至这一天，我们知道什么”）。因此，单个记忆库仍可从多个维度进行查询。但对于组织哪些内容放在一起，标签是最主要的调节手段。

## 无需自己从头实现 {#you-do-not-have-to-hand-roll-this}

上面的策略不只是需要手动实现的概念。有些集成会直接通过配置提供记忆库范围；阅读它们的实现方式，是快速理解这一模型的好方法。

有些集成使用单个静态记忆库 ID，一行配置就能实现“共享记忆库”模式。在“一个记忆库，三个界面”的方案中，OpenClaw 固定使用静态 `bankId`，Vapi Webhook 也使用同一个 `bank_id` 构造，因此语音通话和编程会话会读写同一份存储。

另一些集成则根据上下文派生记忆库 ID。Claude Code 集成提供 `dynamicBankId` 开关和 `dynamicBankGranularity` 列表，用来指定组合成 ID 的上下文字段，可从 `agent`、`project`、`session`、`channel` 和 `user` 中选择。设置为 `["user"]`，就会按用户划分记忆库；设置为 `["agent", "project"]`，就会按智能体和项目的组合划分记忆库。Paperclip 提供了相同的概念，配置项为 `bankGranularity`，默认值是 `["company", "agent"]`，因此记忆范围对应于智能体在公司的角色，而不是单次运行。oh-my-pi 示例则把选择明确列为三种命名模式：`global`、`per-project` 和 `per-project-tagged`；最后一种正是“一个记忆库加项目标签”。

值得特别看看 `per-project-tagged`：它把两个维度合成了一条建议——在一个信任域中使用一个记忆库，再用标签区分其中的项目。如果拿不准，通常可以采用这种结构。

## 一个或多个记忆库会影响性能吗？ {#does-one-bank-or-many-affect-performance}

性能受记忆库数量的影响比人们通常想象的要小，因此这很少是值得优先优化的因素。所有记忆都存储在同一张表中，每行用 `bank_id` 标记，而不是为每个记忆库单独建表或数据库。拆分成多个记忆库不会增加预配工作；把所有内容放在一个记忆库中，也不会因此形成一个自身结构庞大的整体。召回通过 `bank_id` 筛选；在默认的 Postgres 后端中，每个记忆库都有自己的向量索引，因此一个记忆库的搜索基本不受另一个记忆库数据量的影响。

因此，记忆库数量通常不是决定召回速度的关键。“用一个大记忆库来扩展”以及“用许多小记忆库来保持速度”，都是选择结构时不充分的理由。应根据正确性来决定谁能召回哪些内容，并把性能作为另一个问题单独考虑。

## 反模式 {#anti-patterns}

**把每段对话单独放进一个记忆库，并以此作为实际策略。** 有些集成在未配置其他选项时，会回退到按对话划分记忆库。这作为一个*默认值*很合适，作为一种*策略*却很糟糕：因为记忆库会在首次使用时新建，每段新对话都会对应一个新的空记忆库，智能体自然无法跨会话记住任何内容。过去的记忆并未删除，只是无法访问，因为没有任何东西会再指向那段对话的 ID。如果你的智能体“每次会话之间都会忘光”，这几乎总是原因：检查记忆库 ID 最终解析成了什么。

**多租户应用使用一个全局记忆库。** 这是经典的数据泄漏场景。单用户演示中运行完美，第二个用户出现后就会变成一次安全事故。租户边界就是记忆库边界，没有例外。

**过度碎片化。** 这是相反方向的问题。为每个（用户 × 项目 × 智能体 × 会话）组合都建一个记忆库，看似整齐，却会让召回缺少足够内容：每个记忆库中的内容都太少，智能体几乎无法获得足以发挥作用的上下文。召回效果取决于同一个记忆库中有哪些内容。拿不准时，优先减少记忆库数量，并使用标签。

**记忆库 ID 不稳定。** 新 ID 会对应一个新的空记忆库，因此如果从本不该变化的值派生 ID（例如因机器不同而变化的绝对路径、会话令牌或可能被编辑的显示名称），一个记忆就会悄悄分散到多个记忆库中。应从稳定的身份信息派生记忆库 ID，例如用户 ID、代码库名称或租户 ID。

## 决策清单 {#a-decision-checklist}

按以下顺序检查每条边界：

1. **它属于租户边界或安全边界吗？**（例如不同客户、不同的不可信来源）→ 始终使用**独立记忆库**。不要试图用标签替代隔离。
2. **A 的记忆是否需要被 B 获取？** 不需要 → 使用独立记忆库。需要 → 继续判断。
3. **它们属于同一个信任域，只是组织方式不同吗？**（例如一个租户内的项目、主题或团队）→ 使用**一个记忆库加标签**。
4. **这些智能体是否需要协作并共享上下文？** → 让它们都指向**同一个共享记忆库**。
5. **无论选哪种方案，记忆库 ID 都稳定吗？** 应从持久的身份信息派生，而不是依赖偶然的值。

## 可以改变主意，但需要付出代价 {#you-can-change-your-mind-at-a-cost}

记忆库策略不是单向门，但要逆转也不是零成本。由于召回以记忆库为范围，把一个记忆库拆分成多个（或把多个合并成一个），就需要在记忆库之间迁移记忆，并在需要的地方重新建立历史，而不能只改一个配置开关。这完全可行，而且在积累一年的记忆之前完成，要比之后容易得多。现在花十分钟按清单作出选择吧。
