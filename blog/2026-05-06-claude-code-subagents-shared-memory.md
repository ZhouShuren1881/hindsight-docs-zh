![您的Claude Code子代理不分享他们学到的东西](/img/blog/claude-code-subagents-memory.webp)

[ClaudeCode的子代理系统](https://docs.claude.com/en/docs/claude-code/sub-agents) 是今年在线束层中发布的最好的东西之一。您可以将工作委托给专门的智能体 — `Plan` 来思考策略，`Explore` 来抓取代码库，`general-purpose` 来处理多步骤任务，或者您在 `.claude/agents/` 下定义的任何自定义子代理。每个程序都在自己的上下文中运行，具有自己的系统提示符和工具，并在完成时报告。

这是一个干净的委托模型。默认情况下，它也是以特定方式失忆的：每个子代理调用都是全新的，即使您选择持久性功能Claude Code确实发布了，知识仍然孤立在每个子代理内。

​​无论子代理发现什么——它发现的文件、它注意到的架构模式、它遇到的死胡同、用户在任务中做出的决定——在它返回时都会消失。协调器收到最后一条消息。其他一切都蒸发了。

如果您曾经连续两次启动相同的`Explore`智能体来寻找它已经找到的东西，那么您就成功了。如果您曾经看到两个并行子代理独立地发现相同的约束，那么您就遇到了这一点。如果您曾经想知道为什么您的自定义代码审查子代理似乎永远不会了解您的团队真正关心的内容，那么您就遇到了这个问题。

## 概览 {#tldr}

- Claude Code子代理（`.claude/agents/`下的计划、探索、通用和自定义子代理）默认在每次调用时重新启动
- Claude Code确实提供了两个部分答案 - `memory` 字段（每个子代理持久目录）和通过 `SendMessage` 恢复实验子代理 - 但都没有解决 *跨子代理* 共享问题
- 每个子代理的 `memory` 目录与其他子代理的目录是相互隔离的。代码审查者看不到安全审核员学到的内容，反之亦然。
- 共享记忆层（单个项目记忆库上的Hindsight）为每个子代理（加上协调器）提供了一个共同的、积累的理解
- 该模式镜像文件系统与记忆：每个子代理`MEMORY.md`文件是一个硬盘；共享学习记忆库更接近于记忆
- [Hindsight](https://github.com/vectorize-io/hindsight)是记忆层； [hindsight-记忆插件](https://hindsight.vectorize.io/integrations) 自动将其连接到 Claude Code的会话挂钩

## 子代理已经做得很好的事情 {#what-subagents-already-do-well}

子代理不是问题。它们是对真实问题的答案。

单个Claude Code会话有限制。上下文窗口被填满。长时间的探索任务会产生噪音，从而排挤工作。专门的工作——规划、搜索、代码审查、安全分析——受益于集中的系统提示，而不必与编排器的一般指令共存。

​​子代理解决了所有这些问题。他们给你：

- **每个任务都有新鲜的上下文。** 大型探索工作不会毒害编排者的工作记忆。
- **专门的提示和工具。** 代码审阅者子代理可以比父代理拥有更严格的工具权限和更严格的系统提示。
- **并行性。** 多个子代理可以独立运行，完成后返回其摘要。
- **干净的返回协议。** 编排器收到一条可以采取行动的最终消息。没有保姆。

该模型有效。也正是这种模型使得记忆差距不可避免。

## 当子代理返回时会消失什么 {#what-disappears-when-a-subagent-returns}

子代理在其自己的循环中运行。它读取文件。它发出 grep 声。它调用工具。它形成假设。它排除了一些事情。它对值得追求的事情做出中间决定。它写入最终消息并退出。

协调器收到最终消息。其他一切都消失了。

包括：

- **探索之路。** 子代理打开了哪些文件，排除了哪些文件，查找了哪些文件但没有找到。
- **中间决策。**“我尝试了方法X，但由于Y而不起作用，所以我改用Z。”
- **发现的隐式约定。**“此存储库中的所有 HTTP 处理程序都使用 `withAuth` 包装器，即使它不在自述文件中。”
- **死胡同。** 子代理考虑并拒绝的五件事，未来的子代理可能会直接返回。

对于单个一次性任务，这些都不重要——最终消息捕获相关结果。对于随着时间的推移涉及多个子代理调用的任何工作，所有这些都是您生成然后丢弃的信息。

## Claude Code已经做了什么（以及它停止的地方） {#what-claude-code-already-does-and-where-it-stops}

Claude Code并非不知道这一点。它提供了两种部分解决子代理持久性问题的机制——两者都值得了解，但都不足以实现跨子代理共享理解。

**`memory`字段。** 子代理的YAML frontmatter 可以包括`memory: project`（或`user`、或`local`）。设置后，Claude Code会为该子代理提供一个持久目录 - `~/.claude/agent-memory/<name>/`用于`user`范围，`.claude/agent-memory/<name>/`用于`project` - 并在每次调用时从该目录将前200行`MEMORY.md`自动注入到系统提示符中。子代理启用读/写/编辑工具，以便它可以随着时间的推移整理自己的笔记。

对于同一个子代理重复执行相同类型工作的任务来说，这是真正的持久性和真正的胜利。问题是：每个子代理都有其 **自己** 记忆目录。您的 `code-reviewer` 子代理的 `MEMORY.md` 对您的 `security-auditor` 子代理不可见，反之亦然。知识是按每个子代理积累的，而不是跨子代理积累的。它也是一个 Markdown 文件——与我们批评的 `CLAUDE.md` 相同的文件系统即记忆模式。没有综合，没有相关性排名，没有心智模型。仅记录子代理在启动时读取并在出现提示时进行编辑的文件。

**子代理通过`SendMessage`恢复。** 实验性，位于`CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`后面。启用后，Claude 可以通过 ID 恢复特定的子代理，并且子代理会获取其完整的对话历史记录 - 每个先前的工具调用、结果和推理步骤。子代理记录独立于主对话压缩而持续存在，并在 Claude Code重新启动（通过恢复父会话）时继续存在。

当您想继续时，这是正确的答案*一个*子代理正在进行的工作。它没有解决这样的情况：许多子代理（不同类型、跨不同会话）应该共享对您的项目不断积累的理解。

所以Claude Code的本机答案解决了“这个子代理应该记住它自己的过去”。它们并没有解决“我的所有子代理应该对我们共同学到的东西有一个共同的、不断增长的理解”的问题。

## 疼痛出现的地方 {#where-the-pain-shows-up}

这不是理论上的。模式重复：

### 两个探索智能体，一个代码库 {#two-explore-agents-one-codebase}

您在周一启动`Explore`子代理来查找使用身份验证中间件的每个位置。它返回一个干净的摘要。您在周二启动了另一个 `Explore` 子代理来查找构建用户模型的每个位置。第二个智能体重新 grep 一半相同的文件，重新发现相同的身份验证包装器，并像第一次一样报告回来。

第一个智能体的探索可以捷径到第二个智能体的探索。没有什么可以延续。

### 发生碰撞的并行子智能体 {#parallel-subagents-that-collide}

您并行生成三个子代理来调查三个相关问题。每个人都独立地重新发现代码库中相同的架构怪癖。在三个返回的消息中，您会得到同一观察的三个略有不同的框架，编排器必须协调它们。

如果他们共享记忆，第二个和第三个智能体就会从“第一个智能体已经注意到这一点；还有什么是真的？”开始。

### 永远不会了解您团队偏好的自定义子代理 {#the-custom-subagent-that-never-learns-your-teams-preferences}

您在`.claude/agents/code-reviewer.md`中编写了一个`code-reviewer`子代理。它在第一个 PR 上做得很好。在第二个 PR 上，它标记了您的团队明确决定不强制执行的相同 lint 模式。在第三个 PR 中，它主张您在上次冲刺中拒绝的重构模式。

您可以更新系统提示以捕获这些决定。但你必须记住要做，而且必须手动去做。子代理本身没有从前两个 PR 中学到任何东西。

### 每次都需要重新指导的编排器 {#the-orchestrator-that-has-to-re-instruct-every-time}

协调者从对话中了解事情。它刚刚产生的子代理对那次对话一无所知。因此，协调器必须每次都在子代理提示中重复上下文。这会消耗 Orchestrator 令牌，但仍然不会转移到 *下一个* 子代理。

## 共享记忆会带来什么变化 {#what-changes-with-shared-memory}

共享记忆层——协调器在会话运行时读取和写入的记忆库——翻转模型。您将获得一个学习层，而不是每个子代理一个的 N 个孤立的 `MEMORY.md` 文件。

现在图片是这样的：

- 编排器在每个回合之前提取相关记忆，并将该上下文带入它发送给子代理的提示中
- 完整的会话记录——编排器回合加上每个子代理的工具结果——在回合结束时保留回同一个记忆库
- 下一个子代理（在此会话或下一个会话中）继承之前保留的所有内容，通过协调器呈现

第一个`Explore`智能体的发现可用于第二个——因为它们是在前一个会话的记录中捕获的，并在下一个相关提示中再次出现。自定义 `code-reviewer` 子代理继承了您的团队在之前的审核中积累的偏好 - 因为编排器会召回它们并将它们包含在审核摘要中。并行子代理不再发生冲突，因为它们是由已经知道项目已确定的内容的协调者委托的。

协调器停止在每个会话中花费token重新解释相同的上下文。它从记忆库中提取它。

这是一个不小的人体工程学胜利。这是作为委托原语的子代理和作为*团队*的子代理之间的区别。

## 设置 {#setting-it-up}

集成是故意省力的。 Claude Code的[hindsight-记忆插件](https://hindsight.vectorize.io/integrations)使用标准[钩子架构](https://docs.claude.com/en/docs/claude-code/hooks)：

- `SessionStart` — 记忆库健康检查
- `UserPromptSubmit` — 在调用模型之前自动记忆相关记忆
- `Stop` — 回合结束时自动记忆存储会话记录
- `SessionEnd` — 清理

钩子在**会话级别**处触发，而不是在子代理循环内。这听起来像是一个限制，但实际上正是使共享记忆的设计变得干净的原因：

- **记忆召回** 在编排器轮到时发生一次 — 编排器拾取相关上下文 *之前* 它决定委托。无论它从记忆中知道什么，都会被带入它通过 `Task` 工具构建的子代理提示中。子代理通过协调器间接继承上下文，而不需要自己的钩子。
- **记忆存储
子代理完成并返回后，** 在编排器的 `Stop` 运行。它读取完整的会话 JSONL 记录，该记录捕获每个子代理的工具结果和最终消息。因此，子代理所做或发现的所有内容最终都会存储在记忆库中 - 不需要每个子代理的连接。

最终效果就是您想要的：子代理从累积的学习中受益（在进入时由编排器介导，在退出时捕获完整记录），并且您只需配置一组钩子。

典型的项目设置位于`~/.hindsight/claude-code.json`：

```json
{
  "bankId": "my-project",
  "autoRecall": true,
  "autoRetain": true
}
```

`bankId` 是共享身份 — 该项目中的每个会话以及它生成的每个子代理，都会向`my-project` 写入和读取。如果您想要按项目、按用户或按通道隔离，请设置 `dynamicBankId: true` 并配置 `dynamicBankGranularity`（例如 `["agent", "project"]` 或 `["user"]`）。 [记忆库参考](https://hindsight.vectorize.io/developer/api/memory-banks)覆盖了图案；同一套钩子支持所有这些。

这就是整个设置。经过几个正常工作会话后，您可以针对此记忆库运行子代理，并观察编排器表面的偏好和先前子代理在上一个会话中找出的决策。

## 一周后会是什么样子 {#what-this-looks-like-across-a-week}

记忆效果复合。针对共享记忆库正常使用子代理一周后，您开始注意到：

- 重复探索不再重复
- 编排器不再需要将上下文重新粘贴到子代理提示中
- 自定义子代理（代码审阅者、安全检查者、文档编写者）可以更好地匹配您团队的偏好，而无需您编辑他们的系统提示
- 新会议并不感觉像是冷启动——项目积累的理解已经存在

对于单独工作，感觉就像安全带终于记住了。对于多人在同一项目记忆库上使用Claude Code的团队设置，感觉智能体正在共享大脑而不是独立的重新推导中工作。

## 即将发生的事情的快速说明 {#a-quick-note-on-whats-coming}

当前模型是：Hindsight保留和回忆记忆；您（或您的子代理）通过记忆库读取和写入它。

下一步更接近真正自我完善的智能体。很快，Hindsight将能够**直接写回塑造智能体行为的 Markdown 文件** - [`CLAUDE.md`](https://docs.claude.com/en/docs/claude-code/memory)，`.claude/agents/`下的自定义子代理提示，甚至[技能](https://docs.claude.com/en/docs/claude-code/skills)。当智能体学习您团队的惯例和决策时，这些学习内容将反映到下一个会话加载的静态文件中。您停止手动维护`CLAUDE.md`。智能体根据其实际观察到的情况为您维护它。

这是更广泛的自动驾驶智能体推动的一部分，我们很快就会详细讨论。目前，共享记忆层是目前可用的部分，也是为您提供即时复合效果的部分。

## 权衡和限制 {#tradeoffs-and-limits}

共享记忆并不总是正确的选择。一些诚实的权衡：

- **记忆库范围很重要。** 在不相关的项目之间共享的单个记忆库会产生噪音。在适当的情况下，每个项目使用一个记忆库，或每个团队使用一个记忆库。 [记忆库参考](https://hindsight.vectorize.io/developer/api/memory-banks) 覆盖了图案。
- **敏感上下文。** 如果子代理正在读取客户数据，请仔细考虑保留哪些内容。插件的保留是可配置的；您可以将特定数据保留在记忆库之外。
- **单拍作品。** 如果您几乎从不使用子代理并且您的会话是隔离的，则该值较低。 当工作是迭代的时候，记忆就会得到回报。
- **最初的几天。** 新的记忆库是空的。经过几次训练后，复合效应就会开始显现——通常在正常使用后一周内。
- ​​**你可能不需要共享记忆。** 如果您只使用一种类型的子代理并且它可以单独工作，则Claude Code的本机`memory`字段本身就足够了——它随着时间的推移而管理的每个子代理`MEMORY.md`。当您有多个应该共享理解的子代理时，当您想要学习记忆而不是基于文件的笔记时，或者当相同的知识需要在协调器及其子代理中呈现时，Hindsight 是正确的答案。

这些并不是破坏交易的因素，只是需要考虑尺寸。对于大多数定期运行多个子代理的Claude Code用户来说，正确的答案是一个具有自动记忆存储和自动记忆召回功能的记忆库项目。

## 回顾 {#recap}

- Claude 默认情况下，代码子代理在每次调用时都会重新启动；只有最终消息返回到协调器
- Claude Code的本机 `memory` 字段为子代理提供了自己的持久 `MEMORY.md` — 有用，但每个子代理的目录与其他子代理的目录是隔离的
- `SendMessage`简历（实验性）让您可以继续*一个*子代理的工作，但不解决共享知识的情况
- 如果没有共享层，同级子代理会发生冲突，顺序子代理会重新推导其前辈发现的内容
- 一个共享的Hindsight记忆库为每个子代理和编排器提供了共同的、不断增长的理解——而不是N个孤立的`MEMORY.md`文件
- 后见之明记忆插件使用Claude Code的会话挂钩，因此子代理继承对共享记忆库的访问权限，而无需每个子代理连接
- 自我改进行为——包括更新自己的`CLAUDE.md`的智能体——是下一层；共享记忆是它的基础

子代理是Claude Code如何扩展到一个上下文窗口之外的。共享记忆库是这些子代理如何不再彼此陌生的原因。
