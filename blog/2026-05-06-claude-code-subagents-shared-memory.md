![Claude Code 子代理不会共享它们学到的内容](/img/blog/claude-code-subagents-memory.webp)

[Claude Code 的子代理系统](https://docs.claude.com/en/docs/claude-code/sub-agents)是今年智能体运行框架层最值得推出的功能之一。你可以把工作委托给专门的智能体：让 `Plan` 制定策略，让 `Explore` 遍历代码库，让 `general-purpose` 处理多步骤任务，或使用你在 `.claude/agents/` 下定义的自定义子代理。每个子代理都在自己的上下文中运行，使用自己的系统提示和工具，并在完成后汇报。

这是一种简洁的委托模式。默认情况下，它也有一种特定的遗忘方式：每次调用子代理都会从头开始；即使启用 Claude Code 已提供的持久化功能，知识仍会被隔离在各个子代理内部。

子代理发现的一切——找到的文件、注意到的架构模式、遇到的死路、用户在任务中途做出的决定——都会在它返回时消失。编排器只会收到最终消息，其他一切都烟消云散。

如果你曾连续两次启动同一个 `Explore` 智能体去寻找它刚找到过的内容，就遇到过这个问题。如果你曾看到两个并行子代理各自发现同一个约束，也遇到过这个问题。如果你曾纳闷自定义代码审查子代理为何始终学不会团队真正关心什么，同样是这个问题。

## 概览 {#tldr}

- Claude Code 子代理（`.claude/agents/` 下的 Plan、Explore、general-purpose 和自定义子代理）默认每次调用都会从头开始
- Claude Code 确实提供了两种不完整的解决方案——`memory` 字段（每个子代理各自的持久目录）和通过 `SendMessage` 实验性地恢复子代理——但都无法解决**跨子代理共享**的问题
- 每个子代理的 `memory` 目录都与其他子代理隔离。代码审查子代理看不到安全审计子代理学到的内容，反之亦然
- 共享记忆层（在单个项目记忆库上使用 Hindsight）让每个子代理以及编排器都能拥有共同且不断累积的理解
- 这种模式体现了文件系统与记忆的差别：每个子代理各自的 `MEMORY.md` 文件像硬盘；共享的学习型记忆库则更接近记忆
- [Hindsight](https://github.com/vectorize-io/hindsight)提供记忆层；[hindsight-memory 插件](/integrations)会自动通过 Claude Code 的会话钩子接入

## 子代理已经做得很好的事情 {#what-subagents-already-do-well}

子代理不是问题，而是对一个现实问题的解决方案。

单个 Claude Code 会话有其局限。上下文窗口会被填满。漫长的探索任务会产生大量信息，挤占实际工作的空间。规划、搜索、代码审查和安全分析等专门工作，适合使用聚焦的系统提示，而不必与编排器的通用指令挤在一起。

子代理解决了这些问题。它们为你带来：

- **每项任务都有全新上下文。** 大型探索任务不会污染编排器的工作记忆。
- **专门的提示和工具。** 代码审查子代理可以比父级智能体拥有更严格的工具权限和更精炼的系统提示。
- **并行处理。** 多个子代理可以独立运行，并在完成后返回摘要。
- **清晰的返回协议。** 编排器会收到一条可供采取行动的最终消息，无需全程盯着子代理。

这种模式行之有效。但也正是它让记忆缺口无可避免。

## 子代理返回后，哪些内容会消失 {#what-disappears-when-a-subagent-returns}

子代理在自己的循环中运行：读取文件、搜索代码、调用工具、形成假设、排除可能性，并判断哪些方向值得继续探索。最后，它写下最终消息并退出。

编排器收到最终消息，其他一切都不复存在。

消失的内容包括：

- **探索轨迹。** 子代理打开了哪些文件、排除了哪些文件、搜索了什么却没有找到什么。
- **中间决策。**“我试了方法 X，但因为 Y 行不通，所以改用了 Z。”
- **发现的隐性约定。**“这个代码库中的所有 HTTP 处理器都使用 `withAuth` 包装器，即使 README 里没有提到。”
- **走过的死路。** 子代理考虑后放弃的五种做法，未来的子代理可能会再次尝试。

对于一次性的任务，这些都无关紧要——最终消息已经包含相关结果。但只要工作需要在一段时间内多次调用子代理，这些内容就都是你生成后又丢弃的信息。

## Claude Code 已经提供了什么（以及它的局限） {#what-claude-code-already-does-and-where-it-stops}

Claude Code 并非没有意识到这个问题。它提供了两种部分解决子代理持久性问题的机制，值得了解，但都不足以让不同子代理共享理解。

**`memory` 字段。** 子代理的 YAML frontmatter 可以包含 `memory: project`（也可以是 `user` 或 `local`）。启用后，Claude Code 会为该子代理提供一个持久目录：`user` 范围使用 `~/.claude/agent-memory/<name>/`，`project` 范围使用 `.claude/agent-memory/<name>/`；每次调用时，它还会自动将该目录中 `MEMORY.md` 的前 200 行注入系统提示。子代理会获得 Read、Write 和 Edit 工具，以便随时间推移整理自己的笔记。

对于反复执行同类工作的同一个子代理来说，这确实带来了持久性，也确实很有帮助。问题在于，每个子代理都有**自己的**记忆目录。你的 `code-reviewer` 子代理的 `MEMORY.md` 对 `security-auditor` 子代理不可见，反之亦然。知识只会在各个子代理内部累积，不能在它们之间共享。而且，这仍是一个 Markdown 文件——正是前面批评 `CLAUDE.md` 时提到的“以文件系统充当记忆”的模式。它没有综合生成、相关性排序或心智模型，只是一些子代理启动时读取、在得到提示后编辑的文件。

**通过 `SendMessage` 恢复子代理。** 这是实验性功能，需启用 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`。启用后，Claude 可以按 ID 恢复特定子代理；该子代理会接续完整的对话历史，包括之前的每次工具调用、结果和推理步骤。子代理记录独立于主对话压缩而持续保存；通过恢复父会话，也可以在 Claude Code 重启后继续使用。

如果你想继续**一个**子代理尚未完成的工作，这就是合适的方案。但它无法解决另一个问题：多个不同类型的子代理跨越多个会话，共享对项目不断累积的理解。

因此，Claude Code 的原生方案解决的是“这个子代理应该记住自己的过去”，却没有解决“我的所有子代理应该共享对我们共同所学内容的、持续增长的理解”。

## 问题会在哪里显现 {#where-the-pain-shows-up}

这不是理论上的担忧。类似情况会一再发生：

### 两个 Explore 智能体，一个代码库 {#two-explore-agents-one-codebase}

周一，你启动一个 `Explore` 子代理，查找身份验证中间件的所有使用位置。它返回一份清晰的摘要。周二，你又启动另一个 `Explore` 子代理，查找构造用户模型的所有位置。第二个子代理重新搜索了半数相同的文件，再次发现相同的身份验证包装器，并像第一次发现一样汇报结果。

第一个子代理的探索本可以让第二个少走弯路，却没有任何内容得以延续。

### 并行子代理彼此撞车 {#parallel-subagents-that-collide}

你并行启动三个子代理，分别调查三个相关问题。它们各自独立地重新发现代码库中同一个架构特征。于是你在三条返回消息中看到对同一观测的三种略有差异的表述，还得由编排器协调这些结果。

如果它们共享记忆，第二和第三个子代理就可以从“第一个已经注意到这一点；还有什么值得确认？”开始。

### 永远学不会团队偏好的自定义子代理 {#the-custom-subagent-that-never-learns-your-teams-preferences}

你在 `.claude/agents/code-reviewer.md` 中编写了一个 `code-reviewer` 子代理。它审查第一个 PR 时表现不错。到了第二个 PR，它又标记了团队明确决定不强制执行的同一种 lint 规则。第三个 PR 中，它又建议采用你们上个冲刺已经否决的重构模式。

你可以更新系统提示来记录这些决定，但得先记得这么做，而且还得手动修改。子代理自己并没有从前两个 PR 中学到任何东西。

### 编排器每次都得重新交代背景 {#the-orchestrator-that-has-to-re-instruct-every-time}

编排器从对话中了解一些情况，但刚启动的子代理对那段对话一无所知。因此，编排器每次都必须在子代理提示中重复这些背景。这会消耗编排器的 token，却仍然无法把这些背景传递给**下一个**子代理。

## 共享记忆会带来哪些变化 {#what-changes-with-shared-memory}

共享记忆层会改变这种模式：编排器在会话进行期间从同一个记忆库读取并写入记忆。这样，你就不再需要为每个子代理各自维护一个互相隔离的 `MEMORY.md` 文件，而是有了一个供所有人共同使用的学习层。

整体流程会变成这样：

- 编排器在每轮开始前提取相关记忆，并把这些背景带入发给子代理的提示中
- 每轮结束时，完整会话记录——包括编排器的轮次和每个子代理的工具结果——都会存回同一个记忆库
- 无论是在当前会话还是下一个会话中启动的子代理，都能通过编排器获取此前存入的内容

第一个 `Explore` 智能体的发现可以供第二个使用，因为这些发现已记录在上一轮会话的记录中，并会在下一个相关提示中重新呈现。自定义 `code-reviewer` 子代理可以继承团队在以往审查中积累的偏好，因为编排器会召回这些偏好并将其放进审查简报。并行子代理也不再彼此撞车，因为它们是由已经了解项目既有结论的编排器委派的。

编排器不必在每个会话中都花费 token 重新解释相同背景，而是可以从记忆库中提取这些信息。

这带来的不只是小小的使用体验改善，而是让子代理从一种委托机制变成一个**团队**的区别。

## 设置方法 {#setting-it-up}

这项集成刻意设计得很简单。面向 Claude Code 的 [hindsight-memory 插件](/integrations)使用标准的 [钩子架构](https://docs.claude.com/en/docs/claude-code/hooks)：

- `SessionStart` — 检查记忆库的健康状态
- `UserPromptSubmit` — 在调用模型前自动召回相关记忆
- `Stop` — 在轮次结束时自动存入会话记录
- `SessionEnd` — 清理

这些钩子在**会话级别**触发，而不是在子代理循环内部触发。乍看这像是限制，但恰恰因此，共享记忆的设计才更清晰：

- **Recall（召回）** 会在编排器的一轮开始时执行一次：编排器先获取相关背景，之后才决定是否委派任务。它从记忆中获得的内容会通过 `Task` 工具写入它构造的子代理提示中。子代理通过编排器间接继承背景，无需为自己配置钩子。
- **Retain（存入）** 会在子代理完成并返回后，于编排器的 `Stop` 钩子中运行。它会读取完整的会话 JSONL 记录，其中包含每个子代理的工具结果和最终消息。因此，子代理做过或发现过的内容最终都会存入记忆库，无需为每个子代理单独接线。

最终效果正如你所需：子代理能受益于累积的学习成果（进入时由编排器传递，退出时由完整记录保存），而你只需配置一套钩子。

典型的项目配置位于 `~/.hindsight/claude-code.json`：

```json
{
  "bankId": "my-project",
  "autoRecall": true,
  "autoRetain": true
}
```

`bankId` 是共享身份标识：该项目中的每个会话，以及它启动的每个子代理，都会从 `my-project` 读取并向其中写入。如果你希望按项目、用户或通道隔离，可以将 `dynamicBankId` 设为 `true`，并配置 `dynamicBankGranularity`（例如 `["agent", "project"]` 或 `["user"]`）。[记忆库参考](/developer/api/memory-banks)介绍了这些模式；同一套钩子都适用。

这就是全部设置。正常工作几个会话后，你就可以让子代理使用这个记忆库，并观察编排器如何呈现此前会话中的子代理总结出的偏好和决策。

## 一个具体的前后对比 {#a-concrete-beforeafter}

之前：

> **编排器：** 使用 Explore 智能体，找出所有调用 Stripe webhook 处理器的位置。
>
> *（Explore 智能体搜索代码并打开 12 个文件，随后返回：“找到 7 个调用位置。它们都在 `src/billing/` 中。处理器签名为 `(req, res) => Promise<void>`，7 个包装调用中有 5 个使用我们的 `withSpan` 追踪辅助函数。”）*
>
> **编排器：** 现在使用 Explore 智能体，找出所有调用 Slack webhook 处理器的位置。
>
> *（Explore 智能体搜索代码并打开 11 个文件，随后返回：“找到 4 个调用位置。它们都在 `src/notifications/` 中。处理器签名为 `(req, res) => Promise<void>`，4 个包装调用中有 3 个使用我们的 `withSpan` 追踪辅助函数。”）*

第二次探索没有从第一次探索中学到任何东西，只能从头重新发现共享的 `withSpan` 模式。

之后：

> **编排器：** 使用 Explore 智能体，找出所有调用 Slack webhook 处理器的位置。
>
> *（Explore 智能体从共享记忆库中召回：“我们在项目范围内约定用 `withSpan` 包装 webhook 处理器；上次是在探索 Stripe webhook 时观察到的。请确认这一约定仍然成立。”）*
>
> *（Explore 智能体搜索代码并打开 4 个文件，随后返回：“在 `src/notifications/` 中找到 4 个调用位置。该约定仍然成立：4 个中有 3 个使用 `withSpan` 包装。第 4 个是 Slack 重试路径中的已知例外，建议进行审查。”）*

任务相同，探索量减半，答案却更有用。第二个智能体是在第一个的基础上继续工作的。

## 一周后的情况 {#what-this-looks-like-across-a-week}

记忆带来的效果会不断累积。使用共享记忆库正常运行子代理一周后，你会开始注意到：

- 重复探索不再反复做相同的事
- 编排器不再需要把背景重新粘贴到子代理提示中
- 自定义子代理（代码审查、安全检查、文档编写）更能贴合团队偏好，而且不需要你编辑它们的系统提示
- 新会话不再像冷启动，因为项目积累的理解已经留存下来

对于个人工作来说，这种体验就像智能体运行框架终于记住了事情。如果团队中的多人都在同一个项目记忆库上使用 Claude Code，体验则像是智能体共享同一套认知，而不是各自独立重新推导。

## 简述即将推出的功能 {#a-quick-note-on-whats-coming}

当前的模式是：Hindsight 存入并召回记忆；你（或你的子代理）通过记忆库读取和写入这些内容。

下一步将更接近真正能够自我改进的智能体。不久后，Hindsight 将能够**直接回写塑造智能体行为的 Markdown 文件**，包括 [`CLAUDE.md`](https://docs.claude.com/en/docs/claude-code/memory)、`.claude/agents/` 下的自定义子代理提示，甚至是[技能](https://docs.claude.com/en/docs/claude-code/skills)。随着智能体学会团队的约定和决策，这些学习成果会反映到下次会话加载的静态文件中。你不必再手动维护 `CLAUDE.md`；智能体会根据实际观察到的内容替你维护它。

这是更广泛的自动驾驶智能体计划的一部分，我们很快会进一步介绍。目前，共享记忆层是已经可用的部分，也能立即带来累积效应。

## 权衡与限制 {#tradeoffs-and-limits}

共享记忆并非总是合适的选择。以下是一些需要坦诚考虑的权衡：

- **记忆库范围很重要。** 在互不相关的项目间共用一个记忆库会产生噪音。可按项目使用一个记忆库，或在适当时按团队使用一个记忆库。[记忆库参考](/developer/api/memory-banks)介绍了这些模式。
- **敏感背景。** 如果子代理会读取客户数据，请仔细考虑哪些内容会被存入。插件的存入行为可以配置；你可以让特定数据不进入记忆库。
- **单次任务。** 如果你几乎不用子代理，而且会话彼此独立，共享记忆的价值就较低。工作具有迭代性时，记忆才更有用。
- **最初几天。** 新记忆库是空的。经过几轮会话积累后，复合效应才会显现——通常在正常使用一周内开始体现。
- **你可能不需要共享记忆。** 如果你只使用一种类型的子代理，而且它可以独立工作，Claude Code 原生的 `memory` 字段及其随时间整理的各自 `MEMORY.md` 可能就够用了。当多个子代理需要共享理解、你需要学习型记忆而非基于文件的笔记，或相同知识需要同时呈现在编排器和子代理面前时，Hindsight 才是合适的选择。

这些因素并非不可接受的障碍，只是需要衡量的取舍。对于大多数经常运行多个子代理的 Claude Code 用户来说，合适的做法是为项目使用一个同时启用自动存入和自动召回的记忆库。

## 回顾 {#recap}

- Claude Code 子代理默认每次调用都会从头开始；只有最终消息会返回给编排器
- Claude Code 原生的 `memory` 字段会为子代理提供各自持久的 `MEMORY.md`，很有用，但每个子代理的目录都与其他子代理隔离
- 实验性的 `SendMessage` 恢复功能可以继续**一个**子代理的工作，却无法解决共享知识的问题
- 没有共享层时，同级子代理会彼此撞车，先后运行的子代理则会重新推导前序子代理已经发现的内容
- 一个共享的 Hindsight 记忆库能让所有子代理和编排器共享共同且不断增长的理解，而不是各自维护 N 个互相隔离的 `MEMORY.md` 文件
- hindsight-memory 插件使用 Claude Code 的会话钩子，让子代理无需单独接线也能访问共享记忆库
- 自我改进的行为（包括智能体更新自己的 `CLAUDE.md`）属于下一层能力；共享记忆是它建立其上的基础

子代理让 Claude Code 能够突破单个上下文窗口的限制。共享记忆库则让这些子代理不再彼此陌生。
