![智能体记忆整合难题](/img/blog/agent-memory-consolidation.webp)

智能体记忆整合是一个策略层，用来决定智能体的记忆保留什么、合并什么，以及驱逐什么。它通过四个杠杆发挥作用：重要性（什么内容会成为记忆）、合并（关于同一实体的事实如何统一成一条记录）、衰减（旧事实的置信度如何随时间降低），以及驱逐（何时将记忆彻底移出系统）。

什么都记住的智能体，等于什么有用的都记不住。投入生产六个月后，一个客服助手记录了每位用户说过的每句话。如今，即使客户六周前已经从 Postgres 迁移到 MySQL，它仍会信誓旦旦地告诉客户，他们还在用 Postgres。检索过程正常，出问题的是记忆本身。

<!-- truncate -->

这是整合问题，不是检索问题。每个长期运行的[智能体记忆](https://vectorize.io/what-is-agent-memory)系统最终都需要一套策略，来决定什么内容成为记忆、相关事实如何统一、旧事实的置信度如何随时间降低，以及何时将记忆彻底移出系统。大多数智能体记忆系统会明确说明检索架构，却对整合策略避而不谈。生产环境中的故障往往就源于这种沉默。

本文提出一个用于智能体记忆整合的四杠杆框架——重要性、合并、衰减、驱逐——并逐一介绍 [Mem0](https://mem0.ai)、[Zep](https://www.getzep.com)、[Letta](https://www.letta.com)、[LangChain](https://www.langchain.com) 和 Hindsight 如何处理（或跳过）每个杠杆。

## 为什么过时记忆会降低性能 {#why-stale-memory-degrades-performance}

有三种因素使整合成为任何长期运行的智能体记忆系统中最重要的工程决策。

**上下文成本。** 在 128K token 的上下文窗口和前沿模型定价下，每轮提示都塞入完整对话历史，其成本大约是检索精选子集的十倍。成本确实不低，但更大的问题是注意力被稀释。检索出的上下文里若包含关于同一实体的五条相互矛盾的事实，即使是强大的模型也无法据此给出连贯的答案。

**实体状态漂移。** 用户会变化，代码库也会变化。一月份还在使用 Postgres 的客户，三月份迁移到了 MySQL。如果两条事实在记忆中的权重相同，智能体就会选取本轮检索器评分较高的那条。正确做法是让新事实取代旧事实——通过合并，而不是删除。

**索引精度。** 随着索引增大，检索质量会下降。文档越多，争夺 top-k 名额的近似重复内容越多，过时事实的得分超过当前事实的机会也越大。要让检索精度保持稳定，需要做好整合——采用按新近度加权的评分、合并和重要性筛选。无需删除。

简要谈谈认知科学，不过是为了说明相反的一点。艾宾浩斯的记忆保持研究和互补学习系统假说（McClelland 等人，1995）指出，记忆消退是生物上的必需过程，而非设计目标。海马体储存情景记忆，新皮质整合模式；由于突触容量有限，大部分情景细节都会在此过程中被舍弃。智能体记忆系统不受突触容量限制。认知科学给我们的启示不是应该模仿生物遗忘，而是整合能让记忆变得有用。值得借鉴的是模式提取、实体消解和按新近度加权的检索，而不是容量限制。

## 记忆整合的四个杠杆 {#the-four-levers-of-memory-consolidation}

每套整合策略都通过四个杠杆发挥作用：

1. **重要性** — 哪些观测会成为记忆。
2. **合并** — 如何将相关事实合并为一条规范记录。
3. **衰减** — 记忆的置信度如何随时间降低。
4. **驱逐** — 何时将记忆彻底移出系统。

下文将依次讨论这四个杠杆，再用这个框架对照主要的智能体记忆系统。

## 重要性：什么内容会成为记忆 {#importance-what-becomes-a-memory}

在写入时控制智能体记忆质量，成本最低。凡是进入索引的内容，都必须一直参与检索、重排和相关性判断。进入门槛应该设高一些。

有两种主流做法：

**由 LLM 评定重要性。** 这种做法来自 Park 等人的 Generative Agents 论文（[arxiv 2304.03442](https://arxiv.org/abs/2304.03442)）：给每条观测评一个 1–10 的重要性分数，存下分数，之后在检索时将其纳入权重计算。这种方法可行，但每次写入都会增加一次模型调用，而且评分会随着模型版本变化而漂移。对于高吞吐量的智能体来说，成本很高。

**把事实提取作为重要性筛选。** 不给原始对话轮次打分，而是将对话拆解为原子事实，只存储提取后保留下来的事实。这是 Hindsight 的做法：写入管道会执行事实提取、实体消解和 Reflect（基于记忆推理），提取步骤本身就是重要性筛选器。闲聊填充语、重复问候和流程噪声不会成为记忆，因为它们不会被提取为事实。

这种权衡有两面。重要性筛选太严格会损害召回能力——有用的上下文在检索之前就消失了。筛选太宽松则会污染索引，把精度问题推到后续重排阶段。合适的设置取决于检索层能否在读取时恢复精度。如果有交叉编码器重排，就可以多保留一些内容；如果没有，写入时就必须筛得更严。

## 合并：避免对同一事物重复建档 {#merge-resolving-the-same-thing-twice}

同一实体可能有多种称呼。“Ben”“Ben Bartholomew”“用户”和“你”指的都是同一个人。“身份验证服务”“我们的登录系统”和“OAuth 微服务”指的都是同一个组件。如果记忆把它们存成不同记录，检索结果就会碎片化，智能体也会丢失跨会话的上下文。

有三个环节很重要：

**实体消解。** 将提及关联到规范实体 ID。这必须在写入时完成，而不是等到查询时再做。若在查询时消解，每次检索都得遍历各种表面形式，既昂贵又不可靠。

**事实去重。** 同一主张，不同说法。“Ben 在 Vectorize 工作”和“用户受雇于 Vectorize”应该合并为一条事实，而不是两条。

**冲突处理。** 同一实体，主张却相互矛盾。这是最棘手的情况。这里有三种合理策略，适用哪种取决于领域：

- **新近事实优先。** 新事实取代旧事实。适用于状态变化（“使用 Postgres” → “使用 MySQL”），但不适用于可能被错误重申的稳定属性。
- **来源优先。** 可信来源覆盖可信度较低的来源。适用于有明确来源信息的系统，但需要一套信任模型。
- **置信度优先。** 每条事实都带有置信度分数，取分数最高者。适用于提取结果带概率的情况，但需要做好校准，避免置信度失控攀升。

实践中，采用显式失效的新近事实优先策略是最站得住脚的默认做法。用户说“我已经迁移到 MySQL”时，系统写入新事实，并将旧事实标记为失效，而不是删除。旧状态仍可恢复以供审计；对检索来说，当前状态也一目了然。

## 衰减：置信度随时间变化 {#decay-confidence-over-time}

衰减是大多数智能体记忆系统跳过的杠杆。它对长期运行的智能体也最为重要，而且薄弱的整合策略往往会最先在这一环节暴露出来。

其基本想法很简单：不同事实的时效变化并不相同。用户今天早上表达的偏好，比一年前表达的相同偏好更可靠。迁移之前的配置声明可能仍留在索引中，但不应再被当作当前状态来排序。

常见的衰减曲线有三种：

- **线性衰减。** 置信度每单位时间固定下降一定数值。容易理解，但很少符合实际情况。
- **指数衰减。** 置信度在一定时间尺度内减半。这与艾宾浩斯曲线和大多数认知科学模型相符，是一个合理的默认选择。
- **阶跃式衰减。** 置信度保持不变，直到外部事件使事实失效，例如用户提出矛盾说法、系统事件发生，或出现新的冲突事实。

Zep 的 Graphiti 是最认真对待衰减的生产系统，这一点值得直说。Zep 知识图谱中的每条边都带有明确的时间元数据：`valid_at` 时间戳、事实被取代时的 `expired_at` 时间戳，以及事实被明确否定时的 `invalid_at` 标记。这样，Zep 就能回答大多数记忆系统难以应对的问题，例如：“客户去年 10 月搬家之前的地址是什么？”Hindsight 将时间筛选作为四种检索策略之一，因此可以处理“显示三月份的交互记录”这类请求，但 Zep 对事实有效时间段的处理更深入。如果智能体的主要工作是跟踪状态随时间的变化，这种能力很难匹敌。

衰减的权衡很直接：它以稳定的长期事实为代价换取新近性。衰减设得太强，会让系统忘记用户的姓名；设得太弱，又会让过时状态永久保留。没有放之四海而皆准的正确答案，具体取决于领域。

## 驱逐：何时移出记忆 {#eviction-when-memories-leave}

驱逐是最不可逆的杠杆；对大多数智能体记忆工作负载来说，它也是最不必要的。只要整合做得好——重要性筛选、合并和按新近度加权的检索——过时事实就能在不删除的情况下变得几乎无法检索。仍会用到驱逐的情况有三种：

**硬删除。** GDPR、用户要求删除、安全事件、PII 脱敏。这些要求不可妥协，应绕过其他所有策略。这是唯一真正必须驱逐记忆的情况。

**归档分层。** Letta 的做法是：核心记忆留在上下文中，归档记忆存放在向量存储里，智能体自己通过工具调用决定哪些内容在不同层之间移动。这更接近层级管理，而非真正删除——事实仍可检索，只是不在提示中。

**TTL 或 LRU 驱逐。** 通过基于时间或最近最少使用的策略限制索引大小。这类策略实现成本低，但在实践中会丢失信息，而且通常说明管道前面的整合做得不够。限制索引大小是在优化存储成本，并不会提升质量。

LangChain 的 `ConversationSummaryMemory` 推广了“先总结再丢弃”的做法。从技术上说，这是驱逐，但它属于有损压缩，而非整合。摘要会丢失检索所依赖的实体级细节。这种做法之所以存在，是因为底层记忆系统没有整合管道；它只是掩盖了这个缺失，并没有弥补它。

实用原则是：驱逐是合规工具，不是性能工具。对于 GDPR、用户要求删除和 PII 脱敏，驱逐不可妥协。至于其他问题——过时事实、噪声累积、索引增长——答案是在管道前段做好整合。

## 主要系统如何处理这四个杠杆 {#how-the-major-systems-handle-the-four-levers}

没有哪种智能体记忆系统能把这四个杠杆都处理好。下面是实际情况：

| 系统 | 重要性 | 合并 | 衰减 | 驱逐 |
| --- | --- | --- | --- | --- |
| **Mem0** | 写入时由 LLM 驱动 | 由 LLM 驱动的 ADD/UPDATE/DELETE | 原生不支持 | 显式 DELETE |
| **Zep / Graphiti** | 事实提取 | 感知实体 | 强：时间有效区间 | 显式失效 |
| **Letta** | 由智能体决定 | 由智能体决定 | 原生不支持 | 层级转换（核心/归档） |
| **LangChain Memory** | 窗口或摘要 | 无 | 无 | 窗口驱逐或总结后丢弃 |
| **Hindsight** | 事实提取筛选 | 由 LLM 驱动的整合 | 检索时提升新近事实的权重 | 原生不支持 |

Zep 的衰减机制最强。Letta 的分层设计最清晰。Mem0 的写入时操作 API 最成熟。LangChain 的记忆原语被弃用是有原因的——它们做的是压缩，不是整合。Hindsight 有意跳过对单条记忆的驱逐，其架构的前提是：良好的整合会让这类驱逐变得没有必要。通过 LLM 驱动的整合和按新近度加权的评分，过时事实会变得几乎无法检索；合规要求的删除则通过记忆库级清理来处理。上表中的“原生不支持”是设计选择，不是能力缺口。

## 如何评估整合策略 {#evaluating-a-consolidation-policy}

怎样判断智能体记忆整合策略是否正确？有三个重要信号。

**多会话推理准确率。** LongMemEval（[Wu 等人，arxiv 2410.10813](https://arxiv.org/abs/2410.10813)）测试的正是整合策略容易处理好或处理错的问题：跨会话跟踪事实、处理矛盾，以及对时间信息进行推理。在公开的 [Agent Memory Benchmark](https://agentmemorybenchmark.ai/) 排行榜跟踪的 LongMemEval-s 划分中，Hindsight 得分为 94.6%，SuperMemory 为 81.6%，Zep 为 71.2%，Mem0 为 67.6%。有几个较新的研究系统——Chronos 得分 95.6%、Mastra 得分 92.8%、Honcho 得分 90.4%——与 Hindsight 持平或高于它，而且排行榜上的分数分布很广。重点不在于某个系统今天排第几；排名靠后与靠前系统之间的差距反映了检索架构，也同样反映了整合策略。即使嵌入效果出色，如果系统把每轮对话原样存储，并且只通过向量相似度进行检索，得分也会很低。

**矛盾检测准确率。** 可以做一项合成测试：注入一个状态变化（“用户在 3 月 14 日从 Postgres 迁移到 MySQL”），一周后再询问智能体当前使用的数据库。正确答案是 MySQL。没有衰减机制或合并机制的系统会回答 Postgres，或者说“两者都可能，取决于查询”。

**每轮 token 成本。** 有效的整合策略会让每轮 token 用量在索引增长时保持平稳。如果 token 成本随会话数量线性增长，说明策略没有阻止噪声累积。

生产环境中应记录：每轮检索数量、每轮 token 用量、实体消解合并率、事实失效事件，以及检索缓存命中率。其中任何一项退化，都可能是智能体记忆整合出了问题，只是表现形式不同。

## 实用默认做法 {#practical-defaults}

设计或评估智能体记忆系统时，可以按以下顺序考虑：

1. **从事实级存储开始，而不是按对话轮次存储。** 在写入时提取事实，是影响最大的整合决策。后续工作都会因此变得容易。
2. **在写入时完成实体消解。** 查询时再消解会造成索引碎片化，并拖慢每次检索。写入时一次性付出成本即可。
3. **只有在存在值得衰减的时间性主张时，才添加衰减机制。** 如果智能体不跟踪状态变化，指数衰减只会丢弃稳定事实。
4. **只为满足合规要求而驱逐。** GDPR、用户要求删除和 PII 脱敏都要求硬驱逐。遇到性能问题——过时事实、索引噪声、token 成本上升——应在管道前段加强整合。

这些是 Hindsight 开箱即用的默认做法。第四条其实不算整合默认值，而是一条合规边界。如果供应商说不清系统如何处理前三个杠杆，你就找到了系统上线后会遇到的故障模式。

## 将四个杠杆作为检查清单 {#the-four-levers-as-a-checklist}

下次评估智能体记忆系统时，可以围绕其整合策略提出四个问题：

1. 什么内容会成为记忆，什么不会？
2. 系统如何判断两条事实说的是同一件事？
3. 旧事实的置信度如何降低？
4. 记忆何时、为何会离开系统？

如果其中任何一个问题的答案是“由 LLM 在写入时决定”或“我们没有对此建模”，你就找到了生产环境中的智能体会悄然出错的地方。检索分数是容易解决的部分。真正困难的是策略层：它决定了哪些内容应该留存下来，以便之后检索。

Hindsight 的架构——事实提取、LLM 驱动的整合、多策略检索、交叉编码器重排——建立在这样一个前提上：做好整合，就无需为了性能而驱逐记忆。智能体记忆系统不受生物限制，而这些限制使人类记忆消退成为必要。目标不是模仿这些限制，而是做好整合，让记忆中的内容始终是正确的检索对象。架构文档见 [hindsight.vectorize.io](/)，源代码已在 GitHub 上以 MIT 许可证发布。
