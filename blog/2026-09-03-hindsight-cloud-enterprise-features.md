大多数企业功能清单看起来都差不多：SSO、审计日志、角色、私有部署——每家都在提供，也都列在清单里，但这些项目并不能说明它们是否真的有效。

这里也列出这些功能，但每一项都会说明它能防止什么问题。能够被绕过的控制就不算控制；下面有几项功能，正是因为那些看似显而易见的实现方式并不可靠才存在。

## 单点登录 {#single-sign-on}

*企业版。*

SSO 的价值不在于登录更方便，而在于**离职撤权**。有人离开时，你希望只需在一个系统中撤销一次访问权限，而不是逐个供应商检查是否还留有未关闭的账号。

Hindsight Cloud 通过 **OIDC 或 SAML** 与你的身份提供商建立联合认证，因此 Okta、Entra、Google Workspace 以及任何符合标准的服务都可以使用。你需要声明自己的邮件域名并通过 DNS 验证。域名验证完成且配置生效后，任何人使用该域名的地址登录，都会自动转到你的 IdP。成员会在首次登录时创建，并在团队列表中标记为由 SSO 自动配置，因此无需预先创建账号，也无需维护和清理一份影子名单。

确保这项控制真正生效的关键是：**某个域名启用 SSO 后，该域名的密码登录和密码重置都会被拒绝。** 如果用户还能点击“忘记密码”绕过 IdP，SSO 就没有起到强制作用；这正是外挂式 SSO 常见的失效方式。这里会关闭密码登录路径，而不只是建议用户别用。

客户端密钥在静态存储时会加密，API 绝不会返回密钥本身，只会返回 `has_client_secret` 布尔值。

## 多因素认证 {#multi-factor-authentication}

*企业版。*

所有者可以要求整个组织启用 MFA。支持两种认证因素：**认证器应用**（TOTP，因此 1Password、Authy、Google Authenticator 或任何兼容 TOTP 的应用都可以使用）和**邮件一次性验证码**。

需要理解的区别是：强制执行时检查的是**当前会话是否通过了某个认证因素的验证**，而不只是账号是否登记过该因素。这是两种不同的保证。账号即使绑定了闲置的 TOTP 密钥，也只能满足较弱的要求。每个请求都会检查会话本身是否已通过 MFA 验证。

即使组织没有强制要求，个人也可以在账户安全页面自愿登记 MFA。

强制 MFA 和 SSO 是两种替代方案，而不是叠加使用的功能。如果登录经过 IdP，MFA 会按照你自己的策略在 IdP 中执行，因此同一个组织不会同时启用这两种方式。

## 空闲会话超时 {#idle-session-timeout}

*所有方案。* 闲置 30 分钟后，会话结束，用户必须重新登录。现在所有组织都会启用这项功能，不再仅限于企业版。

这项控制不起眼，却是清单中唯一防范完全不涉及技术的威胁的功能：一台没有锁屏的笔记本电脑。

## 基于角色的访问控制 {#role-based-access}

*所有方案。* 角色刻意只设三个：

| 角色 | 权限 |
|---|---|
| **所有者（Owner）** | 完整访问权限，包括删除组织 |
| **管理员（Admin）** | 管理成员和 API 密钥 |
| **成员（Member）** | 只读访问权限，并可使用 API 密钥 |

权限边界就在这里：成员可以*使用* API 密钥，但不能*管理*密钥。这种区分在实际中很重要：工程师需要基于记忆进行开发，但不应有权创建在其访问权限终止后仍然有效的凭据。

## API 密钥控制 {#api-key-controls}

*所有方案。* 应用实际通过密钥访问记忆，因此密钥泄露才是现实中更可能发生的安全事件，而不是控制台密码被盗。

每个密钥都可以设置**有效期**——指定小时数或天数，也可以永不过期；还可以**限定到特定记忆库**，使其只能访问所需的记忆，而不是组织拥有的全部记忆库。密钥在创建时**只显示一次**。

限定范围是最容易被忽略的一项，也是限制事故影响范围的关键。未限定范围的密钥一旦泄露，就会暴露你拥有的所有记忆库；限定到一个记忆库的密钥泄露，则只会暴露这一个记忆库。

## 限定范围的子密钥 {#scoped-child-keys}

*所有方案。*

这项功能会改变你构建多租户产品的方式，值得多说明几句。

可以授予某个密钥**以编程方式创建、列出和撤销限定记忆库范围的子密钥**的权限。你的后端只需持有一个父密钥，然后为每位客户签发一个子密钥；每个子密钥只能访问该客户的记忆库。

看看另一种做法：如果没有这项功能，多租户应用就只能持有一个范围很广的凭据，并在自己的代码中实现租户隔离——每条访问记忆的路径都要写上 `WHERE tenant_id = ?`。只要有一条路径漏掉这项筛选，就可能把一位客户的记忆提供给另一位客户。

签发限定范围的密钥，会把隔离边界从代码移到凭据中。只能访问一个记忆库的子密钥，无论调用代码出了什么差错，都无法访问其他记忆库。隔离因此成为令牌本身的属性，而不再是开发者必须时刻记得正确执行的要求。

撤销也遵循同样的边界：撤销一个子密钥，就会终止对应租户的访问，不会影响其他内容。

## 审计日志 {#audit-logging}

*企业版。*

你可以查询记忆库中发生的操作记录，包括 Retain（存入）、Recall（召回）、Reflect（反思）及其他受审计的操作；还可以按操作和严重程度筛选，并查看随时间变化的请求量图表。

审计日志是**按记忆库选择启用**的，而不是在整个部署中统一启用。乍看像是限制，实际并非如此。大规模启用审计会产生海量数据，其中大多数涉及的记忆库永远不会有人调查。按库启用后，存有受监管数据或客户数据的记忆库可以保留完整记录，而某人临时创建来测试提示词的记忆库则不会产生大量无关记录。

## 记忆防护 {#memory-defense}

*所有方案。*

记忆防护会在 Retain 时检查内容，并在**写入任何内容之前**决定如何处理。

时机就是这项设计的全部。等到 Recall 时再过滤已经太晚：那时内容已经存储、生成嵌入并编入索引，任何直接访问数据库或 API 的主体都能读取它，不受 Recall 最终返回内容的影响。

每个记忆库都有一个总开关、一个用于未匹配任何具体规则内容的默认操作，以及**密钥脱敏**功能。检测到的 API 密钥和令牌会被替换为 `[REDACTED:github_token]` 这样的标记，因此周边上下文仍然保留，凭据则不会留下。

脱敏而不是拒绝内容这一点，比乍看起来更重要。这样仍能保留有用的记忆。某段对话即使包含令牌，也仍会作为记忆存入，只是不再包含令牌本身。

## 企业版记忆防护 {#memory-defense-enterprise}

*企业版。*

此外还提供多个检测器，每个检测器都可以单独启用和调整：

| 检测器 | 检测内容 |
|---|---|
| **提示注入防护** | 试图在记忆中植入指令的内容，例如“忽略之前的指令”或覆盖系统指令 |
| **大小异常检测** | 过大的载荷；默认阈值为 64 KB |
| **受保护文档标签** | 重新提交时会移除或替换受保护标签的内容 |
| **广泛模式库** | 在基础检测集之外，额外提供 220 多种敏感信息检测模式 |
| **Base64 解码** | 解码 Base64 内容并重新扫描，捕获简单模式匹配遗漏的内容 |
| **LLM 筛查** | 任何模式都无法匹配的自然语言泄露，例如“密码是……” |

每个检测器都有各自的**操作**和**最低严重程度**。这让功能能够在实际生产环境中持续运行。只能阻止内容的扫描器一旦误拒了合法内容，就可能马上被关闭。高置信度时阻止、低置信度时仅标记，正是持续启用的控制与被关掉的控制之间的区别。

功能授权在**服务端**执行，而不只是由控制台界面控制，因此无法通过 API 设置界面本身不允许的策略。

为什么选择这些检测器？记忆具有持久性，并且按语义编入索引，这改变了错误写入的代价。进入聊天窗口的注入只会影响一次回复；进入记忆的注入则会在未来的轮次和会话中持续被召回，只要它仍然匹配。密钥一旦存入，即使之后已经轮换，仍然可以被检索到。过大的载荷会挤满候选集合，把相关记忆排挤出结果。这些不是通用内容过滤器，而是针对系统会记住内容所特有的三类问题。

## Webhook {#webhooks}

*企业版。* 记忆库事件发生时立即推送到你自己的系统，而不必轮询等待。

- Retain 和整合完成后发送**实时事件**。
- 使用 **HMAC 签名的载荷**，让你的端点可以验证投递确实来自我们。
- 采用**异步投递和重试**，并保留每次投递的历史记录，供你查看处理情况。
- 提供**记忆防护违规告警**。这项能力尤其重要：密钥被阻止或注入被捕获时，可以直接向 SIEM 或事件处理工具发送事件，而不是让告警留在没人查看的日志中。

最后这一点让记忆防护从过滤器变成安全团队可以实际监控的功能。

## 自带云账户 {#bring-your-own-cloud}

*企业版。*

有些要求无法靠任何应用层控制来满足，因为约束不是“谁可以读取这些数据”，而是“这些数据不能离开我们的账户”。

针对这种情况，Hindsight 可以部署**到你自己的云账户中**，支持 AWS、GCP 或 Azure。

同时提供**私有连接**。你的应用与 Hindsight 之间的流量会留在云服务提供商的私有网络中，而不会经过公共互联网；具体使用哪种私有端点机制，取决于相应的云服务提供商。

**也支持本地部署。** 如果要求数据不能离开的是你自己的硬件，而不仅仅是云账户，企业版同样支持这种部署方式。

## 常见问题 {#frequently-asked}

**Hindsight Cloud 支持 SAML，还是只支持 OIDC？**
两者都支持。每份配置只能选择其中一种。

**不使用 SSO，也可以要求启用 MFA 吗？**
可以。组织无需配置身份提供商，也可以要求成员的 Hindsight 账号使用 MFA。

**有人离职时，如何切断其访问权限？**
使用 SSO 时，在 IdP 中撤销该用户，就会关闭其登录途径；不会留下仍可使用的 Hindsight 密码。对于程序化访问，应撤销相应密钥。如果应用签发了限定范围的子密钥，撤销其中一个就会终止对应范围的访问，而不影响其他范围。

**记忆防护是在 Retain 时运行，还是在 Recall 时运行？**
在 Retain 时运行，且在内容写入之前完成。

**能通过 API 绕过控制台上的功能授权吗？**
不能。授权在服务端的写入路径上执行。

**我们完全不能把数据放进共享环境。这种部署方式受支持吗？**
支持。可以将 Hindsight 部署到你自己的 AWS、GCP 或 Azure 账户，并使用私有连接，确保流量不会经过公共互联网；如果数据必须留在你自己的硬件上，也可以选择本地部署。

**我们可以接收推送事件，而不必轮询吗？**
可以，通过 Webhook 接收。Retain 和整合完成后会触发事件，载荷使用 HMAC 签名，投递采用异步方式并支持重试，同时保留每次投递的历史记录；记忆防护违规也可以路由到你的 SIEM。
