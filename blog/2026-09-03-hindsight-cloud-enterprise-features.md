大多数企业功能清单难以区分：SSO、审计日志、角色、私有部署，人人都提供，也都列出来，但清单不能说明控制是否真正有效。

因此这里仍是一份清单，不过每项都解释防止了什么。能够绕过的控制不算控制，以下一些功能正是因为直观实现不够可靠而设计。

## 单点登录 {#single-sign-on}

*企业版。*

SSO 重要的原因不只是登录方便，而是**离职撤权**。员工离开时，应该只需在一个系统撤销一次，而不必检查每个供应商中遗留的账号。

Hindsight Cloud 通过 **OIDC 或 SAML** 联合你的身份提供商，支持 Okta、Entra、Google Workspace 和其他标准兼容服务。声明邮件域名并通过 DNS 验证，配置生效后该域名邮箱的登录自动进入 IdP。首次登录自动创建成员，团队列表标注为 SSO 创建，无需维护提前建账号流程或清理影子名单。

真正保证控制有效的是：**域名启用 SSO 后，拒绝该域名的密码登录和密码重置。** 能点击“忘记密码”绕过 IdP，就没有真正执行控制，这也是外挂式 SSO 常见的失败方式。这里会关闭密码路径，而非仅不建议使用。

客户端密钥静态加密，API 从不返回密钥，只返回 `has_client_secret` 布尔值。

## 多因素认证 {#multi-factor-authentication}

*企业版。*

所有者可要求全组织使用 MFA，支持两种认证因素：**认证器应用**（TOTP，例如 1Password、Authy、Google Authenticator 等）和**邮件一次性验证码**。

关键区别是：强制执行检查**当前会话是否经过认证因素验证**，而非仅检查账号是否注册因素。闲置 TOTP 密钥只能满足较弱保证；这里每次请求都要求会话已通过 MFA。

组织未要求时，个人也可从账户安全页面自愿注册。

强制 MFA 与 SSO 是替代关系，不是叠加关系。登录经过 IdP 时，由你的策略在 IdP 中执行 MFA，因此同一组织不会同时启用两者。

## 空闲会话超时 {#idle-session-timeout}

*所有方案。* 无操作 30 分钟后结束会话，需要重新登录。现在对所有组织启用，不仅限企业版。

它不起眼，却是清单中唯一防止非技术威胁的控制：一台没锁屏的笔记本。

## 角色访问控制 {#role-based-access}

*所有方案。* 有意保持为三个角色：

| 角色 | 权限 |
|---|---|
| **所有者（Owner）** | 完整权限，包括删除组织 |
| **管理员（Admin）** | 管理成员和 API 密钥 |
| **成员（Member）** | 仅查看，并可使用 API 密钥 |

成员可*使用*密钥，但不能*管理*密钥。这是实际关键：工程师需要基于记忆开发，却不应创建可能在其访问权限终止后仍有效的凭据。

## API 密钥控制 {#api-key-controls}

*所有方案。* 应用通过密钥访问记忆，因此密钥泄露比控制台密码被盗更接近实际风险。

每个密钥可设**有效期**，按小时、天数或永不过期；也可**限定到指定记忆库**，只访问所需记忆，而非组织全部内容。密钥只在创建时**显示一次**。

范围限制经常被忽略，却决定事故影响：无限定密钥泄露暴露全部记忆库，限定单库的密钥只暴露一个。

## 限定范围的子密钥 {#scoped-child-keys}

*所有方案。*

这项能力会改变多租户产品的构建方式，值得深入解释。

可授予密钥**通过程序创建、列出和撤销限定记忆库范围的子密钥**的权限。后端持有一个父密钥，为每位客户创建只访问其记忆库的子密钥。

否则，多租户应用持有广泛权限的凭据，在每条访问记忆的路径中靠 `WHERE tenant_id = ?` 实现隔离。只要一条路径忘记筛选，就可能将一位客户的记忆提供给另一位。

创建限定范围的密钥，将隔离边界从代码移到凭据。只能查看单库的子密钥，无论调用代码犯什么错都无法访问其他库。隔离成为令牌属性，而非必须记得正确实现的事。

撤销也一样：撤销一个子密钥，只终止对应租户访问，不影响其他租户。

## 审计日志 {#audit-logging}

*企业版。*

提供记忆库中 retain、recall、reflect 等审计操作的可查询记录，支持按操作、严重程度筛选，并绘制请求量随时间变化的图表。

日志**按记忆库选择启用**，不是全部署统一启用。大规模审计会产生海量数据，多数记忆库无人需要调查。按库开启，保存监管或客户数据的库就能有完整记录，而临时测试提示词的库不会用噪声淹没它。

## 记忆防护 {#memory-defense}

*所有方案。*

记忆防护在 retain 时检查内容，**写入任何内容前**决定处理方式。

时机就是设计核心。召回时筛选已太晚：内容已被存储、嵌入和索引，拥有数据库或 API 直接访问权限的调用方仍能读取，无论 recall 返回什么。

每个记忆库都有总开关、未匹配规则时的默认动作，以及**密钥脱敏**：将 API 密钥和令牌替换为 `[REDACTED:github_token]` 等标记，保留周边上下文而不保留凭据。

脱敏而非拒绝，使记忆仍有用。偶然包含令牌的对话依然可存储，只是不携带令牌。

## 企业版记忆防护 {#memory-defense-enterprise}

*企业版。*

额外检测器可分别启用和调整：

| 检测器 | 检测内容 |
|---|---|
| **提示注入防护** | 向记忆植入“忽略此前指令”或覆盖系统指令等尝试 |
| **大小异常** | 超大请求体，默认阈值 64 KB |
| **受保护文档标签** | 重新提交时剥离或替换受保护标签 |
| **广泛模式库** | 在基础模式之外增加 220 多种密钥检测模式 |
| **Base64 解码** | 解码 Base64 并重新扫描，捕获普通模式匹配遗漏的内容 |
| **LLM 筛查** | 模式找不到的自然语言泄露，例如“密码是……” |

每个检测器都有独立**动作**和**最低严重程度**，让功能能适应生产环境。只能阻止的扫描器一旦误拒正常内容，很快就会被关闭。高置信度阻止、低置信度仅标记，决定控制能否持续开启。

授权在**服务端**执行，不只是控制台展示，不能通过 API 设置界面不允许的策略。

为何选这些检测器：记忆持久且按语义索引，错误写入的成本因此改变。进入聊天窗口的注入只影响一次回复，进入记忆的注入则可能在未来轮次和会话中持续召回。密钥存储一次，即使轮换后仍可检索；超大内容会挤占候选池，把相关记忆挤出结果。它们不是通用内容过滤器，而是针对“系统会记住”带来的三类问题。

## Webhook {#webhooks}

*企业版。* 事件发生时立即将记忆库事件推送到你的系统，无需轮询。

- 存储和整合完成的**实时事件**。
- **HMAC 签名请求体**，接收端可验证确实由我们发送。
- **异步投递与重试**，并保留每次投递历史。
- **记忆防护违规告警**：被阻止的密钥或捕获的注入可直接发送到 SIEM 或事件处理工具，而非停留在无人读取的日志。

最后一点让安全团队真正可以监控记忆防护。

## 自带云账户 {#bring-your-own-cloud}

*企业版。*

有些要求无法通过应用级控制满足，因为限制是“数据不能离开我们的账户”，而非“谁能读取”。

为此，Hindsight 可以部署到 AWS、GCP 或 Azure 上**你自己的云账户**。

同时提供**私有连接**。应用与 Hindsight 的流量使用云厂商的私有端点机制，保留在私有网络，不经过公网。

也支持**本地部署**。若数据不仅不能离开自有云账户，还必须留在自己的硬件上，企业版也支持。

## 常见问题 {#frequently-asked}

**Hindsight Cloud 支持 SAML，还是只有 OIDC？**
两者都支持，每份配置选择其中一种。

**不使用 SSO，可以强制 MFA 吗？**
可以，无需配置身份提供商即可要求 Hindsight 账号使用 MFA。

**有人离职时如何终止访问？**
使用 SSO 时，在 IdP 撤销用户即可关闭登录路径，不会留下可用的 Hindsight 独立密码。程序访问应撤销密钥；应用使用限定范围的子密钥时，撤销一个即可终止该范围访问，不影响其他范围。

**记忆防护在存储还是召回时运行？**
在存储时，写入内容之前。

**可以通过 API 绕过控制台授权吗？**
不能，授权在服务端写入路径执行。

**完全不能将数据放在共享环境，支持吗？**
支持。可部署到自有 AWS、GCP 或 Azure 账户并使用不经过公网的私有连接；若数据必须留在自有硬件上，则可本地部署。

**可以推送事件，而非轮询吗？**
可以，通过 webhook。存储和整合完成后触发事件，请求体使用 HMAC 签名，异步投递、支持重试并保留历史，记忆防护违规可路由到 SIEM。
