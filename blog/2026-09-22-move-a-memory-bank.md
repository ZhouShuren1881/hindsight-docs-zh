过去，选择记忆库 ID 就像迈过一道单向门：你本该选择 `support-prod`，却选了 `support`；或者本想按工作区而不是按客户划分记忆库。唯一的补救办法，就是通过一条流水线重新摄取所有内容，白白花掉真金白银的 LLM 费用。

Hindsight 0.10.1 让记忆库可以迁移：你可以复制记忆库、在实例之间移动它，或原地重命名，而且完全不必重新提取任何事实。

<!-- truncate -->

## 要点 {#tldr}

- **克隆**：通过一次 API 调用将记忆库克隆到新的 ID。操作在后台运行，不涉及 LLM。
- **导出和导入**：将整个记忆库导出为 ZIP 归档并重新导入，同时明确指定范围：数据、记忆库配置和历史记录。
- **重命名**：使用 `hindsight-admin` 原地重命名记忆库，同时将存储的文件移至新前缀。
- **派生内容不会随行。** 嵌入、数据库 ID 和实体图会在目标位置重建，因此迁移后的记忆库会原生适配其落脚环境。
- **有三处容易踩坑**：克隆默认继承来源记忆库的 Webhook；恢复操作拒绝覆盖已有记忆库；重命名不会处理由外部存储管理的记忆库。

## 三种迁移记忆库的方式 {#three-ways-to-move-a-bank}

**克隆**是只需一次调用的选项。`POST /v1/default/banks/{bank_id}/clone?target_bank_id=...` 会返回 `202` 和一个操作 ID，你可以轮询该 ID 查看进度。底层会在同一进程中依次执行导出和导入，归档不会接触磁盘：正如代码注释所说，把它存进文件存储“只会多一次往返，还会多出一个需要清理的对象”。读取在一个事务中完成，因此你得到的是某一时刻的副本，同时来源记忆库仍可继续写入。如果不这样做，正如注释所说，克隆出来的就会是“把当时正在写入的各种内容胡乱混在一起”。

**导出和导入**适用于跨实例迁移。`POST .../transfer/export` 会返回一个操作，其结果中包含下载 URL；`POST .../transfer/import` 则通过 multipart 接收 ZIP。这是更改已填充的记忆库中无法原地修改的配置的受支持方式，例如嵌入模型、向量扩展或全文检索后端。

**重命名**是运维工具，不是 API。`hindsight-admin rename-bank --from old --to new` 会在单个事务中移动所有 `bank_id` 对应的行，然后为记忆库存储文件换用新前缀，并发重建其向量索引。它还支持 `--dry-run`。

## 哪些内容会随行 {#what-travels}

范围由三个布尔值控制，而不是一个枚举；每个值的含义如下：

| 标志 | 默认值 | 携带内容 |
|---|---|---|
| `include_data` | 开启 | 文档、分块、事实、整合后的观测、附件及其字节内容、人工维护归档、操作日志、**心智模型和知识页目录树** |
| `include_bank_config` | 开启 | 记忆库记录（配置覆盖项、名称、任务说明、性格倾向）、强制指令、**Webhook** |
| `include_history` | 关闭 | 审计日志和 LLM 请求记录 |

让人意外的是，心智模型和知识页归在*数据*而不是配置中。代码解释了原因：

> 心智模型和知识页归在 `data` 而不是 `bank_config` 中，因为它们是对记忆库事实的解读，而不是设置：心智模型的 `based_on` 证据通过 ID 引用记忆单元；如果不连同这些单元一起携带，恢复后的综合生成结果就会失去其依据，无法解析到任何内容。

开发过程中，这一归类曾被反过来处理——第一个版本把它们放在配置中——这说明两者很容易混淆。实际结果是：`include_data=false` 且 `include_bank_config=true` 时，你会得到记忆库设置、强制指令和 Webhook，但不会得到任何心智模型。

## 派生内容不会随行 {#nothing-derived-travels}

这正是整个机制能够奏效的关键。

嵌入绝不会随归档携带。数据库 ID、实体表、共现图和记忆关联也不会。归档保存的是来源材料：文档、文档分块、以文本形式保存的提取事实，以及以规范名称而非 ID 命名的实体。导入器会重新处理这些材料：使用**目标**记忆库的模型为每条事实重新生成嵌入，在目标记忆库中重新解析实体，并重建图。

整个过程不会调用 LLM。导入器对自身的描述是，它会“准确执行 retain 在 LLM 提取之后所执行的步骤”。因此，迁移记忆库消耗的是嵌入计算，而不是 token；副本会原生适配目标环境，而不会携带目标可能根本无法运行的模型所生成的向量。

这也解释了为什么官方文档建议通过导出和导入来更换嵌入模型：已填满内容的记忆库无法原地更换模型，但你可以将其迁移到一个新记忆库。

有一点需要注意：文档会保留原 ID，事实、观测和实体则会获得新 ID。心智模型和知识页会保留原 ID，因此知识页目录树仍可正常解析。如果你在自己的数据库中保存了 Hindsight 事实 ID，这些 ID 将无法在迁移后继续使用。

## 容易踩坑的地方 {#where-it-will-bite-you}

如果你要对重要数据执行这些操作，事先有四点需要了解。

**克隆会继承来源记忆库的 Webhook。** `include_bank_config` 默认开启，而 Webhook 属于记忆库配置，因此默认克隆的记忆库会调用来源记忆库配置的 Webhook 端点。API 文档明确指出：如果端点对应的是每个记忆库各自的消费者，应传入 `include_bank_config=false`，或在副本中删除这些 Webhook。克隆生产环境来搭建调试沙箱，结果却看到沙箱触发了生产环境的 Webhook，会让人头疼一下午。

**恢复操作拒绝已有目标。** 克隆和恢复写入的目标记忆库都必须尚不存在；如果目标已存在，错误信息会提示先删除它，或改用其他 ID。这意味着你无法定期循环执行“将开发环境提升为生产环境”：你必须先删除再恢复，或每次都使用新的记忆库 ID 并重新指向客户端。虽然有合并模式，但它按文档粒度应用冲突策略，而且不会对事实去重，因此重新导入同一个归档可能留下基于相同事实的重叠观测。

**重命名的限制比看上去多。** 它仅支持 PostgreSQL。当记忆库有等待处理或正在处理的操作时，重命名会被拒绝。对于记忆存储在 SQL 之外的由外部存储管理的记忆库，重命名也会直接被拒绝；要更改这类记忆库的 ID，只能克隆到新 ID 后删除旧库。你还必须先停止客户端：仍在使用旧 ID 的客户端会收到 404；如果客户端会按需创建记忆库，它还可能悄悄以旧名称创建一个全新的空库。

**缩小范围会静默失败。** 导入时，你请求的范围会与归档实际包含的内容取交集。请求归档未包含的内容不会报错，而是什么也不做。请检查清单，不要想当然地认为设置的标志已经生效。

## 如果要升级带有附件的由外部存储管理的记忆库 {#if-you-upgrade-with-attachments-in-a-store-owned-bank}

0.10.1 提供了一项迁移：附件现在归属于其文档，取代了单独的 `document_attachments` 表。在常规部署中，这项操作开销很小，因为它不会移动任何字节；迁移后的记录仍使用原来的存储键。

但由外部存储管理的记忆库写入附件记录时，并不会写入回填过程要读取的文档附件记录，因此这些附件无法找到所属文档，**迁移会删除它们**。相应的二进制对象仍会留在文件存储中，直到记忆库被删除。如果你的部署使用外部存储且包含附件，请在升级之前了解这一点，不要等升级之后才发现。

## 模板是另一种功能 {#templates-are-a-different-feature}

Hindsight 自 0.5.0 起就支持[记忆库模板](https://hindsight.vectorize.io/blog/2026/04/10/templates-hub-hindsight-050)，很容易让人误以为这次的迁移功能与它是同一回事。其实并不是。

模板是可手工编辑的 JSON 清单，包含配置覆盖项、强制指令和心智模型*定义*——也就是模型要回答的问题，而不是答案内容。将模板导入一个新记忆库时，系统会运行 reflect 来重新生成这些模型，这会调用 LLM。模板采用插入或更新方式，因此也可以应用到已有记忆库。

迁移则是一个不透明的归档，其中包含完整记忆库及其全部内容；整个过程不调用 LLM，且目标记忆库必须尚不存在。

模板迁移的是配方，迁移功能迁移的是记忆库本身。

## 可用入口 {#where-this-is-available}

克隆、导出和导入功能可通过 HTTP API 以及 Python、TypeScript 和 Go 客户端使用。控制台的 Actions 菜单中提供克隆功能。Hindsight Cloud 已开放这些端点。

重命名只能通过 `hindsight-admin` 执行：没有对应的 API、MCP 工具或 SDK 方法。管理 CLI 也提供 `export-bank` 和 `import-bank`，但只有 HTTP 接口支持这三种范围选项。

如果你打算编写脚本，需要注意：归档大小没有上限，任务也没有超时限制；克隆会在进程内存中保存载荷和归档。操作结果会报告归档的字节大小，这是你能获得的唯一大小信号。
