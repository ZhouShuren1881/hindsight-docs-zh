![查看某项操作将发送的确切提示词，并按生成提示词的设置拆分](/img/blog/prompt-preview.png)

你为记忆库写下一条任务说明，比如“关注计费决策，以及由谁批准”。保存后，提取效果可能会变好，也可能不会。

那么，这句话到底去了哪里？

如果你猜它在系统提示词里，那在使用它的三种操作中，你有两种猜错了。

<!-- truncate -->

## 要点 {#tldr}

- Retain（存入）或整合操作的任务说明位于**用户**消息中，而非系统提示词。Reflect（反思）的任务说明位于系统提示词中，会替换智能体的角色行，而不是追加在后。
- `POST /banks/{id}/prompts/preview` 返回 Retain、整合或 Reflect 将发送的确切消息，不调用 LLM，也不写入数据。
- 活动块按字节拼接后就是实际提示词；有一项测试会将这个结果与实际构建器的输出锁定为一致。
- 你关闭的设置会作为非活动块返回，位置与启用时本该出现的位置相同。
- 该端点有意拒绝接收你的示例文本或候选任务说明。
- 此功能随 v0.10.0 发布，Hindsight Cloud 和自托管部署均可使用。

## 为什么任务说明放到了用户消息中 {#why-the-mission-moved}

Retain 和整合所用的系统前缀有意不依赖特定记忆库。服务器上的每个记忆库都会发送同一个前缀，因此模型供应商侧的一份提示缓存就能供它们共用。如果把各记忆库自己的任务说明写进前缀，每个记忆库就会各有一份缓存；摄取量大时，这会实实在在地增加费用。

因此，任务说明改放在用户消息中。Retain 使用由代码围栏括起的 `FOCUS` 前言；整合使用 `## MISSION` 标题。Reflect 是个例外，而且带来另一种意外：`reflect_mission` 不会追加任何内容，而是**替换角色行**。写上“关注计费问题”，就会悄然删掉“你是一名通过检索记忆进行推理并回答问题的反思智能体”这条角色说明。

配置页面看不出这些。你设置了一个字符串，它最终出现在哪里，取决于代码。

预览正好填补了这个空白。新增此功能的提交直接说明了这一点：只有看到任务说明进入了哪条提示词，它才有意义；而在此之前，想弄清楚就得追踪 Python 常量和格式化调用。

## 它会返回什么 {#what-it-returns}

`POST /v1/default/banks/{bank_id}/prompts/preview` 接收一个操作，按发送顺序返回消息，并将每条消息拆分成多个块：

```json
{
  "text": "FOCUS — What to retain for this bank...",
  "source": "config",
  "field": "retain_mission",
  "active": true,
  "kind": "text",
  "editable": true
}
```

每个块都会说明其来源：`source` 是 `config` 或 `builtin`，`field` 指明对应的设置，`editable` 则说明它是可以修改的记忆库级设置，还是服务端级设置；如果界面提供修改后一类设置的入口，结果只会是一个 400 错误。

代码注释强调的核心保证是：*活动块恰好划分了提示词*。拼接所有活动块，就会得到模型将收到的字节。有一项测试会并排生成预览和实际提取提示词，并断言两者完全一致，因此二者不会逐渐偏离。

即使其中一条消息为空，两条消息也总会一并返回，因为只显示系统提示词会让人误以为配置的任务说明不存在。正如模块文档字符串所说，这恰好把事实完全弄反了。

## 看得见的缺失项 {#absence-you-can-see}

我觉得设计尤其周到的地方，是关闭某项设置后的处理方式。

它仍会返回：`active: false`、空文本，并放在启用设置后本该出现的位置。空文本无法通过匹配提示词来定位，因此渲染器会把它锚定在最后一个匹配片段上。如果关闭的设置漂到响应末尾，就无法说明它原本的位置。

源码对此的解释是：

> 你还没写下的那条任务说明，正是你来到这里准备写的内容；它没有文本可供放在旁边。

还有两项细化可以避免产生噪声。如果插槽根本不存在，就不会生成对应的非活动块：例如，非 `custom` 模式不会渲染 `retain_custom_instructions`，因为构建器在该模式下根本不会读取它。整合任务说明也永远不会处于非活动状态，因为不设置它只意味着由内置默认值填入该插槽。

## 它不会接收你的示例文本 {#it-wont-take-your-sample-text}

这是多数人可能会反对的设计决定。请求体只有两个字段：要预览哪种操作，以及可选的 Retain 策略。你不能传入候选任务说明，也不能传入自己的示例文本。

文档字符串不只是记录设计，还为它辩护：

> 操作就是整个请求：所有影响提示词的内容都来自记忆库，因此有意不提供任何覆盖项。预览回答的是“这个记忆库会发送什么”；允许调用方传入自己的任务说明或示例文本，只会把问题移到记忆库无法回答的地方。要尝试候选值，就先保存，再查看。

因此，每个块都带有 `editable`。工作流程不是“模拟一次修改”，而是“修改，再查看”。控制平面构建的正是这个循环：直接编辑某个块对应的设置，保存，然后重新获取预览。

如果你想看*返回什么*，那要用另一个端点。Retain 测试器会执行一次试运行提取，实际调用 LLM，但不保存任何内容；与预览不同，它还允许一小组白名单覆盖项。一个免费展示会发送什么，另一个则让你付出一次调用的费用来查看结果。

## 只有查看才能知道的细节 {#things-you-can-only-learn-by-looking}

预览之所以有用，是因为提示词组装存在一些容易出错的边界情况。下面每一种都是真实行为，却都无法从配置页面看出来。

| 设置 | 实际行为 |
|---|---|
| 策略名称拼错 | 记录警告，而非错误。策略中的未知字段会被静默忽略。|
| 在 `custom` 以外的模式中设置 `retain_custom_instructions` | 从不读取该设置，因此没有效果。|
| 使用 `custom` 模式，但指令为空 | 静默回退到 `concise`。|
| 设置 `entities_allow_free_form`，却未设置 `entity_labels` | 没有效果。它只是标签区中的一句说明，而只有配置了标签时才会有这个区块。|
| `llm_output_language` | 替换默认语言规则，而不是在其上追加，因为两条规则彼此矛盾。|
| `chunks` 提取模式 | 完全不发送提示词。任务说明、标签和自定义指令都会变得不起作用。|

最让我确信这个端点非有不可的，是该功能自身的提交记录。试运行和预览都曾直接解析配置，而没有通过 Retain 解析器，因此带默认策略的记忆库会在一套真实 Retain 永远不会采用的设置下生成预览。这个原本用来展示真相的工具，一度也犯了同样的错。现在已经为此添加了回归测试。

## 它的成本和影响范围 {#what-it-costs-and-what-it-touches}

不花费任何调用，也不触及任何状态。

渲染器不会接触 LLM 客户端、队列或锁；如果记忆库不存在，也不会创建它；不会写入操作记录，路由上也没有审计装饰器。有一项测试断言，预览前后记忆单元数量保持不变。

有一项权限细节值得了解：预览使用的权限与读取记忆库配置相同，而不是普通读取权限。把设置渲染成提示词文本，是另一种披露同样信息的途径，因此扩展若拒绝读取配置，也会拒绝预览。另有专门测试确保响应不会泄露任何模型供应商凭据，因为渲染器处理的是完全解析后的内部配置。

## 预览没有展示的内容 {#what-it-doesnt-show}

在把预览当成全部实情之前，有几点值得了解。

- **有些运行时区块会被省略。** Retain 预览会渲染文本分块、事件日期和上下文，却不显示真实 Retain 操作包含的元数据、叙述者或附件指令。对于大量使用图片的记忆库，这意味着你看不到一大段文本。
- **Reflect 按最大配置渲染。** 它会包含所有可用工具和无标签强制指令，也不会提供请求级的预算指导。实际 Reflect 调用如果使用不同选项，发送的内容也会不同。
- **整合操作的容量说明永远不会出现。**
- **没有 CLI，也没有 MCP。** 这是一个 HTTP 端点，并提供生成的客户端方法。CLI 项目的豁免说明指出，多块载荷是面向界面的结构，并不适合作为 CLI 输出。
- **块归属尽力而为。** 如果构建器改写了某个片段，该块就会被跳过，其文本仍留在周围的内置块中。即使标签不够准确，拼接保证依然成立，因此提示词始终正确。

## 常见问题 {#faq}

**预览会消耗 token 吗？**
不会。它从不调用模型。控制平面测试器中的试运行提取会调用模型，这部分也明确标为需要付费的部分。

**能预览尚未保存的修改吗？**
不能。保存后再查看。响应会标明哪些块可以编辑，方便你了解哪些内容可以修改。

**系统消息看起来是空的，为什么还会返回两条消息？**
因为 Retain 和整合的任务说明都在用户消息中。只显示系统提示词，会让人以为并未设置任务说明。

**这和提取测试器有什么区别？**
它们在同一个对话框中，分别展示不同的一半。预览免费展示三种操作将发送的内容；测试器只针对 Retain，根据示例文本执行一次真实提取，而且不会保存任何内容。
