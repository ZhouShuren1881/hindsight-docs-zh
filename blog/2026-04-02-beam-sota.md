[Hindsight](https://github.com/vectorize-io/hindsight) 在 BEAM 上达到当前最先进水平。BEAM 是一项在 1000 万 token 规模上测试记忆能力的基准；在这个规模下，根本不可能把所有内容都塞进上下文，只有真正的记忆架构才能发挥作用。

---

## 为什么 10M 这一档的结果最重要 {#why-the-10m-tier-is-the-most-important-result}

如果你一直关注智能体记忆评测，就会知道 LoComo 和 LongMemEval。它们都是可靠的数据集。问题不在数据集质量，而在于它们设计时所处的时代。

这两个数据集都诞生于 32K 上下文窗口的时代。当时，无法把一段长对话完整放进一次模型调用中，因此基准测试以“记忆系统需要有选择地检索正确事实”为前提。这让这些基准测试具有实际意义。

那个时代已经过去了。

如今，最先进的模型已经支持百万 token 的上下文窗口。在目前的大多数 LoComo 和 LongMemEval 测例中，简单地“把所有内容都倒进上下文”也能取得有竞争力的分数。这不是因为这种架构好，而是因为窗口大到足以装下整个数据集。这些基准测试已经无法区分真正的记忆系统和单纯填充上下文的系统。它们的分数也不再能说明太多问题。

[BEAM](https://arxiv.org/pdf/2510.27246)（“超越百万 token”）正是为了解决这个问题而设计的。它在上下文填充这一捷径行不通的长度上进行测试：

| 上下文长度 | 测试内容 |
| --- | --- |
| 100K token | 基线：大多数系统都能处理 |
| 500K token | 检索开始变得重要 |
| 1M token | 接近当前上下文窗口的边界 |
| **10M token** | **没有任何上下文窗口足够大，只有真正的记忆系统才能奏效** |

在 10M token 规模下，没有捷径可走。你无法把数据装进上下文。想取得好成绩，唯一的办法是使用记忆系统，从大到任何模型的注意力窗口都无法容纳的数据池中，检索出正确的事实。BEAM 论文显示，在这个规模下，采用恰当记忆架构的系统比原始基线提升超过 +155%。在这种规模下，不同架构之间的差距最明显，Hindsight 的结果也最能体现这一点。

## 数据 {#the-numbers}

以下是 BEAM 10M 这一档所有已发布的结果：

| 系统 | 10M 得分 |
| --- | --- |
| RAG（Llama-4-Maverick）— BEAM 论文基线 | 24.9% |
| LIGHT（Llama-4-Maverick）— BEAM 论文基线 | 26.6% |
| Honcho | 40.6% |
| **Hindsight** | **64.1%** |

Hindsight 在 10M 这一档得分为 64.1%。已发布结果中，得分第二高的是 40.6%，因此 Hindsight 领先 58%。与论文中的基线相比，Hindsight 的得分超过其 2.4 倍。

以下是 BEAM 各档位的完整结果：

| 档位 | Hindsight | Honcho | LIGHT 基线 | RAG 基线 |
| --- | --- | --- | --- | --- |
| 100K | **73.4%** | 63.0% | 35.8% | 32.3% |
| 500K | **71.1%** | 64.9% | 35.9% | 33.0% |
| 1M | **73.9%** | 63.1% | 33.6% | 30.7% |
| **10M** | **64.1%** | 40.6% | 26.6% | 24.9% |

有一点值得注意：Hindsight 在 1M 档的得分（73.9%）高于 500K 档（71.1%）。token 数量增加时，性能没有下降，反而有所提升。大多数系统的表现正好相反。这说明该架构按预期发挥作用，也让它与其他方案之间的差距更加明显。

所有结果都在 [Agent Memory Benchmark](https://agentmemorybenchmark.ai/dataset/beam) 上公开跟踪。若想了解我们为何构建这项基准以及如何评测，请参阅 [Agent Memory Benchmark：宣言](/blog/2026/03/23/agent-memory-benchmark)。

## 1000 万 token 实际意味着什么 {#what-10-million-tokens-actually-looks-like}

为了直观理解这个规模：1000 万 token 大约相当于与 AI 智能体进行一整年的每日对话、一家公司全部的内部文档，或一个软件项目数百个会话的完整输出。这不是人为设计的压力测试，而是生产系统随着时间推移实际积累的数据量。

达到这个规模后，上下文填充不再只是需要权衡的做法，而是根本无法实现。GPT-4o 的 128K 上下文窗口只能容纳 10M token 历史记录的大约 1.3%。Gemini 1.5 Pro 的 2M 窗口只能容纳 20%。即使是目前最大的上下文窗口，也远远不够。在这种数据规模下运行的智能体只能有选择地检索；检索质量决定了记忆能否正常工作。

即使不考虑容量限制，填充上下文的效果也不好。Chroma 关于[上下文退化](https://research.trychroma.com/context-rot)的研究表明，随着输入变长，LLM 的表现会显著下降，即使输入还在模型支持的窗口范围内也是如此。输入达到 128K token 时，模型已经会失去连贯性，并遗漏埋在中间的信息。1M token 的上下文窗口并不意味着模型能可靠地关注全部 1M token；输入越长，增加的上下文越难带来相应收益。选择性检索不只在 10M token 规模下不可或缺；即使在技术上还能把内容塞进上下文的规模下，它也更有效。

这就是我们为何投入重建检索流程、改进事实提取以及观测机制等架构工作，从而取得这些 BEAM 结果。观测机制会根据累积的事实综合生成更高层次的知识，让检索结果提供洞见，而不只是原始历史记录。这些架构选择在大规模场景下会相互叠加，发挥更大作用。我们也在 [Agent Memory Benchmark 宣言](/blog/2026/03/23/agent-memory-benchmark)中进一步介绍了这些做法，以及我们采用这些评测方式和优化方向背后的理由。

## 免费本地运行，也可使用云服务 {#free-and-local--or-cloud}

Hindsight 可以完全在本地运行。无需账号或 API 密钥，数据也不会离开你的设备：

```bash
# 启动本地守护进程，无需安装
uvx hindsight-embed
```

你的智能体连接到 `http://localhost:8888`。完整设置步骤请见[快速入门](/developer/api/quickstart)。

如果你希望记忆能在多台设备间使用，或供多个智能体共享，可以改为连接 Hindsight Cloud。只需更改一项配置：

```json
{
  "hindsightApiUrl": "https://api.hindsight.vectorize.io",
  "hindsightApiToken": "hsk_your_token"
}
```

两种模式使用相同的 API。从本地切换到云端只需更改配置，无需迁移。
