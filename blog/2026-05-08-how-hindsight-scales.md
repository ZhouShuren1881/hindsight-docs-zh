智能体记忆系统面临着传统数据库所没有的扩展问题。这不仅仅是“我们能否存储更多数据”，而是“随着记忆在数周、数月和数年的积累中，系统能否保持快速、准确且经济实惠”。

挑战在于智能体记忆涉及LLM调用、语义搜索、图遍历和合成。每个都有自己的缩放曲线。有些会根据输入大小进行缩放。有些与存储的记忆总数成比例。有些会随着查询的复杂性而扩展。了解每个操作在哪个轴上扩展就足以预测成本和延迟的形状，甚至在您获得确切的数字之前也是如此。

这篇文章是设计分析，而不是基准报告——性能曲线是未来的文章。我们在这里可以解释的是为什么每个操作都有它所执行的缩放配置文件、最坏情况的边界是什么以及哪些旋钮控制哪些权衡。故障模式和恢复行为（队列背压、速率限制降级）也超出了范围 - 我们将分别介绍这些内容。

五个架构决策塑造了扩展故事：

- **读写不对称**：我们在写入时支付LLM成本，因此读取无需LLM。
- **分层知识压缩**：原始事实→观察→心智模型，每一层都压缩其下一层。
- **平行一切**：四路记忆感知、32路提取、异步整合。
- **有界遍历**：每个操作都有一个由配置控制的最坏情况上限。
- **尽可能使用本地模型**：嵌入和重排序默认在本地运行，因此记忆召回的LLMAPI成本为零。

​​本文的其余部分展示了这些决策如何在每个操作中发挥作用。

## 记忆存储——成本随输入而变化，而不是随已存储的内容而变化 {#retain--cost-scales-with-input-not-with-whats-already-stored}

记忆存储是写入路径。内容进入，被分块，事实由 LLM 提取，生成嵌入，所有内容都通过实体、时间、语义和因果链接进行存储。

**扩展论点：记忆存储成本与你摄取的内容成正比，而不是与已经存储的内容成正比。** 无论记忆库有 100 个还是 1,000,000 个现有事实，处理 10 个块的记忆存储调用的成本都是相同的。

原因如下。管道是一个流式生产者-消费者系统。内容被分成约 3,000 个字符的块，分组为小批量，并通过三个阶段进行处理：

1. **阶段 1（大量读取、外部事务）：** 通过三元组 GIN 扫描、语义 ANN 搜索进行实体解析以查找相似的现有事实。在单独的连接上运行，以避免在缓慢读取期间持有行锁。
2. **阶段2（写事务）：** 插入事实、创建实体链接、构建时间链接（24 小时窗口内）、语义链接（批内 + 预先计算的 ANN）和因果链接。每批次原子。
3. **阶段 3（交易后，尽力而为）：** 最终的人工神经网络遍历整个记忆库——针对整个现有语料库查找新插入事实的语义邻居。

LLM 事实提取（主要成本）是每个块一次调用（`retain_chunk_size`，默认约 3,000 个字符），并行最多 32 个并发提取。块被分组为小批量（`retain_chunk_batch_size`，默认 100），无论输入大小如何，这些小批量都会限制内存使用量。每个提取的事实都有一个嵌入。数据库写入与事实数量成线性关系。所有这些都与输入量有关，而不是记忆库大小。每个事实最多创建 20 个临时链接 - 这是一个硬上限，可防止链接存储无限制增长。

唯一的例外是第 3 阶段的 ANN 通行证，它查询完整的记忆库以查找新事实的语义邻居。但是 HNSW 每个查询的复杂度为 O(log N)，因此即使在记忆库大小很大的情况下，它也会缓慢增长。

**Delta 记忆存储** 使重复摄入更加便宜。如果文档的内容哈希与先前版本匹配，则完全跳过未更改的块 - 没有LLM提取，没有嵌入，没有写入。对于定期重新同步文档的集成，第一次同步后的成本降至仅更改的块。

事实提取质量与记忆库大小无关——每个块都是单独处理的。随着规模的扩大，**链接密度**：记忆库中更多的事实意味着更多的时间邻居、更多的语义邻居和更丰富的实体共现图。随着时间的推移，图的联系越来越紧密，这有利于下游基于图的检索。

## 记忆召回——零LLM调用，O(log N)检索 {#recall--zero-llm-calls-olog-n-retrieval}

记忆召回是阅读路径。它并行运行四种检索策略，将它们与倒数排名融合融合，并使用交叉编码器重新排名。我们涵盖了[完整架构在上一篇文章中](/blog/2026/03/27/parallel-hybrid-search)。在这里，我们重点关注什么与什么成比例。

**扩展论点：记忆召回进行零次LLM调用。** 纯粹是检索加跨编码器重排序。这是一个经过深思熟虑的架构选择——我们在记忆存储时间（事实提取）支付LLM成本，以便记忆召回在任何规模上都没有LLMAPI成本。

以下是不花费任何成本、花费 O(log N) 以及受配置限制的内容：

**无需任何成本（结构上为零）：** LLM 呼叫。没有。跨编码器重排序器默认在本地运行（CPU 上的小型模型），但也可以配置为使用外部提供程序。不管怎样，记忆召回路径本身永远不会调用LLM。

**成本 O(log N):** 语义搜索。 HNSW 索引给出对数查询时间。我们使用按记忆库、按事实类型的部分索引，以便查询规划器为每个查询臂准确命中正确的索引。 BM25 通过 PostgreSQL GIN 索引也与语料库大小呈亚线性缩放。

**受配置限制：** 图遍历的上限为`budget`（LOW=100，MID=300，HIGH=1000 个已探索的节点）。时间搜索限于 5 次 BFS 迭代，每个源单元最多扩展 10 个邻居。这些都是硬性上限——无论链接图有多密集，图和时间检索时间实际上都是恒定的。 `ef_search`（默认 200）控制 HNSW 搜索彻底性，以记忆召回质量换取查询速度。

四种策略并行运行——语义+BM25+时间共享连接；图表按事实类型独立运行。总记忆延迟是最慢分支的最大值，而不是总和。跨编码器推理和连接池获取不会从索引中受益，因此它们设置了延迟下限。

​​在质量方面，随着记忆库的增长，图检索有更多的材料可供使用——更密集的实体共现和更多的语义 kNN 路径为其提供了更多的遍历选项。语义搜索是唯一可以在非常大的范围内稍微降低性能的策略（HNSW 是近似的），通过过度获取和可调`ef_search` 来缓解。 BM25 是词汇且稳定的。集成效应意味着即使一种策略变得更加嘈杂，其他三种策略也会进行补偿 - RRF 融合是基于排名的，因此它可以自然地处理混合质量的输入。

## 整合 — LLM绑定后台工作 {#consolidation--llm-bound-background-work}

整合在记忆存储完成后运行。它采用原始经验和世界事实，并将它们合成为**观察**——代表更高层次模式和见解的综合知识。将其视为系统“思考”它学到的东西。

**扩展理论：整合成本与新记忆的数量线性扩展，并且它受 LLM 限制** — 在我们的分析中，大约占挂钟时间的 80% 以上。 DB 和嵌入工作相对可以忽略不计。

管道：

1. 批量获取未合并的记忆
2. 对于每个记忆，运行记忆召回来查找相关的现有观察（并行、仅数据库回忆）
3. 将记忆分组为子批次，并对每个子批次进行一次 LLM 调用
4. 执行LLM的指令：创建、更新或删除观察
5. 为新的/更新的观察生成嵌入
6. 检查点：将记忆标记为合并的

它作为后台工作程序异步运行 - 它永远不会阻止面向用户的操作。批处理架构具有内置的背压：`consolidation_max_memories_per_round`（默认100）限制单轮处理的记忆数量，`consolidation_llm_batch_size`（默认8）控制每个LLM调用的记忆数量。这些共同构成了一个硬性上限：一轮整合永远不会进行超过 `max_memories_per_round ÷ llm_batch_size` LLM 次调用。自适应错误处理将失败的子批次一分为二（8→4→2→1）并重试，因此一个错误的记忆不会阻止其余的记忆。

整合质量 **随着规模的扩大而提高** — 更多原始事实意味着更丰富的观察综合源材料。范围隔离（基于标签）可防止跨上下文污染，源事实跟踪可保留出处，因此每个观察都可以追溯到其合成的事实​​。

随着时间的推移，整合在不同意义上变得亚线性：随着记忆库的成熟，更多的记忆会更新现有的观察而不是创建新的观察。每批的LLM调用计数保持不变，但观察计数的增长速度慢于记忆计数。

## 梦想 — 对分层知识的有限推理 {#reflect--bounded-reasoning-over-hierarchical-knowledge}

反思是综合操作。给定一个问题，它使用代理LLM循环搜索三层知识层次结构——心智模型，然后是观察，然后是原始事实。

**缩放主题： 质量与总记忆数脱钩。** 分层检索意味着对观察和心智模型（压缩原始语料库）的推理，而不是直接对所有记忆的推理。原始事实搜索是有针对性的后备方案，而不是全语料库扫描。

智能体在进入自由形式推理之前遵循强制工具调用序列。每次迭代（包括强制迭代）都是一次 LLM 调用，其中模型被限制为使用特定工具：

1. **搜索观察**（强制）：LLM 调用工具选择仅限于搜索观察。内部调用记忆召回，过滤为观察类型的事实。
2. **搜索原始事实**（强制）：LLM 调用工具选择仅限于记忆召回经验和世界事实。
3. **搜索心智模型**（强制，仅当心智模型存在于记忆库中时）：LLM 调用工具选择限制为搜索心智模型嵌入。
4. **推理迭代**（自动）：LLM 决定是否扩展结果、运行附加搜索或合成最终答案。
5. **最终合成**：无需工具强制仅文本响应。

每次迭代都是一次LLM调用。强制序列通常为 2 个步骤（观察 + 原始事实），当记忆库有心智模型时扩展到 3 个步骤。强制序列后，智能体进入自动模式，LLM自由选择。

硬上限防止成本失控：`reflect_max_iterations`（默认 10）限制迭代总数，`reflect_max_context_tokens`（默认 100,000）在累积上下文增长太大时强制最终合成，`reflect_wall_timeout`（默认 300 秒）是挂钟截止。默认情况下，一个 ^ 调用永远不会进行超过 12 次 LLM 调用（2 次强制 + 10 次自动迭代），永远不会累积超过 100K 令牌，并且运行时间永远不会超过 5 分钟。

随着记忆库的增长，观察力会吸收复杂性。它不是需要对数千个原始事实进行推理，而是对总结它们的观察进行推理。 心智模型提供了一个更高级别的缓存——预先计算出常见问题的答案，反思可以参考而无需重新推导。

## 心智模型——用新信息而非全部知识刷新成本量表 {#mental-models--refresh-cost-scales-with-new-information-not-total-knowledge}

心智模型位于知识体系的顶端。它们是用户定义的问题，带有预先计算的答案——系统保持最新的固定反映。

**扩展论点：增量刷新仅处理自上次刷新以来的新事实，因此由 10,000 个事实支持的心智模型看到 5 个新事实的刷新成本与由 100 个事实支持的心智模型的刷新成本相同。** 用新信息的比率而不是现有知识的存量来刷新成本规模。读取心智模型是通过 ID 直接进行数据库查找——没有LLM，没有向量搜索。昂贵的工作发生在刷新时，而不是读取时。

心智模型由**来源查询**、**标签**（范围过滤器）和**触发配置**定义。关键触发标志是`refresh_after_consolidation`——启用后，链是自动的：记忆存储→整合创建观察→心智模型，并在后台刷新匹配的标签。

刷新以两种模式运行。 **全面刷新**在内部运行一个完整的履历循环（强制搜索+推理+综合），从头开始重写整个文档——简单可靠，但它会重新生成没有改变的部分。 **Delta刷新** 将记忆召回缩小到 *之后* 最后刷新时间戳创建的事实。 LLM 不是合成新文档，而是发出应用于现有文档结构的结构化补丁操作（追加/插入/替换/删除块和部分）。未提及的部分未受影响 - 稳定内容上的零散文漂移，手动策划的部分在刷新后完好无损。 Delta 需要额外的 LLM 调用来生成操作，但处理的上下文要小得多。当源查询发生更改、文档结构格式错误或自上次刷新以来不存在新事实时，它会自动回退到完全刷新。

背景成本链很重要：N个新记忆→M个观察更新→K个心智模型刷新→K×多个LLM分别调用。对于一个有很多心智模型并且频繁保留的记忆库来说，这个加起来就很重要了。但整合触发的刷新是异步的——它们作为后台任务运行，永远不会阻止面向用户的操作。

## 旋钮及其权衡 {#knobs-and-what-they-trade-off}

这些是控制缩放行为的配置参数，按其权衡进行组织：

**记忆质量与延迟：**
- `budget` — 更高的预算探索更多的图节点，以遍历时间为代价找到更多的连接
- `ef_search` — 较高的值使 HNSW 搜索更彻底，以查询时间为代价减少近似误差
- 语义超取乘数 - 从 HNSW 获取更多候选者可以提高记忆准确度，但会增加重排序工作量

**集成吞吐量与资源使用情况：**
- `consolidation_llm_batch_size` — 更大的批次意味着更少的 LLM 调用，但更大的提示。受提供商的上下文窗口和速率限制的约束
- `consolidation_max_memories_per_round` — 更高的限制每轮处理更多记忆，但保留工作槽的时间更长

**反思深度与成本：**
- `reflect_max_iterations` — 更少的迭代意味着更快、更便宜的反映，但代价是不太彻底的推理
- `reflect_max_context_tokens` — 较低的上限迫使更早的合成，交易深度以获得可预测性

**心智模型新鲜度与背景成本：**
- `refresh_after_consolidation` — 启用自动刷新，但在每轮整合后添加 LLM 调用
- 完整刷新模式与增量刷新模式 - 增量每次刷新更便宜（仅处理新事实），但无法重组文档

**水平缩放：**

Hindsight 使用基于代理的架构，具有两种独立扩展的不同流程类型：

- **API流程** (`hindsight-api`) 处理 HTTP/MCP 请求并将后台任务写入共享的 PostgreSQL `async_operations` 表。在负载均衡器后面运行任意数量的实例——除了数据库之外，它们不共享任何状态。
- **工作进程** (`hindsight-worker`) 轮询PostgreSQL待处理任务并执行后台操作（集成、心智模型刷新）。多个工作线程竞争从队列中获取任务——无需进程间通信。

对于单实例开发，`HINDSIGHT_API_WORKER_ENABLED=true`（默认）将工作线程嵌入到API进程中。在生产中，禁用它并运行专用工作实例以将后台工作与面向用户的流量分开。

一旦你超过了一些连接池（PgBouncer 或同等的）就变得很重要API实例。工人是LLM-bound，因此将工作人员扩展到超出您的范围LLM提供商的速率限制不会有帮助 - 仅当您有速率限制空间时才添加更多工作人员。
