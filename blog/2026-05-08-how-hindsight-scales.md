智能体记忆系统面临着传统数据库没有的扩展问题。问题不只是“能否存储更多数据”，还包括“随着数周、数月乃至数年间记忆不断累积，系统能否保持快速、准确且成本可控”。

挑战在于，智能体记忆涉及 LLM 调用、语义检索、图遍历和综合生成。每一项都有自己的扩展曲线。有些随输入规模增长，有些随存储的记忆总数增长，还有些随查询复杂度增长。了解每种操作受哪个维度影响，即使还没有精确数据，也足以预测成本和延迟的变化趋势。

本文是设计分析，不是基准测试报告；性能曲线会在后续文章中介绍。本文将解释各项操作为何具有相应的扩展特征、最坏情况的上限是什么，以及哪些配置项会影响哪些权衡。故障模式与恢复行为（例如队列背压和速率限制导致的性能下降）不在本文讨论范围内，我们会另行介绍。

五项架构决策决定了扩展特征：

- **读写不对称**：我们在写入时承担 LLM 成本，因此读取时无需调用 LLM。
- **分层知识压缩**：原始事实 → 观测 → 心智模型；每一层都会压缩其下一层的内容。
- **全面并行**：四路 Recall、32 路事实提取、异步整合。
- **有界遍历**：每项操作都有由配置控制的最坏情况硬上限。
- **尽可能使用本地模型**：嵌入和重排序默认在本地运行，因此 Recall 不产生 LLM API 调用成本。

本文接下来会展示这些决策如何影响各项操作。

## Retain：成本随输入规模增长，与已有存储量无关 {#retain--cost-scales-with-input-not-with-whats-already-stored}

Retain 是写入路径。内容进入系统后会被分块，由 LLM 提取事实，生成嵌入，并与实体、时间、语义和因果连接一起存储。

**扩展规律：Retain 的成本与正在摄取的内容量成正比，而不是与已有存储量成正比。** 无论记忆库中已有 100 条还是 1,000,000 条事实，处理 10 个分块的 Retain 调用成本相同。

原因在于，这条处理管线采用流式生产者-消费者架构。内容被切分为约 3,000 个字符的分块，再组成小批次，并经过三个阶段处理：

1. **阶段 1（读取密集，在事务之外）：** 通过三元组 GIN 扫描进行实体解析，并通过语义 ANN 搜索查找相似的已有事实。此阶段使用单独的连接，以免在耗时的读取期间持有行锁。
2. **阶段 2（写入事务）：** 插入事实、创建实体连接，并建立时间连接（24 小时窗口内）、语义连接（批次内连接及预先计算的 ANN 结果）和因果连接。每个批次的写入都是原子的。
3. **阶段 3（事务之后，尽力执行）：** 最后再对整个记忆库运行 ANN 检索，为新插入的事实查找整个现有语料库中的语义邻居。

成本最高的是 LLM 事实提取：每个分块调用一次（由 `retain_chunk_size` 控制，默认约 3,000 个字符），最多并行执行 32 次提取。分块按 `retain_chunk_batch_size`（默认 100）组成小批次，因此无论输入规模多大，内存用量都有上限。每条提取出的事实生成一个嵌入。数据库写入量随事实数量线性增长。这些成本都随输入量变化，而非记忆库大小。每条事实最多创建 20 个时间连接，这个硬上限可以防止连接存储无限增长。

唯一的例外是阶段 3 的 ANN 检索：它会查询整个记忆库，为新事实查找语义邻居。不过，HNSW 每次查询的复杂度为 O(log N)，因此即使记忆库很大，成本也只会缓慢增长。

**增量 Retain** 还能进一步降低重复摄取的成本。如果文档内容哈希与先前版本相同，未变化的分块会被完全跳过，不进行 LLM 提取、嵌入生成或写入。对于定期重新同步文档的集成，首次同步之后只需为发生变化的分块付费。

事实提取质量不受记忆库大小影响，因为每个分块都是独立处理的。随规模增长而改善的是**连接密度**：记忆库中的事实越多，时间邻居和语义邻居就越多，实体共现图也越丰富。图会随时间变得更连通，从而有利于下游的图检索。

## Recall：零次 LLM 调用，O(log N) 检索 {#recall--zero-llm-calls-olog-n-retrieval}

Recall 是读取路径。它并行运行四种检索策略，通过倒数排名融合（RRF）合并结果，再由交叉编码器重排序。我们在[上一篇文章](/blog/2026/03/27/parallel-hybrid-search)中介绍了完整架构；本文聚焦于哪些成本随什么因素变化。

**扩展规律：Recall 不调用 LLM。** 它只执行检索和交叉编码器重排序。这是有意的架构选择：我们在 Retain 阶段承担 LLM 成本（事实提取），因此无论规模如何，Recall 都不产生 LLM API 调用成本。

下面分别说明哪些成本为零、哪些为 O(log N)，以及哪些受配置限制：

**结构上为零的成本：** LLM 调用。这里一次也没有。交叉编码器重排序模型默认在本地运行（在 CPU 上运行的小型模型），也可以配置为使用外部服务提供方。无论采用哪种方式，Recall 路径本身都不会调用 LLM。

**O(log N) 的成本：** 语义检索。HNSW 索引提供对数级查询时间。我们使用按记忆库和事实类型划分的部分索引，因此查询规划器会为每条查询分支命中恰当的索引。通过 PostgreSQL GIN 索引实现的 BM25 检索，其扩展速度也低于语料库大小的线性增长。

**受配置限制的成本：** 图遍历由 `budget` 限制（LOW=100、MID=300、HIGH=1000 个探索节点）。时间检索最多进行 5 轮 BFS 迭代，每个来源单元最多扩展 10 个邻居。这些都是硬上限，因此无论连接图变得多密集，图检索和时间检索的耗时实际上都保持恒定。`ef_search`（默认 200）控制 HNSW 搜索的彻底程度，在 Recall 质量和查询速度之间进行权衡。

四种策略并行运行：语义检索、BM25 和时间检索共用一个连接；图检索则按事实类型分别运行。Recall 的总延迟取决于最慢的分支，而不是把各分支耗时相加。交叉编码器推断和连接池连接获取不会因索引而加速，因此决定了延迟下限。

就质量而言，记忆库越大，图检索可利用的材料越多：更密集的实体共现和更多语义 kNN 路径会提供更多遍历选择。只有语义检索在规模特别大时可能略有退化（HNSW 是近似算法）；可以通过超额获取候选结果和调整 `ef_search` 来缓解。BM25 属于词法检索，表现稳定。集成效应意味着即使一种策略的结果噪声增加，其他三种也能补偿。RRF 融合基于排名，因此能自然处理质量参差的输入。

## 整合：受 LLM 限制的后台工作 {#consolidation--llm-bound-background-work}

Retain 完成后会运行整合。整合会获取原始经历事实和世界事实，并将它们综合为**观测**，即表达更高层模式和洞见的整合后知识。可以把它理解为系统在“思考”自己学到的内容。

**扩展规律：整合成本随新增记忆数量线性增长，并且主要受 LLM 耗时限制。** 根据我们的性能分析，LLM 大约占总耗时的 80% 以上。数据库和嵌入相关工作所占时间相对很少。

处理管线如下：

1. 分批获取尚未整合的记忆。
2. 对每条记忆执行 Recall，查找相关的已有观测（并行执行，仅访问数据库）。
3. 将记忆分成子批次，每个子批次调用一次 LLM。
4. 执行 LLM 给出的指令：创建、更新或删除观测。
5. 为新建或更新的观测生成嵌入。
6. 创建检查点，将记忆标记为已整合。

整合由后台工作进程异步执行，不会阻塞面向用户的操作。批处理架构内置背压：`consolidation_max_memories_per_round`（默认 100）限制每轮处理的记忆数量，`consolidation_llm_batch_size`（默认 8）控制每次 LLM 调用包含的记忆数量。两者共同构成硬上限：一轮整合的 LLM 调用次数不会超过 `max_memories_per_round ÷ llm_batch_size`。自适应错误处理会将失败的子批次不断二分（8→4→2→1）并重试，因此一条有问题的记忆不会阻塞其余记忆。

整合质量会**随规模增长而提高**：原始事实越多，综合生成观测时可用的来源材料就越丰富。按标签隔离范围可以防止不同上下文相互污染；来源事实追踪则会保留来源追溯信息，因此每条观测都能追溯到用于综合生成它的事实。

随着记忆库逐渐成熟，整合还会在另一种意义上呈现次线性增长：更多记忆会更新已有观测，而不是创建新观测。每个批次的 LLM 调用数量保持不变，但观测数量的增长速度会低于记忆数量。

## Reflect：对分层知识进行有界推理 {#reflect--bounded-reasoning-over-hierarchical-knowledge}

Reflect 是综合生成操作。给定一个问题后，它通过智能体 LLM 循环，在三层知识结构中搜索：先查心智模型，再查观测，最后查原始事实。

**扩展规律：Reflect 的质量与记忆总数相互独立。** 分层检索让 Reflect 基于观测和心智模型推理（它们压缩了原始语料库），而不是直接处理所有记忆。原始事实搜索是有针对性的后备检索，不会扫描整个语料库。

智能体会先按规定顺序调用工具，然后才进入自由形式推理。每轮迭代（包括强制调用的轮次）都需要一次 LLM 调用，此时模型只能使用指定工具：

1. **搜索观测**（强制）：LLM 调用被限制为选择搜索观测的工具。该工具内部调用 Recall，并将结果筛选为观测类型的事实。
2. **搜索原始事实**（强制）：LLM 调用被限制为选择 Recall，以检索经历事实和世界事实。
3. **搜索心智模型**（强制，仅当记忆库中存在心智模型时）：LLM 调用被限制为搜索心智模型嵌入。
4. **推理迭代**（自动）：LLM 决定是否扩展结果、执行更多搜索，或综合生成最终答案。
5. **最终综合生成**：强制生成纯文本响应，不调用工具。

每轮迭代都要调用 LLM。强制序列通常包含 2 步（搜索观测和原始事实）；如果记忆库中存在心智模型，则增加到 3 步。完成强制序列后，智能体进入自动模式，由 LLM 自主选择操作。

硬上限可以防止成本失控：`reflect_max_iterations`（默认 10）限制迭代总数；`reflect_max_context_tokens`（默认 100,000）会在累积上下文过大时强制开始最终综合生成；`reflect_wall_timeout`（默认 300 秒）限制墙钟时间。使用默认值时，单次 Reflect 调用最多执行 12 次 LLM 调用（2 次强制调用 + 10 次自动迭代），累积上下文不会超过 100K tokens，运行时间也不会超过 5 分钟。

随着记忆库增长，观测会吸收更多复杂性。Reflect 无需再对数千条原始事实直接推理，而是基于总结这些事实的观测进行推理。心智模型则提供更高层的缓存，其中包含常见问题的预先计算答案，Reflect 可以直接参考，而不必重新推导。

## 心智模型：刷新成本随新增信息增长，而非随知识总量增长 {#mental-models--refresh-cost-scales-with-new-information-not-total-knowledge}

心智模型位于知识层级的顶端。它们是用户定义的问题及其预先计算的答案，相当于可固定保存并由系统持续更新的 Reflect 结果。

**扩展规律：增量刷新只处理上次刷新以来新增的事实。因此，一个基于 10,000 条事实的心智模型若只新增 5 条事实，其刷新成本与一个基于 100 条事实的心智模型相同。** 刷新成本随新增信息的速度增长，而非随既有知识的存量增长。读取心智模型时只需按 ID 直接查询数据库，无需调用 LLM 或执行向量检索。高成本工作发生在刷新时，而非读取时。

心智模型由**来源查询**、**标签**（范围筛选条件）和**触发器配置**定义。关键触发标志是 `refresh_after_consolidation`。启用后，处理链会自动运行：Retain → 整合创建观测 → 在后台刷新标签匹配的心智模型。

刷新有两种模式。**完整刷新**会在内部执行一次完整的 Reflect 循环（强制搜索、推理和综合生成），从头重写整份文档。它简单可靠，但也会重新生成没有变化的章节。**增量刷新**会把 Recall 的范围缩小到上次刷新时间戳之后创建的事实。LLM 不会综合生成一份新文档，而是输出结构化补丁操作（追加、插入、替换或移除内容块和章节），并将这些操作应用于现有文档结构。未提及的章节保持不变，因此稳定内容不会发生文字漂移，人工维护的章节也能在刷新后完整保留。增量刷新需要额外调用一次 LLM 来生成操作，但处理的上下文小得多。如果来源查询已更改、文档结构格式错误，或上次刷新后没有新事实，系统会自动回退到完整刷新。

后台成本链也很重要：N 条新记忆 → M 次观测更新 → K 次心智模型刷新 → 每次刷新调用多次 LLM。对于心智模型很多且 Retain 频繁的记忆库，这些成本会不断累积。不过，由整合触发的刷新是异步后台任务，不会阻塞面向用户的操作。

## 配置项及其权衡 {#knobs-and-what-they-trade-off}

以下配置参数控制扩展行为，按其权衡关系分类：

**Recall 质量与延迟：**
- `budget`：提高预算会探索更多图节点，从而找到更多连接，但遍历耗时也会增加。
- `ef_search`：提高数值会让 HNSW 搜索更彻底，减少近似误差，但查询时间会增加。
- 语义检索超额获取乘数：从 HNSW 获取更多候选项可以提高 Recall 的精确度，但会增加重排序工作量。

**整合吞吐量与资源用量：**
- `consolidation_llm_batch_size`：批次越大，LLM 调用越少，但提示内容也越多。具体受模型服务提供方的上下文窗口和速率限制约束。
- `consolidation_max_memories_per_round`：提高上限可以让每轮处理更多记忆，但工作进程槽位会被占用更久。

**Reflect 深度与成本：**
- `reflect_max_iterations`：减少迭代次数可以让 Reflect 更快、成本更低，但推理也会较不充分。
- `reflect_max_context_tokens`：降低上限会更早开始综合生成，以牺牲推理深度换取更可预测的成本。

**心智模型更新状态与后台成本：**
- `refresh_after_consolidation`：启用自动刷新，但每轮整合后都会增加 LLM 调用。
- 完整刷新与增量刷新模式：增量刷新每次成本更低（只处理新事实），但不能重组文档结构。

**水平扩展：**

Hindsight 采用基于任务代理的架构，包含两类可以独立扩展的进程：

- **API 进程**（`hindsight-api`）处理 HTTP/MCP 请求，并将后台任务写入共享的 PostgreSQL `async_operations` 表。可以在负载均衡器后运行任意数量的实例；这些实例除了数据库外不共享状态。
- **工作进程**（`hindsight-worker`）轮询 PostgreSQL，领取等待处理的任务并执行后台操作（整合、心智模型刷新）。多个工作进程会竞争领取队列中的任务，无需进程间通信。

在单实例开发环境中，`HINDSIGHT_API_WORKER_ENABLED=true`（默认值）会把工作进程嵌入 API 进程。生产环境中应禁用此设置并运行独立工作进程，以便将后台工作与面向用户的流量分开。

当 API 实例达到数个之后，连接池（如 PgBouncer 或同类工具）就会变得重要。工作进程的工作受 LLM 耗时限制，因此将工作进程扩展到超出 LLM 服务提供方的速率限制并无帮助；只有在速率限制尚有余量时，增加工作进程才有意义。
