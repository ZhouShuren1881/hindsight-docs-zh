Hindsight 0.9.0 带来了两项我们并行开发了数月的功能：**知识页**——由记忆库编写并持续维护、介绍记忆库自身的动态文档；以及**统一的编程智能体插件**。它只需一条命令、无需配置，就能为十种编程智能体——Claude Code、Codex CLI、Cursor CLI、opencode、GitHub Copilot CLI、Cline、Kilo、Grok Build、Antigravity 和 Devin——提供项目长期记忆。

这两项功能最终都和我们最初设想的不同。这篇文章讲述我们如何走到这一步，因为这些弯路本身就是产品的一部分：我们不得不自创一套基准测试，它揭穿并淘汰了我们自己的架构；我们也做出了一套学会自我修复的 wiki。

## 1. “这真的有帮助吗？” {#1-is-this-actually-helping}

一切始于一个令人不安的问题。我们为编程智能体做了记忆集成，用户喜欢它，演示效果也不错：你问智能体某个错误，它就能从记忆中找出解释这个错误的旧决策，现场的人纷纷点头。可客户接着会问：“这究竟能帮上多大忙？”我们只能讲个例，因为手里没有数据。

于是，我们用最直接的办法去找数据：跑 SWE-bench。它有真实代码库、真实问题，也是业内的衡量标准。几天后我们才意识到，它回答不了我们的问题。这不是因为它是糟糕的基准，而是因为它衡量的是另一种场景。

SWE-bench 是**单轮测试**：智能体阅读问题、提交补丁、补丁接受评分，测试就结束了。没人会那样使用编程智能体。真实工作是一段反复推进的过程：你提出需求，智能体尝试，测试给出反馈，智能体修改，你再推动它继续。弱智能体的代价不是最后交付了一个失败补丁，而是中间每一步都可能让人停下手头工作、纠正方向。单轮基准从结构上就看不到这个循环。

问题还不止于此：SWE-bench 的任务可以**仅凭代码库**解决。问题描述加上代码就包含了答案。只有当决定性上下文**不在代码库里**时，记忆才能发挥价值；而在 SWE-bench 上，有完美记忆和完全没有记忆，结果理应趋同。一个无法体现记忆作用的基准，自然无法告诉我们记忆究竟有没有作用。

## 2. 一个贴近真实工作的数据集 {#2-a-dataset-shaped-like-real-work}

于是我们自己构建了一套数据集：**61 项错误修复任务**，全部基于真实的开源代码库 `boltons`。我们保留了约 1,600 条真实提交作为干扰，还把 140 段冗长、可信、技术性强、却没有提供任何决策结论的诱饵对话混进历史记录。检索必须对结果**排序**，不能只把内容找出来。

每项任务都取决于一项**无法猜出、且针对特定项目的决策**。公开的错误报告会复现真实故障，而显而易见的修复也能通过该复现测试。随后，一项智能体从未见过的**隐藏测试**会检查团队实际采用了什么决策。我们最喜欢的例子是一个导出错误：教科书式的修复方法（标准 CSV 引用）**有记录表明已经试过并被否决**，因为接收数据的 ERP 系统会强制转换数字字符串，即使它们带引号也不例外，还会去掉前导零。它能逐字节导入的唯一格式是 Excel 文本公式 `="00042"`。而且，这种格式只用于带前导零的数字字符串；其他字段则采用最少引用，并以 CRLF 结尾。三个彼此关联的约束，没有任何模型能从代码中推导出来。决定性依据存在于团队实际保存决策的地方：过去的开发者对话（27 项任务）、提交消息（28 项），或者最棘手的情况——一段**后来又被另一段对话修改**的对话（6 项）。这样可以检验记忆能否区分已被取代的决策与最终决策。

评分方式也模拟了这个反复推进的过程：尝试修复 → 运行包括隐藏测试在内的完整测试套件 → 将失败信息原样返回，不给提示 → 智能体重试，最多五轮。指标是**纠正次数**，也就是修复错误后被退回重做的次数。每一次都代表人可能被打断一次。整个流程由 pytest 确定性地端到端执行，不使用 LLM 评判。

我们还吸取了一个惨痛教训，定下了另一条规则：早期某次“有记忆”的运行得分和普通运行接近得可疑。深入排查后我们发现，检索一直在悄悄失败——我们测出来的只是安慰剂。从那以后，每次有记忆的运行都会针对每项任务提供机器可检查的证据，证明检索结果确实到达了智能体；否则，这次运行就会作为无数据样本丢弃。

没错，我们是有意把答案预先写入记忆库的，因为这才符合现实前提。在真正的团队中，决定性上下文早已存在于 Git、讨论串和工单里。要测试的是系统能否找到它：跨越用词差异、抵御干扰，并且不返回已被取代的版本。

在运行任何任务之前，设计数据集这件事就教会了我们一些东西。要让决策信息的放置方式贴近现实，我们必须先弄清楚真实团队会把信息放在哪里；诚实的答案总是**Git**。最终有一半任务的决策依据都来自提交消息，因为工程决策往往正是保存在那里。接着我们审视自己的插件，发现了一个令人尴尬的问题：**没有一个插件会摄取 Git 历史**。它们记住了对话和会话，却看不到每个代码库免费提供的最丰富的决策记录。基准测试还没有产生任何数字，就已经发现了架构上的第一个漏洞。

## 3. 运行自家的插件，却输给了什么都没有 {#3-running-our-own-plugin--and-losing-to-nothing}

随后，我们用这套基准测试检验已经发布的产品，得到了今年最有用的一条坏消息。

我们的集成和大多数同类产品一样，会**在每次提示时自动召回记忆**：嵌入消息、检索相似记忆，再把它们注入上下文。按当时的测试套件计算，它每项任务需要纠正 **1.06 次**，而完全不使用记忆只需要 **0.97 次**。记忆反而让智能体表现更差。

复盘让我们认识到两件事，现在我们把它们视为原则。

**零散的记忆会分散注意力。** Recall 返回的是片段：几个相似度不高的片段，各自看似合理，却没有经过综合。对于症状相距甚远的错误（导出错误说的是**行被破坏**，决定性对话说的是**前导零**，两者没有一个共同词），相似度搜索找回的内容只是听起来相像。编程智能体有自己的任务目标和计划；把零散、看似笃定的片段塞给它，并不能帮助它完成任务，反而会让它偏离方向。智能体开始追着记忆里的用词跑，而不是处理错误本身。

**绝不要让热路径承担额外工作。** 每次提示都召回记忆，意味着**每条消息**前都要进行一次检索往返：每一轮都付出延迟并承受噪音，换来的上下文却几乎帮不上忙。编程会话的热路径至关重要：智能体应该读代码、跑测试，而不是等一个即将分散它注意力的记忆服务器响应。

我们曾发布过这种模式的不同变体。基准测试只用一个下午就把它淘汰了。

## 4. Reflect：把智能放在目标所在之处 {#4-reflect-put-the-intelligence-where-the-goal-is}

Hindsight 还有第二种检索模式——**Reflect（反思）**。它更智能：由智能体对**整个**记忆库进行推理，从症状沿线索追溯到决策，检查后续对话是否修改过决策，然后给出综合答案，并逐字引用确切规则和具体值。它不像 Recall 那么快：真正的推理需要几秒，而非几毫秒。这正是它不该出现在每条提示里的原因。

但看看它**适合出现在哪里**。会话的第一条消息很特别：这是你向智能体交代**目标**的时候——那个错误、功能或问题，也是整场会话要围绕的内容。这是深入了解项目历史能为后续整个会话创造价值的时刻。因此，插件会在**第一条提示时反思一次**，缓存综合结果，并在每一轮重新注入。深度理解恰好用在交代任务的地方，之后不再给热路径增加工作量。智能体也不会被限制在这一次推理上：Reflect 仍然**可作为工具调用**。如果会话中途转向新问题，智能体可以自行判断是否再进行一次深度推理，并像其他工具调用一样将调用记录显示在对话记录中。这样，会话一开始就能得到一项 Recall 无法生成的内容：一个**结论**。

> 🧠 来自 Hindsight 记忆：带前导零的数字字符串应写成 `="00042"`——ERP 即使遇到带引号的数字也会强制转换；普通引用格式去年试过，后来已回退。其他字段均使用最少引用、将嵌入的引号加倍，并以 `\r\n` 结束每行。

指标立刻发生了变化，此后每次重新设计架构，改善都保持住了。最终测试包含完整的 61 项任务、三个智能体、两组对照配置，每组各运行三次；这就是我们愿意为之署名的数据：

| 智能体（61 项任务，每项取 3 次运行的平均值） | 每项任务纠正次数：普通运行 | 使用 Hindsight | 纠正次数变化 | 成本变化 | 每项任务耗时 |
| ------------------------------------- | --------------------------- | -------------- | ----------- | ---- | ----------------------------- |
| **Claude Code** · Claude Sonnet 5     | 0.85                        | **0.36**       | **−57%**    | −24% | 84.7s → **75.1s** (**−11%**)  |
| **opencode** · Gemini 3.5 Flash        | 1.20                        | **0.80**       | **−33%**    | −13% | 174.2s → **163.3s** (**−6%**) |
| **Codex CLI** · GPT-5.4 mini           | 1.34                        | **0.47**       | **−65%**    | −52% | 53.6s → **48.6s** (**−9%**)   |

两组配置的解决率都保持在 99–100%，而且每个智能体的每项任务耗时都缩短了——九次有记忆的运行全部快于各自智能体普通运行的平均值。因此，记忆并没有牺牲正确性或速度来换取准确率；它减少了原本需要人类把测试失败反馈给智能体的修正轮次。我们会逐项验证注入是否成功（没有证据证明记忆到达智能体的运行会作为无数据样本丢弃）。每种配置的成本也都降低了，因为一次有针对性的综合取代了大量探索性阅读。按信息来源拆分结果，就能看出这套架构的作用：对于决策只存在于过去对话、没有记忆就无从得知的任务，纠正次数下降了 28–71%；对于依据保存在 Git 的决策，最强的智能体几乎不需要帮助（Claude 会自行挖掘历史），而较弱的智能体则相当于获得了这种能力。我们在早期 Sonnet 测试中首次发现的规律一直延续到最后：智能体越强，剩下的失败就越集中在那些无法猜出、而记忆能提供依据的决策上。

## 5. 知识页：会自我修复的 wiki {#5-knowledge-pages-the-wiki-that-heals-itself}

基准测试艰难推进的同时，另一条工作线也在进行，只是它起因于完全不同的挫败感。

我们一直在尝试 _llm-wiki_ 这个想法：让智能体维护一份关于代码库的 wiki，记录架构说明、约定和决策，并在后续会话中重新阅读。我们用自己的智能体、Hermes 和 Claude Code 试过，遇到了所有人都会遇到的问题：**智能体不会持续更新 wiki**。第一天它兴致勃勃地写页面，第二天就不情愿地修改；到了第二周，wiki 已成了一份排版精美的谎言。让负责做事的智能体同时维护工作文档，正是人类也做不好的苦差事，原因如出一辙。

随后我们突然意识到一件显而易见的事：**Hindsight 已经掌握了这些数据**。每次提交、每场会话、每项决策都会作为提取出的事实流入记忆库；而我们的**心智模型**——保存的综合视图，会随着新事实整合而重新生成——在架构上恰好适合这个场景：现实一旦变化，页面就会重写。它能自我修复，因为修复不再是智能体可能忘记的苦差事，而是记忆引擎本来就在做的事。

但直接使用心智模型会暴露太多底层机制，例如综合查询、触发器和整合设置。谁都不该为了使用 wiki 而操心这些细节。于是我们在上面构建了一层：**知识页**。知识页有层级结构，可以用文件夹组成目录树；呈现给智能体的方式也符合它们熟悉的思维模式：**就像文件系统**。列出页面、读取页面、搜索页面。这是在记忆引擎上提供 wiki 式的界面。

这里值得停下来谈谈一个合理的质疑：_如果答案是目录树中的文档，你们不就是重新发明了文件——而记忆系统存在的目的不就是取代文件吗？_关键在于底层是什么。原始信息写进文件后会逐渐过时：最后编辑的人说了算，矛盾会悄悄累积，内容也永远得不到协调。知识页是建立在经过处理的记忆之上的**映射视图**——就像数据库视图并不是数据表。Hindsight 已经完成了文件无法自行完成的工作：从原始提交、会话和文档中提取事实；去重并清理事实；最重要的是，**通过整合协调相互矛盾的内容**。因此，团队先决定 X、之后又将其修改为 Y 时，页面会写明 Y，并能解释**为什么**，而不是像 wiki 那样把两种说法隔一段话并列保留。原始文档仍然是“当时说过什么”的事实来源；知识页则说明“目前成立的结论”经过协调后是什么。删除一个页面不会丢失任何内容，系统会根据记忆重新生成它。试试看删除 wiki 后还能不能把它恢复出来。

这就是自我修复并非噱头的原因：页面之所以能修复，是因为它们不是存储本身，而是**呈现结果**。只要整合改变了底层认定的事实，记忆引擎就会重新生成页面。

我们还为编程智能体提供了知识页的**混合搜索**（全文检索与语义检索相结合，由服务器端融合，在几十毫秒内返回排序后的片段）。这是智能体**自行选择**调用的工具，调用情况会显示在对话记录中；内容不会被直接塞进智能体的上下文。这样就遵循了第三节总结的专注原则：智能体主动请求的检索结果能帮助它完成任务；它没有请求的检索结果则可能让它偏离方向。

还有一个问题：根据历史综合生成的页面，质量取决于已经摄取的内容；新代码库在记忆库中还没有历史记录。因此，首次打开时会运行一个**探索智能体**：在你自己的智能体 CLI 下启动，执行时间较短、只读且有预算上限的调查，梳理代码库结构并创建初始页面，包括组件图、核心概念、约定与模式、关键决策及其依据、正在推进的计划。从那以后，_Hindsight 会负责维护它们_：每场会话和每次提交都会自动流入记忆库，整合过程会重新综合，页面也就能持续反映真实情况。曾经无法持续维护 wiki 的智能体不必再做这件事；不会遗忘的记忆引擎会代劳。

有了知识页，会话既**更快**也**更准确**。以前需要花几分钟探索代码才能回答的问题（“这里有哪些组件？”、“我们的错误处理约定是什么？”），现在一次可见的工具调用就能解决，并标明答案来自何处：`🧠 From Hindsight memory (Conventions and patterns): …`。

## 今天：0.9.0 {#today-090}

以上功能现在都已发布。

**一个插件，适配每个智能体，只需一条命令：**

```bash
npx @vectorize-io/hindsight-coding-agents install all
```

它会检测你已安装的编程智能体，并以原生方式逐一完成接入：使用钩子或原生插件；宿主需要时则通过 MCP 接入。（`install` 必须指定明确目标：`all`，或 `claude-code` 这样的运行框架名称，因此不会意外接入机器上的所有智能体。）在终端中，它还会询问**记忆应存放在哪里**：Hindsight Cloud、你运行的服务器，或这台机器上的本地守护进程。无需摄取 CLI，也没有同步按钮；记忆会在后台自动建立（先处理近期历史，再逐步深入），会话内容也会自动写回，而状态横幅会告诉你当前进度：

```
Hindsight is tracking the decisions, conventions and history of this repo
  ↳ memory bank “coding-agent::your-repo” · git in sync
```

数据会使用你的密钥发送到**你自己的** Hindsight 服务器，无论服务器是自托管还是云端。完整设置说明——包括各智能体的接入方式、配置以及如何从旧的单智能体插件迁移——请见[编程智能体文档](/sdks/integrations/coding-agents)。

**知识页适用于每个记忆库**，不限于编程场景。你可以在仪表板新增的 Knowledge 视图中浏览和编辑知识页，将它们整理成目录树，通过混合 API 搜索，也可以用记忆库模板一次性创建整套分类目录。如果你的记忆库一直在积累事实，这些事实已经可以用来生成知识页。

数据集今天已公开：[github.com/vectorize-io/sde-bench](https://github.com/vectorize-io/sde-bench)，以及 [Hugging Face](https://huggingface.co/datasets/vectorize-io/sde-bench) 上可直接用于 `load_dataset()` 的镜像。基准测试运行框架、逐项任务结果和完整的强化记录（包括我们自己的架构输给完全不使用记忆的那次运行），将于 2026 年 8 月发布在 [agentmemorybenchmark.ai](https://agentmemorybenchmark.ai)。文档：[编程智能体集成](/sdks/integrations/coding-agents)。

我们原本想用一个营销数字来回答“这真的有帮助吗？”，最后得到的却是一个不同的产品。这一切很值得。
