Hindsight 0.8.5 在 [0.8.4](/blog/2026/06/30/version-0-8-4) 的基础上，重点提升**成本、韧性和运行完整性**：借助 **Anthropic 批处理和提示缓存**以及 **Gemini 为 Reflect（反思）提供的上下文缓存**降低 LLM 开支，并通过**更可靠的模型输出解析**让操作在异常情况下继续运行。本次版本还修复了许多**存入、整合和召回完整性问题**。**自行管理部署的用户应升级**，尤其是大规模运行整合任务的用户。

<!-- truncate -->

- [**降低 LLM 成本**](#lower-llm-costs)：Anthropic Batch API 和提示缓存，以及 Gemini Reflect 的逐步上下文缓存。
- [**提高模型输出的可靠性**](#more-resilient-model-output)：从格式错误或带代码围栏的 JSON 中恢复，避免操作因此失败。
- [**按记忆库控制审计与操作**](#per-bank-audit--operations-control)：按记忆库切换审计日志、删除已终结的操作，并改进数据库配置的安全性。
- [**保障存入、整合和召回的完整性**](#retain-consolidation--recall-integrity)：升级 Hindsight 的原因。

## 降低 LLM 成本 {#lower-llm-costs}

以下三项改动显著降低了提取、整合和 Reflect 所需的 token 开支：

- **Anthropic 消息批处理。** Retain（存入）和整合现在可以通过 Batch API 发起 Anthropic 调用；符合条件的工作负载可享受 **50% 的 token 折扣**。
- **Anthropic 提示缓存。** 系统会缓存重复的提示前缀，因此高负载场景不必在每次调用时都为相同上下文支付全价，批处理中的系统提示也包括在内。
- **Gemini Reflect（反思）上下文缓存。** Reflect 的多步工具调用循环现在会逐步缓存上下文，从而降低使用 Gemini 进行长时间、多轮推理的成本。

如果你经常使用 Anthropic 或 Gemini，这些改进都可以选择启用，而且无需改变 API 的调用方式。

## 提高模型输出的可靠性 {#more-resilient-model-output}

语言模型偶尔会输出被代码围栏包住、遭到截断或略有格式错误的 JSON；过去，这可能导致原本成功的操作失败。0.8.5 增加了多层恢复机制，让一次格式疏漏不再使整次调用付诸东流：

- **最后手段：修复格式错误的 JSON。** 模型返回结构损坏的 JSON 时，Hindsight 现在会在放弃之前尝试修复并解析；如果确实没有可恢复的内容，仍会明确报错。
- **从代码围栏和多余文本中恢复。** 现在可以正确提取带代码围栏、被说明文字包围或内部包含反引号的 JSON，避免内容遭到截断。
- **在适用场景使用更严格的结构化输出。** 每种操作都可以采用严格的 JSON 模式，并支持按单次调用显式选择不使用该模式；规范化的工具结果消息也提高了 OpenAI 兼容服务提供方和 Anthropic 的结构化响应可靠性。
- **更容易排查遭拒绝的调用。** 新增的可选模式会在所有服务提供方返回 4xx 拒绝时，转储完整的请求载荷，让你准确查看服务提供方拒绝了什么。

总体而言，由服务提供方的格式问题导致的 Retain 和 Reflect 失败会减少。

## 按记忆库控制审计与操作 {#per-bank-audit--operations-control}

- **按记忆库记录审计日志。** `audit_log_enabled` 现在采用分层配置，因此你可以单独为每个记忆库启用或关闭审计日志，而不必只在全局控制。
- **删除已终结的操作。** 现在可以删除已完成或已失败的记忆库操作，并可通过控制台管理，以便更好地控制操作历史的规模。
- **更安全的数据库配置。** 数据库 URL 中的百分号编码内容在迁移期间会保留；`pg0://` URL 可以包含用户名和密码凭据；嵌入式 Postgres 会遵循数据库 URL 中的凭据；获取池化连接时，也会正确重新应用会话设置。
- **限定数据库模式的维护例程。** 维护例程会安装到配置的数据库模式中。过期操作清理会通过一次查询发现各个模式，且默认关闭。
- **恢复向量索引。** 如果记忆库的向量索引在数据库恢复、升级或切换向量扩展后（极少数情况下）覆盖不完整，Hindsight 现在会修复索引覆盖范围，确保召回结果完整。可重复运行的 `repair-bank` 管理命令还可以让你按需协调记忆库状态。

## 保障存入、整合和召回的完整性 {#retain-consolidation--recall-integrity}

升级的核心原因，是这一系列修复能够保护已存储的内容，并确保后台任务正常运行：

- **确保实体连接正确。** 关联记忆单元之前会重新确认已消解的实体；规范化实体时也会保留每一组成对共现关系，因此连接会指向正确且已提交的实体。
- **拒绝存储无效文本。** Retain 现在会在存储前拒绝无效的事实文本；过滤这类文本时，仍会保持事实之间的对应关系。
- **原子化创建记忆库。** 延迟创建记忆库现在是原子操作，避免并发首次写入时发生竞态。
- **避免操作卡住。** 操作完成流程与尽力执行的副作用相互隔离，因此 Webhook 或聚合失败不再会让操作一直停留在 `processing` 状态；崩溃恢复尝试也会计入重试预算。
- **可靠的 Webhook 和水位标记。** 即使是处于边界情形或包含零条事实的批次，`retain.completed` Webhook 也会进入队列；无操作的增量刷新会推进水位标记，而不会重新处理数据。
- **增强整合的稳健性。** 去重决策现在通过 JSON 请求并经过规范化；无效操作默认采用保留；并行整合期间的外键冲突也已修复。
- **保留人工维护与元数据的完整性。** 人工维护时会保留记忆库归属；编辑时会刷新搜索向量；发生日期可以通过 `null` 清除；浏览端点会返回完整元数据。

其他值得关注的改动：

- **列表端点支持标签筛选。** `list_memories` 和 `list_memory_units` 现在接受标签筛选条件。
- **调整 Recall（召回）。** 可选的 BM25 查询词数量上限、保留的组合图激活分数，以及按事实类型限制的实体扩展范围，让检索结果更可预测。
- **完善 Reflect。** 限制答案长度，将扩展后的记忆与对应的记忆正确配对，让水平分隔线留在围栏代码块内，并在服务提供方调用中保留记忆库归属。
- **改进日期解析。** 现在会优先采用最强的日期匹配；日-月-年格式的日期也不再被合并为整个月。
- **安全更新。** 已移除存在漏洞的 API 运行时软件包，并出于安全考虑升级了若干依赖项。
