Hindsight 0.5.3 聚焦于多租户公平性和运行韧性。新增的观测整合回合限制可防止单个记忆库独占工作进程槽位；心智模型采用更智能的增量刷新；OpenAI Agents SDK 获得了原生支持；此外，一系列修复也增强了文件存入、迁移路径和 GPU 重排序的可靠性。

<!-- truncate -->

- [**观测整合回合限制**](#consolidation-round-limit)：限制每轮处理的记忆数量，防止单个记忆库占满工作进程。
- [**OpenAI Agents SDK 集成**](#openai-agents-sdk-integration)：为 OpenAI Agents SDK 提供原生记忆工具。
- [**心智模型增量刷新**](#mental-model-delta-refresh)：采用更小的结构化更新，避免完整重写。
- [**CLI 连接配置**](#cli-connection-profiles)：通过命名配置在不同环境间切换。
- [**工作进程公平性与可靠性**](#worker-fairness--reliability)：按租户公平领取批次、幂等提交任务，并支持由扩展触发重新入队。
- [**可靠性修复**](#reliability-fixes)：涵盖迁移链、GPU 崩溃、Ollama、文件存入等方面。

## 观测整合回合限制 {#consolidation-round-limit}

当记忆库中有数千条尚未整合的记忆时（例如批量摄取之后），整合作业可能会占用一个工作进程槽位数分钟，导致其他记忆库无法获得处理机会。新增设置 `HINDSIGHT_API_CONSOLIDATION_MAX_MEMORIES_PER_ROUND`（默认值：100），用于限制单个观测整合回合处理的记忆数量。达到上限后，作业会让出槽位并重新入队，让其他记忆库获得处理机会。为避免重复工作，心智模型刷新会推迟到最后一轮执行。

此设置可通过配置 API 按记忆库配置，因此高优先级记忆库可以不设上限（`0`），而共享部署则继续采用默认上限。

## OpenAI Agents SDK 集成 {#openai-agents-sdk-integration}

新增的 `hindsight-openai-agents` 包提供用于 Retain（存入）、Recall（召回）和 Reflect（反思）的 `FunctionTool` 实例，可直接接入 OpenAI Agents SDK 的 `Agent`。只需调用一次 `configure()` 完成配置，就可以在任意位置创建工具，其余工作由 SDK 的异步运行时处理。该包开箱即支持按需选择工具、按标签限定范围以及全局配置。

```python
from hindsight_openai_agents import configure, create_tools

configure(base_url="http://localhost:8888", bank_id="my-bank")
tools = create_tools()
agent = Agent(name="assistant", tools=tools)
```

## 心智模型增量刷新 {#mental-model-delta-refresh}

心智模型刷新现在会使用结构化增量操作（插入、更新、删除和重新排序章节），而不是从头重新生成整份文档。这意味着 LLM 调用规模更小、成本更低，以观测为依据的心智模型内容变动更少，历史记录也能更清楚地显示具体改动及其原因。控制台中的 UI 也已更新，现在会显示待更新状态信号和每次刷新的历史快照。

## CLI 连接配置 {#cli-connection-profiles}

CLI 现在支持通过 `-p`/`--profile` 使用命名连接配置。在 `~/.hindsight/profiles.toml` 中定义不同的基础 URL、API 密钥和默认记忆库，然后只需一个标志就能在本地、预发布和生产环境之间切换。无需再来回管理环境变量。

## 工作进程公平性与可靠性 {#worker-fairness--reliability}

以下三项变化改进了工作进程分配和处理任务的方式：

- **按租户公平轮换。** `claim_batch` 现在会以轮询方式遍历各租户的 schema，因此即使负载分布不均，也不会有单个租户独占工作进程槽位。
- **幂等提交任务。** `submit_task` 现在可以妥善处理载荷已设置的情况，避免并发调用方重复提交或提交无效任务。
- **由扩展触发重新入队。** 新增的 `DeferOperation` 异常允许扩展明确要求将任务重新入队，而不是将其标记为失败。这适用于速率限制后的退避等待或等待依赖项就绪等场景。

## 可靠性修复 {#reliability-fixes}

- **恢复迁移链。** 从 v0.4.22 升级到 v0.5.x 现在会遵循正确的迁移路径，无需手动干预。
- **修复 Apple Metal GPU 崩溃。** jina-mlx 重排序模型现在会串行执行 Metal GPU 操作，以避免在 macOS 上发生 SIGSEGV 崩溃。
- **Ollama 思考模式。** Ollama 原生调用现在会明确禁用“思考”模式，修复了响应中包含推理过程的问题。
- **TEI 重排序模型超时。** TEI 重排序模型的超时时间现在可以通过 `HINDSIGHT_API_RERANKER_TEI_HTTP_TIMEOUT` 配置；超时发生时也会显示更清楚的错误信息。
- **文件存入。** 修复了上传失败和遗留的存入操作，并确保文件存入 API 正确处理 `timestamp` 字段。
- **孤立观测。** 如果源记忆在整合过程中被删除，整合操作现在不会再创建孤立观测。
- **心智模型 `max_tokens`。** 配置的 `max_tokens` 现在会在心智模型刷新时正确传递。
- **控制台中的记忆库 ID。** 包含特殊字符的记忆库 ID 现在会在整个流程中正确编码到 URL 中。
- **LLM 重试默认值。** 默认的 LLM 最大重试次数从 10 次降至 3 次，以避免服务提供方故障时造成长时间延迟。
- **按记忆库配置 Recall 预算。** 现在可以按记忆库配置 Recall 推理预算映射，从而更精细地控制成本。
- **观测整合详情。** 现在可以在控制台中查看失败的观测整合数量，并进一步查看详情。
- **JSON 日志中的租户字段。** JSON 日志现在会包含租户标识符，并支持配置字段允许列表。
