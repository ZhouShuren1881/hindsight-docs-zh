“智能体记忆”听起来很抽象，直到你发现，它其实是用同一种办法解决十几种不同问题。只要智能体需要记住当前会话之后的信息，而每次启动又都从空白状态开始，就存在一个需要记忆填补的缺口。[Hindsight](https://vectorize.io/hindsight) 在所有场景中都用相同的三个操作来填补这个缺口：`retain` 用于存入，`recall` 用于召回，`reflect` 用于基于记忆推理。不同用例之间的变化不在于这些基本操作，而在于记忆属于谁，以及它会在哪里发挥作用。

下面介绍人们实际构建的智能体记忆用例，每个用例都附有具体示例。

<!-- truncate -->

## 1. 了解你代码库的编程智能体 {#1-coding-agents-that-know-your-codebase}

这是最常见的用例，因为编程智能体的健忘最明显。每次开启新会话，智能体都得重新学习：你用的是 `uv` 而不是 pip，API 基于 FastAPI 和 asyncpg，以及你上个月决定弃用消息队列。持久记忆会保存这些约定、决策和过去遇到的错误，让智能体随着你在代码库中工作的时间增长而变得更有用。

Hindsight 已经接入了大多数常见的编程工具：Aider、Zed、Cursor、Claude Code、Roo Code 和 ZCode。记忆库通常按代码仓库划分范围，因此其中的记忆与*这个*代码库有关。由于记忆存储独立于任何一种工具，你在一个编辑器中积累的上下文也能在下一个编辑器中使用。

## 2. 带有用户专属记忆的面向客户产品 {#2-customer-facing-products-with-per-user-memory}

当产品开始服务多位用户时，记忆就成了数据模型的设计决策，而不是一个功能开关。每位用户都需要各自隔离的记忆，而且这些记忆绝不能泄漏到其他租户。这意味着要为每位用户设置独立的记忆库，因此一开始就划清边界非常重要。

一位构建者分享了他们如何从一开始就实现这一点：[从第一天起便支持多用户 AI 记忆的金融产品](/blog/2026/04/13/hindsight-financial-ai-memory-customer-story)。每位用户的历史都限定在自己的记忆库中，助手因此能记住此人的情况，而不会看到其他人的信息。这适用于任何需要在每次会话中都专门记住*你*的助手。

## 3. 客服与账户助手 {#3-support-and-account-assistants}

客服是最能体现记忆价值的场景。客户每次回来时，都不该再次解释自己的设置、套餐或上周提出的问题。由记忆支持的助手会在回答前召回账户历史，让对话从上次停下的地方继续，而不是重新开始。

这种场景通常按客户划分记忆，并结合 `tags` 在同一账户内区分账单、技术问题等主题。`reflect` 在这里也很有用：“这个账户的整体状况如何？”属于综合生成问题，而不是查找问题。

## 4. 能跨通话记忆的语音智能体 {#4-voice-agents-that-remember-across-calls}

语音场景让记忆变得更重要，因为来电者希望智能体认得自己。没人愿意把名字、订单号和问题再次告诉昨天刚接待过自己的语音智能体。Hindsight 可与 Vapi、Pipecat 等语音技术栈集成，让智能体在通话开始时就知道来电者是谁，以及上次发生了什么。

处理方式与文本相同：通话开始时召回相关历史，结束时存入通话中发生的事。区别在于，语音对话中忘记信息会显得格外失礼。

## 5. 聊天平台上的智能体 {#5-chat-platform-agents}

运行在 Slack、Discord 或 Telegram 中的智能体有一个特殊的记忆难题：许多用户、许多频道，却只有一个机器人。你通常会希望机器人跨频道记住某个人，或者让它记住一个频道中不同人的上下文，并且需要选择采用哪种方式。OpenClaw 等集成可以按用户或频道划分范围，让机器人的记忆符合团队的实际工作方式。

这时，记忆库范围和标签就能发挥作用：用共享的团队记忆库保存项目上下文，为个人偏好分别设置用户记忆库，或者用一个带标签的记忆库同时按这两个维度筛选。

## 6. 自行构建的各类智能体 {#6-any-agent-you-build-yourself}

并非所有智能体都是现成工具。如果你基于某个框架构建智能体，记忆应该即插即用，而不该成为一个独立项目。Hindsight 已集成到许多框架中，包括 LangGraph、CrewAI、Pydantic AI、Google ADK、OpenAI Agents SDK、LlamaIndex 等；对于任何支持 MCP 的框架，也可以直接使用 MCP。

价值在于，你无需自行构建记忆系统。只要针对记忆库调用 `retain` 和 `recall`（需要综合分析时再调用 `reflect`），提取、实体解析、整合和排序检索等复杂工作就会由 Hindsight 处理。

## 7. 共享学习成果的多智能体系统 {#7-multi-agent-systems-that-share-what-they-learn}

当你运行一个由规划者、研究者和审阅者等智能体组成的团队时，它们彼此协作、利用对方的成果会带来有趣的行为。让它们访问同一个共享记忆库，研究者存入的事实就能被审阅者通过 `recall` 取回。这样，记忆就成了团队共享的认知，而不是每个智能体各自的私人笔记。

另一方面，需要隔离的智能体就不应共享上下文，而应使用各自的记忆库。哪些智能体共享一个记忆库，是整个设计的关键。我们还写了一份[正确配置记忆库的实践指南](/blog/2026/07/16/bank-strategy-agent-memory)。

## 8. 根据记忆采取行动的自动化流程 {#8-automations-that-react-to-memory}

记忆不只适用于聊天。借助 Zapier 和 n8n，工作流可以在事件触发时存入信息，稍后再召回这些信息并据此决策。表单提交会成为持久事实；定时作业可以根据一周内积累的记忆进行反思并生成摘要。这样，记忆就成了自动化流程中的核心步骤，而不是后来附加的数据库。

## 共同点 {#the-common-thread}

这些并非不同的产品，而是同一组基本操作：在记忆库上调用 `retain`、`recall` 和 `reflect`，只是范围和呈现方式不同。编程智能体按代码仓库划分范围，产品按用户划分，团队共享记忆库，自动化流程则根据事件写入和读取。一旦把智能体记忆理解为“这份记忆归谁所有，又会在哪里发挥作用”，这些用例就不再像一张清单，而更像一种可以应用到任何场景的能力。

如果你的智能体每次会话都从零开始，那它就有记忆用例。接下来只需决定如何划分记忆范围。
