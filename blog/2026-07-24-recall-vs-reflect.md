您的智能体通过`retain`写入智能体记忆。但是有两种方法可以读回它，并且它们经常被混淆，因为两者都接受查询并返回有用的东西。 `recall` 和 `reflect` 不是同一事物的两个名称。其一是搜索引擎。另一个是分析师。如果选错了，您要么为不需要的 LLM 电话付费，要么在您想要答案时得到一堆原始事实。

区分它们的最简洁方法是一个问题，而代码恰好是这样描述它们的：**​​使用`recall`“我对X说了什么？”和 `reflect` 代表“我应该对 X 做什么？”**

<!-- truncate -->

## 概览 {#tldr}

- **`recall` 检索。** 它找到与查询相关的记忆并将它们作为事实的排名列表返回。没有LLM。亚秒级。便宜的。
- **`reflect` 负责推理。** 它是一种智能体，可以跨多个级别搜索您的记忆，并使用 LLM 来合成答案。慢点。模型调用费用。
- 问自己：你想要*事实*，还是*从事实得出的结论*？这就是整个决定。
- 他们不是对手。 `reflect` 在底层使用 `recall` 作为其基本事实。

## 记忆召回：记忆搜索引擎 {#recall-a-search-engine-for-your-memory}

`recall` 是纯粹的检索。你向它发出一个查询，它就会返回重要的记忆，并进行排名。它没有做的是思考它们。

在幕后它不仅仅是矢量搜索。对于每种事实类型，Hindsight 并行运行多种检索策略：语义向量搜索、BM25 关键字搜索和链接实体上的图激活，以及当查询具有时间元素时的时间传递。它将那些与倒数排名融合融合，使用交叉编码器（默认为本地）对幸存者重新排名，并修剪您的token预算。结果是事实的排名列表，每个事实都有其类型、时间戳和实体。

在两个操作之间进行选择的重要一点是：**`recall`从不调用LLM。**整个管道是嵌入加上重排序器，默认情况下都是本地的。这就是为什么它可以在不到一秒的时间内返回并且几乎不花费任何费用。这是你可以在每一回合都进行的操作。

两个旋钮塑造它的形状：

- **`budget`** (`low`, `mid`, `high`) 控制搜索的深度，默认情况下大约为 100、300 或 1000 个单位的图遍历。预算越高，发现的东西就越多，工作量也稍微多一些。
- **`max_tokens`** 限制返回的数量。 Hindsight 返回事实，直到达到预算并在超出预算之前停止。

您还可以获得查询时间过滤器：`tags`和`tags_match`按标签范围，以及`query_timestamp`来锚定相对日期，例如“上周”和偏差新近度。完整的参数列表位于[记忆召回API参考](/developer/api/recall)。

到达`recall`。它回答“我对此了解什么？”并把原材料交给你。

## 反思：一位分析师为你解读你的记忆 {#reflect-an-analyst-that-reads-your-memory-for-you}

`reflect` 是一种不同的动物。它不只是检索，它会*推理*。给它一个问题，它会运行一个代理循环：它决定要寻找什么，在多个级别上搜索你的记忆，然后LLM根据它发现的内容写出一个综合答案。

它的检索是分层的，最好的来源优先：

1. **心智模型**：用户策划的、自我刷新的智能体经常询问的主题摘要。
2. **观察**：从许多原始事实中提炼出的经过整合的、有证据支持的知识。
3. **原始事实**：通过`recall`拉取，作为地面事实，以在更高级别过时时进行验证。

所以`reflect`不是`recall`的竞争对手。它是建立在它之上的。 `recall`是保持`reflect`诚实的底层。

因为循环中有一个LLM，`reflect`可以做`recall`结构上不能做的事情：

- **合成。** 它返回书面答案，而不是列表。 “我应该对X做什么”，“总结一下我们这个月学到的东西”，“这个用户的总体偏好是什么”。
- **结构化输出。** 传递 `response_schema` ，它会返回一个与您的 JSON 模式匹配的经过验证的对象，因此您可以将结论直接输入代码中。
- **引用来源。** 设置`include_based_on`，它会返回一个 `based_on` 块，命名确切的记忆、心智模型和它实际使用的指令。这些引文是根据检索到的内容进行验证的，因此它无法发明来源。

它的旋钮也有不同的含义。 `budget` 这里控制智能体获得多少次迭代，因此它在回答之前探索的彻底程度（`high` 更深，成本更高）。 `max_tokens` 仅限制最终书面答案的长度，而不限制其一路检索的数量。

权衡是：`reflect`进行一个或多个模型调用，因此速度较慢并且需要花费真正的token。 Hindsight 在循环中缓存稳定的提示前缀以缓解这种情况，但反思本质上比查找更昂贵。您不必在每次击键时都运行它。每个选项都记录在[反思 API 参考](/developer/api/reflect)中。

## 一张表的区别 {#the-difference-in-one-table}

||`recall`|`reflect`|
|---|---|---|
|职责|检索相关记忆|跨记忆推理并回答问题|
|LLM？|否，仅嵌入 + 重排序器|是的，带有LLM的代理循环|
|返回|事实排名列表|综合答案（可选结构）|
|速度和成本|亚秒级，近乎免费|速度较慢，需要模型调用|
|`budget` 控制|搜索深度|智能体探索得有多彻底|
|`max_tokens` 控制|返回事实的大小|最终答案的长度|
|引用来源|事实*是* 结果|`include_based_on` 返回经过验证的来源|
|最适合|“我对X说了什么？”|“对于X我该怎么办？”|

## 如何实际选择 {#how-to-actually-choose}

决定几乎总是这样：**你想要事实，还是从事实得出的结论？**

在以下情况下使用`recall`：

- 您正在组装上下文并在模型回答之前将其放在模型前面。这是常见的情况，而且应该便宜且频繁。
- 您想要向用户显示原始记忆，或者将确切的事实输入确定性逻辑。
- 延迟和成本很重要，这在每回合热路径上总是如此。

在以下情况下使用`reflect`：

- ​​你想要的是答案，而不是证据。总结、分析、建议、简报。
- 您需要通过`response_schema`为代码整形的输出。
- 你想要在整个记忆中引用、可验证的推理，而不仅仅是最匹配的事实。
- 调用是偶尔的，不是每次都调用。每日摘要、入职摘要、“我们对该帐户了解多少”面板。

健康的智能体同时使用两者。 `recall` 持续且廉价地接地普通转弯。当你真正需要综合时，`reflect`就会介入，而当它需要综合时，它会依靠`recall`来保持基础。当您需要事实时进行搜索。当你想要答案时询问。

## 常见问题 {#frequently-asked-questions}

**`recall`使用LLM吗？**
没有。检索是嵌入加上交叉编码器重排序器，默认情况下都是本地的，这就是为什么它可以在不到一秒的时间内返回并且几乎不需要任何成本。

**`reflect`比`recall`慢吗？**
是的。 `reflect` 使用一个或多个 LLM 调用运行代理循环，因此速度较慢并且需要花费真实的token。 `recall` 是一个查找。当你需要合成时使用`reflect`，而不是每回合都使用。

**`reflect`可以返回结构化输出吗？**
是的。传递一个 `response_schema` ，它会返回一个根据您的 JSON 模式验证的对象，准备好输入代码。

**`reflect`是否引用其来源？**
是的。设置`include_based_on`，它会返回准确的记忆、心智模型和它使用的指令，并根据实际检索到的内容进行验证，因此它无法发明引文。
