![recall 检索相关事实，reflect 基于这些事实进行推理并综合得出答案](/img/blog/recall-vs-reflect.png)

智能体通过 `retain` 将内容写入智能体记忆。但读取记忆有两种方式，人们经常把它们混为一谈，因为两者都接受查询，也都会返回有用内容。`recall` 和 `reflect` 并不是同一件事的两种叫法：一种是搜索引擎，另一种是分析师。选错了，要么为不需要的 LLM 调用付费，要么在你想要答案时只拿到一堆原始事实。

区分两者最简单的方式是问自己一个问题，而且代码对它们的描述恰好也是如此：**“关于 X，我说过什么？”用 `recall`；“关于 X，我应该怎么做？”用 `reflect`。**

<!-- truncate -->

## 概览 {#tldr}

- **`recall` 负责检索。** 它会找到与查询相关的记忆，并按相关性排序后以事实列表的形式返回。不调用 LLM。通常不到一秒。成本很低。
- **`reflect` 负责推理。** 它会像智能体一样在多个层级搜索记忆，并调用 LLM 综合得出答案。速度较慢，也会产生模型调用成本。
- 问问自己：你要的是*事实*，还是*根据事实得出的结论*？这就是选择的关键。
- 它们不是竞争关系。`reflect` 会在底层使用 `recall`，并以其结果作为事实依据。

## Recall：智能体记忆的搜索引擎 {#recall-a-search-engine-for-your-memory}

`recall` 只负责检索。你向它提供查询，它就会按相关性返回重要记忆；它不会进一步分析这些记忆。

它在底层做的不只是向量搜索。对于每种事实类型，Hindsight 都会并行运行多种检索策略：语义向量搜索、BM25 关键词搜索、在关联实体上进行图激活；如果查询涉及时间，还会执行时间检索。系统会通过倒数排名融合（Reciprocal Rank Fusion）合并结果，再用交叉编码器（默认在本地运行）对候选结果重新排序，最后按 token 预算截取。结果是按相关性排序的事实列表，每条事实都带有类型、时间戳和实体信息。

选择这两种操作时，最重要的一点是：**`recall` 绝不会调用 LLM。** 整条处理流程只使用嵌入模型和重排序器，而且默认都在本地运行。因此它通常不到一秒就能返回，成本也很低。你可以在每一轮对话中都使用它。

有两个参数会影响检索：

- **`budget`**（`low`、`mid`、`high`）控制搜索深度，默认大约对应 100、300 或 1000 个图遍历单元。预算越高，找到的内容通常越多，计算量也会略有增加。
- **`max_tokens`** 限制返回内容的 token 数量。Hindsight 会持续返回事实，直到达到预算上限，并在超出上限前停止。

你还可以在查询时使用过滤条件：用 `tags` 和 `tags_match` 按标签限定范围；用 `query_timestamp` 为“上周”之类的相对日期提供参照时间，并调整结果的新近程度。完整参数列表请参阅 [Recall API 参考](/developer/api/recall)。

当你想在模型回答前把相关上下文载入提示词，或向用户展示实际存储的事实时，可以使用 `recall`。它回答的是“我对此了解什么？”，并把原始材料交给你。

## Reflect：替你解读记忆的分析师 {#reflect-an-analyst-that-reads-your-memory-for-you}

`reflect` 则不同。它不只是检索，还会*推理*。你向它提出问题后，它会运行智能体循环：先判断要查找什么，再跨多个层级搜索记忆，最后由 LLM 根据找到的内容撰写综合答案。

它按层级检索，并优先使用较高层级的信息来源：

1. **心智模型**：由用户整理、会自行刷新的主题摘要，涵盖智能体经常被问到的内容。
2. **观测**：从许多原始事实中整合而来、有证据支持的知识。
3. **原始事实**：通过 `recall` 获取，用作事实依据；当较高层级的信息待更新时，可用它们进行核验。

因此，`reflect` 并不是 `recall` 的竞争对手，而是构建在 `recall` 之上的能力。`recall` 是底层依据，帮助 `reflect` 保持可靠。

由于流程中有 LLM 参与，`reflect` 可以完成一些 `recall` 在机制上无法完成的工作：

- **综合信息。** 它返回书面答案，而不是列表。例如：“关于 X，我应该怎么做？”“总结一下我们这个月学到的内容。”“这个用户的总体偏好是什么？”
- **结构化输出。** 传入 `response_schema` 后，它会返回一个符合 JSON 模式并经过验证的对象，你可以直接在代码中使用这个结论。
- **引用来源。** 设置 `include_based_on` 后，它会返回一个 `based_on` 区块，列出实际使用的具体记忆、心智模型和强制指令。这些引用会根据已检索到的内容进行验证，因此它无法凭空编造来源。

这里的参数含义也不同。`budget` 控制智能体可以进行多少轮迭代，也就是它在回答前探索得有多充分（`high` 会探索得更深入，成本也更高）。`max_tokens` 只限制最终书面答案的长度，不限制过程中检索的内容量。

这种权衡正是两者的区别所在：`reflect` 会进行一次或多次模型调用，因此速度较慢，也会实际消耗 token。Hindsight 会在循环中缓存稳定的提示词前缀，以降低开销，但反思本质上比查找更昂贵。它不适合每次按键都运行。所有选项请参阅 [Reflect API 参考](/developer/api/reflect)。

## 一张表看懂区别 {#the-difference-in-one-table}

| | `recall` | `reflect` |
|---|---|---|
| 作用 | 检索相关记忆 | 基于记忆进行推理并回答问题 |
| 是否使用 LLM？ | 否，仅使用嵌入模型和重排序器 | 是，通过含 LLM 的智能体循环完成 |
| 返回内容 | 按相关性排序的事实列表 | 综合答案（可选结构化输出） |
| 速度与成本 | 通常不到一秒，成本极低 | 速度较慢，会产生模型调用成本 |
| `budget` 控制 | 检索深度 | 智能体探索的充分程度 |
| `max_tokens` 控制 | 返回事实的总量 | 最终答案的长度 |
| 引用来源 | 事实本身就是结果 | `include_based_on` 返回经过验证的来源 |
| 适用场景 | “关于 X，我说过什么？” | “关于 X，我应该怎么做？” |

## 如何选择 {#how-to-actually-choose}

选择时几乎总是只需想清楚一件事：**你要的是事实，还是根据事实得出的结论？**

在以下情况下使用 `recall`：

- 你要整理上下文，在模型回答前提供给它。这是最常见的场景，应该以低成本、高频率运行。
- 你想向用户展示原始记忆，或把准确事实交给确定性逻辑处理。
- 延迟和成本很重要；在每轮都会经过的关键路径上尤其如此。

在以下情况下使用 `reflect`：

- 你要的是答案，而不是证据，例如摘要、分析、建议或简报。
- 你需要通过 `response_schema` 将输出整理成代码可用的结构。
- 你需要基于整个记忆库进行有来源、可验证的推理，而不只是查看匹配度最高的事实。
- 这是偶尔执行的调用，而非每轮都调用，例如每日摘要、入职概览，或“我们对这个账户了解什么”的面板。

成熟的智能体会同时使用两者。`recall` 持续、低成本地为日常对话提供依据；真正需要综合信息时，`reflect` 再介入，并依靠 `recall` 保持答案有据可依。要事实时就检索，要答案时就提问。

## 常见问题 {#frequently-asked-questions}

**`recall` 会使用 LLM 吗？**
不会。检索只使用嵌入模型和交叉编码器重排序器，默认都在本地运行，因此通常不到一秒就能返回，成本也很低。

**`reflect` 比 `recall` 慢吗？**
是的。`reflect` 会运行智能体循环，并进行一次或多次 LLM 调用，因此速度较慢，也会实际消耗 token。`recall` 只是查找。需要综合信息时再使用 `reflect`，而不是每轮都调用。

**`reflect` 能返回结构化输出吗？**
可以。传入 `response_schema` 后，它会返回一个符合 JSON 模式并经过验证的对象，可直接用于代码。

**`reflect` 会引用来源吗？**
会。设置 `include_based_on` 后，它会返回实际使用的具体记忆、心智模型和强制指令，并依据实际检索到的内容进行验证，因此不会凭空编造引用。
