![Hindsight 如何按预算而不是按文档大小限制 Retain 的内存：按窗口计算大小、流式分块和流式拆分子批次，让不同大小文档的峰值内存保持稳定](/img/blog/retain-memory-budget.png)

过去，将一份大文档通过 Retain（存入）操作写入 [Hindsight](https://hindsight.vectorize.io) 所需的内存与*文档*大小成正比，而不是与实际处理的工作量成正比。输入 90 MB 的正文，峰值内存分配就会随之增长；对于需要规划容量并安排并发任务的工作进程来说，这正是我们不希望看到的增长方式。Hindsight 0.9.2 重构了 Retain 管道的前半段，让处理 4 MB 到 90 MB 的正文时峰值内存都保持稳定，并增加了一个明确预算，便于据此规划工作进程容量。

有意思的是，内存实际消耗在了哪里？答案和大家原先猜想的不同。

<!-- truncate -->

## 概要 {#tldr}

- 存入大文档时，持有的状态大小与**文档**成正比，而不是与工作集成正比。峰值内存会随输入大小增长。
- 大家通常怀疑的对象（以 `list[float]` 保存的嵌入向量）**并非**原因。测量结果显示，真正占用内存的是两个*处理整个文档*的操作；它们运行时还没有生成任何事实或嵌入向量。
- 三项改进让任意大小文档的峰值内存都**保持稳定**：按窗口计算 token 数、流式处理文本分块，以及流式拆分子批次。
- 现在内存上限有了**明确预算**：`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`（默认值为 `128`）。无论文档大小如何，都可以据此规划工作进程容量。
- 提交的正文是唯一仍随输入大小增长的部分，也是无法再降低的下限：必须保留正文，才能将其写入 `documents.original_text`。
- 所有改进均在 **0.9.2** 中发布。

## 误判的原因 {#the-misdiagnosis}

当峰值内存随输入大小增长时，人们往往会先怀疑最显眼、规模最大的结构。这里被怀疑的是嵌入向量：提取出的事实带有向量，而向量存放在 `list[float]` 中；Python 会为每个浮点数创建对象，所以看起来它们肯定占用了大量内存。

我们没有猜测，而是用 `tracemalloc` 进行了测量。事实并不是问题所在。流式管道早已将事实数量限制在 `retain_chunk_batch_size` 个文本分块内，大约是 1,700 条事实、约 21 MB；文档再大，这个占用也不会增加。

真正的内存开销来自 Retain 一开始执行的两个操作。那时还没有事实或嵌入向量生成，但每个操作都会在内存中构造一个与整个文档同等规模的数据结构：

| 操作 | 45 MB 正文，改进前 | 改进后 |
| --- | --- | --- |
| **计算大小**（`count_tokens`） | 384.7 MB | 9.6 MB |
| **文本分块**（`split_text`） | 200.8 MB | 0.0 MB |

计算 45 MB 正文的大小时分配了 385 MB；文本分块又分配了 200 MB。这两步都发生在管道生成第一条事实之前。峰值内存正是由此产生的。

## 改进 1：逐窗口计算正文大小 {#fix-1-size-the-body-a-window-at-a-time}

为了检查正文是否超过批次预算，原先的 token 计数会对整份文档进行分词，并为每个 token 创建一个装箱的 Python `int` 对象。对于含 11.6 M 个 token 的正文，这意味着一次要同时持有 11.6 M 个整数对象，纯粹是为了得到计数。

`count_tokens_windowed()` 每次处理一兆字节的正文，并累加计数，因此最多只需持有一个窗口所包含的 token。计算大小时的峰值内存由 384.7 MB 降至 9.6 MB，并且现在无论文档多大都保持稳定。

“按窗口处理”有意接受了一项权衡：逐窗口计数可能漏掉跨越窗口边界的 token。在 11.6 M 个 token 中，实际会漏掉约 45 个。每个调用方要么把计数与批次预算进行比较，要么只记录这个计数，因此实践中无法察觉这 0.0004% 的少计；这正是按窗口处理安全可行的原因。

## 改进 2：流式生成分块，不再一次性构造全部分块 {#fix-2-stream-the-chunks-instead-of-materializing-them}

文本分块原先使用 LangChain 的 `RecursiveCharacterTextSplitter`。它会一次性把文档的所有分块作为列表返回。这个列表相当于再次保存了整份文档，只是文档被切成了多个部分，并且仍与原文同时占用内存。

现在，`iter_chunks()` 会逐个流式生成文本分块。它还惰性地重新实现了 Retain 所依赖的分块器配置。文本分块的峰值内存由 200.8 MB 降至实际上为零，并且不再随文档大小增长。

这项重新实现值得特别说明，因为分块器不能在不知不觉中出现哪怕*一点点*偏差：边界一旦移动，所有存储文档都会在后续处理时被悄悄重新分块。因此，**LangChain 并未从代码库中移除，只是不再走运行时路径。**它仍作为参照，由差异测试逐个分隔符层级对比我们的流式分块器，确保分块边界与 LangChain 自身的输出一致。（这也是为什么 `langchain-core` 和 `langsmith` 仍在依赖列表中，尽管请求处理时没有代码导入它们。）

## 改进 3：也流式拆分子批次 {#fix-3-stream-the-sub-batch-split-too}

还剩下一种针对整个文档构造的数据结构。正文太大、无法在一次 Retain 操作中处理时，系统会把它拆成多个子批次；原来的分割器会一次性返回所有子批次。这些切片*合起来就是*被切开的文档：处理 45 MB 正文时会产生 45.5 MB 的切片，并在整个 Retain 操作期间与提交的正文同时留在内存中。因此，管道前半段的峰值内存和实时内存仍随输入增长，相当于同时持有两份文档。

现在，`iter_sub_batches()` 会逐个生成子批次，并在每个子批次到达时进行筛选、计算内容哈希和标记，从而使峰值内存不再随文档大小增长：

| 峰值内存（拆分 + 筛选） | 16 MB 正文 | 45 MB 正文 | 90 MB 正文 |
| --- | --- | --- | --- |
| **改进前** | 55.6 MB | 113.9 MB | 204.4 MB |
| **改进后** | 25.5 MB | 25.5 MB | 25.6 MB |

实时内存也同样下降：处理 45 MB 正文时，从 68.9 MB 降至 23.5 MB，并保持稳定。唯一仍随文档大小增长的是提交的正文本身，这是无法再降低的下限：必须保留正文，才能将其写入 `documents.original_text`。

让循环改为流式处理也改变了一项不变量。以前持有完整列表时，判断 `is_last` 很简单；现在则要在生成器中向前查看一项，因为 Retain 循环必须知道哪个子批次是最后一个：事务发件箱回调只会在最后一个子批次的事务内部触发，其他事务中都不会触发。此次改动之前加入的测试覆盖了这项不变量。

## 现在有了明确的内存上限 {#the-bound-is-now-explicit}

重构内部实现让峰值内存保持稳定；增加配置后，这个上限就成了可以据此规划的具体数值。`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`（默认值为 `128`）限制单次 Retain 操作可以持有多少已提取但尚未写入的状态。无论文档大小如何，单次 Retain 的峰值内存大致就是这个数值；将其乘以并发 Retain 槽位数，就能规划工作进程容量。超过预算时，提取过程会等待写入路径跟上，而不是继续增长。

这取代了一个看起来像内存上限、实际上并不可靠的限制。`HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE` 原先已经限制了同时处理的文本分块数量，但只有在每个项目的内存开销可预测时，按*数量*限制才能约束内存；而文本分块的开销并不固定，因为每个分块所含的事实数量取决于提取器。以 MB 为单位的预算才是可靠的上限。将 `RETAIN_MEMORY_BUDGET_MB` 设为 `0`，即可恢复原先仅按数量限制的行为。

## 改进结果 {#the-result}

总的来说，Retain 管道的前半段不再随文档大小增长。三个需要构造整个文档的数据结构变成了三个流式处理步骤：

| 改进 | 变更 | 45 MB 正文的峰值内存，改进前 → 改进后 |
| --- | --- | --- |
| 按窗口计算大小 | 每次计算一个窗口，而不是为每个 token 创建一个装箱整数 | 384.7 MB → 9.6 MB |
| 流式文本分块 | 逐个生成分块，不再一次性构造整个列表 | 200.8 MB → 0.0 MB |
| 流式拆分子批次 | 逐个生成经过筛选的子批次 | 113.9 MB → 25.5 MB |

处理 4、16、45 和 90 MB 的正文时，峰值内存现在都保持稳定，并由明确预算约束，而不是取决于用户提交的内容大小。此外，计算大小和文本分块现在还稍快了一些，因为这两步都不再构造巨大的临时数据结构。

## 具体规划工作进程容量 {#sizing-a-worker-concretely}

既然峰值内存现在取决于预算，而不是输入大小，规划 Retain 工作进程容量就可以直接计算，不必再靠猜测：

- **工作集** ≈ `RETAIN_MEMORY_BUDGET_MB` × 并发 Retain 槽位数。按默认值 128 MB 和 4 个槽位计算，约为 512 MB。
- **再加上正在处理的正文。** 唯一仍与输入大小成正比的是每份已提交的正文；必须保留它，才能将其写入 `documents.original_text`。应根据实际接受的最大正文大小，为每个并发槽位预留空间。
- **容量模型就是这些。** 按此方式规划的工作进程，无论用户存入的是一段短文还是 90 MB 的导出文件，都能应对；超过预算时，管道会施加背压，而不是突破上限。

## 常见问题 {#frequently-asked-questions}

### 为什么改进前峰值内存会随文档大小增长？ {#why-did-peak-memory-scale-with-the-document-before}

Retain 开始时有两个操作会在任何事实生成之前，各自构造一个与整个文档同等规模的数据结构：计算 token 数时会为每个 token 创建一个装箱的 Python `int`，文本分块则会把所有分块一次性构造成列表。处理 45 MB 正文时，这两项操作分别占用 385 MB 和 200 MB。通常被怀疑的事实和嵌入向量早已受到限制，从来都不是原因。

### `HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB` 的实际作用是什么？ {#what-does-hindsightapiretainmemorybudgetmb-actually-do}

它限制单次 Retain 操作可以持有多少已提取但尚未写入的状态，默认值为 128 MB。无论文档多大，单次 Retain 的峰值内存大致就是这个数值，因此可以按“预算 × 并发 Retain 数”规划工作进程容量。超过预算时，提取过程会施加背压并等待写入路径跟上，而不是继续增长。将其设为 `0`，即可退回到原先仅按数量限制的方式。

### 你们移除了 LangChain 吗？ {#did-you-remove-langchain}

只是不再让它走运行时路径。文本分块不再导入 `RecursiveCharacterTextSplitter`，而是使用流式重新实现。LangChain 仍是差异测试的参照；测试会逐个层级对比我们的分块器，避免边界悄悄偏移。这也是 `langchain-core` 和 `langsmith` 仍留在依赖列表中的原因。

### 这些配置可以按记忆库分别设置吗？ {#is-any-of-this-configurable-per-bank}

内存预算和文本分块批次大小都是服务器级配置项（`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`、`HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE`），通过环境变量设置。它们随 0.9.2 发布。

### 这些数字是如何测量的？ {#how-did-you-measure-the-numbers}

使用 `tracemalloc` 测量，并报告 Python 分配的峰值字节数；结果与分配顺序无关，因此不会受采样时刻哪些分配仍在内存中的影响。每个数字都是在指定大小的正文上单独运行 Retain 前半段（计算大小、文本分块、拆分、筛选）得到的。

### 这会影响 Retain 的吞吐量或延迟吗？ {#does-this-change-retain-throughput-or-latency}

吞吐量没有下降；计算大小和文本分块现在还略快了一些，因为它们不再构造巨大的临时数据结构。这项工作改变的是 Retain 管道前半段的内存占用，并未改变事实提取所需的墙钟时间；事实提取是开销较大的部分，此次保持不变。

### 嵌入向量占用的内存呢？ {#what-about-the-memory-the-embeddings-use}

这次改进之前，嵌入向量的内存占用就已经受到限制，所以它们只是转移注意力的对象。提取出的事实及其向量被限制在 `retain_chunk_batch_size` 个文本分块内，约为 1,700 条事实或 21 MB，无论文档多大都如此。与文档大小成正比的峰值完全来自那两个在任何事实生成之前运行、需要处理整个文档的操作。

### 要获得稳定的内存占用，我需要做什么改动吗？ {#do-i-need-to-change-anything-to-get-the-flat-memory}

不需要。0.9.2 会自动启用重构后的大小计算、文本分块和拆分流程。`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`（默认值为 128）供你按需调整上限；即使保留默认值，峰值内存也已经保持稳定并受到限制。

### 这也会影响 Recall 路径吗？ {#does-this-affect-the-recall-path-too}

不会。这些改进针对 Retain（写入）管道的前半段。Recall 有自己的预算；0.9.2 还单独改进了 Recall，使其跳过超出预算的事实，而不是因此停止。本文介绍的按窗口计算大小、流式文本分块和流式拆分都只用于写入路径。
