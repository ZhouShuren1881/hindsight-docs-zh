每个企业系统都有文档描述。问题在于：这些文档*在哪里*？

架构决策藏在 SharePoint 深处的影响评估中。集成细节藏在三年前编写的 Confluence 页面里。当前状态图则留在某个项目的幻灯片中，而那个项目的“第二阶段”早已不了了之。有人问“现在计费实际上是如何运作的？”时，答案从来不在一个地方。它散落在数十份文档中，每份文档的编写时间和目标读者各不相同，对何为“当前”也各有假设。

architxt 正是为了解决这个问题而构建的。它集成了 [Hindsight](https://github.com/vectorize-io/hindsight)，将这个智能体记忆系统用作持久且具备时间感知能力的记忆层，以支持企业语义检索和跨文档推理。

## architxt：将文档转化为结构化知识 {#architxt-turn-documents-into-structured-knowledge}

architxt 是一个可通过 Web UI 使用的文档处理管道和研究框架。用户上传文档（PDF、Word 文件、PowerPoint 演示文稿）后，它会借助 Docling、基于 LLM 的降噪、图表视觉分析和实体检测，提取整洁、结构化的内容。随后，系统会将结果与关键元数据组合起来，供 Hindsight 使用。其主要组成部分包括：

- **文档**：包含元数据、标签和提取出的内容块。
- **实体**：在不同文档中检测并规范化的系统、服务和能力。
- **心智模型**：可重复使用的 LLM 提示词，从特定角度（如能力、接口、摘要）分析某个实体。借助它们，可以快速检索每个实体的常见维度。
- **时态马赛克**：通过研究和查询，提取每个实体目前所知的最佳状态，无论来源文档是在何时编写的。

![architxt 检测并规范化文档中的实体，再将别名映射回同一个实体。](/img/blog/architxt-entity-detection.webp)

关键在于：**知识的更新状态不等于文档的新旧程度**。如果某个组件没有发生变化，那么 2020 年的组件设计依然有效，即使系统的其余部分此后已经重写过两次。architxt 会追踪每份文档在何时涉及了哪个实体，让你能够基于整个语料库进行推理，同时不必假设存在一份统一的“现状”文档。

## architxt 的处理流程与最低可行输入 {#the-architxt-process-and-minimum-viable-input}

文档只要附带少量统一格式的数据，工具就能发挥最佳效果。architxt 不要求所有内容都完美无缺；它只需要足够的结构信息，以确定每份文档是什么、何时生成以及涉及什么主题。

### 文档整理 {#document-hygiene}

每份文档都应包含：

- **文档 ID**：稳定的标识符。同一文档重新上传时应保留相同的 ID。
- **文档日期**：以 ISO 8601 表示的发布日期，是时间推理的参照点。
- **上下文**：经过整理、用于描述文档所属层次或用途的值，例如影响评估、组件设计或业务能力定义。
- **标签**：统一的筛选条件，例如项目、领域、系统或数据区域。
- **来源元数据**：文档来自何处（Confluence、SharePoint 或文件路径），以及由谁生成。

architxt 提供标签对齐工具，帮助分配上下文、标签、来源元数据和实体标识符。它节省时间的关键在于，能够对整个语料库进行批量修改和一致性检查。用户无需通过 UI 逐份手动更新文档，就能对齐数十乃至数百份文档中的信息。只有能够再次找到文档、按需筛选并确认其日期可信，它才对马赛克有用；architxt 利用这些经过外部整理的结构，构建可靠、一致的当前状态视图。

### 实体是锚点 {#entities-are-the-anchor}

实体是核心单元。组件、服务或能力都可以成为稳定的参照点，让来自不同文档的观测关联到同一对象。没有实体，文档就只是一袋文本；有了实体，2020 年设计中的一句话和 2024 年迁移文档中的一段话就能指向同一事物，architxt 也就能完整保留该事物的最新视图。

在实际文档中，同一实体很少始终使用同一个名称。一份文档可能称它为“计费引擎”，另一份称为“计费服务”，还有一份只写“BE”。借助别名，architxt 可以把这些不同名称映射回同一个实体。已知别名越多，实体时间线就越完整。

为了让实体在不同时间的文档中保持可关联，可以使用轻量级标记约定，将带稳定 ID 的实体写入文档，例如 `Billing Engine (SYS-001)`。人类可读的名称可能会变化（后续设计中，“Billing Engine”可能改称“Billing Platform”），但稳定 ID 会保留下来。architxt 随后会根据稳定 ID 解析当前名称，因此即使命名约定发生变化，旧文档中的引用仍然可用。

![architxt 中的实体命名空间：稳定 ID、别名，以及每个实体出现过的文档。](/img/blog/architxt-entities.webp)

这就是最低可行输入如此重要的原因。良好的元数据和标签能让检索更准确。稳定且包含别名的实体命名空间，则让跨文档、跨年份的信息组合成为可能。心智模型、反思和时态马赛克等其余能力，都建立在这个基础之上。

## Hindsight 增加了什么 {#what-hindsight-adds}

现在我们有了数据，也有一组基本元数据。我们知道其中蕴藏着大量信息，而这些信息的编写成本可能高达数千甚至数百万美元。那么，如何处理和存储这些信息，才能容纳来源文本的差异？

Hindsight 会将提取出的知识存储在持久且具备时间感知能力的记忆库中。它不会用单一摘要替代文档，而是将观测作为独立条目保存，并记录捕获时间和来源。这一点很重要：只有能够询问“关于 X，我们最近掌握的信息是什么？”，而不是“最新文档写了什么？”，时态马赛克才成为可能。

Hindsight 的两个基本操作让这一流程得以实现：

- **Retain（存入）/ 观测**：architxt 从文档中提取事实后，会将事实作为带时间戳且标明来源的记录存入系统，随后将它们整合为观测。关于同一实体的新文档不会覆盖旧内容，而是添加较新的事实，并据此重新整合观测。因此，对于每个方面，马赛克可以优先采用最新观测；在没有较新内容的方面，旧观测仍会保留并可见。

- **Reflect（反思）/ 心智模型**：心智模型是可重复使用的提示词，会基于当前记忆运行。添加新文档后，可以刷新这些模型，让摘要、能力清单和接口说明保持最新；整合后自动刷新则需要选择启用。输出会关联到作为依据的观测，因此生成的视图有据可查、来源可追溯。

Retain（存入）和 Reflect（反思）共同让马赛克能够增量更新。新文档被摄取，事实被存入，心智模型重新运行。“当前状态”无需从头重建，而是持续更新的知识栈中最新的一层。

## 时态马赛克：没有单一事实来源的当前状态 {#the-temporal-mosaic-current-state-without-a-single-source-of-truth}

这种组合之所以重要，是因为大多数架构工具都迫使用户采用以下两种模式之一：

1. **静态模型**：画一次图，然后眼看着它逐渐过时。
2. **设计与交付核对**：试图同时维护两套平行现状，再将它们合并。

architxt 选择第三条路径：将 Hindsight 用作持久记忆层。“当前状态”是一幅马赛克，其中每个实体都呈现其最新的可靠信息，来源是最近涉及该实体的文档。2020 年设计中的一个组件，可以与 2024 年迁移文档中的一个服务并列呈现。只有当某个查询跨越这些接缝时，矛盾、过时的接口和孤立依赖等问题才会显现。

这就是**时态马赛克**。它承认组织不会产出一份前后一致的架构文档；组织产出的是一系列不完整、带有日期且彼此重叠的文档。architxt 不会把它们压平成单一模型，而是借助 Hindsight 将它们组合起来供查询。答案以来源文档为依据，并带有实体标签，因此可以追溯来源，而不必依赖模型幻觉。

## 实际应用示例 {#what-this-looks-like-in-practice}

文档完成标记并被摄取后，提问方式也会改变。你可以直接针对整个语料库提问，而无需再猜“答案可能在哪份文档里？”。

例如：

- “计费服务与客户平台之间有哪些集成点？”
- “订单处理系统支持哪些能力？哪些文档描述了这些能力？”
- “自 2022 年平台迁移以来，客户记录的数据模型是否发生了变化？”

![某个实体的能力摘要：以来源文档为依据综合生成，并按能力、接口等方面组织。](/img/blog/architxt-grounded-answer.png)

Hindsight 返回有依据的答案。每项陈述都关联到对应的文档和来源观测，因此你可以核验内容，而不必直接相信生成的摘要。如果两份文档意见不一致，系统会呈现这种分歧，而不是将其抹平。这样，文档检索就从猜测变成了结构化查询。

## 简而言之 {#in-short}

架构知识碎片化所造成的真正成本并非文档本身，而是人们花在拼凑这些文档含义上的时间。

architxt 通过将文档转化为结构化、带实体标签的观测来降低这项成本。Hindsight 让这些观测能够随时间持续更新。最终形成的时态马赛克提供了当前状态视图：它不假装组织曾经产出过一份权威描述，却仍让汇总后的知识可检索、可核验且保持最新。

这就是变化所在：重点不是增加文档或绘制更好的图表，而是从现有文档中提取价值，并为新文档编写后如何持续更新当前状态提供路径。未来设计文档的格式和范围尚不可知，但其中仍会包含值得利用的信息。architxt 与 Hindsight 相结合，正是为了实现这一目标。
