每个企业系统都有描述。问题是*哪里*。

架构决策存在于 SharePoint 中埋藏的影响评估中。集成细节隐藏在三年前编写的 Confluence 页面中。幻灯片中的当前状态图来自一个已被“遗忘”的“第二阶段”的程序。当有人问“现在计费实际上是如何运作的？”时，答案永远不会在一处。它分布在数十份文件中，每份文件都是在不同的时间、针对不同的受众编写的，对“当前”的内容有不同的假设。

这是 architxt 旨在解决的问题。它与[Hindsight](https://github.com/vectorize-io/hindsight)集成，这是一种智能体记忆系统，用作企业语义搜索和跨文档推理的持久、时间感知记忆层。

## archittxt：将文档转化为结构化知识 {#architxt-turn-documents-into-structured-knowledge}

architxt 是一个文档处理管道和研究框架，可通过 Web UI 访问。您上传文档（PDF、Word 文件、PowerPoint 演示文稿），它会使用 Docling、基于 LLM 的去噪、图表视觉分析和实体检测来提取干净、结构化的内容。输出与关键元数据相结合，为 Hindsight 做好准备。其主要组成部分是：

- **文件** 包含元数据、标签和提取的块。
- **实体

- **心智模型**：可重用的LLM提示，从特定角度（功能、接口、摘要）分析实体。这些允许快速检索每个实体的常见维度。
- **时间马赛克**：研究和查询提取每个实体的最知名状态，无论源文档何时编写。

![architxt 检测并标准化文档中的实体，将别名映射回单个实体。](/img/blog/architxt-entity-detection.webp)

关键的见解是**知识新鲜度不是文档新鲜度**。如果 2020 年的组件设计没有发生变化，即使系统的其余部分自此被重写了两次，该设计仍然有效。 architxt 跟踪哪个文档在何时接触了哪个实体，并让您可以对整个语料库进行推理，而无需假装存在单个“原样”文档。

## architxt 流程和最小可行输入 {#the-architxt-process-and-minimum-viable-input}

当文档到达时带有少量一致数据时，该工具效果最佳。 architxt 不需要一切都完美；它需要足够的结构来了解每个文档的内容、生成时间以及内容。

### 文档卫生 {#document-hygiene}

每份文件应包含：

- **文档ID**：稳定的标识符。重新上传的同一文档保留相同的 ID。
- **文件日期**：ISO 8601 中的发布日期。这是时间推理的锚点。
- **上下文**：描述文档的层或目的的策划值，例如影响评估、组件设计或业务能力定义。
- **标签**：一致的过滤器，例如项目、域、系统或数据区域。
- **源元数据**：文档来自哪里（Confluence、SharePoint、文件路径）以及是谁生成的。

architxt 包括标签对齐工具，可帮助分配上下文、标签、源元数据和实体标识符。时间的节省来自于 architxt 在整个语料库中启用的批量更改和一致性检查。它可以对齐数十或数百个文档中的信息，而无需直接通过 UI 手动更新每个文档。仅当您可以再次找到它、通过它进行过滤并信任其日期时，文档在马赛克中才有用； architxt 使用外部管理的结构来构建可靠、一致的当前状态视图。

### 实体是锚 {#entities-are-the-anchor}

实体是中心单元。组件、服务、功能：每一个都成为可以附加来自不同文档的观察的稳定参考点。如果没有实体，文档只是一袋文本。对于实体，2020 年设计中的一个句子和 2024 年迁移文档中的一个段落都可以引用同一事物，而 architxt 可以完整地保留该事物的最新视图。

在实践中，同一实体很少在每个文档中被称为相同的事物。一个文档可能会说“计费引擎”，另一个文档可能会说“计费服务”，另一个文档可能会说“BE”。别名让 architxt 将这些不同的名称映射回单个实体。已知的别名越多，实体时间线就越完整。

​​为了使这项工作能够跨时间进行，实体被嵌入到具有稳定 ID 的文档中，使用轻量级标记约定（例如 `Billing Engine (SYS-001)`）。人名可以改变（在以后的设计中“计费引擎”可能会变成“计费平台”），但稳定的 ID 会保留下来。然后 architxt 根据稳定 ID 解析当前名称，因此即使在命名约定发生变化后，旧文档中的引用仍然可用。

![architxt 中的实体命名空间：稳定 ID、别名以及每个实体出现的文档。](/img/blog/architxt-entities.webp)

这就是为什么最小可行输入很重要。良好的元数据和标签可以使记忆准确。稳定的别名实体命名空间使得跨文档和跨年份的组合成为可能。其余的，心智模型、反思和时间马赛克，都建立在这个基础之上。

## Hindsight 添加了什么 {#what-hindsight-adds}

因此，我们拥有数据并拥有一组基本的元数据。我们知道存在着一座信息金矿，编写这些信息可能要花费数千或数百万美元。我们如何以适应源文本差异的方式处理和存储它？

Hindsight 将提取的知识存储为持久的、具有时间感知能力的记忆库。它将观察保留为离散条目，包括捕获时间和来源，而不是用单个摘要替换文档。这很重要，因为只有当你可以问“我们最近对 X 了解什么？”时，时间镶嵌才有可能。而不是“最新文件说了什么？”

两个 Hindsight 原语使此工作有效：

- **记忆存储/观察**：当architxt从文档中提取事实时，它们被保留为带时间戳的、源引用的事实，然后合并到观察中。关于同一实体的新文档不会覆盖旧文档；它增加了新的事实，并且观察得到了重新巩固。然后，马赛克可以更喜欢每个方面的最新观察结果，同时在没有新内容存在的地方仍然保持旧的观察结果可见。

- **反思 / 心智模型**：心智模型是可重复使用的提示，运行在当前的记忆集上。它们可以随着新文档的添加而刷新，因此摘要、功能列表和接口描述保持最新状态；选择加入整合后自动刷新。输出与其所基于的观察相关联，因此生成的视图保持接地且可追踪。

记忆存储和直觉意味着马赛克增量更新。摄取新文档，保留事实，并重新运行心智模型。 “当前状态”不是从头开始重建的；它是不断更新的知识堆栈的最新层。

## 时间马赛克：没有单一事实来源的当前状态 {#the-temporal-mosaic-current-state-without-a-single-source-of-truth}

这种组合很重要，因为大多数架构工具强制使用以下两种模型之一：

1. **静态模型**：画一次图表，看着它腐烂。
2. **设计与交付的协调**：尝试维持两个平行的现实并将它们合并。

architxt 采用第三条路径，使用 Hindsight 作为其持久记忆层。 “当前状态”是一个马赛克：每个实体的最新可靠知识，源自最后触及它的文档。 2020 年设计中的组件位于 2024 年迁移文档中的服务旁边。仅当查询与接缝（矛盾、过时的接口、孤立的依赖项）交叉时，接缝才会出现。

这是**颞马赛克**。它承认组织不会生成一份一致的架构文档。它们产生一系列部分的、过时的、重叠的文档。 architxt 没有将它们扁平化为单个模型，而是使用 Hindsight 使它们作为一个组合进行查询，答案基于源文档并用实体标记，因此它们具有出处，而不是依赖于模型幻觉。

## 这在实践中是什么样子的 {#what-this-looks-like-in-practice}

一旦文档被标记并被摄取，问题就会改变。您可以针对语料库直接提出问题，而不是“哪个文档可能有答案？”。

例如：

- “计费服务和客户平台之间的集成点是什么？”
- “订单处理系统支持哪些功能，哪些文档描述了这些功能？”
- ​​“自 2022 年平台迁移以来，客户记录的数据模型是否发生了变化？”

![一个实体的基础能力摘要，从源文档合成并组织成能力和接口等方面。](/img/blog/architxt-grounded-answer.png)

Hindsight 返回接地答案。每个声明都与文档及其来源的观察相关联，因此您可以验证它而不是信任生成的摘要。如果两份文件存在分歧，那么分歧就会浮出水面，而不是被平息。这将文档搜索从猜谜游戏转变为结构化查询。

## 简而言之 {#in-short}

碎片化架构知识的真正成本不是文档本身。人们花时间试图重建这些文件放在一起时的含义。

architxt 通过将文档转变为结构化的、实体标记的观察来降低成本。 Hindsight 让这些观察随着时间的推移而保持活力。时间马赛克就是结果：一种当前状态的视图，它并不假装组织曾经产生过单一的权威描述，但仍然使组合的知识可搜索、可验证和最新。

这就是转变。不是更多的文档，或者更好的图表，而是一种从现有文档中提取价值的方法，并提供一种在新文档编写时保持当前状态的途径。未来设计文档的格式和范围尚不清楚，但它们将包含值得利用的信息。 architxt 与 Hindsight 相结合，就是为了让这一切成为可能。
