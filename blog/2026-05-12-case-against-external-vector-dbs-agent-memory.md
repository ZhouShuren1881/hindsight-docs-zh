打开几乎任何智能体记忆框架的文档，快速入门教程的开头都一样：安装一个向量数据库。[Mem0](https://mem0.ai) 要求使用 Qdrant 或 Pinecone。自托管的 Zep，或者更准确地说，如今还剩下的那部分 Zep，需要 [Neo4j](https://neo4j.com)、FalkorDB 或 Kuzu。LangChain 的记忆示例默认使用 Chroma。这种做法如此普遍，以至于“智能体记忆就意味着向量数据库”已经成了一种常见说法。

但多数情况下，这些都没有必要。

<!-- truncate -->

这不是在反对向量数据库。[Pinecone](https://www.pinecone.io)、[Weaviate](https://weaviate.io) 和 [Qdrant](https://qdrant.tech) 都针对各自设计的工作负载做得很好：在大型且大多静态的语料库上进行读多写少的相似度搜索。这类工作负载通常称为 RAG。智能体记忆则是另一类问题；把两者当成同一种问题，正是错误默认做法产生的原因。

本文讨论的范围更窄：对于大多数智能体记忆工作负载，运行第二个有状态服务带来的运维复杂度并不值得。而这笔运维成本换来的能力——快速相似度搜索——也不是应该优先优化的层。把对话流转化为有用[智能体记忆](https://vectorize.io/what-is-agent-memory)的大部分工作都发生在写入侧：提取事实、解析实体、处理矛盾、标记失效以及综合生成。向量数据库看不到这些，它只看到嵌入向量写入和读出。真正的记忆位于更上层。

## 智能体记忆不同于 RAG {#agent-memory-is-not-rag}

先看工作负载，因为后面的讨论都由此展开。

| 维度 | RAG | 智能体记忆 |
|---|---|---|
| 读写比例 | 读多；语料库构建一次 | 写多；每轮对话都会产生事实 |
| 每租户的数据量 | 数百万到数十亿个向量 | 数十万到数百万个向量 |
| 检索方式 | 主要是语义相似度 | 语义 + 实体 + 时间 + 图检索 |
| 延迟预算 | 数百毫秒（搜索界面） | 低于 200 毫秒（智能体循环） |

RAG 是读多写少的工作负载。语料库构建一次，批量计算嵌入向量并建立索引，之后系统大部分时间都在静态索引上处理相似度查询。数据也会更新，但更新并非主要路径。主要路径是“用户输入问题，返回语义最相似的文本分块”。近似最近邻搜索的吞吐量是最受关注的指标。

智能体记忆在大多数方面都与之相反，而且原因不只是写入“更频繁”。每次写入都会经过学习管道。原始对话轮次会拆解为原子事实。系统会将这些事实中提到的实体与已有实体进行解析：“身份验证服务”“我们的登录系统”和“OAuth 微服务”应该归并到同一个规范节点。新事实若与已有事实矛盾，就会触发矛盾协调处理。被取代的事实会标记为失效。系统还会定期综合累积的事实，并写回更高层次的观测。这些环节在 RAG 摄取中都不存在，也不是向量数据库的设计目标。

检索模式也不同。RAG 查询大多是一次性的语义查找；智能体记忆查询则混合了多种方式。“用户上周二对定价做了什么决定？”依赖时间信息并锚定到实体。“显示与数据库迁移讨论相关的所有内容。”需要图结构检索。“用户有没有提到对新仪表盘的担忧？”需要语义检索，也需要解析实体以识别同义表达。这些都不是纯粹的 ANN 问题。

每租户的数据量是第三个差异。典型的智能体记忆语料库每个租户有几十万到几百万条事实。这比值得在生产环境运行 Pinecone 的 RAG 工作负载小两到三个数量级。让专用向量数据库值得其运维成本的规模（十亿级向量）通常并不存在。

如需更深入地了解这两类系统的差异，可以阅读[关键架构差异](https://vectorize.io/articles/agent-memory-vs-rag)。

## 外部向量数据库的隐性成本 {#the-hidden-tax-of-external-vector-databases}

如果智能体记忆与 RAG 的形态相同，那么额外运行一个向量数据库所带来的运维成本就是正常开销。但实际并非如此，因此这笔成本大多换不来什么价值。

### 运维面 {#operational-surface-area}

运行外部向量数据库意味着还要为第二个有状态服务配置资源、扩缩容、保障安全、备份、监控和升级版本。对于已经因其他需求而大规模运行 Pinecone 或 Weaviate 的团队，这些工作可以摊销；对于尚未运行这类服务的团队，智能体记忆项目会让数据库数量直接翻倍。

主要智能体记忆框架的自托管方式能看出这种模式。自托管 Mem0 需要另外部署 Qdrant 或 Pinecone。Zep 的 Community Edition 已被弃用，而自托管 Graphiti 现在意味着除了 Graphiti 自身的服务之外，还要部署 Neo4j、FalkorDB 或 Kuzu。真正费力的不是框架本身，而是它们依赖的数据库。

### 网络跳转与延迟 {#network-hop-and-latency}

与 RAG 管道相比，智能体循环的延迟预算更紧。一次记忆检索如果耗时 400 毫秒，在搜索界面中感觉还可以；但在每轮要调用四次工具的智能体中，这就会让人觉得系统坏了。路径中的每个外部服务都会增加一次往返和一次序列化。对于低流量的智能体记忆工作负载，访问托管向量数据库的网络跳转所占延迟预算，往往比实际查询本身还多。

### 小规模时的成本 {#cost-at-small-scale}

托管向量数据库有最低收费门槛。Pinecone 的 serverless 和 pod 方案都有定价下限，因此费用不会随智能体记忆常见的小数据集线性缩减。Weaviate Cloud、Zilliz 和 Qdrant Cloud 也有类似的定价结构。（请核实当前价格；供应商经常调整。）对于一个能轻松装进几 GB Postgres 的工作负载，支付托管向量数据库的最低费用，只是为运维便利付出的成本，却买不到工作负载真正需要的能力。

## 向量数据库缺少学习层 {#the-learning-layer-a-vector-database-doesnt-have}

如果把检索层面的讨论再往下追溯，会发现更根本的问题其实完全发生在检索上游。

有用的智能体记忆不是一堆对话文本分块，而是一种随着对话积累而逐步构建、持续重建的结构化表示。让这套机制运转起来的架构原语并不是向量：

- **事实提取。** 模型会把每轮对话拆解为可检索的原子主张，并保留它们与原始消息之间的来源追溯信息。
- **实体解析。** 新提及的实体会与已有实体关联。无论名称如何变化，同一个客户、项目或服务都会解析到同一个规范节点。
- **矛盾处理。** 新事实与已有事实冲突时，系统必须判断哪条事实优先、哪些事实应标记为失效，以及哪些应作为历史记录保留。
- **标记失效。** 事实有自己的有效期。“仪表盘正在测试”这条事实在仪表盘正式发布后，就不应再被检索到。
- **反思。** 系统定期读取累积的事实，并写回综合生成的观测——例如模式、总结和反复出现的主题。这些内容不会明确出现在任何一段单独对话中，而是从多段对话中逐渐显现。

向量数据库对上述处理都没有自己的判断。它接收一个 `id` 和一个 `vector`。结构、关系、时间有效性和去重逻辑都必须放在别处。实际中，“别处”通常意味着再加一个数据库，或一大堆分散的应用逻辑和缓存；向量存储则沦为你已经维护的更大数据模式中的一列。

这样一来，你并没有从技术栈中移除一个数据库，反而增加了一个。

把学习层和检索底层放在同一个事务数据库中，就能简化整个架构。事实提取管道写入同一个由 pgvector 建立索引的 Postgres。实体解析就是一次联接。矛盾协调处理就是一个事务。Reflect 生成的内容与其他事实一样，也会和输入事实一起建立索引。智能体实际需要的混合检索方式由数据模型直接支持，无需跨多个服务拼装。

## 单一检索策略才是真正的上限 {#single-strategy-retrieval-is-the-real-ceiling}

向量数据库擅长一件事：对嵌入向量进行近似最近邻搜索。即使前面关于运维的理由都不成立，仅使用向量的系统依然不是智能体记忆的合适底层，因为大多数智能体记忆查询都无法简化为纯语义相似度。

以 Hindsight 对每个查询并行运行的四种检索策略为例：语义检索、基于实体的检索、时间筛选和图遍历。其中三种不是 ANN。基于实体的检索是在实体表中进行结构化查找。时间筛选是对时间戳进行范围查询。图遍历则是沿着边递归遍历。向量数据库能处理第一种；其他方式则必须委托给别的服务，或重复存储数据。

这并非 Hindsight 独有的观察。任何足够完善的智能体记忆系统最终都会至少支持这四种检索模式中的三种，因为查询本身就有这样的需求。Zep 的时间知识图谱是认真处理图和时间问题的有力例子，但相应的代价是：一旦沿图遍历，Zep 的图数据库就不再只是“向量数据库的问题”。从不同角度看，架构上的取舍也会不同。

实测结果也反映了这种架构差异。在[长期对话记忆的标准评估 LongMemEval](https://arxiv.org/abs/2410.10813)中，以向量检索为主的系统得分较低。Mem0 公布的成绩是 49.0%。采用多策略检索的系统得分更高。Hindsight 在同一基准上的成绩为 91.4%。同样采用多种检索模式的 SuperMemory 公布的成绩为 81.6%。准确率差距清楚地反映了架构差异。若要深入比较架构，可以阅读[比较 Hindsight 与 Mem0](https://vectorize.io/articles/hindsight-vs-mem0)，其中详细讨论了相同的取舍。

## 向量数据库针对错误的工作负载进行了优化 {#vector-databases-are-optimized-for-the-wrong-workload}

向量索引结构（HNSW、IVF、ScaNN）都针对读取进行了优化。构建索引和增量更新的成本都很高。有些实现支持删除后重建；另一些则在发生较大变更时必须完整重建索引。它们都不适合像智能体记忆那样频繁写入、更新和标记事实失效的工作负载。

更糟的是，向量索引看到的写入甚至不是最重要的写入。有意义的工作——提取事实、解析实体、处理矛盾、反思——都发生在上游，并产生许多小型派生记录；向量存储只能看到这些记录最终嵌入后的形式。大多数学习逻辑完全不会接触向量索引，这正说明了问题：向量存储只是整个系统中的一种底层支撑，而系统的重心在别处。

PostgreSQL 花了三十年时间打磨事务型工作负载能力。MVCC、WAL、时间点恢复、在线模式变更、成熟的复制机制，都不是为向量设计的，却适用于智能体记忆实际需要的访问模式（写入、更新、删除和并发读取）。通过 pgvector 添加向量检索，也就继承了这些能力。

到了十亿级向量规模，情况就会反过来。专用向量数据库在原始吞吐量和索引构建时间上更有优势，其运维开销也能因此得到回报。但大多数智能体记忆工作负载都没有达到十亿级向量规模。

## pgvector 已经足以支持智能体记忆 {#pgvector-is-already-good-enough-for-agent-memory}

过去“直接用 Postgres”的主要反对理由是性能：pgvector 早期的 IVFFlat 索引在大规模场景下缺乏竞争力。如今这已不再是主要限制。[pgvector](https://github.com/pgvector/pgvector) 支持 HNSW 索引，在智能体记忆工作负载关注的召回率和延迟方面具有竞争力。Postgres 16 的并行索引构建和查询并行处理也弥补了大部分剩余差距。

更重要的是，把向量放进 Postgres，实体表、时间事实、图边和应用数据就都能位于同一个事务数据库中。多策略检索只需一次联接，而不必执行分布式查询。四种检索底层之间的原子写入无需额外成本。备份只需运行一次 `pg_dump`。

实际实现可以是一个查询：

```sql
-- 在一个数据库的同一条查询中合并三种检索策略
WITH semantic AS (
  SELECT fact_id, 1 - (embedding <=> $query_embedding) AS score
  FROM facts
  ORDER BY embedding <=> $query_embedding
  LIMIT 50
),
temporal AS (
  SELECT fact_id, 1.0 AS score
  FROM facts
  WHERE created_at BETWEEN $window_start AND $window_end
),
entity AS (
  SELECT f.fact_id, 1.0 AS score
  FROM facts f
  JOIN fact_entities fe USING (fact_id)
  WHERE fe.entity_id = ANY($resolved_entity_ids)
)
SELECT f.*,
       COALESCE(s.score, 0) AS semantic_score,
       COALESCE(t.score, 0) AS temporal_score,
       COALESCE(e.score, 0) AS entity_score
FROM facts f
LEFT JOIN semantic s USING (fact_id)
LEFT JOIN temporal t USING (fact_id)
LEFT JOIN entity   e USING (fact_id)
WHERE s.fact_id IS NOT NULL OR t.fact_id IS NOT NULL OR e.fact_id IS NOT NULL;
```

图遍历可以通过针对边表的递归 CTE 实现。应用程序会对合并后的候选集运行交叉编码器重排序。同一个数据库容纳所有这些数据和操作，并且所有操作都处于同一个事务中。

选择并不是“用 Postgres 代替向量数据库”，而是“使用 Postgres，因为检索模式需要联接”。

## AI 智能体需要向量数据库吗？ {#do-you-need-a-vector-database-for-an-ai-agent}

默认情况下不需要。大多数智能体记忆工作负载都足够小，可以和应用数据一起放在使用 pgvector 的 Postgres 中。外部向量数据库是为 RAG 规模的语料库和读多写少的相似度搜索而设计的；智能体记忆则写入和更新频繁，而且相比原始 ANN 吞吐量，更需要结合向量、图和时间的检索能力。确实存在一些例外，接下来会介绍。

---

## 外部向量数据库仍然适用的情况 {#when-an-external-vector-database-still-makes-sense}

有三类情况会让权衡确实反转。

**每租户向量数极多的多租户 SaaS。** 如果你在数百个租户中为每个租户存储数千万个向量，pgvector 的索引构建时间和共享资源争用就会成为实际问题。Pinecone 的无服务器索引和 Weaviate 的租户隔离能力可能值得相应的运维成本。

**智能体记忆与真正的 RAG 语料库共用基础设施。** 如果团队已经为数百万份文档的产品 RAG 运行向量数据库，那么把智能体记忆也放到相同基础设施上，可能比另行部署一套 Postgres 更高效。向量数据库的边际成本已经付过了。

**读取吞吐量占主导的工作负载。** 某些智能体记忆部署（例如企业知识库中的长尾记忆召回、多区域只读副本）看起来更像 RAG，而不像智能体记忆。专用向量数据库正是为这种形态设计的。

这些都不是默认情况。它们属于工作负载重新回到适合向量数据库的领域时的例外。

---

## 更适合智能体记忆的默认方案 {#a-better-default-for-agent-memory}

适合大多数智能体记忆工作负载的默认架构是：

- 一条学习管道，将事实、实体、边和综合生成的观测写入一个 Postgres；其中 pgvector 存储嵌入向量，图表存储边，时间索引支持事实生命周期管理
- 采用多策略检索，对同一个数据库并行查询，再在应用层合并结果
- 在应用程序中对合并后的结果运行交叉编码器重排序
- 将系统部署为一个容器，并像备份其他 Postgres 一样进行备份

这是 Hindsight 提供的架构，并非偶然。我们选择这种架构，是因为工作负载有此需求；而这种需求之所以存在，是因为智能体记忆不是 RAG。自托管只需一条 Docker 命令。存储使用嵌入式 PostgreSQL。无需配置外部向量数据库，也无需在旁边运行图数据库。如果你接下来想了解[比较 Hindsight 与 Zep](https://vectorize.io/articles/hindsight-vs-zep)（图优先架构与基于 Postgres 的多策略检索），可以阅读这篇比较。

## 结论 {#conclusion}

正确的问题不是“智能体记忆应该运行哪个向量数据库？”，而是两个问题：检索上游的学习管道实际上会做什么？我的检索组合实际上是什么样的？对于大多数团队，答案是：事实提取、实体解析、矛盾处理和反思；检索组合则大多不依赖语义相似度，不需要十亿级规模，以写入为主，而且数据量通常小到足以与应用数据放在一起。与单独运行向量数据库相比，一个 Postgres 能更好地处理这两个层面，运维成本也更低。

外部向量数据库仍然非常擅长处理其设计目标。只是智能体记忆通常并非这种工作负载；其中最不像 RAG 的部分是学习层，而不是搜索。
