当您的 AI 产品在另一客户会话中调用一个客户的数据时，您就不会遇到个性化错误。你有违规行为。每个用户的记忆看起来像一个功能，并且表现得像一个安全边界，大多数“只需添加一个`user_id`”的建议悄悄地让这一点倒退。

如果您正在构建多租户AI产品，记忆就是隔离保证您已经在数据库中强制执行的系统，该系统旨在故意模糊上下文。这篇文章是关于如何将它们分开：模式、重要的决定以及如何证明它成立。

该类别的新手？从[什么是智能体记忆](https://vectorize.io/what-is-agent-memory)开始。这篇文章假设您正在向具有多个客户的产品添加记忆，并希望他们的数据保留在他们自己的数据中。

## 为什么多租户记忆是一个不同的问题 {#why-multi-tenant-memory-is-a-different-problem}

单用户记忆只有一项工作：记忆正确的事情。多租户记忆有两项工作，记忆召回正确的事情**和**永远不会记忆召回别人的事情，当这两个目标发生冲突时，隔离获胜。仅针对记忆召回进行调整的记忆系统很乐意呈现语义上相似的事实，无论它属于谁。这正是您无法发货的故障。

这是每个用户设计都必须解决的压力。个性化需要对产品所知道的一切进行广泛的记忆召回。隐私希望每个用户的记忆被密封。整个游戏是在系统为你强制执行的地方绘制密封，而不是你必须记住在每次调用时强制执行的地方。

## 重要的一个决定：硬边界还是软分区？ {#the-one-decision-that-matters-hard-boundary-or-soft-partition}

几乎每个“多租户记忆”指南都简化为“在每条记录上放置一个`user_id`并通过它进行过滤”。这并没有错，但它隐藏了真正决定你是否泄漏的决定。有两种根本不同的工具，并且它们不可互换：

||硬隔离边界|软隔断|
|---|---|---|
|**这是什么**|每个租户/用户一个单独的存储|一个共享存储内的标签/过滤器|
|**执行者**|存储层|通话时您的询问|
|**用于**|租户、客户、每用户数据，其中泄漏是一个错误|您有时想要交叉引用的切片（项目、主题）|
|**故障模式**|难以泄露——没有跨界查询|忘记或错误过滤器时发生泄漏|

在Hindsight中，硬边界是**记忆库**。一个[记忆库是记忆召回边界](/blog/2026/07/16/bank-strategy-agent-memory)：`recall`、`retain`和`reflect`每个都恰好命名一个`bank_id`并保留在其中，并且没有跨越记忆库的内置查询。软分区是一个**标签**：当你记忆存储时附加标签，当你记忆召回时通过它们进行过滤。

这是人们错过的部分，这也是这很重要的全部原因。 Hindsight中的**你可能忘记通过的过滤器并不是隔离。**标签过滤默认为甚至*包括未标记的记忆*的模式（`any`），因为标签意味着组织提示，而不是墙壁。这个默认值就是告诉我们：如果记忆绝对不能在错误的上下文中出现，那么不要将其隐藏在别人可以省略的标签后面。将其置于存储层强制执行的边界后面。

因此针对每用户产品的规则很短：**用户（或租户）是一个硬边界，因此它有一个记忆库。其他一切都是标签。**

## 每用户、每组织和共享知识 {#per-user-per-org-and-shared-knowledge}

实际产品有两个以上的范围。通常是三个：

- **用户私有** — 此人的对话、偏好和历史记录。硬边界。
- **在组织/工作空间内共享** — 每个席位都应该看到的团队大会、共享项目、帐户级事实。组织级别的硬边界。
- **全球产品知识** — 文档、入门、每个人都会得到的默认值。一个共享的、以阅读为主的存储。

映射是直接的。让记忆库永远不会泄露：对于消费品，`bank_id="user:{id}"`，每个人的记忆都不能触及其他人的记忆；对于 B2B，`bank_id="org:{id}"`，同一帐户中的席位应该共享上下文，但两个客户不得共享上下文。然后在该边界、项目、来源、敏感度内使用记忆的*种*标签，这样您就可以在需要时进行过滤，并在需要时进行交叉引用，而无需穿墙而过。

具体的失误让它粘在一起。支持 SaaS 通过一个共享记忆库中的 `customer_id` **标签** 来确定其记忆范围，而不是每个客户的记忆库。它在测试中起作用了。然后，单个记忆存储调用没有标签，一个被遗忘的参数，并且由于默认匹配模式包括未标记的记忆，因此客户 A 的合同条款出现在客户 B 的会话中。修复的并不是更严格的过滤器。这是一个真正的边界：每个客户一个记忆库，所以没有什么可以忘记的。

## 跨界阅读，无需跨记忆库查询 {#reading-across-boundaries-without-a-cross-bank-query}

硬边界提出了一个明显的问题：如果`recall`只命名一个记忆库，那么智能体如何在单个答案中使用用户的私有记忆*和*组织的共享知识*和*产品的全局文档？你不需要在边界上打一个洞来做到这一点。您在应用程序层进行编写。

该模式是扇出：来自当前调用者有权访问的每个记忆库的记忆召回，然后在结果到达模型之前对结果进行合并和排序。权利检查存在于您的代码中，它属于它，并且每个记忆召回仍然保留在它自己的边界内。

```python
def recall_for(user, query, k=8):
    scopes = [
        user_bank(user.id),          #该用户私有
        f"org:{user.org_id}",        #在组织内共享
        "product:global",            #阅读——主要是产品知识
    ]
    hits = []
    for bank in scopes:
        hits += hs.recall(bank_id=bank, query=query, max_results=k)
    return rank(hits)[:k]            #在您的应用中合并 + 重新排名
```

由此得出两个属性。用户只能读取您的权利逻辑交给他们的记忆库，因此仍然无法寻址其他用户的记忆库。范围由*加法*组成：您可以通过添加允许调用者查看的记忆库来扩大答案，而不是放松过滤器。写入是镜像，它们会精确地写入一个记忆库，即私有记忆库，除非某个事实确实是组织级别的，在这种情况下，它是有意写入组织记忆库的，而不是偶然的。

## 你可以证明的隔离 {#isolation-you-can-prove}

如果租户隔离是一种安全属性，则可以像安全属性一样对其进行测试。不要因为幸福的道路看起来是正确的而假设边界成立。这与构建[您真正信任的评估](/blog/2026/07/31/evaluate-agent-memory-system)相同，应用于隔离而不是检索。

最小跨租户泄漏测试：

1. **存储为A，读取为B。** 记忆存储是租户 A 记忆库中的一个独特事实。 记忆 从租户 B 的记忆库中记忆。断言没有任何返回。
2. **使用共享实体进行模糊测试。** 为两个租户提供相同的实体名称（“Acme 帐户”、“我们的临时服务器”），并确认 [实体解析](/blog/2026/06/29/entity-resolution-agent-memory) 保留在每个边界内，而不是跨边界合并。
3. **攻击软分区。** 如果您在任何地方都依赖标签，则没有标签的记忆存储并确认未标记的默认行为不会在过滤查询中显示它。这就是仅标签“隔离”失败的地方。
4. **删除并重新检查。** 完全删除租户A，然后确认A的记忆已消失且B的记忆未受影响。

它的核心是你可以断言的三行，其他的都是变体：

```python
hs.retain(bank_id="tenant:A", content="A的秘密：发布日期是3月3日。")
leaked = hs.recall(bank_id="tenant:B", query="发布日期是哪天？")
assert leaked == [], f"cross-tenant leak: {leaked}"
```

​​在 CI 中运行它，而不是手动运行一次。当有人添加一个新的代码路径，从错误的变量构造 `bank_id` 时，边界就会发生漂移，而捕获它的唯一方法是进行一个测试，将其存储为一个租户并读取为另一个租户。

## 每用户删除和 GDPR 问题 {#per-user-deletion-and-the-gdpr-question}

被遗忘权是边界选择得到回报或咬你一口的地方。如果用户是边界，删除就是一种操作：删除该用户的记忆库以及记忆、提取的实体以及根据它们构建的图表。干净、完整、可审计。

将其与软分区版本进行比较。如果每个用户的事实都存在于 `user_id` 过滤器后面的一个共享索引中，那么“删除该用户”就变成了一项外科手术：找到每一行、每个派生嵌入、接触它们的每个图形边缘，并在不干扰其他任何人的情况下将其删除，然后证明您已获得所有这些信息。您可以将其中之一交给合规审核员。另一个你希望你做对了。存储层的隔离将删除审计变成了一件简单的事。

## 在不爆炸的情况下扩展到许多租户 {#scaling-to-many-tenants-without-an-explosion}

对“每个用户一个记忆库”的明显反对是成本：一万个用户是否意味着一万个数据库？不应该，答案是架构问题，而不是建模问题。

Hindsight 将记忆库存储为单个系统的作用域分区，而不是单独配置的数据库，因此边界是逻辑的，在每个查询上强制执行，而无需为每个租户建立基础设施的操作重量。这就是让 [系统规模](/blog/2026/05/08/how-hindsight-scales) 跨越多个边界的原因：您可以用一个足迹来隔离不同的存储。当您评估任何多租户使用的记忆系统时，这是要问的问题，因为每个租户需要一个真实数据库的系统将使您在隔离和基础设施账单之间做出选择，而这是您不必做出的选择。

金融科技团队构建多用户AI[从第一天起就这么做了](/blog/2026/04/13/hindsight-financial-ai-memory-customer-story)：在单个自托管部署上以每租户隔离为边界，为其中的软切片添加标签。

## 放在一起 {#putting-it-together}

代码中的模式很小，这就是重点。边界发挥作用。

```python
#硬边界：用户（或组织）是记忆库。
def user_bank(user_id: str) -> str:
    return f"user:{user_id}"

#记忆存储仅进入调用者的记忆库。标签用于切片*以内*边界。
hs.retain(
    bank_id=user_bank(current_user.id),
    content="更喜欢深色模式和公制单位。主要用于计费服务。",
    tags=["project:billing"],
)

#记忆召回永远不会命名另一个用户的记忆库，因此跨用户的记忆召回是不可表达的。
hits = hs.recall(
    bank_id=user_bank(current_user.id),
    query="该用户对于计费工作的偏好是什么？",
    tags=["project:billing"],   #边界内软滤镜
)
```

有两件事要坚持。首先，`bank_id`始终源自经过身份验证的调用者，而不是源自请求主体可以影响的任何内容，这就是阻止租户 A 访问租户 B 记忆库的线路。其次，标签在用户自己的记忆中选择*哪个片*，其匹配模式（`any`包括无标签，`all`需要所有标签，`_strict`变体排除无标签，`exact`匹配集合）是关于组织的，而不是安全的。每当回答“A 存储的记忆是否应该被 B 调用？”时，就寻求一个新的记忆库，而不是更严格的标签。是没有。

## 导致泄漏的三个错误 {#three-mistakes-that-cause-leaks}

- **从请求中派生`bank_id`。** 如果记忆库 id 的任何部分来自请求正文、标头或客户端提供的字段，则调用者可以寻址其他人的记忆库。仅从经过身份验证的会话派生它。
- **使用标签作为租户墙。** 标签是组织，而不是隔离，默认匹配模式包括无标签记忆。没有标签的单个记忆存储会泄漏。租户获得记忆库。
- **CI 中无泄漏测试。** 当有人添加从错误变量构建 id 的代码路径时，边界就会发生漂移。存储为 A、读取为 B 测试是唯一能在客户之前捕获它的测试。

## 隔离第一，个性化第二 {#isolation-first-personalization-second}

要随身携带的三样东西。多租户记忆同时优化了记忆召回和隔离，并且隔离赢得了平局。决定是否泄漏的决定不是模式，而是租户边界是由存储层还是由您必须记住的过滤器强制执行的，因此使租户成为硬边界，并使其他所有内容成为标签。并将隔离视为一种可测试的属性：在 CI 中作为一个租户存储，作为另一个租户读取，断言没有任何返回。

找到正确的边界，剩下的就会变得更容易，而不是更难。删除变成了一句台词，个性化可以自由地广泛*里面*每个用户自己的记忆，并且您不再希望通过代码的每条路径都传递过滤器。

如果您想要一个存储强制边界，而不需要为每个租户建立一个数据库，Hindsight 可以为您提供记忆库作为单个部署上的独立认知记忆边界，通过一个 Docker 命令进行自托管或在 [Hindsight Cloud](https://hindsight.vectorize.io) 上进行管理。无论您基于什么构建，请在选择模式之前选择边界。
