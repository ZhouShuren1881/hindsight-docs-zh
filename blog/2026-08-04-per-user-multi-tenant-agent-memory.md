当 AI 产品在一个客户的会话中召回了另一个客户的数据，这就不是个性化功能出了问题，而是发生了数据泄露。每用户记忆看起来像一项功能，实际却是一条安全边界；而大多数“只要加个 `user_id`”的建议，恰恰把这点说反了。

如果你正在构建多租户 AI 产品，记忆是一个关键交汇点：一边是你已经在数据库中实施的隔离保证，另一边是一个专为主动混合上下文而设计的系统。这篇文章将介绍如何让两者保持分离：可采用的模式、真正关键的那项决策，以及如何证明隔离确实有效。

<!-- truncate -->

如果你刚接触这个领域，可以先了解[什么是智能体记忆](https://vectorize.io/what-is-agent-memory)。本文假设你正在为有多个客户的产品添加记忆，并希望每位客户的数据只属于他们自己。

## 为什么多租户记忆是一个不同的问题 {#why-multi-tenant-memory-is-a-different-problem}

单用户记忆只有一个任务：召回正确的信息。多租户记忆有两个任务：召回正确的信息，**并且**绝不召回其他人的信息。当这两个目标冲突时，隔离优先。只针对召回效果调优的记忆系统，会乐于呈现语义相似的事实，而不管这些事实属于谁。这正是绝不能上线的故障。

这是每种每用户设计都必须解决的矛盾。个性化希望广泛召回产品掌握的一切信息；隐私则要求封存每位用户的记忆。关键在于把这道封锁线设在由系统替你强制执行的位置，而不是设在每次调用时都得靠人记住去执行的位置。

## 真正关键的决策：硬边界还是软分区？ {#the-one-decision-that-matters-hard-boundary-or-soft-partition}

几乎所有“多租户记忆”指南最终都会简化成“给每条记录添加 `user_id`，再按它过滤”。这话不算错，但它掩盖了真正决定你是否会泄漏数据的选择。有两种本质不同的工具，不能互换：

| | 硬隔离边界 | 软分区 |
|---|---|---|
| **含义** | 每个租户/用户使用单独的存储 | 在一个共享存储中使用标签/过滤器 |
| **执行位置** | 存储层 | 每次调用时由你的查询执行 |
| **适用场景** | 租户、客户和每用户数据；一旦泄漏就是缺陷 | 有时需要交叉引用的范围（项目、主题） |
| **故障模式** | 难以泄漏，因为不存在跨边界查询 | 一旦忘记过滤或过滤错误就会泄漏 |

在 Hindsight 中，硬边界是**记忆库**。[记忆库就是召回边界](/blog/2026/07/16/bank-strategy-agent-memory)：`recall`、`retain` 和 `reflect` 每次都只指定一个 `bank_id`，并且只在该记忆库内操作；系统没有内置的跨记忆库查询。软分区则是**标签**：存入记忆时附加标签，召回时按标签过滤。

人们容易忽略的正是这一点，也是这件事至关重要的原因。**可能被忘记传入的过滤条件，不构成隔离。**Hindsight 的标签过滤默认使用 `any` 模式，甚至会*包含无标签记忆*，因为标签是整理提示，不是隔离墙。这个默认行为已经说明问题：如果某条记忆绝不能出现在错误的上下文中，就不要把它交给一个可能被省略的标签来把关。应将它放在由存储层强制执行的边界之后。

因此，每用户产品的规则很简单：**用户（或租户）是硬边界，所以应该有自己的记忆库。其他内容都用标签。**

## 每用户、每组织与共享知识 {#per-user-per-org-and-shared-knowledge}

真实产品通常不止有两个范围，而是三个：

- **用户私有**——个人的对话、偏好和历史记录。使用硬边界。
- **组织/工作区内共享**——团队惯例、共享项目，以及每个成员都应该看到的账户级事实。在组织层级设置硬边界。
- **全局产品知识**——文档、入门信息和所有人共用的默认值。存放在共享的、以读取为主的存储中。

映射方式很直接：以绝不能泄漏的对象作为记忆库。对每个人的记忆都绝不能触及其他人的消费级产品，可以使用 `bank_id="user:{id}"`；对同一账户内成员需要共享上下文、不同客户之间不能共享的 B2B 产品，可以使用 `bank_id="org:{id}"`。然后在边界内用标签标记记忆的*类别*，例如项目、来源和敏感级别。这样你可以按需过滤或交叉引用，却永远不会越过隔离墙。

来看一个具体的失败案例。一家支持服务 SaaS 把记忆范围放在同一个共享记忆库里的 `customer_id` **标签**上，而不是为每个客户使用一个记忆库。测试时一切正常。后来有一次 `retain` 调用漏传了标签——只忘了一个参数。由于默认匹配模式会包含无标签记忆，客户 A 的合同条款就出现在客户 B 的会话中。解决办法不是收紧过滤条件，而是建立真正的边界：每个客户一个记忆库，这样就没有过滤条件可忘。

## 跨边界读取，无需跨记忆库查询 {#reading-across-boundaries-without-a-cross-bank-query}

硬边界会引出一个显而易见的问题：如果 `recall` 每次只能指定一个记忆库，智能体如何在同一个答案中使用用户私有记忆、组织共享知识和产品全局文档？答案不是在边界上开个口子，而是在应用层组合结果。

可以采用扇出模式：从当前调用者有权访问的每个记忆库分别召回，再在结果交给模型之前合并并排序。权限检查由你的代码负责，这正是它应该在的位置；每次召回仍然只在各自的边界内进行。

```python
def recall_for(user, query, k=8):
    scopes = [
        user_bank(user.id),          # 仅该用户可见
        f"org:{user.org_id}",        # 在组织内共享
        "product:global",            # 以读取为主的产品知识
    ]
    hits = []
    for bank in scopes:
        hits += hs.recall(bank_id=bank, query=query, max_results=k)
    return rank(hits)[:k]            # 在应用中合并并重新排序
```

由此可以得到两个特性。用户只能读取权限逻辑交给他们的记忆库，因此仍然没有办法访问其他用户的记忆库。各个范围通过*相加*来组合：要扩大答案的范围，就添加调用者获准查看的记忆库，而不是放宽过滤条件。写入则与读取相对应：只写入一个记忆库，也就是用户私有记忆库；如果某条事实确实属于组织级别，就有意写入组织记忆库，而不是意外写进去。

## 可验证的隔离 {#isolation-you-can-prove}

如果租户隔离是一项安全属性，就应像测试安全属性那样测试它。不要因为正常流程看起来正确，就认定边界有效。这和构建[值得信赖的评估](/blog/2026/07/31/evaluate-agent-memory-system)遵循的是同一原则，只不过这里测试的是隔离，而不是检索。

一个最小化的跨租户泄漏测试应包含以下步骤：

1. **以 A 的身份存入，以 B 的身份读取。** 在租户 A 的记忆库中存入一条特征鲜明的事实，再从租户 B 的记忆库召回，并断言没有任何结果。
2. **用共享实体名称进行模糊测试。** 给两个租户使用相同的实体名称（“Acme 账户”“我们的预发布服务器”），并确认[实体解析](/blog/2026/06/29/entity-resolution-agent-memory)仍局限于各自的边界内，不会跨边界合并实体。
3. **攻击软分区。** 如果有任何地方依赖标签，就进行一次不带标签的存入，并确认无标签默认行为不会让该记忆出现在经过过滤的查询中。标签单独承担“隔离”职责时，问题就在这里暴露。
4. **删除后再次检查。** 完整删除租户 A，然后确认 A 的记忆已消失，而 B 的记忆不受影响。

核心可以归结为三行断言，其他测试不过是它们的变体：

```python
hs.retain(bank_id="tenant:A", content="A's secret: the launch date is March 3.")
leaked = hs.recall(bank_id="tenant:B", query="what is the launch date?")
assert leaked == [], f"cross-tenant leak: {leaked}"
```

要在 CI 中运行这个测试，而不是只手动运行一次。当有人添加了从错误变量构造 `bank_id` 的新代码路径，边界就可能被破坏；只有一个“以某租户身份存入、以另一租户身份读取”的测试，才能及时发现问题。

## 每用户删除与 GDPR 问题 {#per-user-deletion-and-the-gdpr-question}

被遗忘权会让边界选择带来回报，也可能让你付出代价。如果用户就是边界，删除只需一次操作：删除该用户的记忆库，其中的记忆、提取出的实体以及据此构建的图也会一并删除。过程简洁、完整且可审计。

再看软分区方案。如果所有用户的事实都存放在同一个索引中，只靠 `user_id` 过滤，那么“删除这位用户”就成了一项精细的手术：找出每一行、每个派生嵌入向量、每条与其相关的图边，在不影响其他人的前提下将它们删除，然后证明没有遗漏。其中一种方案可以直接交给合规审查人员；另一种只能祈祷自己做对了。由存储层实施隔离，能让删除审计简化为一条命令。

## 扩展到大量租户而不让系统失控 {#scaling-to-many-tenants-without-an-explosion}

对于“每个用户一个记忆库”，最显而易见的质疑是成本：一万名用户是否意味着一万个数据库？不应该。这是架构问题，不是数据建模问题。

Hindsight 将记忆库存储为同一个系统中的范围分区，而不是为每个记忆库单独配置数据库。因此，边界是逻辑上的，并且会在每次查询时强制执行，不必承担为每个租户单独搭建基础设施的运维负担。这让[系统能够扩展](/blog/2026/05/08/how-hindsight-scales)，同时容纳许多边界：你能获得独立存储的隔离效果，却只需一套基础设施。评估任何用于多租户场景的记忆系统时，都应该问这个问题；如果一个系统要求每个租户都使用真正独立的数据库，你就得在隔离和基础设施账单之间做选择，而你不该被迫做这样的选择。

一家为多用户 AI 产品服务的金融科技团队[从第一天起就采用了这种方案](/blog/2026/04/13/hindsight-financial-ai-memory-customer-story)：以每租户隔离作为边界，在单次自托管部署中用标签表示边界内较软的细分范围。

## 综合来看 {#putting-it-together}

代码中的模式很简单，这正是重点。真正起作用的是边界。

```python
# 硬边界：用户（或组织）就是记忆库。
def user_bank(user_id: str) -> str:
    return f"user:{user_id}"

# 只写入调用者自己的记忆库。标签用于边界内的分类。
hs.retain(
    bank_id=user_bank(current_user.id),
    content="Prefers dark mode and metric units. Works mostly on the billing service.",
    tags=["project:billing"],
)

# 召回时不会指定其他用户的记忆库，因此无法跨用户召回。
hits = hs.recall(
    bank_id=user_bank(current_user.id),
    query="what are this user's preferences for the billing work?",
    tags=["project:billing"],   # 边界内的软过滤条件
)
```

有两点需要牢记。第一，`bank_id` 始终根据经过身份验证的调用者生成，绝不能来自可受请求正文影响的值；这条规则能阻止租户 A 访问租户 B 的记忆库。第二，标签用来选择用户自己记忆中的*某个范围*，其匹配模式（`any` 包含无标签记忆，`all` 要求匹配所有标签，`_strict` 变体排除无标签记忆，`exact` 要求标签集合完全相等）用于组织记忆，而不是实施安全隔离。当问题“B 是否应该能够召回 A 存入的记忆？”的答案为否时，就建立新的记忆库，而不是收紧标签过滤条件。

## 导致泄漏的三个错误 {#three-mistakes-that-cause-leaks}

- **从请求中生成 `bank_id`。** 如果记忆库 ID 的任何部分来自请求正文、标头或客户端提供的字段，调用者就可能访问其他人的记忆库。只能根据经过身份验证的会话生成它。
- **把标签当作租户隔离墙。** 标签用于组织记忆，不负责隔离，而且默认匹配模式会包含无标签记忆。一次存入时漏掉标签就会造成泄漏。每个租户都应有自己的记忆库。
- **没有在 CI 中测试泄漏。** 一旦有人添加了从错误变量构造记忆库 ID 的代码路径，边界就可能被破坏。“以 A 的身份存入、以 B 的身份读取”是唯一能在客户发现之前捕获这类问题的测试。

## 先隔离，再个性化 {#isolation-first-personalization-second}

请记住三点。多租户记忆需要同时优化召回和隔离；两者冲突时，隔离优先。决定是否会泄漏的关键不是数据模式，而是租户边界由存储层强制执行，还是依赖你记得传入的过滤条件；因此，应把租户设为硬边界，其他内容都用标签表示。还要把隔离视为一项可测试的属性：在 CI 中以一个租户的身份存入，以另一个租户的身份读取，并断言没有任何结果。

设好边界之后，其他工作会更简单。删除只需一条命令；个性化可以在每位用户自己的记忆范围内充分展开；你也不必再担心代码的某条路径漏传了过滤条件。

如果你需要由存储层强制执行的边界，又不想为每个租户单独搭建数据库，Hindsight 可以在单次部署中提供相互隔离的记忆库，既可以通过一条 Docker 命令自托管，也可以使用托管服务 [Hindsight Cloud](https://hindsight.vectorize.io)。无论采用什么系统，都应先确定边界，再决定数据模式。
