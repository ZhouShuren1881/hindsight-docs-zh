Hindsight 0.4.16 引入了用于事件驱动记忆管道的 Webhook 系统、改进的搜索质量以及多项可靠性修复。

<!-- truncate -->

- [**Webhooks**](#webhooks)：React 使用新的 webhook 系统实时记忆事件。
- [**搜索质量**](#search-quality)：通过乘法得分提升提高记忆排名。

## Webhooks {#webhooks}

Hindsight 现在支持 webhook，让您可以实时对记忆事件做出反应，而无需轮询 API。

Webhooks 按记忆库注册，并在发生匹配事件时自动触发。支持两种事件类型：

**`retain.completed`** — 在记忆存储操作完成后（同步和异步）每个文档触发一次。当保留一批 N 个文档时，会触发 N 个单独的事件。

```json
{
  "event": "retain.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-05T12:00:01Z",
  "data": {
    "document_id": "doc-abc123",
    "tags": ["meeting", "q1-2026"]
  }
}
```

**`consolidation.completed`** — 在 Hindsight 完成将新记忆整合到观察中后触发。

```json
{
  "event": "consolidation.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-05T12:00:00Z",
  "data": {
    "observations_created": 3,
    "observations_updated": 1,
    "observations_deleted": null,
    "error_message": null
  }
}
```

**交付和重试**：失败的传递（非 2xx 响应或 30 秒后超时）会在 5 秒、5 分钟、30 分钟、2 小时和 5 小时时以指数退避方式重试，然后被标记为永久失败。交付任务与触发操作在同一数据库事务中排队，因此事件在服务器崩溃时仍然存在，并将在重新启动时重试。如果您的端点多次收到相同事件，请使用 `operation_id` 字段进行重复数据删除。

控制平面 UI 包括一个新的 Webhook 管理部分，您可以在其中注册端点、查看交付历史记录、检查有效负载以及重放失败的交付。

请参阅 [webhooks 文档](/developer/api/webhooks) 以获得完整参考。

## 搜索质量 {#search-quality}

不同的重排序器在非常不同的范围和分布中对输出分数进行建模 - 交叉编码器可能返回紧密聚集在零附近的值，而另一个模型将分数分布在很宽的范围内。之前的归一化对所有模型都一视同仁，这导致重排序器分数在与语义和 BM25 信号结合时要么占主导地位，要么被淹没，具体取决于配置的模型。

记忆召回排名现在应用时间邻近度和新近度作为重排序器分数之上的乘法提升，而不是将它们添加为单独的分数组成部分。这回避了归一化问题：提升不是对可能不兼容的尺度上的值进行求和，而是按比例缩放重排序器得分。最终排名对所配置的重排序器模型的绝对分数范围不太敏感。

无需配置。无论配置了哪个重排序器，该更改都会自动应用于所有记忆召回请求。

## 其他更新 {#other-updates}

**错误修复**
- 通过在后台线程而不是事件循环中运行数据库架构迁移来修复启动期间的异步死锁风险。
- 修复了 Webhook 传递，因此事务不再由于发件箱处理器中的数据库架构名称不正确而静默回滚。
- 修复了观察记忆召回，以使用`source_memory_ids`正确解析并返回相关块。
- 修复MCP记忆库级工具过滤以与FastMCP 3.x兼容。
- ​​修复了当LLM在所有重试中返回无效的JSON时发生的崩溃 - 现在可以干净地处理错误，而不是引发`TypeError`。
- 修复了没有源日期的观察，以保留 `None` 时间字段，而不是错误地填充它们。
