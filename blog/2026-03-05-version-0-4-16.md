Hindsight 0.4.16 引入了用于事件驱动记忆处理流程的 Webhook 系统、改进了检索质量，并修复了多项可靠性问题。

<!-- truncate -->

- [**Webhook**](#webhooks)：借助新的 Webhook 系统实时响应记忆事件。
- [**检索质量**](#search-quality)：通过乘法加权提升改进召回排序。

## Webhook {#webhooks}

Hindsight 现在支持 Webhook，因此您无需轮询 API，也能实时响应记忆事件。

Webhook 按记忆库注册；发生符合条件的事件时会自动触发。目前支持两种事件类型：

**`retain.completed`** — 每份文档的 Retain（存入）操作完成后触发一次（同步和异步操作均如此）。一次存入包含 N 份文档时，会分别触发 N 个事件。

```json
{
  "event": "retain.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-05T12:00:01Z",
  "data": {
    "document_id": "doc-abc123",
    "tags": ["meeting", "q1-2026"]
  }
}
```

**`consolidation.completed`** — Hindsight 将新记忆整合为观测后触发。

```json
{
  "event": "consolidation.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-05T12:00:00Z",
  "data": {
    "observations_created": 3,
    "observations_updated": 1,
    "observations_deleted": null,
    "error_message": null
  }
}
```

**投递与重试**：投递失败（收到非 2xx 响应，或 30 秒后超时）时，系统会按指数退避策略在 5 秒、5 分钟、30 分钟、2 小时和 5 小时后重试，之后将其标记为永久失败。投递任务与触发事件的操作在同一个数据库事务中入队，因此即使服务器崩溃，事件也会保留下来，并在服务器重启后重试。如果端点多次收到同一事件，可使用 `operation_id` 字段去重。

控制台界面新增了 Webhook 管理版块，可用于注册端点、查看投递历史、检查载荷以及重放失败的投递。

完整参考信息请参阅 [Webhook 文档](/developer/api/webhooks)。

## 检索质量 {#search-quality}

不同重排序模型输出的分数，其范围和分布可能相差很大：交叉编码器的分数可能紧密聚集在零附近，而另一个模型的分数则可能分布在很宽的范围内。此前的归一化方式对所有模型一视同仁。因此，将重排序分数与语义和 BM25 信号结合时，重排序分数可能占据主导，也可能被其他信号压过，具体取决于所配置的模型。

现在，Recall（召回）排序会在重排序分数的基础上，以乘法方式应用时间接近度和近期性加权提升，而不是把它们作为独立分数组件相加。这样可以避开归一化问题：加权提升会按比例缩放重排序分数，无需相加可能处于不兼容尺度的数值。因此，最终排序不再那么容易受到所配置重排序模型的绝对分数范围影响。

无需进行任何配置更改。无论配置了哪种重排序模型，这项更改都会自动应用于所有 Recall（召回）请求。

## 其他更新 {#other-updates}

**错误修复**
- 将数据库模式迁移放到后台线程运行，而不是在事件循环中运行，修复了启动期间可能发生的异步死锁。
- 修复了 Webhook 投递问题：发件箱处理器使用了错误的数据库模式名称，导致事务可能被静默回滚。
- 修复了观测检索逻辑，使其能够通过 `source_memory_ids` 正确解析并返回相关文本分块。
- 修复了 MCP 记忆库级工具筛选，使其兼容 FastMCP 3.x。
- 修复了 LLM 在所有重试中都返回无效 JSON 时发生的崩溃；现在会妥善处理错误，而不会抛出 `TypeError`。
- 修复了观测缺少来源日期时的处理方式，使时间字段保留为 `None`，而不是被错误填充。
