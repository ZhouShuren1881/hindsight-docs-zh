![智能体记忆中的实体解析与Hindsight](/img/blog/entity-resolution-agent-memory.webp)

大多数智能体记忆系统在必须决定两个提及是否指向同一个人时都会使用嵌入模型或LLM。 Hindsight 没有。它通过三个廉价、可检查的信号来解析实体：名称的相似程度、它们旁边显示的其他实体以及每个实体最近出现的时间。

这个选择对于 2026 年来说听起来几乎是复古的。事实证明，这对记忆来说是正确的选择，错误的合并比错过的合并更糟糕，并且你希望能够解释为什么系统认为“莎拉”和“新总理”是同一条记录。

这篇文章是对[智能体记忆](https://vectorize.io/what-is-agent-memory)如何进行实体解析的演练，使用Hindsight的实现作为具体参考。如果你想知道记忆层如何防止“莎拉”、“莎拉·陈”和“她”分裂成三个互不相关的历史，这就是机制。

## 概览 {#tldr}

- **实体解析** 正在决定两个不同的提及（“Sarah”、“Sarah Chen”、“她”）何时指代同一个现实世界实体，并将它们链接起来。
- Hindsight在事实提取过程中提取带有LLM的实体，但**解决**没有嵌入或LLM判断。
- 分辨率是三个信号的加权分数：**姓名相似度** (0.5)、**共现重叠** (0.3) 和 **时间新近度** (0.2)。清除`0.6`并且提及解析为现有实体；否则将创建一个新的。
- A **共现图** (`entity_cooccurrences`) 是区分器：实体出现在谁旁边可以消除两个同名的人的歧义。
- 系统是**对于合并刻意保守**，并且在检索时依靠图表而不是折叠它不确定的记录。
- 您可以预先使解析可靠：在记忆存储时传递一个`context`字符串，或者将已知的转换声明为**枚举实体标签**，这样就可以通过精确匹配来映射到固定词汇表。

## 实体解析实际上意味着什么 {#what-entity-resolution-actually-means}

三个术语可以互换使用，但不应该互换使用。 **实体提取** 正在将“Sarah”从句子中拉出来。 **实体解析** 正在确定这个“Sarah”是您上周存储的同一 Sarah。当智能体提出请求时，**基于实体的检索** 使用已解析的身份来拉回所有相关内容。

记忆需要这三者，但解决能力是最难的。提取是一个很好理解的LLM任务。检索是数据库连接。解决方案是中间的判断，也是记忆层成功或失败的地方。

在一个方向上出错，你就会过度合并：两个名叫 Alex 的不同人会陷入一个矛盾的记录中，而智能体则自信地告诉客户有关内部冲刺的信息。如果在另一个方向上出错，你就会融合不足：“莎拉”和“莎拉·陈”保持分开，所以关于莎拉的记忆会错过她一半的历史。整个工作就是远离这两条沟渠。

如果您评估记忆系统的不仅仅是检索分数，那么解决行为值得直接探索。这部分决定了你的智能体对一个人的记忆是连贯的还是支离破碎的。 （对于更广阔的景观，[各大框架比较](https://vectorize.io/articles/best-ai-agent-memory-systems) 是一张很好的地图。）

## 显而易见的方法，以及为什么Hindsight跳过它 {#the-obvious-approach-and-why-hindsight-skips-it}

2026 年的默认本能是嵌入每个提及的实体并通过余弦相似度进行合并，或者询问LLM“这些是同一个人吗？”两者都有效，并且都有真正的优势：嵌入捕获字符串匹配错过的语义等价性，并且 LLM 可以推理得分无法推理的上下文。

​​它们还存在对记忆比对搜索更重要的故障模式。嵌入相似性是一个黑匣子：当它错误地将“作为客户的 Apple”与“作为水果的苹果”合并时，您无法轻易看出原因，并且在不重新嵌入的情况下无法对其进行调整。每个实体每个事实的 LLM 调用速度很慢并且具有不确定性，并且它会偶尔且不可预测地确定两个陌生人是同一个人。

Hindsight 针对不同的属性进行优化：**错误的合并应该很少见，调试成本低，并且永远不会沉默。** 因此分辨率取决于工程师可以直接读取的信号。权衡是诚实的，嵌入会捕获这种方法遗漏的一些等价物，但遗漏是安全的（重复记录），而避免的错误是危险的（损坏的记录）。

## 三个信号 {#the-three-signals}

当一个新事实出现时，它提取的每个实体都会与同一记忆库中的现有实体进行匹配。对于每个候选人，Hindsight 计算加权分数：

```python
score  = name_similarity      * 0.5   #difflib 序列匹配器，0–1
score += cooccurrence_overlap * 0.3   #图中的共享邻居
score += temporal_proximity   * 0.2   #新近度，7 天窗口内

if best_score > 0.6:
    resolve_to(best_candidate)        #同一实体
else:
    create_new_entity()               #创造新纪录
```

**名称相似度（权重0.5）** 使用 Python 的 [`difflib.SequenceMatcher`](https://docs.python.org/3/library/difflib.html)，一个简单的字符串比率比较。 “Sarah”对“Sarah”得分 1.0； “Sarah”对“Sarah Chen”的得分接近 0.7。候选者本身是通过 PostgreSQL 的 [`pg_trgm`](https://www.postgresql.org/docs/current/pgtrgm.html) 三元组索引获取的，因此大型记忆库每次提及都会返回一些模糊匹配，而不是完整扫描。

**共现重叠（权重0.3）** 是有趣的，下一节完全是关于它的。

**时间接近度（权重0.2）** 将分辨率推向最近看到的实体。如果匹配的名字最后一次出现是在两天前，那么它就获得了大部分的时间权重；如果最后一次看到它是在六个月前，那么它几乎没有收入。您正在积极谈论的人更有可能是您所指的人。

`0.6`阈值是保守度刻度盘。提及必须清除这些信号之间的实际栏才能合并到现有记录中。如果没有，Hindsight 创建一个新实体而不是猜测，因为重复的实体是可恢复的，而错误的合并则不可恢复。

## 共现图可以消歧 {#the-co-occurrence-graph-does-the-disambiguation}

仅凭姓名相似度无法区分两个名叫 Alex 的人。图可以。

Hindsight 维护一个 `entity_cooccurrences` 表：每当两个实体出现在同一个事实中时，它们的配对计数就会增加。经过几周的对话，这构建了一张地图，显示谁出现在谁旁边。该地图承载着消歧负载。

这是使它具体化的场景。你的记忆库有两个亚历克斯。其中之一是**前端团队的 Alex**，与“React”、“Sprint 14”和“分阶段部署”同时出现。另一个是**Alex 在 Acme**，一位客户，与“续订”、“SOC 2 审查”和“Acme”同时出现。相同的名字，图中两个完全不同的社区。

一个新事实出现：“Alex 在 Acme 续订上标记了一个阻止者。”一提到“亚历克斯”，两位候选人的名字就被拉出来了。名称相似度为平局，各为 1.0。但事实也提到了“Acme”和“更新”，与客户-Alex 的同现重叠度很高，而与工程师-Alex 的重叠度为零。 0.3 的图表权重打破了平局，事实与右边的 Alex 相关。

没有任何嵌入可以仅通过名称来完成此操作，因为名称是相同的。解决这个问题的信号不是实体*是*，而是它的*附近*。这是大多数“只是嵌入”设计留在桌面上的部分。

## 如何解析实体功率检索 {#how-resolved-entities-power-retrieval}

如果解决方案不改变智能体的记忆，那么它就是学术性的。它为实体链接扩展提供动力，即Hindsight并行[混合检索](/blog/2026/03/27/parallel-hybrid-search)的实体臂。

当查询显示一组种子事实时，Hindsight 收集这些事实中的实体，并跟踪它们到提及相同实体的所有其他事实，根据候选者与种子共享的实体数量对候选者进行评分。询问“Acme 续订的状态如何”，找到一些种子事实，扩展就会引入涉及 Acme-Alex、续订和 SOC 2 审查的所有其他事实，甚至包括那些从未使用过“状态”一词的事实。

这就是分辨率质量复合的原因。每个正确解决的提及都会加深事实之间的联系，因此检索可以在更少的提示下找到更多的相关历史。它还与语义、因果和[时间意识](/blog/2026/03/12/spreading-activation-memory-graphs)链接一起运行，而不是替换它们，因此错过的实体匹配通常会被另一种策略覆盖。

## 如何确保实体解析 {#how-to-make-sure-entities-resolve}

解析器在设计上是保守的，这意味着当您不希望这样做时，它有时会分开两条记录。当分辨率精度很重要时，您有两个杠杆，并且都可以发挥作用*之前*在提取时间进行评分。他们比希望名字相似度达到 0.6 可靠得多。

### 给出提取器上下文 {#give-the-extractor-context}

每个记忆存储调用都在内容旁边带有一个可选的`context`字符串。它直接融入提取提示中，并且在归因谁说了或做了什么时，它优先于模型的默认值。

这对于文字记录和多方文本最为重要，其中“我”、“她”和“客户”本身就很模糊。告诉提取者谁在房间里，第一人称陈述就会被归因于正确的人，而不是默认为智能体。出来的实体已经指向了你所指名的人，所以决议的猜测要少得多。

```python
client.retain(
    content=transcript,
    context="支持智能体 Maria Lopez 和客户 John Doe (Acme) 之间的通话。",
)
```

### 在枚举模式下使用实体标签 {#use-entity-labels-in-enum-mode}

如果您已经了解完整的演员表、项目人员、产品目录、支持分类，请不要让解析器重新发现它。将这些值声明为记忆库的 `entity_labels` 配置中的 **实体标签**，并且提取被限制为将每个提及映射到其中一个。

在底层，`value`类型标签编译为允许值的 Pydantic `Literal[...]`，因此模型无法返回列表之外的任何内容。并且标签实体通过**精确匹配**解析，而不是模糊评分。 “Sarah”、“Sarah Chen”和“她”都崩溃到您定义的一个规范值上，0.6 阈值完全超出了范围。

```json
{
  "entity_labels": {
    "attributes": [
      {
        "key": "person",
        "type": "value",
        "values": [
          { "value": "sarah-chen", "description": "工程师主管，前端" },
          { "value": "alex-kim",   "description": "PM, growth" }
        ]
      }
    ]
  }
}
```

Enum 模式是Hindsight 提供的最可靠的分辨率杠杆。问题在于，它只有在集合已知且有界时才有效：对于固定团队或有限目录来说是理想的选择，对于你在工作中发现的开放式演员阵容来说是错误的。对于开放式情况，`context`字段加上共现图是正确的工具。 （如果您已经识别了上游实体，您还可以通过记忆存储调用上的 `entities` 字段直接传递它们。）

## 数据模型，简要 {#the-data-model-briefly}

三张桌子承载了整个系统，它们值得一看，因为它们令人耳目一新：

- **`entities`** 为每个规范实体保留一行：`canonical_name`、`mention_count`、`first_seen`、`last_seen`，以及在数据库级别执行不区分大小写的重复数据删除的 `UNIQUE (bank_id, LOWER(canonical_name))` 约束。
- **`unit_entities`** 是将事实映射到它们提到的实体的联结表，多对多。
- **`entity_cooccurrences`** 是图：`(entity_id_1, entity_id_2, cooccurrence_count, last_cooccurred)`，带有`CHECK (entity_id_1 < entity_id_2)`，因此每对都存储一次。

没有外部图形数据库，没有单独的实体向量存储。存储层与保存其他所有内容的嵌入式 PostgreSQL 相同，这使得自托管故事保持为一个 Docker 命令。

## 工程诚信科 {#the-engineering-honesty-section}

没有进入营销图表的部分才是真正的工作所在。

**标签有意通过精确匹配来解析。** 像`pedagogy:scaffolding` 这样的受控词汇实体完全跳过模糊匹配，因为三元组相似性会愉快地合并两个不同的标签值并悄悄地破坏分类法。这个边缘情况来自一个真正的错误。

**Unicode 小写是一个陷阱。** Python 的 `str.lower()` 和 PostgreSQL 的 `LOWER()` 在土耳其语点分 Á 上不一致：Python 产生两个字符的结果，Postgres 产生一个字符的结果。如果一侧的应用程序小写，另一侧的数据库小写，“伊斯坦布尔”将自行解析并失败。 Hindsight 让数据库在比较中进行小写，以便双方都同意。

​​**并发保留种族。** 两个worker可以尝试同时创建同一个实体。新实体进入 `INSERT ... ON CONFLICT DO NOTHING`，后续 `SELECT` 查找获胜的行，因此一场竞赛会产生一个实体，而不是两个实体或一个错误。提及计数和共现更新被推迟并以固定的锁定顺序刷新，以避免死锁。

## 它不做什么 {#what-it-doesnt-do}

诚实地对待边界比功能列表更重要。

Hindsight 不会追溯合并规范实体。如果“Sarah”和“Sarah Chen”最终成为两条记录，则稍后的共同提及会加强它们之间的图形链接，但不会将它们合并为一条记录。也没有实体分割操作：如果两个真人早期被错误地合并，系统没有内置方法将他们分开。并且没有别名表，身份是从名称加上图形结构中产生的，而不是策划的映射。

这些都是经过深思熟虑的选择，而不是疏忽。追溯合并和拆分正是批量发生灾难性错误的操作，而保守的路径（更喜欢重复，在读取时依赖于图表）会使故障模式变得无聊。如果您的用例需要积极的规范化，那么这是权衡其他系统的合理理由；这个优化是为了不破坏记忆。

## 如何看待自己 {#how-to-look-at-it-yourself}

如果您正在运行Hindsight，则可以直接查询实体表：`mention_count`向您显示哪些实体主导记忆库，`entity_cooccurrences`向您显示邻域。这是一个很好的方法来检查你的智能体实际上认为世界是什么样子。您可以 [自行托管整个事情](https://hindsight.vectorize.io) 并检查图表，或者从云免费层开始。

## 常见问题解答 {#frequently-asked-questions}

**Hindsight是否使用嵌入进行实体解析？**
没有。嵌入支持系统中其他地方的语义检索，但实体解析本身使用字符串相似性、共现图和时间新近度。目标是可调试的、保守的合并，而不是最大的记忆召回。

**它如何区分两个同名的人？**
​​他们的邻居。同现图记录了哪些实体一起出现，因此“Acme”附近的“Alex”会解析为与“Sprint 14”附近的“Alex”不同的记录，即使名称相同。

**不确定时会发生什么？**
它创建一个新实体。仅当加权分数清除`0.6`时，分辨率才会合并。重复的记录很容易忍受；错误的合并会破坏一个人智能体的记忆，因此系统会犯安全错误。

**如何确保合并正确的实体？**
两个杠杆，均在提取时。当您记忆存储时传递一个 `context` 字符串（它告诉提取器谁参与并优先进行归因），并且当已知转换时，将这些值声明为枚举实体标签，以便提及通过精确匹配映射到固定词汇表。两者都比事后依靠姓名相似度评分更可靠。

**如果它知道两条记录相同，它可以稍后合并它们吗？**
不会自动。它们之间的共现联系加强，这有助于检索到达两者，但Hindsight不会追溯折叠规范实体，也没有分裂操作。
