今天早上 9:14，我们中的一个人告诉Cursor，我们将放弃 ORM，并在数据访问的薄存储库层上进行标准化。 2:30，一位没有参与对话的队友询问我们的 Slack 机器人为什么要手写查询，它解释了存储库的决定，而没有任何人重新输入。在开车回家的路上，另一位工程师问我们的语音智能体“我们在什么地方进行数据访问？”并大声得到同样的答案。

三种不同的工具。三个不同的表面。一记忆。没有人重复自己，因为这些工具都没有真正忘记。

<!-- truncate -->

## 概览 {#tldr}

- 我们在同一项目上运行三个AI工具：[Cursor](/blog/2026/06/12/cursor-persistent-memory)用于构建，[OpenClaw](/blog/2026/05/27/openclaw-codebase-memory)作为我们的Slack/Discord智能体，[Vapi](/blog/2026/06/03/vapi-persistent-memory)用于语音。
- 每个人都有一个Hindsight集成，可以在回答之前回忆相关记忆，并在工作时保留持久的事实。
- 诀窍是一行配置：**将所有三个点指向同一个记忆库**。任何工具保留的事实都会被所有工具回忆起来。
- 结果不是“三个AI工具”。这是一名助理，恰好有三个前门。

## 设置是一个共享记忆库 {#the-setup-is-one-shared-bank}

每个Hindsight集成将其记忆范围限定为**记忆库**，一个单独的存储。在代码存储库中，编辑器集成将记忆库默认为存储库名称，因此它们自行排列。聊天机器人和语音智能体并不“在存储库中”，因此我们做了显而易见的事情，并为这三个机器人提供了相同的记忆库 ID。

```text
# Cursor：在仓库中默认使用项目记忆库
#（或在集成配置中设置显式记忆库 ID）

# OpenClaw：默认为每个对话记忆库，所以切换它
# 到一个静态共享存储 —dynamicBankId: false,bankId: "acme-web"

#Vapi：构建 webhook 时传递相同的记忆库 —
#   HindsightVapiWebhook(bank_id="acme-web")
```

每个工具的语法不同，但动作是相同的：将每个表面瞄准一个记忆库。这就是整个想法。没有要连接的总线，没有同步作业，没有每个工具的真相副本。每个工具都会读取和写入一个记忆库。当记忆重叠时，Hindsight会将它们整合为持久的[观察](/blog/2026/05/21/agent-memory-consolidation)，而不是堆叠三个几乎相同的笔记，因此共享存储保持干净，而不是变成一堆。有关此论证的较长版本，请参阅[每个AI工具都有一个记忆](/blog/2026/04/07/one-memory-for-every-ai-tool)。这篇文章是关于实际生活在其中的感觉。

## 共享记忆中的一天 {#a-day-in-the-shared-memory}

**早上，Cursor。** 决策是在做出决策的地方做出的：在编辑器中，任务中。 “我们正在放弃 ORM，一切都通过存储库。” Cursor 的智能体应用了变化，并且因为它在工作时保留了持久的事实，所以决策和推理都存储在记忆库中。我们没有运行记忆命令。我们刚刚打了电话并继续编码。

**下午，在 Slack 中。** 三个时区之外的队友打开 PR，看到一个手写的查询，并在频道中向我们的 OpenClaw 智能体询问该问题。 OpenClaw 回顾他们的问题，找到今天早上的决定，并用实际上下文回答：我们转移到存储库层，这就是原因，这就是它所在的位置。队友不在编辑器中，也不在站立会议中。无论如何，他们从Cursor所写的同一个记忆中继承了这个决定。

**晚上，打电话。** 有人离开了他们的笔记本电脑并打电话给我们的 Vapi 语音智能体，以便在明天之前检查方法的健全性。 “我们对数据访问做出了什么决定？”语音智能体从同一个记忆库中回忆并说出它。没有屏幕，没有搜索，没有 Slack 回滚。上下文完全脱离了键盘。

一天之内三个表面接触到同一个事实，并且这个事实只写了一次。

## 到底改变了什么 {#what-actually-changed}

我们已经运行了很长一段时间没有共享记忆的智能体，所以对比很鲜明。

- **我们不再对每个工具重新解释自己。** 以前，每个表面都是自己的岛屿：教导Cursor，单独教导Slack机器人，分别向语音智能体上的人通报。现在第二个和第三个工具已经知道了。
- **队友继承了他们不在场的决定。** 在 Slack 中提问的人从未见过 Cursor 会话。记忆将决定传递给他们，这是悄悄改变团队工作方式的部分。
- **上下文在表面切换后仍然存在，而不仅仅是会话。** 离开编辑器过去意味着离开上下文。现在从代码转移到聊天再到语音保留了线程，因为线程存在于记忆库中，而不是在任何一个应用程序中。
- ​​**工具的分歧较少。** 当三名助手阅读一份巩固的记忆时，他们倾向于给出一个答案，而不是三个略有不同的答案。

这一切都不需要新的工作流程。它需要删除一个：重复自己的工作流程。

## 为什么它会随着成长而坚持下去 {#why-it-holds-up-as-it-grows}

共享记忆只有在保持快速和准确的情况下才有用，因为它充满了跨三个噪声源的数月决策。有两件事承载着它。 整合使存储保持精炼，合并同一实体的相关事实，并解决“数据层”、“存储库更改”和“ORM 删除”是同一决策而不是三个决策的问题。检索必须在数量上保持敏锐，这是 [BEAM](/blog/2026/04/02/beam-sota) 测试的制度，在 1000 万个标记中，你不能将所有内容都塞进上下文中。 Hindsight 得分 64.1%；第二好的公布结果是 40.6%。这种余量可以让一个记忆库支持三种工具，而不会退化为噪音。

## 自己接线 {#wire-up-your-own}

如果您已经在项目上运行了多个AI工具，则这是当天下午的更改：

1. 为您使用的每个工具安装Hindsight集成。每个人在回答之前都会回忆并在工作时保留。
2. 给他们所有的**相同记忆库id**。在存储库中，编辑器会自动对齐；将聊天和语音智能体指向同一个记忆库（对于像 OpenClaw 这样的每次对话工具，将其切换到一个静态共享记忆库）。
3. 将它们指向[Hindsight Cloud](https://hindsight.vectorize.io)或自托管服务器。

然后在一种工具中做出决定并在另一种工具中询问。第二个工具已经知道了。

## 常见问题 {#frequently-asked-questions}

**工具会互相踩踏对方的记忆吗？**
没有。他们读写一个记忆库，整合将重叠的事实合并成单个观察，而不是重复它们。更多的作家会让记忆更丰富，而不是更混乱。

**所有东西都必须在同一个仓库中吗？**
没有。存储库名称只是编辑器集成的默认记忆库。任何工具都可以指向任何记忆库 ID，这正是聊天机器人和语音智能体加入项目记忆的方式。

**这仅适用于编码工具吗？**
不，这就是重点。这里的三个界面是编辑器、聊天智能体和语音智能体。任何具有Hindsight集成的东西都可以共享记忆库。

**私有或每用户上下文怎么样？**
对于应该分开的内容使用单独的记忆库。共享是您通过分发相同的记忆库 ID 做出的选择，而不是泄露所有内容的默认设置。
