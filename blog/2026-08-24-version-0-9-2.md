Hindsight 0.9.2 向 MCP 客户端开放知识库，让调用者直接指定 Recall 的时间窗口，而不必用英文在查询中描述；新增 GitHub Copilot 提供方和非对称嵌入前缀；还为运维人员增加了两个此前没有的上限：一个限制单次 Retain 可在内存中暂存的内容，另一个决定哪些记忆库可以拥有自己的向量索引。

- [**知识库现可通过 MCP 访问**](#the-knowledge-base-is-now-an-mcp-surface)：注册了 7 个面向智能体的原生工具，并可在目录树中查看刷新触发器。
- [**Recall：自行指定时间窗口**](#recall-supply-the-time-window-yourself)：直接设置 `temporal_window`，同时跳过由它取代的解析步骤。
- [**心智模型：控制刷新节奏并审计结果**](#mental-models-pace-the-refreshes-and-audit-the-results)：自动刷新之间可设置最小间隔，每次刷新都会报告类型化结果。
- [**GitHub Copilot 提供方与非对称嵌入**](#a-github-copilot-provider-and-asymmetric-embeddings)：使用 Copilot 订阅运行 LLM 通道，并为查询和文本段落设置不同前缀。
- [**Retain：以 MB 为单位的内存上限**](#retain-a-memory-ceiling-in-megabytes)：流水线会按预算控制内存；文档从 4 MB 到 90 MB 时，峰值内存保持平稳。
- [**按记忆库规模分配向量索引**](#vector-indexes-earned-by-bank-size)：达到行数阈值后，记忆库才会获得自己的索引，适用于拥有数千个记忆库的部署。

## 知识库现可通过 MCP 访问 {#the-knowledge-base-is-now-an-mcp-surface}

此前只能通过 HTTP 访问知识库，因此 MCP 客户端若要浏览或维护知识库，就必须再接入一套集成。现在有 7 个面向智能体的操作注册为原生 MCP 工具，其记忆库范围、租户身份验证和操作校验器行为都与现有工具相同：

`get_knowledge_base_tree`、`search_knowledge_base`、`get_knowledge_page`、`create_knowledge_folder`、`create_knowledge_page`、`update_knowledge_node`、`delete_knowledge_node`

智能体现在可以通过原本用于 Retain 和 Recall 的同一连接，读取、搜索和维护自己的维基。`export_knowledge_base` 仍仅通过 HTTP 和 CLI 提供：它会将整个记忆库打包为一个 Markdown 文件，这类内容不适合放进智能体的上下文窗口。

此外，**目录树现在会显示每个页面的刷新触发器**，因此无需打开页面，就能查看是什么条件会触发页面重建。

## Recall：自行指定时间窗口 {#recall-supply-the-time-window-yourself}

`RecallRequest` 接受包含 `start` 和 `end` 的 `temporal_window`。设置该参数后，系统会原样使用这个时间范围。

此前，限制时间范围的唯一方法是在查询文本中用英文描述，并寄希望于日期解析器能正确理解。日期选择器或已经按实际日历将“上季度”解析为日期范围的智能体，没有理由再走这一步。现在，已经知道时间范围的调用者可以直接传入它。

设置此参数还会跳过它所取代的提取步骤，而解析并非没有成本：这是纯 CPU 工作，由单个工作进程串行处理；对于文档大小的查询文本，耗时最高约 1.3 秒。查询整合和 Reflect 内部也会遇到完全相同的问题，因此这项优化不只对手动发起的调用有帮助。

## 心智模型：控制刷新节奏并审计结果 {#mental-models-pace-the-refreshes-and-audit-the-results}

为会自动刷新的心智模型提供了两项控制能力。

**设置自动刷新的最小间隔。** `HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS` 用于设置同一心智模型两次自动刷新之间的最短间隔，适用于整合后触发和 cron 定时任务。在间隔内触发的刷新不会被丢弃，而是暂存起来，等间隔结束后再执行；此期间后续触发都会合并到这次暂存的刷新中，而执行时也会纳入等待期间累积的所有内容。因此，一连串小批量 Retain 只需刷新一次，而不是每次 Retain 都刷新。通过 API、MCP 或控制平面显式发起的刷新会忽略此间隔，立即执行。该设置支持分层配置：可在服务器级、记忆库级设置，也可通过 `trigger.min_refresh_interval_seconds` 对单个心智模型设置；其中设置为 `0`，可让某个高频心智模型不受记忆库级间隔限制。默认值为 `0`，因此只有主动设置后才会改变行为。

**每次刷新都会报告执行结果。** 刷新操作现在会在操作列表和单条操作详情中携带类型化的 `outcome`，失败时还会提供 `failure_reason`；这些信息不再埋在会被下一次刷新覆盖的调试元数据中。结果依据可观察到的效果判定，而非依据执行它的代码路径。因此，如果候选内容与已存储文档完全相同，结果会报告为 `content_unchanged`，而不是声称写入了内容。现在无需外部采样器持续轮询每个心智模型的最新状态，就能衡量它们在一段时间内的实际行为。刷新操作还会标明 `mental_model_id`，而此前的操作列表无法提供这一信息。

控制平面现在会显示**每个心智模型的待更新状态**，并在所有显示位置采用一致的描述。

## GitHub Copilot 提供方与非对称嵌入 {#a-github-copilot-provider-and-asymmetric-embeddings}

- **使用 Copilot 订阅运行 LLM 通道。** 设置 `HINDSIGHT_API_LLM_PROVIDER=github-copilot`，无需 API 密钥。
- **为查询和文本段落设置不同前缀。** 许多嵌入模型要求查询与存储文本段落使用不同的指令前缀；将二者合并会降低检索质量。现在，文本输入提供方可以分别设置 `HINDSIGHT_API_EMBEDDINGS_QUERY_PREFIX` 和 `HINDSIGHT_API_EMBEDDINGS_PASSAGE_PREFIX`；此前无法区分这两类输入。
- **由你指定实体名称时进行精确解析。** `update_memory` 和 Retain 现在接受 `resolve_entities` 标志。Retain 仍使用模糊解析，这适合处理提取出的名称；人工维护的编辑现在可以要求精确匹配。这样，你输入的实体名称会被视为明确指令，而不是需要与图中的实体协调处理的猜测。
- **批量 Retain 会路由到支持批处理的模型成员。** 因此，多 LLM 配置会将批量任务交给实际支持批处理的后端。

## Retain：以 MB 为单位的内存上限 {#retain-a-memory-ceiling-in-megabytes}

`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`（默认值为 `128`）限制单次 Retain 操作可以暂存多少尚未写入的提取结果。

`HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE` 已限制同时处理的文本分块数量，但只有当每个分块的内存成本可预测时，数量才能代表内存上限；实际并非如此，因为每个分块所含的事实数量取决于提取器从中找到多少事实。这个预算才是估算工作进程内存需求的依据：无论文档大小如何，单次 Retain 的峰值内存大致由该数值决定，再乘以并发 Retain 槽位数。超过预算时，提取会等待写入流程跟上，而不会继续占用更多内存。设置为 `0` 可恢复此前仅按数量限制的行为。

流水线前半部分经过重构，使这个上限真正发挥作用。过去，仅为一个 45 MB 的正文估算大小就会分配 385 MB；随后将其切分为文本分块，又会额外占用 200 MB，而且这两步都发生在生成任何事实之前。现在，针对 4、16、45 和 90 MB 的文档，大小估算的内存占用均为 9.6 MB，分块所占内存则几乎为零；大小估算和分块也比以前稍快。超大文档拆分为子批次时，现在也会以流式方式处理，不再一次性保留所有切片：对于 90 MB 的正文，拆分和预处理阶段的峰值内存从 204 MB 降至 26 MB；处理 16 MB 正文时同样为 26 MB。仍会随文档大小增长的部分只有提交的正文，因为它必须一直保留到存储完成。运行时分块也不再依赖 langchain，因此安装中不再需要 `langchain-core` 和 `langsmith`。系统通过覆盖每种分隔符层级的差异测试，将分块边界与 langchain 自身的输出保持一致；边界一旦偏移，就会在不易察觉的情况下重新切分每份已存储文档。

## 按记忆库规模分配向量索引 {#vector-indexes-earned-by-bank-size}

`HINDSIGHT_API_VECTOR_INDEX_MIN_ROWS` 用于设置记忆库中每种事实类型需要达到多少行，才会为该类型创建独立向量索引。

在大规模部署中，这一点很重要：每个记忆库的索引都建在共享的记忆表上，而且其他每个记忆库的查询计划都会考虑这些索引。如果不加区分地为每个记忆库创建 3 个索引，就会限制单个部署可容纳的记忆库数量。将阈值设为例如 `10000` 后，小型记忆库会改用精确搜索；在这种规模下，精确搜索既更快也能获得精确结果。大型记忆库则会获得实际需要的索引，后台维护会在其跨过阈值时创建索引，低于阈值时删除索引。`HINDSIGHT_API_VECTOR_INDEX_MAINTENANCE_MIN_INTERVAL_SECONDS` 可避免记忆库在阈值附近波动时反复创建和删除同一索引。

默认值仍为 `0`，表示关闭阈值；因此每个记忆库仍会像以前一样在创建时建立索引。

还有两项面向同一类用户的小改进：**记忆库列表现在支持分页**；**工作进程执行会被追踪，并加入调用者的追踪链路**，因此异步 Retain 可以端到端查看，不会在 API 返回后失去踪迹。
