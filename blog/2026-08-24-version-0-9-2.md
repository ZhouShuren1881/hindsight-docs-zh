Hindsight 0.9.2 向MCP客户端开放知识库，让调用者手动记忆召回时间窗口而不是用英语书写，添加GitHubCopilot提供者和不对称嵌入前缀，并为操作员提供了两个他们以前没有的上限 - 一个是记忆存储可以在记忆中保存的内容，另一个是记忆库得到自己的向量索引。

- [**知识库现在是一个MCP表面**](#the-knowledge-base-is-now-an-mcp-surface)：七个面向智能体的操作注册为本机工具，加上树上的刷新触发器。

## 知识库现在是一个MCP表面 {#the-knowledge-base-is-now-an-mcp-surface}

知识库只能通过 HTTP 访问，因此 MCP 客户端必须退回到第二个集成路径来浏览或维护它。七个面向智能体的操作现在是本机MCP工具，具有与现有操作相同的记忆库范围、租户身份验证和操作验证器行为：

`get_knowledge_base_tree`、`search_knowledge_base`、`get_knowledge_page`、`create_knowledge_folder`、`create_knowledge_page`、`update_knowledge_node`、`delete_knowledge_node`

智能体现在可以通过它已经用于记忆存储和记忆召回的相同连接来读取、搜索和维护自己的维基。 `export_knowledge_base` 仅保留 HTTP 和 CLI — 它将整个记忆库作为一个 markdown 包返回，这在智能体的上下文窗口中没有任何作用。

旁边还有**每个页面的刷新触发器在树上可见**，这样您就可以看到导致页面重建的原因，而无需打开页面进行查找。

## 记忆召回：自己提供时间窗口 {#recall-supply-the-time-window-yourself}

`RecallRequest` 采用 `temporal_window` 以及 `start` 和 `end`。设置它，该范围将被逐字使用。

到目前为止，限制时间的唯一方法是在查询文本中用英语表达它，并希望日期解析器同意你的观点——日期选择器或已经根据真实日历解析“上季度”的智能体没有理由这样做。现在，已经知道范围的呼叫者可以直接说出来。

设置它也会跳过它所替换的提取，并且该解析不是免费的：它是纯 CPU 工作，通过单个工作程序序列化，在文档大小的查询文本上花费高达约 1.3 秒。这正是查询整合和内部问题的形式，因此节省的费用比您手动拨打的电话要多。

## 心智模型：调整刷新速度并审核结果 {#mental-models-pace-the-refreshes-and-audit-the-results}

​​两个控件可供任何运行自行刷新模型的人使用。

**自动刷新的一层。** `HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS` 设置同一模型的两次自动刷新之间的最小间隔 - 整合后触发器和 cron 计划。在窗口内触发的触发器不会被丢弃：它的刷新会被暂停，直到窗口关闭，同时每个进一步的触发器都会折叠到那个暂停的刷新中，它仍然会看到在等待时累积的所有内容。因此，大量的小保留需要花费一次刷新，而不是每个记忆存储一次。来自API、MCP或控制平面的显式刷新会忽略楼层并立​​即运行。它是分层的——在服务器范围内、每个记忆库或每个模型上使用`trigger.min_refresh_interval_seconds`进行设置，其中`0`将一个热门模型从记忆库范围的底层中免除。默认值为 `0`，因此在您选择一个值之前不会发生任何变化。

**每次刷新都会报告它所做的事情。** 刷新操作现在在操作列表和单次读取上携带类型化的`outcome`（以及失败时的`failure_reason`），而不是埋藏在下次刷新覆盖的调试元数据中。结果是由可观察的效果决定的，而不是由产生它的代码路径决定的，因此与存储的文档相同的候选者报告`content_unchanged`，而不是声明写入。测量模型在窗口上的实际行为不再需要外部采样器轮询每个模型的最新状态。刷新操作也将其命名为 `mental_model_id`，之前的列表无法告诉您这一点。

控制平面显示**每个模型的陈旧程度**，在它出现的任何地方都以相同的方式描述。

## A GitHub Copilot 提供者，以及非对称嵌入 {#a-github-copilot-provider-and-asymmetric-embeddings}

- **在 Copilot 订阅上运行 LLM 通道。** 设置 `HINDSIGHT_API_LLM_PROVIDER=github-copilot` — 无需 API 钥匙。
- **查询和段落的不同前缀。** 许多嵌入模型期望查询的指令前缀与存储的段落的指令前缀不同，并且将两者合并会降低检索质量。 `HINDSIGHT_API_EMBEDDINGS_QUERY_PREFIX` 和 `HINDSIGHT_API_EMBEDDINGS_PASSAGE_PREFIX` 现在为文本输入提供程序独立设置，以前无法区分两侧。
- **当您是唯一命名者时，精确的实体解析。**`update_memory`和存储记忆采用`resolve_entities`标志。 记忆存储保持模糊解析，这对于提取出来的名字是正确的；精心策划的编辑现在可以要求精确匹配，因此您输入的实体名称是一条指令，而不是根据图表进行协调的猜测。
- **批处理记忆存储通过具有批处理能力的模型成员运行**，因此多LLM 设置将批处理工作路由到实际支持它的后端。

## 记忆存储：以兆字节为单位的记忆上限 {#retain-a-memory-ceiling-in-megabytes}

`HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB`（默认`128`）限制了一个记忆存储操作可以保存多少提取但未写入的状态。

`HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE`已经限制了正在运行的块的数量，但是如果块的成本是可预测的，那么计数只是记忆的限制——而事实并非如此，因为无论提取器在其中找到多少事实，一个块都携带着多少事实。预算是衡量员工规模的数字：每个记忆存储的峰值大致是这个数字（无论文档如何）乘以并发记忆存储槽位。超出预算，提取会等待写入路径赶上而不是增长。 `0` 恢复之前的仅计数边界。

管道的前半部分被重建，使那个天花板变得有意义。调整 45 MB 主体的大小用于分配 385 MB，并将其分块另外 200 MB — 两者都是在单个事实存在之前。现在，4、16、45 和 90 MB 文档的大小都保持不变，为 9.6 MB，实际上为零，并且大小调整和分块速度比以前更快。将超大文档拆分为子批次流，因此切片不再同时保留：拆分和屏幕阶段的峰值从 90 MB 正文上的 204 MB 变为 26 MB，现在在 16 MB 上仍为 26 MB。文档中剩下的就是提交的正文本身，它必须存活下来才能存储。分块也不再依赖于运行时的 langchain，这会从安装中删除 `langchain-core` 和 `langsmith`；通过跨每个分隔层的差异测试将边界固定在 langchain 自己的输出上，因为移动的边界会默默地重新分块每个存储的文档。

## 由记忆库大小获得的向量索引 {#vector-indexes-earned-by-bank-size}

`HINDSIGHT_API_VECTOR_INDEX_MIN_ROWS` 设置在一种事实类型获得其自己的向量索引之前，记忆库需要多少个记忆。

这在规模上很重要：每个记忆库索引都位于共享记忆表上，并由每个_其他_记忆库的查询进行计划，因此每个记忆库创建三个无条件地设置了一个部署可以容纳的记忆库数量的上限。将其设置为类似 `10000` 的值，小记忆库会回退到精确搜索 - 在该大小下，这既更快又准确 - 而大记忆库则获得它们实际需要的索引，当它们越界时，由后台维护构建和删除。 `HINDSIGHT_API_VECTOR_INDEX_MAINTENANCE_MIN_INTERVAL_SECONDS` 使记忆库保持在阈值上徘徊，避免重复构建和删除相同的索引。

默认保持`0`，这意味着阈值关闭，每个记忆库在创建时都被索引，与以前一样。

针对同一受众的两个较小的事物：**记忆库列表已分页**和**worker 运行被跟踪并加入调用者的跟踪**，因此异步存储记忆是端到端可见的，而不是在API返回后消失。
