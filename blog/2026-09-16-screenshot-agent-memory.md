一条支持对话包含两段文字、一张 CLI 输出截图和另一句话。请求 ID、记忆库 ID 和错误码只存在于图片中。

智能体读了并记住文字，截图却只变成某个存储桶里的文件。

<!-- truncate -->

## 要点 {#tldr}

- `content` 接受有序文本、图片和文件块，按附件实际位置读取。
- 召回事实携带其来源附件，按事实而非分块关联。
- 归属不是按位置猜测，而是询问提取器；无法解析的引用会丢弃，不会凑成最近的图片。
- 配置模型无法读图时，存储在写入任何字节前失败。
- 随 v0.10.0 发布，Hindsight Cloud 和自托管均可使用。

## 不只是上传文件 {#this-isnt-file-upload}

Hindsight Cloud [从三月起支持文件上传](https://hindsight.vectorize.io/blog/2026/03/09/hindsight-document-upload)：上传 PDF、提取文字并存储。文件本身就是内容单元时，这仍是正确方式。

对话中途粘贴的截图不是独立文档。将其独立处理，会丢失最重要的关系：它被附在*那里*、那句话之后，作为该陈述的证据。

新增两项能力都与位置而非存储有关：附件按实际位置读取，两段间的图表仍按两段之间解读；来源按事实关联，因此召回“声明为 image/png 的 PNG 出现尺寸不匹配错误”时，可返回该句来源截图，而非整个文档或分块中所有图片。

## 保持一个字符串，才能兼容既有流程 {#one-string-or-everything-breaks}

直观实现会让新内容结构贯穿整个流程。Hindsight 则在 API 边界将块展平为单一规范正文，每个附件成为独立段落中的不可分占位符。

太多功能已依赖字符串内容：内容哈希幂等性、`update_mode=append`、分块增量提取、`reprocess_document`、导出和导入。因此文本展平必须完全等价。下面的内容：

```json
{"content": "导入器采用四舍五入。"}
```

与下面的内容：

```json
{"content": [{"type": "text", "text": "导入器采用四舍五入。"}]}
```

产生相同存储正文和内容哈希。占位符只在提示词组装时展开为多模态内容，图片精确位于占位符原处。附件字节不会随后台操作请求传输，而是先写入按 SHA-256 内容寻址的存储，重试已入队操作不会再携带 Base64 数据。

## 询问，而非猜测 {#asking-rather-than-guessing}

按距离归属会给事实配上最近图片，按分块归属会让所有事实配上全部附件，两者都能给出结果，也都经常错误。

提示词改为给附件编号，询问提取器每条事实需要哪些附件，并严格要求：只有不看附件就无法陈述事实时才列出它。事实返回整数编号，按该分块的占位符顺序解析。

无法解析的编号会被丢弃。只有两个附件却引用附件 3 的事实，不会附上证据；代码注释说明，将其改为最近附件就是虚构来源。零和负数同样丢弃，纯文本分块即使模型声称用了图片，也无法解析出附件。

因此系统可能返回没有附件证据的事实，这是正确的失败方式。“无法展示来源”仍可用，“这张截图并不支持该陈述”则不可用。

测试覆盖两个方向：用真实模型读取图表，其事实不在正文中，要求部分事实引用图片，否则证据不可见；也要求并非所有事实引用图片，否则它在为不受图片支持的文字提供虚假证据。

需要准确理解：这是模型判断，外层有确定性和范围检查，并非正确性保证。

## 一张图片占约 22 个字符 {#an-image-costs-22-characters}

分块有字符预算。按真实图片大小计数，会让带三张截图的长文与自身截图分离，早期实现确实如此。

现在预算只计算文字，附件占位符约占 22 个字符。真正限制是与提供商单次请求容量对应的独立分块附件上限，默认 8。一句话和后续十张图片可以留在同一分块，因为拆开会破坏理解图片所需的唯一上下文；超限不会拒绝，只会产生更多分块。

## 同一响应中的两类附件 {#two-kinds-of-attachments-in-one-response}

召回响应在两个位置携带附件，含义有意不同。

| | `chunks{}.attachments` | `results[].attachments` |
|---|---|---|
| **范围** | 分块文本引用的全部附件 | 提取器归属于该事实的附件 |
| **粒度** | 按分块 | 按事实 |
| **回答的问题** | “来源里有哪些内容？” | “该陈述基于什么？” |
| **为空时** | 分块没有附件 | 事实来自文字 |

渲染来源文档使用分块附件；向用户解释智能体为何相信某事，使用事实附件，因为前者会夸大证据。没有附件时省略字段，不返回空集合。

## 获取图片 {#getting-the-image-back}

召回结果不携带字节，而携带引用：

```json
{
  "id": "8f41c2ad9e6b",
  "hash": "8f41c2ad9e6b47f0...",
  "kind": "image",
  "media_type": "image/png",
  "byte_size": 68344,
  "filename": "error-screenshot.png",
  "url": "/v1/default/banks/acme-support/attachments/8f41c2ad9e6b"
}
```

对该路径执行 `GET`，按存储时声明的 Content-Type 返回字节。授权针对记忆库，使用与召回相同的凭据。附件不存在或记忆库不可见均返回 404，防止探测库内内容。ID 来自内容哈希，URL 字节不可变化，可无限期缓存。

这份引用足以支持两种常见用途。

**作为引用展示。** 获取前已有 `media_type`、`byte_size` 和原始 `filename`，可以在答案旁渲染缩略图，或为 PDF 提供下载链接，仅在用户需要时下载字节。

**重新提供给模型。** 获取字节、转为 Base64，再以图片块放入下一次提示词，结构与存储时相同。召回“错误是尺寸不匹配”的智能体，可以将原截图交给视觉模型提出新问题。

## 拒绝处理的情况 {#where-it-refuses}

这里多数有趣的工程工作都在失败路径上。

**没有视觉模型就不能存图片。** 带图请求在入口、写入前失败。若只提取文字并静默跳过图片，文档看似已存储，重要信息却丢失。明确报错可恢复，静默遗漏则无法发现。

**“大概可以”也算不支持。** 能力有支持、不支持、不确定三种状态，不确定时拒绝。非 OpenAI 的兼容端点会报告不确定，涵盖大多数本地和网关部署。必须由运维人员显式设置视觉能力标志，而非默认假定支持。

**批量模式不兼容。** 启用批量 retain API 时，带附件请求直接失败，因为该路径直接构建提供商请求体，不经过交错内容组装。

有一种情况会降级而非拒绝：存储中的附件字节丢失时，提示词插入“附件不可用”标记，不使整个存储失败。

## 存储机制 {#storage-briefly}

附件在记忆库内按 SHA-256 去重，同一截图存入四十个文档，也只保存一个二进制对象和一行记录。文件名不与字节绑定，因为同一 PDF 在一个文档中可叫 `policy-v1.pdf`，另一个中叫 `escalation-runbook.pdf`。清理依据引用，重新摄取时去掉图片就删除关联，最后一个引用消失时删除对象。

升级迁移新增两个空表，并在记忆表上增加数组列。成熟部署中后者可能不小，应像任何大规模加列操作一样规划。

## 需要了解的限制 {#limits-worth-knowing}

| 限制 | 值 | 说明 |
|---|---|---|
| 来源类型 | 仅内联 Base64 | 尚不支持 URL 获取或预上传句柄 |
| 最大大小 | 每附件 20 MB | 解码后大小，服务器级设置 |
| 最大数量 | 每个 retain 条目 50 个 | 更多附件应分到多个条目 |
| 每分块数量 | 默认 8 | 可按记忆库配置，不会因此拒绝请求 |
| 媒体类型 | 任意格式合法的类型 | 无白名单，无法读取时返回提供商错误 |
| 按事实来源 | `facts` 提取模式 | `chunks` 和 `verbatim` 使用分块全部附件 |
| MCP | 尚不支持 | 附件通过 HTTP 返回，不通过 MCP 工具 |
| Hindsight Cloud | 已支持 | 运行 0.10.0，已配置视觉模型 |

提取模式限制尤其容易意外：使用 chunks 或 verbatim 模式时，事实就是分块，因此带有分块全部附件，不询问模型。

## 常见问题 {#faq}

**需要修改现有代码吗？**
不需要。`content` 仍接受普通字符串，连内容哈希都保持不变。每个条目可自主选择块模式。

**将图片发送给不能读图的模型会怎样？**
存储明确报错，而非丢弃图片。非 OpenAI 的兼容提供商报告未知能力，显式设置视觉标志前会被拒绝。

**事实与图片关联保证正确吗？**
不保证，提取器判断事实需要哪些附件。保证的是无法解析为分块真实附件的引用会被丢弃，不会近似匹配，因此更可能缺少引用，而非给出错误引用。

**能通过 MCP 获取附件吗？**
0.10.0 尚不支持。附件字段在 HTTP 响应中，MCP 召回工具只返回事实。
