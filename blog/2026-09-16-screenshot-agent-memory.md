![从智能体记忆中召回的事实，以及提取该事实所依据的截图](/img/blog/screenshot-agent-memory.png)

收到一条支持对话：两段文字、一张 CLI 输出截图，后面还有一句话。请求 ID、记忆库 ID 和错误码只存在于一个地方：图片里。

智能体读了文字，也记住了文字。截图却成了某个存储桶里的一个文件。

<!-- truncate -->

## 要点 {#tldr}

- `content` 现在接受由文本块、图片块和文件块组成的有序列表，因此附件会在它所在的位置被读取。
- 召回的事实会带回提取该事实时使用的附件；关联粒度是事实，而不是分块。
- 附件归属不会根据位置推断。系统会询问提取器；无法解析的回答会被丢弃，而不会随便配给最近的图片。
- 如果配置的模型无法读取图片，存储操作会在写入任何字节前失败。
- 此功能随 v0.10.0 发布，可用于 Hindsight Cloud 和自托管部署。

## 这不是文件上传 {#this-isnt-file-upload}

Hindsight Cloud 从三月起就[支持文件上传](/blog/2026/03/09/hindsight-document-upload)：上传 PDF、提取文本，再存入记忆。如果文件本身就是处理单位，这仍然是合适的工具。

在对话中途粘贴的截图不是一份文档。把它当成文档处理，就会丢掉最值得保留的关系：截图是在*那里*、那句话之后附上的，用来支持那项陈述。

这里新增的两项能力关注的是位置，而不是存储方式。附件会在它所在的位置被读取，所以夹在两段文字之间的图表会作为两段文字之间的图表来读取。来源则按事实关联，因此 Recall（召回）返回“这个错误是 PNG 声明为 image/png 时发生的尺寸不匹配”时，可以一并返回产生这句话的截图，而不是整份文档，也不是分块中的每张图片。

## 一个字符串，否则一切都会出问题 {#one-string-or-everything-breaks}

直观的实现方式，是让新的内容结构贯穿整条处理流程。Hindsight 采取了相反的做法：在 API 边界将内容块展平为单一规范正文，并把每个附件转换为独立段落中的原子占位符。

这是因为已有太多功能依赖内容是一个字符串：基于内容哈希实现幂等、`update_mode=append`、分块差异增量提取、`reprocess_document`、导出和导入。因此，文本展平前后的结果必须完全等价。下面两种写法：

```json
{"content": "The importer rounds half-up."}
```

以及：

```json
{"content": [{"type": "text", "text": "The importer rounds half-up."}]}
```

会产生相同的存储正文和相同的内容哈希。占位符只会在一个地方重新展开为真正的多模态部分：组装提示词时。每张图片都会回到占位符原来的位置。字节不会经由请求载荷传输；它们会先写入存储，并按 SHA-256 内容寻址，因此重试已入队的操作时，不必再次携带 Base64 数据。

## 询问，而不是猜测 {#asking-rather-than-guessing}

直观的做法全都不对。按距离归属，事实就会配上最近的图片；按分块归属，每条事实就会配上所有附件。这两种做法都会给每条事实提供答案，而且经常是在说谎。

改用提示词给附件编号，并询问提取器每条事实需要哪些附件，同时严格要求：只有不查看附件就无法陈述该事实时，才列出附件。事实会带回整数编号，再按该分块中的占位符顺序解析这些编号。

编号无法解析时怎么处理，才是关键。编号 3 无法对应只包含两个附件的分块，因此这条事实不会引用任何附件。代码注释也说明原因：改为附上最近的图片，就等于虚构来源。零和负数同样会被丢弃；即使模型声称使用了图片，纯文本分块也不会解析出任何附件。

因此，系统可能返回没有关联证据的事实；这才是正确的失败方式。“我无法指出它的来源”仍有用；“这张截图支持不了这个说法”则没有用。

测试固定了这两方面的行为，其中一项会让真实模型读取一张图表，而图表中的事实并未出现在正文里，并要求结果满足这样的划分：有些事实必须引用图片，否则证据就不可见；但不能所有事实都引用图片，否则就会把不支持正文内容的图片也当作证据。

需要准确理解这一点：归属由模型判断，外围再进行确定性的范围检查。这不是正确性保证。

## 一张图片占 22 个字符 {#an-image-costs-22-characters}

分块有字符预算。若按图片真实大小计入，一篇带三张截图的长文就可能和自己的截图分到不同分块。早期版本确实出现过这种情况。

现在，预算只计算文本，附件按占位符计费，长度约为 22 个字符。另有单独的每分块附件数量上限，与提供商单次请求可接受的数量相匹配，默认值为 8。一句话后面跟着十张图片时，它们会留在同一分块，因为拆开会破坏理解这些图片所需的唯一上下文。超过上限不会导致拒绝，只会生成更多分块。

## 同一响应中的两类附件 {#two-kinds-of-attachments-in-one-response}

Recall 响应会在两个位置返回附件数据，两处的含义有意不同。

| | `chunks{}.attachments` | `results[].attachments` |
|---|---|---|
| **范围** | 分块文本引用的所有内容 | 提取器归属于该事实的附件 |
| **粒度** | 按分块 | 按事实 |
| **回答的问题** | “来源中这里包含什么？” | “这项陈述依据什么？” |
| **为空时** | 分块没有附件 | 事实由文本陈述 |

要渲染来源文档时，使用分块附件。要向用户说明智能体为何相信某件事时，使用事实附件，因为分块附件会夸大证据范围。没有内容可返回时，字段会被省略，而不是以空值返回。

## 取回图片 {#getting-the-image-back}

Recall 结果不包含字节，只包含一个引用：

```json
{
  "id": "8f41c2ad9e6b",
  "hash": "8f41c2ad9e6b47f0...",
  "kind": "image",
  "media_type": "image/png",
  "byte_size": 68344,
  "filename": "error-screenshot.png",
  "url": "/v1/default/banks/acme-support/attachments/8f41c2ad9e6b"
}
```

对该路径执行 `GET`，就会取得字节；返回的 Content-Type 是调用者在存入时声明的类型。访问权限按记忆库检查，因此使用与 Recall 相同的凭据即可。附件不存在和记忆库不可见都会返回 404，所以不能通过该端点探测记忆库中存有什么。ID 根据内容哈希生成，因此 URL 对应的字节永远不会改变，并且可以无限期缓存。

这个引用足以满足两种常见需求。

**作为引用展示。** 在取回内容前，你就已拥有 `media_type`、`byte_size` 和原始 `filename`，可以在答案旁边显示缩略图，或提供 PDF 下载链接；只有用户要求查看时，才取回字节。

**再次提供给模型。** 取回字节，转换为 Base64，再以图片块形式放入下一次提示词，结构与存入时相同。智能体召回“错误是尺寸不匹配”后，可以把原始截图再次交给视觉模型，提出新的问题。

## 哪些情况下会拒绝处理 {#where-it-refuses}

这里大多数有意思的工程处理都发生在失败路径上。

**没有视觉模型，就不能存入带图内容。** 带图片的存储请求会在入口处、任何内容写入之前失败。另一种做法是从文本中提取信息并悄悄跳过图片，结果文档看似已成功存入，真正重要的信息却不见了。明确报错后可以恢复；静默遗漏则无法恢复，因为之后不会有任何信号告诉你发生过遗漏。

**“大概可以”也算不支持。** 能力状态有三种：支持、不支持和无法判断。无法判断时会拒绝处理。非 OpenAI 的 OpenAI 兼容端点会报告无法判断，因此大多数本地和网关部署都会遇到这种情况。显式设置视觉能力标志是运维人员的决定，系统不会默认开启。

**批量模式不兼容。** 启用批量 retain API 时，带附件的存储请求会直接失败，因为这条路径会直接构建提供商请求正文，无法处理交错排列的内容部分。

有一种情况会降级处理而不是拒绝：如果存储中的附件字节丢失，提示词中会插入“附件不可用”标记，而不是让存储操作失败。

## 简述存储 {#storage-briefly}

附件会在记忆库范围内按 SHA-256 去重，因此同一张截图存入四十份文档，也只会有一个二进制对象和一条记录。文件名不会与字节一同保存，因为文件名并不是文件内容的属性：同一份 PDF 在一份文档中可以叫 `policy-v1.pdf`，在另一份文档中则可以叫 `escalation-runbook.pdf`。清理操作根据引用进行：重新摄取文档时，如果不再包含图片，就会移除对应的引用关系；最后一个引用消失时，二进制对象也会被删除。

升级时，迁移会新增两张空表，并在记忆表上增加一个数组列。在成熟部署中，这个列可能不小。规划时应像处理任何大规模加列操作一样谨慎。

## 需要了解的限制 {#limits-worth-knowing}

| 限制 | 值 | 说明 |
|---|---|---|
| 来源类型 | 仅支持内联 Base64 | 暂不支持通过 URL 获取或使用预上传句柄 |
| 最大大小 | 每个附件 20 MB | 按解码后的大小计算，是服务器级设置 |
| 最大数量 | 每个 retain 条目 50 个 | 要增加数量，可拆分到多个条目 |
| 每个分块的数量 | 默认 8 个 | 可按记忆库配置；超出不会导致拒绝 |
| 媒体类型 | 任意格式正确的类型 | 没有允许列表；如果提供商无法读取，会返回其错误 |
| 按事实关联来源 | `facts` 提取模式 | `chunks` 和 `verbatim` 会使用分块中的所有附件 |
| MCP | 暂不支持 | 附件通过 HTTP 返回，不通过 MCP 工具返回 |
| Hindsight Cloud | 已支持 | 运行 0.10.0，且已配置支持视觉的模型 |

最容易让人意外的是提取模式的限制。如果配置为 chunk 或 verbatim 模式，事实就是整个分块，因此它会带上分块中的所有附件，也不会询问模型。

## 常见问题 {#faq}

**需要修改现有代码吗？**
不需要。`content` 仍接受普通字符串，这条路径从内容哈希开始都没有变化。每个条目可以选择使用块结构。

**如果把图片发给无法读取图片的模型，会怎样？**
存储操作会明确报错，而不是丢弃图片。如果你的提供商与 OpenAI 兼容但并非 OpenAI，它会报告未知能力；在你设置视觉能力标志之前，请求会被拒绝。

**事实和图片的关联保证正确吗？**
不保证。由提取器判断每条事实需要哪些附件。可以保证的是：无法解析为该分块中真实附件的编号会被丢弃，而不会用近似匹配代替。因此，漏掉引用的可能性高于给出错误引用的可能性。

**能通过 MCP 获取附件吗？**
在 0.10.0 中还不行。附件字段位于 HTTP 响应中；MCP Recall 工具返回的事实不包含附件。
