Hindsight 0.10.2 可以在客户端持续运行时更换记忆库 ID，为不同标签范围分别设置整合规则，并让每个心智模型自行选择刷新时的推理预算。它还会以流式方式导出数据，避免大型记忆库耗尽内存，并修复一系列挂起、一致性和 Oracle 问题。**所有使用 0.10.x 的用户都应升级**；完整修复列表请参阅[更新日志](/changelog)。

- [**记忆库别名**](#bank-aliases)：为记忆库添加第二个 ID，按自己的节奏逐步迁移调用方。
- [**按范围设置整合策略**](#consolidation-strategies-per-scope)：在同一记忆库中，为用户、团队和公司范围设置不同的观测规则。
- [**每个心智模型的刷新预算**](#a-refresh-budget-per-mental-model)：刷新默认使用 `mid` 预算，且不再继承 Reflect（反思）的默认配置。
- [**在截图和文件上测试提取**](#test-extraction-on-screenshots-and-files)：提取测试器可接收图片和文件，附件也会传递到观测和 reflect。

- [**可靠性修复**](#reliability-fixes)：不再挂起的工作进程、更安全的整合，以及 Oracle 功能对齐。

## 记忆库别名 {#bank-aliases}

![记忆库同时响应旧 ID 和新别名，调用方可以逐个迁移](/img/blog/0-10-2-bank-aliases.svg)

过去，重命名记忆库意味着要停止所有客户端，完成重命名后再一次性更新它们的目标。现在，记忆库可以同时响应额外的 ID：

```
POST   /v1/default/banks/{bank_id}/aliases     {"alias": "new-id"}
GET    /v1/default/banks/{bank_id}/aliases
DELETE /v1/default/banks/{bank_id}/aliases/{alias}
```

添加别名会立即生效，且不会复制任何内容。两个 ID 都能访问同一个记忆库，因此你可以逐个迁移调用方；等旧 ID 不再被使用时，再将其移除。

迁移完成后，可以将某个别名设为记忆库的**显示 ID**（使用 `PATCH .../aliases/{alias}` 并传入 `{"primary": true}`，或运行 `hindsight bank alias primary <bank> <alias>`）。真实 ID 仍会显示在旁边；身份认证、计量、导出和日志仍使用真实 ID。

## 按范围设置整合策略 {#consolidation-strategies-per-scope}

![同一事实在用户范围内以完整细节整合，在公司范围内则只形成总体趋势](/img/blog/0-10-2-consolidation-strategies.svg)

现在，一个记忆库可以同时保存用户、团队和公司范围的记忆，并按各自的规则进行整合。例如，可以要求公司范围只记录总体趋势，同时让各用户范围保留完整细节：

```json
"consolidation_strategies": [
  {
    "scopes": [{ "tags": ["company:*"] }],
    "observations_mission": "Record only generalized, industry-level trends. Name no specific company.",
    "max_observations_per_scope": 20
  }
]
```

可以按记忆库设置，也可以通过全局配置项 `HINDSIGHT_API_CONSOLIDATION_STRATEGIES` 设置。首个匹配某个范围的策略会生效；该策略中未设置的项目回退到记忆库自身的配置。控制平面在 **Bank → Configuration → Observations（记忆库 → 配置 → 观测）** 下提供带标签页的编辑器，并会在保存前预览各条规则会匹配哪些现有范围。`observation_scope_limits` 已弃用，但仍会生效。

整合任务现在也会在不同范围组之间公平调度，因此某个繁忙范围不会再让其他范围的任务长期得不到处理。

## 每个心智模型的刷新预算 {#a-refresh-budget-per-mental-model}

![心智模型的触发器设置刷新预算；reflect 不再使用记忆库的 reflect 默认配置](/img/blog/0-10-2-refresh-budget.svg)

过去，心智模型刷新会在不显眼的情况下使用 `low` 预算，这会将 Reflect 可执行的步骤数减半；对于编写完整页面来说，这通常不够。现在，每个心智模型都可以设置自己的**刷新预算**（`low` / `mid` / `high`）；未设置时默认为 `mid`。可以在触发器编辑器的 Advanced 面板中设置，也可以通过知识页默认触发器设置记忆库级默认值。

刷新现在也**不再读取 `reflect_default_options`**。这些选项用于回答问题；过去调整它们也会悄然改变页面的编写方式。

刷新失败后现在会结束，不再循环重试并不断增加 LLM 费用；同一心智模型同时最多只会运行一次刷新。

## 在截图和文件上测试提取 {#test-extraction-on-screenshots-and-files}

![提取测试器读取文本和图片，并显示每条事实来自哪个文件](/img/blog/0-10-2-multimodal-extraction.svg)

控制平面中的**提取测试器**以及试运行提取端点，现在都能像 Retain（存入）一样接收由文本、图片和文件块混合组成的输入。你可以在保存任何内容之前，查看记忆库会从截图或 PDF 中提取出什么；每条事实也会标明来源文件。

附件也能传递到更多环节：观测现在会显示其依据事实的附件；Reflect 的 `based_on` 会为每条引用的记忆附带其文档、标签、元数据和附件。在知识库文章中存入的截图，现在也会随依赖该截图的答案一同返回。

## Reflect 可以区分来源 {#reflect-can-tell-sources-apart}

![Reflect 区分来自手册和聊天的事实，并依据手册作答](/img/blog/0-10-2-reflect-metadata.svg)

手册中的规则和聊天消息可能互相矛盾；一旦二者都变成事实，它们看起来就没有区别。Reflect 因而往往会选择较新的那条，通常也就是聊天消息。现在，Reflect 可以读取每份文档各自的元数据，因此你可以在记忆库的 `reflect_mission` 中说明优先级（例如“优先采用 `source=handbook` 的文档”）。无需新增设置；不存储元数据的记忆库不会产生额外开销。

## 运维 {#operations}

![导出时分批读取文档，并分块流式传输附件，使峰值内存保持在约 25 MiB](/img/blog/0-10-2-streamed-export.svg)

- **流式导出。** 记忆库和文档导出现在逐段写入，而不是先在内存中构建完整内容。导出含有 256 MiB 附件的记忆库时，内存占用从约 545 MiB 降至约 25 MiB。整库导出归档现在也会按保留策略清理。
- **ONNX 嵌入支持 CUDA。** 设置 `HINDSIGHT_API_EMBEDDINGS_ONNX_DEVICE=cuda`（也可以设置 `HINDSIGHT_API_EMBEDDINGS_ONNX_CUDA_DEVICE_ID`），即可在 GPU 上运行进程内嵌入。默认值仍为 `cpu`；`docker/docker-compose/cuda-onnx/` 下提供了镜像示例。
- **面向扩展的人工维护钩子。** 操作验证器现在可以批准或拒绝记忆编辑、失效或恢复操作，并会在操作提交后收到重新嵌入内容的信息。
- **pg0** 会将 URL 查询参数传递给 PostgreSQL。
- **Helm** Ingress 现在可以正确路由 `/v1` 下的数据 API 请求。

## 可靠性修复 {#reliability-fixes}

- **LLM 超时现在是真正的截止时间。** 即使服务提供方持续一点点地返回响应，也不能再无限占用工作进程槽位。进程内重排序现在也受相同的墙钟时间限制。
- **如果调用期间来源事实被编辑，整合过程会丢弃该批次**，避免根据过时事实写入观测。每条观测的来源也会被保存，并且只显示一次。
- **迁移失败后会释放锁**，使下次启动可以重试，而不必继续等待。
- **其他进程删除记忆库后，对该库的 Recall（召回）会返回 404**，而不是空结果或 500。
- **OpenAI 与 GPT-6** 已恢复正常，包括通过 Responses API 使用时。
- **Oracle**：此前仅 PostgreSQL 可用的 Retain（存入）路径、记忆库归档导入，以及若干 JSON 和时间戳边界情况现在都可以正常工作。
- **MCP** 列表工具现在使用与 HTTP 相同的分页限制。

有一项数据库模式变更会影响一张大表：实体名称索引现在按记忆库限定范围，使模糊实体匹配保持在单个记忆库内。迁移会在启动时运行，因此大型部署应预留更多时间。
