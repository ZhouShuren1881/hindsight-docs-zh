Hindsight 0.10.1 新增 TypeSafe Jev 作为重排序器，并让记忆库可以迁移：一次调用即可克隆，按明确范围导出和导入，也可以通过管理 CLI 原地重命名。本版还为记忆和文档 API 增加服务端时间筛选，让自动心智模型刷新使用独立的 LLM，并修复了一系列隔离、死锁和提供商问题。**所有使用 0.10.x 的用户都应升级**；完整修复列表请参阅[更新日志](/changelog)。

## 使用 TypeSafe Jev 重排序 {#reranking-with-typesafe-jev}

设置 `HINDSIGHT_API_RERANKER_PROVIDER=typesafe` 后，Recall 的重排序会使用 TypeSafe 的 Jev 模型（默认模型为 `jev-latest`）。它不是 Cohere 风格的 `/rerank` 端点：模型不会逐个为候选打分，而是把所有候选都作为选项，针对它们回答**一个问题**；答案就是排序结果。无论候选有多少，都只需一次请求。

这种方式既更准确，也快得多。把候选放在一起判断时，模型只需指出哪个候选优于哪个，而不必在每次调用时都为每个候选重新建立绝对评分尺度。以下是在 LoCoMo 上的测量结果，与相同任务使用的当前默认重排序器对比；gold 指数据集自身标注的证据轮次。

**每个查询 30 个候选，共 200 个问题：**

|                                          | recall@1  | recall@5  | NDCG@10   | 秒/查询   |
| ---------------------------------------- | --------- | --------- | --------- | --------- |
| `local` MiniLM（当前默认）               | 0.800     | 0.876     | 0.850     | 0.12      |
| **typesafe，仅排序（默认）**             | **0.950** | **0.966** | **0.957** | **0.027** |

**每个查询 240 个候选——这是生产环境中 Recall 实际重排序的候选池规模——共 60 个问题：**

|                            | recall@1  | recall@5  | NDCG@10   | 秒/查询   |
| -------------------------- | --------- | --------- | --------- | --------- |
| `local` MiniLM             | 0.583     | 0.719     | 0.682     | 0.41      |
| **typesafe，仅排序**       | **0.783** | **0.903** | **0.856** | **0.063** |

候选池越大，差距越明显：候选数为 30 时，recall@1 高出 15 个百分点；候选数为 240 时，高出 20 个百分点。整池候选通过一次请求发送，因此耗时也大幅缩短。超过模型 255 个选项的上限时，系统会分轮排序，再将各轮的胜出候选放在一起排序。

**裁剪无关的尾部候选需要主动启用。** 设置 `HINDSIGHT_API_RERANKER_TYPESAFE_PRUNE_CANDIDATES=true` 后，系统会再提出一个问题，判断排序后的候选列表中相关内容延伸到哪里；该位置之后的候选都会被排除。无需调整阈值，模型会自行确定截断位置，而且至少会保留一个候选，因此查询结果不会为空。

在相同的 30 个候选测试中，启用裁剪后平均保留 1.6 个候选，保留结果的精确率从 0.051 提高到 0.850（17 倍），代价是裁掉了 19% 的 gold 证据。因此该选项**默认关闭**：在一个真实记忆库中，它曾将 300 个候选缩减到 3 个，这会给智能体一个截然不同的答案。请先在自己的数据上试用。

此提供商给出的分数表示**排名位置，而非置信度**：在一个候选池内，某个概率分数只表示“这些候选中最佳”，并不表示“相关”；不同候选池的分数也无法相互比较。分数恰为 `0.0` 表示后端判定该候选位于裁剪线之后。

使用 `HINDSIGHT_API_RERANKER_TYPESAFE_API_KEY` 配置凭据；如有需要，还可以配置 `..._MODEL`、`..._BASE_URL`、`..._TIMEOUT` 和 `..._MAX_CONCURRENT`。

## 迁移记忆库 {#move-a-bank}

过去，记忆库只是记忆的存放位置，无法像对象一样迁移。0.10.1 的三项变更让记忆库可以迁移：

- **一次调用即可克隆记忆库**，无需自行编排导出和导入。
- **统一的导出和导入**支持明确指定传输范围，因此归档会说明其中包含什么，导入时也会按相同范围恢复。记忆存储在 memories store 中的记忆库现在也能正确导出、导入和克隆；转换后的文件及附件也会随之保留。
- 通过 `hindsight-admin` **原地重命名记忆库**。记忆库存储的文件也会移动到新的前缀，因此重命名后不会出现无法访问的文件。

本版还包含一项迁移：附件现在直接关联到对应文档，取代单独的 `document_attachments` 表。迁移只涉及附件记录，因此无论部署规模如何，都能很快完成。

## 在服务端按时间筛选 {#filter-by-time-on-the-server}

过去，列出记忆或文档后再按日期缩小范围，意味着先拉取那些最终会被丢弃的分页结果。现在两个 API 都可以直接接受时间筛选和排序选项；控制平面的文档列表也提供预设范围（例如最近 24 小时、最近一周等）和自定义范围。知识页新增了高级搜索对话框，也采用相同的思路；此外，知识页搜索分数现在统一归一化到 0–1，因此不同查询中的同一分数含义一致。

## 为心智模型刷新配置独立 LLM {#a-separate-llm-for-mental-model-refreshes}

过去，自动刷新心智模型时会使用记忆库处理其他所有任务的 LLM。刷新属于后台工作，其成本考量与面向用户的 Retain 操作不同。0.10.1 允许为刷新单独配置提供商和模型：后台刷新可以使用成本更低的模型，用户正在等待的操作则继续使用常用模型。

本版还增加了两项相关配置：反思过程中搜索观测所用的预算及纳入考虑的实体现在都可以配置；新建知识页的默认触发方式也可以设置，不再固定不变。

## 相同硬件完成更多工作 {#more-work-out-of-the-same-box}

- **对分块文档执行 Retain** 时，同一文档的各个分块不再重复构建提示词和 schema。
- **记忆库列表**在包含大量记忆单元的部署中不再缓慢。
- **创建归档**时不会阻塞事件循环，也不会在整个过程中持续持有读取事务，因此导出大型记忆库时，其他操作不必一直等待。
- **Recall** 会在处理流程中复用观测的来源记忆 ID，而不再重新推导。
- **启动时快速失败**：如果配置的 API 端口已被占用，服务会立即给出明确错误，而不是之后才以难以理解的方式失败。

## 提供商与平台 {#providers-and-platforms}

- 调用方未设置输出上限时，**Anthropic 响应不再被截断**。
- 提供商以数字形式给出重试时间时，**限流恢复**也能正常工作。
- **Apple Silicon**：MLX 仅会安装在受支持的机器上；本地模型会关闭不稳定的 MPS 加速路径；MLX 重排序器会在每批处理后释放内存。
- **Windows**：uv 管理的虚拟环境现在可以正常启动本地嵌入模型。
- **非英语内容**摄取后会保留原有文字体系；同一批次内的实体聚类也更加准确。
- 服务器绑定到回环地址时，**控制平面界面仍可访问**；其中的 Recall 和 Reflect 选项更简洁，并附有界面内说明。
