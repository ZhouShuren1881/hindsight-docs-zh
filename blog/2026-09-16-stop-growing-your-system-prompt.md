每个智能体起初都有一段简短的系统提示词，不过如今它更常见于 `CLAUDE.md` 或 `AGENTS.md`，而不是代码中的字符串。我们把这一整套内容称为常驻上下文：无论它实际存放在哪里，都是智能体每一轮都会读取的指令。接着，智能体做错一件事，你就加一行；它又做错另一件事，你就加一段。六周后，提示词已经累积了两千个 token 的修正内容，没人记得其中一半为什么会在那里，删掉任何一条又都让人觉得有风险。

这是再自然不过的做法，而且在一段时间内确实是正确的选择。问题在于，之后会发生什么。

## 为什么起初有效 {#why-it-works-at-first}

把内容写进提示词确实有好处。在提出反对意见前，应该先如实承认这些好处。

它**立即生效**。加上一行，下一轮的行为就会改变。无需索引、无需处理流程，也不用等待。

它**效果确定**。模型肯定看到了这条内容，不会像检索那样可能漏掉，也不会像排序那样可能把它排到后面。对于必须每次都执行的规则，这种确定性很有价值。

它**便于检查**。提示词就在代码里，可以阅读、比较差异并据此分析。

规模变大并不会让这些优点消失，变化的是成本。

## 成本是无条件产生的 {#the-cost-is-unconditional}

无论这一轮在处理什么，系统提示词都会在每一轮产生开销。

用户让你重命名变量时，要发送两千个 token 的累积指令；用户让你制定迁移计划时也要发送；修复拼写错误时还是要发送。token 成本显而易见，说实话也是最不值得关注的一项。另有两件事更重要。

**它挤占实际任务的空间。** 即使上下文窗口很大，它的容量仍然有限；用于常驻指令的空间，就不能用于眼下要做的事。在长会话中，膨胀的提示词会直接与智能体需要阅读的代码争夺空间。

**内容越多，相关性越低。** 模型只需关注二十行高度相关的内容，与它需要关注两百行、其中只有二十行适用的内容，行为会有所不同。你不只是给信号增加了噪声，也让信号所占比例变小。新增一条规则，确实可能让已有规则更难得到遵守。这个问题很难排查：新增的那一行没有问题，出问题的那一行也从未改动。

## 但我的智能体运行框架已经处理了这些问题 {#but-my-harness-already-handles-this}

自问题最严重的时期以来，工具已经进步了。常驻上下文现在放在文件里，按项目、有时还按目录限定。提示缓存让稳定前缀不必每一轮都按完整费用计费。智能体运行框架会自动压缩长会话、把工作交给有独立上下文窗口的子智能体，并且只在指令看起来相关时加载其中一部分。

这些改进都确实存在，也确实改变了成本计算方式，但没有改变问题的结构。

**缓存降低了价格，却没有减少占用。** 在 Anthropic 的 API 中，读取缓存前缀的费用大约是普通输入费用的十分之一；写入缓存的费用则高约 25%，缓存条目的默认有效时间为五分钟。这大幅降低了三项成本中最不重要的一项。token 仍会占用窗口，模型仍会关注这些内容；埋在两千个常驻指令 token 中的规则，并不会因为发送成本低就更容易得到遵守。

**规则文件比提示词更容易只增不减。** Python 字符串提示词只有一个作者；版本控制中的文件则人人都能改，而且增删的难度仍不对等：加一行只需提交一个没人反对的 PR，删除一行却要证明它已经过时。按目录限定确实有帮助：只在 `services/api` 下加载的文件，就是有条件的上下文，这个方向是对的。但大部分累积内容仍然面向整个项目。

**压缩处理的是症状。** 自动摘要发生在上下文窗口已经装满之后。它会丢失信息、偏重最近的轮次，而且会在长任务进行到一半时触发——这恰恰是丢失早期细节代价最高的时候。它事后决定丢掉什么，却没有事先决定哪些内容本来就值得常驻。

**渐进式披露只是换了种形式的检索。** 智能体运行框架只在看起来相关时才加载技能或限定范围的规则文件，就等于不再把这些知识放进提示词，而是开始检索。这正是本文所说的做法，而且已经有人认可并付诸实践。尚待解决的问题是：对于运行框架没有替你管理的知识，该怎么办？例如团队做过什么决定、尝试过什么，以及为什么这么做。

## 它只会不断增长 {#it-only-ever-grows}

结构性问题在于，给系统提示词添加内容轻而易举，从中删除内容却令人惶恐。

添加只需片刻，而且理由显而易见：刚刚出了问题。删除则要求你知道某一行已经过时；通常还得知道当初为什么添加、何时添加，以及导致它出现的情形是否依然存在。六个月后，没人还知道这些。

于是提示词只增不减。每次事故都会添上一行，却没有哪次事故会删掉一行，自然而然的平衡点就是“只要还能忍受，就尽量加大”。这不是纪律出了问题。任何一种新增成本低、删除令人担忧的结构，都会变成这样。

## “放进提示词”究竟意味着什么 {#what-put-it-in-the-prompt-is-really-doing}

把常被混为一谈的两类内容区分开，会更容易理解。

**指令**是你希望智能体始终遵守的要求，不受当前任务影响。例如采用某种风格、绝不触碰某个目录、运行迁移前先询问。这些要求确实无条件适用，提示词正是放置它们的合适位置。

**知识**则是关于项目的事实：为什么重试策略排除了某个端点；何时决定采用某种舍入方式；上个季度有人尝试过什么，结果并不奏效。

知识会无限增长，而且其中大部分几乎从不与当前任务相关。知识很多，每次只需要其中一小部分，而具体需要哪一部分完全取决于你眼下在做什么。

把知识放进提示词，等于为了用上其中一部分而支付全部内容的成本。

## 另一种选择是检索 {#retrieval-is-the-other-option}

另一种做法不是“少记一点”，而是把知识放在可查询的位置，每轮只取回相关部分。

这正是记忆系统的作用。它带来的一个重要设计结果是**预算**。在 Hindsight 中，Recall 会按照明确设定的预算运行，而不是找到多少就返回多少。在默认的 `fixed` 设置下，每种检索方法对每种事实类型分别处理：`low` 预算每次检索 100 项，`mid` 为 300 项，`high` 为 1000 项。另有 `adaptive` 模式，会根据请求自身的 `max_tokens` 按比例设定预算。

重点不是这些具体数字，而是成本**有上限，并且按请求产生**，而非固定且永久存在。简单的一轮几乎可以什么都不检索；复杂的架构问题则可以检索很多。两种情况不会互相承担对方的成本。

第二个结果是，知识不再需要专人维护。系统提示词只会包含某人在想到要记录时写下的内容。由 git 历史和过去对话构建的记忆库，则会包含实际发生过的事，包括那些在下午 6 点的 PR 讨论串里做出、却没人记得写进文档的决定。

## 提示词应该保留什么？ {#so-what-should-the-prompt-hold}

保留提示词，把它用作指令层。

- 每一轮都希望智能体遵守的**常驻行为**。
- **硬性约束**，尤其是任何可能造成危险的操作。
- 智能体绝不应偏离的**风格和格式**规则。

把真正属于记录的内容移出去：决策及其理由、架构历史、过去尝试过什么、代码为何采用当前的设计。将这些内容放在可检索的位置，注明时间和来源，并且只在与问题有关时返回。

可以用一个简单的方法判断：逐条查看提示词中的内容，问问自己，如果当前任务与这一条完全无关，发送它仍然值得吗？如果不值得，它就是披着指令外衣的知识。

## 必须坦承的限制 {#the-honest-limits}

检索既不是免费的，也不是万能的。

它可能会**漏掉内容**。提示词中的一行一定会被看到；检索到的记忆则必须先被找到。对于绝不能被忽略的内容，提示词仍然是合适的选择。这也正是指令层不该被清空的原因。

它会增加**依赖**：必须有某个服务在运行，也必须有人先把内容记录下来。

它还需要**时间才能发挥作用**。记忆库在第一天掌握的信息少于一份写得很好的提示词。只有经过一段时间，优势才会显现；而且只有在长期项目中，这种取舍才划算。

只运行两次的脚本，把要求放进提示词。要维护一年的代码库，提示词最终会落败；这个过程又慢到你甚至察觉不到是哪条规则出了问题。
