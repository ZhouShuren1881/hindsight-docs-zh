智能体起初只有简短系统提示词，现在更多是 `CLAUDE.md` 或 `AGENTS.md`，而非代码字符串。将每轮都读取的所有指令称为常驻上下文。出错一次加一行，再错加一段；六周后累积为两千 token 的更正，没人记得一半内容为何存在，删除任何一条都觉得危险。

这是自然做法，起初确实正确。问题是之后发生什么。

<!-- truncate -->

## 为什么起初有效 {#why-it-works-at-first}

将信息放入提示词有真实优势，应先承认。

它**立即生效**。加一行，下一轮行为就变，无需索引、流程或等待。

它**确定可见**。模型一定看到，不会被检索遗漏或排名埋没。每次必须执行的规则，这种确定性很有价值。

它**可检查**。提示词就在代码里，可阅读、比较差异和分析。

规模变大后，这些仍成立，变化的是成本。

## 成本无条件产生 {#the-cost-is-unconditional}

无论当前任务是什么，每轮都为系统提示词付费。

重命名变量、制定迁移计划、修复拼写时，都发送两千 token 的积累指令。token 费用显而易见，却最不值得关注，另外两点更重要。

**挤占实际任务。** 上下文再大也有限，常驻指令占用的空间就无法用于当前工作。长会话中，提示词膨胀直接与所需代码争夺空间。

**越大越不相关。** 关注二十行高度相关内容，与关注二百行但只有二十行适用的内容，模型行为不同。不只增加噪声，还降低信号比例。新增规则可能使已有规则更难遵守，而新增行正常、失效行未改，会让调试令人抓狂。

## 但我的运行工具已经处理了这些 {#but-my-harness-already-handles-this}

工具已比最糟时期进步。常驻上下文放在文件中，按项目甚至目录限定；提示缓存使稳定前缀无需每轮全额计费；工具自动压缩长会话、将任务交给有独立窗口的子智能体，并按相关性加载部分指令。

这些确实改变成本结构，却没改变问题形态。

**缓存降价，不减少占用。** Anthropic API 的缓存读取约为普通输入费用十分之一，写入约贵 25%，默认保留五分钟，显著降低三项成本中最不重要的一项。token 仍占窗口、模型仍需关注；两千 token 中埋藏的规则不会因发送便宜而更容易遵守。

**规则文件比提示词更容易只增不减。** Python 字符串可能只有一个作者，版本控制文件所有人都能添加：新增是一行 PR，删除却要证明内容已过时。目录范围有帮助，例如只在 `services/api` 内加载，就是正确的条件上下文。但累积内容多数仍是全项目的。

**压缩只管理症状。** 自动摘要发生在窗口已满后，有损且偏向最近轮次，常在长任务中途触发，而这恰是早期细节最重要的时候。它事后决定丢弃什么，不能事前决定什么值得常驻。

**渐进展示本质也是检索。** 只在相关时加载技能或限定范围规则，就已不再将知识常驻提示词，而开始检索。这个观点已被接受并实现。问题剩在工具不代管的知识：团队决定过什么、试过什么，以及为什么。

## 它只会增长 {#it-only-ever-grows}

结构性问题是：添加系统提示词极容易，删除却令人担忧。

新增只需片刻，动机明确，因为刚发生错误。删除需要知道该行已过时，通常要了解添加原因、时间，以及触发情形是否仍在。六个月后往往没人知道。

因此提示词只增不减：每次事故加一行，没人因事故删一行，自然平衡是“尽可能大，直到无法忍受”。这不是纪律失败，而是任何添加便宜、删除可怕的结构都会发生的事。

## “放进提示词”究竟在做什么 {#what-put-it-in-the-prompt-is-really-doing}

需要区分常被混在一起的两种内容。

**指令**是无论任务如何，都希望智能体执行的事：使用某风格、不碰某目录、迁移前询问。它们确实无条件适用，提示词就是正确位置。

**知识**是项目中的事实：为何不重试某端点、何时决定采用何种舍入、上季度试过哪种无效方案。

知识会无限增长，却几乎不会全部与当前任务有关。内容很多，每次只需要少量，所需部分完全取决于当前工作。

将知识放入提示词，就为使用一小部分而支付全部成本。

## 另一种选择是检索 {#retrieval-is-the-other-option}

可以将知识保存在可查询的位置，每轮提取相关部分，无需减少记住的内容。

这就是记忆系统的工作，重要设计结果是**预算**。Hindsight 召回有明确预算，不是找到多少返回多少。默认 `fixed` 下，每种检索方法、每种事实类型，`low` 获取 100 项，`mid` 300 项，`high` 1000 项。`adaptive` 则按请求 `max_tokens` 的比例决定预算。

关键不在具体数字，而在成本**有界且按请求产生**，不再固定常驻。简单轮次几乎不检索，复杂架构问题可检索很多，两者无需互相承担费用。

另一个结果是知识不再需要专人整理。系统提示词只包含某人当时想到记录的内容，基于 git 历史和对话的记忆库保存实际经历，包括下午六点在 PR 讨论中作出、无人记得写文档的决定。

## 提示词应保留什么？ {#so-what-should-the-prompt-hold}

保留它，作为指令层。

- 每轮都应执行的**常驻行为**。
- **硬性约束**，尤其是危险操作。
- 不应偏离的**风格与格式**规则。

真正属于记录的内容应移出去：决策和理由、架构历史、以前试过什么、代码为何这样设计。放在可检索的位置，记录日期和来源，只在与问题相关时返回。

逐行问自己：当前任务完全无关时，这行还值得发送吗？不值得，就可能是伪装成指令的知识。

## 必须承认的限制 {#the-honest-limits}

检索不是免费，也不是魔法。

它可能**遗漏**。提示词一定被看到，记忆却要先被找到。不能接受被忽略的内容仍应放在提示词里，这也是不能清空指令层的原因。

它增加**依赖**：服务要运行，内容也要先被采集。

它需要**时间才能有用**。第一天的记忆库不如精心编写的提示词，优势之后才出现，只有长期工作才值得。

只运行两次的脚本，放进提示词。要工作一年的代码库，提示词迟早会输，而且过程慢到你注意不到哪条规则失效。
