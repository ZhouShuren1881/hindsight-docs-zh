规划器将二十个工作智能体分派到整个代码库。每个智能体读取一部分内容，得出一些结论，再把结论记下来。十分钟后，它们都已离开，留下的只有记忆库。

有意思的问题不是这些写入有没有成功，而是记忆库现在包含什么：二十份关于同一个重试错误的独立记录，还是一条由二十个工作智能体各自确认过的观测？这两种产物截然不同，而最终得到哪一种，并不取决于智能体有多优秀。

<!-- truncate -->

## TL;DR {#tldr}

- **Hindsight 中的原始事实永远不会彼此合并。** 二十个智能体得出相同结论，就会永久写入二十行。这是审计轨迹按设计运行的结果，并非去重失败。
- **观测整合会把冗余转化为证据。** 一条观测的 `proof_count` 统计的是 *不同且仍有效的来源记忆 ID*。因此，二十个智能体达成一致后，会形成一条引用二十条事实的观测——独立佐证是智能体集群能够为记忆提供、而单个智能体在结构上无法提供的东西。
- **并发对实体名称的影响最大，而非对事实的影响最大。** 变体合并仅在单次批次内进行；智能体集群的写入彼此独立，因此名称是否收敛取决于能否匹配到已经提交的实体。
- **一个智能体写入错误，会变成所有智能体的上下文。** 对单个智能体来说，被污染的写入只是一次错误记忆；在集群中，它会成为接下来十九个工作智能体回忆起的共同前提。
- **工作智能体没有稳定的 `document_id` 时，重试不会覆盖，而会制造重复内容。**

## 智能体集群会把同一事实写二十次 {#a-swarm-writes-the-same-fact-twenty-times}

先从这里说起，因为后续的一切都由此而来。

两份文档用不同措辞描述同一事实时，Hindsight 会存储两个记忆单元。整个存入流程中没有文本相等检查、嵌入向量相似度检查，也没有基于重复*内容*的 upsert。（重复的 `document_id` 会执行 upsert，但那是按身份识别，而非按相似度——下文会再谈。）实际发生的是建立连接：嵌入向量相似度高于 `semantic_link_min_similarity`（默认值为 0.7）的事实之间会建立一条边。两条事实即使有 99% 相似，也只会形成一条很强的连接，两条事实仍都可以被完整召回。

后台也没有定期搜寻重复项的作业。图维护通过队列驱动的两轮处理完成：补回因删除邻居而丢失的连接，以及清理删除操作可能遗留的孤立实体。它的文档注释也明确指出，这些是排队等待处理的工作，并非全量扫描。没有任何流程会遍历整个记忆库并查找需要合并的内容。

这是有意为之。原始层是审计轨迹——当你想知道系统为何相信某件事时，可以追溯到这一层。如果存入流程因为某条事实与已有内容相似就悄悄丢弃它，你便无法再相信该流程完整保留了你交给它的内容。

对单个智能体来说，这会造成一些浪费；对智能体集群来说，这正是它的关键特性。扇出本来就会带来冗余：这就是扇出的含义。你不可能在写入层把这种情况消除，也不应该希望这么做。

## 如果观测整合看得到，一致意见就是证据 {#agreement-is-evidence-if-consolidation-sees-it}

合并发生在上一层，以异步方式进行，而且它会创建新内容，而不是销毁任何内容。

观测整合会读取原始事实，并将相关事实归并成**观测**。对智能体集群而言，关键数字是 `proof_count`。它的准确定义正是重点：该值等于观测中去重后、仍有效的来源记忆 ID 列表长度，并会在每次归入来源时重新计算。它不是递增计数器，也不是写入时累计的总数。

因此，二十个工作智能体各自得出“检出操作最多会重试三次”的结论，并不会产生二十条观测，而会产生一条 `proof_count` 为二十的观测。这个数字在单个智能体场景中不可能有同样的含义。一个智能体在五次会话里重复说同一件事，只能说明它重复了；二十个互不知晓彼此上下文的智能体各自说一次，才算相互佐证。

观测整合提示明确要求优先采用这种形式：

> 不要创建近似重复的同级观测。一条包含多个来源事实的规范观测，始终优于多条各自仅有一个来源事实的同级观测。

提示背后还有两道确定性防护。如果模型已经看到某条观测，而新建观测的规范化文本与之相同，或者新建内容与同一响应中发出的更新文本相同，该创建操作就会被丢弃。如果新观测与现有观测的相似度达到 `consolidation_dedup_threshold`（默认值为 0.97），系统会启动专门的合并或保留判定，把来源、`proof_count` 和时间范围并入那条匹配观测，而不是另建一条同级观测。

还要记住两点限制。这项协调逻辑**仅适用于 Postgres**；在 Oracle 上，无论阈值如何设置，都会完全跳过。此外，观测整合不会删除底层事实，而是为它们写入 `consolidated_at` 标记，并继续保留原始内容。二十行记录不会消失，只是不再是主要阅读对象。

这里还有一项很好的并发防护。创建观测时，系统会在与插入操作相同的事务中检查来源是否仍有效，并对其持有 `FOR SHARE` 锁。这样可以避免并发删除恰好发生在检查和写入之间，从而让新观测引用到已不存在的事实。智能体集群的整合流程不会因为自身的并发竞争，而引用失效事实。

## 并发真正影响的地方：实体名称 {#where-concurrency-actually-bites-entity-names}

Hindsight 会合并新实体名称的表面变体，例如将 “Acme Corp” 和 “Acme Corp.” 合为一个实体。但这一步是**批次内**处理：只会协调同一次存入操作创建的名称。二十个工作智能体各自执行存入操作，无论名称多相似，都不会一起经过这一步。

是否收敛，取决于能否与已存储的实体进行解析匹配；匹配下限由 `ENTITY_MERGE_MIN_SIMILARITY` 设为 0.3。只要工作智能体一的写入已经提交，工作智能体二的 “Acme Corporation” 就会解析到 “Acme Corp”。如果两个智能体同时写入完全相同的名称，系统会通过 `ON CONFLICT DO NOTHING` 插入语句和失败方的回退读取妥善处理；但在同一时刻写入、且彼此为名称变体的内容，还没有已提交的实体可供匹配，因此同一家公司可能会形成两个实体。

理解这一点就好，不必特意绕开。只有名称**首次出现时**发生竞争的写入才可能把实体拆开；一旦有某个工作智能体提交了 “Acme Corp”，后续智能体都会解析到它。随着集群持续运行，词汇会逐渐收敛，剩余的拆分也能被发现并在之后合并。提前声明实体可以避免这种情况，但如果你能预先把完整词汇表交给智能体集群，它也就算不上真正的发现过程了。

## 一个智能体写错，所有智能体都会继承上下文 {#one-bad-agent-is-everyones-context}

智能体集群会扩大错误写入的影响范围，因此，即使单个智能体场景可以跳过某项设置，集群也有理由启用它。

[记忆防护（Memory Defense）](https://hindsight.vectorize.io/developer/api/memory-banks#memory_defense) 是针对单个记忆库的策略，默认关闭。它会运行多个检测器：`prompt_injection`、`sensitive_data`、`protected_key`、`immutable_key` 和 `size_anomaly`，并将每项检测结果映射到一种操作：`allow`、`redact`、`quarantine` 或 `block`；也可以设置最低严重性门槛。

其中有两个字段对智能体集群尤其有用：

- **`immutable_tag_namespaces`** 会直接阻止对某个命名空间的写入。将规划器的任务简报和集群共同认可的结论放入该命名空间后，工作智能体就无法覆盖其他智能体正在读取的前提。
- **`prompt_injection` 配合 `quarantine`** 很重要，因为读取了恶意文件的工作智能体并非只是自身受到了影响。它存入的任何内容都会成为接下来十九个工作智能体可召回的上下文，而那些智能体无法分辨这究竟是同事的诚实发现，还是恶意内容。

单个智能体污染了自己的记忆，只会让这一轮会话变糟；而共享记忆库被污染后，集群里的十九个智能体都会信心十足地在错误前提上继续工作，`proof_count` 也会欣然显示有十九个来源达成一致。

## 扇出场景下，幂等性不可或缺 {#idempotency-is-not-optional-at-fan-out}

如果省略 `document_id`，Retain 会为每个请求生成一个新的 UUID。因此，即使再次存入相同内容，也会创建另一份文档和一整组全新的事实。文档对此说得很清楚：重复摄取相同内容会创建重复记忆。

对单个智能体来说，这是个会被注意到的小麻烦；对带重试机制的智能体集群来说，它会放大问题：重启后的工作智能体会把所有内容再写一遍，而观测整合又会把第二份副本当作对第一份内容的额外佐证。`proof_count` 增加了，但实际上并没有任何独立确认。

提供 ID 后，行为就会相反。Retain 会按 `document_id` 执行 upsert：先删除现有文档及其关联的所有记忆，再插入新内容。这样一来，重试会替换该工作项自己的上一次尝试，而不是不断叠加。

也要了解这种做法的代价。upsert 中的删除部分会执行与删除文档相同的级联操作：删除引用这些记忆的观测，并重置其他文档中与之共同作为来源的记忆的整合状态，以便重新处理。因此，在多个工作智能体的事实已被归并到共享观测的集群中，一个工作智能体重试也会让自身任务范围以外的内容重新触发整合。这是正确的取舍：优先保证正确性，而非降低成本；但这也说明，应该尽量减少重试，而不是把重试当作常规操作。

`document_id` 应根据工作项本身生成，而不是根据尝试次数生成。使用工作智能体 ID 加任务 ID，绝不要使用时间戳。

## 共享整合层，还是各自私有 {#shared-layer-or-private-ones}

最后要决定的是，智能体集群是否要共享观测层。

观测整合会根据底层记忆的标签集合来确定观测范围，因此标签决定二十个工作智能体是汇聚到一起，还是彼此隔离。为所有工作智能体的写入使用相同标签，就会形成一个能汇总共同意见的整合层，也就是上文所说的 `proof_count`。如果按工作智能体分别打标签，就会形成二十个私有层，无法相互佐证；有时这正是你想要的结果，例如由多个对抗式评审智能体组成的集群，就不应该把它们的分歧整合成一条看似确定的观测。

[按范围划分的观测整合策略](https://hindsight.vectorize.io/blog/2026/09/30/per-scope-consolidation-strategies)介绍了范围的选择方式。应预先决定要采用哪种行为，因为之后改标签的代价很高：标签变化会使基于这些记忆生成的观测失效，并将来自其他文档的所有共同来源重新加入队列。

## 实际做法 {#what-i-would-actually-do}

1. **处理共同问题时，让整个集群使用一个记忆库和一套标签。** 相互佐证正是这样做的目的；不要因疏忽而把它按范围拆开。
2. **为每个工作项设置稳定的 `document_id`**，由工作智能体和任务共同生成，这样重试才是真正的重试。
3. **启用记忆防护**，将 `prompt_injection` 设为 `quarantine`，并把规划器简报放进不可变命名空间。
4. **读取观测，而不是事实。** 原始层按设计会保留二十份副本；整合层才是为阅读而构建的。
5. **把 `proof_count` 当作信号，而不是评分。** 它统计不同且仍有效的来源，恰好反映相互佐证——前提是智能体确实没有共享上下文，并且重试没有虚增计数。
6. **如果近似重复观测的协调对你很重要，就使用 Postgres**，因为 Oracle 会跳过这一步。

智能体集群并不是多了一双手的单个智能体。只有在这种架构中，记忆才能区分某件事是单个智能体的看法，还是多个智能体独立发现的结果；而这种能力完全依赖其中一层，以及少数几个决定你能否获得它的设置。
