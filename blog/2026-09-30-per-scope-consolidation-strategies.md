![同一事实在不同范围按各自的任务说明进行整合：用户范围保留完整细节，公司范围只保留趋势](/img/blog/per-scope-consolidation.webp)

七月，我们发布了[智能体记忆结构指南](https://hindsight.vectorize.io/blog/2026/07/16/bank-strategy-agent-memory)，把核心选择描述成一个两难：

> 范围太宽，一个用户的记忆会渗入另一个用户的记忆；范围太窄，智能体又无法访问它需要的内容，因为这些内容位于另一个它看不到的记忆库中。

Hindsight 0.10.2 放宽了这一限制。你可以只保留一个记忆库，让所有内容都可访问，同时为库内的不同读者设置不同的任务说明。

<!-- truncate -->

## 要点 {#tldr}

- **现在，每个观测范围都可以按自己的任务说明进行整合**，通过 `consolidation_strategies` 设置。
- **每项策略恰好只能设置四个字段**，其他配置仍在记忆库级生效。
- **首个匹配项整体生效。** 后续策略不会补上前一项留下的空缺。
- **有一个实际陷阱：** 策略永远无法匹配无标签范围，而文档没有说明这一点。
- `observation_scope_limits` 仍然有效，但匹配规则不同；直接迁移可能会扩大原本想收窄的范围。

## 原先哪些设置按范围配置，哪些不是 {#what-was-already-per-scope-and-what-wasnt}

先简要回顾一下，因为这里的术语很重要。

**观测范围**是整合时用于对观测分组的标签集合。你可以在存入时通过 `observation_scopes` 选择范围的构成方式：`combined` 将一条记忆的全部标签合并，在一次处理中整合；`per_tag` 按每个标签分别处理一次；`all_combinations` 按每个子集分别处理一次；`shared` 则在无标签的空范围内统一处理一次。

因此，一条带有 `user:dana`、`team:exec`、`company:acme` 标签的记忆，原本就可以按不同读者分别生成三组观测。这并非新功能。

原先无法区分的是这些读者各自的要求。唯一可按范围设置的是观测数量上限：通过 `observation_scope_limits` 将范围模式映射为一个整数。**任务说明则是记忆库级配置。** 所有范围收到的都是相同记录指令。

文档直言了这种做法的后果：

> 每个范围都会生成自己的观测。但如果大家共用同一份任务说明，公司范围就会获得与 Dana 私有范围一样详细的信息，包括姓名、交易规模以及任何保密内容，只是更多人能看到这些信息。

披着配置问题外衣的，其实是保密问题。范围隔离已经存在，但内容上没有相应的克制。

## 相同事实，两份任务说明 {#the-same-facts-two-briefs}

`consolidation_strategies` 可以将任务说明关联到范围模式：

```json
[
  {
    "scopes": [{"tags": ["company:*"]}],
    "observations_mission": "This scope is shared with the whole company. Record only general, industry-level trends. Never name a specific company, person, deal size or funding stage.",
    "max_observations_per_scope": 20
  },
  {
    "scopes": [{"tags": ["team:*"]}],
    "observations_mission": "Record decisions the team must act on."
  }
]
```

同一批底层事实可以得到这样的结果：

> Dana 的范围保留“Acme Robotics 签下为期 3 年的租约，租用一组 4,000 GPU 集群”，而公司范围只记录“企业正在租用 GPU 集群来运行开放权重模型”。

这不是事后脱敏。公司范围从一开始就没有接收到这些细节，因为每个范围都有自己的任务说明，并各自单独调用整合流程。一个范围的设置不会传入另一个范围的调用。

可以在单个记忆库中设置 `consolidation_strategies`，也可以通过 `HINDSIGHT_API_CONSOLIDATION_STRATEGIES` 全局配置，或在控制平面的“记忆库 → 配置 → 观测”中设置。

## 策略可以改变的恰好是四项设置 {#exactly-four-things-a-strategy-can-change}

这里需要说清楚：策略并不能按范围覆盖任意设置。每项策略可以设置四个字段：

| 字段 | 作用 |
|---|---|
| `observations_mission` | 面向这类读者的任务说明 |
| `max_observations_per_scope` | 此范围最多可容纳多少条观测 |
| `consolidation_source_facts_max_tokens` | 每次调用能看到多少证据 |
| `consolidation_source_facts_max_tokens_per_observation` | 分配给每条观测的证据预算 |

列表上方的代码注释解释了这条规则：这些设置只保留了真正会因读者而异的部分，即任务说明、范围可容纳的观测数，以及每次整合调用所能看到的来源证据量。其他配置仍在记忆库级生效。

特别是，**语义去重阈值不属于策略设置**，它仍是记忆库级的 `0.97`。这没有造成问题，因为去重只会比较同一范围内的观测；因此，经过删减的公司观测不会与 Dana 的详细观测成为合并候选。两项功能可以组合使用，彼此无需感知对方。

## 首个匹配项整体生效 {#first-match-wins-whole}

范围模式使用 glob。在同一个模式中，每个 glob 都必须匹配某个标签。一个策略的 `scopes` 中，任意一个模式匹配上即可认领该范围。多个策略之间则按列表顺序判断，首个认领此范围的策略会完整地接管它。

这条规则比听起来更严格，而且是有意如此：

> 按列表顺序，第一个认领此范围的策略会整体生效。例如 `["company:*"]` 和 `["company:acme"]` 同时匹配时，只应用排在前面的策略：使用它所设的值；它未设置的字段则使用记忆库级值。后续策略绝不会补上前一项留下的空缺。

因此，若列表是 `[{company:acme, cap 5}, {company:*, mission X}]`，`company:acme` 会使用上限 5，以及**记忆库级**任务说明，而不是任务说明 X。请将具体规则排在通用规则之前，并确保每项规则都完整。

提交记录说明了这种设计的原因。早期版本会逐字段解析：任务说明取自第一个设置了任务说明的策略，容量上限则取自第一个设置了上限的策略。

> 这样会让两个策略在同一范围内悄悄混合，没人能看出该范围实际采用的是哪项策略。现在只有一个获胜策略，控制平面就能显示出来。

这种做法以牺牲灵活性换取可调试性。对于决定智能体可以记住哪些个人信息的配置，这通常是合理的选择。

匹配有两种模式。默认的 `"all"` 是包含匹配：范围拥有模式中的所有标签，也可以有更多标签。`"exact"` 要求标签集合完全一致。没有 `"any"` 模式，因为策略的多个范围模式本来就是候选项；若要表示“这些标签中任意一个”，可以为每个标签各写一个模式。

## 陷阱：策略无法认领全局范围 {#the-trap-your-global-scope-cannot-be-claimed}

这是我们本该记录、却没有写进文档的行为。

**策略永远无法认领无标签范围。** 两种匹配器都会直接拒绝空标签集合。包含匹配器的实现正是：

```python
return bool(tags) and all(any(fnmatchcase(t, g) for t in tags) for g in globs)
```

开头的 `bool(tags)` 意味着任何模式都无法匹配全局范围：`["company:*"]` 不行，单独的 `["*"]` 也不行。文档字符串顺带承认了“无标签范围永远不会匹配”，测试套件也对此作了断言。但策略章节完全没有提到这一点。

这比乍看之下影响更大，因为文档建议用 `shared` 来处理易变标签。如果 Retain（存入）调用带有每个会话各自的 ID，建议在 `shared` 范围内整合，这样所有会话就会合并处理，而不是每个会话都生成自己的范围。照此操作后，你就会得到一个永久采用记忆库默认值、任何策略都无法触及的范围，而且系统不会告诉你。

如果你需要一条使用不同任务说明的兜底规则，请为它添加真实标签并匹配该标签，而不要依赖 `shared`。

## 从 `observation_scope_limits` 迁移 {#migrating-from-observation_scope_limits}

旧字段已弃用，但仍然有效，只作为观测数量上限的回退值。优先顺序是：获胜策略设置的上限（如果有），然后是 `observation_scope_limits`，最后是记忆库默认值。

有两个容易弄错的后果。

只设置任务说明的策略不会同时带上容量上限。如果策略认领了某范围，却没有设置 `max_observations_per_scope`，上限仍会从 `observation_scope_limits` 获取；即使后面还有其他策略，也会**越过它们**去查找回退值。相关测试的名称正是 `test_the_winners_missing_cap_falls_back_past_later_strategies`。

此外，这两个字段的匹配方式不同。`observation_scope_limits` 只做精确匹配；策略默认做包含匹配。若逐字复制旧规则，新规则会悄悄匹配**更多**范围，除非你加上 `"tags_match": "exact"`。目前没有任何提示会提醒你这一步迁移要求，因此本文特别指出这一点。

还应知道，弃用只体现在文档中，没有运行时警告，日志里也不会出现迁移提示。

## 其他值得了解的限制 {#other-limits-worth-knowing}

**无法表达否定条件。** 你不能写“包含公司标签但不包含用户标签”。模式只能做正向匹配。

**在 Oracle 上，策略可用，但协调处理不可用。** 语义去重使用仅适用于 Postgres 的 SQL，因此无论配置的阈值是多少，Oracle 上都会跳过去重。由于容量上限能防止近似重复项不断填满范围，Oracle 部署会更依赖 `max_observations_per_scope`。

**验证结果取决于配置入口。** 通过 API 或控制平面保存时，格式错误的策略会被拒绝：模式禁止未知键，因此把 `"scopes"` 错写为 `"scope"` 会返回 400，而不会变成一条悄然不起作用的规则。通过环境变量配置则没有这类检查。条目会以宽松方式解析，错误条目会被静默丢弃；无法识别的 `tags_match` 会静默变为 `"all"`，而不是报错。如果通过环境变量配置，请随后在控制平面检查策略实际认领的范围是否符合预期。

**观测不会标明生成它的策略。** 跨范围 Recall（召回）时，你会看到由不同任务说明生成的观测并列显示，只有它们携带的范围标签能区分彼此。范围端点会列出范围及观测数量，预览则会显示每个范围归属哪项策略；但要查明归属，你得查看配置，而不是观测结果本身。

## 这对“一个记忆库还是多个”的选择意味着什么 {#where-this-leaves-the-one-bank-question}

七月那篇文章建议谨慎选择记忆库边界，因为它也是 Recall 能触及的边界；这一点仍然成立。变化在于，保密性的全部责任不必再由记忆库边界承担。

Recall 能触及哪些内容，由记忆库决定；采用哪份任务说明，则由范围决定。你可以让智能体访问整个组织的记忆，同时按不同读者决定记忆中允许表达哪些内容。

## 常见问题 {#faq}

**策略能为自己的范围更改去重阈值吗？**
不能。策略只支持上面四个字段。语义去重阈值仍在记忆库级设置为 `0.97`。实际上这不会造成问题，因为去重只会比较同一范围内的观测，所以公司范围的概括内容与 Dana 的详细内容不会成为彼此的合并候选。

**没有任何策略认领的范围会怎样？**
它会使用记忆库级配置，控制平面会将其标记为“默认”。没有隐式兜底策略；这也是无标签范围限制影响较大的另一个原因：你无法写一条兜底策略来覆盖所有未匹配项。

**如果我写了一项没有设置任何字段的策略，它会挡住后面的策略吗？**
不会。解析配置时会丢弃不含任何设置的策略，因此它不会认领范围，也不会遮挡后续策略。这是有意设计的，因为控制平面会在你输入时保存配置，尚未写完的规则不应生效。

**我能为 `shared` 范围单独设置任务说明吗？**
不能。这是一个确实令人意外的限制：没有模式能匹配空标签集合。如果你需要使用不同任务说明的兜底范围，请添加真实标签并匹配它。

**`observation_scope_limits` 会被移除吗？**
它已弃用，但尚未移除，并且仍可作为观测数量上限的回退值，在策略之后读取。注意，它原本只负责设定上限；策略之所以存在，正是因为需要根据不同读者改变任务说明。

**某个范围的任务说明会泄漏到其他范围的观测中吗？**
不会。每个解析出的范围都会单独调用整合流程，因此一个范围的设置不会传入另一个范围。写入的观测会带有该范围的标签。

**如何检查某个范围实际由哪项策略认领？**
控制平面会显示每个范围所属的策略；范围端点会列出记忆库中的范围及其观测数量。每次修改后都值得检查，特别是在通过环境变量配置策略时。
