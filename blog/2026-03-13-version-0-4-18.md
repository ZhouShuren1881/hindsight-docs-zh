Hindsight 0.4.18 添加了具有布尔逻辑的复合标签过滤、更精简的 Python 软件包、MiniMax 和 Jina MLX (Apple Silicon) 提供程序支持、每个记忆库 HNSW 向量索引以及可配置的记忆查询查询令牌限制。

<!-- truncate -->

- [**复合标签过滤**](#compound-tag-filtering)：用`tag_groups`表达复杂的AND/OR/NOT标签谓词。
- [**超薄Python 封装**](#slim-python-packages)：仅安装您需要的可选 ML 和嵌入式数据库附加功能。
- [**MiniMax LLM 提供商**](#minimax-llm-provider)：使用 MiniMax-M2.5（204K 上下文）作为LLM 后端。
- [**Jina MLX重排序器**](#jina-mlx-reranker)：原生 Apple Silicon 重排序，无需外部 API。
- [**每个记忆库 HNSW 索引**](#per-bank-hnsw-indexes)：通过每个记忆库的专用向量索引实现更快的语义搜索。

## 复合标签过滤 {#compound-tag-filtering}

以前的标签过滤支持具有单一匹配模式的平面标签列表（`any`、`all`、`any_strict`、`all_strict`）。这对于简单的范围界定很有效，但当您需要表达诸如“用户 A，在这些工作流程步骤之一中，但未存档”之类的谓词时，它就显得不足了。

`tag_groups`为记忆召回和反思添加了递归布尔过滤语言。每个组要么是带有标签列表和匹配模式的**叶**节点，要么是使用`and`、`or`或`not`的**化合物**节点。顶级组通过 AND 组合在一起。

**步骤过滤器和用户范围** — 两组在顶层进行 AND 运算：

```json
{
  "tag_groups": [
    { "tags": ["step:5", "step:8", "step:12"], "match": "any_strict" },
    { "tags": ["user:ep_42"], "match": "all_strict" }
  ]
}
```

**嵌套 OR** — 用户必须匹配，加上步骤或优先级标志：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "or": [
        { "tags": ["step:5"], "match": "any_strict" },
        { "tags": ["priority:high"], "match": "all_strict" }
    ]}
  ]
}
```

**排除** — 用户必须匹配，但存档的记忆被排除：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "not": { "tags": ["archived"], "match": "any_strict" } }
  ]
}
```

`tag_groups` 也可以与现有的 `tags` / `tags_match` 字段组合 - 它们通过 AND 组合在一起。这使得您可以轻松地将复合过滤增量添加到现有的记忆召回调用中，而无需重写您已有​​的更简单的过滤器。

请参阅 [记忆召回文档](/developer/api/recall#tag_groups) 以获得完整参考。

## 超薄Python 封装 {#slim-python-packages}

默认情况下，`hindsight-api`捆绑了运行嵌入和重排序所需的所有内容**本地**——PyTorch、句子转换器、转换器和MLX。这些本地 ML 库使零配置部署开箱即用，但它们很重（几个 GB 的依赖项）。如果您已经将 Hindsight 指向外部嵌入或重排序服务（TEI、Cohere、ZeroEntropy、LiteLLM），则不需要任何这些。

我们已经为此用例提供了一个超薄的Docker图像变体。现在 PyPI 上也可以使用同样的拆分。

该软件包现在分为可选的附加功能：

|安装|你得到什么|
|---------|-------------|
|`pip install hindsight-api-slim`|核心API服务器；没有本地机器学习模型|
|`pip install "hindsight-api-slim[local-ml]"`|添加 PyTorch、句子转换器、MLX（Apple Silicon）|
|`pip install "hindsight-api-slim[embedded-db]"`|添加 pg0 嵌入（本地 PostgreSQL）|
|`pip install "hindsight-api-slim[all]"`|本地机器学习+嵌入式数据库；相当于旧的`hindsight-api`|
|`pip install hindsight-api`|不变；仍然安装完整的堆栈以实现向后兼容性|

基础`hindsight-api-slim`软件包包括FastAPI服务器、所有LLM提供商集成（OpenAI、Anthropic、Gemini、Groq、MiniMax等）、Cohere云嵌入/重排序、LiteLLM、MCP等API 功能。只有本地 ML 模型依赖项被门控在 `[local-ml]` 额外项后面。

如果您使用外部嵌入和重排序提供程序，您现在可以通过 `pip install hindsight-api-slim` 获得显著精简的 Python 环境。

## MiniMax LLM 提供商 {#minimax-llm-provider}

MiniMax 现在是受支持的 LLM 后端。 MiniMax-M2.5 是该提供商的默认模型，具有 204K 令牌上下文窗口。

```bash
HINDSIGHT_API_LLM_PROVIDER=minimax
HINDSIGHT_API_LLM_API_KEY=your_minimax_key
HINDSIGHT_API_LLM_MODEL=MiniMax-M2.5   #可选；这是默认值
```

MiniMax 使用OpenAI兼容的API，因此不需要额外的依赖项。一个供应商特定的细节：MiniMax 要求温度值在 `(0.0, 1.0]` 范围内，因此超出该范围的值会被自动限制。

## Jina MLX重排序器 {#jina-mlx-reranker}

很大一部分Hindsight用户在Mac上本地运行。默认的本地重排序器在低并发下运行良好，但在较高负载下它会成为瓶颈——它通过 PyTorch 在 CPU 上运行，根本没有利用 Apple Silicon 中的 GPU 内核。当许多记忆召回请求同时进行时，这一点尤其明显。

`jina-mlx` 提供商通过在 MLX 上本地运行重排序器解决了这个问题，MLX 是 Apple 的 ML 框架，直接针对 M 系列芯片的统一记忆和 GPU/神经引擎。结果是每次重新排序调用的延迟显著降低，并发负载下的吞吐量显著提高 - 无需外部重排序API。

```bash
HINDSIGHT_API_RERANKER_PROVIDER=jina-mlx
```

提供商运行[`jinaai/jina-reranker-v3-mlx`](https://huggingface.co/jinaai/jina-reranker-v3-mlx)，一个 0.6B 多语言交叉编码器。该模型（约 1.2 GB）会在首次启动时自动从 HuggingFace Hub 下载并缓存在本地。

​​它也是一个列表式重排序器，这意味着它会在一次前向传递中对所有候选者进行评分，而不是一次对一个文档进行评分。延迟与候选者的数量呈亚线性关系，这有助于在高记忆负载下进一步发挥作用。

:::note jina-重排序器-v3-mlx 模型已获得 CC BY-NC 4.0 许可。如需商业用途，请联系 Jina AI。
:::

## 每个记忆库 HNSW 索引 {#per-bank-hnsw-indexes}

语义搜索现在使用每个记忆库和事实类型的专用部分 HNSW 向量索引，而不是单个全局索引。

以前，当通过`bank_id`过滤记忆召回查询时，PostgreSQL的规划器将在该列上使用B树索引，然后顺序扫描嵌入值。存在的仅事实类型的部分 HNSW 索引从未被选择，因为规划者有一个更便宜的 `bank_id` 过滤器选项。结果：大型记忆库上的语义搜索速度比应有的速度要慢。

0.4.18 为每个记忆库创建三个部分 HNSW 索引（`world`、`experience` 和 `observation` 事实类型各一个），并将检索查询重写为每个事实类型子查询的 `UNION ALL`。现在，每个臂都可以使用其专用的部分索引，并且规划器始终选择 HNSW 索引扫描而不是顺序扫描。

迁移在启动时自动运行，并为所有现有记忆库创建索引。新记忆库在创建时立即获取其索引，并且当记忆库被删除时索引将被删除。无需配置。

## 其他更新 {#other-updates}

**改进**
- 记忆召回查询令牌限制现在可以通过`HINDSIGHT_API_RECALL_MAX_QUERY_TOKENS`进行配置（默认值：500）。当您希望允许更长的多轮上下文作为记忆召回查询时很有用。
- LiteLLM 重排序器现在会截断超出提供程序上下文限制的文档，从而防止在单个事实块异常长时重排序失败。

**错误修复**
- 修复了回忆记忆未作为OpenClaw的系统上下文注入的问题。
- 修复了守护进程启动时嵌入式配置文件未在 CLI 元数据中注册的问题。
- ​​删除记忆库时取消进行中的异步操作，以避免悬而未决的后台工作。
