Hindsight 0.4.18 新增了支持布尔逻辑的复合标签过滤、更精简的 Python 软件包、MiniMax 和 Jina MLX（Apple Silicon）服务提供方支持、按记忆库划分的 HNSW 向量索引，以及可配置的 Recall 查询令牌上限。

<!-- truncate -->

- [**复合标签过滤**](#compound-tag-filtering)：通过 `tag_groups` 表达复杂的 AND/OR/NOT 标签条件。
- [**精简版 Python 软件包**](#slim-python-packages)：按需安装软件包，并通过可选附加项选择 ML 和嵌入式数据库支持。
- [**MiniMax LLM 服务提供方**](#minimax-llm-provider)：使用 MiniMax-M2.5（204K 上下文）作为 LLM 后端。
- [**Jina MLX 重排序模型**](#jina-mlx-reranker)：在 Apple Silicon 上原生运行重排序，无需调用外部 API。
- [**按记忆库划分的 HNSW 索引**](#per-bank-hnsw-indexes)：通过为每个记忆库单独建立向量索引，加快语义搜索。

## 复合标签过滤 {#compound-tag-filtering}

此前，标签过滤支持带有单一匹配模式（`any`、`all`、`any_strict`、`all_strict`）的扁平标签列表。这适用于简单的范围限定，但无法充分表达“属于用户 A、处于这些工作流步骤之一、且未归档”之类的条件。

`tag_groups` 为 Recall 和 Reflect 增加了一种递归的布尔过滤语言。每个组可以是带有标签列表和匹配模式的**叶节点**，也可以是使用 `and`、`or` 或 `not` 的**复合节点**。顶层的各组之间采用 AND 关系。

**步骤过滤条件与用户范围**——顶层的两个组通过 AND 组合：

```json
{
  "tag_groups": [
    { "tags": ["step:5", "step:8", "step:12"], "match": "any_strict" },
    { "tags": ["user:ep_42"], "match": "all_strict" }
  ]
}
```

**嵌套 OR**——必须匹配用户，同时还要匹配某个步骤或优先级标记：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "or": [
        { "tags": ["step:5"], "match": "any_strict" },
        { "tags": ["priority:high"], "match": "all_strict" }
    ]}
  ]
}
```

**排除条件**——必须匹配用户，同时排除已归档的记忆：

```json
{
  "tag_groups": [
    { "tags": ["user:alice"], "match": "all_strict" },
    { "not": { "tags": ["archived"], "match": "any_strict" } }
  ]
}
```

`tag_groups` 还可以与现有的 `tags` / `tags_match` 字段组合使用；两者之间采用 AND 关系。这样，你可以逐步为现有的 Recall 调用添加复合过滤条件，而无需重写已有的简单过滤器。

完整说明请参阅 [Recall 文档](/developer/api/recall#tag_groups)。

## 精简版 Python 软件包 {#slim-python-packages}

默认情况下，`hindsight-api` 会捆绑本地运行嵌入和重排序所需的全部依赖——PyTorch、sentence-transformers、transformers 和 MLX。这些本地 ML 库让部署无需配置即可开箱运行，但依赖体积很大（数 GB）。如果你已将 Hindsight 配置为使用外部嵌入或重排序服务（TEI、Cohere、ZeroEntropy、LiteLLM），就不需要这些本地依赖。

我们此前已为此用例发布精简版 Docker 镜像。现在，PyPI 上也提供了同样的拆分方式。

软件包现在拆分为可选附加项：

| 安装命令 | 包含内容 |
|---------|-------------|
| `pip install hindsight-api-slim` | 核心 API 服务器；不含本地 ML 模型 |
| `pip install "hindsight-api-slim[local-ml]"` | 增加 PyTorch、sentence-transformers、MLX（Apple Silicon） |
| `pip install "hindsight-api-slim[embedded-db]"` | 增加 pg0-embedded（本地 PostgreSQL） |
| `pip install "hindsight-api-slim[all]"` | 本地 ML 与嵌入式数据库；等同于旧版 `hindsight-api` |
| `pip install hindsight-api` | 保持不变；仍安装完整依赖栈，以保持向后兼容 |

基础版 `hindsight-api-slim` 软件包包含 FastAPI 服务器、所有 LLM 服务提供方集成（OpenAI、Anthropic、Gemini、Groq、MiniMax 等）、Cohere 云端嵌入与重排序、LiteLLM、MCP 以及全部 API 功能。只有本地 ML 模型依赖项需要通过 `[local-ml]` 附加项安装。

如果你使用外部嵌入和重排序服务提供方，现在可以通过 `pip install hindsight-api-slim` 获得精简许多的 Python 环境。

## MiniMax LLM 服务提供方 {#minimax-llm-provider}

现在可以将 MiniMax 用作 LLM 后端。MiniMax-M2.5 是该服务提供方的默认模型，上下文窗口为 204K 个令牌。

```bash
HINDSIGHT_API_LLM_PROVIDER=minimax
HINDSIGHT_API_LLM_API_KEY=your_minimax_key
HINDSIGHT_API_LLM_MODEL=MiniMax-M2.5   # 可选；这是默认值
```

MiniMax 使用兼容 OpenAI 的 API，因此无需安装额外依赖。需要注意一个服务提供方特有的要求：MiniMax 的 temperature 值必须在 `(0.0, 1.0]` 范围内，超出范围的值会自动截断到该范围内。

## Jina MLX 重排序模型 {#jina-mlx-reranker}

许多 Hindsight 用户在 Mac 上本地运行服务。默认的本地重排序模型在并发量较低时运行良好，但负载较高时会成为瓶颈：它通过 PyTorch 在 CPU 上运行，完全没有利用 Apple Silicon 的 GPU 核心。多个 Recall 请求同时运行时，这个问题尤其明显。

`jina-mlx` 服务提供方通过在 MLX 上原生运行重排序模型解决了这个问题。MLX 是 Apple 的 ML 框架，专为 M 系列芯片的统一内存以及 GPU/神经网络引擎而设计。这样可以显著降低每次重排序调用的延迟，并在并发负载下大幅提高吞吐量，而且无需调用外部重排序 API。

```bash
HINDSIGHT_API_RERANKER_PROVIDER=jina-mlx
```

该服务提供方运行 [`jinaai/jina-reranker-v3-mlx`](https://huggingface.co/jinaai/jina-reranker-v3-mlx)，这是一个 0.6B 参数的多语言交叉编码器模型。模型大小约为 1.2 GB，首次启动时会自动从 HuggingFace Hub 下载并缓存在本地。

它还是一种列表式重排序模型，也就是说，它会在一次前向传播中为所有候选项评分，而不是逐个处理文档。延迟随候选项数量的增长呈次线性，这在 Recall 负载较高时还能进一步提升性能。

:::note
`jina-reranker-v3-mlx` 模型采用 CC BY-NC 4.0 许可。商业用途请联系 Jina AI。
:::

## 按记忆库划分的 HNSW 索引 {#per-bank-hnsw-indexes}

语义搜索现在会针对每个记忆库和事实类型使用专用的 HNSW 部分向量索引，而不是共用一个全局索引。

此前，Recall 查询按 `bank_id` 过滤时，PostgreSQL 规划器会使用该列上的 B-tree 索引，然后顺序扫描嵌入向量值。已有的仅按事实类型划分的 HNSW 部分索引从未被选中，因为规划器认为先按 `bank_id` 过滤成本更低。因此，大型记忆库上的语义搜索速度低于预期。

0.4.18 会为每个记忆库创建三个 HNSW 部分索引，分别对应 `world`、`experience` 和 `observation` 事实类型，并将检索查询改写为按事实类型划分的子查询，再通过 `UNION ALL` 合并。这样，每个子查询分支都可以使用对应的专用部分索引，规划器也会稳定地选择 HNSW 索引扫描，而非顺序扫描。

迁移会在启动时自动运行，并为所有现有记忆库创建索引。新记忆库在创建时会立即建立索引；删除记忆库时，相应索引也会删除。无需进行任何配置。

## 其他更新 {#other-updates}

**改进**
- 现在可以通过 `HINDSIGHT_API_RECALL_MAX_QUERY_TOKENS` 配置 Recall 查询的令牌上限（默认值：500）。如果你希望 Recall 查询支持更长的多轮上下文，这项设置会很有用。
- LiteLLM 重排序模型现在会截断超过服务提供方上下文限制的文档，避免单个事实文本分块过长时导致重排序失败。

**错误修复**
- 修复了 Recall 得到的记忆未注入 OpenClaw 系统上下文的问题。
- 修复了守护进程启动时，嵌入式配置档案未登记到 CLI 元数据中的问题。
- 删除记忆库时会取消正在进行的异步操作，以避免后台任务遗留。
