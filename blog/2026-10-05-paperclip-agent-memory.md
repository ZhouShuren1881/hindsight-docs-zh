![Paperclip 为智能体提供组织结构图；bankGranularity 决定记忆边界如何划分](/img/blog/paperclip-agent-memory.webp)

你有两个为同一家公司工作的智能体。

其中一个已经调查过某项客户集成，找到了反复出现的故障原因，并在某条工单评论中记录了决定。另一个智能体现在接手了一条相关工单。它拥有相同的工具、相同的公司背景，也能访问相同的工作内容。但它开始工作时，并不知道第一个智能体发现了什么。

于是它又调查了一遍同一个故障。

现在，只改一个设置。

不要再给每个智能体各自的记忆库，而是给公司一个共享记忆库。第二个智能体可以在开始工作前召回第一个智能体做出的决定。工作由此逐步积累，而不是一再重来。

这听起来像一个很小的配置改动，其实并非如此。

Paperclip 为智能体提供组织结构：谁向谁汇报、谁可以接收工作，以及每个主体获准执行哪些操作。Hindsight 在这套结构之下又划出一道边界：智能体可以记住什么。

问题不在于智能体是否应该拥有记忆，而在于这道记忆边界应该设在哪里。

在 Paperclip 集成中，决定这一点的设置就是 `bankGranularity`。

## 简要说明 {#tl-dr}

- **默认范围是每家公司、每个智能体各自一个记忆库。** `bankGranularity` 默认为 `["company", "agent"]`，因此 Paperclip 的每家公司中，每个智能体都有自己的 Hindsight 记忆库。
- **这个默认值是一种决策，并非中性设置。** 它会阻止智能体看到彼此的记忆，但也意味着某个智能体可能会重复另一个智能体已经完成的工作。
- **按公司划分会让记忆成为协作界面。** `["company"]` 让同一公司的所有智能体使用同一个记忆库，同时将不同公司隔开。
- **按智能体划分会朝另一个方向改变边界。** `["agent"]` 允许智能体在不同公司之间沿用记忆；这可能有用，但显然会带来跨公司影响。
- **该选择位于 Paperclip 实例级别的 Hindsight 插件设置中。** 安装 `@vectorize-io/hindsight-paperclip`，然后在 Settings、Plugins、Hindsight Memory 中配置。
- 在多智能体系统中，`bankGranularity` 回答的是“一个智能体可以记住另一个智能体工作的哪些内容”，而默认设置已经替你回答了这个问题。

## 1. Paperclip 已经提供了什么 {#1-what-paperclip-already-gives-you}

Paperclip 将一家公司建模为由多个智能体组成的组织。

智能体有角色、职务、汇报关系、权限和预算。按照 Paperclip 自己的描述，每个智能体都有上级、职务和工作说明，任务会沿着组织结构图向上或向下委派。工单是工作的基本单位，任务可以分配给智能体或人员。

Paperclip 也会管理谁能做什么。组织结构图有意同时涵盖人类和智能体。不过，底层访问控制是分开的：一边是人类角色与权限，另一边是智能体 API 密钥与智能体是否符合条件。

还有一个对后文都很重要的特性：一次 Paperclip 部署可以承载多个组织，并通过公司范围的访问检查，将各组织的工作、智能体和活动彼此隔开。

可以用下面的模型来理解组织：

```
                 CEO
                /   \
        Research     Engineering
          /             \
     Researcher       Coder
```

组织结构图说明谁为谁工作。

任务系统说明每个智能体在做什么。

权限系统说明每个智能体获准做什么。

但这些结构没有回答一件事：

每个智能体可以记住什么？

这就是记忆边界开始变得重要的地方。

## 2. 组织结构图未涵盖的内容 {#2-the-thing-the-org-chart-does-not-cover}

权限管理操作。

记忆管理上下文。

两者彼此相关，但边界并不相同。

设想一个研究智能体发现某个客户使用了不常见的身份验证流程，并将这一决定记录在记忆中。后来，一个编码智能体接到涉及同一客户的任务。

编码智能体是否应该能够召回这个决定？

如果答案是肯定的，两个智能体就需要共享记忆边界。

如果答案是否定的，它们就需要各自独立的记忆。

Hindsight 记忆库就是这样一种边界。它是供 Recall（召回）和 Retain（存入）操作使用的隔离记忆存储。一个记忆库中的记忆不会自动提供给从另一个记忆库进行召回的智能体。

因此，选择记忆库是一项架构决策。

Paperclip 集成将这项决策做成了配置，无需你把它分别构建到每个智能体中。

关键设置是 `bankGranularity`。

默认值是：

```json
["company", "agent"]
```

这意味着同一家公司中的研究智能体和编码智能体不会共用一个记忆库。

这个设置确实如其名称所示在发挥作用，同时也替你做出了选择。

## 3. 插件具体如何工作 {#3-what-the-plugin-does-concretely}

Hindsight Paperclip 插件安装在 Paperclip 实例级别。目前发布的版本是 `@vectorize-io/hindsight-paperclip` v0.4.1，要求 Paperclip 版本为 2026.720.0 或更高。

通过以下命令安装：

```bash
pnpm paperclipai plugin install @vectorize-io/hindsight-paperclip
```

然后在 Settings、Plugins、Hindsight Memory 中配置。

你不需要修改每个智能体。

插件会订阅 Paperclip 生命周期事件，并将这些事件接入 Hindsight。

一次运行开始时，插件会收到与该次运行关联的工单。它会获取工单，将标题和描述合并成召回查询，然后在该智能体的记忆库中搜索。

搜索结果会缓存下来，供本次运行使用。

运行期间，智能体还可以使用两个工具：

```
hindsight_recall(query)
hindsight_retain(content)
```

`hindsight_recall` 允许智能体针对特定内容进行查找。如果查询与运行开始时使用的查询相同，就会复用缓存结果。两者通过去除首尾空白后的字符串相等来判断。查询不同则会触发实时召回。

`hindsight_retain` 允许智能体立即存入重要的事实、决定或结果。

此外还有一条自动存入路径。

触发 `issue.comment.created` 时，插件会获取评论全文并将其存入记忆。事件载荷中只有一段 120 字符的摘要，因此插件会调用 Paperclip 的评论 API 获取全文。如果调用失败，它会退回使用这段摘要，避免完全丢失评论。

对于智能体撰写的评论，插件会使用评论所属的智能体来确定记忆库归属。如果评论没有智能体归属信息，插件就会回退使用工单的受派人。

整个流程如下：

```
Paperclip 工单
      │
      ▼
agent.run.started
      │
      ├── 获取工单
      │
      ├── 标题 + 描述
      │
      ▼
   Hindsight
      │
      ▼
 将召回结果写入运行状态
      │
      ▼
    智能体
      │
      ├── hindsight_recall()
      │
      └── hindsight_retain()
      │
      ▼
issue.comment.created
      │
      ▼
 存入完整评论
```

有一个细节值得指出，因为过去的命名容易让人误以为订阅的是另一个事件。

插件订阅了 `agent.run.finished`，但对应的处理程序不执行任何操作。Paperclip 的运行结束事件载荷不包含智能体输出，因此插件无法从该事件中存入运行输出。

`autoRetain` 控制**评论**的自动存入。它不会让 `agent.run.finished` 处理程序存入运行输出。

在 0.4.0 及更早版本中，这个设置的标签是“运行结束时自动存入”，说明文字也称运行完成时会存入运行输出，但实际行为并非如此。0.4.1 重新命名了此设置。如果插件设置仍显示旧文案，说明你使用的是 0.4.0。

## 4. 划分记忆的四种方式 {#4-four-ways-to-organise-the-memory}

一旦把记忆库看作一道记忆边界，`bankGranularity` 就更容易理解。

不要从配置字符串入手。

先想清楚你希望建立怎样的组织。

### 默认设置：每位专家都有自己的笔记本 {#the-default-each-specialist-keeps-its-own-notebook}

```json
["company", "agent"]
```

生成的记忆库 ID 如下：

```
paperclip::{companyId}::{agentId}
```

假设你的公司有三个智能体：

```
Researcher
Coder
Reviewer
```

每个智能体都有单独的记忆库。

研究员记住自己的研究内容。编码员记住自己的编码工作。审核员记住自己的审核工作。

一个智能体学到的内容不会自动成为另一个智能体的记忆。

当智能体确实承担不同职责，或者你还不确定哪些内容应该共享时，这是最稳妥的默认设置。

但对协作团队来说，这也会造成不易察觉的浪费。

如果研究员发现一条重要事实并将其存入自己的记忆库，编码员就无法召回它。编码员只能重新发现这条事实，或者通过其他明确渠道接收它。

这就是关键的权衡。

隔离可以避免不希望发生的记忆共享。

它也会阻止有用的记忆共享。

### 公司记忆：整个团队共用一本笔记 {#company-memory-the-team-keeps-one-notebook}

```json
["company"]
```

生成的记忆库 ID 如下：

```
paperclip::{companyId}
```

现在，公司内部的所有智能体都会使用同一个记忆库。

研究员记录一项决定。

编码员可以召回这项决定。

审核员可以召回他们双方学到的内容。

如果这些智能体是同一协作团队中的不同角色，而不是互不相关的专家，这就是自然的选择。

这种方式也保留了公司边界。A 公司的智能体不会自动召回 B 公司的记忆。

对于许多 Paperclip 部署来说，这是默认设置之外最值得考虑的选择。

组织结构图表明这些智能体属于同一家公司。

此时记忆库的划分也与之相符。

### 智能体记忆：专家可以带着笔记本跨公司工作 {#agent-memory-the-specialist-carries-its-notebook-between-companies}

```json
["agent"]
```

生成的记忆库 ID 如下：

```
paperclip::{agentId}
```

注意这里少了什么：

`companyId`。

因此，同一智能体身份无论属于哪家公司，都会使用同一个记忆库。

如果智能体代表一位长期存在的专家，而它的知识应该随其跨越不同公司环境，这种设置可能很有用。

但它也可能划错边界。

如果同一个智能体能够为多个租户工作，那么它在一家公司学到的信息就可能在另一家公司被召回。

这不是配置带来的隐晦后果；`["agent"]` 表达的就是这个意思。

只有在有意让记忆跨公司共享时才使用它。

### 用户记忆：笔记本属于具体的人 {#user-memory-the-notebook-belongs-to-the-person}

在粒度配置中加入 `user`：

```json
["company", "agent", "user"]
```

最终生成的 ID 格式如下：

```
paperclip::{companyId}::{agentId}::user::{userId}
```

这样，记忆不仅按公司和智能体隔开，也会按与工单关联的人隔开。

这里的重点是技术层面的，而非合规层面的：插件会在公司与智能体组成的边界内，为每个已识别的用户创建单独的记忆库。

不要把插件配置中的“有助于满足 GDPR 合规要求”理解为合规保证。记忆库边界可以支持隔离策略，但是否合规取决于系统的其他部分和你的政策。

还有一个值得了解的回退行为，它不太显眼。

如果插件无法识别用户，它会省略用户字段，而不是凭空构造一个身份。此时记忆库会变成：

```
paperclip::{companyId}::{agentId}
```

这就是该智能体所有用户共用的记忆库。

不凭空构造身份是正确的做法。但需要留意其后果：在按用户划分的设置下，来自无法识别用户的工单的记忆不会进入独立记忆库，而会落入共享记忆库。如果你的目标是按用户隔离，请确认工单确实带有身份信息。

### 静态记忆：有意移除动态边界 {#static-memory-deliberately-remove-the-dynamic-boundary}

还有一种选择：

```json
dynamicBankId: false
bankId: "shared-team-bank"
```

在静态模式下，插件会直接返回配置的 `bankId`。

这意味着使用此配置的所有智能体都会读取和写入同一个记忆库。

各种 ID 格式汇总如下：

```
paperclip::{companyId}::{agentId}                  default
paperclip::{companyId}                             company
paperclip::{agentId}                               agent
paperclip::{companyId}::{agentId}::user::{userId}  user
{bankId}                                           static
```

前四种格式由 Paperclip 身份信息派生；最后一种是显式覆盖值。

这个区别很重要。

使用静态记忆库时，你不再让 Paperclip 根据组织结构决定边界，而是直接指定边界的位置。

## 5. 让问题具体化的用户身份细节 {#5-the-user-identity-detail-that-makes-this-concrete}

按用户划分的粒度并不基于随机会话标识符。

插件会检查 Paperclip 工单。

如果工单包含：

```
originId = "slack::alice@acme.com"
```

插件可以提取：

```
alice@acme.com
```

如果 `creatorEmail` 可用，则优先使用它。

否则，插件会按 `::` 拆分 `originId`，从末尾开始扫描各段，并取第一个包含 `@` 的部分。

这意味着，来自 Slack 的工单可以将记忆限定到创建该工单的人。

例如：

```
paperclip::acme::support-agent::user::alice@acme.com
```

Alice 的支持上下文和 Bob 的支持上下文不必进入同一份记忆。

这里有一条值得借鉴的设计经验：

记忆边界的可靠程度取决于用于构造边界的身份信息。

插件有意从工单而不是运行中派生身份。这就是为什么智能体每次开始工作时，运行 ID 不会变成一个新的记忆库。

## 6. 这样做的代价 {#6-what-this-costs-you}

没有一种配置能同时实现完美隔离和完美共享。

共享记忆有一种失败模式。

如果一个智能体记录了错误结论，其他智能体也能获取该结论。共享记忆库可能让错误决定传播得更快。

按智能体隔离记忆则有另一种失败模式。

如果研究员找到了正确答案，而编码员看不到它，系统就会重复劳动。

这两个问题都不是 Hindsight 造成的。

它们是选择记忆边界位置所带来的结果。

因此，真正应该问的不是：

“哪种设置能让我的智能体拥有最好的记忆？”

而是：

“如果智能体 A 学到了一些内容，智能体 B 是否应该能够召回它？”

如果应该，它们就属于边界的同一侧。

如果不应该，它们就不属于同一侧。

无论你是在客户、团队、智能体还是用户之间作出选择，原则都一样。

## 7. 如何选择 {#7-how-to-choose}

你可以在几分钟内作出决定。

先处理最难确定的边界。

**首先，确定租户边界。**

如果两家公司绝不能共享记忆，就在记忆库身份中保留 `company`。不要仅仅因为共享上下文听起来有用，就把它删掉。

**接下来，判断这些智能体是否在协作完成同一项工作。**

如果是，通常值得优先考虑 `["company"]`。它让整家公司共用一个记忆库，同时仍将不同公司隔开。

**如果智能体是彼此独立的专家，就保留默认设置。**

`["company", "agent"]` 为每位专家提供单独的记忆，同时不跨越公司边界。

**只有在有意共享跨公司记忆时，才选择 `["agent"]`。**

移除 `company` 并不是性能优化，而是改变信息边界。

**当人也属于边界的一部分时，加入 `user`。**

如果同一个智能体服务多个人，而这些人的记忆应保持分离，这种设置就很有用。

**如果你想要明确指定共享记忆域，就使用静态 `bankId`。**

这是最明确表达“这些智能体属于同一个团队”的方式。同时，它也最容易在不同租户之间配置错误，因此要审慎确定共享范围。

最后再检查一件事：

六个月后，这个记忆库 ID 是否仍然代表同一件事？

稳定的身份带来稳定的记忆边界。

## 8. 如果遇到异常 {#8-if-something-looks-wrong}

**插件已安装，但 Paperclip 要求授予新能力**

插件声明了 `issues.read` 和 `issue.comments.read`，因为它会在运行开始时获取工单，并检索评论全文。

Paperclip 可能会在首次安装或升级时提示授予这些能力。如果出现提示，这是预期行为，并不表示发生了故障。

**升级插件后，Hindsight API 密钥无法使用了**

打开 Hindsight Memory 设置，并使用 Paperclip 的密钥选择器重新选择 API 密钥。

旧版插件可能保存的是密钥名称。当前主机需要的是密钥引用，因此升级后，旧配置可能会指向错误的表示形式。

**某个智能体似乎始终无法获取记忆**

检查 `enabledAgentIds`。

空列表表示启用所有智能体。一旦列表中包含 ID，只有这些智能体才能在运行开始时获得记忆召回、自动存入评论，以及调用两个供智能体使用的工具。

如果你使用的是 0.4.0，在依赖最后一项功能前先确认版本。在 0.4.0 中，允许列表只应用于三个事件处理程序，而不应用于工具。因此，被排除的智能体不会自动召回或存入记忆，但仍可以自行调用 `hindsight_recall` 和 `hindsight_retain`，操作其身份信息所派生的记忆库。0.4.1 修复了这一点。如果你使用允许列表是为了阻止某个智能体访问记忆，而不仅仅是控制成本，请升级。

这看起来可能像是记忆库问题，实际原因却是启用配置。

**评论没有被存入，也看不出任何故障**

存入记忆时需要有一个可归属的智能体。

如果评论带有自己的智能体信息，插件就使用该智能体；否则，它会回退使用工单的受派智能体。如果工单也没有受派智能体，评论就没有可归属的智能体，因此插件会跳过存入操作，并记录没有可用的智能体归属信息。

所以，未分配智能体的工单中的评论不会被存入记忆。如果你希望讨论内容进入记忆，请先给工单分配智能体。

**将 `autoRetain` 设为 `false` 后，评论不再出现在记忆中**

这是预期行为。

`autoRetain` 控制 `issue.comment.created` 存入处理程序。它不控制那个不执行操作的 `agent.run.finished` 订阅处理程序。

如果你希望已完成的运行输出自动存入记忆，目前发布的工作进程不会通过 `agent.run.finished` 完成这项操作。

**自托管实例上的 Recall 超时**

`requestTimeoutMs` 的默认值为 15,000 毫秒。

插件文档特别指出，当工单描述很长时，自托管实例的召回可能需要更长时间。如果这正是瓶颈，请调高超时值，不要把超时当作记忆库为空的证据。

**你以为两个智能体会共享记忆，结果并没有**

检查实际使用的记忆库边界。

默认设置为：

```json
["company", "agent"]
```

下面两个记忆库彼此不同：

```
paperclip::acme::researcher
paperclip::acme::coder
```

改为：

```json
["company"]
```

两个智能体就会使用同一个记忆库：

```
paperclip::acme
```

共享记忆库意味着记忆边界不同，而不是召回查询不同。

## 9. 常见问题 {#9-faq}

**更改 `bankGranularity` 会迁移已有记忆吗？**

不会。更改粒度会改变插件派生出的记忆库 ID。

例如，从 `["company", "agent"]` 改为 `["company"]`，会将 `paperclip::acme::coder` 改为 `paperclip::acme`。这是两个不同的记忆库，因此已有记忆不会自动在它们之间迁移。

因此，最好在记忆积累很多之前就确定记忆库的划分方式。

**能否让两个智能体共用一个记忆库，同时让第三个智能体保持隔离？**

单靠一个 `bankGranularity` 设置做不到。

该配置在实例级别生效，因此 `["company"]` 会让所有已启用智能体使用公司记忆库。`["company", "agent"]` 则会为所有智能体分别提供公司范围内的记忆库。

`enabledAgentIds` 控制插件会为哪些智能体工作，但不会为不同智能体指定不同的记忆库策略。

如果需要混合拓扑，就必须在这一项全局粒度设置之外进行设计。

**删除智能体后会发生什么？**

智能体消失时，插件不会删除或迁移它的 Hindsight 记忆库。

记忆库 ID 根据智能体 ID 派生，而工作进程没有用于删除相应记忆库的智能体删除处理程序。

因此，删除智能体不等于删除它的记忆。应将记忆库生命周期与 Paperclip 智能体生命周期视为两个独立问题。

**每次运行都会获得一个新的记忆库吗？**

不会。

默认记忆库包含公司和智能体身份，而不包含 Paperclip 运行 ID。

因此，在某家公司中运行该智能体时，会从与其先前运行相同的记忆库中召回内容。

运行 ID 用于临时插件状态，例如缓存的召回结果和用户身份。它不是默认记忆边界的一部分。

**静态 `bankId` 和 `bankGranularity` 可以同时使用吗？**

两者可以同时配置，而且设计上由 `bankId` 优先。派生逻辑会将 `dynamicBankId` 中任何不等于 `true` 的值视为静态覆盖；测试套件也断言，单独设置 `bankId` 会启用静态路径，这是明确的向后兼容保证。

有一项注意事项值得直接处理，无需猜测：插件清单将 `dynamicBankId` 声明为默认值为 `true` 的字段，因此该值到达派生逻辑时究竟是 `undefined` 还是 `true`，取决于主机如何落实模式默认值。不要依赖这一行为，应显式设置该字段：

```json
dynamicBankId: false
bankId: "shared-team-bank"
```

无论主机如何处理默认值，这样设置都没有歧义；插件文档也建议这样配置。若要使用按粒度派生的记忆库，请将 `dynamicBankId` 设为 `true`。

**默认设置是否意味着智能体永远不会共享知识？**

它意味着默认情况下，智能体不会共享 Hindsight 记忆库中的记忆。

Paperclip 仍然提供自己的协作界面：工单、评论、委派和组织结构本身。

这个区别很重要。默认设置不会阻止智能体沟通；它阻止的是一个智能体的 Hindsight 记忆自动成为另一个智能体的 Hindsight 记忆。

**每个多智能体 Paperclip 部署都应该使用共享记忆库吗？**

不应该。

如果智能体在同一个领域协作，并且应当从彼此积累的上下文中获益，共享记忆就很有用。

如果不同租户、团队或专家需要真正独立的记忆，共享记忆就划错了边界。

`bankGranularity` 的目的不是默认开启共享，而是明确划定边界。
