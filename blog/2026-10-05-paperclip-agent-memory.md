![Paperclip 为智能体提供组织结构图；银行粒度决定记忆线的绘制位置](/img/blog/paperclip-agent-memory.webp)

你有两个智能体在同一家公司工作。

有人已经调查了客户集成，找到了反复出现故障的原因，并在问题评论中留下了决定。另一个智能体现在被分配了一个相关的问题。它具有相同的工具、相同的公司背景以及相同的工作。但当它开始时，它并不知道第一个智能体学到了什么。

因此它再次调查相同的故障。

​​现在更改一项设置。

不是为每个智能体提供自己的记忆库，而是为公司提供一个共享的记忆库。第二智能体可以在第一智能体开始之前记住第一智能体的决定。工作复合而不是重新开始。

这听起来像是一个小的配置更改。它不是。

Paperclip 为您的智能体提供组织结构：谁向谁汇报，谁可以接受工作，以及每个负责人可以做什么。 Hindsight 在该结构下添加了另一个边界：智能体可以记住什么。

问题不在于你的智能体是否应该有记忆。问题是记忆边界应该位于哪里。

在Paperclip集成中，`bankGranularity`是回答它的设置。

## 概览 {#tldr}

- **默认为每个公司和每个智能体。**`bankGranularity`默认为`["company", "agent"]`，这为每个Paperclip公司内的每个智能体提供了自己的Hindsight记忆库。
- **默认是一个决定，而不是一个中立的设置。** 它可以防止智能体看到彼此的记忆，但这也意味着一个智能体可以重复另一个智能体已经完成的工作。
- **公司粒度使记忆成为协作表面。**`["company"]`为公司中的每个智能体提供相同的记忆库，同时保持公司独立。
- **​​智能体粒度改变了另一个方向的边界。**`["agent"]`让智能体在公司之间携带记忆，这可能很有用，但具有明显的跨公司影响。
- **选择位于Paperclip的实例级Hindsight插件设置中。** 安装`@vectorize-io/hindsight-paperclip`，然后在设置、插件、Hindsight记忆下进行配置。
- 在多智能体系统中，`bankGranularity`是“一个智能体允许记住另一个智能体的工作是什么”的答案，默认值已经为你解答了。

## 1。 Paperclip已经给了你什么 {#1-what-paperclip-already-gives-you}

Paperclip 将公司建模为智能体组织。

智能体有角色、头衔、汇报关系、权限和预算。在Paperclip自己的描述中，你的智能体有一个老板、一个头衔和一个工作描述，并且授权在组织结构图中上下流动。问题是工作单元，任务可以分配给智能体或个人。

Paperclip 还规定了谁可以做什么。组织结构图有意涵盖人类和智能体。不过，底层的访问控制是分开的：一方面是人类角色和权限，另一方面是智能体API密钥和智能体资格。

还有一个属性对于接下来的一切都很重要。单个Paperclip部署可以托管多个组织，并通过公司范围的访问检查将每个组织的工作、智能体和活动分开。

这为您提供了一个有用的组织模型：

```
                 CEO
                /   \
        Research     Engineering
          /             \
     Researcher       Coder
```

组织结构图告诉您谁为谁工作。

任务系统告诉你每个智能体正在做什么。

权限系统告诉你每个智能体可以做什么。

有一件事这些结构没有回答。

每个智能体可以记住什么？

这就是记忆边界开始重要的地方。

## 2。组织结构图未涵盖的内容 {#2-the-thing-the-org-chart-does-not-cover}

权限控制操作。

记忆支配语境。

这些是相关的，但它们不是同一个边界。

想象一个研究智能体发现特定客户使用不寻常的身份验证流程。智能体将这个决定记录在记忆中。随后，编码智能体收到涉及同一客户的任务。

编码智能体应该能够记忆那个决定吗？

如果答案是肯定的，则两个智能体需要共享的记忆边界。

如果答案是否定的，他们需要单独的记忆。

A Hindsight记忆库就是这样的边界之一。它是记忆召回和记忆存储所针对的孤立的记忆存储。一个记忆库中的记忆不会自动可供智能体从另一个记忆库中调用。

这使得记忆库的选择成为一个架构决策。

​​Paperclip 集成将该决策公开为配置，而不是让您将其构建到每个智能体中。

重要的设置是`bankGranularity`。

默认为：

```json
["company", "agent"]
```

这意味着同一家公司的研究智能体和编码智能体不共享记忆库。

设置正如其所言。它也在为你做决定。

## 3。该插件具体是做什么的 {#3-what-the-plugin-does-concretely}

Hindsight Paperclip 插件安装在 Paperclip 实例级别。当前发布的软件包是`@vectorize-io/hindsight-paperclip` v0.4.1，需要Paperclip 2026.720.0 或更高版本。

安装它：

```bash
pnpm paperclipai plugin install @vectorize-io/hindsight-paperclip
```

然后在设置、插件、Hindsight记忆下进行配置。

你不修改每个智能体。

插件订阅Paperclip生命周期事件并将这些事件连接到Hindsight。

在运行开始时，插件会收到与运行相关的问题。它获取问题，将其标题和描述组合到记忆召回查询中，并在记忆库中搜索该智能体。

结果被缓存以供运行。

在运行过程中，智能体还有两个工具：

```
hindsight_recall(query)
hindsight_retain(content)
```

`hindsight_recall`让智能体执行有针对性的查找。如果查询与运行开始查询相同，则重新使用缓存的结果。比较是修剪后的字符串相等性。不同的查询会触发实时记忆。

`hindsight_retain` 让智能体立即存储重要的事实、决定或结果。

还有一个自动保留路径。

当 `issue.comment.created` 触发时，插件会获取完整的评论正文并保留它。事件负载仅包含 120 个字符的片段，因此插件调用 Paperclip 的注释 API 获取全文。如果该调用失败，它会退回到代码片段，而不是完全丢失注释。

对于智能体撰写的评论，该评论的智能体用于记忆库归属。如果没有智能体归属，则插件将回退给问题的受让人。

因此流程为：

```
Paperclip issue
      │
      ▼
agent.run.started
      │
      ├── fetch issue
      │
      ├── title + description
      │
      ▼
   Hindsight
      │
      ▼
 recall into run state
      │
      ▼
    Agent
      │
      ├── hindsight_recall()
      │
      └── hindsight_retain()
      │
      ▼
issue.comment.created
      │
      ▼
retain full comment
```

有一个细节值得指出，因为命名过去常常指向错误的事件。

`agent.run.finished` 已订阅，但处理程序是无操作的。 Paperclip的运行完成的有效负载不包含智能体的输出，因此插件无法记忆存储事件的输出。

`autoRetain` 控制**评论** 的自动保留。它不会使`agent.run.finished`处理程序记忆存储运行输出。

通过 0.4.0，该设置被标记为“运行完成时自动记忆存储”，并被描述为在运行完成时保留运行输出，但这不是它的作用。 0.4.1 重新标记它。如果您的插件设置仍然显示旧的措辞，则您使用的是 0.4.0。

## 4。组织记忆的四种方法 {#4-four-ways-to-organise-the-memory}

一旦你将记忆库视为记忆边界，`bankGranularity`就变得更容易推理。

不要以配置字符串开头。

从您想要建立的组织开始。

### 默认：每个专家都有自己的笔记本 {#the-default-each-specialist-keeps-its-own-notebook}

```json
["company", "agent"]
```

这会产生：

```
paperclip::{companyId}::{agentId}
```

假设你的公司有三个智能体：

```
Researcher
Coder
Reviewer
```

每个人都有一个单独的记忆库。

研究人员记得其研究。编码员会记住其编码工作。审稿人会记住其审稿意见。

一个智能体自动学习的任何东西都不会成为另一个智能体的记忆。

当智能体具有真正不同的职责或当您尚未确定应该共享什么时，这是最安全的默认设置。

对于协作团队来说这也是一种无形的浪费。

如果研究人员发现了一个重要的事实并将其放入自己的记忆库中，编码员就无法记忆它。编码器必须再次发现相同的事实，或者通过其他显式渠道接收它。

这是关键的权衡。

隔离可以防止不必要的记忆共享。

它还会阻止有用的记忆共享。

### 公司记忆：团队保留一本笔记本 {#company-memory-the-team-keeps-one-notebook}

```json
["company"]
```

这会产生：

```
paperclip::{companyId}
```

现在公司内部的每个智能体都使用相同的记忆库。

研究人员记录一个决定。

编码器可以记忆它。

复习者可以回忆起他们都学到了什么。

当智能体是同一协作团队中的不同角色而不是独立专家时，这是自然的选择。

它还保留了公司边界。 A公司的智能体不会自动记忆B公司的记忆。

对于许多 Paperclip 部署，这是默认值最有趣的替代方案。

组织结构图显示智能体属于一家公司。

记忆库现在同意了。

### 智能体记忆：专家在公司之间携带笔记本 {#agent-memory-the-specialist-carries-its-notebook-between-companies}

```json
["agent"]
```

这会产生：

```
paperclip::{agentId}
```

注意消失的东西。

`companyId`。

因此，无论公司如何，相同的智能体身份都使用相同的记忆库。

​​当智能体代表一位持久的专家，其知识应该在公司环境之间遵循它时，这会很有用。

它也可能是完全错误的边界。

如果同一个智能体可以为多个租户工作，那么在一家公司学到的信息可以在另一家公司中调用。

这并不是配置的微妙结果。这就是`["agent"]`的意思。

仅在有意跨公司记忆时使用它。

### 用户记忆：笔记本属于该人 {#user-memory-the-notebook-belongs-to-the-person}

将`user`添加到粒度：

```json
["company", "agent", "user"]
```

最终的形状是：

```
paperclip::{companyId}::{agentId}::user::{userId}
```

现在，记忆不仅被公司和智能体分开，而且被与问题相关的人分开。

重要的一点是技术而非监管：该插件正在为该公司内的每个已识别用户创建一个单独的记忆库 - 智能体边界。

不要在插件配置中阅读“对 GDPR 合规性有用”作为合规性的保证。记忆库边界可以支持隔离策略，但合规性取决于系统的其余部分和策略。

还有一个值得理解的后备方案，因为它比看起来更安静。

如果插件无法识别用户，它会忽略用户段而不是发明身份。记忆库则变为：

```
paperclip::{companyId}::{agentId}
```

这是该智能体的每个用户共享的记忆库。

不发明身份是正确的选择。结果是需要注意的部分：在用户粒度下，没有可识别用户的问题的记忆不会获得自己独立的记忆库。它落在共享的那一处。如果每用户隔离是重点，请检查您的问题是否确实带有身份。

### 静态记忆：刻意去除动态边界 {#static-memory-deliberately-remove-the-dynamic-boundary}

还有一种选择：

```json
dynamicBankId: false
bankId: "shared-team-bank"
```

静态模式下，直接返回配置的`bankId`。

这意味着使用该配置的每个智能体都会读取和写入相同的记忆库。

完整的形状集是：

```
paperclip::{companyId}::{agentId}                  default
paperclip::{companyId}                             company
paperclip::{agentId}                               agent
paperclip::{companyId}::{agentId}::user::{userId}  user
{bankId}                                           static
```

前四个源自Paperclip恒等式。最后一个是显式覆盖。

这种区别很重要。

有了静态记忆库，你不再要求Paperclip来决定组织的边界。你正在准确地告诉它边界在哪里。

## 5。使这一点具体化的用户身份细节 {#5-the-user-identity-detail-that-makes-this-concrete}

用户粒度不是基于随机会话标识符。

该插件着眼于Paperclip问题。

如果问题有：

```
originId = "slack::alice@acme.com"
```

插件可以提取：

```
alice@acme.com
```

如果`creatorEmail`可用，则优先。

否则，插件会在 `::` 上拆分 `originId` 并从末尾扫描片段，获取第一个包含 `@` 的片段。

这意味着源自 Slack 的问题可以成为创建它的人的记忆。

例如：

```
paperclip::acme::support-agent::user::alice@acme.com
```

Alice 的支持上下文和 Bob 的支持上下文不必成为相同的记忆。

这里有一个有用的设计课程。

记忆边界的好坏取决于构建它的身份。

该插件故意从问题而不是运行中派生出该身份。这就是为什么每次智能体开始工作时，运行ID不会成为新的记忆库。

## 6。这会让你付出什么代价 {#6-what-this-costs-you}

没有任何配置可以同时为您提供完美的隔离和完美的共享。

共享记忆有一个失败模式。

如果一个智能体记录了错误的结论，该结论将可供其他智能体使用。共享的记忆库可以使错误的决定传播得更快。

每个智能体记忆有不同的故障模式。

如果研究人员发现了正确答案而编码员看不到它，系统会重复工作。

这两个问题都不是由Hindsight引起的。

它们是选择记忆边界所在位置的结果。

这就是为什么正确的问题不是：

“哪种设置给我的智能体带来最好的记忆？”

问：

“如果智能体A学到了一些东西，智能体B应该能够记忆它吗？”

如果是，则它们属于边界的同一侧。

如果没有，他们就没有。

无论你是在客户、团队、智能体还是用户之间做出选择，这都是同样的原则。

## 7。如何选择 {#7-how-to-choose}

您可以在几分钟内做出决定。

首先从最难的边界开始。

**首先，确定您的租赁边界。**

如果两家公司绝不能共享记忆，请将`company`保留在记忆库标识中。不要仅仅因为共享上下文听起来有用而将其删除。

**然后询问智能体是否在同一工作主体上进行协作。**

如果这样做，`["company"]`通常是第一个值得考虑的配置。它为公司提供了一个共享的记忆库，同时保持公司独立。

**如果智能体是独立专家，则保持默认。**

`["company", "agent"]` 为每个专家提供自己的记忆，而无需跨越公司边界。

**只有有意跨公司记忆时才选择`["agent"]`。**

删除`company`并不是性能优化。它改变了信息边界。

**添加`user`。**

当同一个智能体为多个人服务并且他们的记忆应该保持不同时，这非常有用。
当您想要显式共享记忆域时，

**使用静态`bankId`。**

这是“这些智能体是一个团队”的最强形式。它也是最容易在租户之间配置错误的一种，因此请慎重考虑共享范围。

还有一项最后检查。

询问六个月后记忆库ID是否仍然具有相同的含义。

稳定的身份造就稳定的记忆边界。

## 8。如果看起来有问题 {#8-if-something-looks-wrong}

**插件已安装，但Paperclip要求新功能**

插件声明`issues.read`和`issue.comments.read`，因为它在运行开始时获取问题并检索完整的评论正文。

Paperclip 可能会在首次安装或升级时提示输入这些信息。如果确实如此，这是预期的，而不是出现问题的迹象。

**您升级了插件，HindsightAPI键停止工作**

打开Hindsight记忆设置并使用Paperclip的秘密选择器再次选择API键。

较旧的插件版本可以保存秘密的名称。当前主机需要一个秘密引用，因此升级可能会使旧配置指向错误的表示。

**一个智能体似乎永远无法记忆**

检查`enabledAgentIds`。

空列表表示所有智能体均已启用。一旦列表包含 ID，只有那些智能体在运行开始时获得记忆召回、注释保留以及两个智能体可调用工具。

如果您使用的是 0.4.0，请在依赖最后一部分之前检查版本。在 0.4.0 中，白名单应用于三个事件处理程序而不是工具，因此被排除的智能体没有自动记忆召回或保留，但仍然可以根据其自身身份派生的记忆库调用 `hindsight_recall` 和 `hindsight_retain` 本身。 0.4.1 关闭了它。如果您使用白名单是为了让智能体远离记忆而不仅仅是为了控制成本，请升级。

这看起来像是记忆库问题，但实际上是一个启用问题。

**一条评论从未被保留，看起来没有任何损坏**

记忆需要一个智能体来归因于记忆。

当有评论自己的智能体时，插件会使用评论自己的智能体，否则会回退到问题分配的智能体。如果问题也没有分配的智能体，则没有任何可归因于记忆的内容，因此插件会跳过记忆存储并记录没有可用的智能体归因。

因此不会存储对未分配问题的评论。如果您希望其讨论能够被记住，请分配该问题。

**您将`autoRetain`设置为 false，并且注释不再出现在记忆中**

这是预料之中的。

`autoRetain` 门控`issue.comment.created` 保留处理程序。它不控制无操作`agent.run.finished`订阅。

如果您希望自动存储已完成的运行输出，则当前发布的工作线程不会从 `agent.run.finished` 执行此操作。

**记忆召回在自托管实例上超时**

默认`requestTimeoutMs`为15,000毫秒。

插件文档特别指出，当问题描述很大时，自托管实例需要更长的记忆召回时间。如果这是您的瓶颈，请增加超时，而不是将超时视为记忆库为空的证据。

**您期望两个智能体共享记忆，但他们没有**

检查实际的记忆库边界。

默认：

```json
["company", "agent"]
```

这些是不同的：

```
paperclip::acme::researcher
paperclip::acme::coder
```

更改为：

```json
["company"]
```

使智能体同时使用：

```
paperclip::acme
```

共享记忆库是不同的记忆边界，而不是不同的记忆召回查询。

## 9。常见问题解答 {#9-faq}

**更改`bankGranularity`是否会迁移现有记忆？**

没有。更改粒度会更改插件派生的记忆库 ID。

例如，从`["company", "agent"]`移动到`["company"]`会将`paperclip::acme::coder`更改为`paperclip::acme`。这些是不同的记忆库，因此现有的记忆不会自动在它们之间移动。

这就是为什么在记忆大量积累之前，记忆库的选择更容易做出。

**两个智能体可以共享一个记忆库，而第三个智能体则保持孤立吗？**

不是通过单个`bankGranularity`设置。

配置是实例级的，因此`["company"]`将公司记忆库应用于所有启用的智能体。 `["company", "agent"]` 为所有智能体提供他们自己的公司范围的记忆库。

`enabledAgentIds` 控制插件作用于哪个智能体。它没有赋予个体智能体不同的记忆库策略。

如果您需要混合拓扑，则需要在此单一全局粒度设置之外进行设计。

**​​智能体被删除后会发生什么？
当智能体消失时，**

插件不会删除或迁移其Hindsight记忆库。

记忆库ID源自智能体ID，并且工作人员没有删除相应记忆库的智能体删除处理程序。

这意味着删除智能体与删除其记忆不是一回事。将记忆库生命周期和Paperclip智能体生命周期视为单独的问题。

**跑步会获得新的记忆库吗？**

没有。

默认记忆库包含公司和智能体身份，而不是Paperclip运行ID。

因此，一次运行会从与该公司中该智能体的先前运行相同的记忆库中进行回忆。

运行ID用于临时插件状态，例如缓存的记忆召回和用户身份。它不是默认的记忆边界。

**静态`bankId`和`bankGranularity`可以一起使用吗？**

您可以同时配置两者，`bankId`旨在获胜。该推导将 `true` 以外的 `dynamicBankId` 的任何值视为静态覆盖，并且测试套件断言单独设置 `bankId` 会激活静态路径，作为显式向后兼容性保证。

有一个警告值得采取行动，而不是推理。插件清单声明 `dynamicBankId`，默认为 `true`，因此该值是否作为 `undefined` 还是 `true` 到达派生取决于主机如何实现架构默认值。不要依赖它。显式设置标志：

```json
dynamicBankId: false
bankId: "shared-team-bank"
```

这在任何一种行为下都是明确的，这就是插件文档告诉您要做的事情。当您想要粒度衍生的记忆库时，请设置`dynamicBankId: true`。

**默认值是否意味着智能体从不共享知识？**

这意味着他们默认不共享Hindsight记忆库记忆。

Paperclip 仍然有自己的协作界面：问题、评论、授权和组织本身。

这种区别很重要。默认情况下不会阻止智能体进行通信。它防止一个智能体的Hindsight记忆自动成为另一个智能体的Hindsight记忆。

**每个多智能体Paperclip部署都应该使用共享记忆库吗？**

没有。

当智能体在同一领域进行协作时，共享记忆非常有用，并且应该从彼此积累的上下文中受益。

当不同的租户、团队或专家需要真正独立的记忆时，这是错误的边界。

`bankGranularity`的要点不是让共享成为默认。就是要明确界限。
