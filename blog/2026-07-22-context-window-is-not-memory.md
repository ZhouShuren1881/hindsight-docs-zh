每当某个实验室推出更大的上下文窗口，同一种说法就会迅速走红：记忆系统已经没用了，把所有内容放进提示词就行。Inkling 和 Gemini 可以在一百万个 token 的上下文中进行推理。Claude Sonnet 的上下文窗口有一百万个 token。Llama 4 Scout 曾宣传支持一千万个 token。照这种说法，现在你可以把完整历史记录粘进窗口，完全不需要记忆层了。

事实并非如此，原因也不是扩大窗口就能解决的限制。上下文窗口不是记忆，而是工作记忆。无论窗口有多大，它都有两个特性，注定无法承担记忆的职责：会话结束时，它会忘掉所有内容；而且在窗口填满之前很久，它使用你提供的信息就已经*开始变差*。

## 上下文窗口是 RAM，不是磁盘 {#a-context-window-is-ram-not-disk}

可以把上下文窗口想成智能体的 RAM。它速度快，是实际推理发生的地方，而且完全易失。请求一结束，其中的内容就消失了。模型并没有“记住”你上周二发送的一百万个 token。每次调用时，它都会从头重新读取你提供的内容。

智能体记忆则像磁盘。它能跨会话持久保存，重启后仍然存在；即使当前没有人在积极思考，知识也存放在那里。把两者混为一谈，正是问题所在。让上下文窗口充当记忆，就像因为买了很多 RAM，便指望 RAM 充当硬盘。内存再大，也不会改变它的用途。

| | 上下文窗口 | 智能体记忆 |
|---|---|---|
| 会话结束后还保留吗？ | 不会，每次调用都会重置 | 会，跨会话持久保存 |
| 内容增多后的质量 | 会下降（上下文退化） | 召回仍然聚焦 |
| 存储原始文本还是知识？ | 原始 token | 整合后的事实和观测 |
| 能消解实体和日期吗？ | 不能 | 能 |
| 能否忘记或更新过时信息？ | 不能 | 能，通过近期性加权和整合实现 |
| 能否供多个智能体和工具共享？ | 不能，只限于一个会话 | 能，一个记忆库，多种使用界面 |

这在实践中有四个方面的含义。

## 1. 它不会持久保存 {#1-it-does-not-persist}

这是最关键的一点。明天开启一个全新会话，窗口就是空的。智能体刚才“知道”的一切都会消失，除非模型之外的某个东西把信息重新放回去。

所以，只要你希望智能体能跨会话记忆，就需要一个位于上下文窗口之外的存储。按定义，这个存储就是记忆系统，无论你是自行托管，还是在 [Hindsight Cloud](https://ui.hindsight.vectorize.io) 上启动托管记忆库。窗口大小对此毫无影响。每个会话都会重置的一千万 token 窗口，能记住的内容和两千 token 的窗口一样多：什么也记不住。

## 2. 窗口填满之前，效果就已退化 {#2-it-rots-long-before-it-fills}

即使在单次会话中，“把所有内容都粘进去”这个办法也会悄然失效，而且现在已有确凿的数据证明这一点。

斯坦福大学和伯克利大学的研究人员早在 2023 年就记录了[迷失在中间](https://arxiv.org/abs/2307.03172)现象：模型善于关注长上下文的开头和结尾，却不善于关注中间部分；相关事实位于中间而非两端时，准确率会下降超过 30%。2025 年，Chroma 发布了一项关于[上下文退化](https://research.trychroma.com/context-rot)的研究，让这一现象有了名称。该研究测试了 18 个前沿模型，发现即使距离已公布的窗口上限还很远，准确率也会下降 30% 到 50%。性能下降也不是平缓的：它会断崖式下跌，有些模型在 32K token 时表现正常，到 64K token 时却会崩溃。

当数据彼此相似时，情况会更糟。如果上下文里的干扰项在语义上与答案相似——把整个项目历史记录一股脑塞进去时，正是如此——准确率就会更快崩溃。所以，把窗口塞满后让模型自行筛选，这种天真的做法不只是成本高，还会让模型更难找到真正重要的信息。

范围更小、相关性更高的上下文，胜过庞大而嘈杂的上下文。这不是权宜之计，而是研究得出的结论。

## 3. 它是原始转储，不是知识 {#3-it-is-a-raw-dump-not-knowledge}

上下文窗口会保存你放进去的任意文本。它不会理解第 3 条消息里的“Ben”和第 300 条消息里的“他”指的是同一个人；不会发现三月份作出的决定在六月份被推翻；也不会把一段冗长的对话转化为持久事实。

记忆系统会在任何内容进入模型之前完成这些处理。它从原始文本中提取事实，消解实体，让“Ben”和“他”归为同一人；为事件标记时间；并把重复提及整合成置信度更高的观测。它还会协调矛盾证据，并通过提高近期且有充分依据的事实的权重，让过时信息逐渐淡出。上下文窗口中的对话记录只是数据；记忆系统产出的是知识。两者的区别，在于记忆系统执行了原始上下文窗口本身永远不会执行的处理。

## 4. 你仍然要决定放入哪些内容 {#4-you-still-have-to-choose-what-goes-in}

“大窗口会让记忆失去意义”这派说法忽略了这一点：即使窗口有一百万个 token，你仍然有预算，而且仍会遇到上下文退化，所以*不可能*把所有内容都放进去。你必须挑出相关的一部分。决定模型在当前这轮交互中应该看到什么，这个选择问题不是枝节，而是记忆的核心工作。

因此，买一个更大的窗口，并不能让你真正摆脱记忆。你只是把选择问题挪到别处，再指望它自行解决。但它不会自行解决。检索会挑出少量合适的事实，只把这些事实注入上下文，从而让上下文保持精简；上下文精简，模型才能保持敏锐。

## 两者互为补充，而非相互竞争 {#the-two-are-complements-not-competitors}

这并不意味着大上下文窗口不好。它们很有用：推理就在其中发生，拥有更大的推理空间确实能带来提升。错误在于把窗口当成*存储*。

正确的架构其实很简单：记忆是持久、经过整合、能跨会话使用的存储；每一轮中，它都会召回少量相关且信号明确的信息，交给上下文窗口进行推理。上下文窗口保持精简，就不会退化。知识能跨会话留存，因为它从一开始就不在窗口里。这样两全其美：模型准确思考当前所需的信息，同时有它历来学到的一切作为后盾。

[Hindsight](https://vectorize.io/hindsight) 这样的系统就是为此而设计的。它从每次交互中[存入](/blog/2026/07/13/inside-retain-agent-memory)事实，将其整合为观测，消解实体和日期，并在召回时返回与当前查询相关的精简事实集，而非完整历史记录。你可以自行运行，也可以在几分钟内免费启用 [Hindsight Cloud](https://ui.hindsight.vectorize.io)。无论采用哪种方式，上下文窗口负责思考，记忆负责决定哪些内容值得思考。

## 判断是否需要记忆的关键问题 {#the-test-that-settles-it}

如果你仍不确定自己需要的是记忆，还是一个更大的窗口，只要问一个问题：**会话结束后，你希望智能体还记得这件事吗？**

如果不需要，上下文窗口就够了。把内容放进提示词，继续处理即可。如果需要，再大的窗口也帮不了你，因为窗口无法跨会话保留内容。你需要的是记忆。界线就在这里，不会因为窗口变大而移动。

1M token 的上下文窗口是很出色的思考空间，却是糟糕的记忆存储空间。两者都交给你的智能体，别再让其中一个承担另一个的职责。
