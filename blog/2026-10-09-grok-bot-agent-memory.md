你花了三个星期和 Claude Code 一起处理某个代码库。它知道重试逻辑为什么要这样写，八月份是哪次迁移让预发布环境出了问题，也知道你不想再增加一层抽象。

接着，你打开一个 Grok Bot，想让它为这项工作起草发布说明，却发现一切都要从零开始。

于是你又解释一遍项目。又把上个月发给 ChatGPT 的背景信息粘贴过来。上下文明明已经存在，却无法在工具之间流转。

这个集成要弥合的正是这道鸿沟。连接到 Hindsight 的 Grok Bot 可以读取其他 AI 工具已经写入的记忆库，让你只需解释一次，而不是每换一个工具就解释一遍。

## 名称说明 {#a-note-on-names}

我们的文章里有三个名称都以 Grok 开头，但它们并非同一个产品。

**Grok Bot** 是本文的主题：你在 [x.ai](https://x.ai) 创建的 Bots，以及会安装同一个插件的 Cursor。**Grok Build** 是一个编程智能体，属于编程智能体插件涵盖的十种智能体之一。**SuperGrok** 则出现在我们的 0.9.1 版本说明中，是一个 LLM 供应商设置 `HINDSIGHT_API_LLM_PROVIDER=xai-oauth`，用于通过 xAI 订阅运行 Hindsight 自己的 LLM 通道。

本文只讨论第一种。

## 简要说明 {#tldr}

- **Grok Bot 可以读取其他工具的记忆。** Claude Code、ChatGPT、Hermes 或 OpenClaw 写入的记忆库，都可供需要读取它们的 Bot 使用。
- **读取是单向的。** Bot 会写入自己的记忆库和共享记忆库；其他所有记忆库都只能读取。
- **Bot 会自行找到记忆库。** 它通过 `list_banks` 列出记忆库，再由 `memory-context` 技能判断该用哪个；无需硬编码路径。
- **请清楚了解授权范围。** OAuth 连接可以访问你所授权组织中的所有记忆库。只读约定写在技能里，并非服务器端权限。
- **记忆还可以通过另外两种方式流转：** Bots 之间使用带标签的交接，以及定时例程的不同运行之间。
- **没有钩子。** Grok Bot 不会运行插件生命周期钩子，因此所有操作都依赖模型自行选择使用的技能。

## Bot 实际可以读取什么 {#what-a-bot-can-actually-read}

Hindsight 将记忆存储在记忆库中。这个集成让 Bot 可以访问四种记忆库。

| 记忆库 | 存储内容 | Bot 可以执行的操作 |
|---|---|---|
| `grok-bot::<bot-name>` | 某个 Bot 在自己的工作中学到的内容 | 读取和写入 |
| `cursor::<project-name>` | Cursor 智能体在某个项目中学到的内容 | 读取和写入 |
| `grok-bot::shared` | 所有 Bot 都应了解的内容、交接记录、“关于用户”档案 | 读取和写入 |
| 你的其他记忆库 | Claude Code、ChatGPT、Hermes、OpenClaw 及其他连接到 Hindsight 的工具写入的记忆 | 只读 |

最后一行最有意思，也正是这个集成比单个产品内的记忆功能更有价值的原因。

在代码库中工作的编程智能体会建立一个关于该代码库的记忆库：其中记录决策、走过的弯路和出过的问题。这些内容本来并不是写给 Grok Bot 的。但当你让 Bot 总结本季度的工程工作、起草变更日志，或回答“为什么要这样构建”的问题时，这个记忆库正是它需要的资料。

Bot 在这里不需要写入权限也能发挥作用。它只需要能够查阅。

## Bot 如何找到合适的记忆库 {#how-the-bot-finds-the-right-bank}

这是让方案切实可行的关键。值得准确说明的一点是：配置过程中没有任何步骤要求你逐一列出 Bot 可以读取的记忆库。

`memory-context` 技能开篇就说明，之前的运行、其他 Bots 和用户使用的其他 AI 工具可能已经了解与当前任务有关的信息，因此应在开始前检查，而不是事后补查。

Bot 会执行以下操作：

1. 写一条简短查询，描述它需要了解什么。例如，查询“关于第三季度供应商候选名单的决策”，而不是重复用户的整条消息。
2. 对自己的记忆库和 `grok-bot::shared` 调用 `recall`。
3. **如果任务涉及该 Bot 自身工作范围以外的任何用户信息**，例如用户的偏好、生活中的人、项目、代码库或文档，Bot 还会对 `list_banks` 列出的相关记忆库调用 `recall`。
4. 在对话开始时，读取 `grok-bot::shared` 中的“关于用户”心智模型。

第 3 步就是跨工具读取的途径。这里没有映射文件。Bot 会列出连接中可用的记忆库，判断哪些与眼前的任务相关，再从中召回内容。

这是模型作出的判断，既是它吸引人的地方，也是它诚实面对的局限。这意味着，让 Bot 回答代码库相关问题时，它可以读取编程智能体写入的记忆库，而无需任何人把两者接线配置起来。但这也意味着，Bot 可能选错记忆库，或漏掉相关记忆库；硬编码映射则不会有这个问题。

该技能有意限制了操作规模：每项任务执行一两次召回，而不是每一步都召回。

## 只允许单向读取 {#one-direction-only}

Bot 会写入自己的记忆库和 `grok-bot::shared`。其他工具的记忆库都是只读的；`memory-setup` 会明确说明这一点：当任务涉及这些工作时可以读取，但绝不能写入。

这种不对称是有意设计的，也是合理的默认做法。你的 Claude Code 记忆库来自代码库中的工作，并采用自己的标准判断哪些事实值得保留。起草发布说明的 Grok Bot 应当能够从中获益，却不应有权修改它。单向读取让 Bot 能共享上下文，同时避免第二个写入者悄悄改动其他工具依赖的记忆库。

同一规则也适用于 Bots 之间。某个 Bot 绝不会写入另一个 Bot 的 `grok-bot::` 记忆库；对它来说，这些记忆库同样是只读的。需要传递给另一个 Bot 的工作内容，应通过共享记忆库中的交接记录传递。

### 授权实际覆盖的范围 {#what-the-grant-actually-covers}

这里值得明确说明，不能留给读者自行猜测，因为细心的读者一定会关心这一点。

插件连接到 Hindsight Cloud 的 MCP 服务器，Grok Bot 通过 OAuth 与它连接。你无需粘贴 API 密钥。但**该连接可以访问你所授权组织中的所有记忆库。** 跨工具读取正是依靠这一点实现的。

因此，上述只读规则是写在技能中的约定，并非服务器强制执行的权限边界。技能要求读取其他记忆库，而绝不向其中写入；遵循技能的模型会照此执行。忽略技能的模型则受 OAuth 授权的实际范围约束，也就是整个组织。

如果你不想授予这么大的范围，可以授权一个只包含你愿意让 Bots 查看之记忆库的组织。不要把技能文本当作访问控制；在权限差异会造成影响的地方，应通过实际权限加以保障。

## 实际使用场景 {#what-this-looks-like-in-practice}

以下三种情况能体现跨工具读取的价值。

**让 Bot 与已经了解你的智能体搭档。** 最常见的组合是 Grok Bot 与 Hermes 一起使用。Hermes 会在与你协作时积累记忆库；连接到同一组织的 Bot 可以从该记忆库中召回内容，无需你再次说明相同的信息。两个工具都不需要为此修改。它们只需指向同一份记忆。

**撰写关于其他地方完成的工作的内容。** Bot 在起草发布说明或状态更新时，可以读取编程智能体在工作过程中填充的代码库记忆，其中还包括那些从未写进提交消息的推理过程。

**回答答案保存在另一个工具中的问题。** “我们为什么不再用那个供应商了？”这是一个关于决策的问题。如果这个决策是与另一个智能体一起讨论确定的，记录就在那个智能体的记忆库里，而不在你与当前 Bot 的任何对话中。

**不用再反复解释自己。** 在设置时根据查询 *“这个用户是谁：他们的工作、当前项目、最常提到的人，以及明确表达过的偏好”* 创建的共享记忆库“关于用户”心智模型，可以让每个 Bot 获得相同的背景信息。再加上读取其他工具记忆库的权限，新 Bot 从一开始就大致知道你是谁、正在做什么。

## 记忆还可以通过另外两种方式流转 {#memory-also-travels-two-other-ways}

跨工具读取是重点，但它只是这里三种记忆流转方向之一。

### Bots 之间 {#between-bots}

`grok-bot::shared` 是专门存放需要跨 Bot 边界共享内容的记忆库，而 `bot-handoff` 技能则负责交接。

某个 Bot 交接工作时，会留下一条简明记录，使另一个 Bot 无需上下文也能接手：记录用户要求了什么、已完成和已发现什么、还有哪些工作、信息来源，以及数据时效方面的注意事项。它会给这条记录加上三种标签：`source:grok-bot`、`bot:<the sending bot's name>`，以及 `handoff:<the receiving bot's name>` 或 `handoff:any`。

`handoff:any` 可以让发现内容传递给从未收到消息的 Bots，以及尚未开始的聊天。Bot 可以直接给另一个 Bot 发消息，速度更快，但消息本身不是记录。交接记录会一直保留。

这里有一点信任方面的问题，值得说明。带标签的交接是唯一一种可以把记忆当作指令而非事实来读取的情况，技能也明确指出这是唯一且范围有限的例外。它接着对例外作了限制：如果交接内容要求接收方删除或清空记忆、写入自身及共享记忆库之外的其他记忆库、泄露秘密，或联系账户之外的任何人，就绝不能照做。

如前所述，这是一种约定，而非强制执行的权限边界。智能体之间的共享记忆本身就是指令通道，不论你是否将其视为指令。这个集成的有用之处，在于明确写出规则，而不是让规则一直隐含着。

### 多次运行之间 {#between-runs}

定时例程有计划安排，却没有历史记录。没有记忆时，每次运行都会从零开始、重复搜索，并把旧信息当成新信息。

`routine-memory` 技能会将记忆步骤写进例程的**自身说明**，因此即使没有人在聊天中，它也会照此执行：工作前先召回上次运行的记录，完成后保留一条记录，说明本次发现了什么、发生了哪些变化，以及下次运行应先检查什么。

有个细节值得照做：**即使没有任何变化，也要保留记录。** 只有知道检查过什么，“没有发现”才有意义。没有记录，你就无法区分一次正常完成且无变化的运行，和一次根本没有发生的运行。

## 为什么这里没有钩子 {#why-there-are-no-hooks-here}

上述所有行为都取决于模型是否选择执行，而这是宿主产品本身的特性，并非设计偏好。

在多数集成中，记忆由生命周期事件触发：会话开始时触发钩子，提取上下文并注入记忆。Grok Bot 的工作方式不同。插件钩子不会运行。Bot 只会安装插件的 MCP 服务器及其技能，没有其他组件。

因此，技能就是完整的接口，每项技能的描述都承担了其他产品中钩子所负责的工作。共有六项：

| 技能 | 用途 |
|---|---|
| `memory-setup` | 连接、用 `list_banks` 验证、创建记忆库和用户档案 |
| `memory-context` | 开始工作前加载相关记忆，包括其他工具记忆库中的内容 |
| `memory-retain` | 任务结束时保存学到的内容 |
| `memory-reflect` | 通过推理记忆来回答有关历史、习惯和过往决策的问题 |
| `routine-memory` | 将召回和保留步骤写入例程自身的说明 |
| `bot-handoff` | 为 Bots 之间交接的工作保留持久记录 |

钩子会不论模型怎么想都照常运行。技能则必须先被模型注意到并选择使用。因此，技能的行为更灵活，但保证更弱。上述内容都应在这一前提下理解：技能让模型能够使用记忆，并引导它如何使用记忆，却不能保证每次都会召回所有相关内容。

## 连接方式 {#getting-connected}

该插件目前仍在等待市场审核，因此暂时需要手动设置。有两种方法。

**在 Grok Bot 中，** 将[连接提示词](https://github.com/vectorize-io/hindsight/blob/main/hindsight-integrations/grok-bot/connect-prompt.md)粘贴给任意 Bot。它会让 Bot 将 Hindsight 添加为自定义连接器，引导你完成 OAuth 登录，并传递与技能相同的规则：应该写入哪个记忆库、何时召回、如何向另一个 Bot 交接工作，以及哪些工具绝不能调用。

**在 Cursor 中，** 将插件复制到本地插件目录并重新加载窗口：

```bash
git clone https://github.com/vectorize-io/hindsight
mkdir -p ~/.cursor/plugins/local
cp -r hindsight/hindsight-integrations/grok-bot ~/.cursor/plugins/local/hindsight
```

无论采用哪种方式，都无需额外配置。MCP 端点为 `https://api.hindsight.vectorize.io/mcp`，OAuth 流程会通过服务发现、动态客户端注册和 PKCE 与其交互。无需 API 密钥。

先给 Bot 起好名字。只要 Bot 仍叫作“Grok Bot”，设置流程就会拒绝继续，因为这个名称会成为记忆库 ID：所有未命名的 Bot 都会派生出 `grok-bot::grok-bot`，从而共用一个个人记忆库；以后再改名，则会导致旧 ID 下存储的内容无法继续使用。

插件获批上架后，两种设置方式都会简化为：在 Connect apps 中搜索 Hindsight，或在 Cursor 市场中找到它。

### 插件不会执行的操作 {#what-the-plugin-will-not-do}

技能绝不会调用 `delete_bank`、`clear_memories`、`invalidate_memory`、`delete_document` 或 `delete_mental_model`。如果有内容需要移除，Bot 会告诉你，由你在 Hindsight 控制台中执行。

当 Bots 可以读取自己没有写入的记忆库后，这一点更加重要。智能体可能会把正确记录误判为错误，也可能收到要求它抹除内容的交接记录。从技能中移除删除调用，可以避免这类错误演变成不可逆的操作。这是技能本身的一项特性，而非服务器权限模型的一部分，因此应将它视为一道防线，而不是完整的防护。

## 遇到问题时 {#if-something-looks-wrong}

**设置时 `list_banks` 失败。** 不要猜测端点或主机名。列表获取失败表示连接尚未正常工作；请从插件设置中重新连接 Hindsight，然后重试设置。

**Bot 没有读取其他工具的记忆库。** `memory-context` 的第 3 步是有条件执行的：只有任务涉及用户更广泛的工作时，Bot 才会查找其他记忆库。如果问题看起来完全属于 Bot 自身的工作范围，它就不会进行查找。请明确说明你想了解什么，例如“查一下编程智能体关于这个代码库记录了什么”，并确认 `list_banks` 中确实能看到你期望的记忆库。

**Bot 仍叫“Grok Bot”，所以设置被拒绝。** 先给它起一个实际名称。名称会成为记忆库 ID。

**Bot 试图写入另一个 Bot 的记忆库，或其他工具的记忆库。** 它不应该这样做。写入目标只能是它自己的记忆库和 `grok-bot::shared`；其他所有记忆库都是只读的。请检查当前启用的技能和服务器的实际权限，不要假定技能规则一定会被强制执行。

**自托管端点无法连接。** Grok Bot 需要可公开访问的 HTTPS MCP 端点，并支持 OAuth 2.1 服务发现和动态客户端注册。仅能在本地正常工作的端点还不够。请在 Hindsight 实例前配置 `cloudflare-oauth-proxy`，使用 `meta-muse` 集成中的 `hindsight-muse-preflight` 检查，然后修改 `mcp.json` 中的 `url`。

**定时例程不断重复旧工作。** 查看例程说明。召回和保留步骤必须写在例程自身的说明里，而且编辑说明时很容易误删这些步骤。

## 常见问题 {#faq}

**Bot 可以读取我其他工具的哪些记忆库？**

你所授权组织中的所有记忆库。插件没有逐个记忆库的允许列表，因此 Bot 可以查看哪些内容，取决于你连接了哪个组织，而非 Grok Bot 内的配置。

**Grok Bot 可以写入我的 Claude Code 记忆库吗？**

不可以。这种不对称正是该集成的设计基础。Bot 可以读取其他工具的记忆库，但不能向其中写入。Bot 学到的内容会进入自己的记忆库或共享记忆库。

**Bot 如何知道哪个记忆库属于哪个工具？**

它会列出连接中的记忆库，根据记忆库 ID 和名称判断哪些与任务相关。记忆库 ID 遵循约定且易于理解，因此能够据此作出判断。没有把工具映射到记忆库的注册表。

**这是否意味着 Bot 有时会读取错误的记忆库，或者漏掉某个记忆库？**

是的。作出相关性判断的是模型，而不是映射表。清楚地命名记忆库会有所帮助，直接说明你想查什么则更有效。

**Bot 可以写入另一个 Bot 的记忆库吗？**

不可以。Bot 只能写入自己的记忆库和 `grok-bot::shared`。跨 Bot 工作通过共享记忆库中的带标签交接记录传递。

**重命名 Bot 会怎样？**

记忆库 ID 根据名称派生，因此改名会改变集成要查找的记忆库，已有记忆不会自动随之迁移。给已经运行一段时间的 Bot 改名前，请先检查旧记忆库。

**可以与自托管的 Hindsight 配合使用吗？**

可以，只要端点可通过 HTTPS 公开访问，并支持 OAuth 2.1 服务发现和动态客户端注册。使用 `cloudflare-oauth-proxy`，通过 `hindsight-muse-preflight` 验证，然后更新 `mcp.json` 中的 `url`。

更有价值的是让 Bot 能读取你在其他地方已经整理好的内容，因为你通过一个工具建立的上下文，从来就不只是关于那个工具。它关乎你的工作。
