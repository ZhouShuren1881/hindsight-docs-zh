Hindsight 0.9.1 在 [0.9.0](/blog/2026/08/07/version-0-9-0) 的基础上，进一步加固了上一版发布的功能，并扩展了可接入的能力：**更快的 Recall（召回）**、新的 **xAI OAuth** 提供方、**可携带知识页的迁移**、更精准的 **Reflect（反思）**，以及一轮大规模可靠性和正确性修复。**自托管部署建议升级**：其中多项修复能够保护数据完整性，并避免后台工作停滞。

- [**更灵活的模型控制**](#more-model-control)：新增 xAI OAuth 提供方；为 LiteLLM 增加强制工具调用式结构化输出；恢复负载均衡后端上的提示缓存；并扩大提供方兼容范围。
- [**可移植的迁移**](#portable-transfers)：支持异步导出文档、迁移时携带知识页，并使记忆库的所有配置字段都支持导出和导入。
- [**更精准的 Reflect**](#a-sharper-reflect)：支持基于当前时间进行推理、在子召回中解析实体名称，并确保综合整理时不会丢失证据。
- [**更快的 Recall**](#faster-recall)：Recall 的读取路径显著提速，返回内容保持不变。
- [**更可靠的运维**](#operate-with-confidence)：新增无需访问数据库的存活探针，严格限定每个记忆库的操作范围，并进行了大规模可靠性和性能改进。

## 更灵活的模型控制 {#more-model-control}

- **xAI OAuth 提供方。** 设置 `HINDSIGHT_API_LLM_PROVIDER=xai-oauth`，即可通过 SuperGrok 订阅运行 Hindsight 的 LLM 通道，并使用 OAuth 身份验证，无需原始 API 密钥。
- **LiteLLM 的强制工具调用式结构化输出。** 某些经 LiteLLM 路由的后端（例如特定地区的 Bedrock）会拒绝通过 `response_format` 方式请求结构化输出。设置 `HINDSIGHT_API_LLM_STRUCTURED_OUTPUT_FORCED_TOOL=true`，即可让这些后端改用强制工具调用，从而在它们不支持响应格式模式时仍能进行结构化提取。
- **恢复负载均衡后端上的提示缓存。** 服务器端提示缓存现已重新支持经过负载均衡的 OpenAI 兼容后端，可降低重复前缀带来的延迟和成本。
- **可配置 Ollama 的思考行为。** Ollama 的原生 `think` 行为现在通过 `extra_body` 控制，因此可以根据模型和配置启用或关闭推理。
- **扩大提供方兼容范围。** 配置了推理强度时，系统现在会显式发送该设置，避免模型静默回退到自己的默认值。针对 Llama.cpp、OpenAI 兼容后端和 Codex 后端，`extra_body` 透传现已修复，提供方特有的选项能够实际传到模型。作为内容发送的内联 `<think>` 文本也会逐字保留，不再被误当作模型自身的推理内容而剥除。

## 可移植的迁移 {#portable-transfers}

本次更新让记忆库在不同实例之间的迁移更加完整。

- **异步导出文档。** 导出大型文档不再通过单个可能占用 API 的阻塞请求完成，而是作为异步操作运行：先启动操作，准备好后再下载。
- **迁移时携带知识页。** 整个记忆库的迁移现在会包含知识页目录树，并在导入时重新生成心智模型搜索状态。因此，迁移后的记忆库不仅包含原始记忆，也保有完整的知识页，并可立即搜索。
- **迁移所有记忆库配置字段。** 记忆库模板的导出和导入现在会往返保存每个配置字段，因此恢复后的记忆库配置与原记忆库完全一致。
- **按记忆库配置存储能力。** 现在可以为每个记忆库单独设置底层存储能力，让同一引擎下的不同记忆库启用不同的存储功能。

## 更精准的 Reflect {#a-sharper-reflect}

- **了解当前时间。** Reflect 现在会收到当前日期和时间，因此“上周”“最近”等说法会根据实际时间解析，不再含糊不清。
- **在子召回中解析实体名称。** Reflect 内部执行的子召回现在会解析实体名称，让推理引用真实且规范的名称，而不是不透明的标识符。
- **综合整理时保留所有证据。** Reflect 被要求进行综合整理时，不再丢弃检索到的证据；系统会拆分处理步骤，确保每条检索到的事实都能进入答案。

## 更快的 Recall {#faster-recall}

Recall 是智能体每轮都会调用的关键路径，因此它的延迟会影响整个系统。0.9.1 在**不改变返回内容**的情况下显著提升了速度：

- **时间提取速度约提升 9 倍。** 推断查询隐含的时间范围（例如“上周”或“2023 年”）过去会占据每次 Recall 中相当一部分时间，现在只占很小一部分。
- **对整个候选集合统一评分。** 观测扩展现在一次性对整个候选集合评分，而不是逐行评分，从而减少大规模 Recall 中的重复工作。
- **避免重复查找实体。** 如果结果已经包含实体 ID，Recall 现在会直接复用，而不是再次查询，从而减少每次查询的往返次数。

## 更可靠的运维 {#operate-with-confidence}

- **无需访问数据库的存活探针。** 数据库变慢不再会导致存活检查失败并重启原本健康的 Pod。存活探针现在可以独立响应，因此数据库故障仍是数据库故障，不会演变成重启风暴。
- **严格限定每个记忆库的操作范围。** 文档更新和删除操作现在都会限定在对应记忆库内，堵住了操作影响其他记忆库中记忆单元的路径。

0.9.1 还包含一轮大规模可靠性和性能修复：对同一文档的并发追加不再丢失追加内容；Retain（存入）不再在写入独立存储期间一直占用数据库连接；Retain 和删除记忆库中的多处死锁已修复；极端的相对日期偏移不再导致 Recall 崩溃。图维护也变得更快、更稳定：过时共现关系的清理，以及删除文本分块时的链接匹配，都从几十秒缩短到几毫秒；实体清理现在由队列驱动，不再扫描整个记忆库。记忆库配置值现在会进行类型验证，错误值不会再卡住后台任务；整合、Recall 和知识页也各自获得了正确性修复。完整列表请参阅[变更日志](/changelog)。
