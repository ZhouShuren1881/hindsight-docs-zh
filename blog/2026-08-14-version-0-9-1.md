Hindsight 0.9.1 建立在 [0.9.0](/blog/2026/08/07/version-0-9-0) 的基础上，强化了已发布的内容并扩展了可插入的内容：**更快的记忆能力**，一个新的 **xAI OAuth
一周后，** 提供程序，**携带知识页面的传输**，更清晰的 **反思**，以及大量的可靠性和正确性修复。 **自我管理部署应该升级** — 多项修复可保护数据完整性并阻止后台工作停滞。

- [**更多模型控制**](#more-model-control)：xAI OAuth 提供程序、LiteLLM 的强制工具结构化输出、在负载平衡后端上恢复提示缓存以及更广泛的提供程序兼容性。
- [**便携式传输**](#portable-transfers)：异步文档导出，携带知识页面的记忆库传输，以及每个记忆库配置字段都可导出+导入。
- [**更敏锐 反思**](#a-sharper-reflect)：当前时间推理、子召回的实体名称解析以及永不丢失证据的合成。
- [**更快的记忆力**](#faster-recall)：记忆召回的读取路径变得更快，而它返回的内容没有改变。
- [**充满信心地操作**](#operate-with-confidence)：无数据库的活性探针，严格的每个记忆库范围，以及大的可靠性和性能通过。

## 更多模型控制 {#more-model-control}

- **xAI OAuth 提供商。** 设置 `HINDSIGHT_API_LLM_PROVIDER=xai-oauth` 在 SuperGrok 订阅上运行 Hindsight 的 LLM 通道，使用 OAuth 而不是原始 API 密钥进行身份验证。
- **LiteLLM的强制工具结构化输出。** 一些LiteLLM路由后端（例如某些区域的基岩）拒绝`response_format`路由到结构化输出。设置 `HINDSIGHT_API_LLM_STRUCTURED_OUTPUT_FORCED_TOOL=true` 将这些后端选择为强制工具调用，因此结构化提取可以在响应格式模式不起作用的情况下起作用。
- **在负载平衡后端上快速恢复缓存。** 服务器端提示缓存现在可以在负载平衡的OpenAI兼容后端上再次运行，从而减少重复前缀的延迟和成本。
- **可配置Ollama思维。** Ollama 上的本机 `think` 行为现在通过 `extra_body` 控制，因此您可以根据模型和设置打开或关闭推理。
- **更广泛的提供商兼容性。** 现在，每当您配置推理工作时，都会显式发送推理工作，因此模型不会默默地回退到其自己的默认值。 `extra_body` 直通对于 Llama.cpp / OpenAI 兼容和 Codex 后端是固定的，因此特定于提供者的选项实际上到达了模型。作为内容发送的内联 `<think>` 文本会逐字保留，而不是像模型自己的推理一样被剥离。

## 便携式传输 {#portable-transfers}

在实例之间移动记忆库在此版本中变得更加完整。

- **异步文档导出。** 大型文档导出不再作为可能占用 API 的单个阻塞请求运行 — 它作为异步操作运行，您启动并在准备好时下载。
- **传输带有知识页面。** 整个记忆库传输现在包括知识页面树并在导入时重新生成心智模型搜索状态，因此记忆库到达时其 wiki 完好无损且可立即搜索 - 而不仅仅是其原始记忆。
- ​​**每个记忆库配置字段都会移动。** 记忆库模板导出/导入现在会往返每个配置字段，因此恢复的记忆库的配置与原始配置完全相同。
- **每记忆库存储功能。** 现在可以为每个记忆库设置记忆库背后的存储功能，因此不同的记忆库可以在同一引擎下启用不同的存储功能。

## 更敏锐 反思 {#a-sharper-reflect}

- **它知道现在是什么时间。** 现在接收当前日期和时间，因此“上周”和“最近”根据实际时钟解析，而不是模棱两可。
- **子召回中的实体名称。** 的内部子回忆现在解析实体名称，因此推理引用真实的、规范的名称而不是不透明的标识符。
- **综合永远不会丢失证据。** 当“估”被强制进行综合时，它不再丢弃检索到的证据——它会分割工作，因此每个检索到的事实仍然可以得出答案。

## 更快的记忆力 {#faster-recall}

记忆召回是热路径——智能体在每个转弯处都会撞击它——所以它的延迟随处可见。 0.9.1 使其速度大大加快 **不改变它返回的内容**：

- **时间提取速度快了约 9 倍。** 计算出查询所暗示的时间窗口（“上周”、“2023 年”）曾经是每个记忆召回的一个有意义的片段；现在是一个小了。
- **按组评分。** 观察扩展是一次性对整个候选集进行评分，而不是逐行评分，从而减少了较大召回的冗余工作。
- **没有冗余的实体查找。** 当结果已经携带其实体 ID 时，记忆召回会重用它们而不是重新获取 - 每个查询的往返次数更少。

## 充满信心地操作 {#operate-with-confidence}

- **无数据库的活性探针。** 缓慢的数据库不再会导致活性检查并重新启动原本健康的 Pod。活性会自行回答，因此数据库事件仍然是数据库事件，而不是变成重启风暴。
- **严格的每个记忆库范围。** 文档更新和删除操作现在属于记忆库的范围，从而关闭了操作可以触及另一个记忆库的记忆单元的路径。

0.9.1 还进行了大量的可靠性和性能修复：并发追加到一个文档不再丢失轮次，记忆存储不再跨单独存储写入保持数据库连接，记忆存储和记忆库删除中的几个死锁消失了，极端的相对日期偏移不再导致记忆召回崩溃。图维护更快、更稳定——过时共现剪枝和块删除链接匹配时间都从几十秒缩短到毫秒，并且实体剪枝现在是队列驱动的，而不是扫描整个记忆库。 记忆库配置值经过类型验证，因此错误的值不会干扰后台任务，并且集成、记忆召回和知识页面各自选择自己的正确性修复。完整列表请参见[变更日志](/changelog)。
