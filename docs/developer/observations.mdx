# 观测：知识整合 {#observations-knowledge-consolidation}

记忆存入后，Hindsight 会自动把相关事实整合成**观测**：记忆库从多条记忆中累积形成、经过去重且有证据依据的认知判断。每条观测都会记录支持证据（包括原文引句）和支持事实数；有新证据时，观测会随之修订，而不是被覆盖。

<Figure doc={observationsFigure} />

---

## 什么是观测？ {#what-are-observations}

观测是由多个事实构成的**整合后知识**。原始事实是单条信息；观测则是以累积证据为依据、经过去重的认知判断、偏好和经验。它们不是 LLM 临时编造的摘要：每条观测都有特定来源记忆作为依据，记录支持事实数，并会随着新证据的支持、反驳或补充而演变。

| 原始事实 | 观测 |
|-----------|--------------|
| “Alice 偏好 Python” | “Alice 是一位专注于 Python 的开发者，重视可读性和简洁性” |
| “Alice 不喜欢冗长的代码” | |
| “Alice 建议使用类型提示” | |

观测带来以下能力：

- **去重**：用一条持久的认知判断取代许多重叠事实
- **建立依据**：每条观测都会引用支持它的具体记忆（及引句）
- **持续演变**：证据增强、减弱或出现矛盾时，观测会相应修订，并保留历史
- **感知更新状态**：较新的记忆尚未整合时，`reflect` 会将受影响的观测视为待更新，并对照原始事实进行核验
- **提高效率**：压缩知识以便更快检索

## 整合如何运作 {#how-consolidation-works}

### 自动后台处理 {#automatic-background-processing}

`retain()` 完成后，整合引擎会自动运行：

1. **分析新事实**——将每条新事实与现有观测进行比较
2. **检测模式**——将相关事实归组并综合生成
3. **创建或更新观测**——创建新观测，或修订现有观测
4. **追踪证据**——每条观测都会维护指向支持事实的引用

### 近似重复项协调处理 {#near-duplicate-reconciliation}

整合过程仍可能产生两条措辞略有不同、含义却相同的观测。例如，能力较弱的模型可能新写一条近似相同的观测，而没有修订现有观测；或者修订某条观测时改变了措辞，导致它与另一条观测重叠。若不处理，这些近似重复项会让召回结果充斥冗余的认知判断。

启用后，Hindsight 会自动协调这些近似重复项。每当创建或更新观测时，系统都会将它与内容最相近的现有观测比较。如果相似度很高，系统会进行一次针对性检查，决定将它们**合并**为一条认知判断（合并双方的支持证据），还是**分别保留**。检查会读取双方的完整文本，因此只要存在有意义的差异——例如数字、否定表达、命名实体或语言不同——就会正确地将观测分开保留，而不会错误合并。

此功能由 [`HINDSIGHT_API_CONSOLIDATION_DEDUP_THRESHOLD`](/developer/configuration#observations) 设置控制：当两条观测的余弦相似度达到或超过此阈值时，系统会协调处理。此功能**默认启用**（`0.97`）；阈值越低，协调越积极；设为 `1.0` 则禁用。协调处理仅在 PostgreSQL 部署中运行；Oracle 部署会跳过此功能，无论阈值为何。

协调处理只会比较**同一标签范围内**的观测。如果每次存入时都用唯一值标记（例如 `session-id`），每个会话就会进入各自独立的范围，彼此不会去重，结果是每个会话都会产生一条近似相同的观测。若要跨越这类易变标签进行整合，请使用 [`observation_scopes: "shared"`](/developer/api/retain#shared) 存入数据。这样观测会被限定在一个全局的无标签认知判断范围内，同时源事实仍保留会话标签，供召回筛选使用。

### 禁用自动整合 {#disabling-auto-consolidation}

设置 `HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION=false`（或通过[记忆库配置 API](/developer/api/memory-banks#observations-configuration)按记忆库配置），即可阻止系统在存入、删除和更新操作后自动运行整合。禁用后，只有显式调用[整合端点](#trigger-consolidation)时才会运行整合。

如果你希望完全掌控整合时机，这会很有用。例如，可以先批量存入多条记忆，再运行整合；也可以只针对特定范围运行整合。

默认情况下，整合会处理记忆库中**所有**尚未整合的记忆。你可以在整合端点中使用 `observation_scopes` 参数，将处理范围限定为特定标签集合：

每个范围都是一个标签列表。如果某条记忆的标签**包含该范围内的所有标签**，这条记忆就匹配该范围。例如，范围 `["user:alice"]` 会匹配带有 `["user:alice", "team:eng"]` 标签的记忆。

### 基于证据的演变 {#evidence-based-evolution}

随着新证据出现，观测会持续演变：

| 事件 | 记忆库学到的内容 | 观测状态 |
|-------|---------------------|----------------|
| **第 1 天** | “Redis 采用 BSD 许可证，且是开源软件” | “Redis 非常适合缓存——速度快、可靠，而且对开源软件友好”（2 条支持事实） |
| **第 2 天** | “Redis 有很好的社区支持” | 观测得到强化（3 条支持事实） |
| **第 30 天** | “Redis 将许可证改为 SSPL” | 观测修订为：“Redis 技术实力强，但用于云服务存在许可证方面的顾虑” |
| **第 45 天** | “Valkey 从 Redis 分叉，并采用 BSD 许可证” | 新观测：“新项目若要求真正的开源软件，可考虑 Valkey” |

### 处理相互矛盾的证据 {#handling-contradictory-evidence}

新事实与现有观测矛盾时会发生什么？

整合引擎不会盲目覆盖，而是通过记录变化过程来**协调处理**矛盾：

**示例：用户偏好发生变化**

| 时间 | 事实 | 观测 |
|------|------|--------------|
| 第 1 周 | “用户说自己很喜欢 React” | “用户偏好用 React 进行前端开发” |
| 第 2 周 | “用户称赞 React 的组件模型” | “用户热衷于 React，尤其喜欢它的组件模型” |
| 第 3 周 | “用户说自己已经转用 Vue，以后不会再用 React” | “用户之前热衷于 React，并欣赏其组件模型；现在已转用 Vue，不再使用 React” |

请注意，最终观测记录了偏好的**完整变化过程**，而不只是“用户偏好 Vue”。这种更细致的理解意味着：

- 智能体不会再向明确表示已经转用 Vue 的用户推荐 React 教程
- 智能体理解*这件事为何重要*（用户以前很喜欢 React，因此这次是经过考虑的选择）
- 有需要时，智能体可以引用这段历史（“我记得你以前使用 React……”）

系统会：

1. **检测冲突**——新事实与现有观测矛盾
2. **保留历史**——将先前的理解纳入新观测
3. **形成细致的观测**——综合生成更丰富的理解，记录发生的变化
4. **更新状态**——将观测标记为最近更新

**示例：纠正错误信息**

| 时间 | 事实 | 观测 |
|------|------|--------------|
| 第 1 天 | “Alice 在 Google 工作” | “Alice 是 Google 的员工” |
| 第 10 天 | “Alice 实际上在 Meta 工作，而不是 Google” | “Alice 在 Meta 工作（先前误以为她在 Google 工作）” |

当某条事实明确纠正先前信息时，系统会更新观测以反映更正，同时记录先前的理解。原始事实始终会保留，因此你可以追溯最初陈述的内容，以及更正发生的时间。

## 更新状态感知 {#freshness-awareness}

观测会追踪其上次更新时间。反思过程中，智能体会考虑观测的更新状态：

- **最新观测**：直接用于推理
- **待更新观测**：智能体会先对照当前事实核验，再决定是否依赖它

这样即使底层数据发生变化，也能确保回答保持准确。

## 观测范围 {#observation-scopes}

默认情况下，观测范围由一条记忆的全部标签组合而成。Retain（存入）参数 `observation_scopes` 可以控制范围：按单个标签、每种标签组合分别生成观测，或使用自定义范围列表。当单条记忆带有多个标签，而你希望每个标签都能独立累积观测时，这项设置尤为关键。

完整说明和选项见 [Retain API 中的 `observation_scopes`](./api/retain#observation_scopes)。

若要查看某个记忆库中已有的范围，请调用 `GET /v1/default/banks/{bank_id}/observations/scopes`。响应会列出每个精确标签集合及其观测数量；空标签列表表示全局范围。列表采用分页方式（`limit` 默认为 100，另有 `offset`）；`total` 表示该记忆库包含的不同范围总数。需要筛选某个精确观测范围、且不匹配带有额外标签的观测时，可将返回的范围作为 `tags`，并设置 `tags_match: "exact"`。若要**仅召回**全局范围——即通过 `observation_scopes: "shared"` 写入的无标签观测——请传入空列表并使用精确匹配：`tags: []`、`tags_match: "exact"`。

## 观测任务说明 {#observations-mission}

你可以设置**观测任务说明**（`observations_mission`），精确定义此记忆库应综合生成什么内容。它会取代内置的持久知识规则，让你控制观测的内容形式。

```
例如：观测是关于人物和项目的稳定事实。
     始终纳入偏好、技能和反复出现的模式。
     忽略一次性事件和短暂状态。
```

留空则使用服务器默认值：经过筛选的持久、具体事实，这些事实会长期保持有效（偏好、技能、关系和反复出现的模式），并排除短暂状态。

**示例：**

| `observations_mission` | 会综合生成的内容 |
|------------------------|----------------------|
| *(未设置——使用默认值)* | 持久事实：偏好、技能、关系和反复出现的模式 |
| *“观测是每周冲刺成果与阻碍的总结”* | 按时间段归组的宽泛事件摘要 |
| *“观测仅记录有关具名人物的稳定事实”* | 以人物为中心、与特定人物相关联的知识 |
| *“观测是客户支持互动中反复出现的模式”* | 故障模式、常见请求和痛点 |

可通过[记忆库配置 API](/developer/api/memory-banks#observations-configuration)或 [`HINDSIGHT_API_OBSERVATIONS_MISSION`](/developer/configuration#observations) 环境变量设置 `observations_mission`。

## 整合策略 {#consolidation-strategies}

任务说明、观测上限和来源事实 token 限制默认适用于记忆库中的每个范围。**整合策略**（`consolidation_strategies`）允许特定范围使用各自的设置。

借助这一功能，一个记忆库就能服务多个受众。假设每条记忆都带有作者、所属团队和公司标签，并以 `observation_scopes: [["user:dana"], ["team:exec"], ["company:acme"]]` 存入。每个范围都会生成自己的观测。但如果所有范围共用一份任务说明，公司范围就会包含与 Dana 个人范围相同的细节——姓名、交易规模以及保密信息——只是可见对象变多了。整合策略可以解决这个问题：

```json
[
  {
    "scopes": [{"tags": ["company:*"]}],
    "observations_mission": "This scope is shared with the whole company. Record only general, industry-level trends. Never name a specific company, person, deal size or funding stage.",
    "max_observations_per_scope": 20
  },
  {
    "scopes": [{"tags": ["team:*"]}],
    "observations_mission": "Record decisions the team must act on."
  }
]
```

这样一来，Dana 的范围会保留“Acme Robotics 签订了为期 3 年的租约，租用一组包含 4,000 个 GPU 的集群”，而公司范围只会记录“各家公司正在租用 GPU 集群来运行开放权重模型”。

策略的匹配方式如下：

- **`scopes`** 是一个备选规则列表。每条规则的格式为 `{"tags": [...], "tags_match": "all" | "exact"}`；其中 `tags` 是 [fnmatch](https://docs.python.org/3/library/fnmatch.html) 模式（`*` 匹配任意文本）。只要某个整合范围匹配任一备选规则，策略就会应用于该范围（OR）；单条规则中的标签则必须全部存在（AND）。
- **`tags_match`** 按规则设置，用于决定是否允许出现其他标签：

  | `tags_match` | `{"tags": ["company:*", "team:*"]}` 会匹配…… | ……但不会匹配 |
  |---|---|---|
  | `"all"` *(默认)* | `{company:acme, team:exec}`、`{user:dana, team:exec, company:acme}` | `{company:acme}`（没有 team） |
  | `"exact"` | 仅 `{company:acme, team:exec}` | `{user:dana, team:exec, company:acme}`（多了 `user:` 标签） |

  由于匹配模式按规则设置，同一策略可以混用不同模式，例如 `[{"tags": ["company:*"], "tags_match": "exact"}, {"tags": ["team:*"]}]`。它会匹配**仅含公司标签**的范围，也会匹配带有团队标签、同时还含其他标签的范围。若要匹配多个标签中的**任意一个**，请为每个标签分别设置规则：`[{"tags": ["company:*"]}, {"tags": ["team:*"]}]`。目前无法表达排除标签的条件（例如“有公司标签但没有用户标签”）。

  :::caution 无标签范围永远无法被策略匹配
  没有任何模式能匹配不带标签的范围，包括单独使用 `["*"]`。这意味着，若记忆库使用
  [`observation_scopes: "shared"`](./api/retain#observation_scopes) 将内容整合到唯一的无标签范围，
  整合策略就无法匹配该范围；它始终会使用记忆库级设置。若需要采用不同任务说明的兜底范围，
  请为它添加一个实际标签并以此为目标，不要依赖 `shared`。
  :::

  请记住，策略匹配的是**观测范围**——即整合时用来归组观测的标签集合，由存入时设置的 [`observation_scopes`](./api/retain#observation_scopes) 决定；策略匹配的不是单条记忆的标签。比如，某条记忆带有用户、团队和公司标签，但存入时使用 `observation_scopes: [["user:dana"], ["team:exec"], ["company:acme"]]`，最终会产生三个仅含单个标签的范围；其中没有一个同时包含公司和团队标签。
- **策略可以设置的项目：**`observations_mission`、`max_observations_per_scope`、`consolidation_source_facts_max_tokens` 和 `consolidation_source_facts_max_tokens_per_observation`。这些设置都可选。
- **策略中未设置的项目，以及任何未匹配到策略的范围**，都会采用记忆库级设置。控制台会将记忆库级设置显示为 **Default（默认）** 策略。

### 两个策略匹配同一范围时 {#when-two-strategies-match-the-same-scope}

**列表中的第一个策略整体生效**。每个范围只会应用一个策略。列表顺序就是优先级顺序，在控制台中对应从左到右排列的标签页。

策略不会混合使用。如果优先策略漏设了某项设置，该设置会采用 **Default（默认）** 值，而不是从后续同样匹配的策略中读取。例如：

```json
[
  {"scopes": [{"tags": ["company:acme"]}], "max_observations_per_scope": 5},
  {"scopes": [{"tags": ["company:*"]}], "observations_mission": "Record only general trends."}
]
```

`company:acme` 范围的观测上限为 5，任务说明则采用**记忆库级设置**，而不是“只记录总体趋势”。第二个策略仍会应用于其他所有 `company:*` 范围。若要让 `company:acme` 同时采用两项设置，请将它们都放在第一个策略中。

要查看某个范围使用哪个策略，请在控制台中打开策略：每条规则都会显示匹配的现有范围数量、被更早策略占用的数量及示例。也可以调用 `POST /v1/default/banks/{bank_id}/consolidation-strategies/preview` 获取相同信息。该端点接收一份待预览的 `strategies` 列表（不会保存），并按策略和规则报告匹配的范围，以及实际处理各范围的策略；计算方式与整合时的匹配逻辑一致。它最多扫描 10,000 个不同范围；超过此数量时，`complete` 为 `false`，所报告的数量只是下限。只有已经包含观测的范围才会出现在预览中。

未设置任何项目的策略会被忽略：它不会匹配任何范围，也不会阻止后续策略生效。

通过控制台或记忆库配置 API 保存格式错误的策略时，系统会拒绝该策略。例如，使用未知键（`"scope"` 而不是 `"scopes"`）、标签列表不是字符串列表，或 `tags_match` 值未知时，都会返回 400 错误，并指出出错的条目。`HINDSIGHT_API_CONSOLIDATION_STRATEGIES` 环境变量不会经过这类校验：格式错误的条目会被静默丢弃，无法识别的 `tags_match` 则回退到 `"all"`，不会报错。若通过环境变量配置策略，请在配置后检查预览，确认每条规则匹配的范围符合预期。未完成的策略也会被接受，因为控制台会随着你的输入保存策略：尚未填写标签的规则或尚未设置任何项目的策略都会被保存，但在你补全之前会被忽略。策略经由[记忆库模板](/developer/api/memory-banks)导出和导入后会保持不变。

每个范围会在单独的 LLM 调用中进行整合，因此一个范围的任务说明不会传入其他范围的调用。

可在控制台（记忆库 **Configuration → Observations**）中设置 `consolidation_strategies`，也可通过[记忆库配置 API](/developer/api/memory-banks#observations-configuration)或 [`HINDSIGHT_API_CONSOLIDATION_STRATEGIES`](/developer/configuration#observations) 环境变量设置。它取代了旧设置 `observation_scope_limits`。旧设置仍可使用，但仅在整合策略之后检查，而且过去只能设置观测上限。

:::note 从 `observation_scope_limits` 迁移规则
这两种字段的匹配方式不同。`observation_scope_limits` 只支持精确覆盖：其模式必须涵盖范围内的每个标签。整合策略的 `tags_match` 默认为 `"all"`，因此允许存在额外标签。直接照搬模式会扩大匹配范围。若要保持旧行为，请添加 `"tags_match": "exact"`。

另外，若某条匹配范围的策略未设置 `max_observations_per_scope`，观测上限会交由 `observation_scope_limits` 设置；即使后续策略匹配该范围并设置了上限，也不会采用后者的值。
:::

## 观测的生命周期与失效 {#observation-lifecycle-invalidation}

### 删除记忆时 {#when-memories-are-deleted}

观测由来源记忆派生而来。来源记忆被删除时，Hindsight 会自动维护观测的一致性：

| 操作 | 对观测的影响 |
|--------|----------------------|
| 删除文档 | 删除由该文档中的记忆派生的所有观测 |
| 按类型删除单条记忆 | 删除来源于这些记忆的观测 |
| 删除整个记忆库 | 删除所有观测及其他全部内容 |

删除后，为受影响观测提供依据的**剩余来源记忆**会重置整合状态；下一次运行整合时，它们会重新整合并生成新的观测。

### 清除特定记忆对应的观测 {#clearing-observations-for-a-specific-memory}

你可以清除由单条记忆派生的所有观测，同时保留该记忆本身。当你希望强制重新综合生成这条记忆对整合后知识的贡献时，这种方式很有用。

请调用 `DELETE /v1/default/banks/{bank_id}/memories/{memory_id}/observations` 端点。此操作会：

1. 删除所有将该记忆列为来源的观测
2. 重置该记忆本身及其他所有为这些观测提供依据的来源记忆上的 `consolidated_at`
3. 触发整合任务，自动生成新的观测

## 触发整合 {#trigger-consolidation}

使用整合端点手动触发整合：

```http
POST /v1/default/banks/{bank_id}/consolidate
Content-Type: application/json

{
  "observation_scopes": [["user:alice"], ["team:engineering"]]
}
```

请求正文为可选项。省略正文或发送空正文时，会处理记忆库中所有尚未整合的记忆。

| 参数 | 类型 | 说明 |
|-----------|------|-------------|
| `observation_scopes` | `list[list[str]]` \| `null` | 可选的标签范围列表。只有标签包含至少一个范围内全部标签的记忆才会被处理。省略此参数则扫描整个记忆库。 |

## 配置 {#configuration}

默认情况下，观测整合会自动运行。你可以通过 [`HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION`](/developer/configuration#observations) 禁用自动整合，并通过[整合端点](#trigger-consolidation)按需触发。可通过[操作 API](./api/operations)监控整合进度。
