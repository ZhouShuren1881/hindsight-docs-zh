# 记忆 {#memories}

**记忆单元**是 Hindsight 提取并存储的原子事实。本页介绍操作单个记忆单元的端点：读取和列出记忆单元、查看派生观测如何演变，以及对记忆单元进行**人工维护**（更正、退役或恢复）。存入和查询记忆的内容分别见 [Retain](./retain.mdx) 和 [Recall](./recall.mdx)。

## 端点 {#endpoints}

| 方法 | 端点 | 用途 |
|---|---|---|
| `GET` | `/v1/default/banks/{bank}/memories/list` | 列出/筛选记忆库中的记忆单元 |
| `GET` | `/v1/default/banks/{bank}/memories/{id}` | 获取单个记忆单元 |
| `GET` | `/v1/default/banks/{bank}/memories/{id}/history` | 获取派生观测的刷新历史 |

| `DELETE` | `/v1/default/banks/{bank}/memories/{id}/observations` | 清除记忆单元的派生观测 |

## 列出记忆单元 {#list-memory-units}

列出记忆库中的记忆单元。响应会包含每个单元的 `fact_type`（`world` | `experience` | `observation`）、`state`（`valid` | `invalidated`）、元数据、实体、发生日期，以及用户编辑过的事实的 `edited_at` 时间戳。默认**包含已标记失效的行**，以便人工维护过程可审计；使用 `state=` 筛选。

使用查询参数缩小结果范围：`type=`（事实类型）、`q=`（在文本和上下文中进行不区分大小写的子字符串筛选；该筛选未建立索引，因此会扫描整个记忆库，适合浏览和检查；生产环境搜索请使用 Recall）、`document_id=`（单个来源文档）和 `entity_id=`（与指定实体关联的记忆单元）。`entity_id` 筛选器会对已存储的实体关联进行精确反向查找，不按文本或语义匹配；因此无需扫描所有记忆，就能列出某个实体的证据（例如使用 `type=observation` 获取其观测）。由于只有有效单元才有实体关联，同时使用 `entity_id` 和 `state=invalidated` 不会返回任何结果。

### 时间范围 {#time-window}

`start_date=` 和 `end_date=` 将结果限制在左闭右开的区间 `[start, end)` 内；`time_field=` 用于选择这两个边界所应用的时间戳：

| `time_field` | 含义 |
|---|---|
| `created_at`（默认） | 记忆被摄取的时间 |
| `updated_at` | 最近一次写入的时间 |
| `mentioned_at` | 提及该事实的时间 |
| `occurred_start` / `occurred_end` | 事实本身发生的时间 |

`time_field` 也会成为排序依据（从新到旧），并且**该列没有值的记忆会被排除**。因此，`total` 只统计具有该时间戳的记忆；即使记忆库并非空库，`total` 也可能为 `0`。省略这三个参数可保留默认列表：先按 `mentioned_at`、再按 `created_at` 排序，且不排除任何记忆。

这种方式会筛除结果；Recall 的 `temporal_window` 则只影响排序。需要完整读取某个时间范围内的记忆，而不是获取最匹配的结果时，请使用这里的筛选。

## 人工维护：编辑、标记失效与清理 {#curation-editing-invalidating--pruning}

记忆在设计上只追加、不覆盖；但有时已存储的事实确实**有误**、处于**待更新**状态，或是**重复项**。人工维护可以更正单条记忆，或将其标记失效，同时保留审计记录。已标记失效的事实会移出有效集合，因此 Recall 永远不会返回它们，但仍可完整恢复。

### 根据情况选择操作 {#when-to-reach-for-what}

并非所有“有问题的记忆”都该用同一种工具。应根据它出问题的*原因*来选择：

| 记忆的情况 | 使用 | 原因 |
|---|---|---|
| **整个记忆库的提取都不正确**（例如主体总是提取错） | 修正记忆库的 `retain_mission` / `observations_mission`，然后对文档**重新处理** | 系统性问题最好从源头修正，再重新处理文档；参见 [Retain](./retain.mdx) 和 [Observations](../observations.mdx)。 |
| **个别事实有误**（单条事实提取错误） | **编辑**记忆 | 更正事实，并重新生成所有基于它派生的内容。 |
| **事实已不再成立，且没有替代事实**（服务器已退役、工具已修复、角色发生变化） | **标记记忆失效** | 处理流程无法知道现实已经改变，因此需要你明确告知。 |
| **事实重复或已被取代** | **标记记忆失效** | 从 Recall 结果中去掉干扰，同时保留审计记录。 |
| **你本来就要存入一个更新的事实来取代它**（例如“喜欢 BMW” → “喜欢 Toyota”） | 直接存入新事实 | 整合过程已会协调同一流中的矛盾，并将其归并为一个观测。 |

经验法则是：**如果 Hindsight 有机会得知，就交给整合处理；如果只有你知道，就进行人工维护。**

只有原始的**世界事实**和**经历事实**可以进行人工维护。观测是*派生内容*，会从其来源重新生成，因此应维护底层事实，而不是观测。对观测执行 `PATCH` 会返回 `400`。

### 编辑记忆 {#edit-a-memory}

更正 LLM 提取的内容。你可以更改**文本**、**上下文**、**发生日期**、**提及时间**（`mentioned_at`）、**事实类型**和**实体**，也就是提取器可能弄错的任何内容。Hindsight 会重新嵌入该事实，移除从旧版本派生的观测和关联，再次执行整合，使下游知识反映这项更正。编辑过的事实会带有 `edited_at` 时间戳（控制台中显示为 **Edited** 徽标）。

更正事实不会丢弃它所参与的**因果关系**：这些关系来自读取原始来源，因此编辑（或先标记失效再恢复）都会保留它们，而不会移除那些无法重新构建的关联。

你无需自行重建任何内容：编辑会在后台**自动重新计算知识图谱和关联**。系统会根据新的文本/实体重新消解事实关联的实体，重新推导时间和语义关联，并重新执行整合；这些操作均由编辑触发。变更提交后，PATCH 会立即返回；知识图谱和观测随后在后台异步重建。

### 消解实体名称 {#resolving-entity-names}

`resolve_entities` 控制如何将 `entities` 中的名称与记忆库里的实体匹配：

| 值 | 行为 |
| --- | --- |
| `true`（默认） | 与 Retain 的行为相同。每个名称都会在记忆库中进行消解，因此某个名称可能根据名称相似度以及它与请求中其他名称共同出现的强度，被归到一个名称相近的现有实体。 |
| `false` | 按名称原样处理。只有名称忽略大小写后完全一致时才会复用现有实体；任何其他名称都会创建新实体，而且同一请求中的名称绝不会彼此合并。 |

**手动更正事实时，请传入 `false`。** 开启消解后，一个与记忆库中现有名称相近的名称可能会匹配到那个名称相近的实体，而不是你指定的实体：例如 `Dr. Waller` 可能被归到名称拼错的 `Dr Wall`，`Alice Smith` 可能被归到 `Alice`。由于编辑仍会正常成功，响应中不容易看出发生了替换。对于从提取结果中得到的名称，消解是合适的，因为拼写可能不同，而记忆库中已有的实体通常就是所指对象；但当你已明确知道目标实体时，消解就不合适。默认值仍为 `true`，以免影响现有调用方。

[Retain](./retain#resolve_entities) 中也有同一标志，可控制如何处理你在那里提供的实体。

### 标记记忆失效（可逆） {#invalidate-a-memory-reversible}

以可恢复的方式将事实标记为失效。已标记失效的记忆会：

- **不再出现在 Recall、整合结果和知识图谱中**；
- **清理其关联**，并在不包含该事实的情况下**重新计算派生观测**（因果关系会暂存起来，恢复记忆时会重新关联）；
- **仍保留在记忆库中**供审计（可通过记忆和文档视图查看）；并且
- 可随时**恢复**。

:::note 文档是事实来源
记忆从文档中提取。编辑或标记记忆失效**不会**更改其来源文档，这是有意为之：文档会作为准确的历史记录保留下来。因此，**重新处理文档会重置对其所产生事实的人工维护状态**（系统会从原始文本重新进行提取）。系统性问题应在任务说明层面修正后重新处理；剩余的个别问题则通过编辑/标记失效来处理。
:::

### 清理流程 {#a-pruning-workflow}

若要清理重复项并减少干扰，请先从 `memories/list` 中找出重复项并分组，然后将它们**标记为失效**。这样 Recall 会立即排除这些内容，同时保留审计记录。
