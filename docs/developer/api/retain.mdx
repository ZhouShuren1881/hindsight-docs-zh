# 摄取数据 {#ingest-data}

将文档、对话和原始内容存入 Hindsight，以便自动提取并创建记忆。

存入内容时，Hindsight 不只是保存原始文本，还会智能分析内容，提取有意义的事实、识别实体，并构建相互关联的知识图谱。这个过程会把非结构化信息转换为结构化、可查询的记忆。

## 参数 {#parameters}

### content {#content}

要存入的原始文本。这是唯一必填字段。Hindsight 会将内容切分为文本分块，把每个分块发送给 LLM 提取事实，并存储得到的结构化事实，而不是原始文本。一个 `content` 值可根据所含信息量生成多条记忆。

### timestamp {#timestamp}

内容所述事件实际发生的时间。接受以下三种形式：

| 值 | 行为 |
|-------|-----------|
| 省略 / `null` | 默认为摄取时的当前时间。 |
| ISO 8601 字符串（例如 `"2024-01-15T10:30:00Z"`） | 使用提供的日期时间。 |
| `"unset"` | 存储内容时**不附带任何时间戳**。适用于参考文档、书籍或虚构内容等没有真实事件时间的永恒性材料。 |

时间戳会注入 LLM 的事实提取提示词，使模型能够解析内容中的相对时间表达。例如，如果内容写着“上周一”，模型会将提供的时间戳作为基准，确定实际日期。传入 `"unset"` 时，提示词会显示 `Event Date: Unknown`，模型因此可以为每条提取事实的 `when` 字段正确返回 `N/A`。提供真实时间戳也能让“去年春天发生了什么？”之类的时间召回查询正常工作。

### context {#context}

简短标签，用于描述来源或情境，例如 `"team meeting"`、`"slack"` 或 `"support ticket"`。它会直接注入 LLM 提示词，因而会实际影响事实提取。同一句话在不同上下文中可能含义迥异：在 `"performance review"`（绩效评估）上下文中说“项目被终止”，与在 `"product roadmap"`（产品路线图）上下文中说这句话，会生成不同的记忆。

持续提供上下文，是提升记忆质量最有效的做法之一。

### metadata {#metadata}

用于补充此输入项上下文的任意字符串键值对。例如：`{"source": "slack", "channel": "engineering", "thread_id": "T123"}`。元数据会包含在事实提取提示词中，LLM 可将其作为额外上下文来提取事实；例如，了解文档标题或来源有助于提高准确性。元数据也会存储在每个记忆单元上，并随每条召回的记忆返回，因此你可以在客户端筛选，或直接补充固定信息，而无需额外查询。例如，可用它将记忆关联回来源 URL、thread ID 或应用特定标识符。

值会以字符串形式存储和返回。值为 `null` 的键会被丢弃，不会存储，因此召回记忆时也不会返回；如果需要保留该键，请发送空字符串。

### document_id {#document_id}

由调用方提供的字符串，用于将一个或多个输入项归入同一逻辑文档。此字段是让 Retain 实现**幂等**的关键。

提供 `document_id` 后，Hindsight 会对文档执行 upsert：如果记忆库中已存在该 ID 的文档，系统会先删除该文档及其所有关联记忆，再处理并插入新内容。这样，你可以安全地对更新后的内容再次调用 Retain，例如新增消息后的聊天线程，而不会累积重复记忆。

省略 `document_id` 时，Hindsight 会分配一个随机 UUID，因此再次摄取相同内容会创建重复记忆。没有 `document_id` 的输入项如何分组，取决于请求中的其他内容：

| 请求 | 结果 |
|---------|--------|
| 所有输入项都没有 `document_id` | 所有输入项进入**同一个**新文档。如果请求太大，无法一次处理（超过 `HINDSIGHT_API_RETAIN_BATCH_TOKENS`），系统会将其拆分为多个部分，每部分各自成为一个文档。 |
| 部分输入项有 `document_id`，其余没有 | 每个缺少 `document_id` 的输入项都会成为**各自独立的**新文档。它绝不会并入其他输入项的文档，因此替换或删除该文档不会影响其他文档。 |
| 多个输入项共用同一个 `document_id` | 这些输入项按请求顺序进入该文档。 |

没有 `document_id` 的附件输入项始终会单独成为一个文档，因此在上表中应视为**有** `document_id` 的输入项。

若要让每个输入项各自独立，请为每项指定不同的 `document_id`。若要将多个输入项放进同一个文档，请为它们指定相同的 `document_id`。

### update_mode {#update_mode}

当你使用已存在的 `document_id` 调用 Retain 时，此参数控制 Hindsight 如何处理现有文档。

| 值 | 行为 |
|-------|-----------|
| `"replace"` *(默认值)* | 删除旧文档及其所有记忆，然后从头处理新内容。这就是上文所述的标准 upsert。 |
| `"append"` | 将新内容拼接到现有文档文本后面，再重新处理合并后的文档。增量 Retain 会自动跳过未变化的文本分块，因此只有新增部分会触发 LLM 提取。 |

追加模式要求提供 `document_id`；没有它就没有可供追加的现有文档。

**何时使用追加模式**：对于逐步增长的内容，例如日志文件、日记或逐条收到新消息的聊天记录，请使用 `"append"`。每次更新时无需重新发送全部历史记录，只需通过 `update_mode: "append"` 发送新增内容，Hindsight 就会将它高效地合并到已有内容中。

```json
{
  "items": [
    {
      "content": "New entry to add to the existing document.",
      "document_id": "my-growing-doc",
      "update_mode": "append"
    }
  ]
}
```

### entities {#entities}

你希望确保得到识别的实体列表，并会与 LLM 自动提取的实体合并。每个条目都有一个 `text` 字段（实体名称）和可选的 `type`（例如 `"PERSON"`、`"ORG"`、`"CONCEPT"`；省略时默认为 `"CONCEPT"`）。

如果你知道某些实体很重要，但 LLM 可能会漏掉它们，或在内容不同部分以不一致的方式提及它们，就可以使用此参数。显式提供实体可确保它们始终关联到知识图谱中。

### resolve_entities {#resolve_entities}

默认情况下，你在 `entities` 中传入的名称会与记忆库中已有的实体进行**消解**：根据名称相似度，以及它与同一输入项中其他名称共同出现的强度，系统可能会将相近名称匹配到已有实体，而不是新建实体。通常这正是你想要的效果；例如，`Dr. Waller` 和 `Dr Waller` 会成为同一个实体，而不是两个。

当你传入的名称具有权威性、必须按原样存储时，请设置 `resolve_entities: false`。之后只有名称忽略大小写后完全匹配时才会复用已有实体；其他名称都会创建新实体，并且你提供的名称彼此不会合并（`Alice` 和 `Alice Smith` 会保留为两个实体）。

这只适用于**你提供的实体**。自动提取的实体始终会进行消解，因为它们是提取器对名称的推测，而非你指定的名称；关闭这类实体的消解会让记忆库充满近似重复实体。

[编辑记忆](./memories#resolving-entity-names)时也有同样的标志；在这种场景中它尤其重要：你手动输入的更正，正是不能让相似的已有实体覆盖它的情况。

### tags 和 document_tags {#tags-and-document_tags}

标签控制**可见性范围**，也就是召回时哪些记忆可见。仅当记忆的标签与召回请求中提供的标签筛选条件有交集时，该记忆才会被返回。因此，当一个记忆库供多个用户或会话共用，且每个用户或会话只能看到自己的记忆时，标签就很有用。

采用一致的命名模式，可使标签筛选更易预测。常见约定包括：用 `user:<id>` 限定用户范围、用 `session:<id>` 隔离会话、用 `room:<id>` 标记聊天室、用 `topic:<name>` 按类别筛选。记忆库还提供一个 list-tags 端点，可返回所有标签及其记忆数量，便于 UI 自动补全或展开通配符。

请参阅 [Recall API](./recall#tags)，了解如何在检索时按标签筛选。

### observation_scopes {#observation_scopes}

控制此记忆在整合时会影响哪些[观测](../observations)。每个范围都会独立执行一轮处理，并创建或更新仅带有该范围标签的观测。

:::info 范围隔离
整合期间，Hindsight 使用 `all_strict` 匹配来查找要更新的已有观测；只有标签与当前范围完全相同的观测才会纳入考虑。这样可以隔离各个范围：在 `["student:alice"]` 下整合的记忆，绝不会渗入标记为 `["student:alice", "teacher:bob"]` 的观测。
:::

以下示例假设存入了一份课程对话记录，其标签为 `tags: ["student:alice", "teacher:bob", "session-id:s1"]`。

#### combined（默认值） {#combined-default}

将所有标签合在一起执行一轮整合。生成的观测会带上完整标签集。

- 创建的观测：`["student:alice", "teacher:bob", "session-id:s1"]`
- ✗ *“Alice 在所有课程中遇到哪些困难？”* — 不匹配，因为从未单独为 `student:alice` 创建观测
- ✗ *“Bob 如何教学？”* — 没有单独匹配 `teacher:bob` 的观测
- ✓ *“Alice 和 Bob 在课程 s1 中发生了什么？”* — 精确匹配

**适用场景**：只有将记忆视为整体才有意义，并且你永远不需要单独查询任何一个标签。

#### shared {#shared}

在单个全局的**无标签**范围内执行一轮整合。记忆自身的标签不会用于观测范围限定（它们仍保留在来源事实中，供召回筛选使用），因此带有*不同*标签的记忆都会整合到**同一个**观测中。

- 创建的观测：一个无标签观测（`[]`）
- ✓ 无标签观测会匹配所有召回请求，无论标签筛选条件是什么
- 消除每次调用所带临时标签的重复：如果每个会话存入时都带有唯一的 `session-id:…` 标签，`combined` 和 `per_tag` 会在每个会话创建一个新观测（标签不会重复），而 `shared` 会将它们全部归入同一个观测。

**适用场景**：标签用于记录每次调用的来源信息（例如会话 ID），你希望用它们筛选召回结果和调试，但不希望它们成为整合边界。此时应将标签留在 `tags` 中，并设置 `observation_scopes: "shared"`。

:::caution `shared`、`[[]]` 与 `[]` 的区别
`shared` 等价于显式指定范围 `[[]]`，也就是包含一个空范围的列表。**不要**将它与 `[]`（空列表）混淆：后者声明了**零个**范围，并会静默回退到 `combined`。
:::

#### per_tag {#per_tag}

对每个单独标签分别执行一轮整合。每个标签都有自己的隔离观测；之后每当有新记忆带有该标签，该观测都会继续累积。

- 创建的观测：`["student:alice"]` · `["teacher:bob"]` · `["session-id:s1"]`
- ✓ *“Alice 在所有课程中遇到哪些困难？”*
- ✓ *“Bob 如何教学？”*
- ✓ *“课程 s1 中发生了什么？”*
- ✗ *“Alice 和 Bob 在一起时表现如何？”* — 没有 `["student:alice", "teacher:bob"]` 组合对应的观测
- ✗ *“Bob 在线上课程中如何教学？”* — 没有 `["teacher:bob", "session-id:s1"]` 对应的观测

**适用场景**：内容涉及多个标签，且每个标签都代表一个独立主题。这是对话、课程或支持会话等多方内容最常用的选项。

#### all_combinations {#all_combinations}

对标签的每个子集分别执行一轮整合，包括单标签、标签对、标签三元组等。3 个标签会产生 7 轮处理。

- 创建的观测：上文所有 `"per_tag"` 范围，以及 `["student:alice", "teacher:bob"]` · `["student:alice", "session-id:s1"]` · `["teacher:bob", "session-id:s1"]` · `["student:alice", "teacher:bob", "session-id:s1"]`
- ✓ 上文 `"per_tag"` 的所有问题
- ✓ *“Alice 和 Bob 在一起时表现如何？”* — 与 `["student:alice", "teacher:bob"]` 匹配

**适用场景**：你需要每种粒度的观测，包括按单个标签、标签对以及标签组划分的观测。

#### custom {#custom}

传入明确的标签集列表。每个内层列表就是一个范围。

```json
[["student:alice"], ["teacher:bob"], ["teacher:bob", "session-id:s1"]]
```

- 创建的观测：恰好是这三个范围，不多不少
- ✓ *“Alice 遇到哪些困难？”*
- ✓ *“Bob 如何教学？”*
- ✓ *“Bob 在课程 s1 中具体如何教学？”*
- ✗ *“不论老师是谁，课程 s1 中发生了什么？”* — 列表中没有单独的 `["session-id:s1"]`

**适用场景**：你清楚哪些组合有意义，并希望避免不必要的处理轮次。

### 响应 {#response}

同步 Retain 响应包含：

- `success` — 操作是否完成且未发生错误
- `bank_id` — 接收内容的记忆库
- `items_count` — 已处理的输入项数量
- `async` — 处理是否异步运行
- `usage` — LLM 调用的 token 用量（`input_tokens`、`output_tokens`、`total_tokens`），仅同步操作会返回此字段

## 文件 {#files}

直接上传文件，Hindsight 会将其转换为文本并自动提取记忆。文件处理始终以异步方式运行，并返回操作 ID 供跟踪进度。

**支持的格式：** PDF、DOCX、DOC、PPTX、PPT、XLSX、XLS、图像（JPG、PNG、GIF 等；OCR 支持情况取决于配置的解析器）、音频（MP3、WAV、FLAC 等；支持转录）、HTML 和纯文本格式（TXT、MD、CSV、JSON、YAML 等）

### 使用 `operation_id` 安全重试 {#safe-retries-with-operation_id}

如果异步 Retain 的响应丢失或超时，你无法判断操作是否已创建。盲目重试可能会将同一任务重复加入队列，导致重复提取、重复生成嵌入，并增加供应商费用。

自行提供一个 `operation_id`（任意 UUID），即可安全重试：

```json
{
  "items": [{ "content": "Alice works at Google", "document_id": "conv_123" }],
  "async": true,
  "operation_id": "3f2b8c1a-9d4e-4a7b-9c2f-1e6d5a4b3c2d"
}
```

- 使用相同的 `operation_id` 重新提交时，会返回原操作且不会创建新任务，因此确认响应丢失后的重试不会产生其他效果。
- 如果某个 `operation_id` 已属于另一项操作，重复使用它会返回 HTTP `409`。
- 省略 `operation_id` 时，保持默认行为：每个请求都会创建一项新操作。
- 在发送请求**之前**生成 ID，并在重试时重复使用。同步 Retain 会忽略 `operation_id`；此外，请求中的所有输入项必须归入同一种策略。

### 使用供应商 Batch API 降低 50% 成本 {#cut-costs-50-with-provider-batch-apis}

使用异步 Retain 时，启用供应商 Batch API，可将 LLM 事实提取成本降低 50%。OpenAI、Groq 和 Gemini 均提供这项折扣，代价是处理窗口最长可达 24 小时；由于 Retain 本来就在后台运行，这种取舍通常不会显现出来。

```bash
export HINDSIGHT_API_RETAIN_BATCH_ENABLED=true
```

Hindsight 会将事实提取调用作为批处理任务提交给供应商，轮询任务完成状态，并自动处理结果。你无需更改 API 调用。

:::note
要享受 Batch API 的成本节省，Retain 请求必须设置 `async=true`，且使用兼容的供应商（OpenAI、Groq 或 Gemini）。
:::
