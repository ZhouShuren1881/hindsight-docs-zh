## 什么是心智模型？ {#what-are-mental-models}

心智模型是你为记忆库维护的**已保存的 Reflect 回答**。创建心智模型时，Hindsight 会使用你的来源查询执行 Reflect（反思），并保存结果。以后调用 Reflect 时，系统会优先检查这些预先生成的摘要，从而更快地提供更一致的答案。

<Figure doc={mentalModelsApi} />

### 为什么使用心智模型？ {#why-use-mental-models}

| 优点 | 说明 |
|---------|-------------|
| **一致性** | 对常见问题，每次都提供相同的答案 |
| **速度** | 立即返回预先生成的回答 |
| **质量** | 由你审核并人工维护的摘要 |
| **控制** | 明确定义关键主题应如何回答 |

### 分层检索 {#hierarchical-retrieval}

执行 Reflect 时，智能体按以下优先级检查来源：

1. **心智模型**——用户维护的摘要，优先级最高
2. **观测**——整合后的知识
3. **原始事实**——作为核验依据的记忆

心智模型代表你明确维护的知识，因此会被优先检查。

## 自动刷新 {#automatic-refresh}

可以配置心智模型，使其在观测更新时**自动刷新**，无需人工干预即可与最新知识保持同步。

### 触发器设置 {#trigger-settings}

| 设置 | 类型 | 默认值 | 说明 |
|---------|------|---------|-------------|
| `mode` | `"full"` \| `"delta"` | `"full"` | 刷新策略。参阅下文[刷新模式](#refresh-mode)。 |
| `refresh_after_consolidation` | bool | false | 观测整合后自动刷新 |
| `refresh_cron` | string \| null | null | 定时刷新的 UTC 五字段 cron 表达式，例如 `"0 3 * * *"` 表示每天 UTC 03:00 |
| `min_refresh_interval_seconds` | int \| null | null | 此模型两次*自动*刷新之间的最小秒数。参阅下文[限制自动刷新频率](#rate-limiting-automatic-refreshes)。`null` 使用记忆库级或全局默认值。 |
| `tags_match` | string \| null | null | 刷新时模型的 `tags` 如何筛选来源记忆：`any`、`all`、`any_strict`、`all_strict` 或 `exact`。设为 `null` 时，**有标签**的模型默认采用 `all_strict`，即记忆必须携带模型的每一个标签。设为 `"any"` 可匹配携带*任一*标签的记忆，参阅[标签与可见范围](#tags-and-visibility)。 |
| `tag_groups` | list \| null | null | 高级布尔标签表达式，完全覆盖扁平的 `tags`/`tags_match` 条件。参阅 [Recall 标签参考](./recall#tags)。 |
| `fact_types` | list \| null | null | 限制刷新读取的事实类型，可选 `world`、`experience`、`observation`。`null` 表示全部三种类型。不能使用空列表。 |
| `exclude_mental_models` | bool | false | 刷新时隐藏*所有*其他心智模型，使此模型绝不基于其他模型综合生成内容。 |
| `exclude_mental_model_ids` | list \| null | null | 按 ID 在刷新时隐藏指定心智模型。被刷新的模型自身始终被排除。 |
| `include_chunks` | bool \| null | null | 覆盖刷新内部 Recall 是否返回原始文本分块。`null` 使用记忆库级或全局的 `recall_include_chunks` 默认值。 |
| `recall_max_tokens` | int \| null | null | 覆盖刷新时检索事实的 token 预算。`null` 使用记忆库级或全局默认值。 |
| `recall_chunks_max_tokens` | int \| null | null | 覆盖刷新时检索原始文本分块的 token 预算。`null` 使用记忆库级或全局默认值。 |
| `reflect_search_observations_max_tokens` | int \| null | null | 覆盖刷新中 `search_observations` 调用的 token 预算。较小的预算会丢弃排名最低的观测，并缩小 Reflect 的上下文。`null` 使用随系统提供的 5000。刷新不读取记忆库的 `reflect_default_options`。 |
| `reflect_search_observations_include_entities` | bool \| null | null | 覆盖 `search_observations` 是否附带消解后的实体名称；这些名称可能占工具载荷的一半以上。`null` 表示启用。刷新不读取记忆库的 `reflect_default_options`。 |
| `budget` | string \| null | null | 刷新可使用的智能体步骤数，以服务器 `reflect_max_iterations` 为基准：`low` 减半，`mid` 保持不变，`high` 加倍。`null` 表示 `mid`；刷新会写出整篇文档，因此不继承临时 Reflect 调用默认采用的 `low`。 |
| `response_schema` | object \| null | null | 结构化输出的 JSON 模式。设置后，每次刷新都会在 Markdown 内容之外保存 `structured_output`。参阅下文[结构化输出](#structured-output)。 |
| `keep_trace` | bool | false | 在 `reflect_response.trace` 中记录每次刷新如何得到结果。参阅[排查刷新问题](#troubleshoot-a-refresh)。 |

启用 `refresh_after_consolidation` 后，每次记忆库的观测完成整合，心智模型都会重新生成，以反映最新综合生成的知识。

设置 `refresh_cron` 后，Hindsight 会在服务器的心智模型刷新检查周期中检查计划，只有模型范围内的记忆自上次刷新以来发生变化时才刷新。`refresh_cron` 与 `refresh_after_consolidation` 互斥：模型要么在整合后刷新，要么按固定 UTC 时间计划刷新，不能同时采用两者。

模型上的 `last_refresh_failed_at`（知识树中的页面也有此字段）记录刷新失败的时间，因此列表视图无需逐个读取历史记录，就能显示哪些模型已停止自动刷新。

**刷新失败会暂停自动刷新。** 工作进程会重试失败的刷新，次数由 `HINDSIGHT_API_WORKER_MAX_RETRIES` 控制，默认 3 次，之后停止。在一次刷新成功之前，`refresh_after_consolidation` 和 `refresh_cron` 都不会再次将该模型入队。因此，无法成功的刷新——例如提示词超出模型容量、账户余额耗尽或增量编辑无法应用——只消耗几次尝试的成本，而不会在每个检查周期都产生 LLM 费用。失败会显示在模型的[历史记录](#history)中。修复原因后，请手动刷新模型；成功刷新会恢复自动刷新。`HINDSIGHT_API_REFLECT_WALL_TIMEOUT` 像限制 Reflect 一样限制整个刷新的运行时间，因该限制被中断的刷新也算失败。

### 限制自动刷新频率 {#rate-limiting-automatic-refreshes}

一次刷新就是一次完整的 Reflect 执行，包含检索和智能体 LLM 循环。在持续摄取内容的记忆库上启用 `refresh_after_consolidation` 后，每次小规模存入都可能导致重建其涉及范围内的每个模型，并产生费用。频繁写入的记忆库即便只有少数几个模型，成本也会迅速累积。

`min_refresh_interval_seconds` 为两次自动刷新设置最小间隔：

```json
{
  "trigger": {
    "refresh_after_consolidation": true,
    "min_refresh_interval_seconds": 1800
  }
}
```

间隔内触发的刷新**不会被丢弃**。它会入队并等待间隔结束；期间后续触发都会合并到同一个待执行刷新。因此，连续 20 次存入只产生一次刷新费用，而这次刷新仍会读取这 20 次存入添加的全部内容。唯一的取舍是即时性：模型内容相对其记忆的滞后最多可达到这个间隔。

此间隔限制适用于两种自动触发器：`refresh_after_consolidation` 和 `refresh_cron`。它绝不限制你主动请求的刷新；刷新端点、MCP 工具和控制台的刷新按钮都会立即执行，并解除已有等待刷新的暂停状态。

可以通过 `mental_model_min_refresh_interval_seconds` 在记忆库级设置，或通过 `HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS` 在服务器全局设置。两者与模型级设置同时存在时，模型级值优先。因此，`min_refresh_interval_seconds: 0` 可以让必须及时更新的某个模型不受库级间隔限制。所有层级的默认值均为 `0`，即不设置最小间隔。

刷新等待期间，其操作保持 `pending`，`next_retry_at` 设为间隔结束时刻，因此 `GET /operations` 会明确显示它正在等待什么。

### 结构化输出 {#structured-output}

心智模型的内容始终是 Markdown。设置 `trigger.response_schema` 可*另外*附带机器可读的表示：该值必须是 [JSON 模式（JSON Schema）](https://json-schema.org/)中的 **object**，具有非空 `properties` 映射，支持嵌套对象和数组。随后每次刷新都会在模型的 `reflect_response` 中，将 `structured_output` 与 Markdown 一并保存；你会同时得到文字内容和具有明确类型的对象。

```json
{
  "trigger": {
    "response_schema": {
      "type": "object",
      "properties": {
        "risk_level": { "type": "string" },
        "open_questions": { "type": "array", "items": { "type": "string" } }
      },
      "required": ["risk_level"]
    }
  }
}
```

关键行为：

- **从最终文档提取。** 结构化输出从实际保存的内容中解析，因此在 `delta` 模式下，它反映整个合并后的文档，而不仅是本次刷新中发生变化的事实。
- **失败会明确报告。** 配置了 `response_schema`，但无法生成结构化表示时，刷新会**失败**，不会悄悄保存缺少结构化表示的内容。模型原有的内容和 `structured_output` 会保留，并可重试刷新。
- **请求时拒绝无效模式。** 模式必须是至少具有一个属性的对象，每个属性的 `type` 必须是 `string`、`number`、`integer`、`boolean`、`array` 或 `object`。

相同模式在 `reflect` 端点上的用法，参阅 [Reflect → `response_schema`](./reflect#response_schema)。`structured_output` 的值位于模型的 `reflect_response` 中，参阅[响应字段](#response-fields)。

### 待更新状态判定 {#staleness-gating}

两种自动触发器都会在调用 LLM 之前执行相同检查：**此模型解析后的范围内，是否有比上次刷新所读取的记忆更新的记忆？** 模型的 `tags`/`tags_match`、`tag_groups` 和 `fact_types` 均参与检查，因此记忆库其他范围内的活动不会触发重建，范围未发生变化时的 cron 检查也会完全跳过刷新。仍在等待整合的记忆也计入，因为它们已经存储；范围包含这些记忆的模型会被视为待更新。

**无标签写入绝不会让有标签的模型变为待更新。** 使用 `tags_match: "any"` 或 `"all"` 时，刷新也会*读取*无标签记忆，但待更新状态只计算携带模型标签的写入。否则，在同时进行有标签和无标签写入的记忆库上，这类模型几乎每次写入后都会被判为待更新（#4857）。使用这些模式的 `tag_groups` 叶子条件也遵循相同规则；明确选择无标签记忆的条件组，例如标签为空的 `exact` 叶子条件或 `not`，仍会计入无标签写入。没有标签的模型以整个记忆库为范围，所以任何写入都会将其标记为待更新。

所有可读取的 `is_stale` 都按相同规则计算，包括单个心智模型读取结果中的标志、列表中的标志、Reflect 智能体看到的标志，以及[知识库树](./knowledge-pages)中每个页面的标志。模型被标记为待更新，意味着刷新确实会重写它。

列出模型无需为每个模型单独查询，系统会一次处理整页结果，因此你无需近似判断。如果已经从记忆库统计端点获得 `last_memory_write_at`，那么 `last_memory_seen_at` 等于或晚于该时间的模型可以确定是最新的，无需再查询：记忆库没有任何变化，该模型范围内自然也没有变化。

**删除不会被这项检查察觉。** 待更新状态检查的是，自模型上次读取记忆以来，范围内是否有内容被*写入*。删除范围内的记忆不会留下写入，所以不会触发该标志。引用已删除事实的文档仍会报告自身为最新，直到其范围内有新的写入，或你手动刷新它。

**两个时间戳回答不同的问题。** `last_refreshed_at` 是实际时间，表示上次刷新结束的时刻。每次刷新完成都会推进它，包括读取范围后发现没有新内容、保持文档不变的刷新。因此，自行驱动刷新的客户端可以用它区分“这一轮已执行”和“这一轮仍需调用”。`last_memory_seen_at` 是数据中的位置，表示上次刷新实际看到的范围内最新记忆。在范围没有变化时，无论刷新多少次，它都保持不变，因此适合作为待更新状态比较的一方。较新的 `last_refreshed_at` 与较旧的 `last_memory_seen_at` 并不矛盾，意味着你刷新了一篇没有新内容可写的文档。

### 刷新会读取什么 {#what-a-refresh-reads}

- **某个时点的快照。** 每次刷新都以数据库时间确定截止点，只读取在该时刻或之前提交的记忆，因此刷新期间的写入绝不会只被纳入一部分。刷新后记录的水位是本次实际看到的范围内最新记忆，而非 `now()`；快照之后刚提交的写入仍然比水位更新，会在下一轮处理，不会被跳过。
- **`delta` 模式只读取新内容。** 增量刷新将检索范围限定为上次刷新以来创建的记忆，因此 LLM 读取的是新信息，无需重新读取整个记忆库。
- **依据持续累积。** 即便使用增量模式，`reflect_response.based_on` 也会累积：本次刷新的事实与此前所有刷新依赖的事实合并，并按 ID 去重。文档建立在全部这些事实之上，而不仅是最新一批。
- **没有相关内容时不修改。** 刷新没有找到与主题相关的记忆时，会保持内容不变，只推进水位，避免同一个空窗口反复触发刷新。
- **没有内容可读时完全不调用 LLM。** 智能体循环开始前，刷新会按模型自己的设置检查是否有可读取内容：即在其将读取的窗口内，是否有范围内的记忆（`tags`/`tags_match`、`tag_groups`、`fact_types` 都会收窄范围）；`full` 模式读取整个记忆库，`delta` 模式读取 `last_memory_seen_at` 之后的内容。除非 `exclude_mental_models` 禁止使用其他心智模型，否则其他模型也属于可读取内容。没有任何内容时，刷新立即完成，文档保持不变，不产生费用。这常见于刚创建的记忆库：页面在创建后立即刷新，此时尚未存入任何内容。
- **检索失败不等于没有结果。** 检索步骤抛出异常，例如数据库、嵌入模型或重排序模型不可用时，刷新会**失败**，不会把模型在没有检索结果时自行生成的内容写入。内容、`structured_output` 和水位均保持不变，重试会再次读取同一窗口。这里必须区分：“已查找，但没有这个主题的内容”是可写入的答案；“无法查找”是失败，应保留原内容。若不区分，检索器故障就可能悄悄将积累数月的文档替换为泛泛的“我没有这方面的信息”。

### 刷新模式 {#refresh-mode}

刷新生成新内容时有两种策略：

- **`full`**（*默认*）——每次刷新都从头重新生成全部内容，行为简单且可预测：LLM 根据检索到的记忆综合生成一篇新文档。适合短文档、希望每次刷新都可能重组输出，或尚未确定最终文档结构的情况。

- **`delta`**——刷新针对文档的现有结构输出一系列带类型的*操作*，例如添加章节、追加列表项、替换内容块、移除待更新的段落，然后渲染结果。任何操作都未涉及的章节会按**完全相同的字节**保留，不改写措辞、空白或列表样式。适合长期维护的操作规程类心智模型：希望多次刷新之间保持稳定，只修改确实发生变化的部分。

#### 增量模式的工作方式 {#how-delta-mode-works}

Hindsight 为文档维护一份具有权威性的**结构化**表示：有序的章节列表，每章包含一组内容块。每个内容块是按原样存储的一个 Markdown 片段，可以是段落、列表、表格或代码围栏。你读取的 Markdown 是该结构的确定性渲染结果。内容块不会被重新解释，因此刷新未触及的格式也无法被重写，表格仍然是表格。增量刷新绝不会要求 LLM 重写文档，而是要求它输出针对该结构的操作：

| 操作 | 效果 |
|---|---|
| `add_section` / `remove_section` | 添加或移除整个章节 |
| `rename_section` | 修改章节标题 |
| `replace_section_blocks` | 整体替换章节内容 |
| `append_block` / `insert_block` | 在章节末尾或指定内容块之后添加内容块 |
| `replace_block` / `remove_block` | 修改或移除一个内容块 |

没有被任何操作提及的内容会原样保留；不变的文字不会重新生成后再检查。这一点很重要，因为“保留未变内容”对 LLM 而言只是一项软约束。根据输入的整体印象生成下一个 token 才是其固有行为，所以即便要求保留原文，多次刷新后措辞也会逐渐偏移。

章节和内容块通过 ID 定位，绝不通过位置定位，因此操作不会因数错位置而落到错误对象上。失败处理有意采取保守策略：操作引用不存在的章节或内容块，或内容块位于所指定章节之外时，该操作会被**丢弃**，不会猜测其目标，其他操作仍会应用。如果*所有*操作都指向不存在的对象，系统会向模型展示它用错的 ID 和文档实际具有的章节，再请求一次。刷新会记录被丢弃的操作及原因，便于你发现本轮哪些新信息未能写入文档。

增量模式在两种情况下会自动回退到完整重建：
1. 心智模型尚无既有内容，没有可供编辑定位的基线。
2. `source_query` 自上次刷新以来已改变，主题发生了变化，现有结构可能不再适用。

**增量刷新绝不会用不完整的文档替换原文档。** 增量检索只读取上次刷新之后的新记忆，所以基于该窗口写出的答案只覆盖主题最近的一部分，可用于编辑文档，不能直接替换文档。因此，完全无法进行编辑时——例如服务提供方调用失败、响应无法读取，或每个操作都被拒绝——既有内容会保持原样，刷新会**失败**，不会算作完成。内容不会丢失，刷新的时间窗口不会推进，重试会再次看到同一批记忆。空答案也遵循相同规则：有内容的文档绝不被空文档覆盖。增量刷新绝不会在你不知情时改为全文重写；如果模型的增量刷新持续失败，请将其 `mode` 切换为 `full`。

| 使用场景 | 建议模式 | 原因 |
|----------|-----------------|-----|
| 技能或操作规程文档 | `delta` | 章节会经历多次刷新，只有特定规则改变 |
| 入职摘要 | `delta` | 添加团队成员不应重组文档 |
| 实时仪表板 | `full` | 每次刷新都是一份新快照 |
| 简短 FAQ 摘要 | `full` | 全文重新生成成本低，行为明确 |

### 详细程度 {#detail-levels}

**列表**和**获取**端点都接受可选的 `detail` 查询参数，用于控制返回的数据量。这可以缩小响应，尤其适合上下文预算有限的智能体启动流程或 MCP 客户端。

以下情况适合刷新：
- 存入了影响该主题的新记忆
- 观测已更新

**刷新会合并。** 同一个模型同一时刻最多有一个等待执行的刷新。如果已有刷新入队但尚未开始，此调用会返回*该*操作，而不会再加入第二个相同刷新；待执行刷新会读取运行时的模型状态，因此已涵盖你刚提出的请求。照常轮询返回的 `operation_id` 即可。已经*运行*的刷新不会被复用，因为它可能在你最新修改之前就读取了模型；此时会在其后加入新操作。

**刷新也会逐个执行。** 同一模型的刷新绝不会重叠：排在正在运行的刷新之后的操作，要等前者完成才开始。因此，模型一次只由一个刷新写入，不会由恰巧最后结束的刷新决定内容。这是模型级限制；不同模型仍可并行刷新，并行数取决于记忆库可用的工作进程数。

## 排查刷新问题 {#troubleshoot-a-refresh}

如果刷新后的文档不符合预期，例如没有变化、错误的部分发生了变化，或增量编辑未能应用，仅凭已保存的内容无法知道原因。两种工具可以报告刷新背后的推理过程。

### 试运行：刷新前预览 {#dry-run-preview-a-refresh-before-it-happens}

响应会回答已保存文档无法回答的问题：

| 字段 | 提供的信息 |
|-------|-------------------|
| `requested_mode` / `effective_mode` | 刷新是否按你配置的模式运行 |
| `mode_fallback_reason` | 增量编辑未应用的原因：`no_baseline_content`、`source_query_changed`、`structured_doc_unreadable`、`delta_ops_failed` 或 `delta_ops_all_skipped`（每个操作都被拒绝） |
| `scope` | 实际筛选记忆的标签、匹配模式和事实类型，而非模型上存储的设置 |
| `window` | 读取的 `created_after`/`created_before` 边界，以及将持久化的水位 |
| `facts.retrieved` 与 `facts.used` | 检索返回的数量与 Reflect 智能体判为相关的数量 |
| `delta_operations` | 输出、应用和跳过的操作 |
| `diff` | 从已保存内容到将写入内容的统一格式差异 |
| `outcome` / `would_persist` | 真实刷新会写入内容、保持内容不变还是失败 |
| `warnings` | 用自然语言说明值得关注的情况 |

试运行有意不接受参数。它就是生产环境的刷新流程，只跳过两处写入：内容写入，包括结构化文档和历史记录项；以及推进 `last_refreshed_at` 的水位写入。其运行方式没有可配置项，因为可另行配置的试运行就无法预测它所对应的真实刷新。要预览不同配置，请通过 `PATCH` 修改模型，然后再次运行。

:::warning
试运行执行与真实刷新相同的 LLM 调用，因此消耗相同的 token，耗时也相同。它与刷新采用相同的校验和计费方式。
:::

#### 执行追踪包含什么 {#what-a-trace-contains}

执行追踪有意采用与 [Reflect](./reflect) 追踪类似的结构：智能体发出的调用，加上刷新特有的决策。它存储在心智模型的数据行中，每次获取模型都会重新读取，因此不存储可从其他位置推导的信息。

| 字段 | 内容 |
|-------|----------|
| `effective_mode` | 最终按 `full` 还是 `delta` 运行 |
| `mode_fallback_reason` | 请求增量模式却未应用的原因：`no_baseline_content`、`source_query_changed`、`structured_doc_unreadable`、`delta_ops_failed`、`delta_ops_all_skipped` |
| `outcome` | `content_written`、`content_preserved_no_new_facts`、`refresh_failed_empty_candidate` 或 `refresh_failed_delta_not_applied`（编辑未应用，文档保留，刷新失败）。操作记录还会添加两种执行器无法产生的结果，因为它们发生在一次运行之外：`refresh_failed_structured_output` 和 `refresh_failed_error`（检索工具抛出异常、智能体没有生成答案，或刷新中出现未预见的异常）。 |
| `tool_calls[]` | 每次调用的 `tool`、智能体的 `reason`、完整 `input`、`result_count`、`duration_ms` 和所属 `iteration` |
| `llm_calls[]` | 每次调用的 `scope`（`agent_1`、`agent_2`、…、`final`）和 `duration_ms` |
| `delta_operations` | 增量模式输出的操作，以及 `applied` 和 `skipped` |
| `usage` | 本次运行所有 LLM 调用的 token 数量 |
| `recorded_at`、`duration_ms`、`warnings[]` | 运行时间、耗时，以及需要人工关注的情况 |

#### 执行追踪有意省略什么 {#what-a-trace-deliberately-omits}

- **工具输出。** 只保留 `result_count`。Recall 载荷很大，而每次获取模型都会重新读取追踪；保存这些载荷会使数据行无限增长。数量足以说明某个工具是否返回空结果。需要原始提示词和响应时，请使用 [LLM 请求追踪](../monitoring)；它们会单独存储，并按自身的保留计划过期。
- **证据。** 刷新用于建立文档依据的事实已保存在 `reflect_response.based_on` 中，与 Reflect 使用的结构相同。执行追踪不再重复存储。
- **解析后的范围和时间窗口。** 它们描述的是模型当前配置将读取什么，而非过去某次运行做了什么，因此由试运行返回，不在每次刷新时写入。

这样，保存的执行追踪会保持较小：典型运行只有几 KB，主要内容是工具输入。

## 清空心智模型 {#clear-a-mental-model}

## 标签与可见范围 {#tags-and-visibility}

心智模型支持与记忆相同的标签系统。为心智模型指定标签后，这些标签既控制刷新时**读取哪些记忆**，也控制 Reflect 时**何时向智能体提供该模型**。

### 标签如何影响心智模型刷新 {#how-tags-affect-mental-model-refresh}

:::warning
为心智模型添加标签会收窄刷新可读取的来源记忆池。如果尚无记忆携带这些标签，即便对相同查询直接调用 `reflect` 可以正常回答，刷新也会返回空内容，例如 `"I cannot find any information…"`。请先为相关记忆补上标签，或通过 `trigger.tags_match`/`trigger.tag_groups` 覆盖默认设置。
:::

手动或自动刷新心智模型时，系统会在内部调用 Reflect 来重新生成内容。如果模型具有标签，该调用使用 `all_strict` 标签匹配，即只读取携带模型**全部**标签的记忆，无标签记忆会被排除。

```
Mental model tags: ["user:alice"]

During refresh, it reads:
  ✅ "Alice prefers async communication"     — has "user:alice"
  ✅ "Team uses Slack for announcements"      — has "user:alice" (plus other tags)
  ❌ "Company policy: no meetings on Fridays" — untagged, excluded
  ❌ "Bob dislikes long meetings"             — no "user:alice" tag
```

这意味着，标签为 `["user:alice"]` 的心智模型也会读取标签为 `["user:alice", "team"]` 的记忆；记忆携带额外标签不会使其被排除，只需包含模型自身要求的标签。

#### 用 `tags_match` 覆盖默认值 {#overriding-the-default-with-tags_match}

对只有一个标签的模型，`all_strict` 默认值是最稳妥的选择；但对有**多个标签**、来源记忆各自只携带一个标签的模型，它会筛掉所有内容。例如，模型标签为 `["projects", "mental-model"]`，来源记忆使用较窄的标签，如 `["project:status"]`、`["tooling"]` 等，那么没有任何单条记忆携带模型的*全部*标签，刷新就会返回空内容。

要匹配携带模型**任一**标签的记忆，与 `recall` 和 `reflect` 的默认行为一致，可在创建时将 `trigger.tags_match` 设为 `"any"`：

### 标签如何影响 Reflect 中的心智模型查找 {#how-tags-affect-mental-model-lookup-during-reflect}

调用 `reflect` 时提供的标签，也会用于筛选智能体可见的心智模型。只有模型标签与 Reflect 请求中的标签存在重叠时，该模型才可见。

有关标签匹配模式 `any`、`any_strict`、`all`、`all_strict` 的详细说明和实例，请参阅 [Recall 标签参考](./recall#tags)。

### 列出心智模型标签 {#listing-mental-model-tags}

`GET /v1/default/banks/{bank_id}/tags` 接受 `source` 查询参数，用于选择要列举的标签空间：

- `source=memories`（*默认*）——附加在记忆单元上的标签。
- `source=mental_models`——附加在此记忆库心智模型上的标签。

使用 `mental_models` 来源可为心智模型标签填充自动补全或筛选界面，将其与通常更大的记忆标签集合区分开。

### 响应 {#response}

端点返回历史记录项列表，最新记录排在前面：

| 字段 | 类型 | 说明 |
|-------|------|-------------|
| `previous_content` | string \| null | 此次变更之前的内容；不可用时为 `null`，失败记录上始终为 `null` |
| `changed_at` | string | 发生变更时的 ISO 8601 时间戳 |
| `kind` | `"refresh_failed"` \| absent | 仅在**失败记录**，即拒绝写入的刷新上存在；版本快照上省略 |
| `outcome` | string \| absent | 失败记录中的操作结果，例如 `refresh_failed_error` |
| `failure_reason` | string \| absent | 失败记录中的拒绝原因：`retrieval_failed`、`no_answer`、`unexpected_error`、`empty_candidate`、`structured_doc_unreadable`、`delta_ops_failed`、`delta_ops_all_skipped`、`delta_not_applied`、`structured_output_failed` |
| `error_message` | string \| absent | 失败记录中的异常，与操作报告的一致 |

每个版本记录保存**变更之前的内容**及变更时间。当前内容由标准的[获取心智模型](#get-a-mental-model)端点返回。

**失败也会记录。** 拒绝写入的刷新不会产生版本，此前它也不会在模型上留下任何痕迹：持续刷新失败一周的文档，与从未刷新过的文档无法区分，保存的 `reflect_response` 仍描述上次*成功*的运行。现在，这些运行会追加失败记录，包含原因和异常。可根据 `kind` 读取：只需要版本的客户端可过滤掉带 `kind` 的记录；需要判断模型是否最新的客户端可检查最新记录是否为失败。

保留限制按记录种类分别应用，因此连续失败不会挤掉版本历史；两类记录各自独立受 `HINDSIGHT_API_MENTAL_MODEL_HISTORY_MAX_ENTRIES` 限制。重试刷新时，每次尝试都会记录一项。

:::note
历史追踪默认启用。设置 `HINDSIGHT_API_ENABLE_MENTAL_MODEL_HISTORY=false` 可禁用；通过 `HINDSIGHT_API_MENTAL_MODEL_HISTORY_MAX_ENTRIES` 可调整每个模型保留的版本数，默认 `50`。
:::
