# Webhooks {#webhooks}

Hindsight 会在发生记忆事件时，向你配置的 URL 发送 HTTP POST 请求，实时通知你的应用。

## 投递与重试 {#delivery-and-retries}

Webhook 按记忆库注册，匹配的事件发生时会自动触发。系统会跟踪每次投递尝试，并对失败的投递采用指数退避重试：

| 尝试次数 | 失败后的等待时间 |
|---------|---------------------|
| 1 | 5 秒 |
| 2 | 5 分钟 |
| 3 | 30 分钟 |
| 4 | 2 小时 |
| 5 | 5 小时 |
| 6 | 永久失败 |

如果你的端点返回非 2xx 状态码，或未能在配置的超时时间内响应（默认 30 秒），则此次投递视为失败。连续 6 次尝试失败后，该投递会被标记为永久失败，不再重试。

:::info 至少一次投递
Webhook 投递任务与主要操作（例如存入或整合写入）在同一个数据库事务中入队。这意味着，如果服务器在提交之后、发送之前崩溃，投递任务仍会保留下来并在之后重试。因此，**你的端点可能会多次收到同一事件**；请根据 `event_id` 去重（该值也会通过 `X-Hindsight-Event-Id` 标头发送）。不要使用 `operation_id` 去重：批量存入时，同一操作中的每份文档都会触发一个事件。
:::

## 验证投递 {#verifying-deliveries}

注册 Webhook 时若配置了密钥，每次投递都会附带针对原始请求正文精确字节计算的 HMAC-SHA256 签名。信任载荷前必须先验证签名；仅凭 URL 不能证明请求来自 Hindsight。

| 标头 | 值 | 说明 |
|--------|-------|-------|
| `X-Hindsight-Event` | 事件类型，例如 `retain.completed` | 始终发送 |
| `X-Hindsight-Event-Id` | 事件的 `event_id` | 始终发送。每次重试以及该事件投递到的每个 Webhook 都使用相同的值；可用它去重 |
| `X-Hindsight-Delivery-Id` | 此事件投递到此 Webhook 的标识符 | 始终发送。每次重试都使用相同的值；与 `GET /webhooks/{id}/deliveries` 列出的 `id` 相同 |
| `X-Hindsight-Signature` | 对原始正文计算的 `sha256=<hex>` | 配置签名密钥后发送 |
| `X-Hub-Signature-256` | 与 `X-Hindsight-Signature` 完全相同 | 这是此签名构造的常用名称，因此 GitHub 风格的接收端无需额外适配即可验证 |
| `X-Hindsight-Signature-V2` | 对 `<t>.<raw body>` 计算的 `t=<unix_seconds>,v1=<hex>` | 带时间戳的变体；需要重放防护时使用 |

`X-Hindsight-Signature` 和 `X-Hub-Signature-256` 始终携带相同的值：使用相同的密钥、算法和字节。验证你的框架已支持的那个标头即可，无需同时检查两者。

:::warning 建议使用带时间戳的签名
`X-Hindsight-Signature` / `X-Hub-Signature-256` 只对正文签名，不包含其他内容，因此它们只能证明*此载荷来自 Hindsight*，不能证明*此载荷是新近发送的*。从网络上截获的投递内容可以永远通过验证。`X-Hindsight-Signature-V2` 会将载荷绑定到签名时间；请检查 `t` 是否处于你设定的容差范围内（五分钟是常见默认值），并拒绝更早的请求。时间戳包含在签名字符串中，修改它会导致 MAC 验证失败。每次重试都会重新签名，因此数小时后重试的投递仍会带有新鲜的 `t`。
:::

```python
import hashlib
import hmac
import time

TOLERANCE_SECONDS = 300


def verify(secret: str, body: bytes, header: str) -> bool:
    """Verify an X-Hindsight-Signature-V2 header against the raw request body."""
    parts = dict(p.split("=", 1) for p in header.split(","))
    timestamp, received = parts["t"], parts["v1"]

    if abs(time.time() - int(timestamp)) > TOLERANCE_SECONDS:
        return False  # too old (or too far in the future) — treat as a replay

    expected = hmac.new(
        secret.encode(), f"{timestamp}.".encode() + body, hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, received)
```

无论使用哪种语言，都要正确处理以下两点：

- **对原始字节签名。** 重新序列化已解析的 JSON 会改变空白和键的顺序，导致签名不匹配。应在框架解码请求正文之前读取它。
- **以恒定时间比较**（`hmac.compare_digest`、`crypto.timingSafeEqual` 等），绝不要使用 `==`。

在 Webhook 的 `http_config` 中设置的自定义标头不能覆盖 `X-Hindsight-Event`、ID 标头或任何签名标头，因此无论其他配置如何，接收端都可以信任这些值。

## 事件类型 {#event-types}

### `consolidation.completed` {#consolidationcompleted}

Hindsight 完成将新记忆整合为某个记忆库的观测后触发。

**载荷：**

```json
{
  "event_id": "3f6c2a9e-8d41-4b7a-9c0e-5e2f1d7a6b48",
  "event": "consolidation.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-04T12:00:00Z",
  "data": {
    "observations_created": 3,
    "observations_updated": 1,
    "observations_deleted": null,
    "error_message": null
  }
}
```

**`data` 字段：**

| 字段 | 类型 | 说明 |
|-------|------|-------------|
| `observations_created` | `integer \| null` | 创建的新观测数量 |
| `observations_updated` | `integer \| null` | 更新的现有观测数量 |
| `observations_deleted` | `integer \| null` | 删除的观测数量 |
| `error_message` | `string \| null` | 当 `status` 为 `"failed"` 时设置 |

**`status` 值：** `"completed"` 或 `"failed"`

---

### `retain.completed` {#retaincompleted}

每份文档的存入操作完成后触发一次（同步和异步操作均如此）。一次存入 N 份文档时，会分别触发 N 个事件。

**载荷：**

```json
{
  "event_id": "3f6c2a9e-8d41-4b7a-9c0e-5e2f1d7a6b48",
  "event": "retain.completed",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "completed",
  "timestamp": "2026-03-04T12:00:01Z",
  "data": {
    "document_id": "doc-abc123",
    "tags": ["meeting", "q1-2026"],
    "memory_unit_count": 12
  }
}
```

**`data` 字段：**

| 字段 | 类型 | 说明 |
|-------|------|-------------|
| `document_id` | `string \| null` | 如果存入请求提供了文档 ID，则为该 ID |
| `tags` | `string[] \| null` | 存入时应用于文档的标签 |
| `memory_unit_count` | `number \| null` | 此次存入后该文档拥有的记忆单元数量。若请求未携带 `document_id`，则为 `null`。 |

**说明：**
- 对于异步存入（`async: true`），`operation_id` 与存入 API 返回的 `operation_id` 相同。
- 对于同步存入，`operation_id` 是为跟踪用途生成的标识符。
- 存入请求中的每个内容项都会触发一个事件。
- `memory_unit_count: 0` 表示该文档没有提取出任何事实。存入操作仍然成功，文本也已存储，但 `recall` 和 `reflect` 检索的是记忆，因此在[重新处理](/developer/retain#when-a-mission-excludes-everything-in-a-document)之前无法检索到该文档。请关注此字段，以发现存入任务排除范围超出预期的情况。

---

### `memory_defense.triggered` {#memory_defensetriggered}

当记忆库的 [Memory Defense（记忆防护）](../memory-defense/index.md)策略对已存入的项目采取措施时触发；每个被**脱敏**或**阻止**的项目触发一次。未受影响、正常通过的项目不会触发事件。记忆库必须已启用 Memory Defense 策略，并且有 Webhook 订阅此事件类型。

**载荷：**

```json
{
  "event_id": "3f6c2a9e-8d41-4b7a-9c0e-5e2f1d7a6b48",
  "event": "memory_defense.triggered",
  "bank_id": "my-bank",
  "operation_id": "a1b2c3d4e5f6",
  "status": "redact",
  "timestamp": "2026-03-04T12:00:02Z",
  "data": {
    "action": "redact",
    "detector": "sensitive_data",
    "document_id": "doc-abc123",
    "matched_types": ["github_token", "aws_access_key"],
    "message": "Sensitive data pattern matched: github_token, aws_access_key"
  }
}
```

**`data` 字段：**

| 字段 | 类型 | 说明 |
|-------|------|-------------|
| `action` | `string` | 对该项目采取的操作：`"redact"`（脱敏）或 `"block"`（阻止） |
| `detector` | `string \| null` | 匹配到的检测器（`"sensitive_data"`） |
| `document_id` | `string \| null` | 如果存入请求提供了文档 ID，则为该 ID |
| `matched_types` | `string[] \| null` | 触发的脱敏模式标签（例如 `github_token`、`ssn_us`） |
| `message` | `string \| null` | 对匹配结果的易读摘要 |

**`status` 值**：与 `data.action` 相同，即 `"redact"` 或 `"block"`。

**说明：**
- `redact` 事件表示敏感内容已被清除，脱敏后的记忆仍然存储。`block` 事件表示该项目已被丢弃；如果存入请求中的所有项目都被阻止，存入调用将返回 `422`。
