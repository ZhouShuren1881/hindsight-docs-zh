# 配置指南 {#configuration}

本文完整介绍如何通过环境变量配置 Hindsight 服务。

Hindsight 提供两种服务，每种服务都有自己的配置前缀：

| 服务 | 环境变量前缀 | 用途 |
|---------|--------|-------------|
| **API 服务** | `HINDSIGHT_API_*` | 核心记忆引擎 |
| **控制平面** | `HINDSIGHT_CP_*` | Web 界面 |

---

## API 服务 {#api-service}

API 服务负责全部记忆操作：Retain（存入）、Recall（召回）和 Reflect（反思）。

### 数据库 {#database}

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_DATABASE_URL` | PostgreSQL 连接 URL | `pg0`（内嵌数据库） |
| `HINDSIGHT_API_READ_DATABASE_URL` | 可选的 PostgreSQL 只读副本 URL。设置后，召回查询（语义、BM25、图、时间检索）会通过针对此 URL 的独立连接池执行，从而分担主数据库负载。通常指向只读端点，例如 CNPG 的 `<cluster>-ro` 服务或 Aurora reader 端点。 | 未设置（使用主库） |
| `HINDSIGHT_API_MIGRATION_DATABASE_URL` | 运行迁移时使用的 PostgreSQL 直连 URL，可绕过 PgBouncer 等连接池代理。设置后，advisory lock 和 Alembic 迁移都会使用此 URL，而不是 `DATABASE_URL`。 | 回退到 `DATABASE_URL` |
| `HINDSIGHT_API_DATABASE_SCHEMA` | 存放表的 PostgreSQL schema 名称 | `public` |
| `HINDSIGHT_API_RUN_MIGRATIONS_ON_STARTUP` | API 启动时执行数据库迁移 | `true` |
| `HINDSIGHT_API_MIGRATION_ISOLATION` | 在子进程中运行迁移，而不是在调用方进程中运行：设为 `true` 可避免 Alembic 的导入依赖图和 psycopg2 同步引擎进入长期运行的服务器进程；也可设为 `false`。 | `false` |
| `HINDSIGHT_API_MIGRATION_CONCURRENCY` | 同时迁移的租户 schema 数量（仅限 PostgreSQL）。每个 schema 在独立进程中运行，该 schema 内的迁移仍始终按顺序执行。每个工作进程都有固定启动开销（启动新解释器约需 1–2 秒），所以只有 schema **很多**（大约几十个或更多）或迁移较慢、延迟较高时才有收益；schema 数量不多时反而比串行更慢。每个工作进程约占用 3 个数据库连接，因此 `concurrency × 3` 应低于数据库空闲的 `max_connections`，也要符合 PgBouncer 池限制。`1` 表示完全串行。实测 20k 个 schema 时，将 `concurrency` 设为 `12` 后，每次重启时的无操作重扫从约 60 分钟降到约 11 分钟（约 5 倍）。 | `1` |
| `HINDSIGHT_API_EXTERNALLY_OWNED_ROUTINES` | 以逗号分隔列出此部署自行安装的维护发现例程（参见[自行维护例程](#owning-a-maintenance-routine)）。迁移会跳过这些名称。 | 空（默认安装全部例程） |
| `HINDSIGHT_API_DATABASE_BACKEND` | 数据库引擎后端：`postgresql` 或 `oracle`（Oracle 23ai） | `postgresql` |

如果没有提供数据库 URL，服务器会使用内嵌式 `pg0`。它适合开发环境，但不建议用于生产环境。

要调整内嵌数据库，可在查询字符串中加入 PostgreSQL 参数，例如：`pg0://hindsight?max_connections=300&shared_buffers=256MB`。参数会在内嵌数据库启动时生效，因此修改后需要重启。

要改用 Oracle Database 23ai，请将 `HINDSIGHT_API_DATABASE_BACKEND=oracle`，并使用 `oracle+oracledb://…` URL。完整配置说明参见 [Oracle 数据库指南](./oracle)。

`DATABASE_SCHEMA` 可指定自定义 PostgreSQL schema，代替默认的 `public`。以下场景适合使用此设置：
- 多数据库部署希望将 Hindsight 的表放在独立 schema 中
- 托管平台（例如 Supabase）已保留或共享 `public` schema
- 组织需要遵循特定的 schema 命名惯例

```bash
# Example: Using a custom schema
export HINDSIGHT_API_DATABASE_URL=postgresql://user:pass@host:5432/dbname
export HINDSIGHT_API_DATABASE_SCHEMA=hindsight
```

迁移会在 schema 不存在时自动创建它，并将所有表都建在配置的 schema 中。

#### 自行维护例程 {#owning-a-maintenance-routine}

后台维护循环会调用四个 PostgreSQL 例程来查找待处理任务：`mental_models_with_cron`、`banks_needing_consolidation`、`schemas_with_expired_rows` 和 `schemas_with_expired_operations`。默认实现会在每次循环时扫描数据库中的所有 schema。大型多租户部署中，这意味着每个运行维护循环的进程都会在每个周期串行遍历数千个 schema。

这些例程按名称调用，因此可以替换成适合自身部署的实现。常见方案是通过行触发器维护注册表，让查找只需要一次索引读取，而非扫描。列出自行替换的例程后，迁移便会跳过它们：

```bash
export HINDSIGHT_API_EXTERNALLY_OWNED_ROUTINES=mental_models_with_cron,banks_needing_consolidation
```

该值从执行迁移的进程环境中读取，因此适用于 `hindsight-admin run-db-migration`、迁移 Job 和启动时迁移。

若不设置此项，自定义例程只会保留到某次迁移重新安装该例程为止。迁移会对相同名称执行 `CREATE OR REPLACE`，因此迁移会覆盖自定义版本；数据库也不会记录该实现曾被替换。

还需注意以下几点：

- **自行实现的例程必须与默认签名一致。** 循环会使用固定参数调用例程，并读取固定列。
- **系统不会检查自定义例程是否存在。** 如果列出了尚未安装的名称，数据库会保留当前状态；新数据库中则没有该函数。维护循环随后会因函数缺失而失败，不会悄悄退回到你要避免的扫描。
- **数据库中不记录所有权。** 从列表移除某个名称后，下次迁移会恢复安装默认例程，不会修复数据。
- **默认列表为空。** 没有自行替换例程的部署不会受到影响。

### 数据库连接池 {#database-connection-pool}

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_DB_POOL_MIN_SIZE` | 主连接池的最小连接数 | `5` |
| `HINDSIGHT_API_DB_POOL_MAX_SIZE` | 主连接池的最大连接数 | `100` |
| `HINDSIGHT_API_READ_DB_POOL_MIN_SIZE` | 只读副本连接池的最小连接数（仅在设置 `READ_DATABASE_URL` 时使用） | 回退到 `DB_POOL_MIN_SIZE` |
| `HINDSIGHT_API_READ_DB_POOL_MAX_SIZE` | 只读副本连接池的最大连接数（仅在设置 `READ_DATABASE_URL` 时使用） | 回退到 `DB_POOL_MAX_SIZE` |
| `HINDSIGHT_API_DB_COMMAND_TIMEOUT` | PostgreSQL 命令超时时间，单位秒（asyncpg 客户端侧） | `60` |
| `HINDSIGHT_API_DB_ACQUIRE_TIMEOUT` | 获取连接的等待上限，单位秒。超过上限后调用失败，由调用方重试；设为 `0` 表示无限等待。 | `30` |
| `HINDSIGHT_API_DB_POOL_SLOW_ACQUIRE_THRESHOLD_SECONDS` | 获取池连接耗时超过此秒数时记录 `[DB POOL] Slow acquire` 警告。若新连接通常建立较慢（例如通过 TLS 连接 Aurora Serverless），可调高此值；设为 `0` 关闭警告。 | `0.05` |
| `HINDSIGHT_API_DB_STATEMENT_TIMEOUT` | 对每条池连接应用 Postgres `statement_timeout`，单位秒，作为失控查询的服务器端保护。此项**不适用于**使用独立 psycopg2 引擎运行的 Alembic 迁移。设为 `0` 可禁用。 | `600` |
| `HINDSIGHT_API_DB_MAX_PARALLEL_WORKERS_PER_GATHER` | 可选的 Postgres `max_parallel_workers_per_gather` 设置，应用于本进程的所有池连接。未设置时采用服务器默认值。后台工作进程可设为 `0`，让整合、图维护等批量维护查询串行运行，避免它们扩散到与延迟敏感流量共用的 CPU 核心上。 | 未设置 |
| `HINDSIGHT_API_DB_SESSION_SETUP_ON_ACQUIRE` | 控制每次从池中取出连接时，是否重新应用上述会话设置（`statement_timeout`、`max_parallel_workers_per_gather`、三元组阈值、向量搜索调优，以及 `vchord` 文本检索后端的 search path），而不是只在连接首次打开时应用。除非相同设置已固定在数据库角色或数据库本身（`ALTER ROLE … SET`），否则应保持开启：在事务模式连接池代理后面，一次取连接操作可能关联到从未收到这些设置的服务器连接；直连时设置会保留，因此重新应用属于冗余。若关闭此项且服务器端没有固定这些设置，复用的连接会悄悄在缺少设置的情况下运行；`vchord` 的召回会直接失败，而不只是性能下降。若服务器端已固定这些设置，重新应用不会改变行为，只会让每次取连接多一次往返；对于繁忙且使用事务模式连接池代理的部署，省去这次往返可能有价值。`application_name` 始终会重新应用，不受此设置影响。 | `true` |
| `HINDSIGHT_API_ENTITY_TRGM_SIMILARITY_THRESHOLD` | 对每条池连接应用 Postgres `pg_trgm.similarity_threshold`，决定实体消解的 `%` 三元组匹配要达到多高的名称相似度才纳入候选。必须大于 `0` 且小于 `1`。系统绝不会将它设在 `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY` 之下，因为低于合并门槛的候选无法被合并。提高到合并门槛以上可以减少候选，只留下更接近的名称。 | `0.3` |
| `HINDSIGHT_API_ENTITY_INTRABATCH_MERGE_SIMILARITY` | 同一次 Retain 新建的两个名称，其三元组相似度达到该值时合并成一个实体。此值在内存中计算，效果与 pg_trgm 等同；用于合并同一名称的表面形式变体，例如表情、大小写或后缀不同的写法。必须大于 `0` 且小于 `1`。这是*合并*门槛，刻意比上方仅用于召回候选的阈值更严格。调高到接近 `1.0` 时，只会合并几乎相同的形式。 | `0.5` |
| `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY` | 名称要复用一个**已有**实体所需的最小三元组相似度，无论其他实体消解信号如何。它介于上方的召回阈值（`0.15`，只决定考虑哪些候选）与下方的同批次合并门槛（`0.5`）之间。必须大于 `0` 且小于 `1`。对于很短名称较多的语料，可调低此值，因为这类名称的三元组相似度通常较低（`Jon` 与 `John` 为 `0.29`）；若只应合并明显的表面形式变体，则可调高。 | `0.3` |

并发量较高时，可提高 `DB_POOL_MAX_SIZE`。每个并发召回或思考操作可能会使用 2–4 条连接。

例如要在启动 API 前手动执行迁移，可使用管理 CLI：

```bash
# Migrate the base schema plus all discovered tenant schemas
hindsight-admin run-db-migration

# Or migrate a specific schema only:
hindsight-admin run-db-migration --schema tenant_acme
```

### 向量扩展 {#vector-extension}

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_VECTOR_EXTENSION` | 向量索引算法：`pgvector`、`vchord`、`pgvectorscale` 或 `scann` | `pgvector` |
| `HINDSIGHT_API_ANN_ITERATIVE_SCAN` | 允许向量索引扫描继续执行，直到满足查询的 `LIMIT`，而不是在首批候选耗尽时停止。关闭后，召回返回的行数不会超过首批候选数；例如 pgvector 的 `hnsw.ef_search` 为 `200`，此时提高召回预算只会扩大 SQL，不会获得更多结果。需要 pgvector 0.8.0 或更新版本；较旧服务器会拒绝此设置，首次尝试后系统会自动移除它。这是运维关闭开关：设为 `false` 并重启，就能准确恢复此前的检索深度，无需更改代码。 | `true` |
| `HINDSIGHT_API_ANN_MAX_SCAN_TUPLES` | 单次续扫可访问的元组数量上限（`hnsw.max_scan_tuples`）。此参数决定迭代扫描的成本：相似度下限、标签和日期范围等过滤条件都在索引扫描*之后*才执行，因此选择性强的查询会反复续扫；本项同时限制 CPU 消耗和内存占用（pgvector 还会用 `work_mem × hnsw.scan_mem_multiplier` 限制内存，而在此默认值下不会达到该上限）。调低此值可用检索深度换取延迟；首轮扫描不计入上限，因此即使设为 `1`，原有检索深度也会保留。pgvector 自身的默认值是 `20000`。关闭迭代扫描后，此项会被忽略。 | `4000` |

Hindsight 支持四种 PostgreSQL 向量扩展：

#### **pgvector**（HNSW，默认） {#pgvector-hnsw---default}
- 使用分层可导航小世界算法的内存索引
- 适用于大多数嵌入和数据集规模
- 中小型数据集（&lt;10M 个向量）查询速度快
- 大型数据集会占用较多内存
- 部署最广泛，支持最成熟

#### **pgvectorscale**（DiskANN，推荐用于大规模部署） ⭐ {#pgvectorscale-diskann---recommended-for-scale-}
- 基于 StreamingDiskANN 算法的磁盘索引
- 与专用向量数据库相比，**p95 延迟降低 28 倍**，**吞吐量提高 16 倍**
- 大规模使用可**降低 60–75% 成本**（SSD 比 RAM 便宜）
- 流式检索方式提供更好的过滤性能
- 针对大型数据集（10M+ 个向量）优化
- 支持开源版 **pgvectorscale** 和 Azure 版 **pg_diskann**
- **安装：**
  - 开源/自托管：`CREATE EXTENSION vector; CREATE EXTENSION vectorscale CASCADE;`
  - Azure PostgreSQL：`CREATE EXTENSION vector; CREATE EXTENSION pg_diskann CASCADE;`

#### **vchord**（vchordrq） {#vchord-vchordrq}
- 高性能向量索引的另一种选择
- 针对高维嵌入（3000+ 维）优化
- 集成 BM25 搜索能力
- 需要安装 `vchord` 扩展

#### **scann**（AlloyDB ScaNN） {#scann-alloydb-scann}
- Google 的 ScaNN 索引，可用于 **AlloyDB** 和 **AlloyDB Omni**
- `AUTO` 模式下使用一个全局向量索引，不会创建按记忆库划分的部分索引
- **安装：** `CREATE EXTENSION vector; CREATE EXTENSION alloydb_scann CASCADE;`
- **延后建立索引**，直到表中已填充嵌入的行数达到 **10,000**。AlloyDB 无法在几乎为空的表上创建 ScaNN AUTO 索引；达到门槛之前，Recall 会退回到顺序扫描。行数足够后，下次 API 启动时才会建立全局索引。
- [`docker/docker-compose/alloydb/docker-compose.yaml`](https://github.com/vectorize-io/hindsight/blob/main/docker/docker-compose/alloydb/docker-compose.yaml) 提供可直接使用的 Docker Compose 配置，可在本地通过 AlloyDB Omni 运行 Hindsight。

**适合使用 pgvectorscale（DiskANN）的情况：**
- 大型数据集（10M+ 个向量） ⭐
- 过滤条件复杂
- 部署对成本敏感
- 生产负载需要高吞吐量
- 磁盘 I/O 不构成瓶颈

**适合使用 pgvector（HNSW）的情况：**
- 中小型数据集（&lt;10M 个向量）
- 全部数据都能放入内存，且希望查询速度最快
- 不带过滤器的简单近邻查询
- 倾向于采用标准 PostgreSQL 部署

**适合使用 vchord 的情况：**
- 嵌入维度较高（3000+ 维）
- 希望使用集成的 BM25 搜索
- 已经使用 vchord 进行文本搜索

**适合使用 scann 的情况：**
- 部署在 Google **AlloyDB** 或 **AlloyDB Omni** 上
- 希望使用托管的 ScaNN，并采用 `AUTO` 模式调优

#### 限制大型部署中的向量索引数量 {#limiting-vector-indexes-on-large-deployments}

在 `pgvector`、`pgvectorscale` 和 `vchord` 中，记忆库的记忆按 `(bank, fact_type)` 建立索引。默认情况下，每个记忆库在创建时都会获得自己的索引；这适用于多数部署，且无需额外配置。

记忆库达到数千个后，这种做法就不再合适。所有这些索引都位于同一张共享表上；PostgreSQL 针对该表规划查询时，会检查并锁定**每个**索引。因此，为一个记忆库创建索引的成本会由其他所有库的搜索共同承担。记忆库超过数千个后，查询规划速度会明显下降，服务器最终还可能耗尽锁表空间，导致读取和删除记忆库*都*失败。

设置最小规模门槛可以解决这个问题：只有记忆库大到能从索引获益时，才会获得自己的索引。低于门槛时，PostgreSQL 会使用 `(bank_id, fact_type)` B-tree 和 top-N 排序完成同样的搜索；这对小型记忆库更快，而且结果是*精确*的，不是近似值，因此小库不会受到损失。这样索引数量便随**大型**记忆库数量增长，而不是随全部记忆库数量增长，记忆库总数也就不再构成限制。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_VECTOR_INDEX_MIN_ROWS` | 一个记忆库中，某类事实至少需要达到的记忆数；达到后该事实类型才会拥有独立向量索引。默认 `0` 表示**关闭**门槛，每个记忆库从创建时起就建立索引。拥有数千个库的部署可以从 `10000` 开始尝试。由自定义存储管理记忆的库不受此项影响，因为它们在这里没有数据行；系统不会为它们创建按库索引，也不会移除已有索引（参见[管理 CLI](./admin-cli.md) 中的 `repair-bank`）。 | `0` |
| `HINDSIGHT_API_VECTOR_INDEX_MAINTENANCE_MIN_INTERVAL_SECONDS` | 同一个记忆库两次索引维护之间的最短间隔，避免库大小在门槛附近波动时反复创建、删除同一个索引。关闭门槛时不会使用此设置。 | `900` |

**关闭门槛（默认）时**，索引会在创建记忆库的事务中建立。由于新库为空，创建会立即完成；删除记忆库时索引也会一并删除。系统不会检查库大小，也不会运行后台操作。

**设置门槛后**，创建记忆库、摄取内容和导入数据时都不会创建索引，因此请求不必等待索引 DDL。可能使记忆库跨过门槛的写入会将 `vector_index_maintenance` 操作放入后台队列：记忆库增长到门槛以上时创建索引，缩小到明显低于门槛时删除索引。两种状态之间留有间隔，防止在临界值附近反复切换。相关操作会显示在记忆库的操作列表中。

还原数据、升级或切换扩展后，如果要立即校准索引而不等待下一次写入，请运行：

```bash
hindsight-admin repair-bank --all
```

两种模式都适用：门槛关闭时会重建缺少的索引；门槛启用时还会删除不再符合条件的索引。

**切换扩展：**

需要将向量扩展从一种切换到另一种时：
1. 将 `HINDSIGHT_API_VECTOR_EXTENSION` 设为目标扩展：`pgvector`、`vchord`、`pgvectorscale` 或 `scann`。
2. 如果数据库已有数据，系统会报错并显示迁移说明。注意，即使已有数据，也允许切换**到** `scann`：当前索引会被删除，待表中嵌入行达到 10,000 后再创建 ScaNN 索引。
3. 空数据库会在启动时自动重建索引。

**了解更多：**
- [HNSW 与 DiskANN 对比](https://www.tigerdata.com/learn/hnsw-vs-diskann)
- [pgvectorscale GitHub 项目](https://github.com/timescale/pgvectorscale)

### 文本搜索扩展 {#text-search-extension}

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_TEXT_SEARCH_EXTENSION` | 文本搜索后端：`native`、`vchord`、`pg_textsearch`、`pgroonga` 或 `pg_search` | `native` |
| `HINDSIGHT_API_TEXT_SEARCH_EXTENSION_NATIVE_LANGUAGE` | `native` 后端使用的 PostgreSQL 文本搜索词典（例如 `english`、`french`、`simple`、`zhparser`） | `english` |
| `HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_TOKENIZER` | 创建 BM25 索引时 ParadeDB `pg_search` 使用的分词器。留空时采用 ParadeDB 默认的 `unicode_words`。 | 未设置 |
| `HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_FUNCTION_SCHEMA` | ParadeDB `pg_search` 函数（`score`、`boolean`、`match`）所在的 schema。默认是 `paradedb`；如果托管 PostgreSQL 将函数安装在自定义 schema 中，可设为 `pgsearch` 或其他有效标识符。 | `paradedb` |
| `HINDSIGHT_API_BM25_MAX_QUERY_TERMS` | 原生 PostgreSQL BM25 `tsquery` 的词项上限。长查询会用 OR 连接全部归一化词元；原生排序没有 IDF，且会重新排列每个匹配项，因此对常见词不设上限的查询可能扫描并排序记忆库中很大一部分内容，最终超时。查询超过上限时，会保留**选择性最高**的词项，即租户范围内文档频率最低的词；这些频率可从 `pg_stats` 免费读取（由 autovacuum 维护，无需重建索引），避免简单截断时丢掉信息量高的词。设为 `0` 可恢复过去不限制词项数的行为。此上限只作用于 `native` 后端；其他 BM25 后端会接收原始查询，并通过各自索引原生的运算符排序。 | `16` |
| `HINDSIGHT_API_BM25_SELECTIVE_TERMS` | 达到上方词项上限后，决定是否保留**选择性最高**的词（`pg_stats` 中文档频率最低的词），而不是保留最前面的 N 个。统计信息存在时，`true` 能提高召回且没有额外成本；设为 `false` 可跳过系统目录读取，改按位置截取。词项上限为 `0` 时忽略此项。 | `true` |
| `HINDSIGHT_API_LLM_OUTPUT_LANGUAGE` | 设置后，强制所有由 LLM 生成的内容（Retain 提取的事实、整合得到的观测、Reflect 的回答）都使用此语言。可填写任意语言名称，例如 `Spanish` 或 `Japanese`。 | 未设置 |

Hindsight 提供五种 BM25 关键词检索后端：
- **native**：PostgreSQL 内置全文搜索（`tsvector` + GIN），可配置语言。
- **vchord**：VectorChord BM25，使用 `llmlingua2` 多语言分词器。
- **pg_textsearch**：Timescale 的 pg_textsearch 扩展，仅支持英语。
- **pgroonga**：pgroonga 全文搜索，开箱即支持多种语言和中日韩（CJK）文本。
- **pg_search**：ParadeDB pg_search，提供真正的 BM25，也是唯一兼容 Citus 的后端。

记忆库也可以不使用任何关键词后端：通过 [`enable_text_search`](#recall-pipeline-stages) 可按库关闭关键词检索分支，只保留纯向量搜索。关闭后，本表中的设置对该记忆库都不再使用。

要切换后端，请设置 `HINDSIGHT_API_TEXT_SEARCH_EXTENSION`。如果数据库已有数据，系统会报错并提供迁移说明；数据库为空时，列和索引会在启动时自动重建。

只有在 `HINDSIGHT_API_TEXT_SEARCH_EXTENSION=pg_search` 且创建 BM25 索引时，才会使用 `HINDSIGHT_API_TEXT_SEARCH_EXTENSION_PG_SEARCH_TOKENIZER`。已有数据库修改此项后，需要重建 `pg_search` 索引，或重新创建数据库。支持的值包括空值/未设置、`unicode_words`、`simple`、`whitespace`、`literal`、`literal_normalized`、`chinese_compatible`、`icu`、`jieba`、`source_code`、`chinese_lindera`/`lindera(chinese)`、`japanese_lindera`/`lindera(japanese)`、`korean_lindera`/`lindera(korean)`、`ngram(min,max)` 和 `edge_ngram(min,max)`。

非英语记忆库（尤其是 CJK 语言）以及语言和事实提取语言之间的取舍，请参阅[多语言支持](./multilingual)。

| `HINDSIGHT_API_LLM_STRUCTURED_OUTPUT_FORCED_TOOL` | 对 LiteLLM 后端（`litellm`、`litellmrouter`、`bedrock`），可改用强制单个工具调用来请求结构化输出，并将响应 schema 作为工具参数，而不是使用 `response_format`。对于直接拒绝 `response_format` 的后端，设为 `true`。Bedrock Claude 是否需要此项取决于区域：`ap-southeast-2`（`au.*` 推理配置）会以 `Extra inputs are not permitted` 拒绝转换后的 Converse `outputConfig`；同一模型在 `us-east-1`（`us.*`）可以接受，无需设置。两种情况都已验证。如果模型未调用工具而是直接回答，系统仍按以前的方式将回复当作文本解析。其他提供方会忽略此项。 | `false` |
| `HINDSIGHT_API_LLM_OPENAI_COMPATIBLE_JSON_MODE` | 指定兼容 OpenAI 的后端在宽松（非 strict）结构化输出流程中是否支持 `response_format={"type": "json_object"}`。留空时由提供方决定：LM Studio、Ollama 和 Volcano 只在提示词中提供 schema；llama.cpp 遵循 `HINDSIGHT_API_LLAMACPP_NO_GRAMMAR`；其他提供方会发送 `json_object`。若 `provider=openai` 指向无法约束输出的本地服务器，可设为 `false`。一些服务器会改写提示词，而思考模型可能不断围绕改写后的内容循环，直到 LLM 超时。关闭此项不会让模型自动生成 JSON，只会删除服务器处理不当的请求字段；模型仍须遵循提示词中的 schema。设为 `true` 可强制向默认会跳过此字段的后端发送 `json_object`。 | 由提供方决定 |
| `HINDSIGHT_API_LLM_CODEX_HOME` | `openai-codex` 提供方的凭据目录，内含其用于认证的 `auth.json`。这会覆盖 Hindsight 自身 LLM 调用所用的进程级 `CODEX_HOME`。因为 `CODEX_HOME` 是进程级设置，可将此项与按成员设置的 `HINDSIGHT_API_LLM_<n>_CODEX_HOME` 配合，在一个进程中运行两个独立授权的 ChatGPT 配置档。这样由两个 Codex 成员组成的[多 LLM 链](#multi-llm-strategies-failover--round-robin)便可在不同账户间故障转移。 | 未设置（否则使用 `CODEX_HOME`，再否则使用 `~/.codex`） |
| `HINDSIGHT_API_LLM_OLLAMA_NUM_CTX` | 可选的 Ollama 原生 `num_ctx` 覆盖值。留空时采用模型或服务器默认值；需要更大上下文窗口时才设置为正整数。设置后，包括启动连接探测在内的自由格式调用也会经由原生 `/api/chat` API，因为兼容 OpenAI 的端点不能表达上下文大小；详见下文。 | 未设置 |
| `HINDSIGHT_API_LLM_GEMINI_SAFETY_SETTINGS` | Gemini/VertexAI 内容安全过滤器所用的 `{category, threshold}` 字典列表，以 JSON 编码 | `null` |
| `HINDSIGHT_API_LLM_PROMPT_CACHE_ENABLED` | 使用提供方明确提供的提示缓存重复利用固定系统前缀，并按缓存输入费率计费（Gemini/Vertex 的 `CachedContent`）。所有记忆库共享该缓存前缀；缓存失败时会自动改用普通调用。设为 `false` 可禁用。参见[模型](./models#provider-capabilities)。 | `true` |
| `HINDSIGHT_API_REFLECT_PROMPT_CACHE_ENABLED` | 只对 Reflect 生效：在智能体工具循环中逐步延续上下文缓存，使每一轮都能以缓存输入费率重用先前的完整对话（系统提示、工具及所有先前工具结果），而不只是静态前缀。需要先启用 `HINDSIGHT_API_LLM_PROMPT_CACHE_ENABLED`。每次 Reflect 的缓存都是临时的，操作结束后会删除。设为 `false` 可让 Reflect 不使用缓存，同时其他操作仍可使用提示缓存。当前 Gemini 上关闭此项更便宜，因为创建缓存会按完整输入费率另收存储费用，而且每个滚动缓存只会被一次调用读取。 | `true` |
| `HINDSIGHT_API_LLM_DEBUG_DUMP_4XX` | 诊断用途：启用后，任何 LLM 请求遇到 `4xx` 响应时，提供方都会记录 `[LLM_4XX_DUMP]`，其中包含实际组装的请求：序列化配置（响应 schema 和生成参数，不包含消息正文）以及按长度截断的逐消息预览，便于检查平时难以复现的拒绝请求。所有远程提供方都已接入，包括 Gemini/Vertex、兼容 OpenAI 的提供方（含 Fireworks/Nous）、Anthropic、LiteLLM（含 Router）和 Codex。默认关闭，日常运行时应保持关闭。 | `false` |

当 `HINDSIGHT_API_LLM_PROVIDER=ollama` 时，Hindsight 不再默认发送过去原生 API 使用的 `num_ctx=16384`。如需保留旧的请求行为，请显式设置 `HINDSIGHT_API_LLM_OLLAMA_NUM_CTX=16384`；否则 Ollama 会采用模型 Modelfile 或服务器的默认值。

**Hindsight 使用 Ollama 原生 API 的情形。** 结构化输出调用始终通过原生 `/api/chat` 执行，以确保 schema 得到约束。一旦设置 `HINDSIGHT_API_LLM_OLLAMA_NUM_CTX`，自由格式调用也会改用此 API。Ollama 的 OpenAI 兼容处理器只解析固定的一组字段，其余字段都会丢弃；`/v1/chat/completions` 无法表达 `num_ctx`，放在 `options` 中也不行。这对共享 Ollama 主机尤其重要：Ollama 按上下文大小区分已加载模型实例，因此使用服务器默认上下文的请求会重新加载模型，并针对其他每个使用方再次调优。

**Ollama 原生路径中的 `HINDSIGHT_API_LLM_EXTRA_BODY`。** 原生请求体分为*两层*；兼容 OpenAI 的端点则由 SDK 将全部参数摊平到顶层。通过原生 API 时，`extra_body` 会按以下方式拆分：

- **原生顶层字段**（`think`、`keep_alive` 等）会直接传递。例如，gpt-oss 模型进行结构化提取时需要设置思考级别，可指定 `HINDSIGHT_API_LLM_EXTRA_BODY='{"think": "low"}'`（默认关闭思考）。
- **生成参数**（`seed`、`top_p`、`top_k`、`num_ctx`、`temperature` 等）属于 Ollama 的 `options` 对象，因此应嵌套传入：`HINDSIGHT_API_LLM_EXTRA_BODY='{"options": {"seed": 42, "top_p": 0.9}}'`。相同参数在兼容 OpenAI 的端点上位于顶层。

### SuperGrok OAuth（`xai-oauth`） {#supergrok-oauth-xai-oauth}

`HINDSIGHT_API_LLM_PROVIDER=xai-oauth` 通过设备码 OAuth 使用 SuperGrok 订阅进行身份验证，无需 API 密钥。运行 `python -m hindsight_api.engine.providers.xai_oauth_auth login` 登录一次；授权凭据会存储在磁盘上并自动刷新。下列变量均为可选项，默认值与供应商自己的客户端一致，因此常规部署无需设置任何变量。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_XAI_OAUTH_TOKEN_PATH` | OAuth 授权凭据的存储位置。登录和刷新都会使用该路径，因此它会迁移整个存储位置，而不只是覆盖读取路径。 | `~/.hindsight/xai_oauth.json` |
| `HINDSIGHT_API_XAI_OAUTH_BASE_URL` | 面向整个部署的端点覆盖值。优先级高于 `HINDSIGHT_API_LLM_BASE_URL`；部署通常会将后者用于其他代理。 | `https://api.x.ai/v1` |
| `HINDSIGHT_API_XAI_OAUTH_CLIENT_ID` | 登录和刷新时使用的 OAuth 客户端 ID。 | xAI 公布的 Grok CLI 客户端 |
| `HINDSIGHT_API_XAI_OAUTH_SCOPE` | 登录时请求的权限范围字符串。 | 供应商默认值 |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_SKEW_SECONDS` | 距到期多少秒时视为需要刷新令牌。若此部署很少调用提供方（例如采用 cron 或网关模式），可增大此值。 | `60` |
| `HINDSIGHT_API_XAI_OAUTH_REFRESH_TIMEOUT_SECONDS` | 发现、设备码和刷新请求的单次超时时间。 | `20` |
| `HINDSIGHT_API_XAI_OAUTH_DEBUG_HEADERS` | 非 2xx 响应时，记录允许列表中的响应头（`via`、`x-request-id`、`cf-ray`、`server`、`date`）。仅用于诊断；绝不记录凭据、Cookie 或请求/响应正文。 | `false` |

这是订阅接入方式，不代表支持 xAI API 密钥。若要通过 API 密钥调用 `api.x.ai`，请设置 `HINDSIGHT_API_LLM_PROVIDER=openai` 和 `HINDSIGHT_API_LLM_BASE_URL=https://api.x.ai/v1`。

### LLM Router（LiteLLM Router） {#llm-router-litellm-router}

设置 `HINDSIGHT_API_LLM_PROVIDER=litellmrouter` 后，默认 LLM 会通过 [LiteLLM 的 `Router`](https://docs.litellm.ai/docs/routing) 运行。配置 JSON 会原样传递；故障转移链、负载均衡、速率限制、路由策略及其他受支持的键请参阅 [LiteLLM Router 文档](https://docs.litellm.ai/docs/routing)。Hindsight 始终使用 `model_name: "default"` 发起补全请求，因此配置中至少要有一个此名称的条目。

| 变量 | 说明 |
|----------|-------------|
| `HINDSIGHT_API_LLM_LITELLMROUTER_CONFIG` | 传递给 `litellm.Router(**config)` 的 JSON 对象。提供方为 `litellmrouter` 时必填。 |
| `HINDSIGHT_API_{RETAIN,REFLECT,CONSOLIDATION}_LLM_LITELLMROUTER_CONFIG` | 各操作的覆盖配置。未设置时回退到默认配置。 |

```bash

  "model_list": [
    {"model_name": "default",  "litellm_params": {"model": "openai/gpt-4o-mini", "api_key": "sk-..."}},
    {"model_name": "fallback", "litellm_params": {"model": "anthropic/claude-sonnet-4-5", "api_key": "sk-ant-..."}}
  ],
  "fallbacks": [{"default": ["fallback"]}]
}'
```

此配置属于凭据字段，银行配置 API 不会返回它。Hindsight 已会重试调用；请在 Router 配置中设置 `"num_retries": 0`，以免重复重试。Router 模式不支持批量 API。

### 多 LLM 策略（故障转移 / 轮询） {#multi-llm-strategies-failover--round-robin}

在主 LLM 之外，**按索引**配置额外的 LLM，再选择跨这些 LLM 路由的策略。这是 LiteLLM Router 之外的通用方案：索引 LLM 可混用任意提供方，并分别完成完整配置。

未带索引的 `HINDSIGHT_API_LLM_*` 配置是**主 LLM**（成员 1）。额外成员从 1 开始编号：

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_LLM_<n>_PROVIDER` | 额外成员 `n` 的提供方（`n` = 1、2……）。设置此变量即定义该成员；索引必须从 1 开始连续编号。 | - |
| `HINDSIGHT_API_LLM_<n>_API_KEY` | 成员 `n` 的 API 密钥（提供方不需要密钥时除外）。 | - |
| `HINDSIGHT_API_LLM_<n>_MODEL` | 成员 `n` 使用的模型。 | 提供方默认值 |
| `HINDSIGHT_API_LLM_<n>_BASE_URL` | 成员 `n` 的基础 URL。 | 提供方默认值 |
| `HINDSIGHT_API_LLM_<n>_REASONING_EFFORT` | 成员 `n` 的推理强度。 | `HINDSIGHT_API_LLM_REASONING_EFFORT` |
| `HINDSIGHT_API_LLM_<n>_EXTRA_BODY` / `_DEFAULT_HEADERS` | 每个成员专用的 JSON 覆盖项。 | - |
| `HINDSIGHT_API_LLM_<n>_BEDROCK_SERVICE_TIER` / `_GEMINI_SERVICE_TIER` | 每个成员专用的服务层级。 | - |
| `HINDSIGHT_API_LLM_<n>_VERTEXAI_PROJECT_ID` / `_VERTEXAI_REGION` / `_VERTEXAI_SERVICE_ACCOUNT_KEY` | Vertex AI 成员专用的项目、区域和服务账号密钥路径。未设置时分别回退到全局 `HINDSIGHT_API_LLM_VERTEXAI_*`。 | 全局值 / `us-central1` / ADC |
| `HINDSIGHT_API_LLM_<n>_CODEX_HOME` | 成员专用的 Codex 凭据目录，即此成员用于身份验证的 `auth.json` 所在目录。设置后，两个 Codex 成员可分别使用两个独立授权的 ChatGPT 配置档；否则所有成员都会解析到同一个存储位置。依次回退到全局 `HINDSIGHT_API_LLM_CODEX_HOME`、`CODEX_HOME`、`~/.codex`。 | 全局值 / `CODEX_HOME` / `~/.codex` |
| `HINDSIGHT_API_LLM_<n>_LITELLMROUTER_CONFIG` | LiteLLM Router 成员专用的配置 JSON。未设置时回退到全局 `HINDSIGHT_API_LLM_LITELLMROUTER_CONFIG`。 | - |
| `HINDSIGHT_API_LLM_<n>_TIMEOUT` | 成员专用的请求超时时间，单位秒。未设置时回退到操作超时设置。 | 操作超时设置 |
| `HINDSIGHT_API_LLM_<n>_MAX_RETRIES` | 成员专用的重试次数上限。未设置时回退到操作的 `MAX_RETRIES`；`0` 是有效值，表示立即故障转移。 | 操作的 `MAX_RETRIES` |
| `HINDSIGHT_API_LLM_STRATEGY` | 用于在链中进行路由的 JSON 策略。未设置 = 仅使用主 LLM（行为不变）。 | - |

策略 JSON 支持三种模式：

- `{"mode": "failover"}` — 按顺序尝试成员（先尝试主 LLM）；某成员经过自身重试后仍失败，就切换到下一成员。
- `{"mode": "round-robin"}` — 每个请求轮换起始成员以分摊负载，失败时再依次尝试其余成员。可添加 `"weights": [3, 1, ...]`（每个成员对应一个正整数，主 LLM 排第一）进行**非均衡**轮询。
- `{"mode": "metadata", "routes": [...]}` — **仅适用于 Retain**：根据每条存入项目自身的 `metadata` 选择成员。详见下文[元数据路由](#metadata-routing)。

```bash
# Primary OpenAI, failover to Groq then Anthropic
export HINDSIGHT_API_LLM_PROVIDER=openai
export HINDSIGHT_API_LLM_API_KEY=sk-...
export HINDSIGHT_API_LLM_1_PROVIDER=groq
export HINDSIGHT_API_LLM_1_API_KEY=gsk-...
export HINDSIGHT_API_LLM_2_PROVIDER=anthropic
export HINDSIGHT_API_LLM_2_API_KEY=sk-ant-...
export HINDSIGHT_API_LLM_STRATEGY='{"mode": "failover"}'

# Weighted round-robin: serve the primary 3x as often as member 1
export HINDSIGHT_API_LLM_STRATEGY='{"mode": "round-robin", "weights": [3, 1]}'
```

#### 元数据路由 {#metadata-routing}

`{"mode": "metadata"}` 会根据每条存入项目自身的元数据，为其选择链中的成员，因此同一部署可以用不同模型提取不同文档：

```bash
export HINDSIGHT_API_LLM_PROVIDER=openai
export HINDSIGHT_API_LLM_API_KEY=sk-...
export HINDSIGHT_API_LLM_1_PROVIDER=ollama
export HINDSIGHT_API_LLM_1_MODEL=qwen3:8b
export HINDSIGHT_API_LLM_STRATEGY='{
  "mode": "metadata",
  "routes": [{"key": "classification", "value": "sensitive", "member": 1}]
}'
```

存入 `{"content": "...", "metadata": {"classification": "sensitive"}}` 时，会由本地 `qwen3:8b` 提取事实；其他内容使用主 LLM。

- **按每个项目匹配路由，并按声明顺序检查；首个匹配项生效。** 未匹配任何路由的项目使用成员 `0`（主 LLM）。
- **值会按字符串比较**，因为存入元数据是自由格式 JSON，而路由值来自环境变量：`"member": 1` 可匹配元数据中的 `1` 和 `"1"`。列表值只要有任意一项匹配即可，因此 `{"labels": ["pii", "eu"]}` 会匹配 `labels` 为 `pii` 的路由。
- **不会存储路由选择。** 系统在构建项目提取提示时才选择成员，不会持久化选择结果，因此修改路由只影响之后的存入操作。重新处理文档时会沿用原始元数据，因而会再次按相同方式路由。
- **每个存入项目对应一个提取提示**，所以同一批次混合不同路由的项目没有问题；每个项目都会发送给各自的成员。

**此功能的边界。** 元数据路由决定*由哪个模型提取文档*，但它不构成数据隔离：从路由文档中提取的事实仍会与其他内容一起存入同一个银行；召回、反思、整合、心智模型刷新和试运行提取仍使用主 LLM。如果需要让文档内容完全不经过某个提供方，请使用单独的银行并为其配置专用 LLM。

还有两项限制：

- **`update_mode: "append"` 会根据追加调用时提供的元数据进行路由**，而不是根据已存储文档的元数据。追加操作会将已存储的正文与新文本一起重新提取，因此若要继续使用同一成员，请重新提供相同的元数据。
- 此模式**不支持批量存入**。`HINDSIGHT_API_RETAIN_BATCH_ENABLED=true` 会将一次操作中的所有项目作为单个任务提交给一个成员，无法满足逐项目路由，因此启动时会拒绝此组合。

**按操作配置链。** 每项操作都可以通过 `RETAIN` / `REFLECT` / `CONSOLIDATION` / `MENTAL_MODEL_REFRESH` 前缀配置各自的成员和策略（例如 `HINDSIGHT_API_RETAIN_LLM_1_PROVIDER`、`HINDSIGHT_API_RETAIN_LLM_STRATEGY`）。若某项操作未配置索引成员或未设置策略，就会继承全局链；但 `MENTAL_MODEL_REFRESH` 会继承 reflect 链。

索引成员属于凭据字段，不会由银行配置 API 返回，而且只能在服务器级别配置（不能按银行单独配置）。**批量存入**会按声明顺序选择首个支持批处理的成员，该成员不一定是主 LLM。因此，即使主 LLM 没有批量 API，只要链中的某个成员支持，就仍可启用 `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true`。整个批次都会由该成员处理（提交、轮询和取回操作都使用持有该批次的账户），因此批处理不会像交互式存入、反思和整合调用那样故障转移。正在执行的批次会绑定到提交它的账户，因此即使工作进程在批次处理中重启，也会继续使用该账户，即便此时链的顺序已改变或成员已扩充。如果批次仍在运行时移除了该成员或轮换了它的 API 密钥，操作会明确报错，而不会改为轮询其他账户。

**链内重试。** 故障转移链本身就是一种重试：某个成员失败后，系统会尝试下一个成员。先重试非末尾成员只会延迟切换；如果它因过载而失败，立即重试很可能仍会以相同方式失败。末尾成员则相反：它无法再故障转移，因此其重试次数是防止暂时性错误导致请求失败的唯一保障，也是在此处遵循 `Retry-After` 最有价值。单一的全操作 `MAX_RETRIES` 无法同时表达这两种需求，因此可将 `HINDSIGHT_API_LLM_MAX_RETRIES=0` 设为快速故障转移，再通过 `HINDSIGHT_API_LLM_<n>_MAX_RETRIES` 为末尾成员单独设置重试次数。

### 内置 llama.cpp {#built-in-llamacpp}

`llamacpp` 提供方会将 llama.cpp 服务器作为受管理的子进程运行，无需外部 LLM 服务器。首次运行时，会将默认 GGUF 模型（约 3.5 GB）自动下载到 `~/.hindsight/models`。需要安装 `local-llm` 扩展：`pip install 'hindsight-api-slim[local-llm]'`。

:::warning Docker 镜像中不可用
发布的 `ghcr.io/vectorize-io/hindsight` 镜像有意不包含 llama.cpp，因此无法在镜像中运行 `HINDSIGHT_API_LLM_PROVIDER=llamacpp`；程序会立即失败并提示原因。

如需在 Docker 中进行本地推理，请将 llama.cpp 作为独立容器运行，并通过 `HINDSIGHT_API_LLM_PROVIDER=openai` 和 `HINDSIGHT_API_LLM_BASE_URL` 将 Hindsight 指向其兼容 OpenAI 的 API。可直接运行的配置见 [`docker/docker-compose/local-llm/`](https://github.com/vectorize-io/hindsight/tree/main/docker/docker-compose/local-llm)。
:::

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_LLAMACPP_MODEL_PATH` | GGUF 模型文件的路径。未设置时，会从 HuggingFace 自动下载 `gemma-4-E2B-it-Q4_K_M`。 | 自动下载 |
| `HINDSIGHT_API_LLAMACPP_GPU_LAYERS` | 卸载到 GPU 的层数。`-1` = 所有层（推荐）；`0` = 仅使用 CPU。 | `-1` |
| `HINDSIGHT_API_LLAMACPP_CONTEXT_SIZE` | 上下文窗口的 token 数。 | `8192` |
| `HINDSIGHT_API_LLAMACPP_CHAT_FORMAT` | 聊天模板格式。`null` = 根据 GGUF 元数据自动检测（推荐）。 | 自动检测 |
| `HINDSIGHT_API_LLAMACPP_NO_GRAMMAR` | 禁用 JSON 语法约束。推理速度更快，但 JSON 输出的可靠性会降低。 | `false` |
| `HINDSIGHT_API_LLAMACPP_EXTRA_ARGS` | 传递给 llama.cpp 服务器的额外 CLI 参数，以空格分隔（例如 `--n_threads 8 --type_k 1`）。 | - |

```bash
# Minimal setup (auto-downloads model, uses GPU)
export HINDSIGHT_API_LLM_PROVIDER=llamacpp

# Custom model with tuning
export HINDSIGHT_API_LLM_PROVIDER=llamacpp
export HINDSIGHT_API_LLM_MAX_CONCURRENT=2
export HINDSIGHT_API_LLAMACPP_MODEL_PATH=~/.hindsight/models/my-model.gguf
export HINDSIGHT_API_LLAMACPP_CONTEXT_SIZE=16384
export HINDSIGHT_API_LLAMACPP_NO_GRAMMAR=true  # faster, less reliable JSON
export HINDSIGHT_API_LLAMACPP_EXTRA_ARGS="--n_threads 8"
```

:::note
llama.cpp 服务器由所有 LLM 操作共享（存入、反思、整合）。将 `HINDSIGHT_API_LLM_MAX_CONCURRENT=2` 设为 2，可让存入与整合并发运行，避免彼此阻塞。

自动下载的模型存放在 `~/.hindsight/models`。请将该目录放在持久化存储中；若重启时目录被清除，每次重启都会重新下载整个模型。
:::

| `HINDSIGHT_API_MENTAL_MODEL_REFRESH_LLM_MAX_BACKOFF` | 刷新重试的最大退避时间 | 回退到 `HINDSIGHT_API_REFLECT_LLM_MAX_BACKOFF` |
| `HINDSIGHT_API_MENTAL_MODEL_REFRESH_LLM_TIMEOUT` | 刷新请求的超时时间（秒）。后台刷新时没有调用方等待，因此通常会将此超时设得比反思超时长得多。 | 回退到 `HINDSIGHT_API_LLM_TIMEOUT`，绝不回退到 `HINDSIGHT_API_REFLECT_LLM_TIMEOUT`（后者按调用方等待回答的时长设置） |

**自动刷新心智模型。** 整合完成后运行的后台刷新会驱动与交互式反思相同的智能体，因此默认使用反思 LLM，无需设置上文提到的变量。之所以提供 `MENTAL_MODEL_REFRESH_LLM_*` 变量组，是因为在单 GPU 自托管环境中，两者的取舍方向相反：交互式反思优先考虑推理能力（因为有人正等待高质量结果），而后台刷新更适合使用快速、无需思考的模型，以免超过墙钟超时时限、耗尽推理链的 completion token 预算，或因同时运行而使交互式解码速度减半。每个字段都会回退到对应的 `REFLECT_LLM_*` 字段，而后者再回退到全局 `LLM_*` 设置；全部不设置时，行为与之前完全相同。

:::tip 适合使用按操作配置的场景
- **存入**：使用结构化输出能力强的模型（例如 GPT-4o、Claude），以准确提取事实。
- **反思**：使用更快或成本更低的模型（例如 GPT-4o-mini、Groq）进行推理和回答生成。
- **心智模型刷新**：在共享或本地硬件上，指定无需思考或成本较低的托管模型，避免后台任务影响交互式反思。
- **召回**：不使用 LLM（纯检索），无需配置。
:::

**示例：为存入和反思分别配置模型**

```bash
# Default LLM (used as fallback)
export HINDSIGHT_API_LLM_PROVIDER=openai
export HINDSIGHT_API_LLM_API_KEY=sk-xxxxxxxxxxxx
export HINDSIGHT_API_LLM_MODEL=gpt-4o

# Use GPT-4o for retain (strong structured output)
export HINDSIGHT_API_RETAIN_LLM_MODEL=gpt-4o

# Use faster/cheaper model for reflect
export HINDSIGHT_API_REFLECT_LLM_PROVIDER=groq
export HINDSIGHT_API_REFLECT_LLM_API_KEY=gsk_xxxxxxxxxxxx
export HINDSIGHT_API_REFLECT_LLM_MODEL=llama-3.3-70b-versatile
```

**示例：调整受速率限制 API 的重试行为**

```bash
# For Anthropic with tight rate limits (10k output tokens/minute)
export HINDSIGHT_API_LLM_PROVIDER=anthropic
export HINDSIGHT_API_LLM_API_KEY=sk-ant-xxxxxxxxxxxx
export HINDSIGHT_API_LLM_MODEL=claude-sonnet-4-20250514

# Reduce concurrent requests for retain to avoid rate limits
export HINDSIGHT_API_RETAIN_LLM_MAX_CONCURRENT=3

# Fail faster with fewer retries
export HINDSIGHT_API_RETAIN_LLM_MAX_RETRIES=3

# Or increase backoff times to wait out rate limit windows
export HINDSIGHT_API_RETAIN_LLM_INITIAL_BACKOFF=2.0  # Start at 2s instead of 1s
export HINDSIGHT_API_RETAIN_LLM_MAX_BACKOFF=120.0    # Cap at 2min instead of 1min
```

:::note 各操作的并发上限会与全局上限叠加
`HINDSIGHT_API_RETAIN_LLM_MAX_CONCURRENT`、`HINDSIGHT_API_REFLECT_LLM_MAX_CONCURRENT`、`HINDSIGHT_API_CONSOLIDATION_LLM_MAX_CONCURRENT` 和 `HINDSIGHT_API_MENTAL_MODEL_REFRESH_LLM_MAX_CONCURRENT` 会在 `HINDSIGHT_API_LLM_MAX_CONCURRENT` **之外**额外增加一层上限。一次存入调用同时计入存入上限和全局上限；若反思调用没有单独的操作上限，则只受全局上限约束。

若要为受速率限制的提供方预留实时聊天/反思容量，可将存入和整合上限设得低于全局值。例如，全局上限为 4、存入上限为 1、整合上限为 1 时，会留下两个无法被存入或整合占用的并发名额。心智模型刷新上限涵盖后台刷新、其试运行和增量操作，并独立于反思上限；在共享硬件上，限制此项可防止后台任务挤占交互式反思资源。

与按操作配置的超时和重试/退避参数不同，`*_LLM_MAX_CONCURRENT` 上限是进程级信号量，在启动时从环境变量读取。它们只能在服务器级设置（不能按租户/银行覆盖），修改后需要重启。
:::

| `HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_ENCODING_FORMAT` | 嵌入响应的编码格式。设为空字符串可省略该参数（Voyage AI 和 Gemini 需要这样设置）。 | `float` |
| `HINDSIGHT_API_EMBEDDINGS_GEMINI_API_KEY` | 用于嵌入的 Gemini API 密钥（回退到 `HINDSIGHT_API_LLM_API_KEY`） | - |
| `HINDSIGHT_API_EMBEDDINGS_GEMINI_MODEL` | Gemini 嵌入模型。`gemini-embedding-2` 系列（例如 `gemini-embedding-2-preview`）同时支持 Gemini API 和 Vertex AI。Hindsight 会将每段文本分别作为独立输入发送，因此这些多模态模型会为每条事实返回一个向量，而不会把整个批次合并为单个嵌入。 | `gemini-embedding-001` |
| `HINDSIGHT_API_EMBEDDINGS_GEMINI_BATCH_SIZE` | 每个 `embed_content` 请求的文本数上限，也是客户端并发发送请求时使用的批次单位（参见 `HINDSIGHT_API_EMBEDDINGS_MAX_CONCURRENT_REQUESTS`） | `100` |
| `HINDSIGHT_API_EMBEDDINGS_GEMINI_OUTPUT_DIMENSIONALITY` | 输出嵌入维度（Gemini 支持配置维度） | `768` |
| `HINDSIGHT_API_EMBEDDINGS_GEMINI_FORCE_IPV4` | 强制 Gemini 嵌入客户端使用仅 IPv4 的 HTTP 传输。在 IPv6 出站连接不可用（例如某些 Docker/VPC 配置），且 AAAA DNS 记录导致长时间挂起时，此项很有用。 | `false` |
| `HINDSIGHT_API_EMBEDDINGS_VERTEXAI_PROJECT_ID` | 用于嵌入的 Vertex AI 项目 ID（回退到 `HINDSIGHT_API_LLM_VERTEXAI_PROJECT_ID`） | - |
| `HINDSIGHT_API_EMBEDDINGS_VERTEXAI_REGION` | 用于嵌入的 Vertex AI 区域（回退到 `HINDSIGHT_API_LLM_VERTEXAI_REGION`） | - |
| `HINDSIGHT_API_EMBEDDINGS_VERTEXAI_SERVICE_ACCOUNT_KEY` | 用于 Vertex AI 嵌入的服务账号密钥（回退到 `HINDSIGHT_API_LLM_VERTEXAI_SERVICE_ACCOUNT_KEY`） | - |

嵌入提供方选择、凭据、基础 URL、模型选项、维度、编码格式、批次大小和延迟模式都是静态的服务器级设置，不能按银行分层覆盖。上文的 ONNX 设置同样为静态配置，与现有的 `embeddings_local_*` 设置一致。

:::note 会区别处理搜索内容与存储文本的模型

部分嵌入模型训练时会要求在搜索内容前添加简短指令，而存储文本前不添加指令或使用另一条指令。使用 `local` 提供方时，Hindsight 会应用模型自带的指令，无需自行配置。默认的 `BAAI/bge-small-en-v1.5` 不带指令，因此现有部署的行为不会改变；`Qwen/Qwen3-Embedding-*` 则带有仅用于搜索的指令，这正是这些模型能准确检索的原因。

需要留意的少见情形是，模型也为**存储文本**规定了指令。切换到这类模型会改变新记忆的索引方式，因此已有内容采用了不同的索引方法，之后进行比较时效果会较差。采用这类模型后，请重新为银行建索引（导出再重新导入）。仅对搜索侧使用指令的模型（上文列出的模型均属此类）无需重新建索引。

大多数提供方无法像 `local` 那样自动发现这些指令。只接受纯文本并返回向量的远程端点（`tei`、`litellm`、`litellm-sdk`，以及兼容 OpenAI 的 `/embeddings` URL 后端，如 `llama-server`、`infinity-emb`、vLLM 等）只能收到文本，因此需要通过 `HINDSIGHT_API_EMBEDDINGS_QUERY_PREFIX` 和 `HINDSIGHT_API_EMBEDDINGS_PASSAGE_PREFIX` 自行提供指令。留空时会原样发送文本，这正是对称式托管模型所需的行为。

有两个提供方无需设置并会忽略这两个变量：`local`（应用模型自带的提示）和 `zeroentropy`（由 API 指定当前嵌入的是哪一侧）。`onnx` 提供方有自己的一对变量：`HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX` / `..._PASSAGE_PREFIX`，默认采用 E5 指令。

:::

#### 本地 ONNX 嵌入 {#local-onnx-embeddings}

ONNX 提供方使用 ONNX Runtime 在进程内运行嵌入模型。自行构建 API 环境时，请安装可选依赖：

```bash
pip install 'hindsight-api-slim[local-onnx]'
# or, in this repository:
uv sync --project hindsight-api-slim --extra local-onnx
```

CUDA 执行默认关闭。只有在安装了兼容的 `onnxruntime-gpu` wheel 以及 CUDA/cuDNN 运行时的环境中，才设置 `HINDSIGHT_API_EMBEDDINGS_ONNX_DEVICE=cuda`。官方镜像有意保留 CPU 运行时，避免在不使用此功能时增加镜像体积。若要部署到 Docker，可使用可直接构建的配置 [`docker/docker-compose/cuda-onnx/`](https://github.com/vectorize-io/hindsight/tree/main/docker/docker-compose/cuda-onnx)，该配置会在基于 slim 镜像的私有镜像中安装 GPU wheel：

```bash
docker compose -f docker/docker-compose/cuda-onnx/docker-compose.yaml up --build
```

该配置支持通过 `BASE_IMAGE`、`ONNXRUNTIME_GPU_VERSION` 和 `HINDSIGHT_API_EMBEDDINGS_ONNX_CUDA_DEVICE_ID` 选择发布版本、运行时和设备。如果请求使用 CUDA，但提供方不可用或初始化后的会话没有启用 CUDA，Hindsight 会在启动时失败；此模式下不会静默回退到 CPU。配置会在私有镜像中安装 CUDA/cuDNN 库；主机需要兼容的 NVIDIA 驱动并启用 GPU 透传。个别算子仍可能通过常规图分区在 CPU 上运行。有关依赖隔离、构建未发布版本的代码库以及真实 GPU 测试，请参阅[配置 README](https://github.com/vectorize-io/hindsight/tree/main/docker/docker-compose/cuda-onnx)。

你可以设置 `HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID`，让 Hindsight 在启动时从 Hugging Face 下载模型；也可以预先将 ONNX 计算图和分词器文件下载到 Hindsight 仓库根目录下。

```bash
cd /path/to/hindsight
mkdir -p models

MODEL_ID=intfloat/multilingual-e5-small
MODEL_DIR=models/intfloat__multilingual-e5-small

uv run --project hindsight-api-slim --extra local-onnx python - <<'PY'
import os
from huggingface_hub import snapshot_download

snapshot_download(
    repo_id=os.environ["MODEL_ID"],
    local_dir=os.environ["MODEL_DIR"],
    allow_patterns=[
        "onnx/model.onnx",
        "onnx/model.onnx_data",
        "*.json",
        "*.txt",
        "*.model",
    ],
)
PY
```

然后启动 Hindsight，并使用相对于仓库根目录的路径：

```bash
export HINDSIGHT_API_EMBEDDINGS_PROVIDER=onnx
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_PATH=./models/intfloat__multilingual-e5-small/onnx/model.onnx
export HINDSIGHT_API_EMBEDDINGS_ONNX_TOKENIZER_NAME_OR_PATH=./models/intfloat__multilingual-e5-small
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=384
export HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX="query: "
export HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX="passage: "
```

对于 Docker 部署，请挂载相同的模型目录并使用容器内路径：

```yaml
services:
  hindsight:
    volumes:
      - ./models:/app/models:ro
    environment:
      HINDSIGHT_API_EMBEDDINGS_PROVIDER: onnx
      HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_PATH: /app/models/intfloat__multilingual-e5-small/onnx/model.onnx
      HINDSIGHT_API_EMBEDDINGS_ONNX_TOKENIZER_NAME_OR_PATH: /app/models/intfloat__multilingual-e5-small
      HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS: "384"
      HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX: "query: "
      HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX: "passage: "
```

按模型区分的示例：

```bash
# sentence-transformers/all-MiniLM-L6-v2: 384 dimensions, no E5 prefixes
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID=sentence-transformers/all-MiniLM-L6-v2
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=384
export HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX=""
export HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX=""

# intfloat/multilingual-e5-small: 384 dimensions, keep E5 prefixes
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID=intfloat/multilingual-e5-small
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=384
export HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX="query: "
export HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX="passage: "

# sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2: 384 dimensions, no E5 prefixes
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID=sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=384
export HINDSIGHT_API_EMBEDDINGS_ONNX_QUERY_PREFIX=""
export HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX=""

# BAAI/bge-m3: 1024 dimensions, no E5 prefixes; keep onnx/model.onnx_data next to model.onnx
export HINDSIGHT_API_EMBEDDINGS_ONNX_MODEL_ID=BAAI/bge-m3
export HINDSIGHT_API_EMBEDDINGS_ONNX_DIMENSIONS=1024

export HINDSIGHT_API_EMBEDDINGS_ONNX_PASSAGE_PREFIX=""
```

:::warning
请勿在同一个向量索引中混用不同模型生成的嵌入。从 `local` 切换到 `onnx`，或更换 ONNX 模型后，即使向量维度恰好相同，也必须重新嵌入现有记忆/文档。例如，`BAAI/bge-small-en-v1.5` 和 `intfloat/multilingual-e5-small` 都会生成 384 维向量，但它们的嵌入空间在语义上无法比较。
:::

:::warning
默认 ONNX 查询/文档前缀（`query: ` 和 `passage: `）适用于 E5 模型。对于 MiniLM、BGE 等非 E5 模型，请清空这两个前缀变量，否则 Hindsight 会为未按此格式训练的模型添加 E5 风格文本。
:::

#### 常见问题：提供方专用的嵌入环境变量名称 {#common-pitfall-provider-specific-embedding-env-var-names}

嵌入环境变量的键名中包含提供方字段：

`HINDSIGHT_API_EMBEDDINGS_{PROVIDER}_{PARAMETER}`

例如，设置 `HINDSIGHT_API_EMBEDDINGS_PROVIDER=openai` 时：

| 错误 | 正确 |
|---|---|
| `HINDSIGHT_API_EMBEDDINGS_BASE_URL` | `HINDSIGHT_API_EMBEDDINGS_OPENAI_BASE_URL` |
| `HINDSIGHT_API_EMBEDDINGS_MODEL` | `HINDSIGHT_API_EMBEDDINGS_OPENAI_MODEL` |
| `HINDSIGHT_API_EMBEDDINGS_API_KEY` | `HINDSIGHT_API_EMBEDDINGS_OPENAI_API_KEY` |

这与 LLM 变量不同；LLM 变量采用 `HINDSIGHT_API_LLM_{PARAMETER}` 格式，不包含提供方字段。

:::warning
若嵌入变量名称错误，Hindsight 可能会回退到默认的 OpenAI 嵌入设置（例如 `text-embedding-3-small`），并因向错误端点进行身份验证而失败。
:::

#### 嵌入维度 {#embedding-dimensions}

Hindsight 会在启动时自动检测模型的嵌入维度，并据此调整数据库 schema。默认模型（`BAAI/bge-small-en-v1.5`）会生成 384 维向量，而 OpenAI 模型会生成 1536 或 3072 维向量。

对于 `litellm-sdk`，若设置了 `HINDSIGHT_API_EMBEDDINGS_LITELLM_SDK_OUTPUT_DIMENSIONS`，且底层提供方支持 LiteLLM 的 `dimensions` 参数，启动时会使用指定的输出维度；否则行为不变。下方关于维度变更的规则同样适用。

对于 `zeroentropy`，`zembed-1` 支持 `2560`、`1280`、`640`、`320`、`160`、`80` 和 `40` 维。ZeroEntropy API 默认使用 `2560`；Hindsight 默认使用 `1280`，以兼容默认 pgvector HNSW 索引。若向量扩展支持更高维索引（例如 DiskANN/pgvectorscale 或 ScaNN），可使用 `2560`。

:::warning 维度变更
存入记忆后，不能在不丢失数据的情况下更改嵌入维度。如果需要切换到维度不同的模型：

1. **数据库为空**：启动时会自动调整 schema。
2. **已有数据**：先删除所有记忆，或改用维度相同的模型。

OpenAI 支持的嵌入维度：
- `text-embedding-3-small`：1536 维
- `text-embedding-3-large`：3072 维
- `text-embedding-ada-002`：1536 维（旧版）

Google 的 `gemini-embedding-001` 原生生成 3072 维向量，但支持配置输出维度。设置 `HINDSIGHT_API_EMBEDDINGS_GEMINI_OUTPUT_DIMENSIONALITY` 可调整输出大小（默认值：768）。

ZeroEntropy 的 `zembed-1` 支持 Matryoshka 维度：`2560`、`1280`、`640`、`320`、`160`、`80` 和 `40`。该提供方在 Hindsight 中的默认维度为 `1280`。
:::

### 重排器 {#reranker}

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|

#### 重排器故障转移链 {#reranker-failover-chain}

重排器是检索结果的细化阶段，但默认情况下，无法连接重排器会导致整个召回失败。可通过索引配置额外的重排器；Hindsight 会按顺序尝试：某成员失败（超时、连接错误、HTTP 错误或响应不可用）时，下一个成员会处理该请求。

未带索引的 `HINDSIGHT_API_RERANKER_*` 配置是**主成员**（成员 0）。额外成员从 1 开始编号，每个成员 `n` 的所有设置都使用相同索引，即对上表中任意 `<SETTING>` 使用 `HINDSIGHT_API_RERANKER_<n>_<SETTING>`：

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_RERANKER_<n>_PROVIDER` | 故障转移成员 `n` 的提供方（`n` = 1、2……）。设置此变量即定义该成员；索引必须从 1 开始连续编号。未设置 = 不启用故障转移（默认）。 | - |
| `HINDSIGHT_API_RERANKER_<n>_<SETTING>` | 成员 `n` 的任意其他重排器设置，例如 `HINDSIGHT_API_RERANKER_1_TEI_URL`、`HINDSIGHT_API_RERANKER_1_COHERE_API_KEY`、`HINDSIGHT_API_RERANKER_1_TEI_HTTP_TIMEOUT`。 | 与主成员相同的内置默认值 |

索引成员会**独立读取**：不会继承主成员的设置，也不会继承共享提供方密钥（如 `HINDSIGHT_API_COHERE_API_KEY`），因此需要为其填写所有必需设置。未设置的参数会采用与主成员相同的内置默认值。链级设置（`HINDSIGHT_API_RERANKER_MAX_CANDIDATES`、`HINDSIGHT_API_RERANKER_SEND_BANK_AS_HEADER`）保持全局，不使用索引。

```bash
# Primary: a self-hosted reranker that is not always up.
export HINDSIGHT_API_RERANKER_PROVIDER=tei
export HINDSIGHT_API_RERANKER_TEI_URL=http://workstation:8081

# Member 1: a hosted reranker to fall back on.
export HINDSIGHT_API_RERANKER_1_PROVIDER=cohere
export HINDSIGHT_API_RERANKER_1_COHERE_API_KEY=...

# Member 2: last resort — no reranking, keep the fusion order rather than fail.
export HINDSIGHT_API_RERANKER_2_PROVIDER=rrf
```

若以 `rrf` 作为链的末尾成员，召回会**开放式失败**：返回结果仍按各检索阶段生成的顺序排列，就像未配置重排器一样，而不会让请求失败。若没有 `rrf` 成员，或所有成员都不可用，则仍会报错，这是默认行为。

注意：

- 每次请求都会按顺序尝试成员；系统没有熔断器，因此故障成员会在切换到下一个成员前消耗自身的超时时间。请将不可靠主成员的超时设短（使用 `HINDSIGHT_API_RERANKER_TEI_HTTP_TIMEOUT` 和各提供方的 `*_TIMEOUT` 设置）。
- 启动时无法初始化的成员只会记录日志，不会导致启动失败；下次有请求路由到该成员时会再次尝试初始化。
- 不同提供方的分数不可直接比较（有的返回校准后的 `[0, 1]` 相关性分数，有的返回 logits），因此由故障转移成员处理的请求可能与主成员处理的请求得分不同。故障转移会以 `WARNING` 级别记录。
- 索引成员属于凭据字段，不会由银行配置 API 返回，并且只能在服务器级别配置（不能按银行单独配置）。

:::tip 配置 TEI 重排器容量

TEI 会为重排请求中的每段文本预留一个槽位；池满时会直接拒绝请求。因此启动时至少应配置
`HINDSIGHT_API_RERANKER_TEI_MAX_CONCURRENT × HINDSIGHT_API_RERANKER_TEI_BATCH_SIZE`
个槽位。按上方默认值计算为 1024 个，而 TEI 自身默认值为 512：

```bash
text-embeddings-router --max-concurrent-requests 2048 ...
```

低于这一阈值时，大量召回流量会导致重排器拒绝本可处理的任务。拒绝后会退避重试，因此池容量不足表现为召回变慢，而不是返回错误。

:::

#### LiteLLM 代理与 SDK 的区别 {#litellm-proxy-vs-sdk}

- **`litellm`**：需要单独运行 LiteLLM 代理服务器。适合集中配置、速率限制和缓存。
- **`litellm-sdk`**：无需代理，直接访问 API。配置更简单、延迟更低、基础设施组件更少。

两者支持相同的提供方：
- **Cohere**（`cohere/rerank-english-v3.0`、`cohere/rerank-multilingual-v3.0`）
- **DeepInfra**（`deepinfra/Qwen3-reranker-8B`、`deepinfra/bge-reranker-v2-m3`）
- **Together AI**（`together_ai/Salesforce/Llama-Rank-V1`）
- **HuggingFace**（`huggingface/BAAI/bge-reranker-v2-m3`）
- **Voyage AI**（`voyage/rerank-2`）
- **Jina AI**（`jina_ai/jina-reranker-v2`）
- **AWS Bedrock**（`bedrock/...`）

#### TypeSafe {#typesafe}

TypeSafe 并非 `/rerank` 端点。它会针对某个*状态*评估一组类型化的*问题*；此提供方会提出两个问题。

**排序 — 针对整个候选池提出一个问题。** Choice 会为每个选项返回一个概率，且所有概率之和为 1。因此 Hindsight 将候选项作为选项，并直接从答案读取排序：无论候选项有多少，都只需一次调用。在包含 200 个问题的 LoCoMo 数据集上，单次调用的 recall@1 达到 0.94，逐候选项调用则为 0.87，且调用次数仅为其三十分之一。

Choice 最多接受 255 个选项，因此候选池较大时会分轮排序，再对各轮胜出的候选项排序。每次调用内的概率都会归一化，因此不能直接拼接各轮结果。

**截断 — `HINDSIGHT_API_RERANKER_TYPESAFE_PRUNE_CANDIDATES=true`。** 第二个问题会对排序后的候选项列表评分，判断相关性延续到什么位置；该位置之后的候选项都会排除。召回随后按顺序仅返回相关候选项，不再返回其他内容。无需调整阈值，模型会自行选择截断深度。

使用 Score，而不是在 Choice 中加入“以上皆非”选项，是因为 Score 等级具有*顺序关系*，适合表示截断位置。作为 Choice 选项时，“以上皆非”只是与其他选项争夺概率质量的另一个选项；对于困难查询，它会直接胜出：200 个问题中有 35 个完全没有结果，而使用 Score 时一个都没有。

刻意不提供“没有任何内容相关”这一等级，因此始终至少会保留一个候选项。召回是在检索已经判断为可能相关的候选池中运行；对调用方而言，一条较弱的记忆也比完全没有结果好。

默认关闭此标志，因为它会显著缩减召回返回的内容。若消费方是 LLM 提示（例如反思），且每条无关记忆都会浪费上下文，则可启用。

**分数表示位置，而非置信度。** Choice 概率是候选池内的比例：`0.7` 表示“这些候选项里它最好”，而非“它相关”；两个候选池的分数也不可比较。因此提供方返回的是排名位置，超过截断位置的候选项分数恰为 `0.0`。

#### Jina MLX（Apple Silicon） {#jina-mlx-apple-silicon}

`jina-mlx` 提供方使用针对 Apple Silicon 优化的 [`jinaai/jina-reranker-v3-mlx`](https://huggingface.co/jinaai/jina-reranker-v3-mlx)。模型约 1.2 GB，会在首次启动时从 HuggingFace Hub 自动下载并缓存到本地。

`mlx` 是 Apple 的 Metal 框架，因此 `local-ml` 扩展只会在 Apple Silicon 上安装它；其 Linux 版本仅使用 CPU，速度比 `local` 提供方慢。若在其他平台选择 `jina-mlx`，除非自行安装 `mlx` / `mlx-lm`，否则启动会失败。

### 身份验证 {#authentication}

默认情况下，Hindsight 不启用身份验证。生产环境中，请使用内置租户扩展启用 API 密钥身份验证：

```bash
# Enable the built-in API key authentication
export HINDSIGHT_API_TENANT_EXTENSION=hindsight_api.extensions.builtin.tenant:ApiKeyTenantExtension
export HINDSIGHT_API_TENANT_API_KEY=your-secret-api-key
```

启用后，所有请求都必须在 `Authorization` 标头中包含 API 密钥：

```bash
curl -H "Authorization: Bearer your-secret-api-key" \
  http://localhost:8888/v1/default/banks
```

未提供有效 API 密钥的请求会收到 `401 Unauthorized` 响应。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_TENANT_EXTENSION` | 已加载租户扩展的点分路径。设置为 `hindsight_api.extensions.builtin.tenant:ApiKeyTenantExtension`，即可要求每个请求都提供 API 密钥。 | *（无；身份验证已禁用）* |
| `HINDSIGHT_API_TENANT_API_KEY` | 内置 API 密钥扩展检查的共享 API 密钥。客户端通过 `Authorization: Bearer <key>` 发送。 | *（无）* |
| `HINDSIGHT_API_EXTENSION_PASSTHROUGH_HEADERS` | 以逗号分隔的请求标头列表，这些标头会复制到 `RequestContext.extra_headers` 供扩展读取，匹配时不区分大小写。留空时，扩展只能看到 `Authorization` 标头。 | *（无）* |

若要启用 Memory Defense，请参阅 `docs/developer/memory-defense/`，了解策略 schema、检测器目录和审计记录。

#### 向扩展转发额外标头 {#forwarding-extra-headers-to-extensions}

自定义 `TenantExtension` 通常只能通过 `RequestContext.api_key` 读取 `Authorization` 标头。当 bearer token 标识的是*代理*而非调用方时，这还不够。例如，身份验证网关向 Hindsight 提供一个共享服务身份，并在另一个标头中携带每个调用方的身份。

将需要转发的标头列出：

```bash
export HINDSIGHT_API_EXTENSION_PASSTHROUGH_HEADERS=x-user-assertion,x-request-origin
```

这些标头会在 HTTP 和 MCP 传输中以小写名称为键，出现在 `RequestContext.extra_headers` 中；它们也会与请求上下文的其余内容一起传递到 `OperationValidatorExtension` 钩子。只会包含请求中实际存在且已列出的标头。默认不设置此项，因此除非显式启用，扩展不会收到任何标头数据。

若某个已列出的标头在请求中**出现多次**，系统会丢弃该标头并记录警告，而不会从多个值中任选其一，因此重复标头绝不会悄悄覆盖代理注入的值。通过此方式转发的标头是否可信，取决于 Hindsight 前置代理的行为：只应列出由该代理设置、且代理会移除客户端同名标头的字段。此设置只能在服务器级配置，不能按租户或银行覆盖。

:::tip 自定义身份验证
如需高级身份验证（JWT、OAuth、多租户 schema），请实现自定义 `TenantExtension`。详见[扩展文档](./extensions.md)。
:::

### 出站代理 {#egress-proxy}

出站调用（LLM 提供方和网关、远程嵌入与重排器、文档解析器、Supabase 租户扩展）遵循标准代理环境变量：`HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY`。Hindsight 没有专用代理设置；请在进程启动前通过 pod 环境、systemd 单元或 shell 设置这些变量。

有三点需要注意：

- **代理 URL 必须使用 `http://`。** 对于 API 自身发起的 HTTP 调用（嵌入、重排器、解析器、直接访问的网关），`https://` 代理 URL 会被忽略并记录警告，`ALL_PROXY` / SOCKS 也会被丢弃。自带 HTTP 客户端的提供方 SDK（OpenAI、Anthropic）确实会读取 `ALL_PROXY`，但不应依赖它；请设置 `HTTP_PROXY` 和 `HTTPS_PROXY`。
- **将本地端点加入 `NO_PROXY`。** 系统不会自动排除任何端点，甚至包括 `localhost` 或 `127.0.0.1`。若部署设置了 `HTTP_PROXY`，同时运行本地 Ollama、LM Studio、llama.cpp 或 TEI，就必须将这些主机列入 `NO_PROXY`，否则请求会被发往代理。这也包括 Hindsight 自行启动的 llama.cpp 服务器：就绪探测始终直接连接，但之后的补全调用会通过 OpenAI SDK，并遵循代理设置。
- **`~/.netrc` 中的凭据也会应用到目标主机，而不只是代理。** 与提供方主机匹配的 netrc 条目不会覆盖 Hindsight 发送的 `Authorization` 标头；请求会直接失败并报错 `Cannot combine AUTHORIZATION header with AUTH argument`。请删除该条目，或将 `NETRC` 指向不含该条目的文件。

Webhook 发送有意忽略所有这些设置：它的 SSRF 防护会验证已解析的地址，而代理会连接到一个从未经过验证的地址。

| `HINDSIGHT_API_SEMANTIC_LINK_MIN_SIMILARITY` | 正常存入、流式存入和图维护重建链接时创建语义链接所需的最小余弦相似度，直接控制语义图密度。必须介于 `0` 和 `1` 之间。 | `0.7` |
| `HINDSIGHT_API_BM25_MIN_SCORE` | 候选行进入融合前必须超过的 BM25 最低分。对于 `vchord` 等会给所有文档排序，而非预筛出含查询词文档的后端，此项会过滤零分的不匹配行。`0` 仅保留真正匹配的词项；调高则要求更强匹配。 | `0` |
| `HINDSIGHT_API_RECALL_MAX_CANDIDATES_PER_SOURCE` | 每个检索来源（语义、BM25、图、时间）可贡献给 RRF 的候选项上限，在全局重排上限前应用，避免单个扩展过多的后端独占重排预算。`0` 禁用上限。 | `0` |
| `HINDSIGHT_API_RECALL_STRATEGY_BOOSTS` | 在召回时提高一个或多个检索来源的优先级，以逗号分隔的 `strategy:level` 列表配置（例如 `graph:high` 强烈优先图结果，或 `graph:high,bm25:low`）。策略：`semantic`、`bm25`、`graph`、`temporal`；级别：`low`（轻度，主要避免候选项在重排前被丢弃）、`medium`（中度）、`high`（强，来源会取得大多数重排预算）。候选池超过 `HINDSIGHT_API_RERANKER_MAX_CANDIDATES` 时，预筛选提升在排名空间中生效，不会改写 RRF 分数。比较一个被提升来源和另一个来源时，若提升来源候选项排名为 `r`、另一来源为 `s`，当 `r < divisor × s` 时它优先（divisor：`low` 为 2、`medium` 为 4、`high` 为 8）。这只是单来源比较，不保证融合列表的最终顺序，也不依赖池大小。交叉编码器重排后，每个受青睐候选项会获得附加分：来源排名为 1 时取该级别的完整值，之后随排名降低而递减（排名 1 的值：`low` 为 0.05、`medium` 为 0.2、`high` 为 0.5）；衰减使用相同 divisor 作为初始尺度，因此 `high` 到排名 9 时减半。`temporal` 是例外：它的排名主要表示记忆日期距查询日期范围中点的远近，并不代表范围内记忆之间的相关性，因此时间来源找到的每个候选项（包括其链接记忆）均获得完整加分，不考虑排名。其他来源会按排名衰减，以限制靠后结果的提升。任何来源的加分都不会限制最终排名变化，也不保证强直接匹配一定领先；两个来源的加分会相加。若重排器直通（召回模式 `rrf`、提供方名为 `rrf`，或故障转移链已降级到 `rrf`），则跳过重排后的加分。若候选池未超过上限，此项完全无效；若超过上限，则只影响进入池中的候选项，最终排序依据原始 RRF 以及新近度、时间和证据乘数。只提升显式列出的策略；未列出的策略维持正常权重，不会隐式提升。策略仅写名称（例如 `graph` 或 `graph:`）时默认级别为 `medium`。空值禁用功能。 | （空） |
| `HINDSIGHT_API_RECENCY_DECAY_FUNCTION` | 重排中新近度加分的形状，即如何将记忆年龄转为最终排名中的轻微新鲜度调整。`linear`（默认）从今天的最高新鲜度线性衰减到 `HINDSIGHT_API_RECENCY_DECAY_LINEAR_WINDOW_DAYS` 所定义的下限。`exponential` 使用半衰期：记忆年龄达到 `HINDSIGHT_API_RECENCY_DECAY_HALFLIFE_DAYS` 时视为中性（无加分或惩罚），较新记忆加分、较旧记忆扣分，且平滑衰减而非硬截断。`none` 完全禁用新近度影响。 | `linear` |
| `HINDSIGHT_API_RECENCY_DECAY_LINEAR_WINDOW_DAYS` | 线性衰减时，记忆从最新状态衰减到最低值所需天数。仅在 `HINDSIGHT_API_RECENCY_DECAY_FUNCTION=linear` 时使用。 | `365` |
| `HINDSIGHT_API_RECENCY_DECAY_HALFLIFE_DAYS` | 指数衰减时，记忆达到中性状态的年龄（天）；更年轻的记忆获得新近度加分，较旧记忆受到惩罚。值越小，越强烈地偏好最近记忆。仅在 `HINDSIGHT_API_RECENCY_DECAY_FUNCTION=exponential` 时使用。 | `90` |
| `HINDSIGHT_API_ENABLE_MENTAL_MODEL_HISTORY` | 追踪各心智模型内容变更历史（旧内容及时间戳），每次变更在 `mental_model_history` 表中存一行。设为 `false` 可完全关闭、不写入历史记录，减少审计历史不需要时的存储。**此项才是关闭功能的方法**（不是设置零上限）。 | `true` |
| `HINDSIGHT_API_MENTAL_MODEL_MIN_REFRESH_INTERVAL_SECONDS` | 同一心智模型两次*自动*刷新之间的最短间隔，适用于整合后触发器和 cron 计划。间隔内触发的刷新不会丢弃，而会排队并等待间隔结束；等待期间后续触发会合并到同一个排队刷新中，因此连续多次小规模存入只需刷新一次。银行持续摄取数据且模型无需每分钟更新时可调高；等待期间累积的内容仍会纳入刷新。显式刷新（API、MCP、控制平面）会忽略此下限并立即运行，也会释放其合并的排队刷新。`0` 表示无下限，每次触发都立即刷新。支持分层配置，可通过[配置 API](#hierarchical-configuration)按银行覆盖；也可按模型通过 `trigger.min_refresh_interval_seconds` 覆盖（后者优先，显式设为 `0` 可让某个频繁更新模型不受银行级下限限制）。 | `0` |
| `HINDSIGHT_API_KNOWLEDGE_PAGE_DEFAULT_TRIGGER` | 新建知识页的默认刷新设置，使用 JSON 对象与内置默认值合并（`{"mode": "delta", "fact_types": ["observation"], "exclude_mental_models": true, "refresh_after_consolidation": true}`）。只需设置要更改的字段，例如 `{"refresh_cron": "0 * * * *"}` 可让新页面改为每小时刷新，而不是每次整合后刷新。创建页面时传入的触发器优先；不会修改现有页面。可按银行配置。 | - |
| `HINDSIGHT_API_MENTAL_MODEL_HISTORY_MAX_ENTRIES` | 每个心智模型保留的历史行数上限。每次刷新都会将旧版本插入 `mental_model_history` 表，再删除超出上限的最旧记录，避免经常刷新时历史无限增长。设为 `0` 或负数会**取消上限**（每次刷新都增长且无界）；若要完全关闭历史，请设置 `HINDSIGHT_API_ENABLE_MENTAL_MODEL_HISTORY=false`。 | `50` |

五项依赖嵌入的阈值——主语义检索、图检索种子、时间检索、语义链接创建和观测去重——服务于不同的精确率/召回率取舍，因此有意分别配置。默认值是在 `BAAI/bge-small-en-v1.5` 上校准的行为。更换嵌入模型后，即使两种模型都返回归一化向量，余弦相似度分布也可能变化；投入生产前，请针对各自任务重新校准全部五项阈值。

调整 `HINDSIGHT_API_SEMANTIC_LINK_MIN_SIMILARITY` 不会追溯生效。新值会用于存入、流式存入或图维护期间创建的新语义链接；提高阈值后，维护任务不会删除低于新阈值的现有链接，降低阈值后，已有足够语义链接的节点也不会重新计算。若要让现有语义图完全符合新阈值，请重建图，或将源数据重新导入新的记忆库。

#### 图检索算法 {#graph-retrieval-algorithm}

- **`link_expansion`**（默认）：从语义种子出发，通过实体共现、语义 kNN 和因果链接快速扩展图。目标延迟低于 100 毫秒。

#### 召回预算映射 {#recall-budget-mapping}

召回请求接受 `budget` 参数（`low` / `mid` / `high`，默认为 `mid`），并将其映射为整数 `thinking_budget`，供每种检索方式（语义、BM25、图、时间）使用。以下配置项控制此映射。它们支持分层配置，可通过[配置 API](#hierarchical-configuration) 按银行覆盖。

提供两种函数：

- **`fixed`**（默认，保留旧行为）：`thinking_budget = recall_budget_fixed_<level>`（与 `max_tokens` 无关）。
- **`adaptive`**：`thinking_budget = round(max_tokens * recall_budget_adaptive_<level>)`，并限制在 `[recall_budget_min, recall_budget_max]` 范围内。调用方使用不同的 `max_tokens`，并希望检索广度随请求的输出大小变化时，适合采用此模式。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_RECALL_BUDGET_FUNCTION` | 映射函数：`fixed` 或 `adaptive`。 | `fixed` |
| `HINDSIGHT_API_RECALL_BUDGET_FIXED_LOW` | 函数为 `fixed` 且 `budget=low` 时，每种事实类型在每种检索方式中的项目数。 | `100` |
| `HINDSIGHT_API_RECALL_BUDGET_FIXED_MID` | 函数为 `fixed` 且 `budget=mid` 时，每种事实类型在每种检索方式中的项目数。 | `300` |
| `HINDSIGHT_API_RECALL_BUDGET_FIXED_HIGH` | 函数为 `fixed` 且 `budget=high` 时，每种事实类型在每种检索方式中的项目数。 | `1000` |
| `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_LOW` | 函数为 `adaptive` 且 `budget=low` 时，使用请求 `max_tokens` 的比例。 | `0.025` |
| `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_MID` | 函数为 `adaptive` 且 `budget=mid` 时，使用请求 `max_tokens` 的比例。 | `0.075` |
| `HINDSIGHT_API_RECALL_BUDGET_ADAPTIVE_HIGH` | 函数为 `adaptive` 且 `budget=high` 时，使用请求 `max_tokens` 的比例。 | `0.25` |
| `HINDSIGHT_API_RECALL_BUDGET_MIN` | 自适应函数经范围限制后的下限。 | `20` |
| `HINDSIGHT_API_RECALL_BUDGET_MAX` | 自适应函数经范围限制后的上限。 | `2000` |

#### 召回流水线阶段 {#recall-pipeline-stages}

召回会运行四条检索分支（语义、BM25、图、时间），然后通过交叉编码器对融合后的候选项重新排序。每个阶段都会增加延迟；若银行内容没有关系或时间结构，就会为无法发挥作用的检索分支付出代价。例如，银行以 `retain_extraction_mode: chunks` 导入，且仅作为普通检索使用。

以下配置项可分别关闭对应阶段。它们均支持分层配置，可通过[配置 API](#hierarchical-configuration) 按银行覆盖，因此某个银行可采用精简检索流程，而不改变部署中其他银行的召回行为。语义检索始终运行，是基础检索方式。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_ENABLE_TEXT_SEARCH` | 启用关键词（BM25）检索分支。设为 `false` 后将只进行**纯向量搜索**：该分支会从查询中完全移除，而不是筛选为空，因此其 SQL、查询分词和 `pg_stats` 词项选择查询都会跳过。知识页搜索也会移除关键词分支。 | `true` |
| `HINDSIGHT_API_ENABLE_TEMPORAL_RETRIEVAL` | 启用时间检索分支。设为 `false` 后，还会跳过用于该分支的日期感知查询分析；没有识别到约束，就没有可用于筛选的条件。 | `true` |
| `HINDSIGHT_API_ENABLE_GRAPH_RETRIEVAL` | 启用实体/链接图遍历分支。设为 `false` 后会跳过相关查询，不返回图检索结果。 | `true` |
| `HINDSIGHT_API_ENABLE_RERANKING` | 使用交叉编码器对融合后的候选项重新排序。设为 `false` 后会直接返回 RRF 融合顺序，速度更快但精确度较低。 | `true` |

关闭全部四个阶段后，召回只剩一次向量查询，这是延迟最低的配置。

禁用文本搜索不会影响写入路径：`search_vector` 及其索引仍会维护，因此无需重新建索引即可重新启用该功能。原本要使用的[文本搜索后端](#text-search-extension)只是不再读取。

##### 与存入侧配合：纯检索（“RAG”）银行 {#pairing-with-the-retain-side-plain-retrieval-rag-banks}

这些召回开关只会移除*读取*路径上的工作。如果银行仅用于纯检索，写入路径也应相应配置；否则仍会执行召回不再使用的 LLM 工作：

- **`retain_extraction_mode: chunks`** 完全跳过 LLM 事实提取，并按原样存储每个文本块。此模式会在获取任何 LLM 队列或锁之前返回，因此移除了存入操作中的 LLM 调用，而不只是缩短调用——这通常是摄取的主要成本。
- **`enable_observations: false`** 会跳过整合，即另一项后台 LLM 工作。

同时配置两侧后，银行就像传统向量存储：写入文本块、执行混合搜索，读写路径都不使用 LLM。可在一次调用中设置这两侧：

| `HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE` | 存入长文档时，每个流式批次的文本块数上限。每块约生成 17 条事实，因此默认 100 块约为每批 1700 条事实。大型文档可调低以限制内存和 LLM 负载；小块文档可调高。可按银行配置。 | `100` |
| `HINDSIGHT_API_RETAIN_MEMORY_BUDGET_MB` | 单个存入操作可持有的“已提取但尚未写入”状态的最大 MB 数。`HINDSIGHT_API_RETAIN_CHUNK_BATCH_SIZE` 限制同时处理的文本块数，却不限制其权重（每个文本块可能包含任意数量的提取事实），因此该变量提供了用于规划工作进程容量的上限：无论文档大小如何，每次存入的峰值大致不会超过此值。请按 `WORKER_MAX_SLOTS` 个并发存入操作规划预算。超出预算时，提取会等待写入路径追上，而不是继续占用内存。设为 `0` 可禁用此限制，恢复仅按文本块数量限制。 | `128` |
| `HINDSIGHT_API_RETAIN_ENTITY_LOOKUP` | 存入操作如何为提取出的名称查找现有实体*候选项*：`trigram` 会通过 pg_trgm 索引查找相似名称；`full` 会加载银行中的所有实体，仅保留名称完全匹配或互为子串的实体。两种方式之后都会执行相同的评分流程（参见[实体消解的判断方式](#how-entity-resolution-decides)）；因此这不只是性能选择，也会改变哪些名称有机会合并。 | `trigram` |
| `HINDSIGHT_API_RETAIN_ENTITY_RESOLUTION_BATCH_SIZE` | 每个模糊候选项查询包含的唯一实体名称数上限（PG 上使用 `trigram`，Oracle 上使用 `oracle_fuzzy`）。限制查询大小，避免实体较多的银行中超宽存入批次导致单个 `unnest(...)` 联接超时。 | `100` |
| `HINDSIGHT_API_RETAIN_ENTITY_RESOLUTION_MAX_CANDIDATES` | 每次实体提及参与评分的候选项上限。模糊查找会在评分前按 trigram / Jaro-Winkler 相似度排序，每个名称仅保留得分最高的指定数量。银行中若有数千个相似名称，不设上限的候选集会让一次存入消耗数分钟 CPU，并阻塞工作进程的健康检查；排名低于前约 100 的匹配项实际上也不会胜出。只有在本应合并的实体被重复创建时才调高。 | `200` |
| `HINDSIGHT_API_RETAIN_DEFAULT_STRATEGY` | 默认存入策略名称。设置后，未显式传入 `strategy` 参数的所有存入调用都会使用该策略。 | - |
| `HINDSIGHT_API_RETAIN_BATCH_POLL_INTERVAL_SECONDS` | 已提交的批处理任务运行期间，存入操作等待 LLM 提供方 Batch API 状态检查的间隔。它不是工作进程或摄取参数——不会控制 Hindsight 获取待处理存入任务的频率（参见[分布式工作进程](#distributed-workers)中的 `HINDSIGHT_API_WORKER_POLL_INTERVAL_MS`），且仅在使用提供方批处理模式时生效。设为 `0` 并不会禁用轮询，而是完全取消等待，以紧密循环持续查询提供方状态端点。 | `60` |
| `HINDSIGHT_API_STORE_DOCUMENT_TEXT` | 将原始源文本与提取出的记忆一起持久化。设为 `false` 可跳过存储（`documents.original_text` 为 NULL，`chunks.chunk_text` 为空）。支持分层配置，可通过[配置 API](#hierarchical-configuration) 按银行覆盖，使注重数据最小化的银行只保留派生事实，而其他银行仍可保存原始文本。 | `true` |
| `HINDSIGHT_API_FAIL_ON_EXTRACTION_ERRORS` | 设为 `true` 时，任何累计了事实提取错误的存入操作都会标记为 `failed`（错误消息包含错误数量），而非 `completed`，从而将静默丢弃事实的情况明确报告为失败。默认值保留现有行为。此项为静态服务器级设置。 | `false` |

> **支持批处理的提供方。** `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true` 仅适用于实现了批处理 API 的存入 LLM 提供方：`openai`、`groq`、`gemini` 和 `fireworks`。批处理必须搭配异步存入（`async=true`）；启用批处理时执行同步存入会报错。其他提供方会在启动时快速失败。
>
> **Gemini** 使用 [Gemini Batch API](https://ai.google.dev/gemini-api/docs/batch-api)（输入和输出均享 50% 固定折扣，SLA 为 24 小时，通常只需几分钟）。除 `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true` 和基于 API 密钥的 `gemini` 提供方外，无需其他设置。Vertex AI（`vertexai`）不支持批处理。

#### 存入中的内嵌附件 {#inline-attachments-in-retain}

存入项目的 `content` 可以是普通字符串（原有格式），也可以是由文本、图像和文件块组成的有序列表，以便附件出现在其实际所在位置：

```json
{
  "content": [
    {"type": "text",  "text": "To reset the VPN, click the button shown:"},
    {"type": "image", "source": {"type": "base64", "media_type": "image/png", "data": "..."}},
    {"type": "text",  "text": "...then reconnect."},
    {"type": "file",  "source": {"type": "base64", "media_type": "application/pdf", "data": "..."},
                      "filename": "escalation-policy.pdf"}
  ]
}
```

关键在于*位置*。提取时会将交错排列的文本和附件一起交给视觉模型，因此模型看到的是出现在介绍截图的句子旁边的截图，而不是你预先生成的图片说明。这与 Hindsight 对文本的一贯处理方式相同：传入原始内容，并由提取器负责理解。

`image` 和 `file` 是分开的类型，因为各提供方对两者的处理方式不同——Anthropic 区分图像块和文档块，OpenAI 则区分 `image_url` 和文件片段。因此，保留调用方提供的类型信息，可避免转换时仅凭媒体类型猜测。

这与 [`POST /files/retain`](#file-processing) 不同；后者会将整个文件转换为 Markdown，作为一份**独立**文档存储。如果希望解析扫描版 PDF 和办公文档，而不是让模型直接查看它们，仍应使用后者；但它会将文件内容与周围的文字分开。

**接受的类型。** 任何格式正确的 `type/subtype` 都会被接受，没有允许列表：模型能否读取某种格式，应由模型来决定；若提供方拒绝该格式，存入操作会返回提供方自己的错误，比在入口处猜测更有用。返回附件字节时会使用调用方声明的 Content-Type。

:::warning
由于声明的类型会原样用于提供服务，存入活动内容（如 SVG 或 HTML 文件）的银行写入者，可能在获取内容时让其在数据平面源站中执行。请将银行写入权限视同在该源站托管内容的权限。
:::

字节数据的处理方式：

- 附件会计算 sha256 哈希，并按**内容寻址**方式存储在包含它的文档下。因此相同字节始终对应相同 ID；同一文档中重复出现的附件只存储一次；重新存入未更改的文档时不会产生操作。若两个**不同**文档包含相同附件，则各自保存一份副本——系统有意放弃跨文档去重，这样删除文档时无需确认是否还有其他文档需要这些字节。
- 附件使用与上传文件相同的存储后端：`native`（PostgreSQL）、`s3`、`gcs`、`azure`。参见[文件存储](#file-storage)。
- 文档的存储文本会在附件所在处保留占位符（`⟦hs-att:...⟧`），因此分块、幂等处理、`update_mode=append` 和重新提取的行为与纯文本完全相同。
- 每次写入都会根据该文本推导出文档包含哪些附件；每条 `attachments` 记录都指向所属文档。因此删除文档或重新存入时移除附件，会精确回收该文档自己的附件；所有后端行为一致，包括文档存储在 memories store 的银行。
- 所有读取接口都会连同文本一起返回附件：召回时的 `chunks[].attachments` 和每条记忆的 `attachments`，以及 get-document、get-chunk、get-memory 和 list-memories；每个附件均包含经银行权限验证、可用于读取原始字节的 `url`。

提取出的**事实**绝不会包含占位符：在附件所在位置，事实中会显示 `[image: image/png]`，机器可读的附件句柄则放在 `attachments` 中。内容哈希不是知识。

**记忆**的 `attachments` 只包含实际用于生成该事实的附件，而不是其所在文本块中的全部附件。这些附件会直接存储在记忆本身（`memory_units.attachment_ids`）中，类似标签，因此跟随记忆保存，而不放在独立的关联表里。每个文本块只调用一次提取；包含截图的文本块也包含周围文字，因此若使用文本块的附件列表，每个事实都会显示该块的所有附件——就像把架构图显示为关于分页策略段落的证据一样。提取器会判断每条事实来自哪些附件，而仅由周围文字陈述的事实不会带有 `attachments`。这种空值是有意设计的：记忆旁显示附件，意味着模型确实查看了它并据此生成记忆。

**文本块**的 `attachments` 保持原样，仍列出该文本块引用的全部附件，因为这是关于文本块的问题，而不是关于事实的问题。

以下两种情形会直接以 `422` 拒绝存入，而不会静默丢弃附件：

- 存入 LLM 不支持视觉输入，或 Hindsight 无法确定其是否支持。参见 [`HINDSIGHT_API_LLM_VISION`](#llm-provider)。
- `HINDSIGHT_API_RETAIN_BATCH_ENABLED=true`。批处理路径会直接构建提供方请求正文，因此无法处理交错排列的内容。

#### Fireworks 批量推理 {#fireworks-batch-inference}

Fireworks AI 的批处理 API **不兼容** OpenAI `/v1/batches`；它使用专属的、按账户隔离的数据集/任务工作流，位于单独的控制平面主机（`https://api.fireworks.ai`），与兼容 OpenAI 的推理主机（`https://api.fireworks.ai/inference/v1`）不同。Hindsight 会透明地完成适配，因此启用批处理与其他提供方相同，但还需设置一项必填值：Fireworks **账户 ID**。（这与现有 LiteLLM `fireworks_ai/...` 在线调用路径分开，不影响后者。）

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_FIREWORKS_ACCOUNT_ID` | Fireworks 账户 ID。`fireworks` 批处理存入必填，因为控制平面端点使用 `/v1/accounts/{account_id}/...`。静态服务器级设置。 | - |
| `HINDSIGHT_API_FIREWORKS_BATCH_BASE_URL` | Fireworks 批处理控制平面主机。 | `https://api.fireworks.ai` |
| `HINDSIGHT_API_FIREWORKS_BATCH_MAX_WAIT_SECONDS` | 等待批处理任务的最长时间，超时后报告失败。用于防止一种 Fireworks 特有问题：不符合批处理条件的模型会使任务一直处于 `PENDING`。 | `86400`（24 小时） |

```bash
# Fireworks batch retain (50% cost savings, async only)
export HINDSIGHT_API_RETAIN_LLM_PROVIDER=fireworks
export HINDSIGHT_API_RETAIN_LLM_API_KEY=fw_xxxxxxxxxxxx
export HINDSIGHT_API_RETAIN_LLM_MODEL=accounts/fireworks/models/llama-v3p1-8b-instruct
export HINDSIGHT_API_FIREWORKS_ACCOUNT_ID=your-account-id
export HINDSIGHT_API_RETAIN_BATCH_ENABLED=true
```

> **实体标签**（`entity_labels`）和**自由格式实体提取**（`entities_allow_free_form`）通过[银行配置 API](/developer/api/memory-banks#retain-configuration)按银行设置，而不是使用全局环境变量——每个银行都可以拥有自己的受控词汇表。详情请参阅[实体标签](/developer/retain#entity-labels)。

#### 实体消解的判断方式 {#how-entity-resolution-decides}

将提取出的名称与银行中已有实体进行消解分为**两个阶段，每个阶段使用不同的相似度指标**。在调整上方阈值前要先理解这种区别：最容易手工计算的数值，并不是最终决定是否匹配的数值。

**阶段 1 — 确定要考虑哪些已有实体。** 使用 `trigram`（默认值）时，Postgres 会返回小写规范名称与提取名称在 trigram 上相似的实体，且相似度必须达到 [`HINDSIGHT_API_ENTITY_TRGM_SIMILARITY_THRESHOLD`](#database-connection-pool) 的限制（**`0.3`**）；此值不会低于 `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY`，因为阶段 2 会拒绝低于该下限的候选项。最多保留 `HINDSIGHT_API_RETAIN_ENTITY_RESOLUTION_MAX_CANDIDATES` 个候选项，并按相似度排序。使用 `full` 时，候选项则是名称完全匹配或互为子串的实体。标签实体不会进入此阶段，只按完全匹配进行消解。

**阶段 2 — 判断是否复用某个已有实体。** 系统会为每个候选项评分；最高分达到 **`0.6`** 时便复用该实体，否则创建新实体。

| 信号 | 权重 | 衡量内容 |
|--------|--------|------------------|
| 名称相似度 | 最高 **0.5** | 两个小写名称的字符序列比率（Python 的 `difflib.SequenceMatcher`），**不是**阶段 1 使用的 trigram 相似度 |
| 共现实体 | 最高 **0.3** | 同一事实中提取的*其他*实体里，有多少已经与此候选实体共现；每个实体按其区分能力加权 |
| 时间接近度 | 最高 **0.2** | 事实日期与候选实体 `last_seen` 的接近程度；在 7 天内线性衰减至零 |

开始计算这些信号前，候选项必须达到 `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY`（**`0.3`**）的 trigram 相似度下限。设置此限制是因为两个阶段衡量的指标不同，短名称上差异最明显：序列比率会奖励任意共享字符片段，因此 `Tigran` 与 `Iran` 的得分为 `0.80`，高于 `Alice` / `Alice Chen` 的 `0.67`；而后者才是实体消解器旨在完成的合并。trigram 则能正确区分两者，分别为 `0.20` 和 `0.55`。若没有这个下限，其余信号最高可贡献 `0.5` 分，已经接近合并所需的 `0.6`，银行历史关系本身就可能让仅仅相似的名称被错误合并。

评分前还会执行另外两项检查。候选名称必须**逐词对应**：较短名称中的每个词，都必须在较长名称中找到对应词（相同词、缩写或拼写相近的词）。否则，整名相似度可能让一个共享的长词掩盖完全不同的短词——`John Smith` 和 `Jane Smith` 的 trigram 得分为 `0.47`，序列比率为 `0.80`，会导致仅共享姓氏的两个人被合并。单词名称不受此检查限制，因为只有一个词时，上述下限已经起到逐词检查的作用。反过来，若候选名称的 trigram 集合与目标名称**完全相同**，则无论其他信号如何都会直接复用：pg_trgm 按词构建 trigram，因此集合相同意味着两种写法只在大小写、标点或装饰符号上有区别（如 `Wren 🎵` 和 `Wren`、`GPT-4` 和 `GPT 4`）。

共现加权也基于同样的考虑。像 `user` 这样的实体会与成熟银行中的几乎每条事实共现，因此共享它并不能说明多少问题。每个共享实体都会根据其共现的不同实体数量进行降权；曾与 100 个其他实体共现的伙伴，只相当于曾与一个其他实体共现伙伴的十分之一。

因此有三个阈值，各自回答不同的问题：

| 阈值 | 默认值 | 所回答的问题 |
|---|---|---|
| `ENTITY_TRGM_SIMILARITY_THRESHOLD` | `0.3` | 哪些已有实体会进入考察范围？（不会低于合并下限） |
| `ENTITY_MERGE_MIN_SIMILARITY` | `0.3` | 哪些实体可以与目标合并？ |
| `ENTITY_INTRABATCH_MERGE_SIMILARITY` | `0.5` | 一次存入中哪些全新名称会合并在一起？ |

**若无关实体被合并**，请提高 `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY`。同一名称的真实表面变体通常在 `0.4` 到 `0.7` 之间，因此默认值以上仍有调节空间。对于绝不能进行模糊匹配的名称，可将其建模为[实体标签](/developer/retain#entity-labels)，或自行传入 [`resolve_entities: false`](/developer/api/retain#resolve_entities)。

**若本应合并的变体仍然分开**，请降低 `HINDSIGHT_API_ENTITY_MERGE_MIN_SIMILARITY`。这通常发生在短名称上，因为短名称的 trigram 相似度必然偏低。除非 `HINDSIGHT_API_ENTITY_TRGM_SIMILARITY_THRESHOLD` 设置得更高，否则阶段 1 的候选查找下限会随合并阈值降低；若先前提高过该值，也请一并调低。降低合并下限仍无变化时，请检查 `HINDSIGHT_API_RETAIN_ENTITY_RESOLUTION_MAX_CANDIDATES` 是否在名称相似的实体很多时截掉了正确候选项。

#### 跳过原始文档文本的存储 {#skip-storing-raw-document-text}

默认情况下，Hindsight 会逐字保存所有存入内容，供之后查看源文档、重新处理或导出。如果部署只需保留提取出的记忆（事实、实体、心智模型），不需要源文本，请设置：

```bash
export HINDSIGHT_API_STORE_DOCUMENT_TEXT=false
```

禁用后，完整的存入流水线仍会运行——分块、事实提取、嵌入和实体链接均不变，因此**不会影响记忆质量或召回效果**（召回读取提取出的记忆，而不是原始文本）。变化仅在于持久化内容：

- `documents.original_text` 会存为 `NULL`，而不是原始载荷。
- 原始文本块会被丢弃（存储为空），但仍保留文本块内容哈希，因此再次存入相同文档时仍可正确进行增量去重。

**禁用文本存储后，不允许使用 `update_mode="append"`。** 追加操作会读取之前存储的文本并在其后添加内容，以此重建文档。若没有已存储文本，追加操作会静默丢失原有内容，因此追加存入会返回错误。请使用 `update_mode="replace"`（默认值）。

**禁用文本存储后会受影响的功能**（因为这些功能会重新读取源文本）：

- **文档导出**不包含源文本；重新导入此类银行时，无法根据原始载荷重新运行提取。
- **读取文档源内容**（get-document、list-chunks 和 get-chunk 接口，包括对应的 MCP 接口）会返回空内容。
- **使用 `include_chunks=true` 召回**时，`chunk_text` 为空；事实本身不受影响，但不再提供周围文本块的上下文。
- **反思**不再提供 `expand` 工具（该工具会获取记忆的源文本块/文档），其 `recall` 步骤也不再附加源文本块，因为没有可返回的已存文本。基于已提取记忆进行反思的能力不受影响。
- **根据已存文本重新处理文档**会变成无操作，因为没有可供重新处理的内容。

此项为静态服务器级设置，不能按银行覆盖。

#### 自定义存入：该用哪种方式 {#customizing-retain-when-to-use-what}

存入流水线有五个层级的自定义方式。请从满足需求的最简单方式开始：

| 目标 | 使用方式 |
|------|-----|
| 指定要重点关注或弱化哪些主题 | `HINDSIGHT_API_RETAIN_MISSION` |
| 提取每条事实的更多细节 | `HINDSIGHT_API_RETAIN_EXTRACTION_MODE=verbose` |
| 原样存储文本块，由 LLM 提取元数据 | `HINDSIGHT_API_RETAIN_EXTRACTION_MODE=verbatim` |
| 原样存储文本块，完全不产生 LLM 成本 | `HINDSIGHT_API_RETAIN_EXTRACTION_MODE=chunks` |
| 完全替换提取规则 | `HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom` + `HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS` |

**`HINDSIGHT_API_RETAIN_MISSION` — 引导提取但不替换提取规则（建议从此方式开始）**

使用自然语言告诉银行在提取过程中应重点关注什么。任务说明会与内置规则一起加入提取提示，缩小关注范围但不改变底层逻辑。适用于所有提取模式（`concise`、`verbose`、`verbatim`、`custom`）；在 `chunks` 模式中会忽略。

```bash
export HINDSIGHT_API_RETAIN_MISSION="Focus on technical decisions, architecture choices, and team member expertise. Deprioritize social or personal information."
```

**`HINDSIGHT_API_RETAIN_EXTRACTION_MODE=verbose` — 每条事实提供更多细节**

需要包含完整上下文、关系和更丰富的事实时使用。速度比 `concise` 慢，消耗的 token 也更多。

**`HINDSIGHT_API_RETAIN_EXTRACTION_MODE=verbatim` — 按原样存储文本块**

每个文本块都会作为单个记忆单元存储，并精确保留原始文本——不进行摘要或改写。LLM 仍会运行，以提取实体、时间信息和地点，从而完整索引并支持检索。适用于 RAG 风格的索引、文档摄取流水线，或希望记忆中保留原文而非 LLM 生成摘要的基准测试。

```bash
export HINDSIGHT_API_RETAIN_EXTRACTION_MODE=verbatim
```

**`retain_strategies` / `retain_default_strategy` — 按调用指定提取策略**

命名策略可让同一个银行使用不同的提取设置摄取不同类型的内容。策略是一组分层字段覆盖项，会应用于解析后的银行配置之上。

分层配置中的任何字段都可按策略覆盖，包括 `retain_extraction_mode`、`retain_chunk_size`、`retain_structured_chunk_size`、`entity_labels`、`entities_allow_free_form`、`retain_mission` 等。

通过银行配置 API 设置策略：

```json
{
  "retain_default_strategy": "conversations",
  "retain_strategies": {
    "conversations": {
      "retain_extraction_mode": "concise",
      "retain_chunk_size": 3000,
      "retain_structured_chunk_size": 12000
    },
    "documents": {
      "retain_extraction_mode": "chunks",
      "retain_chunk_size": 800,
      "entity_labels": null,
      "entities_allow_free_form": false
    }
  }
}
```

存入调用未指定 `strategy` 时，将使用 `retain_default_strategy`。若两者均未设置，则直接应用银行/全局配置。

**`HINDSIGHT_API_RETAIN_EXTRACTION_MODE=chunks` — 零 LLM 成本**

每个文本块都会原样存储，完全不调用 LLM。不提取实体，也不进行时间索引；只生成用于语义搜索的嵌入。通过 `RetainContent.entities` 传入的用户实体是唯一的实体数据来源。适用于摄取速度和成本比结构化元数据更重要的场景。

```bash
export HINDSIGHT_API_RETAIN_EXTRACTION_MODE=chunks
```

**`HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom` + `HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS` — 完全自定义**

这会完全替换内置的选择性规则。提示中的结构性部分（输出格式、时间处理、指代消解）保持不变，只替换提取指导内容。

当 `retain_mission` 无法满足需求，且你需要严格控制纳入/排除规则时使用。

```bash
export HINDSIGHT_API_RETAIN_EXTRACTION_MODE=custom
export HINDSIGHT_API_RETAIN_CUSTOM_INSTRUCTIONS="ONLY extract facts that are:
✅ Technical decisions and their rationale
✅ Architecture patterns and design choices
✅ Performance metrics and benchmarks

DO NOT extract:
❌ Greetings or social conversation
❌ Process chatter (\"let me check\", \"one moment\")
❌ Anything that would not be useful in 6 months"
```

#### 选择解析器 {#parser-selection}

客户端可在 `POST /v1/default/banks/{bank_id}/files/retain` 的请求正文中传入 `parser`，覆盖服务器默认值。服务器默认值和单次请求字段都接受单个解析器名称或有序的**故障转移链**；系统会依次尝试解析器，直到其中一个成功。


#### 解析器：markitdown（默认） {#parser-markitdown-default}

使用 [Microsoft 的 markitdown](https://github.com/microsoft/markitdown) 在本地将文件转换为 Markdown。默认无需外部服务。

**支持的格式：** PDF、DOCX、DOC、PPTX、PPT、XLSX、XLS、图像（JPG、PNG——提取文本需安装可选 OCR）、音频（MP3、WAV——转录）、HTML、TXT、MD、CSV。

对于图像工作负载，MarkItDown 可选用兼容 OpenAI 的 OCR/视觉端点。此功能默认禁用。未启用时，图像上传会返回可据以配置的错误，而不是底层解析器输出。启用后，请明确配置 MarkItDown OCR API 密钥、基础 URL 和模型；这些设置不会从 `HINDSIGHT_API_LLM_*` 继承，因为 MarkItDown 直接使用 OpenAI SDK。所选端点必须实现 OpenAI Chat Completions，所选模型必须支持图像输入。

此 OCR 路径使用 MarkItDown 的图像转换钩子。它适用于 JPG、PNG 等图像输入，也适用于使用 MarkItDown `llm_client` 的转换器中的图像处理，但不会将扫描版 PDF 页面栅格化为图像。没有文本层的扫描版 PDF 仍可能无法通过默认 PDF 转换器正确提取。对于扫描版 PDF 或布局复杂的文档，请使用支持 OCR 的文档解析器，例如 `iris` 或 `llama_parse`，也可以配置故障转移链，例如 `llama_parse,markitdown`。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_ENABLED` | 通过兼容 OpenAI 的 OCR/视觉端点启用 MarkItDown 图像 OCR | `false` |
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_API_KEY` | MarkItDown OCR 使用的 API 密钥；启用 OCR 时必填 | — |
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_BASE_URL` | MarkItDown OCR 使用的兼容 OpenAI Chat Completions 基础 URL；启用 OCR 时必填 | — |
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_MODEL` | 支持图像输入的 OCR/视觉模型；启用 OCR 时必填 | — |
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_PROMPT` | 传递给 MarkItDown 图像转换器的 OCR 提示 | 内置 OCR 提示 |
| `HINDSIGHT_API_FILE_PARSER_MARKITDOWN_OCR_DEFAULT_HEADERS` | 可选 JSON 字典，作为 `default_headers` 传给 OCR OpenAI SDK 客户端（代理/请求追踪中间件） | `null` |


### 观测（实验性） {#observations}

观测是从多条事实中整合而成、去重且以证据为依据的知识。每条观测都会追踪其支持记忆和证据计数；出现新证据时会进一步完善，而不会被覆盖。

| 变量 | 说明 | 默认值 |
|----------|-------------|---------|
| `HINDSIGHT_API_ENABLE_OBSERVATIONS` | 启用观测整合 | `true` |
| `HINDSIGHT_API_ENABLE_AUTO_CONSOLIDATION` | 存入、删除和更新操作后自动触发整合。设为 `false` 时，仅能通过[整合端点](/developer/api/operations#consolidation)显式触发。可按银行配置。 | `true` |
| `HINDSIGHT_API_CONSOLIDATION_WALL_TIMEOUT` | 工作进程中单个整合任务在**未取得进展**时允许运行的时间上限（秒）。每次提交一个批次都会重新计时，因此不会截断大型积压任务，只会终止真正停滞的任务。停滞的整合会被取消并标记为 `failed`（API 会重试，而不会像 `processing` 状态那样卡住；协调扫描也会据此重新安排该银行），而不是一直占用保留的工作进程槽位直到进程重启。设为 `0` 可禁用。 | `7200` |
| `HINDSIGHT_API_CONSOLIDATION_RECONCILE_INTERVAL_SECONDS` | 后台扫描重新安排整合的间隔：当银行有尚未整合的事实、但没有正在运行的整合时，会安排任务，以恢复因整合操作最终失败（例如 LLM 提供方不可用）而未安排的事实。仅适用于启用了自动整合的银行。设为 `0` 可禁用扫描；但见下方说明：这会停止*安排*新任务，不会停止已经排队任务的*运行*。 | `300` |
| `HINDSIGHT_API_MENTAL_MODEL_REFRESH_TICK_SECONDS` | 后台循环检查计划刷新的心智模型的间隔。此项只控制*检查*频率；实际计划由心智模型上的 `trigger.refresh_cron` 表达式决定。模型到期后，仅当其范围内自上次刷新后出现了新记忆（即模型已过时）时才会刷新。此项也决定 cron 的**最小粒度**——默认情况下，`* * * * *` 会每 5 分钟触发，而不是每分钟；若需更细粒度，可调低，但跨租户扫描会更频繁（参见[后台维护](#background-maintenance)）。设为 `0` 可禁用扫描；但见下方说明：这会停止*安排*新任务，不会停止已经排队任务的*运行*。 | `300` |
| `HINDSIGHT_API_ENABLE_OBSERVATION_HISTORY` | 追踪每条观测的更改历史（先前文本/标签/日期及时间戳），并按每次更改在 `observation_history` 表中存储一行。设为 `false` 可完全禁用，不再写入历史记录。**这是关闭此功能的方式**（不能通过设置为零来关闭）。 | `true` |
| `HINDSIGHT_API_OBSERVATION_HISTORY_MAX_ENTRIES` | 每条观测保留的历史记录上限。每次更新时，先将旧版本插入 `observation_history` 表，再删除超过此上限的最早记录，避免经常获得支持的观测历史无限增长。设为 `0` 或负数会**取消上限**（无界增长）；若要完全关闭历史记录，请设置 `HINDSIGHT_API_ENABLE_OBSERVATION_HISTORY=false`。 | `50` |
| `HINDSIGHT_API_CONSOLIDATION_MAX_ATTEMPTS` | 整合 LLM 批量调用的外层重试次数，仅用于连接错误和速率限制类故障（重试之间会退避等待）。格式错误或不符合 schema 的输出不会重新发送；批次会立即失败并拆分成更小批次。提供方配额耗尽不会在此重试；整个任务会重新安排到配额恢复后执行。每次重试都会使用内层重试预算（`HINDSIGHT_API_CONSOLIDATION_LLM_MAX_RETRIES`），因此每批最坏的 API 调用数为 `MAX_ATTEMPTS × (LLM_MAX_RETRIES + 1)`。 | `3` |
| `HINDSIGHT_API_CONSOLIDATION_BATCH_SIZE` | 每批加载的记忆数（内部优化项） | `50` |
| `HINDSIGHT_API_CONSOLIDATION_MAX_MEMORIES_PER_ROUND` | 每轮整合处理的记忆数量上限。达到上限时，任务会释放工作进程槽位并重新排队，以便其他银行公平获得调度。心智模型刷新仅在最后一轮运行。`0` = 不限。可按银行配置。 | `100` |
| `HINDSIGHT_API_CONSOLIDATION_MAX_TOKENS` | 整合期间查找相关观测时，召回使用的最大 token 数 | `1024` |
| `HINDSIGHT_API_CONSOLIDATION_MAX_COMPLETION_TOKENS` | 每次整合 LLM 批量调用请求的最大 completion token 数。默认不设置，因此各提供方会保留自身隐式输出预算。若提供方采用较低且不明显的上限（例如从 Bedrock 导入的模型），会截断整合输出，此时可设置此项。 | `unset` |
| `HINDSIGHT_API_CONSOLIDATION_LLM_BATCH_SIZE` | 单次整合调用发送给 LLM 的事实数量。较大的值可减少调用次数、提高吞吐量，但会扩大提示。设为 `1` 可禁用批处理。可按银行配置。 | `8` |
| `HINDSIGHT_API_CONSOLIDATION_DEDUP_THRESHOLD` | 新建或刚更新的观测达到此余弦相似度后，会通过一次聚焦的 1 对 1 LLM“合并还是保留”调用与近乎相同的现有观测协调（模型会同时读取两段文本，因此会注意到数字、否定词或实体差异）。用于捕获较弱的整合模型即使看到重复项仍生成的近似重复观测，以及更新时将观测改写成另一条近似重复项的情况。设为 `1.0` 可禁用。仅适用于 Postgres；无论此值如何，Oracle 上的整合都会跳过协调。 | `0.97` |
| `HINDSIGHT_API_CONSOLIDATION_LLM_PARALLELISM` | 单次整合操作中可并发整合的标签组数量上限。每组处理前会获取范围级锁，因此写入范围重叠的标签组（例如采用 `per_tag` / `all_combinations` / 显式列表 `observation_scopes` 时）会在重叠范围上自动串行执行；发生范围竞争时，实际并发数可能低于此上限。设为 `1` 可完全串行。较高值会按比例提高整合期间的 LLM 峰值 QPS 和连接池使用量；若 LLM 提供方严格限制速率或数据库连接池较小，请调低。可按银行配置。 | `4` |
| `HINDSIGHT_API_CONSOLIDATION_RECALL_BUDGET` | 整合内部召回阶段使用的预算级别（`low`、`mid`、`high`）。较低预算会获取更少的候选行，减少大型银行中的峰值内存用量。 | `low` |
| `HINDSIGHT_API_CONSOLIDATION_SOURCE_FACTS_MAX_TOKENS` | 整合提示中与观测一起包含的源事实总 token 预算。`-1` = 不限。可按银行配置。 | `4096` |
| `HINDSIGHT_API_CONSOLIDATION_SOURCE_FACTS_MAX_TOKENS_PER_OBSERVATION` | 整合提示中每条观测对应的源事实 token 上限。每条观测单独计算，最多包含此数量的源事实 token。`-1` = 不限。可按银行配置。 | `256` |
| `HINDSIGHT_API_OBSERVATIONS_MISSION` | 指定此银行应将哪些内容综合为持久观测。会替换内置整合规则；留空时使用服务器默认值。 | - |

| `HINDSIGHT_API_OBSERVATION_SCOPE_LIMITS` | **已弃用**——请使用同时支持任务说明的 `CONSOLIDATION_STRATEGIES`；此设置仍会生效，但只在后续阶段读取。此 JSON 数组用于按范围覆盖 `MAX_OBSERVATIONS_PER_SCOPE`，规则格式为 `{"scope": [tag-globs], "limit": int}`。每个 `scope` 是一个 [fnmatch](https://docs.python.org/3/library/fnmatch.html) glob 列表；整合范围必须与 glob **完全覆盖**——每个标签都要匹配某个 glob，且每个 glob 都必须匹配一个标签。因此，`["shared"]` 会匹配 `{shared}`，但不会匹配 `{run_1, shared}`。第一条匹配规则优先；没有匹配规则的范围回退到 `MAX_OBSERVATIONS_PER_SCOPE`。示例：`[{"scope": ["shared"], "limit": -1}, {"scope": ["run_*", "shared"], "limit": 50}]` 可让 `{shared}` 范围不设上限，同时将每个 `{run_*, shared}` 范围限制为 50 条。可按银行配置。 | - |
| `HINDSIGHT_API_CONSOLIDATION_STRATEGIES` | 用 JSON 数组为各范围配置整合策略，格式为 `{"scopes": [{"tags": [tag-globs], "tags_match": "all" \| "exact"}, ...], "observations_mission": str, "max_observations_per_scope": int, "consolidation_source_facts_max_tokens": int, "consolidation_source_facts_max_tokens_per_observation": int}`。每个策略会声明其负责的范围；范围由 [fnmatch](https://docs.python.org/3/library/fnmatch.html) glob 列表表示；只要策略中的任意模式匹配其标签，该整合阶段就由此策略负责。每个模式中的 `tags_match` 决定匹配方式：`"all"`（默认）表示范围包含模式中的所有标签，但可以有其他标签；`"exact"` 表示标签必须完全相同，不能有其他标签。所有设置均为可选。**每个范围恰好应用一个策略：按列表顺序选择首个声明该范围的策略。** 该策略未设置的字段，以及未被任何策略声明的范围，都使用银行级 `OBSERVATIONS_MISSION`、`MAX_OBSERVATIONS_PER_SCOPE`、`CONSOLIDATION_SOURCE_FACTS_MAX_TOKENS` 和 `CONSOLIDATION_SOURCE_FACTS_MAX_TOKENS_PER_OBSERVATION`。此项取代 `OBSERVATION_SCOPE_LIMITS`，可让单个银行按用户/团队/公司标签范围进行联邦化：每个范围通过独立的 LLM 调用进行整合，因此各自可采用不同任务说明。示例：`[{"scopes": [{"tags": ["company:*"]}], "observations_mission": "仅记录行业层面的概括趋势。绝不提及具体公司、交易规模或融资阶段。"}]` 会让用户范围保留详细内容，而公司范围保持概括。可按银行配置。 | - |

:::note 禁用扫描会停止任务调度，不会停止任务执行

后台工作分为两个独立阶段，上方的间隔参数只控制第一个阶段：

1. **调度**——维护循环会定期扫描到期工作（待协调的整合、待刷新的心智模型），并为其排入操作。将 `HINDSIGHT_API_CONSOLIDATION_RECONCILE_INTERVAL_SECONDS=0` 和 `HINDSIGHT_API_MENTAL_MODEL_REFRESH_TICK_SECONDS=0` 设为零会关闭这些扫描，因此不会排入*新*任务。

2. **执行**——工作进程轮询器会按自己的节奏（默认每 500 毫秒，参见[分布式工作进程](#distributed-workers)中的 `HINDSIGHT_API_WORKER_POLL_INTERVAL_MS`）领取并运行已有的待处理任务。它不受扫描间隔变量影响；扫描禁用前已排队的操作（包括重启后恢复的操作）仍会被领取。

因此，将间隔设为零可让没有积压任务的部署保持空闲；若已有任务积压，工作进程仍会继续整合和刷新。若要完全停止进程执行后台工作，请禁用工作进程本身：

```bash
HINDSIGHT_API_WORKER_ENABLED=false
```

在隔离工作负载以进行基准测试或调试时，这一点很重要：若仅将间隔设为零，已排队的整合或存入操作仍可能与测试并行运行，并被误认为是测试负载。

:::

#### 自定义观测：该用哪种方式 {#customizing-observations-when-to-use-what}

| 目标 | 使用方式 |
|------|-----|
| 默认行为：保留具体、持久的事实，不保留临时状态 | 留空 |
| 更改此银行中观测的*用途*（采用不同形式或服务于不同目的） | `HINDSIGHT_API_OBSERVATIONS_MISSION` |

**`HINDSIGHT_API_OBSERVATIONS_MISSION` — 重新定义此银行要综合的内容**

默认情况下，观测是从记忆中整合出的具体、持久信念——即长期保持有效的知识（偏好、技能、关系、反复出现的模式）。每条观测都有支持它的源记忆作为依据。临时状态会被过滤。矛盾内容通过时间标记进行追踪，而不会覆盖先前的信念。

设置 `HINDSIGHT_API_OBSERVATIONS_MISSION` 可完全替换此定义。请用自然语言描述你的用例希望观测代表什么。LLM 在决定创建或更新观测时会采用此说明，取代默认规则。留空则保留服务器默认值。

:::tip 何时使用 observations_mission
默认的持久知识行为不适合你的用例时，可使用此项。常见场景：
- 希望获得**更宽泛的事件摘要**，而不是相互独立的事实。
- 希望观测**按时间段分组**（每周、每月）。
- 希望采用**不同的粒度**（每个项目一条观测，而不是每条事实一条）。
- 你的领域对“值得记住的内容”有**特定定义**。
:::

**示例：每周事件摘要**

```bash
export HINDSIGHT_API_OBSERVATIONS_MISSION="Observations are broad summaries of project events grouped by week. Each observation should capture what happened, what was decided, and what was blocked — not individual facts. Merge related events into cohesive weekly narratives."
```

**示例：以人物为中心的知识**

```bash
export HINDSIGHT_API_OBSERVATIONS_MISSION="Observations are durable facts about specific named people: their preferences, skills, relationships, and behavioral patterns. Only create observations for facts that are stable over time and tied to a named individual."
```

**示例：支持工单模式**

```bash
export HINDSIGHT_API_OBSERVATIONS_MISSION="Observations are recurring patterns in customer support interactions: common failure modes, frequently requested features, and pain points that appear across multiple tickets."
```

### 分布式工作进程 {#distributed-workers}

| `HINDSIGHT_API_WORKER_ID` | 唯一工作进程标识符 | 主机名 |
| `HINDSIGHT_API_WORKER_POLL_INTERVAL_MS` | 数据库轮询间隔（毫秒） | `500` |
| `HINDSIGHT_API_WORKER_MAX_RETRIES` | 将任务标记为失败前的最大重试次数 | `3` |
| `HINDSIGHT_API_WORKER_TASK_RETRY_BACKOFF_SECONDS` | 暂时性任务失败后重试的等待秒数 | `60` |
| `HINDSIGHT_API_BACKPRESSURE_DEFER_SECONDS` | 存储后端因背压暂缓的任务，在重试前等待的时间。等待应足够长，让积压有机会消退（满载时立即重试只会再次被暂缓），又不至于在积压清除后仍久等。延后不计入 `HINDSIGHT_API_WORKER_MAX_RETRIES`。 | `120` |
| `HINDSIGHT_API_WORKER_HTTP_PORT` | 工作进程指标/健康检查 HTTP 端口（仅工作进程 CLI） | `8889` |
| `HINDSIGHT_API_WORKER_MAX_SLOTS` | 每个工作进程的最大并发任务总数（所有操作类型合计） | `10` |
| `HINDSIGHT_API_OPERATION_RETENTION_DAYS` | 已完成、失败和取消操作行（包括任务载荷和结果元数据）的全服务器静态保留时长。`0`（默认）表示永久保留；正数天数启用自动清理。 | `0` |
| `HINDSIGHT_API_OPERATION_CLEANUP_BATCH_SIZE` | 每个清理周期中，每个租户 schema 删除的过期终态操作行上限；此值与清理间隔一起决定积压清除速度。必须为正整数。 | `1000` |
| `HINDSIGHT_API_OPERATION_CLEANUP_INTERVAL_SECONDS` | 清理周期的间隔。每次周期会产生一次跨租户发现往返，对租户较多的部署而言，调大间隔是降低这项开销的主要方式（参见[后台维护](#background-maintenance)）。`0` 禁用此作业。 | `900` |
| `HINDSIGHT_API_WORKER_CONSOLIDATION_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为整合预留的最低槽位数，保证整合容量，**不是**按类型的上限（保留银行级串行限制）。见下方说明。 | `2` |
| `HINDSIGHT_API_WORKER_CONSOLIDATION_BANK_PRIORITY` | 整合调度时的银行优先级（见下方说明） | （未设置） |
| `HINDSIGHT_API_WORKER_RETAIN_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为存入预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_FILE_CONVERT_RETAIN_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 file_convert_retain 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_REFRESH_MENTAL_MODEL_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 refresh_mental_model 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_GRAPH_MAINTENANCE_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 graph_maintenance 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_IMPORT_DOCUMENTS_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 import_documents 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_EXPORT_BANK_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 export_bank 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_IMPORT_BANK_RESERVED_SLOTS` | 在 `WORKER_MAX_SLOTS` 内为 import_bank 预留的最低槽位数 | `0` |
| `HINDSIGHT_API_WORKER_<TYPE>_MAX_SLOTS` | **已弃用**的 `..._RESERVED_SLOTS` 别名，`<TYPE>` 可为 `CONSOLIDATION`、`RETAIN`、`FILE_CONVERT_RETAIN`、`REFRESH_MENTAL_MODEL`、`GRAPH_MAINTENANCE`、`IMPORT_DOCUMENTS`。名称有误——它设置预留下限而非上限。目前仍生效但会记录警告，未来将移除。若同时设置它和 `..._RESERVED_SLOTS` 则报错。 | （未设置） |

终态操作会对整行使用统一的保留窗口。操作结束后 Hindsight 不会清除任务载荷：失败和取消的操作需要它来重试，而对已完成操作设置 `include_payload=true` 是一种显式调试方式。将载荷、结果元数据、进度和状态保存在一起也可避免操作历史不完整。终态行的 `updated_at` 超出配置窗口后，后台维护循环会按每个 schema 的有界批次进行清理，与其他定时扫描一起执行。仅适用于 PostgreSQL；Oracle 不运行维护循环。待处理和正在处理的行不会被清理。

:::note 工作进程槽位预留是下限，不是上限
`..._RESERVED_SLOTS` 会在 `WORKER_MAX_SLOTS` 中为某类操作保证预留*最低*槽位数，防止资源池饱和时该类型被饿死；它**不是**每类型上限。预留总和不得超过 `WORKER_MAX_SLOTS`（否则启动时抛出 `ValueError`）。剩余容量（`WORKER_MAX_SLOTS - sum of reservations`）构成所有类型可先到先得共享的**共享池**；某类型用满预留槽位后仍可使用共享池，因此无论预留值是多少，该类型的实际并发上限始终为 `WORKER_MAX_SLOTS`。

例如：`MAX_SLOTS=10`、`CONSOLIDATION_RESERVED_SLOTS=2`、`RETAIN_RESERVED_SLOTS=3`、`REFRESH_MENTAL_MODEL_RESERVED_SLOTS=2` → 共享池 = `10 - (2+3+2) = 3`。

使用默认值（`MAX_SLOTS=10`、`CONSOLIDATION_RESERVED_SLOTS=2`，其余预留值为 `0`）时，整合始终有 2 个预留槽位，剩余 8 个构成共享池；整合也可使用共享池，最多占用 10 个槽位。设 `CONSOLIDATION_RESERVED_SLOTS=0` 可将其预留容量释放到共享池。无论由哪个池提供槽位，整合的银行级串行限制（同一银行不能同时执行两个整合任务）始终生效。

旧版 `..._MAX_SLOTS` 环境变量是 `..._RESERVED_SLOTS` 的弃用别名；尽管名称如此，它设置的是预留下限，绝不是上限。它目前仍有效但会记录警告，之后会移除；请迁移到 `..._RESERVED_SLOTS`。
:::

:::note 整合银行优先级
`HINDSIGHT_API_WORKER_CONSOLIDATION_BANK_PRIORITY` 控制有空闲槽位时优先领取哪些银行的整合任务。格式是以逗号分隔的 `bank-pattern:priority` 配对，数值越大优先级越高。模式支持 `*` 通配符；裸 `*` 用作未列出银行的默认匹配项，未设置时默认为 `1`。

示例：
```
HINDSIGHT_API_WORKER_CONSOLIDATION_BANK_PRIORITY="shadow-*:10,staging-*:5,*:1"
```

这样可确保 `shadow-*` 银行的整合总是先于其他银行，即使它们的任务提交较晚。适用于银行规模差异较大的部署，避免大型银行被许多小银行轮流占用有限槽位而饿死。无论优先级如何，同一银行最多同时运行一个整合任务。未设置时按 `created_at` 顺序领取任务（默认行为）。
:::

### 性能优化 {#performance-optimization}

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_SKIP_LLM_VERIFICATION` | 跳过启动时的 LLM 连接检查 | `false` |

#### 银行统计缓存 {#bank-stats-cache}

`get_bank_stats` 会聚合 `memory_links`（联接 `memory_units`）；对于包含数百万行的银行，扫描可能耗时数秒。结果本来就是近似值，用于界面小组件和 `reflect` 中的新鲜度提示，因此会按 `(schema, bank)` 缓存数十秒，并将并发缓存未命中合并到同一个在途查询。高并发或大型银行可调整以下参数：

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_BANK_STATS_CACHE_TTL_SECONDS` | `get_bank_stats` 结果缓存的存活时间（秒）。设为 `0` 禁用缓存，每次调用都会查询。 | `60` |
| `HINDSIGHT_API_BANK_STATS_CACHE_MAX_ENTRIES` | LRU 淘汰前可缓存的 `(schema, bank)` 项数上限，用于限制银行较多时的内存使用。 | `1024` |

#### 原生线程池 {#native-thread-pools}

本地嵌入或重排在进程内运行时，底层 BLAS/ML 库（OpenBLAS、OpenMP、MKL）各自会启动按主机 CPU 数量配置的线程池。Hindsight 已通过自身线程池执行器并行处理请求，因此这些原生线程池会导致 CPU 过度分配；多核主机上的原生线程总数可能超过 100。这会增加内存用量，并在竞争时降低吞吐量。因此 Hindsight 默认将每个原生线程池限制为**最多 16 个线程**（或可用 CPU 数量，以较小者为准），避免大型主机上线程数失控，同时保留单次调用内部的并行能力。

“可用”CPU 指进程实际获准使用的 CPU 预算，即 CPU 亲和性集合、cgroup CPU 配额（`--cpus` / cpuset）和主机核心数三者中的最小值。容器环境中这一点很重要：BLAS 库否则会按*主机*核心数设置线程池，即便容器只分配了几个 CPU。例如，64 核主机上限制为 `--cpus=4` 的容器会启动远多于其可用数量的 BLAS 线程。

如需调整，将以下任一变量设为所需线程数；只要设置了变量，指定值就会生效（仅当变量未设置时才使用默认值）：

| 变量 | 说明 | 默认值 |
|---|---|---|
| `OMP_NUM_THREADS` | OpenMP 工作线程（torch、ONNX Runtime、部分 BLAS 构建） | `min(16, available CPUs)` |
| `OPENBLAS_NUM_THREADS` | OpenBLAS 工作线程（numpy 默认 BLAS） | `min(16, available CPUs)` |
| `MKL_NUM_THREADS` | Intel MKL 工作线程（使用 MKL 后端的 numpy/torch） | `min(16, available CPUs)` |
| `NUMEXPR_NUM_THREADS` | numexpr 表达式引擎线程 | `min(16, available CPUs)` |

处理大量并发请求的服务器可降低线程数（最低为 `1`），以提高请求级并行并减少线程数量；低并发且运行大型本地模型批次的部署可采用默认值，为单次调用内的并行计算留出空间。这些变量必须在进程启动前设置（相关库只在加载时读取一次），因此不能按租户或银行覆盖。

### 审计日志 {#audit-logging}

审计日志会将更改数据的操作（存入、召回、反思、银行配置更新、[Memory Defense](memory-defense/index.md) 脱敏/拦截操作等）记录到 `audit_log` 表中，并可通过 `/audit-logs` 端点查询。

**审计日志默认关闭。** 当 `HINDSIGHT_API_AUDIT_LOG_ENABLED=false` 时，`audit_log` 表保持为空，且无论发生何种操作，`/audit-logs` 都会返回 `{"total": 0, "items": []}`。若要开始记录事件，请将此标志设为 `true` 并重启 API。

**可以针对单个银行单独启用或关闭审计。** `audit_log_enabled` 支持分层配置，可通过[配置 API](#hierarchical-configuration)或控制平面中该银行的**配置 → 审计日志**开关覆盖。覆盖可双向生效：即使服务器默认值为 `false`，银行也可选择启用；即使默认值为 `true`，银行也可选择关闭。未设置覆盖值的银行遵循服务器默认值。与环境变量不同，按银行更改会立即生效，无需重启。

操作类型允许列表和保留期限仍是服务器级设置：保留扫描会跨所有租户执行，无法限定到单个银行。

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_AUDIT_LOG_ENABLED` | 是否写入审计事件。支持分层配置，可通过配置 API 按银行覆盖。 | `false` |
| `HINDSIGHT_API_AUDIT_LOG_ACTIONS` | 以逗号分隔的审计操作类型允许列表（空值表示所有符合条件的操作） | `""` |
| `HINDSIGHT_API_AUDIT_LOG_RETENTION_DAYS` | 审计日志条目的保留天数。`-1` = 永久保留。 | `-1` |

### LLM 请求追踪 {#llm-request-tracing}

LLM 请求追踪会将 Hindsight 发出的每次 LLM 调用（用于存入、反思和整合）记录到 `llm_requests` 表中，并可按银行通过 `/llm-requests` 端点查询。每行记录输入消息、模型输出、token 用量（输入/输出/缓存/总计，取自提供方响应）、结束原因、提供方/模型、耗时及调用方元数据。**失败的调用也会记录**（`status = "error"` 并包含错误消息），因此该表有助于调试 LLM 的行为和调用失败原因。记录功能接入 OpenTelemetry GenAI 记录路径（即用于导出 OTLP span 的同一个 `record_llm_call` 钩子），因此数据与提供方报告的请求详情保持一致。

**LLM 请求追踪默认启用**，追踪记录保留 1 天。若要完全禁用，请将 `HINDSIGHT_API_LLM_TRACE_ENABLED=false` 并重启 API；之后 `llm_requests` 表会保持为空，且无论发生何种操作，`/llm-requests` 都会返回 `{"total": 0, "items": []}`。

> **注意**：追踪记录包含完整提示和模型输出，可能包含敏感记忆内容且占用空间较大。可通过 `HINDSIGHT_API_LLM_TRACE_MAX_CHARS` 限制存储的每段载荷长度、缩短 `HINDSIGHT_API_LLM_TRACE_RETENTION_DAYS` 保留期限，或设置 `HINDSIGHT_API_LLM_TRACE_ENABLED=false`，以便在敏感环境中关闭追踪。

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_LLM_TRACE_ENABLED` | LLM 请求追踪总开关。只有设为 `true` 才会记录调用。 | `true` |
| `HINDSIGHT_API_LLM_TRACE_SCOPES` | 以逗号分隔的追踪调用范围允许列表（例如 `retain_extract_facts,reflect`；空值表示全部范围） | `""` |
| `HINDSIGHT_API_LLM_TRACE_RETENTION_DAYS` | 追踪记录的保留天数。`-1` = 永久保留。 | `1` |
| `HINDSIGHT_API_LLM_TRACE_MAX_CHARS` | 输入/输出超过此字符数时截断存储（保留该行，但只保存截断预览）。 | `50000` |

### 后台维护 {#background-maintenance}

每个 API/工作进程中的单一周期循环负责 Hindsight 的定期维护：清理 `audit_log` / `llm_requests` 保留期数据、清理终态操作、协调整合任务，以及按 cron 计划刷新心智模型。

此循环会在**每个**进程中运行，不进行主节点选举；其设计确保安全——扫描是幂等删除，而负责排入任务的两个作业会在插入事务中对在途操作去重。不过，规模扩大后此操作并非没有代价：每个作业都要先进行一次跨租户发现调用，探测包含相关表的所有 schema，且每个进程都会执行此探测。成本会随租户数增长，但扫描发现的工作量并不会同步增长；因此在大型多租户部署中，**维护频率是关键调节项**。

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_RETENTION_SWEEP_INTERVAL_SECONDS` | 跨所有租户 schema 删除过期 `audit_log` 和 `llm_requests` 行的频率。保留时限以天为单位，因此此项只影响过期记录被清除的及时程度。设为 `0` 可禁用扫描。 | `3600` |
| `HINDSIGHT_API_OPERATION_CLEANUP_INTERVAL_SECONDS` | 清理过期终态操作行的频率。保留时限和批次大小请参阅[分布式工作进程](#distributed-workers)。设为 `0` 可禁用作业。 | `900` |
| `HINDSIGHT_API_MAINTENANCE_START_JITTER_SECONDS` | 进程首次运行维护周期前应用的随机延迟上限。首次周期中所有作业都会到期，因此若无偏移，同时启动的一组进程（例如部署或滚动重启）会在同一时刻执行各自的所有扫描。设为 `0` 可禁用抖动，采用确定性启动。 | `60` |

:::tip 为大量租户调整参数

租户只有几百个时，默认值的影响可以忽略；租户达到数万时，每次扫描的发现过程会占主导，而保留期限按*天*计的作业完全无需每分钟探测所有 schema。可先调高 `HINDSIGHT_API_OPERATION_CLEANUP_INTERVAL_SECONDS` 和 `HINDSIGHT_API_MENTAL_MODEL_REFRESH_TICK_SECONDS`——这两项扫描频率最高；同时保持启用随机抖动，避免进程重启时间同步。
:::

:::

| `HINDSIGHT_API_RECALL_DIAGNOSTIC_PHASES` | 记录诊断用召回阶段，即 `hindsight.recall.phase.duration` 中标记为 `diagnostic="true"` 的阶段。这些阶段是其他阶段的子集，仅在诊断时有用；繁忙的召回路径可禁用此项以降低埋点开销。 | `true` |
| `HINDSIGHT_API_RECALL_PHASE_SAMPLE_EVERY` | 每 N 条 `hindsight.recall.phase.duration` 指标观测记录 1 条。每条观测独立采样，因此百分位数保持无偏，只有直方图计数按 1/N 缩放。提高此值，例如设为 `10`，可在召回调用频率高时降低指标处理的 CPU 开销。 | `1` |
| `HINDSIGHT_API_METRICS_BACKLOG_ENABLED` | 暴露异步操作队列深度和整合积压指标（`hindsight_async_operations`、`hindsight_consolidation_backlog`、`hindsight_consolidation_failed`）。通过后台任务定期对每个 schema 执行 `COUNT` 查询。 | `false` |
| `OTEL_PYTHON_FASTAPI_EXCLUDED_URLS` | 从请求追踪中排除的 URL 模式，以逗号分隔 | `health,metrics` |

### 运行时停滞诊断 {#runtime-stall-diagnostics}

API 和工作进程会在单个 asyncio 事件循环中运行 `/health` 处理程序及所有任务，且 `/health` 需要获取数据库连接。因此，存活探针失败可能有两种截然不同的原因：同步任务**阻塞事件循环**（重启会有帮助），或**连接池已耗尽**，导致事件循环空闲时 `/health` 仍无法取得连接（通常重启也无济于事）。这些诊断信息仅凭日志和指标就能区分两种原因，无需面对原因不明的重启。

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_LOOP_WATCHDOG_ENABLED` | 运行后台线程检测事件循环停滞并记录阻塞堆栈。也会发出 `hindsight_event_loop_stalls` / `hindsight_event_loop_stall_duration` 指标。 | `true` |
| `HINDSIGHT_API_LOOP_WATCHDOG_STALL_THRESHOLD_MS` | 事件循环无响应达到此时长后记录停滞。 | `1000` |
| `HINDSIGHT_API_LOOP_WATCHDOG_POLL_INTERVAL_MS` | 看门狗线程探测事件循环的间隔。 | `250` |
| `HINDSIGHT_API_DB_ACQUIRE_WARN_THRESHOLD_MS` | 获取连接池连接至少等待此时长时，记录警告（含连接池统计）。 | `1000` |

数据库连接池获取路径还会提供 `hindsight_db_pool_waiting`（当前排队等待连接的调用方数量）和 `hindsight_db_pool_acquire_wait` 直方图。响应缓慢或失败的 `/health` 还会附带 `db_acquire_ms`、`db_pool_waiting`、`db_pool_in_use` 和 `db_pool_max`，便于排查。

### CPU 性能分析 {#cpu-profiling}

上文的事件循环看门狗可回答“事件循环是否阻塞？”此项则进一步回答“**哪些任务在消耗 CPU？**”，即使你无法将调试器附加到进程也可诊断。

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_PROFILE` | JSON 对象；未设置时完全禁用性能分析。示例：`{"every": 60, "top": 20}` | 未设置 |

`every` 表示两次报告之间的秒数，`top` 表示每份报告列出的行数。设置后，API 会按指定间隔将 CPU 报告发送到常规日志流：

```
HINDSIGHT_API_PROFILE='{"every": 60, "top": 20}'
```

```
[profile] thread hindsight-loop-            1.41 cores
[profile] thread asyncio_                   0.37 cores
[profile] 1598 functions active in the last 60s
[profile] tottime=0.923 cumtime=1.833 ncalls=15842 <method 'encode' of 'builtins.CoreBPE' objects>
[profile] tottime=0.691 cumtime=7.039 ncalls=1511590 <built-in method builtins.isinstance>
```

每一行会作为带有 `[profile]` 标记的日志记录，因此可以通过 `grep '\[profile\]'` 从日志还原表格。

**有意将报告写入日志。** 此功能针对的是进程毫无说明地退出的情形。若容器中未预先挂载卷，容器销毁时其中的文件也会消失；HTTP 端点则需要仍在运行的进程及可访问路由，而崩溃的进程恰好不具备这些条件。容器运行时会保留上一个容器的标准输出（`kubectl logs --previous`），因此崩溃前最后一份报告在事后仍然可读。报告写入时会立即刷新，因为致命信号会带走缓冲区中尚未刷出的输出。

#### 读取报告 {#reading-the-report}

每份报告首先列出从 `/proc` 读取的逐线程 CPU 数据；这张表是权威数据，因为性能分析器开销无法扭曲它们，因此两者出现分歧时应以 `/proc` 为准。该表也能显示工作分布在多个事件循环中，还是集中于某一个循环。

若忽略以下三点，可能会得出错误结论：

- **`tottime` 是函数本身消耗的 CPU 时间；`cumtime` 还包括它调用的所有函数。** `cumtime` 排名靠前的协程可能只是在等待。一次按 `cumtime` 排序的结果将某 ASGI 中间件归因于 77% 的事件循环 CPU；移除它后，吞吐量却只改变了 13%。
- **cProfile 会让吞吐量大约减半，并过度计入调用频繁的函数。** 应关注排名而非毫秒数；要确认关键瓶颈，请只改动一项并重新测量。
- **数值是每个时间窗口内的增量。** 每份报告表示从上一份报告以来的变化，而非自启动起的累计值。

#### 限制 {#limits}

性能分析是进程级且只能单实例运行：从 Python 3.12 起，性能分析器是全局监控工具，因此进程中不能同时运行其他性能分析器（第二次尝试会记录 `tool 2 is already in use` 并保持关闭）。若能附加到进程，`py-spy` 仍是更好的工具；此功能则适用于无法附加的情形。

### 分层配置 {#hierarchical-configuration}

Hindsight 通过分层系统支持按银行覆盖配置：**全局（环境变量）→ 租户 → 银行**。

#### 类型安全的配置访问 {#type-safe-config-access}

为防止存在银行级覆盖时误用全局默认值，Hindsight 强制以类型安全的方式访问配置：

**在应用代码中：**
```python
from hindsight_api.config import get_config

# ✅ Access static (infrastructure) fields
config = get_config()
host = config.host  # OK - static field
port = config.port  # OK - static field

# ❌ Attempting to access bank-configurable fields raises an error
chunk_size = config.retain_chunk_size  # ConfigFieldAccessError!
```

**Error Message:**
```
ConfigFieldAccessError: Field 'retain_chunk_size' is bank-configurable and cannot
be accessed from global config. Use ConfigResolver.resolve_full_config(bank_id, context)
to get bank-specific config.
```

**For Bank-Specific Config:**
```python
# Internal code that needs bank-specific settings
from hindsight_api.config_resolver import ConfigResolver

# Resolve full config for a specific bank
config = await config_resolver.resolve_full_config(bank_id, request_context)
chunk_size = config.retain_chunk_size  # ✅ Uses bank-specific value
```

此设计可防止误用全局默认值而非银行覆盖，让这种错误在编译/开发阶段就无法发生。

#### 安全模型 {#security-model}

配置字段按安全属性分类：

1. **可配置字段**——可按银行自定义的安全行为设置：
   - 保留：`retain_chunk_size`、`retain_structured_chunk_size`、`retain_extraction_mode`、`retain_mission`、`retain_custom_instructions`
   - 观测：`enable_observations`、`enable_auto_consolidation`、`observations_mission`、`max_observations_per_scope`
   - MCP 访问控制：`mcp_enabled_tools`

2. **凭据字段**——绝不通过 API 公开或允许配置：
   - API 密钥：`*_api_key`（所有 LLM API 密钥）
   - 基础设施：`*_base_url`（所有基础 URL）

3. **静态字段**——只能在服务器级设置，无法覆盖：
   - 基础设施：`database_url`、`port`、`host`、`worker_count`
   - 提供方/模型选择：`llm_provider`、`llm_model`（需使用尚未实现的预设功能）
   - 性能调优：`llm_max_concurrent`、`llm_timeout`、检索设置、优化标志

#### 并发配置写入 {#concurrent-config-writes}

对同一银行的配置写入会串行执行。校验和持久化作为整体进行：写入操作会锁定银行行，按当时已提交的覆盖值重新校验更新，之后才合并。这样两个请求不会组合出一个两者都未校验过的配置，例如一个请求提高 `retain_chunk_size`，另一个请求移除原本允许该尺寸的存入策略。

无需处理冲突状态，也无需实现重试。竞争失败的请求会收到与两个更新依次到达时相同的 `400` 校验错误；如果请求字段符合更新后的状态，则会成功。彼此无约束关系的字段会分别合并，因此互不相关的并发更新都会保留。

#### 启用 API {#enabling-the-api}

| 变量 | 说明 | 默认值 |
|---|---|---|
| `HINDSIGHT_API_ENABLE_BANK_CONFIG_API` | 允许客户端更改银行级配置（`PATCH` / `DELETE .../config`）。始终允许读取银行配置。 | `true` |
| `HINDSIGHT_API_ENABLE_BANK_LLM_HEALTH` | 启用银行级 LLM 连接探测（`POST /v1/default/banks/{bank_id}/health/llm`）。会真实调用提供方，因此**默认关闭**；启用后才开放端点。只返回状态，不返回提供方/模型/端点信息。 | `false` |
| `HINDSIGHT_API_ENABLE_DRY_RUN_EXTRACT` | 启用提取试运行预览端点（`POST /v1/default/banks/{bank_id}/memories/dry-run-extract`）。只执行提取，会真实调用 LLM，但不存储任何内容。设为 `false` 会移除端点（返回 `404`）。 | `true` |
| `HINDSIGHT_API_DEFAULT_BANK_TEMPLATE` | 自动应用于每个新银行的银行模板清单（JSON）。见下文。 | （未设置） |

##### `HINDSIGHT_API_DEFAULT_BANK_TEMPLATE` {#hindsight_api_default_bank_template}

服务器级默认银行模板。设置后，清单会应用于服务器创建的每个银行一次，并在首次访问银行时触发（例如通过 `PUT /v1/default/banks/{bank_id}`、`/import`、`/retain`）。其值是 JSON 编码的 `BankTemplateManifest`，结构与 `POST /v1/default/banks/{bank_id}/import` 接受的内容一致（参见银行模板 API 中的 `bank`、`mental_models` 和 `directives` 部分）。

优先级：模板字段会成为银行级覆盖值，优先于相应的 `HINDSIGHT_API_*` 环境变量默认值（如 `HINDSIGHT_API_RETAIN_EXTRACTION_MODE`）。用户之后仍可通过 `PATCH /v1/default/banks/{bank_id}/config` 覆盖单个字段。后续访问时**不会**重新应用模板，因此不会覆盖显式设置。

清单无效（JSON 格式错误、版本未知、schema 错误）时会记录日志并忽略；银行仍使用普通默认值成功创建，服务器级设置故障不会让所有调用方都无法使用。

示例（环境变量要求使用紧凑的单行 JSON）：

```bash
export HINDSIGHT_API_DEFAULT_BANK_TEMPLATE='{"version":"1","bank":{"reflect_mission":"Help support agents remember customer interactions.","retain_extraction_mode":"verbose","disposition_empathy":5},"directives":[{"name":"Be concise","content":"Always respond concisely.","priority":10}]}'
```

#### API 端点 {#api-endpoints}

- `GET /v1/default/banks/{bank_id}/config` — 查看解析后的配置（按权限过滤）
- `PATCH /v1/default/banks/{bank_id}/config` — 更新银行覆盖值（仅限允许的字段）
- `DELETE /v1/default/banks/{bank_id}/config` — 重置为默认值

### 反向代理 / 子路径部署 {#reverse-proxy--subpath-deployment}

要将 Hindsight 部署在子路径下（例如 `example.com/hindsight/`）：

1. 将两个环境变量设为相同路径：
   ```bash
   HINDSIGHT_API_BASE_PATH=/hindsight
   NEXT_PUBLIC_BASE_PATH=/hindsight
   ```

2. 配置反向代理：
   - 将 `/hindsight/*` 请求转发到 Hindsight。
   - 保留转发请求中的完整路径。
   - 设置适当的代理标头（X-Forwarded-Proto、X-Forwarded-For）。

**Nginx 配置示例**

```nginx
location /hindsight/ {
    proxy_pass http://localhost:8888/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

**Traefik 配置示例**

```yaml
http:
  routers:
    hindsight:
      rule: "PathPrefix(`/hindsight`)"
      service: hindsight
      middlewares:
        - hindsight-stripprefix

  middlewares:
    hindsight-stripprefix:
      stripPrefix:
        prefixes:
          - "/hindsight"

  services:
    hindsight:
      loadBalancer:
        servers:
          - url: "http://localhost:8888"
```

**重要说明：**
- 基础路径必须以 `/` 开头，且不应以 `/` 结尾。
- API 和控制平面应使用相同基础路径。
- 设置环境变量后需重启两个服务。
- OpenAPI 文档可通过 `<base-path>/docs` 访问（例如 `/hindsight/docs`）。
