心智模型如何刷新

Hindsight 中的每个知识页，都是一个会改写自身内容的心智模型。本文逐步对照当前代码，追踪整个流程：模式选择、七个阶段、每条分支，以及四种结果。

刷新被有意拆分成两部分。_execute_mental_model_refresh 执行完整流程，不写入任何内容，而是返回一个 _MentalModelRefreshRun，记录它作出的每项决策。refresh_mental_model 将这次运行持久化；dry_run_refresh_mental_model 报告运行情况后将其丢弃。这里有意不提供任何让执行器在预览时采取不同行为的标志，因为如果预览可以另行配置，它就无法再预测自己本应预测的那次刷新。

1 · 一次刷新的整体流程

七个阶段依次执行。阶段 1–4 无条件执行：即使是纯粹的完整重建刷新，也会确定范围、获取快照并调用 Reflect（反思）。所有分支都发生在阶段 5 和 6。

2 · 阶段 2：模式门控

请求 delta 模式，并不意味着最终就会使用它。requested_mode 来自触发器：知识页使用 KNOWLEDGE_PAGE_DEFAULT_TRIGGER，其中设置了 mode: "delta"，因此每个页面默认都请求增量编辑。随后由三道门控决定是否继续使用请求的模式。

补充说明

门控 2 不仅在 last_refreshed_source_query 与当前查询相同时通过，在它为 NULL 时也会通过。这是有意为之：先手写页面、随后再开启 delta 模式的人，期望自己的文字作为编辑起点，而不是被一次完整重建丢弃。

3 · 阶段 5：增量编辑分支内部

值得关注的失败情况发生在这里。此分支需要一份基线文档供其编辑，在放弃之前，会按顺序尝试两个来源。

4 · 阶段 6：保护检查

候选内容写入数据库之前，要先经过两项保护检查，最后再进行一次转换。

  • 渲染结果为空。如果 final_content 为空，刷新就会失败。较小的模型、各级重试均已耗尽，或者清理答案的正则表达式匹配过度，都可能产生空答案；将其写入会破坏原本可用的文档。
  • 增量窗口候选内容。如果请求了增量编辑却未能应用，final_content 仍是 Reflect 候选内容；该内容是在 created_after 限制下综合生成的，因此只涵盖上次刷新之后的新记忆。写入它会悄然删除文档从较早记忆中获得的全部知识，同时将水位推进到这些记忆之后。这项保护以窗口为判断依据，而不是分别针对各条失败分支，因此未来新增的分支也会受到它的保护。
  • 初始化基线。如果 final_structured 仍为 None——每次完整重建刷新以及每次失败的增量编辑都是如此——就会解析候选 Markdown，为下次刷新提供可编辑的内容。
表格缺陷曾出现的位置

最后这一步会丢失信息。它在每次完整重建刷新时执行；直到最近，对于无法识别的 Markdown 表格，它仍会把内容用空格拼成一个段落，整张表格被挤在同一行上。由于这种拼接是幂等的，下次刷新会把这份损坏内容重新当作普通文本解析，再次输出，页面因而始终无法恢复。

5 · 阶段 7：实际写入哪些内容

结果的字面值决定了持久化的全部行为。四种结果中有两种会先记录失败供审计，再抛出 MentalModelRefreshError。

结果 content structured_content 水位 抛出异常 原因
content_written 写入 写入 推进 否 正常路径，full 和 delta 模式均适用。
content_preserved_no_new_facts 不变 不变 推进 否 窗口内没有新内容。水位仍会推进，避免再次读取这个空窗口。
refresh_failed_empty_candidate 不变 不变 保持不变 是 几乎总是上游 LLM 失败所致。保持水位不变，意味着重试时会重新读取同一窗口。
refresh_failed_delta_not_applied 不变 不变 保持不变 是 候选内容只涵盖增量窗口，因此不能作为一份完整文档。

持久化本身还可能发生第五种失败：触发器携带 response_schema 时，已存内容会被映射为 structured_output。如果提取失败，整个刷新都会判为失败，避免在持久化内容的同时，保留一份落后于它的机器可读视图。

边界情况

只有设置了 created_after，增量窗口保护才会生效。没有 last_refreshed_at 的心智模型会直接继续执行，将候选内容作为完整文档写入；这是合理的，因为基于完整历史读取而生成的候选内容就是一份文档。实际上，该列设有 NOT NULL 约束，默认值为创建时间，因此增量编辑刷新始终带有窗口。

6 · Markdown 在何处转为结构

这张图是作出设计决策的关键。增量编辑 LLM 从不接触 Markdown；传入的是 current_doc.model_dump_json()，它则以带类型的内容块作答。Markdown 进入结构化表示的入口恰好有三处，其中两处位于刷新的常规执行路径上。

7 · 用图展示主次反转方案

尚待决定的问题是：是否应让 structured_content 成为权威数据源，在读取时再渲染 Markdown。下图展示两者的区别。差异比乍看时更小，因为 Hindsight 在增量编辑路径上已经是这样工作的。

主次反转方案仍需保留什么

  • content 列。search_knowledge_pages 对页面名称和内容上的 BM25 检索结果进行融合，并返回内容片段。必须持续保存渲染后的形式，因此，解析器问题会转变为映射结果的同步问题。
  • 解析器。create_knowledge_page 接受客户端提交的 Markdown，导入也会恢复 Markdown 正文。这两者仍需要 Markdown → 结构转换。
  • 模式的表达上限。只有五种内容块类型，图像和原始 HTML 明确不在支持范围内。在主次反转方案下，未建模的内容在摄取时就无法表示，而不是稍后才降级。这或许更好，因为失败发生在有人能够处理它的环节。

两种方案都无法修复已经损坏的页面：被压成一行的表格只有一个物理行，而识别表格至少需要两行。无论最终选择哪个方向，回填修复都需要另行处理。
