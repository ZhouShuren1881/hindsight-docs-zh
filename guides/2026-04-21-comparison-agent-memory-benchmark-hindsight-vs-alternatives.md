如果你在寻找**智能体记忆基准**，最值得问的问题不是哪个工具在演示中听起来最聪明，而是哪种记忆架构能在简单捷径失效后继续工作。智能体的历史记录一旦足够庞大，把内容塞进上下文就不再是策略，而会碰到物理上限。

这正是 BEAM 的意义所在。在 1,000 万 token 档位，现有上下文窗口都无法容纳完整历史。系统要么从记忆中检索到正确的信息，要么就会失败。在这种情况下，Hindsight 的已公布成绩最高，而且差距足以说明架构本身的作用，而非只是提示词调优。

本文梳理已公布的 BEAM 数据，比较 Hindsight 与 Honcho、LangChain 式记忆以及自定义检索方案，并说明生产环境中真正重要的取舍。如果你想了解这些结果背后的检索机制，可以同时参考[文档首页](/)、[Hindsight 的记忆召回 API](/developer/api/recall)和[快速入门指南](/developer/api/quickstart)。

## 简要结论 {#the-short-version}

已公布的 BEAM 10M 基准档位成绩如下：

| 系统 | 已公布的 10M 分数 |
|---|---:|
| RAG 基线 | 24.9% |
| LIGHT 基线 | 26.6% |
| Honcho | 40.6% |
| **Hindsight** | **64.1%** |

到了这个基准档位，捷径已经行不通：你无法把 1,000 万 token 全部放进上下文，因此需要真正的记忆系统。

## 为什么 BEAM 值得关注 {#why-beam-is-the-benchmark-to-watch}

早期的记忆基准诞生于 32K 上下文窗口还是常见上限的时期。当时这样设计完全合理：对话或语料放不进上下文时，记忆系统就必须检索其中有用的部分。

如今情况不同了。大型模型能容纳更多内容，因此较小规模的基准常常把两种截然不同的设计混为一谈：

- 具备真正长期记忆的系统
- 主要把大量文本直接塞进上下文的系统

BEAM 的价值就在于，它设置了一些规模档位，让暴力回退方案不再奏效。

| 档位 | 实际测试内容 |
|---|---|
| 100K | 系统能否做到合理的检索效果 |
| 500K | 数据量增长后，检索质量能否保持 |
| 1M | 架构能否扩展到常见工作上下文窗口之外 |
| **10M** | **系统是否称得上真正的记忆系统** |

在 10M token 档位，把内容塞满上下文不再是一种取舍，而是根本做不到。

基准的背景和方法见[智能体记忆基准：一份宣言](/blog/2026/03/23/agent-memory-benchmark)和 [Hindsight 在 BEAM 中排名第一](/blog/2026/04/02/beam-sota)。

## 已公布的结果 {#the-published-results}

已公布的 10M 结果清楚呈现了架构上的差距。

| 系统 | 检索方式 | 已公布的 10M 分数 |
|---|---|---:|
| RAG 基线 | 对文本分块进行向量检索 | 24.9% |
| LIGHT 基线 | 另一种记忆基线 | 26.6% |
| Honcho | 以用户建模为重点的记忆 | 40.6% |
| **Hindsight** | 结构化记忆 + 多策略检索 | **64.1%** |

各档位公布的完整结果也呈现出一致的趋势：

| 档位 | Hindsight | Honcho | LIGHT | RAG |
|---|---:|---:|---:|---:|
| 100K | **73.4%** | 63.0% | 35.8% | 32.3% |
| 500K | **71.1%** | 64.9% | 35.9% | 33.0% |
| 1M | **73.9%** | 63.1% | 33.6% | 30.7% |
| 10M | **64.1%** | 40.6% | 26.6% | 24.9% |

这并不意味着每种工作负载都该使用 Hindsight；但这说明，当规模成为决定性限制时，Hindsight 目前有最强的已公布证据表明它能保持记忆质量。

## Hindsight 为何能拉开差距 {#why-hindsight-pulls-away}

关键差异不是某个单独技巧，而是整套检索流程。

Hindsight 不会把记忆当成一堆语义相似的文本分块。它会保留结构化事实、解析实体、跟踪时间信息，并并行使用多种策略进行检索：

- 语义搜索
- BM25 关键词搜索
- 图遍历
- 时间检索
- 对融合后的结果集进行交叉编码器重排序

[检索架构指南](/developer/retrieval)介绍了这套流程，[Hindsight 的记忆召回 API](/developer/api/recall)则直接提供了相应能力。

这一点很重要，因为实际的记忆查询往往很复杂。智能体提出的问题不只有语义问题，还包括：

- 精确名称查询
- 有时间范围限制的查询
- 多跳查询
- 涉及矛盾历史的查询

单次向量检索很难应对其中好几类问题。更丰富的检索流程能在记忆量增长时，避免回答质量大幅下滑。

## 常见替代方案对比 {#how-common-alternatives-compare}

### Hindsight {#hindsight}

如果你需要以下能力，Hindsight 会很适合：

- 跨会话持久记忆
- 感知实体的检索
- 时间推理
- 多个智能体或工具共享记忆
- 已公布的大规模基准证据

需要权衡的是：

- 系统复杂度高于精简的向量存储
- 相比单纯的文本分块搜索，结构化存入和检索带有更多内置设计取舍

### Honcho {#honcho}

Honcho 值得关注，因为它特别重视用户建模和跨会话对齐。对于需要长期积累对用户的理解的助手，这会很有用。

不过，在已公布的 BEAM 10M 档位中，Hindsight 大幅领先。如果你主要评估的是严格上下文限制下的大规模智能体记忆检索，Hindsight 目前的已公布成绩更好。

### LangChain 式记忆栈 {#langchain-style-memory-stacks}

这一类涵盖了许多实际部署方案：对话摘要、向量存储、窗口缓冲区、检索器，以及围绕它们搭建的自定义编排。

它的优势是灵活，你可以按需组合组件。

不足之处在于，常见的默认模式依然是文档检索，而非智能体记忆。你往往需要自行重建 Hindsight 已经内置的功能：

- 支持嵌入检索之外的精确匹配
- 时间推理
- 实体链接
- 重排序
- 共享记忆库的运维设计

LangChain 是一个框架，Hindsight 是一个记忆系统，两者并非同一类产品。

### 自定义记忆方案 {#custom-memory-solutions}

对于约束特殊的团队，自定义方案完全可能是正确选择。如果你的工作负载有专门需求、有私有评估框架，也有人手负责维护，自建系统就可能胜出。

不过，自定义记忆系统在架构图上往往比在生产环境中表现得更好。隐藏成本确实存在：

- 评估结果逐渐偏移
- 检索效果退化
- 排序行为难以调试
- 基础设施日趋庞杂
- 记忆质量下降时，责任归属不清

基准要回答的问题不只是“我们能不能构建一个系统？”，还包括“系统增长后，我们能不能继续保持准确？”。

## 实际使用场景对比 {#real-world-use-case-comparison}

| 使用场景 | Hindsight | Honcho | LangChain 式技术栈 | 自定义技术栈 |
|---|---|---|---|---|
| 长期运行的编码智能体 | 很适合 | 可行 | 通常需要更多组件组合 | 取决于团队 |
| 带用户建模的个人助手 | 很适合 | 很适合 | 适配程度中等 | 取决于设计 |
| 多智能体共享记忆 | 很适合 | 适配程度中等 | 增加额外工作后可行 | 增加额外工作后可行 |
| 有时间感知能力的召回 | 很适合 | 默认能力不明确 | 通常需要额外逻辑才能做好 | 取决于实现 |

| 已公布的规模测试证据 | 强 | 中等 | 通常没有可直接使用的整套方案数据 | 通常仅有私有数据 |

## 基准无法告诉你的事 {#what-the-benchmark-does-not-tell-you}

基准很重要，但产品决策还要考虑其他方面。

优秀的记忆系统还需要：

- 易于运维
- 易于调试
- 费用可承受
- 易于集成
- 故障时表现可预测

因此，最好结合架构和 API 文档来阅读基准数据。[记忆存入 API](/developer/api/retain)和[记忆召回 API](/developer/api/recall)比单看黑盒分数更能帮助你理解系统的底层模型。

## 何时选择 Hindsight {#when-to-pick-hindsight}

以下情况下可以选择 Hindsight：

- 智能体需要跨会话记忆，而不只是单次对话中的记忆
- 历史记录大幅增长后，检索仍需保持有效
- 时间感知和实体感知召回很重要
- 多个工具或智能体需要共享同一记忆层
- 你希望使用的系统在有意义的规模上有公开基准证据

[AI 编码智能体的团队共享记忆【无效博客链接】](https://hindsight.vectorize.io/blog/team-shared-memory-ai-coding-agents)介绍了相关模式：它的价值在于跨工具和会话累积上下文，而不必一遍遍重新解释所有背景。

## 何时简单方案已经足够 {#when-a-simpler-option-is-enough}

不要过度设计。

如果你的工作负载主要是针对静态语料进行文档问答，经典 RAG 可能就够了。如果智能体有意设计为无状态，持久记忆可能只会带来不必要的复杂性。如果短期工作流只需要滚动摘要，轻量记忆层也完全合理。

重点不是每个系统都需要 Hindsight，而是：如果你需要智能体具备真正的长期记忆，就应当在记忆确实经受考验的规模下评估基准证据。

## 总结 {#bottom-line}

智能体记忆基准的情况终于逐渐明朗。

在较小规模下，许多系统看起来相差无几；规模变大后，架构的差异便显现出来。BEAM 的 10M 档位是目前我们用来区分两者的最佳公开测试，Hindsight 在该档位的已公布成绩最高。

这并未结束讨论，却改变了默认的讨论方向：记忆系统已经不必再证明自己有用，接下来需要证明的是，替代方案在上下文窗口耗尽后仍然有效。
