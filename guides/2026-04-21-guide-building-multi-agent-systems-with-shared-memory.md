**多智能体记忆**听起来简单，真正构建时却很复杂。一个智能体学到有用信息，另一个应受益，第三个可能不该看到。加入用户、团队、工具和环境后，“共享记忆”不再只是功能选项，而成为架构问题。

多数多智能体系统因此共享过度或不足：要么所有内容进入一个嘈杂池，召回混乱；要么每个智能体成为孤岛，知识无法积累。正确方式是有意识地设计共享上下文模型，以记忆库边界、严格存储原则和支持跨会话的检索为基础。

本指南介绍实际可用的模式，包括按团队记忆、按用户隔离、项目范围记忆库，以及部分共享、部分本地的混合布局。底层机制可参考[文档首页](/)、[快速入门指南](/developer/api/quickstart)、[Hindsight 记忆存储 API](/developer/api/retain)和 [Hindsight 记忆召回 API](/developer/api/recall)。

## 核心思路 {#the-core-idea}

多智能体系统的记忆边界必须对应真实协作边界。

通常需要决定以下各层应该共享什么：

- 用户。
- 项目。
- 团队。
- 环境。
- 工具或智能体角色。

边界错误，记忆层的行为也会不符合预期。

## 共享记忆实际用于什么 {#what-shared-memory-is-actually-for}

智能体处理同一大任务的不同部分时，共享记忆最有价值。

例如：

- 研究智能体收集材料，写作智能体生成草稿。
- 支持智能体记录用户问题，跟进智能体处理升级。
- 一个编码智能体调查，一个实现，一个审查。
- Hermes 助手和 OpenClaw 工作流使用同一用户或项目上下文。

这些场景的价值都来自跨会话和角色积累知识。

[我使用的每个 AI 工具共用一份记忆](/blog/2026/04/07/one-memory-for-every-ai-tool)从用户角度介绍共享模式，本指南关注其背后架构。

## 第一个设计决策：记忆库边界是什么？ {#the-first-design-decision-what-is-the-bank-boundary}

这是最重要的选择。

### 方案 1：每个用户一个记忆库 {#option-1-one-bank-per-user}

适合：

- 多个智能体服务同一人。
- 每个用户需要跨工具延续。
- 绝不能发生跨用户泄漏。

适用场景：

- 个人助手。
- 面向客户的支持系统。
- 多工具个人工作流。

### 方案 2：每个项目一个记忆库 {#option-2-one-bank-per-project}

适合：

- 多个智能体协作同一项目。
- 项目约定和决策应跨角色延续。
- 工作本身比用户身份更重要。

适用场景：

- 编码团队。
- 研究工作流。
- 长期内部计划。

### 方案 3：每个团队一个记忆库 {#option-3-one-bank-per-team}

适合：

- 整个团队应从共享运维知识受益。
- 存在共同领域和同一信任边界。
- 可以接受跨项目共享。

适用场景：

- 内部支持智能体。
- 平台工程团队。
- 共同操作指南和运行手册。

### 方案 4：混合 {#option-4-hybrid}

这通常才是实际答案。

例如：

- 用户专用记忆库保存个人上下文。
- 项目记忆库保存工作上下文。
- 可选的团队共享记忆库保存通用实践。

这样同时获得个性化和跨智能体协作收益。

## 常见隔离模式 {#common-isolation-patterns}

通常最有效的模式如下。

| 模式 | 内部共享范围 | 隔离边界 | 适合场景 |
|---|---|---|---|
| 按用户 | 服务同一用户的全部智能体 | 用户 | 助手、支持 |
| 按项目 | 同一项目的全部智能体 | 项目 | 软件、研究 |
| 按团队 | 同一团队的全部智能体 | 团队 | 内部运维 |
| 按用户和项目 | 一个用户在一个项目中的工作 | 用户和项目 | 咨询、客户工作 |
| 共享与本地混合 | 共享项目知识及角色本地记忆 | 取决于设计 | 复杂多智能体系统 |

简单原则：只有参与者确实应互相学习时，才默认共享。

## 实用架构 {#a-practical-architecture}

清晰的共享记忆配置通常如下：

```text
                ┌──────────────────────────────┐
                │         Hindsight            │
                │  记忆库：project-acme-api    │
                └──────────────┬───────────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
┌───────▼───────┐      ┌───────▼───────┐      ┌───────▼───────┐
│  研究智能体   │      │  实现智能体   │      │  审查智能体   │
└───────────────┘      └───────────────┘      └───────────────┘
```

三个智能体共享记忆库，因为它们都在为同一项目贡献。

更复杂的布局可能如下：

```text
user:alice          project:acme-api        team:platform
    │                     │                     │
    └──── 本地智能体 ─────┼──── 共享智能体 ───┘
```

这种设计中，智能体可根据产生的知识类型，向多个概念层存储。

## 应该共享什么 {#what-should-be-shared}

适合共享记忆的内容：

- 架构决策。
- 已接受的约定。
- 反复出现的故障模式。
- 部署经验。
- 项目里程碑。
- 所有相关智能体都应遵守的用户偏好。

不适合广泛共享的内容：

- 嘈杂的中间推理。
- 无人重用的一次性草稿。
- 超出预定边界的敏感个人细节。
- 智能体本地临时工作。

存储具有选择性而非追求最多时，共享记忆更强。

## Hindsight 如何提供帮助 {#how-hindsight-helps-here}

Hindsight 不限于文本块的语义相似性。它存储结构化事实并使用多种策略检索，因此适合不同智能体提出不同形态的问题。

一个可能语义搜索，另一个需要精确词语，第三个需要有时间范围的事件链。同一共享记忆库可以支持它们，因为召回结合：

- 语义检索。
- BM25 关键词检索。
- 图遍历。
- 时间检索。
- 对合并结果集重排序。

[召回架构指南](/developer/retrieval)介绍这种检索模型。

## 实际示例 {#real-world-examples}

### 具有专门智能体的支持团队 {#support-team-with-specialist-agents}

分诊智能体识别问题，计费智能体处理账户状态，跟进智能体发送摘要和后续步骤。

此处按用户记忆库很合适。各专员利用彼此存储的上下文，同时不会混合不同客户。

### 按角色分工的编码流程 {#coding-workflow-with-role-based-agents}

研究智能体探索方案，编码智能体实现，审查智能体检查最终改动。

通常按项目记忆库合适。重点是积累项目知识，而非个人身份。

### Hermes 与其他工具入口 {#hermes-plus-other-tool-surfaces}

Hermes 助手和另一智能体都服务同一用户时，可以按用户共享。如果协作同一工程任务，按项目通常更清晰。

## 决策树 {#decision-tree}

使用以下快速规则。

| 问题 | 是 | 否 |
|---|---|---|
| 不同智能体应记住同一用户偏好吗？ | 从按用户记忆开始 | 用户上下文保留在本地 |
| 多个智能体协作同一产物或项目吗？ | 添加按项目记忆库 | 按角色分开 |
| 其他团队看到记忆导致的错误代价高吗？ | 收紧隔离 | 共享记忆库可能可接受 |
| 智能体需要相同运维指南吗？ | 添加团队级记忆库 | 不必广泛共享 |
| 记忆质量变得嘈杂吗？ | 收窄记忆库边界 | 保持当前范围 |

## 常见错误 {#common-mistakes}

### 一个巨大全局记忆库 {#one-giant-global-bank}

起初看似高效，却很快变得嘈杂。

### 没有存储原则 {#no-retention-discipline}

把每轮视为同等重要并全部存储，会让记忆库充斥低价值内容。

### 没有信任模型就共享 {#sharing-without-a-trust-model}

如果无法解释谁应看到什么，记忆库设计就尚未就绪。

### 把检索问题当作存储问题 {#treating-retrieval-problems-as-storage-problems}

即使记忆库包含正确知识，召回薄弱或范围错误仍会让它显得失效。

## 良好的起始模式 {#a-good-starter-pattern}

不确定从哪里开始时，可以采用：

- 团队工作流每个项目一个记忆库。
- 助手工作流每个用户一个记忆库。
- 明确需要前，避免团队级广泛共享。
- 聚焦存储可重用上下文。

这能让多数系统获得稳定初版，同时不过度复杂化。

## 结论 {#bottom-line}

共享记忆不意味着一个巨大的记忆池。

它意味着合适的智能体利用彼此工作，同时不污染应独立的上下文。选好边界、选择性存储、采用超越语义相似性的检索，多智能体记忆就能成为优势，而非噪声来源。
