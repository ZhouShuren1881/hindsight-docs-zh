**多智能体记忆**听起来简单，直到你开始构建它。一个智能体学到有用信息，另一个智能体应该能从中受益，第三个智能体或许不应该看到这些信息。等到你把用户、团队、工具和环境也考虑进来，“共享记忆”就不再只是一个功能选项，而成了架构问题。

因此，多数多智能体系统要么共享过度，要么共享不足。一种情况是所有内容都进入同一个嘈杂的信息池，召回也变得混乱；另一种情况是每个智能体各自为政，知识无法积累。正确做法是有意识地设计智能体共享上下文模型，以记忆库边界、存入原则，以及能够支持跨会话工作的检索为基础。

本指南介绍经过实践检验的模式，包括按团队共享记忆、按用户隔离、使用项目范围的记忆库，以及部分知识共享、部分保留在本地的混合布局。阅读时如需了解底层机制，可以同时查看[文档首页](/)、[快速入门指南](/developer/api/quickstart)、[Hindsight 记忆存入 API](/developer/api/retain)和 [Hindsight 记忆召回 API](/developer/api/recall)。

## 核心思路 {#the-core-idea}

多智能体系统需要让记忆边界与实际协作边界相匹配。

通常，这意味着要决定在以下各个层级中应该共享什么：

- 用户。
- 项目。
- 团队。
- 环境。
- 工具或智能体角色。

如果这些边界设错了，记忆层的表现也会不符合预期。

## 共享记忆究竟有何用途 {#what-shared-memory-is-actually-for}

当多个智能体分别处理同一项更大任务中的不同部分时，共享记忆最有价值。

例如：

- 研究智能体收集材料，写作智能体将材料整理成草稿。
- 支持智能体记录用户问题，跟进智能体处理升级的问题。
- 一个编码智能体调查问题，另一个负责实现，还有一个负责审查。
- Hermes 助手和 OpenClaw 工作流使用同一用户或项目上下文。

在这些场景中，价值都来自跨会话、跨角色积累知识。

[我使用的每个 AI 工具共用一份记忆](/blog/2026/04/07/one-memory-for-every-ai-tool)从用户视角介绍了共享记忆模式。本指南关注其背后的架构。

## 第一个设计决策：记忆库边界是什么？ {#the-first-design-decision-what-is-the-bank-boundary}

这是你要做的最重要的选择。

### 方案 1：每个用户一个记忆库 {#option-1-one-bank-per-user}

适用于以下情况：

- 多个智能体服务同一个人。
- 每个用户都需要跨工具保持上下文连续。
- 必须绝不发生用户之间的信息泄漏。

适合：

- 个人助手。
- 面向客户的支持系统。
- 使用多种工具的个人工作流。

### 方案 2：每个项目一个记忆库 {#option-2-one-bank-per-project}

适用于以下情况：

- 多个智能体协作同一个项目。
- 项目约定和决策应该延续到不同角色的工作中。
- 与用户身份相比，工作流更重要。

适合：

- 编码团队。
- 研究工作流。
- 长期开展的内部计划。

### 方案 3：每个团队一个记忆库 {#option-3-one-bank-per-team}

适用于以下情况：

- 整个团队都应该受益于共享的运维知识。
- 团队处在同一领域内，并且具有相同的信任边界。
- 可以接受跨项目的信息泄漏。

适合：

- 内部支持智能体。
- 平台工程团队。
- 共用的操作指南和运行手册。

### 方案 4：混合模式 {#option-4-hybrid}

实际情况往往需要采用这种方案。

例如：

- 用用户专属记忆库保存个人上下文。
- 用项目记忆库存放工作上下文。
- 可选地使用团队共享记忆库存放通用实践。

这样既能实现个性化，也能让智能体之间共享协作成果。

## 常见隔离模式 {#common-isolation-patterns}

以下模式通常效果最好。

| 模式 | 内部共享范围 | 跨越什么进行隔离 | 适合场景 |
|---|---|---|---|
| 按用户 | 服务同一用户的所有智能体 | 用户之间 | 助手、支持 |
| 按项目 | 同一项目中的所有智能体 | 项目之间 | 软件、研究 |
| 按团队 | 同一团队中的所有智能体 | 团队之间 | 内部运维 |
| 按用户和项目 | 一个用户在一个项目中的工作 | 用户和项目之间 | 咨询、客户项目 |
| 共享与本地混合 | 共享项目知识，加上角色专属的本地记忆 | 视设计而定 | 复杂的多智能体系统 |

可以用一个简单的思路来理解：默认只在确实应该相互学习的参与者之间共享。

## 实用架构 {#a-practical-architecture}

一种清晰的共享记忆配置通常如下所示：

```text
                ┌──────────────────────────────┐
                │         Hindsight            │
                │   记忆库：project-acme-api   │
                └──────────────┬───────────────┘
                               │
        ┌──────────────────────┼──────────────────────┐
        │                      │                      │
┌───────▼───────┐      ┌───────▼───────┐      ┌───────▼───────┐
│ 研究智能体    │      │ 构建智能体    │      │ 审查智能体    │
└───────────────┘      └───────────────┘      └───────────────┘
```

这三个智能体共享同一个记忆库，因为它们都在为同一个项目作贡献。

更复杂的布局可能如下所示：

```text
user:alice          project:acme-api        team:platform
    │                     │                     │
    └──── 本地智能体 ─────┼──── 共享智能体 ───┘
```

在这种设计中，智能体可以根据所生成知识的类型，将内容存入多个概念层级。

## 应该共享什么 {#what-should-be-shared}

适合共享记忆的内容：

- 架构决策。
- 已采纳的约定。
- 反复出现的故障模式。
- 部署经验。
- 项目里程碑。
- 所有相关智能体都应该遵守的用户偏好。

不适合广泛共享的内容：

- 嘈杂的中间推理过程。
- 无人会重用的一次性草稿。
- 超出预定边界的敏感个人信息。
- 智能体本地的临时工作。

选择性地存入记忆，而不是尽可能多地存入，共享记忆才能更有价值。

## Hindsight 如何提供帮助 {#how-hindsight-helps-here}

Hindsight 适用于多智能体共享记忆，因为它不只依赖文本分块之间的语义相似度。它会存储结构化事实，并通过多种策略进行检索；当不同智能体提出形式各异的问题时，这一点很重要。

一个智能体可能会进行语义检索，另一个可能要查找精确术语，还有一个可能需要按时间范围查找事件链。同一个共享记忆库可以支持这些需求，因为 Recall 会结合：

- 语义检索。
- BM25 关键词检索。
- 图遍历。
- 时间检索。
- 对合并后的结果集进行重排序。

[Recall 架构指南](/developer/retrieval)介绍了这种检索模式。

## 实际示例 {#real-world-examples}

### 由专职智能体组成的支持团队 {#support-team-with-specialist-agents}

分诊智能体识别问题，计费智能体处理账户状态，跟进智能体发送摘要和后续步骤。

按用户划分记忆库很适合这种场景。每个专职智能体都能受益于其他智能体存入的上下文，同时不会把不同客户的信息混在一起。

### 按角色分工的编码工作流 {#coding-workflow-with-role-based-agents}

研究智能体探索方案，编码智能体负责实现，审查智能体检查最终改动。

通常，按项目划分记忆库是合适的。重点在于积累项目知识，而不是个人身份信息。

### Hermes 与其他工具入口 {#hermes-plus-other-tool-surfaces}

如果 Hermes 助手和另一个智能体入口都在为同一用户工作，按用户设置共享记忆库可能合适。如果它们在协作完成同一项工程工作，按项目设置记忆库通常更清晰。

## 决策树 {#decision-tree}

使用以下快速规则：

| 问题 | 如果是 | 如果否 |
|---|---|---|
| 不同智能体是否应该记住同一用户的偏好？ | 从按用户划分记忆开始 | 将用户上下文保留在本地 |
| 多个智能体是否在协作同一产物或项目？ | 添加一个按项目划分的记忆库 | 按角色隔离 |
| 如果另一个团队看到这条记忆，出错的代价会很高吗？ | 加强隔离 | 可以考虑使用共享记忆库 |
| 智能体是否需要同一套运维指南？ | 添加一个团队级记忆库 | 避免广泛共享 |
| 记忆质量是否开始变得嘈杂？ | 收紧记忆库边界 | 保持当前范围 |

## 常见错误 {#common-mistakes}

### 一个巨大的全局记忆库 {#one-giant-global-bank}

一开始看似高效，很快就会变得嘈杂。

### 缺少存入原则 {#no-retention-discipline}

如果把每一轮对话都当作同等重要并存入，记忆库就会塞满低价值内容。

### 没有信任模型就共享 {#sharing-without-a-trust-model}

如果你无法解释谁应该看到什么，记忆库的设计就还没有准备好。

### 把检索问题当成存储问题 {#treating-retrieval-problems-as-storage-problems}

记忆库即使包含正确知识，如果召回效果差或范围设置不当，仍会让人觉得它出了问题。

## 良好的起步模式 {#a-good-starter-pattern}

如果不确定从哪里开始，可以先采用以下做法：

- 团队工作流按项目划分记忆库。
- 助手工作流按用户划分记忆库。
- 在确认确有需要之前，避免团队范围的共享。
- 让存入内容聚焦于可重用的上下文。

这样，多数系统无需让布局过于复杂，就能形成稳定的首个版本。

## 结论 {#bottom-line}

共享记忆不等于把所有内容放进一个巨大的记忆库。

它意味着合适的智能体可以在彼此工作的基础上继续推进，同时不会污染应该保持独立的上下文。只要选好记忆库边界、有选择地存入记忆，并使用支持多种检索方式的检索机制，多智能体记忆就能成为真正的优势，而不是噪声来源。
